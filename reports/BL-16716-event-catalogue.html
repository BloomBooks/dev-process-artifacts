What Bloom 6.5 now records

Seven events, down from twenty-two. Each row is an event, the fields it carries, and the question it exists to answer. The second table is what we decided not to keep, and what that costs us — kept in one place so the choices are reversible on purpose rather than by archaeology.

7events we keep, from twenty-two
38fields across them, from seventy-three
13event names dropped outright
4→2names merged, losing no data

Two fields are on every event and cost nothing per event. BookId is filled in by the analytics/track endpoint, and BrandingProjectName — the subscription descriptor, which also encodes tier, flavour and subscriber — has always ridden on every event as an application property. Neither is listed per row.

The seven we keep

Event Fields it carries The question it answers
Where pictures come from
Image Chooser Closed outcome, acceptedProvider, searchCount, providersTried, providers, pixabayKeyPresent Two fields went with the events they were built for. sessionId tied the searches in a visit to how it ended, and there is now one event per visit for it to tie together. priorChooserSessions was for Pixabay Key Saved — and since Bloom identifies users to Segment, a user’s earlier visits are simply their earlier events, so keeping a durable per-machine counter to say so was not worth it. Dropping it leaves this PR persisting nothing at all on the user’s disk. Did the visit end in a picture, and which source earned it. The most valuable event we have. A result count could never answer this — Pixabay and Openverse nearly always return something, so the failure is a full page of wrong pictures, and only what the user did next reveals it. Proved itself on the first real run: Openverse returned 240 results and none were accepted; Pixabay returned 20 and one was taken.
Change Picture source + provider merged pre-existing event; one field added source One field, not two. Every interesting provider value belonged to a single source — the image chooser — so each is now a first-class source in its own right: pixabay, openverse, a local-collection slug, local-disk, clipboard, ai-editor. Which routes pictures actually arrive by. Both new 6.5 routes bypassed this event entirely, so the old count was quietly low. The repaired count is not the point; the breakdown is. Choosing a picture is essential and we already knew people do it.
The AI Image Editor — the only place real money is spent
AI Image Editor Generatesent by the ai-editor over the bridge tool, model, sourceKind, referenceCount, batch, runsLocally, attemptNumber, result, durationSeconds, costUSD, spentCredits What each generation costs, which models and tools people choose, how often they retry, and how much of it fails. This is the spend. Now the fattest event by a wide margin at eleven fields. referenceCount, batch and runsLocally are the three to drop first if the volume gets uncomfortable — none changes a decision on its own.
AI Image Editor Closed Commit + Cancel merged appliedCount, replacementCount, failedCount, generatedCount, reusedCount, generatedThisSession, historyCount appliedCount of zero is the cancel — no separate event needed. Three questions in one event, because exactly one of these fires per session. Did anything reach the book? A non-zero failedCount is the class of bug BL-16702 was — a commit that silently did nothing. Was AI work thrown away? generatedThisSession against a zero appliedCount is the clearest read we have on whether the output is good enough. And how many sessions were there at all — the count that AI Editor Open used to give. Merging the two events forced a change under the surface. The counts now accumulate and are sent when the session settles — overlay gone, no commit outstanding — rather than as each commit is answered. Reporting per reply would let a session with two commits, one failing and one succeeding, be recorded by whichever answered first, filing a session whose pictures did land as one that discarded everything.
Three things nothing else watches
Cover Layout Changed layout, page The baseline nobody has: how much custom-cover use there is, and on which cover. Two releases of charging for this with nothing to show is a weak position in any pricing conversation. The caveat this row carried is gone: master has since fixed BL-16725, so the endpoint is a “set” rather than a toggle and re-picking the ticked option is not reported at all. A standard event now really does mean someone left a custom layout.
Image Transparency Set from, to, pageBackgroundIsColored, imageFormat, path Which way our line-art detection got it wrong. Opaque means Auto fired when it should not and Bloom was erasing parts of a picture; Transparent means the detector missed line art that plainly is line art. There is no other way to evaluate that heuristic in the field. path — the whole sequence of choices on one picture — is the field to drop if this feels heavy. It exists only to spot someone cycling the options because none of the labels predicted the result.
Publish App Build + Install merged stage, result, elapsedSeconds, errorKind, bookCount, apkSizeMB stage is build or install — one event per stage that finishes, so a build the user never installs still reports its own result and duration. Whether the Reading App Builder toolchain works on real machines, where it breaks, and how long a build takes. CI never runs a real RAB build, so field telemetry is the only continuous coverage this path can have. errorKind is the exception type only — never the Gradle log, which is enormous and full of file paths.

The thirteen we dropped

Written down because a dropped event is cheap to restore and expensive to re-derive. The right-hand column is what we can no longer see — not an argument against the decision, just the receipt for it.

It was designed around the search term, which we were later told not to collect, and without it a query count cannot tell one idea tried in three languages from three different ideas. Two things worth deciding next

There are no denominators, and that is now a decision

The 6.5 Analytics Plan asked for session properties at startup so that every rate would have a bottom half. It named the wrong ones — whether the AI Image Editor is in the build is not a real variable, since a released build always contains it, and the tier is already recoverable from BrandingProjectName.

The one that would have mattered is the experimental-features checkbox: both the AI Image Editor and the App Builder sit behind a per-machine setting in Collection Settings → Advanced, and no event says whether it is on. Sending the enabled tokens was offered and declined for 6.5.

So read the AI and App Builder counts as counts, not rates. In particular, few AI sessions among Pro users will not tell you whether the feature is unwanted or simply undiscovered, and those call for opposite responses.

The plan now contradicts the code in six places

It is shared with the organisation and still reads as current. Most seriously it argues at length for sending search terms, which we were told not to do, so anyone reading it today draws the wrong conclusion about what Bloom collects.

  • Search terms. Argued for at length; term and acceptedTerm are gone.
  • A branding field. Dropped as a duplicate of BrandingProjectName.
  • enteredBy (typed versus pasted) on the Pixabay key. Never built, and close enough to watching keystrokes that it should not be.
  • Image Transparency Reverted never became its own event; path carries it.
  • The AI commit reports from the browser, not C#, because only the browser learns whether the swap landed on the page being edited.
  • And now this trim — two thirds of the plan’s events are not being kept.

Implemented on BL-16716-analytics-trimmed, a fresh branch off master carrying these seven events and nothing else, in eight commits. Every field above was checked against its call site there. The parked BL-16716-analytics keeps the dropped code should any of it be wanted back.

Nothing here has been seen reaching Segment: DEBUG builds run with tracking off, so the log line is the only confirmation available on a developer machine, and each event still needs one pass on alpha.
