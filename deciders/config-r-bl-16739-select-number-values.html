What this PR is about

Purpose

Bloom's new Collection Settings dialog (BL-16739, BloomDesktop #8502) has two dropdowns whose settings are numbers with one named choice: Line spacing and Font size in tools, where 0 means "Auto". A ConfigrSelect could not express that. A labelled option had to have a string value, and any number picked came back as a string, because formik-mui's Select re-set the field from the menu item's text data-value. So a stored 0 never showed as selected.

What the PR does

  • ConfigrSelect binds MUI's Select to the field directly, in place of formik-mui's. Choosing an option stores its value exactly as written, so { value: 0, label: 'Auto' } stores the number 0, and a stored number shows as selected. The '' default, dividers, tooltips, override, enableWhen and validation messages behave as before.
  • It is typed by its options. The value type is inferred from the options' values: string, number, or string | number when they mix. validation and overrideValue take that type.
  • Bare numbers are no longer options; write { value: 12 }. Menu items are keyed by value.
  • The Bloom story uses number options with "Auto" = 0, and the README documents it all.

What changed this run

This run made ConfigrSelect generic on plain MUI per the approved brief (7afe2e6). The light review then found that a value-type parameter, inferred from the first option alone, broke mixed options: a '' default beside numbers, or an enum beside a -- divider. So the select is now generic on its option type, and the value type is widened from all the options (94a6cc2).
