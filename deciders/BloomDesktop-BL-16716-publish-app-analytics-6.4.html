What this PR is about

Problem

Bloom 6.4 ships the App Builder, and reports nothing about it. Whether a real Reading App Builder build actually succeeds for a user, how long it takes, and how it fails are things we currently have no way to see. CI never runs a real App Builder build, so field telemetry is the only continuous coverage this path can ever have — and 6.4 has none. PR #8228 wrote exactly that telemetry, but only on the 6.5 branch, and the App Builder is one of the features that also ships in 6.4.

What the PR does

  • Sends a Publish App event when a build or an install finishes, carrying the stage, whether it succeeded, how long it took, the failure type when it failed, the number of books in the app, and the size of the resulting APK. It is identical to 6.5's event, so data from the two versions is directly comparable. Prepare is fast and local and, as in 6.5, deliberately is not reported.
  • Nothing else from #8228 comes back. The other six events cover features 6.4 does not have, and none of the plumbing travels with this one: no analytics/track endpoint, no front-end trackEvent() helper, no BloomAnalytics wrapper and no commit-time check for it. The event is entirely C#-side, so the whole change is one file.
  • Reporting an event cannot disturb the thing it reports on. The event is sent after the build's own outcome has been settled and shown to the user, and the whole of it — gathering the numbers, sending, and logging — cannot throw. That matters more than it looks: this code runs between “the build finished” and “tell the screen the build finished”, so an escaping exception would leave a successful build looking to the user like a hung one. Both halves of that came out of review.

Two deliberate differences from 6.5

Both are forced by 6.4's code rather than chosen. This branch calls DesktopAnalytics.Analytics.Track directly, as all ~30 of its existing call sites do, with a log line kept alongside so the event can be confirmed on a machine where tracking is off. And there is no "cancelled" result, because 6.4's build and install cannot be cancelled — that code does not exist on this branch.

The commit wants a null merge (-s ours) into master and 6.5, which already carry the real implementation.

Decision 1 · from Greptile

A failed build reports the size of an APK it never built

Every Publish App event carries apkSizeMB, the size of the app file. Bloom works that out by looking for the newest APK sitting in the App Builder project folder. On a build that succeeded that is exactly the right number. On a build that failed, there is no new APK — so if an earlier build had succeeded, Bloom reports that older file's size instead, attached to an event that says the build failed. Nobody sees a wrong number on screen; the cost is that anyone later asking “how big are the apps people build?” gets answers contaminated by failed builds describing artifacts they did not produce.

This is inherited, not introduced: 6.5's version of the event does exactly the same thing, because it calls the same status-reading code. So fixing it here alone would make the two versions disagree on failed builds, which cuts against the “equivalent analytics” goal of the backport.

Decision 2 · tracker hygiene

Should the backport have its own card?

This branch is named for BL-16716, so that is the card preflight used: it posted this PR's link, a 6.4-scoped test-ideas comment, and the link to this report there. But BL-16716 is a Bloom 6.5 board card, currently In Progress, and it already carries two earlier PRs (#8215 and #8228), their test ideas, and their preflight reports. Adding a third release's worth of material makes it a card about two different shipments. Nothing is broken either way — this is about whether the 6.4 work is findable by whoever runs the 6.4 release.

Decision 3 · for information

The extra log line 6.5 gets a different way

6.4 writes one line to the Bloom log for every Publish App event, saying what was reported and — on a build where tracking is off, which is every developer and tester build — that it was not actually sent. On 6.5 the BloomAnalytics wrapper does this for every event; on 6.4 that wrapper does not exist, so the line is written at the one call site instead. It is the only part of this PR that is not a straight port, and it is worth keeping: without it, nobody can tell “the event fired but was not sent” from “the event never fired” short of shipping to alpha, which for a code path CI cannot exercise is the difference between a verifiable change and a hopeful one.
