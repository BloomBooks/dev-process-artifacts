What the branch does now

BloomServer counts workers that report themselves blocked, and uses that count to keep at least one worker able to take a request off the queue — because the request that would let the blocked workers finish is often itself sitting in that queue. In BL-16612 a publish held an api lock for minutes while every other worker waited for the same lock, so nobody was left to serve the page the publish was waiting for, and publishing hung until Bloom was restarted.

Four things were wrong with that mechanism, and all four are fixed:

  • The top-up check only ran when a request arrived, which cannot be enough: if the request that would break the deadlock is already queued, no new one need ever come. It now also runs when a worker becomes blocked, from inside the single method every caller already uses.
  • The off-screen browser never reported its block at all, which is why the check read three blocked against four workers and declined to act.
  • A reported block could leak. Both halves decided whether to count by looking at the thread they happened to be on, so a block whose work contained an await was counted and never uncounted. Reporting now returns a scope that remembers the answer.
  • The shortage was judged against workers that may already be dead, so it could conclude a worker was free when nothing of it remained but a stale entry.

No user-visible behaviour changes, except that the server no longer deadlocks here. Nothing was added to bound how long publishing waits for the browser, retry it, or refuse to publish — those stay off the table, as you decided.

The five tests that hold this in place

All in BloomServerWorkerPoolTests, driving a real listening server.

  • A worker is added when the last free one blocks — and, as the sanity half, is not added while one is still free.
  • Disposing the scope on another thread still undoes the block. This is the one that pins the leak. Verified to fail when the old thread-identity check is put back, so it tests the bug rather than the implementation.
  • Disposing twice only undoes the block once, so a nested using cannot make the server believe workers are free when they are not.
  • A dead worker's entry does not suppress the top-up. Plants a dead thread's entry and asserts a worker is still added. This test is what caught the fast-path gap described opposite.
  • Blocks reported by non-worker threads are ignored entirely — they are not consuming a worker.
