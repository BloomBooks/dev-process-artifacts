Decision 1 of 2

The safeguard counts workers that may already be dead

Devin, new on the final pass · open thread

The test that decides whether to add a helper thread is "are at least as many helpers waiting as there are helpers?" The trouble is what counts as a helper. Bloom keeps an entry for a helper thread even after that thread has died, until a housekeeping pass notices and removes it. So the count can be too high, and the test can conclude a helper is free when all that remains of it is a dead entry — and decline to add one.

This is not new; the same comparison lived in the old code. What is new is that this branch makes that comparison the thing standing between Bloom and the hang, so an inflated count now weakens exactly what we are relying on. And Bloom's own code says helper threads do sometimes die — the housekeeping pass exists because of it.

Two things make it less alarming than it first sounds, and they're the reason I'm not recommending the more invasive option. The housekeeping runs on the thread that accepts incoming connections, which is not blocked during the hang and keeps running, so dead entries are usually cleared quickly. And a missed check is not final: the next reported wait, or the next arriving request, checks again. So this reads as a delay in the safeguard rather than a failure of it.

Decision 2 of 2

My comment for your FYI 1 claimed a guarantee the code doesn't give

Devin, new on the final pass · open thread

You asked me to record, in a comment, that the top-up depends on Bloom's shutdown not disposing two particular wait handles. I did — and the comment went on to say a helper created late in shutdown is harmless because shutdown "merely signals" the stop event, so such a helper wakes immediately and exits.

Devin checked whether that signal actually happens, and it is conditional. The line that signals stop sits inside a test for whether the listener still exists, and there is a public method that closes the listener and clears it — whose own comment says it may run first, from the shutdown timer. On that path the stop event is never signalled at all.

That matters because helper threads are foreground threads: one still waiting keeps the whole process alive, so Bloom would not exit. I verified both halves against the code rather than taking Devin's word — the thread creation does not mark helpers as background, and the close method does clear the listener. Long-standing helpers have always had this exposure; what the top-up adds is the chance of creating a new one inside that window.

I have already corrected the comment, because leaving a note asserting a guarantee the code does not provide is worse than the gap itself — the next person would build on it. What remains is whether to close the gap.
