Decision 1 of 2

A second unsoundness in the same mechanism — one this branch does not fix

Found independently by Devin and by the local review · open thread

Bloom's server counts how many of its helper threads are stuck waiting. Both halves of that bookkeeping — "I am about to wait" and "I have finished waiting" — decide whether to count by looking at the name of the thread they happen to be running on. So the pair only balances when both halves run on the same helper thread.

In ApiRequest.cs:342 they do not. The first half runs on a helper thread, but the matching second half runs after an await. A helper thread carries no synchronization context, so unless that work happened to finish instantly, execution resumes on a completely different thread — whose name is not a helper's — and the count is silently never brought back down. It stays one too high, permanently, every time it happens. The local review traced a real route to it through uploading a book to Bloom Library after a book-id change, and noted that an unexpected error out of that call skips both halves entirely.

This is pre-existing and this branch does not cause it. What the branch does is make it matter more: previously a wrong count only added a helper when a new request arrived, whereas now every reported wait re-checks the count — so a steadily leaking count means a steadily growing set of helper threads that are never retired. It also directly undermines the counter this fix now leans on.

Worth being clear about the shape of the real fix: the lesson is about the contract, not this one call site. A register/unregister pair should not straddle an await, and should not re-ask "am I on a helper thread?" the second time — it should remember what it did the first time. That means the pair returns and consumes a token, which touches every call site and the IBloomServer interface.

Decision 2 of 2

Is this branch the whole fix, or does the bounded wait still follow?

Carried over from our discussion — not a reviewer finding

This branch deliberately contains no time limit on how long publishing will wait for the invisible browser. That was your call, and the reasoning held up: the starvation that actually caused BL-16612 is now addressed at its source, and Devin's own analysis confirms the top-up cascades correctly — each waiting request adds a helper, so the pool keeps up rather than adding one and hoping.

What a time limit would still cover is everything the helper pool cannot touch: the browser's renderer process crashing or being killed, a WebView2 fault, or a script in the page looping forever. In any of those, no number of helper threads helps, and publishing waits for as long as Bloom is open — the original symptom, with no message and every later publish in that session dead too.

The cost is equally real, and it is why 30 seconds was wrong: if the limit is anywhere near legitimate working time, a book that would have finished correctly instead publishes silently wrong — no embedded fonts, content that should have been stripped left in, reported as success. Sized as a liveness detector rather than a work budget (minutes, well clear of any real book), that case effectively disappears while the protection remains.

For your information

The top-up can start a helper thread while Bloom is shutting down

Devin, informational — not mirrored to the PR

The old check lived where requests arrive, and that code already gave up once the listener had closed, so it never ran during shutdown. The new check has no such guard, and a helper part-way through a request can still reach it while Bloom is closing down and joining its threads — creating a new thread after the join has gone past.

It is harmless as things stand: shutdown signals the stop event and never disposes the wait handles, so a newly created helper wakes immediately and exits. The trap is for a future maintainer — if those handles are ever disposed during shutdown, this becomes an unhandled error on a background thread, which takes the process down. The recommendation is the middle option: record the dependency where someone would see it, rather than adding a new condition to the very path whose job is to prevent the deadlock.

For your information

The catch-everything is a deliberate exception to AGENTS.md

Devin, informational — not mirrored to the PR

The repo's guidance is to fail fast and not be defensive about errors. The top-up does the opposite: it catches everything, and even wraps its own error logging in a second catch that ignores failures. Devin flagged it so the deviation reads as a conscious decision rather than an oversight, and agreed the reasoning is sound.

The reasoning: callers bump the count and only then arm the finally that brings it down, so anything escaping this method leaks the count for the life of the process — the exact condition the method exists to relieve. Failing fast here would convert a failed log write into a permanently mis-counted server. Devin notes the alternative is to move the increment inside each caller's protected region, which is the same work as decision 1's proper fix — so choosing that would let this defensiveness be removed.

For your information

The pool can end a session larger than it started

Devin, informational · corroborated by the local review — not mirrored to the PR

Helper threads have never been retired once created — that predates this change. What is new is that the pool can top up whenever a helper reports a wait, not only when a request arrives. During a long publish with several requests queued behind the same lock, each one can add a helper, so a busy session can leave the pool noticeably bigger than its starting size for the rest of that session.

Both reviewers judged this acceptable given the deadlock it prevents, and the growth is bounded by how many requests are actually waiting. It is worth knowing for two reasons: it is the one way this change could plausibly make things worse rather than better, and it will make thread counts in future diagnostics look higher than they used to. The QA note asks the tester to publish repeatedly in one session and watch for exactly this.
