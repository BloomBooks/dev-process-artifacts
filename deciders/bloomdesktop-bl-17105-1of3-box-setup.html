What this PR is about

Purpose

Some controls change which languages a translation group shows after the page has loaded: today the Language submenu of a canvas text box, and next the Languages menu of a table's text cell (PR 2/3 of this stack). When the group has no box for the chosen language, the control has to add one, and that box needs everything page load gives a box: CKEditor, the key, paste and placeholder handling, the toolbox's handlers, its language tag and its text direction. Until now the canvas submenu cloned a box and stopped there. This PR makes one way to add such a box and set it up, and uses it for the canvas submenu.

What the PR does

  • A new module, translationGroupLanguages.ts: showLanguagesInTranslationGroup shows exactly the languages asked for and adds a box for any that is missing, copied from the group's z box (else its first) without that box's language, editing state or Talking Book recording; setUpBoxesBuiltAfterLoad gives the added boxes what page load gives every box.
  • The per-box steps of page load become shared helpers that page load calls at the same places, so page load does what it did, in the same order. The list of steps is written out in both places on purpose; the PR description explains why.
  • The canvas text box's Language submenu uses the two functions.
  • The toolbox now takes the boxes to set up and hands them to the tools, so boxes added later are set up without the boxes beside them getting the tools' handlers a second time.
  • Less layout work when languages change, since the next PR does this for every cell of a table: language tags and group font sizes measure every box before changing any (page load gets this too), and a box's classes change only when they are wrong.
  • A new e2e test, canvas-text-language.spec.ts (Notion Test Case ID 860), with helpers for a custom cover and a canvas element's languages.
