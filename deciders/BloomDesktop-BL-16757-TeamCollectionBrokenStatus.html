a05c97d65 — Fix Team Collection status dialog blanking the whole window (BL-16757)

Guards the email before hashing it, at bloomAvatar.tsx:52.

  • Why the whole window went blank, not just the dialog. CollectionsTabPane.tsx:694 mounts the dialog inside the main app's single React root, and ErrorBoundary.tsx is imported nowhere, so a throw during the dialog's render unmounted everything — top bar, book list and all.
  • The throw. CollectionHistoryTable.tsx:166 passes e.UserId as the avatar's email. That column is nullable in C# (HistoryEvent.cs:41), serialized with plain JsonConvert and no NullValueHandling.Ignore, so it arrives as null — and md5Util.ts:24 is message.length.

Of 88 history events across its 12 history.db files, three have a NULL userid — two "uploaded to Bloom Library" rows written by Bloom 6.0.2, one "renamed" row by 5.6.7. Any one is enough. (Those databases were copied out and read; the originals were never modified.)

Master is immune because BL-16514 (ae181659b) rewrote this component behind the same guard — but that commit is 18 files and ~1,560 insertions, adding AccountApi, AvatarApi and a 382-line AvatarCache that 6.4 has no equivalent of. Taking its bloomAvatar.tsx hunk alone would point every avatar at an endpoint 6.4 doesn't serve.

Decision 1 · from Greptile

The types still claim a user is always recorded

The code is now correct at runtime, but the type declarations around it still say the thing that can't happen, can't happen. BloomAvatar declares email: string, and the history table declares UserId: string for a C# column that is genuinely nullable.

That second declaration is the more interesting one: it is why the null reached a render in the first place. TypeScript had been told the field was always a string, so it never asked the question, and the crash shipped. Nothing breaks today either way — the guard handles null, undefined and empty string regardless of what the annotation claims — so this is about whether the next person to touch this code is warned or misled.

Decision 2 · cross-branch hazard

This commit will conflict when 6.4 next merges into master

Master fixed this same crash a different way, as a side effect of the BL-16514 login/avatar feature: it deleted the getMd5 call entirely and fetches avatars from Bloom's own server. This commit edits the very line master deleted.

I confirmed the consequence rather than guessing at it — a read-only git merge-tree of this branch against origin/master produces exactly one conflict, in bloomAvatar.tsx, and nothing else. So the next 6.4-to-master merge will stop there, and resolving it carelessly would drag 6.4's getMd5 call back into master and undo the better fix. Master's side is the one to keep; it already has the guard.

Decision 3 · release scope

The card says 6.3 is affected too

BL-16757's second comment records that "Bloom 6.3 and Bloom 6.4 both exhibit this bug", and that fits the cause: the crash needs only a history record written by an older Bloom, which 6.3 reads the same way 6.4 does. This PR targets Version6.4 only.

Whether that matters is a release question I can't answer from the repo — it depends on whether another 6.3 build will ever ship. I'd default to no backport, on the grounds that shipping a 6.4 upgrade is the normal answer for a 6.3 user hitting this, but you know the release plan.

For your information

Nothing in Bloom uses its ErrorBoundary

react_components/ErrorBoundary.tsx defines a working error boundary, and grep across the whole front end finds exactly one reference to it: its own definition. Nothing imports it — not the app root, not the collection tab, nothing.

That is the difference between this bug being "an avatar didn't load" and "quit Bloom and start again". Master has the same gap, and hit the same failure mode from a different trigger in 0b405085a (BL-16209). Out of scope for a stable-branch fix, and genuinely its own piece of work — but it is the reason this was severe rather than cosmetic.
