Decision · from Devin, thread open

Does TeamCity still expect the old service messages?

Until now, the tool that ran our tests on the build server reported each result to TeamCity as it went, by printing special messages that TeamCity watches for. That tool is what this branch removes. In its place we write a results file and tell TeamCity to read it.

Everything needed for that lives in this branch, and it is verified to produce the right file. What cannot be checked from here is the TeamCity build configuration itself, which lives on the server rather than in the repo. If some part of it still expects the old running commentary, the build could go green while its Tests tab looks empty or wrong.

This is also the single check that would settle the open question below, so the two are best answered together.

Decision · open question

TeamCity runs about 660 more C# tests than this machine can

TeamCity's last run of this suite counted 3687 tests. The most this worktree can run is 3027. The gap is real and it is C# — I checked the names in TeamCity's own results rather than assuming, and they are Bloom C# tests, not front-end ones.

The likeliest explanation is tests that generate their cases from data files a build agent has and a developer checkout does not. Those 660 have therefore never been run under dotnet test by anyone, which is the one genuine risk left in this change.
