The re-run earned its keep

Re-running the gauntlet after the decisions found a severe bug that had been sitting in Bloom all along, and that this branch would have turned destructive.

HasTransparency was calling every palette-based picture opaque — a PNG-8 or a GIF, which keeps its transparency in its palette rather than a per-pixel alpha channel. The "no alpha channel, therefore no transparency" shortcut ran first, and because every indexed pixel format leaves the alpha flags clear, it answered for all of them and the palette check underneath was unreachable dead code. Confirmed at runtime, not by reading: a transparent-palette bitmap returned false.

Harmless for as long as the answer only chose a display format. Not harmless here, where the AI editor deletes the original once told a picture is opaque — a PNG-8 with a see-through background would have been flattened for good. Fixed in 93e89582f by asking the palette first; thread. Three other callers were wrong in the same direction and improve with it: thumbnails of palette-transparent covers now get the cover colour, and the display path stops baking a solid background into its cached copy.

Devin also pushed back on the ten-pixel cap as "a very thin net". That is true and it is your call, already made — so it is recorded on its thread as a deliberate decision and resolved, not reopened. Indexed pictures no longer depend on sampling at all, so that net now covers strictly less ground than before.

Decisions — recorded

All six answered on 2026-08-12. Each one that came from a review thread has the decision written onto that thread, and every thread is now resolved.

Transparency is detected by sampling only the top-left corner

From Devin · thread · Fixed in d1d02a4aa

Rather than accept the gap, the choice was to widen the check: after the corner scan comes up empty, HasTransparency now samples a few more pixels scattered over the rest of the image, capped at ten. That is negligible beside the 225 pixels the corner scan already reads, and it only runs at all on images that have an alpha channel.

This turned out to be a reachable hole rather than a theoretical one. GraphicsMagick turns exactly the shape Devin described — a 300×300 canvas with a 30px opaque border and a transparent middle — into a JPEG 24% of the PNG's size, comfortably past the "worth keeping" threshold. Such a picture really would have been converted and its cutout flattened, with the original deleted.

Two implementation notes. The seed is fixed: the sample positions want to be scattered rather than clustered like the corner scan, but a caller that deletes the original on a "no" needs the same answer for the same picture every time, so a test asserts repeated calls agree. And it is still a sample, not a proof — both doc comments now say so, instead of describing a guarantee the code doesn't make. All four callers get the better answer; for the display paths that means they stop baking a solid background into a cached copy of a cutout.

A picture generated into an empty slot is never re-encoded at all

From Devin · thread · Left as is

A deliberate scope decision, recorded on the thread rather than closed silently. The bug on the card is specifically a .jpg coming back ten times larger, and "don't make a book worse than it already was" is a coherent line to ship. Widening it needs its own policy for when a generated PNG is worth re-encoding with no previous file to measure against — and it would put every new AI picture through a lossy conversion, which would make the transparency question much more pressing than the narrow case it is here. If the bloat shows up on fresh books in practice, it wants its own card.

The other four

All left as is

  • Only freshly generated pictures are re-encoded. A reused book picture keeps its credits inside its own file and nothing on that path rewrites them, so re-encoding could silently lose a picture's copyright information — a worse bug than the one being fixed.
  • The 1.5× size threshold stays. The reported case was ten times over, so the threshold is nowhere near it; its job is to avoid spending a GraphicsMagick run and a lossy re-encode chasing a marginal saving.
  • See-through pictures still land at full size. The price of not destroying them, and not a regression — it is what Bloom did before this PR.
  • JPEG detection coverage stays as it is. A shared helper this PR didn't introduce, and it fails in the safe direction: an unrecognized JPEG means no conversion, never a wrong one.
