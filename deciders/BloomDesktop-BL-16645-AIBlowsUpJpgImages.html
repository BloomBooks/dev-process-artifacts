The run caught a severe regression — mine

Devin found that tryJpegConversion had picked up a !needsResize term. That flag gates two conversion attempts, and the earlier one already required !needsResize, so folding it in as well left the attempt below the resize reachable only for BMP/TIFF. A large photographic PNG was resized and then written straight back out as a PNG.

That lands where it hurts most. BloomPubMaker and EpubMaker both pass max dimensions, so needsResize is true for exactly the large photos where the JPEG saving is biggest. Every ebook and BloomPUB containing one would have grown several times over — the opposite of what this ticket is for.

The term arrived in my commit 6aa6d0250. It was in the working-tree diff I picked up alongside the samplePixels work, and I committed it without scrutinising it or mentioning it in the message. Devin was right that nothing explained it; master has no such term. Fixed in b2271b99b and documented on the PR.

The missing test was the real gap, and it is the durable part of the fix. The existing AdjustImageForDisplay_PhotoButPNGFile_ConvertsToJpeg uses a 118×154 image, which never resizes, so it could not see this. The new one asks for a size smaller than the source — the way the publication code calls in — and asserts the result is still a JPEG after checking it really was shrunk. I wrote it first and confirmed it failed (Expected: <Jpeg> But was: <Png>) before applying the fix.

The full C# suite is only intermittently green — filed as BL-16722, nothing to decide

Found by this run · kept here because it colours how you read the test row, not because it needs an answer

AGENTS.md says the suite is expected green through the wrapper. Across seven full runs today it was green twice, with 1–2 failures each time otherwise, spread over six different and unrelated tests — AI editor, epub audio, credits page, TeamCollection status, BloomPUB compression, device xmatter.

Correction to the first version of this item: I wrote that every failure shared one signature. It does not — I had read the exception messages from two runs and the test names from the others. Three of the six share it; the rest have separate causes, listed below. The mechanism still holds for those three, and they are filed as BL-16722.

Those three are each a DirectoryNotFoundException on a path inside the run’s own isolated temp root, raised from inside RobustFile after its retries — …\BookTests\book\book.htm, …\BookTests\book\epub-thumbnail.png, …\ePUB_export\0\…\lang-qr-code.png. A directory that should exist, vanishing mid-test.

The mechanism. BookTestsBase.Setup() is a [SetUp] — so it runs before every test — and does new TemporaryFolder(GetTestFolderName()), which returns the literal "BookTests", then nests "book" inside it. TemporaryFolder deletes an existing folder of that name before creating it. Eight fixtures derive from BookTestsBase and only BookThumbnailerTests overrides the name, so they all share one path. Any work still touching BookTests\book when the next test’s setup wipes it gets exactly the exception above. That fits the symptoms precisely: intermittent, timing dependent, and clustered in the publishing fixtures — the ones most likely to have something outstanding, which is the same hazard behind this repo’s “tests retire their BloomServers rather than disposing them” rule. ePUB_export is worse: it is a production constant (EpubMaker.kEPUBExportFolder), so every epub test shares one staging root.

The correlation is what makes this more than a guess: all three of those failures are in fixtures that inherit the shared name (ExportEpubTests twice, BloomPubMakerTests once).

The other three failures are not this bug, and I am not claiming them: InCreditsPage_LicenseUrlAndISBN_AreRemoved could not find customBookStyles.css under the shared output\browser — a build artefact, not a temp folder; GetStatus_BuildNeeded… in RabAppProjectTests (which does not inherit the name) reported RAB importing 1 book where 2 were expected; and my own ConvertPngToJpeg_UndecodableFile… lost a file from its fixture’s own per-test folder, which remains unexplained.

Filed as BL-16722 (Bug, Bloom 6.6, Incoming) rather than fixed here — it is test-infrastructure work across nine fixtures, unrelated to this ticket. The fix has a precedent in the tree: BookThumbnailerTests and BookCompressorTests already override GetTestFolderName(), and deriving it from GetType().Name in the base class would make the problem structurally impossible. Worth doing: a suite that goes red two runs in three for reasons unrelated to your change trains everyone to re-run until green, which is how a real regression gets waved through — and AGENTS.md tells people the suite is expected green, so they bisect their own work instead. Which is what I did, for about half an hour.

Two things I got wrong on the way here, both worth knowing. I first blamed my own orphan-cleanup fix, on the strength of a single green run with it reverted; the next run failed elsewhere with the fix restored, so that was wrong. And two of the red runs overlapped a git worktree add/remove I started myself, so I was polluting my own measurements for part of it. The root cause above does not depend on either of those.

Settled

  • The imported upload’s licence — fixed in 688cb7d0a, and my diagnosis of it was wrong twice. I reported that a GraphicsMagick import resize loses the credits, and that this was pre-existing breakage in shared import code. Neither held. Every other caller re-attaches the metadata afterwards (PageEditingModel.ChangePicture does it in the next statement), so only the path this PR added lost anything — and what it lost was not the credits, because libpalaso writes those twice, as PNG tEXt keys and as XMP. GraphicsMagick keeps the tEXt and drops the XMP, where the licence alone lives. So the test I wrote to prove the bug passed; adding one licence assertion turned it red. The real symptom is nastier than the one I described: an uploaded photo arrived with its copyright and creator intact and its Creative Commons licence silently reduced to NullLicense — healthy-looking, and wrong. Fixed with the call the other caller already makes. Bearing on the item below: the reuse exclusion’s credits justification is now definitively gone, since metadata is re-attached whichever path processing took.
