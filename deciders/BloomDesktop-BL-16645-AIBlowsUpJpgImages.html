Your decisions

Six things I did not want to settle on your behalf. The first two have open threads on the PR waiting on them.

Transparency is detected by sampling only the top-left corner

From Devin · open thread · ImageUtils.cs:1859

Before re-encoding a picture as a JPEG we now ask whether it has any see-through areas, because a JPEG cannot store them. That question is answered by Bloom's existing HasTransparency, which is exact for palette-based images but, for an ordinary bitmap, only looks at a 15×15 block in the top-left corner — on the reasoning that a see-through picture is nearly always see-through at its corners.

That shortcut is safe everywhere Bloom currently uses it, because there the original file survives and the JPEG is only a cache copy. Here it is different: if the guess is wrong we re-encode and delete the original, so the see-through areas are gone for good. The picture that would slip through is one transparent only in its interior — a subject cut out on a canvas whose corners happen to be opaque, or a picture with a hole in the middle. Narrow, but silent and unrecoverable when it happens. I recommend leaving it: it is the same heuristic Bloom trusts everywhere else, the case is genuinely rare, and both alternatives cost something real.

One part of this I did fix without asking: the helper's own doc comment claimed "a PNG with any transparency is left alone whatever its size", which promises more than a corner sample can deliver. It now states the real guarantee and names this gap, so nobody reads it as settled. Devin also escalated this from a flag to a Bug in its final round.

Leave as is recommended

A picture generated into an empty slot is never re-encoded at all

From Devin · open thread · AiImageEditorApi.cs:1219

The whole mechanism is comparative: it only acts when the picture being replaced was a JPEG, because that is what gives it a size to judge "too big" against. So if you generate a picture into a slot that was empty — a placeholder, or no picture at all — nothing happens, however large a photographic PNG arrives. Devin's point, which is fair, is that this is arguably the most common case in a fresh book: the saving only ever materialises when you re-edit a slot that already had a photo.

I did not widen it, because doing so is a design decision rather than a tweak. With no previous file there is no size to compare against, so it would need its own rule for when a generated PNG is worth re-encoding at all — and it would put every new AI picture through a lossy conversion, which turns the transparency question above from a narrow edge case into something much more pressing. I recommend leaving it here and treating the empty-slot case as its own ticket if the bloat shows up in practice.

Leave as is recommended

Only freshly generated pictures are re-encoded, never reused ones

My scoping decision during this run · AiImageEditorApi.cs:1046

The AI editor can put two kinds of picture into a book: one it has just generated or you uploaded, and one already in the book that you picked to reuse. As written, the code would have re-encoded both. I limited it to the first kind, because a reused picture carries its credits inside its own file and nothing on that path writes them back afterwards — and re-encoding runs the file through GraphicsMagick, which can drop them. That is the same reason the reuse path already declines to resize. A freshly generated picture is safe because its credits are written in immediately after.

I recommend leaving this as it stands: the bug reported on the card is a generated result, and a reused picture cannot blow a book up anyway, since it was already tidied up on its own way in. Silently losing a picture's copyright information would be a worse bug than the one we are fixing.

Leave as is recommended

A PNG has to be more than 1.5× the JPEG before we try anything

FYI · AiImageEditorApi.cs:1178

The threshold is the number that came with the original work and I kept it. A PNG up to half again the size of the JPEG it replaces is simply left alone, so a picture that grows by, say, 40% still grows. The case reported on the card was ten times, so the threshold is nowhere near it — its real job is to avoid spending a GraphicsMagick run and a lossy re-encode chasing a marginal saving, which is why I recommend leaving it.

Leave as is recommended

See-through pictures still land in the book at full size

FYI — a consequence of the transparency fix

Because a see-through picture is now never re-encoded, an AI result with a transparent background that happens to be ten times the size of the JPEG it replaces will stay ten times the size. That is the price of not destroying it, and it is not a regression — it is what Bloom did before this PR — but it does mean the fix has a hole in it exactly where the pictures are most likely to be overlays. I recommend leaving it for now and treating it as its own piece of work if it turns out to matter.

Leave as is recommended

Some JPEGs aren't recognized as JPEGs, so they never get the benefit

From Devin (informational) · ImageUtils.cs:645

Deciding whether the picture being replaced was a JPEG is done by reading the first few bytes of the file, and that check only recognizes the two most common JPEG variants. A JPEG written by some other tool will not be recognized, and the new optimization will quietly not happen for it. This is a shared helper used elsewhere in Bloom, not something this PR introduced. It also fails in the safe direction — an unrecognized JPEG means no conversion, never a wrong one — which is why I recommend leaving it out of this PR.
