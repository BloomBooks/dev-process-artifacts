What this round did

Three things arrived while this branch sat promoted: John reviewed it and requested changes, Steve part-answered him in the working tree, and master moved 52 commits ahead into a conflict. All three are now folded in, and the PR is back to mergeable.

The substantive find was on John’s second point. He asked whether we could simply preserve the credits rather than work around losing them; the reading on the thread was that ProfilesToStrip = null already preserved them, so nothing was being lost. That was worth measuring rather than arguing, and the measurement is unambiguous:

The reasoning was sound but one step short: not passing +profile means GraphicsMagick is never asked to strip anything, yet it still does not carry metadata across a change of format — libpalaso writes these fields as XMP in a PNG iTXt chunk, and GM’s PNG → JPEG path has nothing that maps it into a JPEG XMP segment. I also ruled out the obvious alternative explanation: GetCurrentFilePath() returned the real credited file, so CreateSourceFileForImage never ran.

So John’s suggested fix is in, using the helper Bloom already had — ImageUtils.TrimMetadataInImage, which only needed to stop being private. This fixes a live bug on the path already enabled: an uploaded result can arrive with the user’s own credits, and before this, uploading a credited photo over a smaller JPEG quietly stripped its copyright.

Your decisions

Three items. The first two have open threads waiting on them.

Sampling still cannot see a small see-through patch — and an exact check turns out to cost 12 ms

From Devin · open thread

This is the third time this gap has come round, and it now comes with a number that changes it. Transparency is judged from a sample — the corner block plus about a hundred jittered points — and on a “no” the picture is re-encoded and the original deleted. A small see-through patch between the sampled points is therefore flattened permanently.

When you capped the extra sampling at ten pixels, and again when John raised it to a hundred, the exhaustive alternative was assumed to cost a slow full-image pass. Measured through LockBits, it does not:

ImageSampled (now)Exhaustive
2800×2800 (7.8M px)0.1 ms11.9 ms
1200×900 (1.1M px)0.1 ms1.4 ms
one transparent pixelmissedfound

Twelve milliseconds at the largest size Bloom imports, against a GraphicsMagick run costing hundreds. I did not implement it, because you have now decided this twice and a third unrequested change to the same call would be presumptuous — but the premise the decision rested on has moved, so it deserves one more look.

Recommended: put the exact check only at the AI-editor call site — the one caller that acts irreversibly — and leave HasTransparency as the cheap sampled check for the display and thumbnail paths. About ten lines, no behaviour change for any other caller, and it closes the gap completely. The alternatives are to keep sampling (the gap is much narrower than at ten pixels) or to make HasTransparency itself exact, which would reach the other three callers.

Reused book images: the reason for excluding them is gone

From John, and independently from Devin · open thread

The conversion still only runs for a freshly generated or uploaded result. Its stated justification was that re-encoding a reused image would lose the credits embedded in it — which is exactly what we just fixed. So the exclusion now rests on scope alone, and the code says so rather than implying a technical reason.

Devin adds a point worth having: the resizeIfNeeded:false argument just above rests on the same now-obsolete reasoning, so if one is revisited the other should be too. A reused PNG bloating a JPEG slot produces precisely the bloat this ticket exists to remove — but widening it is a scope call for you and John, not for a preflight run.
