The run caught a severe regression — mine

Devin found that tryJpegConversion had picked up a !needsResize term. That flag gates two conversion attempts, and the earlier one already required !needsResize, so folding it in as well left the attempt below the resize reachable only for BMP/TIFF. A large photographic PNG was resized and then written straight back out as a PNG.

That lands where it hurts most. BloomPubMaker and EpubMaker both pass max dimensions, so needsResize is true for exactly the large photos where the JPEG saving is biggest. Every ebook and BloomPUB containing one would have grown several times over — the opposite of what this ticket is for.

The term arrived in my commit 6aa6d0250. It was in the working-tree diff I picked up alongside the samplePixels work, and I committed it without scrutinising it or mentioning it in the message. Devin was right that nothing explained it; master has no such term. Fixed in b2271b99b and documented on the PR.

The missing test was the real gap, and it is the durable part of the fix. The existing AdjustImageForDisplay_PhotoButPNGFile_ConvertsToJpeg uses a 118×154 image, which never resizes, so it could not see this. The new one asks for a size smaller than the source — the way the publication code calls in — and asserts the result is still a JPEG after checking it really was shrunk. I wrote it first and confirmed it failed (Expected: <Jpeg> But was: <Png>) before applying the fix.

Your decisions

Two items, both with open threads. The three from the last report are settled.

The exhaustive scan now runs on every alpha-bearing image on the publish path

From Devin · open thread

AdjustImageForDisplay is a hot path, and with samplePixels: false every image carrying an alpha channel now gets a full alpha read instead of a 15×15 corner block. Roughly +10 ms per image, worst case; for a 200-image publish, about two seconds, against a run already spending hundreds of milliseconds per image inside GraphicsMagick. Images with no alpha channel at all — ordinary JPEG photos, the bulk of most books — still exit before any scan.

Recommended: keep it as it is. Devin describes this caller as writing "a temporary display copy" that does not need the guarantee, and that undersells it — this is the method BloomPubMaker and EpubMaker call, so its output is the image inside the published book. A wrong "opaque" there bakes a solid background into what the reader sees.

If the cost does turn out to matter, the answer is not to go back to sampling but to defer the call: tryJpegConversion is computed up front, so the scan currently runs even when the method returns early without converting anything. Evaluating it at the point of use — still on the pre-resize image, to keep the semantics identical — would skip it on those paths for nothing.

Reused book images: the reason for excluding them is still gone

From John, and independently from Devin · open thread

Unchanged from the last report, and still waiting. The conversion runs only for a freshly generated or uploaded result; its stated justification was that re-encoding a reused image would lose its embedded credits, which is exactly what we fixed. So the exclusion now rests on scope alone, and the code says so rather than implying a technical reason.

Devin’s addition still stands: the resizeIfNeeded:false argument just above rests on the same obsolete reasoning, so if one is revisited the other should be too.
