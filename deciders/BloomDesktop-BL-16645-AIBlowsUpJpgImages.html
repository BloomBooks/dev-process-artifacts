The run caught a severe regression — mine

Devin found that tryJpegConversion had picked up a !needsResize term. That flag gates two conversion attempts, and the earlier one already required !needsResize, so folding it in as well left the attempt below the resize reachable only for BMP/TIFF. A large photographic PNG was resized and then written straight back out as a PNG.

That lands where it hurts most. BloomPubMaker and EpubMaker both pass max dimensions, so needsResize is true for exactly the large photos where the JPEG saving is biggest. Every ebook and BloomPUB containing one would have grown several times over — the opposite of what this ticket is for.

An oversized uploaded photo loses its credits before we can carry them across

From Devin, and confirmed by measurement · open thread

Devin asked whether the credits CopyCoreMetadata carries onto the JPEG are still there to be copied, since an uploaded result large enough to need resizing has already been through ProcessAndSaveImageIntoFolder’s GraphicsMagick rewrite on import. It flagged this as “worth confirming”, so I measured it rather than reasoning about it.

It is real. I built a PNG carrying its copyright the way libpalaso stores it — an iTXt chunk keyed XML:com.adobe.xmp — plus a plain tEXt Copyright for comparison, and ran our own lib/gm/gm.exe over it with a resize, which is the shape of the import path (PNG in, PNG out, ProfilesToStrip = null). The XMP chunk — where the IP metadata lives — does not survive; the tEXt one does. Adding +profile "*" changed nothing, so leaving ProfilesToStrip null is not what saves it. On that path the credits are gone at import, before our copy runs, and there is nothing left for it to find.

Two things that does not undo. CopyCoreMetadata still earns its place: it carries the credits for every result that was not resized at import, which is the common case and was a real loss John caught. And this PR did not cause it — the loss is in the shared import resize that every credited oversized image goes through, AI editor or not.

Which is why I have not fixed it. The fix lives in code all image import runs through, and choosing between re-writing the metadata after the resize, not resizing credited images, or handing GraphicsMagick the metadata explicitly is a behavior judgement well outside this ticket. My recommendation is a ticket of its own, if this is news rather than known. The alternative — fixing it here — would widen this PR into shared import code at the point where it is otherwise ready.

Reused book images: the reason for excluding them is gone

From John, and independently from Devin · open thread

Unchanged and still waiting. The conversion runs only for a freshly generated or uploaded result; its stated justification was that re-encoding a reused image would lose its embedded credits, which is exactly what we fixed. So the exclusion rests on scope alone. Devin’s addition stands: resizeIfNeeded:false just above rests on the same obsolete reasoning.

Every published JPEG pays for a GraphicsMagick pass that almost always gets thrown away

From Devin · open thread

tryJpegConversion carries no term for the source’s own format, so an image that is already a JPEG and needs resizing gets a second GraphicsMagick pass at quality 92 after the resize — whose output is then almost always deleted for not being 50% smaller. A wasted subprocess per published JPEG, and in the rare case it is smaller, a second lossy generation in the published book.

Pre-existing, and I verified that rather than taking it on trust: origin/master has the identical condition and the same two call sites, so this branch changes nothing here but the comment. What makes it interesting is inside the helper it calls, which materialises a source file with CreateSourceFileForImage(image, false); // already know it's not jpeg — the helper documents a caller guarantee that this call site does not keep. That reads like an oversight of long standing rather than a decision.

Not fixed here, deliberately. Gating the attempt on the source format changes what Bloom publishes for existing books — today a JPEG that really does halve in size is replaced — which is a user-visible change to the publish path in shared code, outside this ticket. This one expression has already produced two of this branch’s worst moments (!needsResize, then the exhaustive scan), so a third change to it deserves its own change and its own test, not a footnote in a PR that is otherwise ready. My recommendation: its own ticket, unless you know the history and can settle it in a line.
