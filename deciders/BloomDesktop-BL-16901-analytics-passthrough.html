What this PR is about

Problem

Bloom kept its own copy of the analytics vocabulary belonging to the AI Image Editor — the separate bloom-ai-image-tools web app it hosts in an overlay. That copy was an allow-list of the event names the app was permitted to send. The app has since grown more events, and Bloom drops every one it does not recognise, leaving only a console.warn nobody is watching. Usage of those features is therefore indistinguishable in our data from nobody using them at all. Any library Bloom hosts should be able to add an event and have it recorded, without a matching change in this repo.

What the PR does

Two commits, deliberately kept apart. The first makes the passthrough work:

  • Removes the allow-list. Bloom forwards every event the AI Image Editor sends, properties untouched, rewriting only the AI Editor  name prefix to Bloom's own AI Image Editor  so a future AI editing tool for text or video is not confused with this one. The rewrite is blind — it needs no event to exist and works for events not yet invented.
  • Adds a session id. Bloom mints aiEditorSessionId per overlay launch and stamps it on every forwarded event and on its own session event. Nothing previously said which trip through the AI Image Editor a row belonged to, so the app's events could not be joined to what reached the book.
  • Drops generatedThisSession. Computing it meant recognising an event name the library owns — the coupling this card removes. It existed only because there was no session key to group on; the join now answers the same question in more detail, down to which tool and model each discarded generation used and what it cost.
  • Adds durationSeconds, as the card asked. Bloom owns the overlay's lifetime, so it is the right side to measure it — and the clock stops when the overlay goes away, not when a commit still in flight finally settles.

The second commit fixes the names, which had three different denominators under undifferentiated labels — generatedCount and reusedCount were a breakdown of what the user chose, not of what landed, yet sat beside appliedCount looking comparable. The event becomes AI Image Editor Session and its counts become picturesChosen, picturesApplied, chosenNew, chosenReused, historyItemsAtLaunch; failedCount is dropped as derivable. The principle behind all of it is written into the folder's AGENTS.md, along with a rule to write "the AI Image Editor" in full, since Bloom is itself the Bloom Editor.

Worth knowing

  • None of this has been exercised in a running Bloom. Developer builds do not send to Segment, and the pinned AI Image Editor (dist-v0.2.5) sends only AI Editor Generate, so there is nothing new to watch in the event log until the pin moves. The tests are the whole verification.
  • The event rename is safe only because nothing has shipped. This analytics scheme landed on Version6.5 in BL-16716 and is absent from Version6.4, so no released Bloom has ever sent it — no history to migrate, no dashboard to update. That window closes at 6.5's release.
  • The commit-reply appliedCount is untouched on purpose. It is the C#-to-front-end HTTP contract, not an analytics property. The new picturesApplied deliberately carries the same sense, so a reviewer seeing both words should read them as agreeing rather than as a missed rename.
  • The branch was renamed. Work began on BL-16901-library-analytics, which was sitting on master; this branch was cut fresh from Version6.5. The old local branch still exists, unused, and can be deleted.
Who bumps the AI Image Editor pin, and to which version?

This PR removes the gate that was dropping the AI Image Editor's events, but nothing new reaches Segment yet: src/BloomBrowserUI/package.json still pins bloom-ai-image-tools at dist-v0.2.5, which sends only AI Editor Generate. The events this card exists to unblock — Open, Batch Run, Accept — first appear in dist-v0.2.9.

The commit that synced the English strings says the pin bump belongs to BL-16891 ("Make ai-image-editor localizable"), and names dist-v0.2.8 as its target. That leaves a gap: 0.2.8 still sends only Generate, so if BL-16891 lands on 0.2.8 this card stays inert and no card owns getting to 0.2.10.

There is also a trap in the version between. dist-v0.2.9 sends an AI Editor Close event that the old allow-list silently swallowed. With the gate gone it would now be forwarded and sit beside Bloom's own session event — two close-ish events per session disagreeing about how many pictures were kept. The library deliberately deleted that event in dist-v0.2.10 for exactly this reason, so the pin must skip 0.2.9.

Notes
Should a malformed event name throw, or be ignored?

The messages the AI Image Editor posts to Bloom are typed on Bloom's side by assertion only — at runtime the payload is whatever the other side sent. The old code looked the event name up in a Map, so a name that was not a string (a number, an object) simply found nothing and was dropped. The new code guards against an empty name and then calls .replace() on it, so a non-string name raises a TypeError inside the message listener: the event is lost, and an error appears in the console instead.

Only our own code can produce such a message, and the repo's testing guidance is explicit that a dependency used wrongly should fail rather than be quietly worked around — which argues for leaving it. It is nonetheless a behaviour change this PR introduces, so it is yours to confirm rather than mine to assume.
