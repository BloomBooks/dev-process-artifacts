Which of the two designs do you want to keep?

Two separate PRs now, one commit each, both on master: #8193 (A) and #8191 (B). This is the decision the comparison was for.

Both designs fix the reported bug the same way — Bloom saves the page before opening the AI Image Tools, so a picture you have just added is actually there to edit. They differ in where the code that carries on after that save lives.

Both add the same small general-purpose hook to Bloom's editing model, so that something remembers — across the page reload a save causes — to open the tools afterwards. That was not true earlier today: approach B originally avoided the hook, and avoiding it was its main selling point. It turned out to be unsafe, because a save can reload the entire workspace and not just the page area, so B now uses the same hook as A. The two no longer differ there at all.

What still separates them is where the tools window itself lives. A leaves it inside the page area; B moves it out to Bloom's outer window, where the picture chooser and the copyright dialog already live for exactly this reason. That is what lets B save a replaced picture straight away instead of waiting for the user to close the tools — and it fixes a further bug on the way: replacing a picture twice without closing the tools used to fail the second time. Against that, B is a much larger change, and it is the one you have not yet seen running.

What should happen when someone retries a picture replacement that only partly worked?

Open thread — raised by Devin

When the user tells the AI tools to put results into the book, Bloom does the pictures on other pages itself and saves them straight away, and hands the ones on the page currently being edited back to the browser to apply. If that second part fails, the user is told the operation didn't fully succeed — but the other pages have already been changed and saved. If they then simply try again, Bloom redoes those other pages, this time against pictures that have already been replaced, so it fails again and leaves behind unused image files in the book folder.

This is not new to this branch and it isn't a defect in the diff — it is a gap in the agreement between Bloom and the separate AI tools app about what a retry means. I've already made the message honest about which pages were saved, which is what stops someone retrying blindly, and that is why leaving the rest alone is the recommendation: a proper fix means changing the exchange between the two apps, which is a different piece of work with its own card.

Should a queued "open the editor" request expire if it is never used?

Open thread — found by Devin. Applies to both PRs.

Choosing "Edit with AI…" asks Bloom to save the page and remember to open the tools once the page comes back. That memory is cleared as soon as it is used. But if the page-load report that follows is one Bloom decides to ignore — which it does when the load does not match the page it thought it was going to — the memory is neither used nor cleared, and it stays waiting. If the user later comes back to that same page, the tools open by themselves, possibly long after they clicked.

The obvious fix is to clear it on any page load at all. That has a real cost, though, and it is the cost already paid twice on this card: an in-between page load (a blank page while the workspace rebuilds, say) would use up the request and the user would get nothing, with no message. Which of those two rare annoyances you prefer is a judgment call, so I have not made it. Note that this now applies equally to both PRs, since they share the same mechanism.
