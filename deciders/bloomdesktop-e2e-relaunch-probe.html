What this PR is about

Problem

Since 2026-10-24 the nightly's e2e suite has failed every night on "renaming the collection on the Advanced page renames its folder and reopens it" (Test Case 838): it times out, then teardown reports "A Bloom is still answering on port 8089". The relaunched Bloom then stayed alive for the rest of the run, holding that port.

Cause

#8405 gave the fixture's probes a required deadline but missed the two calls in waitForRelaunchedBloom. Their timeout became NaN, AbortSignal.timeout(NaN) throws, and readInstanceInfo reads any error as "nothing answering here". So the fixture never saw the Bloom that relaunched itself under the new name, and the cleanup that should kill a stray copy failed the same way.

Nothing type-checks src/BloomE2E, so tsc's "Expected 2 arguments, but got 1" never surfaced. The same gap let a stale canUndo import stop the whole suite from loading on 2026-10-22.

What the PR does

  • waitForRelaunchedBloom passes its deadline when looking for the relaunched Bloom, and uses quick 2 s probes in its fallback cleanup, like the matching cleanup in startBloomOn.
  • The pre-commit hook type-checks src/BloomE2E whenever e2e sources are staged, and blocks the commit if it can't.
