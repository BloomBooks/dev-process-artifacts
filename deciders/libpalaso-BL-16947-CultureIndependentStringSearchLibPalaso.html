1. Remove Bloom's Thai workaround (BL-16945)

Source: BL-16947 description, "Note that BL-16945 added a workaround for at least a subset of these in BloomDesktop in Version6.4. We should clean that up as part of this."

BL-16945 added code to BloomDesktop 6.4 that works around libpalaso's culture-sensitive searches going wrong under Thai. Once Bloom uses a libpalaso release with this PR, that workaround is dead weight. This PR can't remove it, because the workaround lives in BloomDesktop. The removal also has to wait until libpalaso is released and Bloom's package reference is bumped. The card also says it isn't yet decided whether this goes into 6.5.

2. A few internal sorts now use the invariant culture

Source: preflight, a change to public behavior. Sites: LanguageForm.cs:109, OptionRef.cs:166, RecordToken.cs:166, LdmlNodeComparer.cs:257, and the LDML V0 migration code.

Some public comparison methods used to sort in the computer's current language. They order the forms inside a multi-language field, option keys, query field names, and the elements of writing-system (LDML) files. They now always sort by the invariant culture, which orders text the way English does. None of these orders is shown to users as a sorted list. Users running Windows in English see no change. A user whose language sorts differently (Danish treats "aa" as å; Hungarian and Czech have letter pairs) could see a one-time reordering of forms or LDML elements in files written afterwards. After that, the order is the same whoever saves the file. Leaving it as is is recommended: it's the only option that is both independent of each user's culture and unchanged for English users. Ordinal would reorder by case for everyone and break tests that expect -1/0/1. CurrentCulture would bring back the per-user variation this card is removing.

Sort order

3. Two searches over natural-language text are now character by character

Source: the adversarial review requested in tombogle's comment. Sites: ScrPassageDropDown.cs:428 and LexEntryFromLiftBuilder.cs:420.

Of the 165 changed searches, only these two look at text people read. The first is type-ahead in the Scripture book drop-down: pressing a letter jumps to the next book whose name starts with it. The only difference is a book name that begins with an invisible mark, such as a left-to-right mark, which used to match and now doesn't. The second is a fallback when importing a LIFT dictionary file that maps a bare semantic-domain number such as "4.2.7" to the full domain name. Numbers match exactly as before. Only a full domain name saved in a different Unicode normalization form would no longer be recognized, and the exact-match lookup that runs first never handled that either. Leaving both as is is recommended because the risk is small, and character-by-character matching is more predictable. The old culture-sensitive way also couldn't match an accented name typed in decomposed form, which it now can.

FYI: net48 test problems that exist on master too

Source: the local full test run.

On this computer, four GetLocalizedLanguageName_Valid_GetsNameInTargetLanguageOrNativeAsFallback cases fail under net48. They expect a language name in another language (for example "espagnol") but get the native name ("Español"), because ICU's language names aren't available when these tests run here. A clean build of master fails the same way, and CI passes them. Separately, when many net48 test assemblies run in one dotnet test command, the test host hangs while unloading after every test has passed. Neither is caused by this PR. Leaving both is recommended because CI is unaffected.
