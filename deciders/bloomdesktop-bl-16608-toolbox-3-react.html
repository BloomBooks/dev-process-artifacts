What this PR is about

Problem

Every tool in the Edit tab's toolbox is a React component, but the toolbox around them was not. toolbox.ts kept which tools were offered, which was open and which was running in its own module variables, and called each tool's lifecycle methods by hand, while React rendered the tool list from a separate copy of the same facts. Keeping two copies in step by hand is what failed in BL-16602: leaving a game page withdrew the Game tool but left the toolbox believing it was still current, so the tool that replaced it was never shown and Talking Book lost its highlighting and audio.

Separately, the toolbox has to wait for the page (CKEditor) before restoring the book's saved settings, but it applied settings read before that wait. Anything the user did meanwhile was undone: a toolbox just opened was shut again, a tool just opened closed back to the saved one. People click again and move on; seven e2e tests could not, and were skipped.

What the PR does

  • One React root. Each tool is an ordinary child rendered through ITool.renderPanel(), so React context reaches tools normally and the per-tool ThemeProviders go.
  • toolboxState.ts is the single source of truth for which tools are offered, which is open, which the book has enabled, whether the toolbox shows, and which page it is on.
  • Which tool is running is derived, not stored — the open tool, unless the toolbox has stopped offering it. The two can no longer disagree, making the BL-16602 class of bug unrepresentable rather than fixed.
  • useToolLifecycle.ts runs each tool's lifecycle from a React effect, so a tool runs because it is the current tool of a showing toolbox.
  • Neither late restore overwrites a decision made after its settings were read. Each snapshots the toolbox before its settings request goes out; readerToolsModel.restoreState() seeds defaults only into a model nothing has told yet.
  • The seven skipped e2e tests are back on (Test Case IDs 830, 441, 442, 460).

Worth knowing

  • The game-page path has no end-to-end or by-hand confirmation. Visiting a game page and leaving it is the original BL-16602 scenario; it has unit coverage in useToolLifecycleSpec and toolboxState.spec, but the manual pass did not reach it and no e2e test covers it.
  • The 0-of-40 e2e figure is dev-server evidence, not proof. The card itself notes these specs fail more often against the local dev server than in CI. They also pass at the nightly window size here, but the first nightlies after merge are the real confirmation.
  • A tool's panel now mounts whenever the tool is offered, not only while it runs. Anything a tool starts from its panel's mount must clean up on unmount, because detachFromPage() only runs for the running tool. Motion needed exactly this; other tools are worth a glance for the same pattern.

2. File a card for the two pre-existing findings?

Devin raised two findings about the same piece of startup code that are real but not introduced by this PR — master behaves identically, and both are resolved on the PR as pre-existing rather than fixed here:

  • The marker saying "this loading page wants tool X" is cleared whenever the open tool changes — including by the late settings restore — so it can be cleared before tool X is actually offered. (On master the same clearing lived in switchTool.)
  • doAdjustment retries on a timer holding the tool its own page asked for, so on rapid page changes an older queued adjustment can act after a newer page has arrived.

Both would show up as Talking Book highlighting or audio landing on a page it does not belong to. Fixing either means changing startup ordering, which is why I did not take it inside this PR.
