What changed in the rule

The dialog decision no longer turns on the thread alone. It asks: is there anywhere real to report? A NullProgress reports nowhere, so having one is the same as having none. If the caller handed us something better, we use it. Only when all we have is a NullProgress and we are on the UI thread do we put up our own dialog — and off the UI thread, headless, or under test we never can, so we use whatever we were given.

Your uncommitted change made progress optional and substituted a NullProgress for null. Its reworded doc comment said the dialog appears when we are on the UI thread "and do not have a valid progress" — but the condition never tested that, so I made the code match the comment.

That mattered more than a wording fix, because it caught a regression of mine. The swap I made two runs ago moved the single-book Update Book command onto the dialog path: it runs under ProgressDialogForeground, whose work runs on the UI thread, so it was stacking an "Updating Image Files" dialog inside the progress dialog it already had on screen — and writing nothing at all to that foreground dialog during the shrink. My commit message for the swap claimed it stopped a second dialog stacking. True for Do Updates of All Books; wrong for this command.

Book selection — the case the ticket is actually about — is untouched: it arrives with a NullProgress substituted by EnsureUpToDate, so it keeps its dialog and stays responsive. Exactly one caller changed behavior, and it was the broken one.

What to do

On the UI thread with a real progress, the shrink now runs inline

Source: Devin, informational — confirmed independently by the local review

This is the flip side of the fix. When the caller has a real progress we use it and do the work right there, so if that caller happens to be on the UI thread, the shrink runs on the UI thread rather than on a dialog's background worker.

Today that is exactly one caller, Update Book, and it is fine: it runs under ProgressDialogForeground, which already does the whole of BringBookUpToDate on the UI thread, and its MultiProgress includes ApplicationDoEventsProgress, which pumps on every message — so the dialog keeps painting while images are shrunk. Both reviewers checked this and agree nothing new freezes.

What it does create is an unwritten invariant: a future UI-thread caller that passes a live progress which does not pump would block the UI for the whole shrink. Recommendation is to leave the code alone and record the invariant where someone would trip over it, rather than adding machinery for a caller that does not exist.
