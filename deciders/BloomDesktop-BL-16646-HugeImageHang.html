Where it landed

Progress now follows the thread. Off the UI thread the migration reports into the IProgress the caller already owns, because anything arriving from a background thread is already running under some progress of its own. On the UI thread there is nothing to borrow and inline work would freeze Bloom, so it puts up its own dialog — which is legal there, and which runs the work on a background worker so the app stays alive. Headless callers stay silent. Every symptom on this ticket is addressed by that one rule.

What a user sees, by path: importing a .bloomSource, importing a spreadsheet, Do Updates of All Books and the publish previews all show the picture messages inside the progress box they were already showing, with no extra window. Clicking an old book to select it gets an "Updating Image Files" window with a live progress bar instead of a frozen app. The bulk-upload CLI does the work silently rather than trying to show a modal nobody could dismiss.

A failed shrink now aborts the rest of the book update

Source: Devin, Investigate — replied and resolved on my own authority

This is the flip side of the fix you asked for. Because the exception now propagates rather than being swallowed, a single unreadable or unconvertible image file will abort the whole bring-up-to-date, not just the shrink — including out of book selection.

I resolved it rather than escalating, for three reasons: it is the direct consequence of the decision you made; the no-dialog path has always behaved this way, so the two paths now agree where before the same failure had opposite outcomes depending on the calling thread; and the selection path already wraps this in a try/catch that attaches the book's folder and title and rethrows into Bloom's error reporting (web/controllers/CollectionApi.cs:198), so it surfaces as a reported error naming the book rather than an unhandled crash. Flagging it because "one bad image file stops the book opening" is a judgment you may want to make differently.
