Why the progress line is a warning, not an error

Worth recording, because the obvious call is wrong. Writing the failure to the caller's progress with WriteError would have undone your ModalIf.None: ProgressDialogForeground checks Progress.ErrorEncountered after its dialog closes and pops a modal "There was a problem performing that operation". That is the dialog "Update Book" runs under, so a passive toast plus a modal dialog is exactly what you would have got.

WriteWarning sets no such flag — only WriteError and WriteException do — and WarningsEncountered is consulted solely by Do Checks of All Books and Attempt Missing Image Replacements, neither of which runs this path. The reason is in a comment at the method, so the next person does not have to rediscover it.

Two things I did not change

The report repeats. Because the level deliberately stays at 0 and the once-per-pass flag lives on the BookStorage instance, a book with one unreadable image produces a toast and a Sentry event every time it is brought up to date — and during Do Updates of All Books, one per failing book in quick succession. The toasts expire after 15 seconds and can sit behind the progress window, so in practice the user will often miss them. It is strictly better than the old silence, and I did not want to add throttling machinery on my own initiative, but it is the cost of "retry forever" and you may want it capped.

Where it belongs

2. The catch now swallows OutOfMemoryException

BookStorage.cs — catch (Exception e) on both branches

Both branches catch Exception, so they also catch an out-of-memory failure and carry on into the remaining migrations and the Save. That is the one exception type where "keep going" is questionable here, because running out of memory on a huge image is precisely what this migration exists to prevent — so it is the most likely genuine failure, and the least likely to leave the process healthy afterwards.

What to do

3. The retry cannot get past the bad file

ImageUtils.cs — pre-existing; I raised a version of this last run and it is still open

Sharper than I put it last time, and it undercuts the retry you just paid for. FixSizeAndTransparencyOfImagesInFolder has no per-file try/catch — unlike NeedToShrinkImages, which skips files whose TagLib read throws. So one unreadable image aborts the loop at the same point on every attempt, and every image after it in the folder is never shrunk, no matter how many times we retry.

Separately, the commonest failure never throws at all: a missing or failing GraphicsMagick just returns false, which one of the two call sites ignores outright, so the book gets marked migrated with oversized images.

What to do about it

4. The CLI now succeeds despite a failed shrink

bloom upload, bloom hydrate, spreadsheetImport

In console mode NonFatalProblem writes one line to stderr and returns, so the command carries on and finishes normally — almost certainly exit 0 — with the book's images still oversized. Before this change the exception propagated. A script or build step driving bulk upload has no way to tell the shrink failed except by scraping stderr.
