The fix takes the approach the card argued against

Source: BL-16646, its "Suggested fix" section, plus Hatton's comment on the card

Some background, since this is the one thing here that really needs a person. Bloom shrinks over-large images in old books the first time it brings such a book up to date, and it puts up an "Updating Image Files" progress window while it does. That window is a WinForms dialog, and several of the code paths that bring a book up to date run on a background thread, where Windows does not allow a window to be created. That is the bug: a hang, an error report, or a stray dialog.

There are two ways to fix it. You can keep the dialog and make sure it is always created in a legal place — which is what this branch does. Or you can delete the dialog altogether and report progress through the IProgress object the caller already has, so there is no window to create and therefore no rule left to break.

The card explicitly asked for the second one, and spelled it out in three steps: add an IProgress parameter to the interface, pass the progress already in scope at Book.cs:1110 and :1898, and delete the dialog block. It named the alternative and rejected it in as many words:

"The thread rule being broken is a WinForms rule. Remove the Form and there is nothing left to break, so this does not need per-caller fixes or an 'am I on the UI thread?' branch. It also moves with the conversion to React and a single browser pane instead of adding to what has to be unwound later."

And the one human comment on the card reads:

"Fable came across this while looking at something else and thinks that it could be a real bug that people actually could run into. I have not tried the repro steps. And the fix seems to be working in the direction we want to go anyways, getting rid of another winforms dialog call."

So the expectation on the card is that this fix removes a WinForms dialog. As written, it keeps it and adds a thread check around it. That is a defensible trade — it is a much smaller change, it does not touch a public interface, and it keeps the "this is slow, hang on" feedback the dialog was there to give. But it is a different thing from what was asked for, it leaves the dialog to be unwound later during the React conversion, and it carries the two rough edges in items 2 and 3 below, both of which the IProgress route would have removed for free. This is your call, not mine, so I have not touched the approach.

Which approach ships

Do Updates of All Books will stack a second progress window

Found during this run; confirmed independently by the local review

The Troubleshooting › Do Updates of All Books command already opens its own progress window and runs the whole per-book loop on that window's background worker (CollectionModel.cs:1081). With this fix in place, every book that needs shrinking now marshals to the UI thread and opens a second "Updating Image Files" window on top of the first, while the outer worker sits blocked until the inner one closes.

It does work — the outer window's modal message loop keeps pumping, which is exactly why this is not a deadlock (see ProgressDialogBackground.cs:37). But a user updating an old collection will watch a dialog pop up over a dialog, once per affected book. Recommendation is to leave it, because it is cosmetic, it only bites on books that predate 2019 and have oversized images, and choosing the IProgress route in item 1 removes it anyway — so fixing it separately is likely wasted work. I have asked the tester to report how bad it actually looks.

What to do

Command-line bulk upload now shrinks images silently

Source: Devin, informational (not mirrored as a PR thread)

When nothing is open on screen — the bloom upload bulk-upload command, which has no window and no message loop — the fix does the shrinking against a NullProgress. That is a real improvement on what happened before, which was an attempt to show a modal dialog on a machine with nobody there to dismiss it. But it means a slow shrink now produces no output at all, so an unattended bulk upload can sit there for a long time with nothing in the log to explain the pause.

Recommendation is to leave it: the silence is a pre-existing gap rather than something this change introduced, and if you take the IProgress route in item 1 the CLI's own progress object flows in here and the logging appears for free. Fixing it separately only makes sense if item 1 stays as is.

What to do

The thread check can read "false" for a window that does not exist yet

Source: Devin, informational (not mirrored as a PR thread)

The fix asks the shell "do I need to marshal to you?" via InvokeRequired. WinForms answers false when the form's underlying window has not actually been created yet — so if we happen to catch a form that is registered but not yet realized, which is conceivable during early startup, we would take the "already on the UI thread" branch from a background thread and create the dialog in exactly the place this fix exists to avoid.

Recommendation is to leave it. This is a known rough edge of the idiom rather than something new here, and the same pattern is already long-standing in AudioRecording, NonFatalProblem, and OneDriveUtils; forms are also removed from the open-forms list when their window is destroyed. Tightening it only here would make this one site inconsistent with the other three for a case nobody has hit.

What to do

Merge or rebase when integrating master — house style

Source: you, during this run

You asked why I merged origin/master into the branch instead of rebasing the branch on top of it. I merged because that is what the preflight skill prescribes, and the reason behind that is that rebasing rewrites commit hashes and so needs a force-push; once a PR exists, review threads and bot findings are anchored to those hashes, so a force-push orphans them and makes "what changed since I last looked" hard for a human reviewer. This repo's history is also full of merge commits, so it matched local convention.

Your instinct was reasonable for this particular case, though: I merged before the first push, and the branch had no commits of its own, so a rebase would have been perfectly safe there and would have left linear history. If you want rebase-before-first-push as the standing rule, say so and I will record it — it is only unsafe after the branch has been pushed.
