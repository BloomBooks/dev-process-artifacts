Decisions

Three, all about failure handling, plus what to do next. The first is the one open thread on the PR.

1. The two branches now disagree about the same failure

BookStorage.cs · open thread

The dialog branch now catches, logs, and lets the rest of the update finish. The direct branch has no try/catch, so the same TagLib failure on the same image still propagates and abandons the remaining migrations and the Save.

The consequence I would not want to ship silently is Do Updates of All Books: it runs on a ProgressDialogBackground worker, which never reads RunWorkerCompletedEventArgs.Error, so one bad image ends the whole batch — the dialog closes, the remaining books are never processed, and the user is told nothing. Your own commit removed exactly that shape of silent loss from the dialog branch.

2. Should the user ever be told the shrink failed?

BookStorage.cs — the Logger.WriteError in the dialog branch

On the book-selection path the only trace of a failure is a log line, which a user sees only if they file a problem report. The book is retried next time, so nothing is permanently lost — but a user whose pictures never get shrunk has no way to learn that, and every attempt costs them the wait again.

Bloom's usual tool for this is NonFatalProblem.Report, which can be passive — no modal, no interruption — and so would not undo the point of your change.

3. The likeliest failure still slips past the new flag

ImageUtils.cs:1508, 1569, 1607–1664 — pre-existing, not introduced here

I checked this rather than assume it. ResizeImageFileWithOptionalTransparency does not throw when GraphicsMagick is missing (return false), when it exits nonzero (logged, then false), or when anything inside it throws (written to the console, then false). Its caller checks that return value in one loop and ignores it entirely in the other, and with no transparency fixes requested it simply counts the file as completed and moves on.

So FixSizeAndTransparencyOfImagesInFolder returns normally, success stays true, and the book is marked migrated with its images still oversized — permanently, since the level is never revisited. That is the exact outcome the success flag was added to prevent, and it is the commonest way this fails. What the flag actually catches is the narrower case of an exception escaping: a corrupt or unsupported image reaching TagLib.
