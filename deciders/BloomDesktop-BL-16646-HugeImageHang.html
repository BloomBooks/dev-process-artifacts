One substantive item, two small FYIs, and the process question carried over from the last run.

Bloom now freezes with no feedback when you click an old book

Source: Devin, Investigate flag (thread left open) — independently verified during this run

This is the cost of removing the dialog, and it is worth understanding precisely, because the old dialog was doing two jobs and only one of them was feedback.

ProgressDialogBackground.ShowAndDoWork ran the shrink on a background worker while the UI thread sat pumping messages inside ShowDialog(). So on a call site that was already on the UI thread, the old code both showed a progress bar and kept Bloom responsive. The new code does the shrink inline on whatever thread called it, and reports into whatever progress that caller owns.

For the callers that own a real progress channel that is a clear improvement — Do Updates of All Books, .bloomSource import, and the publish previews all now report into the dialog they had already opened, which is exactly what the card wanted. But some callers have no progress to give and pass NullProgress. The important one is selecting a book: the selectBook endpoint is registered handleOnUiThread: true (CollectionApi.cs:239) and reaches BookSelection.cs:35's bare EnsureUpToDate(). So clicking a pre-4.9 book with a 5000x4000 image now freezes Bloom, showing nothing, until the shrink finishes. PublishModel.cs:835, BookCommandsApi.cs:477 and the hydrate CLI are in the same position.

How much this matters turns on how often it happens. Both gates have to line up — a book still at mediaMaintenanceLevel 0 and carrying an oversized image — which the card itself describes as "an old book that has been sitting untouched". So it is rare, it is once per book, and the freeze is finite. Against that: it looks exactly like a hang, and a hang on book selection is the kind of thing that generates support reports. I have asked the tester to measure it and say whether they would have force-quit.

I have not changed this myself: deciding whether these call sites should acquire a progress channel, and which one, is a design call about Bloom's UX, not a mechanical fix.

What to do

The import dialog's percentage bar will not move during the shrink

Source: local review, low importance

On the .bloomSource import path the progress goes through WebProgressAdapter, whose ProgressIndicator is a do-nothing stand-in. ImageUtils drives its percentage through exactly that, so the numeric progress is swallowed: the user sees the per-image "Preparing image: …" text messages arriving, but the bar itself does not advance while images are being shrunk.

Recommendation is to leave it. The adapter has always behaved this way, the text messages already tell the user work is happening, and the shrink is simply the first long operation routed through it. IWebSocketProgress does expose SendPercent if you ever want the bar wired up.

What to do

An Application.DoEvents() deep in the resize now runs on a different thread

Source: local review, informational

ImageUtils calls Application.DoEvents() during the resize when a progress is present. Previously that always ran on the dialog's background worker; now it runs on whichever thread the caller used. On every path traced it is a near no-op (a server request thread or a progress-dialog worker), so nothing misbehaves today — but if the freeze in item 1 is fixed by giving the UI-thread callers a progress, that DoEvents starts pumping messages on the UI thread mid-shrink, which can re-enter Bloom in surprising ways.

Recommendation is to leave it now and simply remember it if you pick option 1 or 2 above, where it becomes relevant rather than theoretical.

What to do

Merge or rebase when integrating master — house style

Source: you, during the previous run — carried forward, still unanswered

You asked why I merge origin/master into the branch rather than rebasing onto it. I merge because that is what the preflight skill prescribes, and because rebasing rewrites commit hashes and so needs a force-push; once a PR exists, review threads and bot findings are anchored to those hashes, so a force-push orphans them. This branch is a good illustration — it now carries Devin threads anchored to specific commits, and a rebase would strand them.

Your instinct still holds for the narrower case, though: before the first push, a rebase is free and leaves linear history. If you want that as the standing rule, say so and I will record it.
