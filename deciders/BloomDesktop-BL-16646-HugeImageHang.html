The state of the branch

The thread test is backwards. Which callers get the "Updating Image Files" dialog is keyed off shell.InvokeRequired, which is true when the caller is not on the UI thread. So the dialog is built on background threads — the original BL-16646 complaint — and the silent inline path runs on the UI thread, which is where the freeze is. Both halves are the wrong way round: the dialog was restored for exactly the callers that must not have it, and withheld from the one caller that could safely have it. Swapping the two branches fixes both symptoms at once.

Three independent sources reached that conclusion this run: my own reading, a local review agent that verified the WinForms semantics with a throwaway net8.0-windows probe rather than from memory, and Devin, which filed it as its first actual Bug on this branch and prescribed the same swap.

One correction in fairness to the code, because the ticket overstates it: the probe found that .NET 8 does not throw on new Form() + ShowDialog() from a thread-pool thread — the window appears and pumps its own modal loop there. So the dialog branch is not a guaranteed crash. What it is: an ownerless top-level window on a foreign thread, not modal to the shell and with no owner to fix its z-order, registered process-wide in Application.OpenForms while living on a thread that stops pumping the moment it closes, holding a thread-pool thread for the whole multi-minute shrink. A window stuck behind the shell while the shell cannot proceed is precisely what a user reports as "Bloom hangs".

The thread test is inverted

Source: Devin, Bug (open) · local review · my own reading — all three agree

The code reads, at BookStorage.cs:4085:

if (Program.RunningUnitTests
    || progress is WebProgressAdapter
    || shell == null
    || !shell.InvokeRequired)        // ← true only ON the UI thread
        …do the work directly…
else
        …build and show ProgressDialogBackground…   // ← so this runs OFF it

InvokeRequired is true when the caller is not on the control's thread. So the dialog is constructed on background threads (with no Invoke anywhere), and the silent inline path runs on the UI thread. Reversing the last condition — dialog when !shell.InvokeRequired, caller's IProgress when shell.InvokeRequired — puts every path right at once: book selection gets a legal dialog on the UI thread with the work on a background worker, so it neither freezes nor goes silent; Do Updates of All Books reports into the progress dialog it already has open instead of stacking a second one; the CLI and the browser-progress callers are unaffected.

One thing to know if you keep InvokeRequired as the switch: it also reports false for a form whose window handle has not been created yet. That was a harmless edge when it only chose between two safe paths; now that it selects the branch, an early-startup form could route a background caller down the UI-thread path.

What to do

A failed shrink is permanently recorded as done

Source: local review, verified with a probe · only applies while a dialog branch exists

This one is about losing work quietly, so it is worth acting on regardless of item 1's outcome if any dialog path survives. ProgressDialogBackground.ShowAndDoWork wires RunWorkerCompleted += (sender, e) => Close(); and never reads e.Error (ProgressDialogBackground.cs:30), so an exception inside the worker vanishes. Control returns normally and mediaMaintenanceLevel is still set to 1, so a book whose images failed to shrink is marked migrated forever and never retried — with nothing shown to the user and nothing in the log.

The direct branch propagates the exception instead, so today the same failure has opposite outcomes depending only on which thread the caller happened to be on. Design 2 propagated in every case.

What to do

progress is WebProgressAdapter does not mean "this caller already shows progress"

Source: local review and Devin (informational) · only applies while a dialog branch exists

The test is meant to identify callers that already have somewhere visible to report. It misses both directions. Do Updates of All Books has a visible WinForms progress dialog open but passes a MultiProgress, so it fails the test and gets a second dialog. Spreadsheet import has a visible browser progress dialog but passes NullProgress, so it also gets a stray WinForms window on top.

Note that swapping the branches in item 1 makes most of this moot on its own, because those two callers are on background threads and would take the direct path anyway. Recommendation is therefore to leave it and let item 1 do the work, unless you keep a design where this test still decides something.
