What this PR is about

Testing of the merged inline (Word-style) images found five bugs: four in Steve's comment on the card, and a fifth that John found while trying the fixes.

(1/5) Backspace at the start of a block deleted the picture

Problem

Backspace at the very start of a block's text deleted the picture, and a second press emptied the whole block.

Cause

BloomField's Backspace guard looked for embedded images only when the page was set up, and it ran after CKEditor, whose first Backspace selects the picture.

Fix

The Backspace guard, and a matching Delete guard for a picture after the text, work out at each keystroke whether only protected pictures come before or after the paragraph, and run before CKEditor. Both keys are blocked while CKEditor has a picture selected.

(2/5) With a reader tool open, picture commands did nothing

Problem

With the Decodable Reader open, choosing a picture for an inline image did nothing, and Delete from its menu failed.

Cause

The reader tools rebuild each block from CKEditor's data when the text loses focus, which detached the picture element that the menu and toolbar held.

Fix

The rebuild, and the reader tools' own undo and redo, keep the live picture elements. The reader tools' history starts again after a picture change, so it cannot put an old picture back in one language.

(3/5) Moving one picture moved a picture on the other side

Cause

A CSS float cannot start higher than any float before it in the page, so a picture pushed down by the dragged one pulled down whatever came after it.

Fix

The floating pictures are ordered in the page by the highest point each can reach, and a drag or resize puts the others back where they were, measured from the top of the block's text so that scrolling does not move them.

(4/5) A changed picture was not always saved

Cause

CKEditor keeps a copy of each image's file name from when the page loaded and saves that copy.

Fix

When CKEditor has loaded a text block, Bloom removes CKEditor's attributes from the block's inline images, so CKEditor saves the file each picture shows now.

(5/5) A picture could not be left on the bottom of its block

Problem

In a block with room below its text, a picture dragged down the middle jumped back up to just after the text as soon as its bottom edge reached the bottom of the block. In the left or right third, a drag past the bottom left the picture wherever the previous mouse movement had put it.

Cause

In the middle third the drag changed to the bottom dock when the picture touched the bottom of the block, and that dock puts the picture straight after the text. On the sides, the limit on how far down a picture may go left out the picture's bottom margin, so the last part of the move overflowed the block and the whole move was undone.

Fix

The middle band applies all the way down, and a drag stops with the picture's bottom edge on the bottom of the block (computeInlineImageDock). The dock after the text applies only when the picture's center is dragged below the block. A left or right picture stops at the lowest place that fits, half a line above the bottom.

Worth knowing

  • A picture that is already in the dock after the text moves into the middle band (or to a side) as soon as it is dragged inside the block.
  • A picture resting on the bottom keeps a distance in pixels from the top of the block. When the block changes size, Bloom scales that distance by the change in height, so the picture can end up a little off the bottom edge.
  • No e2e spec checks that a dragged picture's bottom edge lands exactly on the bottom of the block. An agent checked it by hand in a running Bloom at 110% zoom.
