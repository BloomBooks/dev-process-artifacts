What this PR is about

Problem

Steve's testing of the merged inline images found four bugs: Backspace at the start of a block's text deleted the picture (and a second press emptied the block); with the Decodable Reader open, choosing a picture or deleting it did nothing; moving one of several pictures also moved a picture on the other side; and a changed picture was not always saved.

Cause

  • BloomField's Backspace guard looked for embedded images only when the page was set up, and ran after CKEditor, whose first Backspace selects the picture.
  • The reader tools rebuild each block from CKEditor's data when the text loses focus, which detached the picture element the menu held.
  • A CSS float cannot start higher than any float before it in the page, so a pushed picture pulled down whatever came after it, on either side.
  • CKEditor saves its own copy of each image's file name from when the page loaded (data-cke-saved-src).

What the PR does

  • Backspace and Delete guards that work out at each keystroke whether only protected pictures come before or after the paragraph, run before CKEditor, and block both keys while CKEditor has a picture selected.
  • The rebuild from CKEditor's data keeps the live picture elements, minus CKEditor's own attributes.
  • Floating pictures are ordered in the page by the highest point each can reach, counting pushes; a drag or a resize then puts the others back where they were.
  • Changing a picture updates CKEditor's saved copy of its file name.
  • Unit tests for each, and four e2e specs (Test Case ID 815).

Worth knowing

  • The Leveled Reader goes through the same rebuild as the Decodable Reader, but no test covers it.
  • No one has tried these fixes by hand in Bloom; the evidence is the unit tests and the e2e specs.
  • The e2e spec for the saved picture checks what a person sees; Bloom's normal save reads src, so it cannot fail on the changeImageInfo change alone.

The reader tools' own Ctrl+Z, with a picture in the block

While the Decodable or Leveled Reader has a markup tool selected, its Ctrl+Z and Ctrl+Y restore one text block's HTML from a snapshot the tool took when the block got focus (decodableReaderTool.tsx, readerToolsModel.undo). That skips Bloom's picture undo, so if the snapshot predates a picture change, Ctrl+Z might put back the old picture in one language only and leave the menu holding a detached element. This was found while diagnosing the Decodable Reader bug. Steve's test of typing and Ctrl+Z with the reader open passed, and nobody has tried Ctrl+Z after a picture change with the reader open.
