FYI: a stand-alone Reading App Builder can now stand in for Bloom's own

Suppose Reading App Builder for Bloom was once installed, but its program folder has since disappeared (for example, deleted by hand). Windows can still record it as installed. Before, Bloom trusted that record, found nothing, and downloaded and ran the installer. Devin flagged that this happens even when a complete stand-alone Reading App Builder, version 14.0 or later, is also on the computer. Bloom now checks that Reading App Builder for Bloom's folder really contains the program. If it doesn't, Bloom uses the stand-alone copy, and it only reinstalls when neither is usable. The card says a stand-alone 14.0 or later is fine to use, so I treated this as in scope and made the change. I'm listing it because it changes which Reading App Builder a user's app gets built with in that one situation. I recommend leaving it as is.

FYI: an unreadable VERSION file shows as an error, not "not installed"

To decide whether a stand-alone Reading App Builder is new enough, Bloom reads a small VERSION file in its program folder. It does this every time the Apps screen refreshes. Greptile and Devin both pointed out that if the file exists but can't be read, the Apps screen gets an error instead of treating that install as unusable. I didn't change this. Bloom's file-reading helper already retries when a file is briefly locked. The file sits in Program Files, which every user can read. And the project's guidance is to surface broken state rather than quietly hide it. Greptile withdrew the finding after my reply. The fix would be small if you'd rather Bloom treat an unreadable file as "too old" and reinstall.
