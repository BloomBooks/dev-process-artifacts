The two bugs found and fixed

Bloom could be left running with no window at all

The reopen path at Program.cs:1911 threw away the "could not open" answer. A comment written earlier in this branch claimed every caller handled that answer; that was simply untrue. Bloom's main window is already closed by the time this path runs, so a collection that refuses to open would have left Bloom alive with nothing on screen — invisible, findable only in Task Manager, and blocking the next launch through the single-instance lock. It is reachable in real use: a teammate on a newer Bloom adds the flag to a Team Collection, it syncs down, and changing a collection setting triggers a reload.

"Upgrade Bloom" could put a dialog up while Bloom was shutting down

Choosing Upgrade Bloom opens the download page and quits. But the code could not tell "we are quitting" from "the user wants a different collection" — both looked the same to the caller — so the collection chooser could be raised during shutdown, starting a fresh modal window that could hold the process open until a 20-second watchdog killed it. The quitting case is now reported explicitly and the caller stops.

Devin independently flagged the second of these, after it had already been fixed.

Decision 1 · Devin bug · thread

Warning dialogs in Bloom show no warning symbol

The new "this collection needs a newer Bloom" dialog asks for a warning symbol, and doesn't get one — it appears as a plain message. A screenshot taken of the running dialog during this preflight confirms it: text and buttons, no warning triangle.

The cause is a long-standing trap rather than anything new. In .NET, "Warning" and "Exclamation" are two names for the same value, and converting it to text yields "Exclamation" — a word the display side doesn't recognise, so it draws nothing. The code already carries a comment noting the identical problem for "Information" arriving as "Asterisk".

The catch is that this affects every warning message box in Bloom, not just the new one. So fixing it hands a warning symbol back to warning dialogs across the whole application — a visible change well outside this card, which is why it is your call rather than something done here.

Decision 2 · Devin · thread

Typing 7 instead of 7.0 silently does nothing

The only way to set this flag today is to hand-edit the collection file. Someone wanting to require Bloom 7 would very reasonably write <MinimumBloomVersion>7</MinimumBloomVersion>. A whole number on its own isn't understood as a version, so it is treated as "no requirement at all" and the collection opens to everybody — the protection silently does nothing, with only a line in the log to say so.

Being forgiving about unreadable values is deliberate: a typo must never lock someone out of their own collection. The question is whether a bare whole number is really a typo, or a correct-looking entry we should honour.

Decision 3 · Devin · thread

A Team Collection is judged before it syncs

The check reads the copy of the collection settings already on this computer. For a Team Collection that copy is refreshed as part of opening the collection — which happens after the check has run.

So if someone on a newer Bloom adds a minimum-version requirement to a shared collection, a teammate on an older Bloom still opens it once, doing exactly the thing the flag exists to prevent, and is only stopped on a later start once the settings file has come down. Leaving it is defensible for now — the card is explicitly groundwork, with no way to set the flag except by hand — but it is worth knowing before the Cloud-syncing work leans on this.

Decision 4 · Devin · thread

Command-line and bulk-upload paths aren't covered

The check sits at the single point that every interactive way of opening a collection passes through. The non-interactive paths — the command-line artifact and font-analytics commands, and bulk upload — build a collection directly without going past it, so they will open, and possibly write to, a collection that declares a newer minimum.

Whether that matters depends on what the flag is ultimately protecting. If it is guarding cloud-synced collections from being written by an older Bloom, then a bulk uploader running an old build is exactly the sort of thing you would want stopped. If the flag is really a message to a human, gating a batch tool only turns a silent problem into a failed overnight job.

Decision 5 · Devin · thread

The dialog is a fixed size, and this message is a long one

Bloom's shared message box is a fixed 500×200 with no sizing to fit its contents. This message is longer than most: a bold heading, a two-clause sentence naming the collection and two version numbers, and two fairly wide buttons.

It was checked in the running app during this preflight and renders correctly with room to spare, so nothing is broken today. The risk is a much longer collection name, or a translation that runs longer than the English, pushing it past the fixed height. Since the size belongs to the shared message box rather than to this dialog, changing it would affect every message box in Bloom.

Things decided along the way

No XLF entries. The four new pieces of dialog text have no translation entries; they use the English fallback, per your decision earlier and the allowance in AGENTS.md for experimental features. The local reviewer raised this; it was dismissed on that basis rather than re-opened.

Major/minor comparison, channel ignored. 6.6 is satisfied by any 6.6.x or later, a build number in the requirement is ignored, and both numbers are displayed the same way they are compared. Alpha, Beta and Release are treated alike, since a version number means the same thing on each. This answers the open question on the card.

"Upgrade Bloom" opens the download page rather than updating in place. Bloom's own updater reports progress through toasts, and the toast host only exists once a collection is open. More decisively, it offers only the newest build on the user's own channel — so someone on Release, blocked by a 6.5 requirement, would be told they were up to date and left with nowhere to go.
