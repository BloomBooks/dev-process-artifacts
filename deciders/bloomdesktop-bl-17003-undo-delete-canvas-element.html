What this PR is about

Problem

On a Canvas page, deleting an item (text box, speech bubble, picture or video overlay, game item) could not be undone. Stage 1 of retiring CKEditor (#8387) put one undo stack behind the Undo button, but nothing recorded onto it yet.

What the PR does

  • Delete is undoable. Undo puts back the same element, so its text and its text editor survive. Ctrl+Y or Ctrl+Shift+Z deletes it again. Ctrl+Shift+Z is now a Redo key alongside Ctrl+Y.
  • Stacking order: the element goes just below the one that was above it, else just above the one that was below it, else on top. Its level comes from where it lands, so a chain of undos, or an element added in between, works out. No other element's data is saved or restored.
  • Comic bubble chains are rejoined by reversing what the delete did, applied to the chain as it is now. Later edits to the chain's style or tail are kept.
  • Ordering rules (rectangles low, draggables last) are left to the existing tidy-up code. A game item's target comes back with it. The undo refuses only if the canvas itself is gone.
  • The reader tools' and CKEditor's undo no longer claim the Undo button for a text box that is no longer on the page. Before this, typing in a box and then deleting it made the delete impossible to undo.
  • comicaljs 0.4.2 (the stale bubble observer fix). The lockfile change is the five comicaljs lines only.

1. File a card for the reader tools claiming Undo?

A problem that predates this PR, found by its e2e test. In a fresh collection the reader tools behave as though a reader tool is active even when none is open: their saved settings switch on text highlighting (restoreState). So when you click Undo after typing, the reader tools' own simple text undo answers, not CKEditor's. That may restore text a little differently from what CKEditor would.

This PR makes it harmless for deletes; it no longer blocks undoing one. It is still wrong for typing, and it will matter more in Stage 3.
