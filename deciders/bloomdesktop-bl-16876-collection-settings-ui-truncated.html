What this PR is about

Problem

On Windows, the web-based tabs of the Collection Settings dialog — Book Making, Bloom Subscription, Advanced Program Settings — draw into only the top-left corner of the tab, with text and controls hard-clipped at the right and bottom and empty grey beyond. It appears after logging out and back in, a machine restart clears it, and it affects installed builds as well as developer runs.

Cause

Bloom runs PerMonitorV2 DPI-aware, but LegacyDpiDialogLauncher deliberately creates this dialog inside a SYSTEM_AWARE thread DPI scope so the WinForms half of these older dialogs keeps laying out as it did before Bloom became PerMonitorV2. WebView2 does not support that mixed-mode combination: handed Bounds of 636×446, BoundsMode=UseRawPixels and RasterizationScale=1, it still creates its own internal host window at systemDPI/monitorDPI of that size — 509×357 — while sizing the content window correctly. The content is clipped by its own undersized parent.

This is not a recent regression: behaviour is identical on WebView2 runtime 151.0.4129.107 and 152.0.4191.66, and the DPI code involved has not changed since May. Whether it fires depends on per-logon-session display state, which is why a restart clears it.

What the PR does

  • After WebView2 initializes, compares its internal host window against the control it should fill and puts it back to the right size when they disagree. Mouse input still maps correctly afterwards.
  • Re-checks after a resize, posted so it runs once WebView2 has applied its own bounds rather than being overwritten by them.
  • Acts only for browsers whose own window is not PerMonitorV2-aware — so the main window, Edit, Publish and the off-screen browsers that produce published output are never touched.
  • Adds LegacyDpiDialogLauncher.IsWindowLegacyDpiAware, keeping the "what counts as legacy DPI awareness" knowledge next to the code that creates that state.
  • Fails safe: the correction can never take Bloom down, logs at most once per browser, and is a no-op whenever WebView2 gets the size right — so it stops acting by itself if WebView2 ever fixes the bug.

Worth knowing

  • Why only this one dialog breaks is unexplained. Being System-aware is necessary but not sufficient: measured with the fix disabled, the Language Chooser, the calendar Setup dialog and the License dialog were all already correct. The only structural difference is that Collection Settings' browser sits inside a TabControl. The fix keys on the observable symptom rather than on that theory, so it does not depend on the answer.
  • It depends on WebView2's internal window class (Chrome_WidgetWin_0). If a future runtime renames it the workaround silently stops working — failing back to today's behaviour, not worse.
  • The fix is deliberately more defensive than AGENTS.md's "fail fast" default, because it reaches into undocumented WebView2 internals rather than our own API. That was a explicit call, not an oversight.
  • Only exercised on this machine's display setup (a 125% monitor alongside two at 100%) and only in the broken logon-session state. The QA notes on the card explain how to reproduce that state.

Over to you

1. Opening Collection Settings under --e2e currently kills Bloom

A parallel session found this while working on something else, and it turns out to share this bug's root cause. When Bloom runs with --e2e, all its embedded browsers share a single WebView2 environment (added 2026-09-03). That shared environment is PerMonitorV2, and Collection Settings tries to create a System-DPI-aware browser against it. WebView2 rejects that mismatch outright, which trips the error path in WebView2Browser that shuts Bloom down immediately. The practical effect is that any automated end-to-end test which opens Collection Settings will kill the app rather than fail with a useful message — and nobody would notice until they wrote one. It is a separate defect from the truncation this PR fixes, and out of scope for it.

Notes

2. We never worked out why only Collection Settings is affected

Three other dialogs in Bloom show web content inside the same System-DPI-aware treatment — the Language Chooser, the calendar Setup dialog, and the License dialog — and all three were measured as already correct with the fix switched off. So whatever makes WebView2 mis-size its window is not simply "the dialog is System-aware". The one difference we can point at is that the Collection Settings browser is nested inside a tab control rather than sitting directly on the window, but that was never confirmed. The fix does not rely on knowing: it reacts to the symptom wherever it shows up. The question is whether to spend more time understanding it.
