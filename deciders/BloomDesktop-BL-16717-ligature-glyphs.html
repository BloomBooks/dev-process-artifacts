What changed this run

5576c58a2 — Stop letters vanishing while typing in ligature fonts (BL-16717)

The bug

About half a second after you stop typing, Bloom tidies up the text box. To keep your place it drops a hidden CKEditor "bookmark" span at the insertion point, does its work, then takes the span out again — see toolbox.ts:1630, on the 500 ms timer at toolbox.ts:1641. This runs on every keystroke pause, whether or not a tool is open.

Inserting that span splits the text node you are typing in, and removing it does not put the halves back — CKEditor's moveToBookmark is just setStartBefore(b); b.remove(), with no normalize(). Chromium shapes a paragraph's text as one run and then hands the glyphs out per text node, so a ligature straddling that boundary loses glyphs. Andika (Bloom's default) and Charis ligate ff, fl and ffl; ABeeZee does not, which is why it never showed the bug.

The fix

New EditableDivUtils.mergeTextNodesSplitByBookmarks(), called wherever bookmarks are removed: toolbox.ts:1635 and editableDivUtils.ts:668 (the decodable/leveled reader path).

  • It does nothing unless there really are adjacent text nodes (hasAdjacentTextNodes, line 571), so on a normal keystroke pause it leaves the selection strictly alone.
  • It saves and restores the insertion point itself rather than trusting normalize()'s live-range fixups. The saved position is anchored to the containing element plus a character offset within it (saveablePosition, line 590), so it cannot drift across a paragraph boundary.
  • It restores with setBaseAndExtent, so a backwards selection stays backwards.

Re-verify the fix by hand?

You told me you had verified the fix in a running Bloom. That verification was against the first version of the code. The code changed after that. During the local review I found that the way it put your cursor back could, in a text box with more than one paragraph, land the cursor at the end of the previous paragraph instead of where you actually were — because it was counting characters across the whole text box, and the end of one paragraph and the start of the next are the same number of characters in.

Fixing that changed the part of the code you exercised when you tested: the cursor position is now anchored to the paragraph (or bold/italic span) it sits in, and the selection is restored with a different browser call that also keeps a backwards selection backwards. Unit tests cover all of this, but nothing has driven the new version in a real Bloom.

What you would be checking: type overflow, insert a second f, pause, type x — nothing vanishes; and then that typing, pausing and typing again in the middle of a multi-paragraph text box still leaves your cursor exactly where you left it.
