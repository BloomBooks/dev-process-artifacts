Round 2: the first fix was not enough

You found that a text box with more than one paragraph still went wrong — and differently: the inspector showed the correct overfflow as a single string, but the screen showed overfow. So repairing the DOM does not repair the display. Chromium keeps painting the paragraph's old glyphs, and the stale paint outlives the DOM being put right.

I reproduced that in your running Bloom over CDP — really typing, then screenshotting the text box — and confirmed two things. Rendered width measured correctly the whole time, so layout was never wrong; only the paint was. And the damage is done by the split-then-rejoin sequence itself, not by the split being left behind.

That changed the fix in two ways: don't take the bookmark at all unless something is actually going to rewrite the box (which for ordinary typing is never), and when we do take one, rebuild the text as a brand-new node instead of calling normalize() — a fresh node has no stale glyphs cached against it. Both were verified by screenshot in the real app, the second with the Talking Book tool open so a bookmark really was taken.

Round 3: the cure for the paint broke the highlighting

Devin then caught something severe in round 2. Rebuilding each run of text as a brand-new node is what cures the stale painting — nothing is cached against a node that didn't exist a moment ago — but replacing a text node collapses any live Range whose boundaries were inside it. Bloom's decodable/leveled reader highlighting and the Talking Book audio highlighting are exactly that: live Ranges over those text nodes, registered by the markup pass moments before the merge runs. The coloured marks would have silently vanished from the paragraph being typed in — the very failure textHighlightManager.hasDeadRanges() exists to detect.

Verified rather than assumed: in real Chromium a Range covering "fflow" across the split comes back collapsed and empty after the fresh-node merge, and survives intact under normalize().

Round 4: and the repaint trick had two problems of its own

Replacing the fresh-node merge with normalize() plus a forced re-layout fixed that, but Devin's next pass found two real faults in the forced re-layout, both of which reproduced exactly. Putting display back by writing its old value clears the declaration but not the attribute, so every paragraph typed in would have picked up an empty style attribute — in the markup Bloom saves into the book. And the parent of a bare text node can be the .bloom-editable itself; hiding a focused contenteditable blurs it, and restoring display does not restore focus, so the next keystrokes would have gone nowhere.

The shipped version therefore hides nothing and touches no attributes: it makes Chromium re-shape the merged node by writing the node's own text back into it — appending a character and immediately deleting it. Both edits sit at the very end of the node, where the spec moves only boundaries strictly beyond the edit point, so no live Range is disturbed; and the extra character is gone before the task ends, so it never paints.

Round 5: deleting the code that was causing the trouble

Devin's next pass found the last real bug, and it was in the part I had added out of caution rather than necessity. The hand-rolled selection restore identified a position as "N characters into this element", and that cannot tell the end of a bold run from the start of the plain text after it. A caret sitting just after a <strong> — or an audio-sentence span — could be put back inside it, so the user's next letters would come out bold, or inside a recorded phrase.

The mechanism turned out to be unnecessary. Keeping the selection on the same characters across a text-node merge is the browser's job per the DOM spec, and Chromium does it — checked in a running Bloom with the caret both at the split and immediately after a <strong>. The only reason I had distrusted it was that jsdom gets it wrong, which says nothing about the browser Bloom runs in. So the save/restore is gone: 201 lines deleted, 47 added. The bug went with it.

The bug

About half a second after you stop typing, Bloom tidies up the text box. To keep your place it drops a hidden CKEditor "bookmark" span at the insertion point, does its work, then takes the span out again — see toolbox.ts:1630, on the 500 ms timer at toolbox.ts:1641. This runs on every keystroke pause, whether or not a tool is open.

Inserting that span splits the text node you are typing in, and removing it does not put the halves back — CKEditor's moveToBookmark is just setStartBefore(b); b.remove(), with no normalize(). Chromium shapes a paragraph's text as one run and then hands the glyphs out per text node, so a ligature straddling that boundary loses glyphs. Andika (Bloom's default) and Charis ligate ff, fl and ffl; ABeeZee does not, which is why it never showed the bug.

The fix

  • Don't take a bookmark unless something will rewrite the box. The two clean-up steps only touch the box when they find a comment or an nbsp to fix, and markup only runs when a tool is open, so needsBookmarks is false for ordinary typing — no span inserted, no split, nothing to repair, and no cursor twitch at the half-second mark either.
  • When we do take one, merge with normalize() and then re-shape the merged node. normalize() is what keeps the live highlight Ranges alive; rewriting the node's own text afterwards is what makes Chromium stop painting the stale glyphs. Neither replaces a node, hides anything, or touches an attribute.
  • It does nothing unless there really are adjacent text nodes, so it never disturbs a selection it didn't need to touch.
  • It saves and restores the insertion point itself, anchored to the containing element plus a character offset within it, so it cannot drift across a paragraph boundary; and restores with setBaseAndExtent, so a backwards selection stays backwards.

Re-verify the fix by hand?

The vanishing letters themselves are now verified by screenshot in your running Bloom, on both code paths — so that part is not in doubt. What has not been driven by hand is the cursor behavior, and that is the part with the most ways to go wrong.

Two things changed the cursor code since you last tested. During the local review I found that the way it put your cursor back could, in a text box with more than one paragraph, land the cursor at the end of the previous paragraph instead of where you were — it was counting characters across the whole text box, and the end of one paragraph and the start of the next are the same number of characters in. Then, fixing your multi-paragraph report, the code stopped taking a bookmark at all during ordinary typing, so the cursor is now simply left alone at the half-second mark instead of being removed and put back. You should see the little cursor twitch disappear when no toolbox tool is open — that is the visible sign the change is working.

That second change should make cursor behavior better everywhere, but it is a change in behavior on every keystroke pause in every text box, so it deserves a human at a keyboard. What you would be checking: type, pause, keep typing — in the middle of a word, at the start and end of a paragraph, in the second of several paragraphs, inside bold or italic text, and with some words selected. In each case your cursor or selection should be exactly where you left it.

One Devin flag left open for you

This is the only review thread on the PR still open, deliberately. Devin raised it and I did not want to guess at an answer.

CKEditor keeps an invisible "filling character" (a zero-width space) in a text node near the cursor, and removes the one it is tracking when it is done. The merge now folds adjacent text nodes together, and if one of them is the node holding that character, CKEditor could lose track of it — leaving an orphaned zero-width space to be saved into the book. That is the corruption BL-16490 was about; a stray zero-width space breaks the reader tools' word matching, because the analyzer treats it as a word break and the highlighter doesn't.

Two things bound the risk. This code only runs when a bookmark was actually taken, which after this change means only when a tool is showing or there is a comment or nbsp to clean up — never during ordinary typing. And the machinery BL-16490 added is still in place: doCkEditorCleanup() strips stray filling characters on every markup pass. I have not been able to make it happen, but I have not proved it cannot.
