What this PR is about

Problem

Bloom referenced SIL.Windows.Forms.Keyboarding, a WinForms-only package that also brings in ibusdotnet and KeymanLegacyBundle (.NET Framework-only), for one call: asking whether an input processor such as Keyman or a Windows IME is active. When one is, the editor keeps its long-press accented-character popup off, because holding a key fights with the input method (BL-1071).

What the PR does

  • Ports that check into Bloom as Utils/InputProcessorDetector.cs: the same Text Services Framework calls as libpalaso 18.0.0, with a comment saying where it came from and why it moved. No other SIL project calls it, so porting beat splitting libpalaso.
  • Keeps the endpoint's threading and error handling as they were (BL-3614).
  • Removes the package, which also drops ibusdotnet and KeymanLegacyBundle, and updates the NU1701 comments and the WinForms plan.

Worth knowing

  • The Keyman/IME-active case has not been exercised inside Bloom; only the unit test covers detection. That's what BL-17058's test ideas are for.
  • The unit test switches input methods for its own process only. An experiment confirmed another process saw no change, so running the suite doesn't disturb whoever is typing.
