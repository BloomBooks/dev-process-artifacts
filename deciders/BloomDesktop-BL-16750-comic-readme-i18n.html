What this PR is about

Problem

Three whole sections of the Paper Comic Book and Digital Comic Book template readmes — “Limitations of Bloom’s current comic book support”, “Tips on using the Canvas Toolbox”, and “A note on White on Black Text”, together with all their bullets — had never been sent to Crowdin. A user reading either readme saw those sections in English whichever UI language they had chosen, and no translator had ever been offered the text. 26 strings in all.

Cause

Template readmes are localized as whole files: HtmlXliff.exe --extract turns ReadMe-en.htm into ReadMe-en.xlf, that goes to Crowdin, and the returned translations are injected back to make ReadMe-<lang>.htm. The extractor only picks up blocks carrying an i18n attribute, which comes from an {i18n="some.id"} annotation on the block in the markdown. Those sections had no annotations, so they were skipped at every stage — and because the extractor writes the same XLIFF either way, regenerating it produced no diff. Nothing anywhere reported it.

What the PR does

  • Annotates the unannotated blocks in both comic readmes. The text is identical in the two files, so it uses shared comic.template.* ids rather than per-readme ones, per the note at the top of each: Crowdin translates each string once and both readmes pick it up.
  • Annotates the four n/a cells in the Leveled Reader table, whose header cells already carried inline i18n attributes. All four hold the same text, so they share one id.
  • Regenerates the English XLIFFs: 27 new trans-units. Nothing was lost — --extract --preserve keeps a unit that is no longer in the HTML, so the Obsolete as of 6.3 full-bleed unit survives, moved to the end of its file.
  • Adds scripts/check-readme-i18n.js, which found this, and wires it into build-prod with --strict so it cannot come back. Four rules: text no i18n attribute covers; an id with text but no trans-unit; one id shared by blocks whose text differs; and a live trans-unit with nothing left in the HTML — tolerating units deliberately marked obsolete.

Worth knowing

  • The translations do not exist yet — this only sends the English to Crowdin. Until translators work on it these sections still show English in every language, so a tester should not read that as the fix having failed. The card’s test-ideas comment says so explicitly.
  • I did not hand-verify the readmes in a running Bloom; the check and the two suites are the evidence. Reading the three templates’ readmes end to end is the first item in the test ideas.
  • The same class of gap almost certainly exists in the other file-based localizations — help pages reached through GetBestLocalizableFileDistributedWithApplication and the xmatter <desc>-<lang>.txt files. Deliberately out of scope here; the checker only looks at template readmes.

Should the readme check fail the production build?

The new check has to run somewhere to be worth anything, and the only place available is the production build. GitHub Actions does not build the front-end for pull requests on this repo, so there is no PR gate to hang it on; build-prod — what TeamCity runs — is the one step that already regenerates the readmes and their translation files, which is exactly what the check needs to look at.

So this PR appends it to build-prod with --strict, meaning a non-zero exit and a failed build. Devin flagged the consequence, correctly: from now on, untranslated text in any template readme fails the whole production build, not just the ones touched here.

What that means in practice: all ten readmes pass as of this PR, so the gate can only fire on a newly introduced problem, and the only way to introduce one is to add readme text without an {i18n="…"} annotation. The failure message names the file and quotes the offending text. The cost is that someone editing a readme can break the release build with what looks like a harmless edit — and it is your build, not mine, so it is your call.
