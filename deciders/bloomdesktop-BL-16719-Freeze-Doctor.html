What this PR is about

Problem

Users report that Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log only shows what Bloom managed to write before it stopped responding. Three quite different failures all arrive looking identical — the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A UI thread blocked in a managed wait on an STA thread keeps dispatching sent messages so COM still works — so the window answers probes, IsHungAppWindow reports it healthy and Process.Responding returns true while Bloom is completely stuck. Measured on a real Bloom: nine minutes frozen, reported responsive throughout. Since Bloom's UI thread awaits WebView2 constantly, that is likely the common shape of freeze rather than an exotic one.

What the PR does

This is Bloom's half; the diagnostic tool itself lives in bloom-freeze-doctor. Nothing here changes what a user sees, and all of it is inert on a machine without the Doctor installed.

  • Publishes a health heartbeat through a shared-memory page a watcher can read without Bloom's cooperation — a UI-thread beat whose silence is the signal outside observation cannot see, plus a background beat so “the UI thread is blocked” can be told from “the whole process is wedged”.
  • Proves its clean exits from one ProcessExit handler, which runs for an orderly exit and not for FailFast, TerminateProcess or an access violation. A hard-failure or forced exit is deliberately not recorded as clean.
  • Records a session file with what a watcher cannot work out from outside: above all which log file this run is writing to, plus the ports, version, channel and collection.
  • Tracks in-flight API requests, so a report can name which request has been running for 47 seconds rather than only that a thread is waiting.
  • Starts the Doctor if installed, honours a request to exit when its UI is gone, and asks for a dump as it crashes — each costing nothing when no Doctor is there.
  • A developer-only freeze simulator, inert unless an environment variable is set and the build is a developer one, so detection can be tested against a real Bloom.

Worth knowing

  • The Doctor's detection has been exercised end to end against a real Bloom; the crash-dump handshake has not. Freezes (including the invisible STA-wait kind), the zombie case and the unreported-crash case were all driven with the simulator and produced correct reports. The dump handshake is wired but never fired in practice, because Bloom's own error handling catches these crashes first and reports them itself — which is the better outcome, and the Doctor correctly stayed silent. A direct FailFast runs no managed handlers at all, so it can never request a dump.
  • Nothing here is reachable by a user yet. The Doctor is a separate, unreleased program, so on any real machine this code publishes facts nobody reads. That makes the testing risk a regression risk — startup, shutdown, and the API request path — which is how the card's test notes are written.
  • Two faults of the same shape are worth knowing about before you review the diagnostic code. The line that records what Bloom was doing has been wrong three times, and its two failure directions are opposites — it either got overwritten a second later, or was never retired and described an idle Bloom hours later — so a fix for one walks into the other. Separately, the shared page's write counter has silently switched the channel off twice. In both cases the invariant was being held up by getting statement order right, which is fragile in proportion to how badly it fails; both are now expressed so that no ordering of failures can break them, and the activity rule is a pure function with both directions pinned by a test. Neither fault would ever have surfaced as an error — they produce a confident, wrong report, which is worse.
  • The two contract files are copies of files in the Doctor's repo, and both repos pin the layout by value in a test, so a divergence breaks two builds. If you edit one, copy it across. One correction to what I said last time: they are identical in substance but not literally byte-for-byte — Bloom's csharpier hook wraps three lines more narrowly than the other repo does. Worth knowing before anyone tries to enforce byte-equality mechanically; the pinned layout tests are the real guard.
  • The 6.4 backport is deliberately not here, per your call to field-test in 6.5 first. The plan's §9.1 records that and the ranked list is intact.

Over to you

Bloom never tells the Doctor when it is legitimately busy, so the five-minute grace does not exist

We agreed the Doctor should be patient with work that is meant to take a long time: it raises its freeze threshold from one minute to five whenever Bloom says a long operation is under way, and still reports if Bloom is stuck beyond that. The Doctor's half is built and reads the flag. Nothing in Bloom ever sets it, so it is permanently false and every freeze is judged at one minute.

What that does and does not threaten. Anything behind a modal progress dialog is safe either way, because ShowDialog keeps pumping messages and the heartbeat keeps ticking — no freeze is detected at all. The exposure is work that blocks the UI thread for over a minute without pumping messages: that would be filed as a freeze, which is the false positive the flag was added to prevent.

I left it unwired rather than guessing, and wrote the gap up at the method so nobody assumes the grace works. The reason it needs you: which operations to mark is a judgement about how Bloom really behaves, and it cannot be inferred from the code — “a request has been running for a minute” is the same signal as the freeze itself, so no automatic rule can tell legitimately-slow from wedged. It also spans several publish/progress paths rather than one chokepoint.
