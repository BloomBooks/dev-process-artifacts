What this PR is about

Problem

lameta's renderer reached into the main process through @electron/remote for its menus, right-click menus, app paths, window title, window events, the save dialog, and quitting. @electron/remote is no longer maintained, so every Electron upgrade risks breaking all of these at once.

What the PR does

  • Everything the renderer did through @electron/remote now goes over IPC, through src/mainProcess/windowIpc.ts and src/other/windowIpc.ts. The package is removed.
  • Menus. The renderer sends menu templates in which each click callback is replaced by a number, and the main process sends back the number of the item that was clicked. A click on a menu that has since been replaced does nothing.
  • Spell-check context menu. The main process forwards the right-click event, and the renderer asks it to cut, copy, paste, replace a misspelling, or add a word to the dictionary. HomePage used to register a new right-click listener on every update. There is now a single handler, so one right-click shows one menu.
  • Settings store. UserSettings reads the renderer's runtime environment instead of the main process's. Both hold the same values, and Vite's build-time replacement of NODE_ENV can't reach it there.
  • New E2E spec. e2e/mainProcessIntegration.e2e.ts covers each of these. It passed against the old remote-based code before the change.

The first commit only formats the files that the change touches, because the pre-commit hook formats every touched file. The second commit holds the change itself.

Worth knowing

  • Only run on Windows. The macOS-only lameta > Quit test is written but has never been run, and nothing on a Mac has been tried by hand.
  • The save dialog for Export is now attached to the main window; before, it had no parent window.

The file menu decides some of its items from the previously selected file

Right-clicking a file row that isn't selected yet builds the menu as if it were for the file that was selected before. If the session's own .session file was selected and you right-click a .txt file, the menu leaves out "Rename..." and "Open in program associated with this file type". The row's handler passes along a flag that was computed for the selected file (FileList.tsx:312, flag computed at line 234). This was already the case before this PR; the new E2E test selects the file first so that it doesn't depend on this.

addToDictionary.e2e.ts passes without checking anything, and changes your Windows dictionary

The existing test looks for a dictionary.txt in the project folder, which lameta never writes (addToDictionary.e2e.ts:68). The check sits inside an if that is skipped when the menu item can't be found, so the test passes whatever happens. When it does click "Add to Dictionary", the word "Xyzzyplugh" goes into the Windows spelling dictionary, which outlives the test run. The new spec tests Add to Dictionary properly, with a random word that it removes afterwards.

The Doondo unit test fails on this machine

The manual RO-Crate spec loads a real project from c:\dev\lameta projects\SayMore Data from Brian Parker\Doondo and expects a session folder named dde-bakala(BZV)1-ori (spec line 121). The copy on this machine has dde-bakala_BZV_1-ori, so one assertion fails. Nothing in this PR touches it, and it runs only where that folder exists, but it is the one red row in the unit tests. I'd leave it: it is a check against your own copy of a real project, which is what a manual spec is for.
