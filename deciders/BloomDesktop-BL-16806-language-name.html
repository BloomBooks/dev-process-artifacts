What this PR is about

Problem

A book can hold text in a language its collection has stopped listing: you set a collection to English, French and Spanish, make some books, then drop Spanish. The books keep their Spanish text, so Publish ▸ Text Languages still offers that language. But the name shown for it depended on the machine.

The CI runner readespagnol
A developer machine readespañol

Two people opening the same book, in the same collection, saw different names for the same language. Per-machine, not intermittent — CI failed it on every run.

Cause

Bloom asked LibPalaso for the language's name in the collection's metadata language (French, here). LibPalaso honors that request only where a native ICU library is findable, and Bloom ships icu.net but no icuuc.dll — so the answer turned on whatever else happened to be on the PATH.

What the PR does

For a language the collection does not name, Bloom now looks the name up in the Ethnologue data — the same data it already treats as a language's default name — instead of asking for it "in" another language. Every machine agrees, and the row reads Spanish.

  • A name the user gave in Collection Settings still wins, as before.
  • The looked-up name keeps BL-8174's script/region distinctions, so nsk-Latn stays distinct from nsk. Chinese is the one case this does not fully rescue — see the decision on the right.
  • An unlisted language (qaa-x-…) keeps the label the lookup builds, rather than nesting it inside itself.
  • If no name can be found at all, Bloom logs why and falls back to the tag.
  • The e2e test that caught this is un-skipped here — it was skipped on master while this was in flight — and now expects the stable name.

Should a dropped Simplified Chinese still say "Simplified"?

This is the one case where the new lookup loses information the old code had. When a collection stops listing zh-CN but a book still holds Simplified Chinese text, the Text Languages row now reads just Chinese, where it would previously have said Simplified (via whichever name that machine happened to produce).

It still reads differently from Traditional Chinese, which shows as Chinese-TW (Chinese) — so the two are distinguishable. But neither says which is which in the way a user would expect, and Devin points out the sharper case: a book holding both zh and zh-CN, after both are dropped, shows two rows that both read "Chinese", with nothing to tell them apart.

Why it happens: the Ethnologue lookup lower-cases the tag before matching, and LibPalaso's Simplified/Traditional special cases are case-sensitive, so zh-CN falls through to the base zh → "Chinese". The script-variant helper then strips the CN marker, because a collection-supplied Chinese name would already have carried "(Simplified)".

Either way you decide, this is recorded behavior rather than an oversight: it is pinned by a test case and described in the comments on both the production code and the test.
