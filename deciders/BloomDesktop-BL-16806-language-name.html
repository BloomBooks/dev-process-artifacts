What this PR is about

Problem

A book can hold text in a language its collection no longer lists — you set a collection to English, French and Spanish, made books, then changed it to English and French. Publish ▸ Text Languages still lists that language, correctly. But the name it shows depends on which machine Bloom is running on.

MachineThe Spanish row reads
GitHub windows-latest runnerespagnol
A developer Windows machineespañol

“espagnol” is the French word for Spanish. Two people with the same collection and the same book read different names for the same language, and neither is the name they would look for.

Cause

For a language the collection does not name, Bloom asked LibPalaso for that language's name “in” the collection's metadata language — French, above. That call honors the request only where a native ICU library is findable, and Bloom ships icu.net but no icuuc.dll. Where ICU is present it answers espagnol; where it is absent it ignores the request and returns the autonym español. So the name is decided by unrelated software on the user's PATH.

It is per-machine, not intermittent. CI gives espagnol on every run; this machine gives español every time. BookDataTests has carried an Or.EqualTo(…) around it for years with a comment that guessed ICU correctly and concluded “I can't find anywhere this actually shows up”. This list is where it shows up.

What the PR does

  • Looks the name up with GetBestLanguageName, which answers from the Ethnologue data on every machine: Spanish, everywhere. That is also what Bloom already treats as a language's default name.
  • Routes it through GetLanguageNameWithScriptVariants like the method's other branches, so BL-8174's script/region distinctions survive — otherwise a zh-CN and a zh-TW row would both read “Chinese”.
  • Restores, explicitly, the name-the-user-gave lookup that the old call was doing as a side effect for collection languages beyond Language1/2/3.
  • Turns the Or.EqualTo(…) pairs on this path into definite expectations, and adds two tests: one that the name is the same whatever the metadata language is, one that script variants survive.
  • Logs a lookup that fails rather than silently showing a bare tag.

1. Is “Spanish” the right label?

The fix makes the name stable, but it also settles which name. A language your collection has stopped naming now reads Spanish — its standard name — where before it read español or espagnol depending on the machine.

Two other candidates exist. The autonym (español) is what the method's old documentation promised and what this machine happened to show. And español (Spanish) is how bloom-player names languages, which is the direction the // TODO (default name BL-13703) note on this very method points. Any of the three is a one-line change at the same place; I picked the standard name because it is what Bloom already treats as a language's default elsewhere.

2. The other half of the same bug

The machine-dependent LibPalaso call still backs WritingSystem's own name derivation. So a language your collection does list, but whose name you never explicitly set, can still be named differently on different machines — the same class of problem, a different code path. BookDataTests still carries an Is.EqualTo("français").Or.EqualTo("Französisch") for exactly that.

I left it alone deliberately: that path decides names that get written into .bloomCollection files, so changing it is a bigger call than this PR should make.
