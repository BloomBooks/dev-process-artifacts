What this PR is about

Problem

Choosing a sign language from the Publish tab can record the language's own name in the collection settings as though the user had typed a custom name for it. Choosing the very same language from Collection Settings records it correctly. SignLanguageIsCustomName is Bloom's record of "the user deliberately gave this language this name, so never replace it with a looked-up one", so setting it when nothing was typed is simply wrong data. The error also runs the other way: a name the user really did type is recorded as not custom whenever it happens to match LibPalaso's name for the tag.

Cause

PublishApi decided the question by setting the writing system's Tag — whose setter derives the name through LibPalaso — and comparing that derived name against the chooser's DesiredName. That predates the new language chooser: when the code was written there was no DefaultName to compare against, and the workaround was carried across verbatim. LibPalaso and the chooser do not always agree; for mzc LibPalaso says "Madagascar Sign Language" and the chooser says "Malagasy Sign Language".

What the PR does

  • The Publish tab's sign-language handler now asks args.IsCustomName, which compares only the two names the chooser itself sent — the same rule all four Collection Settings sites already use (PublishApi.cs:476).
  • The remarks on IsCustomName no longer describe the divergence as intentional; they now say this is the only rule a caller should use, and why.
  • The test that deliberately pinned the divergence is replaced by two that pin the agreed answer in both directions, using the real mzc names.

Verified by hand in a running Bloom: picking Malagasy Sign Language from the Publish tab now writes SignLanguageIsCustomName=false, and typing "Madagascar Sign Language" over it writes true — that second case used to come out false.

Worth knowing

  • The bug is real but nearly invisible in Bloom's own screens. I went looking for a display-level symptom and did not find one for an ordinary bare tag like mzc: nothing renders a sign language name through WritingSystem.GetNameInLanguage, and GetLanguageNameWithScriptVariants ignores the flag when the tag has no script/region/variant codes. The confirmed symptom is the wrong value written to the .bloomCollection file. Where it would show is a sign-language tag carrying those codes (the chooser's CUSTOMIZE panel can produce one). The handoff note that led to this work predicted a localization symptom; that prediction turned out to be wrong, and BL-16760 says so rather than overselling the impact.
  • This PR cannot merge before #8236. LanguageChangeEventArgs.IsCustomName does not exist on master — it is added by #8236, which this PR is based on. See the first question on the right.
  • The base branch moved and was pushed. This run committed a two-line comment that was sitting uncommitted in the working tree (recording that the Collection Settings sign-language handler deliberately ignores args.IsRtl), merged master, and pushed language-chooser-data-mapping-tests. So #8236 has two new commits on it that its own last preflight did not cover.

Decisions

Keep this as a stacked PR, or fold it into #8236?

The fix needs LanguageChangeEventArgs.IsCustomName, which only exists on the language-chooser-data-mapping-tests branch behind PR #8236. I opened #8238 as a separate draft PR based on that branch, as the handoff note suggested, so the behavior change is reviewable on its own and has its own card. The cost is that two PRs now have to land in order, and #8236 is itself still in draft. The alternative is to move these commits onto #8236 and let one PR carry both the tests and the fix they were written to enable.
