What this PR is about

Problem

Publish → Apps shows a size bar so users can tell whether their app fits under the roughly 100 MB Android limit. Before a book had been built its figure was far too high: a Little Zebra book with big pictures showed 116 MB for an app that was really 16 MB. The real sizes that appeared after a build were thrown away each time the user came back to Apps.

Cause

Until a book's BloomPUB existed, Bloom counted every file in the book folder: full-size original pictures, a PDF left from an earlier publish, backups. A BloomPUB leaves most of that out and shrinks the pictures. And entering Apps deleted every BloomPUB made earlier, which also raced with the size request and caused an occasional error.

What the PR does

  • Estimates what publishing will actually produce. Counts only the files the BloomPUB export takes, leaves out pictures the book doesn't use (publishing deletes them), and applies publishing's rules to the pictures on the pages: shrunk to the publish resolution, an opaque PNG or shrunk JPEG at a typical JPEG rate, a picture that is or will be made transparent kept as a PNG. A PNG counts as opaque only when its header rules out transparency, since checking the pixels is too slow for the size bar.
  • Keeps built BloomPUBs between visits, in the user's temp folder rather than the collection, each with a record of what it was made from. The size bar and Build reuse one only while it still matches. The reuse logic is general BloomPUB code (BloomPubCache, BloomPubMaker.GetOrCreateCachedBloomPub) that the BloomPUB and Video tabs could use later.
  • Shows estimated and measured sizes differently (striped vs. solid), and adds a Measure exact sizes button that makes the missing BloomPUBs without building the app.

On the card's collection the four books are estimated at 14, 7.1, 9.0 and 8.8 MB against real BloomPUBs of 3.9, 6.8, 7.3 and 6.5 MB (the old method counted about 104 MB for the first). The estimate errs high; Measure gives the exact figures.

Worth knowing

  • A very old book that still stores a page picture as a background-image style, on a colored page, could be estimated low: publishing may make that picture a larger transparent PNG. John chose the simpler code over this edge case.
  • If the temp folder's path isn't plain ASCII and Windows can't give it a short name, the BloomPUBs go back inside the collection (Bloom App Data\RabWork\bloompubs), because Reading App Builder couldn't read them otherwise.
  • Neither Measure nor Build has been tried by hand since the BloomPUBs moved to the temp folder; the real-build test is the only check of that path.
  • Fonts installed on the computer are not part of a kept BloomPUB's record, so a font update alone doesn't make Bloom rebuild a book.
