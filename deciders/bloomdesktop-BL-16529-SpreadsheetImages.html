What this change does

Context for anyone reading this cold.

Exporting a book to a spreadsheet embeds a small preview of each picture. Bloom builds that preview by asking Windows for a blank image to draw into, and Windows stamps every such image with the current screen's resolution. Since Bloom started declaring itself PerMonitorV2 DPI aware, that stamp is 192 on a 200%-scaled display instead of 96. The spreadsheet library sizes a picture by dividing its pixel count by its own claimed resolution, so a preview claiming 192 was laid out at half the intended size — the reported "images only take up half the column width".

This was measured, not guessed. The three exports of the same book attached to the card show a picture identical in pixels but differing in claimed resolution, and the extent follows the arithmetic exactly:

ExportPreview pixelsClaimed dpiLaid out over
6.4 at 100%150 × 10496150 px right
6.5 at 100%150 × 10419275 px half
6.5 at 200%300 × 208192150 px right

The earlier fix doubled the pixel count, which cancels a 192-dpi error only when the scale is exactly 200%; in general it produced 150 px × scale / 200. That also explains the reproducibility split: the two errors cancel whenever the screen's stamp and the scale factor agree, which they did on your machine and did not on Heather's.

The fix stamps every preview with 96 dpi and removes the display compensation entirely, so export now queries no monitor at all and any machine produces the same file.

Decision

There is a way to keep the previews sharp and still have every machine export the same file

When you chose "leave as is" on the previews looking smaller, the only alternative I had offered was narrowing the column. Devin's review surfaced a third option, so it is worth putting to you once.

The preview's displayed size is its pixel count divided by the resolution stamped on it. Today we embed a 150-pixel-wide picture stamped 96, which occupies a certain physical width on the page. Embedding a 300-pixel-wide picture stamped 192 occupies exactly the same physical width — but carries twice the detail, so it stays crisp when someone zooms in or views it on a high-resolution screen. Crucially it is still the same on every machine, because both numbers would be fixed in the code rather than read from the display. It is not the old bug returning: the bug was the two numbers disagreeing, not either value in particular.

The cost is file size — the old 200% export of the reporter's book was about two and a half times bigger than the 150-pixel one — and a second round of checking in both spreadsheet programs.
