What this change does

Context for anyone reading this cold.

Exporting a book to a spreadsheet embeds a small preview of each picture. Bloom builds that preview by asking Windows for a blank image to draw into, and Windows stamps every such image with the current screen's resolution. Since Bloom started declaring itself PerMonitorV2 DPI aware, that stamp is 192 on a 200%-scaled display instead of 96. The spreadsheet library sizes a picture by dividing its pixel count by its own claimed resolution, so a preview claiming 192 was laid out at half the intended size — the reported "images only take up half the column width".

This was measured, not guessed. The three exports of the same book attached to the card show a picture identical in pixels but differing in claimed resolution, and the extent follows the arithmetic exactly:

ExportPreview pixelsClaimed dpiLaid out over
6.4 at 100%150 × 10496150 px right
6.5 at 100%150 × 10419275 px half
6.5 at 200%300 × 208192150 px right

The earlier fix doubled the pixel count, which cancels a 192-dpi error only when the scale is exactly 200%; in general it produced 150 px × scale / 200. That also explains the reproducibility split: the two errors cancel whenever the screen's stamp and the scale factor agree, which they did on your machine and did not on Heather's.

The fix stamps every preview with 96 dpi and removes the display compensation entirely, so export now queries no monitor at all and any machine produces the same file.

Decision

Our automated tests cannot actually catch this bug coming back

The whole fix is a single line that stamps each preview picture with 96 dpi. The catch is that on a computer whose Windows display Scale is 100% — which is what our build machines use — Windows already stamps 96 anyway. So the two new tests pass whether or not that line is present, and they will keep passing on the build server if someone later deletes it while tidying up.

The bug would then come back silently, and only on high-DPI machines: exactly the situation that made this card take three rounds of fixes and more than two days to pin down, because it was invisible on the developer's own machine. Devin raised the same point independently. The test's doc comment does say this out loud, so nothing here is hidden — the question is whether to close the gap.

For your information

On a scaled-up display, previews will look smaller than 6.5 shows them today

If your Windows Scale is above 100%, the current 6.5 build enlarges the preview pictures so they fill the image column. After this change it stops doing that, and previews go back to the size Bloom 6.4 produced — which on a scaled-up display looks narrower than the column.

That is the deliberate trade, and the reason to accept it is that it is the only way the same book can export to the same spreadsheet on every machine: any sizing keyed to the exporting computer's display is wrong the moment the file is opened somewhere else. Heather already said on the card that she can live with the small picture being a bit smaller, and you chose this approach knowing the trade-off. Recorded here so the change of appearance is not a surprise to anyone reviewing.

For your information

The same underlying problem probably exists in book thumbnails

The reason the previews carried a wrong resolution is not specific to spreadsheets: it is that Bloom asks Windows for a blank image to draw into and inherits the screen's stamp. The shared helper that does that is also used to make the small book thumbnails, so those are very likely carrying a screen-dependent resolution too.

Nothing visibly wrong has been reported there — a thumbnail Bloom draws itself at a known pixel size may never expose it — and chasing it is out of scope for this card. Left untouched on purpose.

For your information

Two out-of-date test-ideas comments are still on the card

The card carries test-ideas comments from the two earlier rounds, and they tell a tester to expect the preview pictures to grow with the Windows Scale setting — the opposite of how it now works. They could not be corrected in place: the tracker Bot is refused permission to edit comments written under your own account.

So a fresh round-2 comment was posted instead, opening with a plain statement that it supersedes them. A tester reading the card from the top will still meet the stale advice first, which is the only reason this is worth your attention.
