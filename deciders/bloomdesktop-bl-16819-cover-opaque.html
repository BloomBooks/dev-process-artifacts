What this PR is about

Problem

On the front cover, choosing Opaque (or Transparent) from the image's Transparency menu did not stick. Set it, quit Bloom, reopen the book, and the cover image is back on Auto, so a line-art picture on a colored cover is rendered with its background made transparent again. Images on content pages kept the setting; only the cover lost it.

Cause

The Transparency choice is stored as a bloom-opaque or bloom-transparent class on the cover's image. Every time a book is opened, Bloom rebuilds the front matter from the xmatter template and refills the cover image from the book's data div. The refilling code (UpdateImageFromDataSet) copied the image's source back, and its style in a couple of special cases, but never its classes, so the choice was thrown away with the old page. It was saved correctly in the data div; it just never made it back onto the page.

A second, hidden half: saving a page merges the image's classes into the data div as a union, only ever adding. So even with the classes restored, changing Opaque back to Auto (or to Transparent) would have brought the old choice back on the next open.

What the PR does

  • When the cover image is refilled from the data div, a short list of image classes that count as user data (_imgClassesToRestoreFromDataDiv, currently the two transparency classes) is restored from the saved class list. The data div is authoritative, so a listed class it lacks is removed, which is how switching back to Auto also survives a reopen.
  • The two transparency classes are also removed from the data div when the saved page no longer has them, so a changed choice is recorded rather than accumulated.
  • No other classes are copied. In particular bloom-imageLoadError is still re-derived each time the book opens (BL-14241).
  • Unit tests in BookDataTests cover the save-then-reopen round trip for Opaque and Transparent, changing the choice afterwards (to the other override and back to Auto) and reopening again, the removal of a stale override when the data div says Auto, and that no unrelated classes are copied. They failed before the fix.

Worth knowing

  • The fix is verified by unit tests only. It has not been exercised by hand in a running Bloom; the QA test ideas on the card cover that.
  • A branding image that also carries data-book="coverImage" (a rare arrangement, BL-16776) would now receive the cover's transparency class too. In current books the branding block is restored first and that image is replaced before it is reached, so it is unaffected.
