What this PR is about

Problem

Bloom's 6.5 features shipped essentially blind. Every existing analytics event came from C#, so anything implemented in React could only be measured by inventing a bespoke endpoint for it — which in practice meant it wasn't measured at all. Nothing under Publish/Rab reported anything, the AI Image Editor and the new image chooser reported nothing, and Change Picture — the one event covering how a picture gets into a book — was bypassed by both new 6.5 image routes, so even the old count was quietly low.

Cause

A second, subtler problem made this hard to fix safely. DesktopAnalytics decides whether to send an event inside its own Track method, and Bloom constructs it with allowTracking: false in DEBUG. So a developer could not tell "fired but not sent" from "never fired" — a new event was easy to write, easy to believe in, and impossible to observe without shipping to alpha.

What the PR does

Seven events, chosen by one test: would the answer change a decision? Counting use of a capability we already know is essential does not. Splitting a known behaviour into actionable parts does.

  • The plumbing. POST analytics/track plus a trackEvent() helper, so front-end code can report an event at all; C# fills in BookId, which React in the edit view does not know. BloomAnalytics wraps DesktopAnalytics and logs every event before handing it on, so a developer running ./go.sh watches events scroll past. Every call site goes through it, and build/check-csharp-analytics.sh keeps it that way: a partial log would be worse than none, since a missing line would read as "not instrumented" as readily as "did not happen".
  • Where pictures come from. Change Picture gains one source field naming the route — pixabay, openverse, a collection slug, local-disk, clipboard, ai-editor — repairing the under-count on the way past.
  • Whether searching works. Image Chooser Closed, one event per visit. A result count could never answer this: Pixabay and Openverse nearly always return something, so the failure is a full page of wrong pictures, and only what the user did next reveals it.
  • What AI costs and whether it lands. AI Image Editor Generate (from the ai-editor over the existing bridge: cost, model, retries, failures) and AI Image Editor Closed, one event per session, where an appliedCount of zero is the abandoned case.
  • A Pro feature with no usage data. Cover Layout Changed — the baseline nobody has after two releases of charging for custom cover layouts.
  • A heuristic we cannot otherwise evaluate. Image Transparency Set. Every explicit choice is a user telling us which way our line-art detection was wrong.
  • A path CI cannot run. Publish App, with the stage as a field. CI never runs a real Reading App Builder build, so field telemetry is this path's only continuous coverage.
  • One fix that is not analytics. "Use this copyright and license for all images" re-read every picture's metadata once per picture — about 160,000 reads on a 400-picture book, appearing to freeze Bloom for minutes. Found while instrumenting that operation; the event that found it is not being kept, the fix is.

No search terms. The image gallery still hands Bloom the search term, so revisiting that is a one-property change, but it is dropped at Bloom's boundary deliberately rather than by omission.

Scope. This supersedes #8215, which instrumented 22 events. That set was judged too large; thirteen event names were dropped and four merged into two. The event catalogue records what each dropped event would have told us, and the parked branch keeps the code.

Should the events carry the one thing that says who could have used the feature?

A user's subscription tier is already recoverable from what we send: BrandingProjectName rides on every event, and the tier follows from that string by fixed rules. So "how many Pro users were active this month" needs nothing new.

But the subscription is not what actually gates the AI Image Editor. It — and the App Builder — sit behind an experimental features checkbox as well: a per-machine setting, ticked in Collection Settings → Advanced, and nothing in any event says whether it is on. That gap breaks the inference in the damaging direction. Few AI sessions among Pro users could mean the feature isn't wanted, or that almost nobody found the checkbox, and those call for opposite responses.

The fix is one line beside the seven properties Bloom already sets per collection, sending the list of enabled experimental tokens. It gives both the AI events and the Publish App events a denominator they currently lack.

One line in CollectionSettings.SetAnalyticsProperties, next to BrandingProjectName. No new event, no new endpoint. Recommended because the alternative is shipping seven events and then finding there is nothing to divide them by.
The same one line, later. Keeps this PR to exactly the seven events that were agreed, at the cost of a release's worth of data that cannot be interpreted.

The AI-editor event waits for the session to end, which loses a session that never ends

Merging the old Commit and Cancel events into one turned out not to be a rename. Both firing under a single name would count some sessions twice; suppressing the second would let a session with two commits — one failing, one succeeding — be recorded by whichever answered first, filing a session whose pictures did land as one that discarded everything.

So the counts now accumulate, and one event is sent when the session settles: the overlay gone and no commit still outstanding. The trade is that a session which never closes — the user quits Bloom with the editor still open — reports nothing at all, where the old code would already have sent its commit figures. In the ordinary flow a successful apply closes the overlay immediately, so this only bites after a partial failure that the user then walks away from.

I judged that the smaller and less misleading of the two losses, and the tests pin both halves. Flagging it because it is a behaviour change I made on my own initiative inside something you asked for as a merge.

Small change, but it reintroduces the double-count this design exists to avoid; the figures would need de-duplicating downstream instead.
