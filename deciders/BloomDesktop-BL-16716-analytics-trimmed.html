What this PR is about

Problem

Bloom’s 6.5 features shipped essentially blind. Every existing analytics event came from C#, so anything implemented in React could only be measured by inventing a bespoke endpoint for it — which in practice meant it wasn’t measured at all. Nothing under Publish/Rab reported anything, the AI Image Editor and the new image chooser reported nothing, and Change Picture — the one event covering how a picture gets into a book — was bypassed by both new 6.5 image routes, so even the old count was quietly low.

Cause

A second, subtler problem made this hard to fix safely. DesktopAnalytics decides whether to send an event inside its own Track method, and Bloom constructs it with allowTracking: false in DEBUG. So a developer could not tell “fired but not sent” from “never fired” — a new event was easy to write, easy to believe in, and impossible to observe without shipping to alpha.

What the PR does

Adds seven events, chosen by one test: would the answer change a decision? Counting use of a capability we already know is essential does not. Splitting a known behaviour into actionable parts does.

  • Plumbing. POST analytics/track plus a trackEvent() helper, so front-end code can report an event at all; C# fills in BookId. BloomAnalytics wraps DesktopAnalytics and logs every event as well as sending it, so a developer running ./go.sh watches events scroll past, and check-csharp-analytics.sh keeps every call site going through it.
  • Where pictures come from. Change Picture gains a source field naming the route, repairing the under-count on the way past.
  • Whether searching works. Image Chooser Closed, one event per visit. A result count could never answer this: the providers nearly always return something, so the failure is a page of wrong pictures, and only what the user did next reveals it.
  • What AI costs and whether it lands. AI Image Editor Generate and AI Image Editor Closed, where an appliedCount of zero is the abandoned case.
  • Three things we have no data on at all: Cover Layout Changed (a Pro feature charged for over two releases), Image Transparency Set (every explicit choice is a user telling us which way our line-art detection was wrong), and Publish App (CI never runs a real Reading App Builder build, so field telemetry is that path’s only continuous coverage).
  • One fix that is not analytics. “Apply this information to all images” re-read every picture’s metadata once per picture — about 160,000 reads on a 400-picture book, appearing to freeze Bloom for minutes. Found while instrumenting it; the event that found it is not being kept, the fix is.

No search terms are sent and nothing is written to the user’s disk. This supersedes #8215, which instrumented 22 events and was judged too large; the event catalogue records what each dropped event would have told us.

Local reviewComplete — 1 finding, fixed

Light pass, done inline. It found a real defect in this branch’s own new test code. BloomDebug.Fail is [Conditional("DEBUG")], which removes the call from the calling assembly — and the caller here was BloomTests itself. Built Release, the BloomDebug.Fail(…) inside each test would not be emitted, nothing would throw, and Assert.Throws would fail. build/agent-dotnet.sh builds Debug, so it passed locally, while build/Bloom.proj defaults to Configuration=Release and the nightly runs BloomTests.dll out of output/Tests/Release/x64 — so the nightly is where it would have broken, days after merge, in a workflow nobody watches per-PR. The fixture is now #if DEBUG, verified in both configurations.

Over to you

Should bloom-image-gallery get a version tag?

This PR reads a search-report callback that exists in bloom-image-gallery 0.0.4 and not in 0.0.3, so it advances the lockfile to the gallery’s current tip. The awkward part is how that dependency is declared: as github:BloomBooks/bloom-image-gallery with no tag at all — the repository has never been tagged. That makes the lockfile the only thing pinning the version, and pnpm holds a git dependency at its locked commit until someone runs an explicit pnpm update. A plain pnpm install will not pick up a new gallery release. That is why master sat on 0.0.3 for five days after the gallery PR adding these APIs had already merged, and why the first attempt at this branch’s merge failed to compile.

Devin raised the same fragility. It is not a bug in this PR — the version is correct now — but it will recur every time the gallery changes. Leaving it alone is recommended because the version is right, and one confused merge every few months is cheaper than establishing a release process for a repo only Bloom consumes; but it is a judgment call about someone else’s repo, so it is yours rather than mine.
