What the fix is3 commits

The three subscription tools (Overlay/Canvas, Motion, Music) show a Bloom-subscription badge at the right end of their toolbox header. That badge sits inside the MUI AccordionSummary whose root toggles the tool open or closed, and its click handler never stopped the click bubbling. So clicking the badge of the open tool also collapsed it — the closed tools and More… jumped up — and then the effect that syncs with the legacy toolbox saw nothing expanded, read legacy's unchanged current tool and re-expanded it. Hence a jump that comes straight back. Without a subscription the dialog covered the flash, which is why only subscribers saw it.

d834501

The badge click stops at the badge

requiresSubscription.tsx:165 — event.stopPropagation() before anything else. With a subscription, clicking the badge now does nothing at all; without one it shows only the dialog.

0602514

The same flash by another route

ToolboxRoot.tsx:894 — clicking the header of the already-open tool produced the identical collapse-then-re-expand. The toolbox always has an active tool, so there was never a state to land in; onChange now ignores the collapse instead of undoing it after the fact.

4f364c8

An operator-precedence fix noticed on the way past

requiresSubscription.tsx:466 — a?.b ?? document !== document parsed as a?.b ?? (document !== document), so the test asked "is there a page iframe body?" rather than "is it in another document?". Behaviour-preserving for every current caller; it would only have misrouted a future caller running inside the page iframe itself.

Decision · behaviour

A badge on a collapsed tool no longer selects that tool

In the Edit tab, the tools are stacked as headers and you click a header to switch to that tool. The subscription badge is a small image at the right-hand end of three of those headers. Because the fix stops a badge click from reaching the header, clicking the badge of a collapsed tool no longer opens it. For someone with a subscription that click is now completely inert; for someone without one it still brings up the "requires a subscription" dialog.

So a subscriber gains a small dead spot: roughly a 1.5em-wide image at the right end of an otherwise fully clickable row. This follows your instruction — "if you have a subscription, clicking should do absolutely nothing" — and it is what makes the badge behave consistently in both places it appears. Recommending it stay as it is for exactly that reason; the alternative reintroduces a difference between the badge on the open tool and the badge on a closed one.

Decision · behaviour

The open tool can no longer be closed at all

Commit 2 makes the toolbox ignore an attempt to collapse the tool that is already open — by clicking its header, and equally by pressing Enter or the space bar on a focused header. Devin raised this as an observation and asked whether any product expectation allows every tool to be collapsed at once.

It was already effectively true before this branch: Bloom always keeps one tool active, and the sync effect re-expanded whatever the legacy toolbox still considered current, so the only thing a collapse attempt ever produced was the flicker this card is about. Before 6.5 the jQuery accordion never set collapsible, and jQuery UI's default of collapsible: false meant the open panel could not be closed either — so this restores 6.4 behaviour rather than introducing a limit. Recommending it stay, since making "no tool open" genuinely possible is a real design change, not a tidy-up.

Decision · verification

The C# test suite did not run in this worktree

Running the C# tests here fails before any test executes: the build can't find IDevice or PodcastUtilities, which AGENTS.md names as the sign that a worktree hasn't fetched its C# binary dependencies yet. The documented remedy is ./init.sh — but its last step is pnpm run build, the full front-end build I'm told not to run, because it wipes the shared output\browser and disrupts a Bloom running from the dev server. So I stopped rather than spring that on a live session.

This branch changes two .tsx files and no C# at all, so there is no path from it to a C# test. Recommending we accept the gap rather than spend a dependency fetch and a full front-end build on unrelated tests; say the word and I'll run both.

FYI · test coverage

No automated test guards either behaviour

You asked to skip the test — "simple to test in Bloom, not expected to regress" — so neither the badge click nor the ignored collapse has a test. Recording it because both are the kind of thing a future edit can quietly undo: a stray wrapper around the badge, or someone restoring the old onChange, would bring the flicker back with every check still green.

The test I had planned would render ToolboxRoot with the feature-status hooks mocked as subscribed, click the badge, and assert the active tool didn't change. ToolboxRoot.spec.tsx already exists and does exactly this kind of thing, so it's a small addition rather than new scaffolding.
