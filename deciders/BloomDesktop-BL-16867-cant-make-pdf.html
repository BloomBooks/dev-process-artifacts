What this PR is about

Problem

In 6.5 BetaInternal, making a PDF fails every time, for every book, for every user. The progress dialog reaches “Compressing PDF”, a Bloom problem dialog appears, and no PDF is produced. Uploading a book to Bloom Library fails at the same point, because that makes a PDF preview first. Two people reproduced it, one on a brand-new empty book. 6.3 and 6.4 are fine.

Cause

Bloom, BloomPdfMaker and BloomFreezeDoctor are three separate .NET apps that we install into one folder — which can hold only one copy of each DLL, so the last one built overwrites the others’ copies. The Freeze Doctor, new in 6.5, pulls in Microsoft.Diagnostics.Runtime, whose Microsoft.Extensions.* dependencies are 6.0.0 — below the 8.x/9.x Bloom resolves — and Bloom.proj builds it last.

The .NET host binds by simple name and accepts a higher assembly version than the one asked for, but rejects a lower one. PdfSharp asked for Logging.Abstractions 8.0.0.0, the folder held 6.0.0.0, and it died with a FileNotFoundException naming a file that was sitting right there.

Confirmed against the shipped BloomBetaInternal-6.5.3041-full.nupkg: six Microsoft.Extensions.* assemblies ship at 6.0.0.0 against the 8.x/9.x Bloom’s own deps.json declares.

What the PR does

  • Pins Microsoft.Extensions.Logging 8.0.1 and Logging.Abstractions 9.0.5 in BloomFreezeDoctor.Core (csproj:96). Their closure is exactly the set Bloom resolves, so one copy of each now serves both apps. This is the rule that csproj already stated, and that BloomPdfMaker has always followed — only the transitive tail had gone unexamined.
  • Adds build/check-dependency-versions.ps1, run from Bloom.proj’s BuildInternal (Bloom.proj:210) once the apps are in the folder together. It compares every deps.json and fails the build on any assembly the co-located apps disagree about, naming which app claims which version.

Nothing looked at the folder as a whole before, which is why this reached BetaInternal.

Worth knowing

  • No unit test can catch this class of bug. The existing PdfMakerTests exercise the exact failing code path and pass regardless — the vstest host supplies its own newer Logging.Abstractions, so the test process never sees the folder Bloom actually ships. The build-time check is the only thing that covers it.
  • Nothing here was verified by launching Bloom. The fix was verified structurally: the rebuilt BloomFreezeDoctor.deps.json now resolves exactly Bloom’s six versions, and the new check passes on that output and fails on the shipped 6.5.3041 package. No PDF was made by hand from an installed build.
  • There is a free end-to-end check already running. Per the note on the card, the nightly’s bulk-upload end-to-end test has failed on this exact exception for three consecutive runs (12–14 Sept), because the headless Bloom doing the upload hits the problem dialog with nobody to dismiss it and hangs after “Compressing PDF”. So the first nightly to run on a tree carrying this fix is a real-world verification at no cost — worth watching rather than hand-building an installer.
  • The check sees only the installer build’s output folder. Test assemblies are not in it — BloomTests builds to output\Tests\... and BloomFreezeDoctor.Tests isn’t built by BuildInternal at all — so the NUnit 3-vs-4 difference between those two test projects is not a false positive here.

Decision 1 · scope of the new check

Should the conflict check also run on ordinary developer builds?

Right now the check runs only from Bloom.proj’s BuildInternal — the path CI and makeWindowsInstaller.bat take. A developer building in Visual Studio, or running ./go.sh, never runs it. That is deliberate: the check needs all three apps built side by side into one folder, which only the installer build guarantees, and the invariant only actually matters for a shipped installer.

The cost of leaving it there is feedback latency. Someone who adds a clashing package learns about it from a CI build rather than from their own, possibly a day later.

Decision 2 · the other branch

How should master get this fix?

master has the identical clash — same three apps, same one folder, same Microsoft.Diagnostics.Runtime dependency tail. It is currently 203 commits ahead of Version6.5. You asked for this fix to land on Version6.5 only, so nothing has been done to master.

Worth knowing before you choose: master’s package graph may have moved on, so the two pinned versions that exactly match Bloom on Version6.5 might not be the versions master resolves. If they aren’t, the new check will say so the first time an installer is built there — loudly, and with the numbers.

Decision 3 · verification

Do you want a real installed build tested before this goes to review?

The fix is verified structurally but not experientially: nobody has installed a build carrying it and made a PDF. Doing that properly means building an installer (makeWindowsInstaller.bat), installing it, and making a PDF — which is also the only way to see the new check run in its real setting.

Against that: the failure mode is completely understood, the shipped artifact was inspected directly, and the same evidence that proves the bug proves the fix. QA will exercise it on the next BetaInternal build regardless — and the nightly’s bulk-upload end-to-end test, which has been failing on this exact exception since 12 September, gives the same proof for free once it runs on a tree carrying the fix.
