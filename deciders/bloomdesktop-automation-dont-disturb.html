What this PR is about

Problem

Bloom treated --automation as "never take the foreground". But ./go.sh passes that to every developer Bloom, so a developer testing by hand got a Bloom that never came to the front. CI, where nobody is at the screen, lost coverage of anything that depends on which window is active. And dialogs still grabbed the foreground during test runs.

What the PR does

  • A new flag, --dont-disturb, owns the rule and covers more windows: the main window, the splash screen, every React dialog, Bloom's WinForms dialogs such as Collection Settings and the progress dialogs, the bring-to-front behind the Choose Collection and minimum-version dialogs, and the bring-to-front when a Bloom Library download starts. Native Windows dialogs (file pickers, raw message boxes) are activated by Windows regardless; that is documented.
  • --automation keeps the rest: running beside other Blooms, the launcher's ready line, window placement. The Choose Collection dialog now follows that placement, centred on its real size.
  • The e2e and visual-regression suites use the flag on a developer's machine but not on CI, and both log their choice. BLOOM_E2E_DONT_DISTURB=0 runs exactly like CI.
  • ./go.sh passes the flag on; the run-bloom skill's --ensure-running (how an agent starts Bloom) always uses it, and your plain ./go.sh does not.
  • Agent guidance says when to use it, and a CI-only e2e failure points its diagnoser at focus.
