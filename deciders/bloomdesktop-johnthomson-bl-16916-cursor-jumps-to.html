What this PR is about

Problem

With the Leveled (or Decodable) Reader open, a user types some text, clicks the dark area around the page, then clicks into the middle of the text and types. The first character lands where they clicked, but half a second later the caret jumps back to where it was before the click away, and everything after that goes in the wrong place.

Cause

When a text box loses the focus, the reader tool's focus-out handler marks up the text inside a CKEditor bookmark save-and-restore. When the click lands on nothing, restoring the bookmarks puts the focus straight back into the box, after CKEditor has locked its selection. The box never loses the focus again, so nothing unlocks it, and every later markup pass puts the caret back where the lock says it is.

What the PR does

  • The handler (decodableReaderTool.tsx:156, shared by both reader tools) keeps the bookmarks only when the focus leaves Bloom's window, e.g. for another program. Any click inside the window, the toolbox included, now skips them; before, only a move to another text box did.
  • A new e2e test reproduces the bug, plus a second one for clicking in the toolbox. The Leveled Reader's "words on this page" count gets a test id, so the test can tell when the markup pass has run.
