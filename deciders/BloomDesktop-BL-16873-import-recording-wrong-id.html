What this PR is about

Problem

A user imports an mp3 with the Talking Book tool’s Import Recording, and Bloom acts as though it worked — no error, the file really is copied into the book’s audio/ folder. But the text box is not narrated: Check/Listen plays nothing, and the published book has no audio for it. Worse, the recording is not merely lost: it can land on another page, which then silently plays audio belonging to the page the user was actually on. Until this merges it fails the nightly most mornings — two of the last three runs.

Cause

Bloom names a narration file after the id of the element that owns the audio — the one carrying audio-sentence. getCurrentAudioId() instead read this.highlightedElement, and the highlight is not always on that element: it can sit on a sub-element (a soft-split segment, a paragraph inside the box), or on a detached node, because CKEditor replaced the paragraph it lived in or the page changed underneath it. The window is normally tiny — a repair tick runs every 200 ms — which is why this shows up on a loaded CI runner rather than an idle developer machine.

What the PR does

  • getCurrentAudioId() asks getCurrentAudioSentence() instead of reading the highlight, so the id it reads — and any id it mints — lands on the element that owns the audio.
  • Before naming a file, the import re-points a stale selection at the page being shown: by id when that element is still there, else the page’s default selection, else — only when the page has exactly one recordable box — that box. It deliberately does not pick “the first of several”: on a multi-box page that is a guess that could overwrite narration already there, which would be worse than the orphaned file it replaced.
  • The microphone path gets the same guard, behind a synchronous staleness check so the normal case adds no await — an unconditional one delayed recording = true past a fast mouseup and left the record button stuck looking active.
  • The import holds off page saving while it writes, so a save cannot serialize the page before the id is attached.
  • Three regression tests — the sub-element case, the detached case, and recovery of the right box on a two-box page. Each fails without its own half of the fix.

Not addressed here, deliberately: the “replace this recording?” prompt reads a cached Play status rather than asking about the element being written to, so it can be skipped. That is pre-existing — this branch never touched it — and is documented in a comment at handleImportRecordingClick.

Worth knowing

  • The microphone path is changed but not exercised by hand. It could not be: a real microphone cannot be automated. The guard is a no-op unless the selection is already off-page, so it cannot make a working case worse — but ordinary recording is the thing to try first if anything feels off. The QA notes on the card call this out.
  • A known gap is left in deliberately. On a multi-box page where the selection cannot be recovered, the import now does nothing rather than guessing. The symptom is an import that appears to do nothing; that is the chosen behaviour, and the card’s test notes say so, so a tester does not file it.
  • The save-delay narrows the window rather than closing it. The shared delay mechanism gives up after four seconds and captures the page anyway, so a large mp3 on a slow disk can still be caught half-done. Raising that cap would affect every user of the mechanism, so it was left alone and noted in the code.
  • The nightly stays red until this merges — it has failed two of the last three runs on this bug alone. That is recorded on the card and in AUTOMATION-DEBT.md, so a red nightly whose only failure is this one needs no investigation.
