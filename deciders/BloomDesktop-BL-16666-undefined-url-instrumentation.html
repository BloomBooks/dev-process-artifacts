What this branch is

The second of the two 404 patterns in Sentry issue 2699459502 — the ones reporting paths like Temp/undefined. The old card framed these as C# building a temp path from a name that was undefined. That is wrong: it is the browser turning a JavaScript value into the *text* “undefined” and asking for a file by that name. The server can only report that a file called undefined is missing, never who asked — which is why finding BL-16447, the one instance we ever fixed, took so much guessing.

It fixes no instance. It makes the next one name itself: the server now reports the referring page, and the front end reports a source-mapped JavaScript stack.

Also worth knowing, because it changes what we will see: the temp folder was incidental. A bare undefined src resolves against the document's base url, and these reports were being suppressed for anything under the current book folder — so the bug was invisible whenever it happened on a book page. We had been seeing a filtered slice. That suppression is now lifted.

What Devin caught that mattered

Recording these because they are the substance of the run, and because two of them were defects I would have shipped.

  • The reports would have interrupted users. Lifting the book-folder suppression meant these requests reached a report that uses PassiveIf.All — a toast on every channel, plus a modal on beta — on pages that previously failed silently. My PR text had described the consequence as “more Sentry volume” and missed this entirely. Now reported with ModalIf.None/PassiveIf.None, and under its own Sentry message so it does not bury itself in the general one.
  • The stacks pointed at a bundle, not our code. errorHandler source-maps its stacks; the new detector was handing over a raw one. For a feature whose only job is to name a line of our source, that would have produced reports nobody could act on — it would have looked like it worked.
  • Only the first report of each kind would ever have been sent. The once-only rule was keyed on the message, and every component that sets an image src to undefined produces the same message — so we would have reported whichever ran first and hidden the rest for the session. That is the exact blind spot this feature exists to remove. Keyed on the stack now. My first attempt at a cleverer key picked a frame two call sites share and silently reinstated the bug; a new test caught it.
  • A stale test assertion. When I repointed card references to BL-16666 the message changed and its assertion did not. I had re-run the C# suite after that rename but not the front-end one — which is exactly how it got through, and why the fast gate exists.

1. Alpha testers will see “A JavaScript error occurred” pop-ups

The front-end half reports through the same path Bloom uses for real JavaScript errors (common/error), and that handler shows a small notice on the alpha channel, labelled “A JavaScript error occurred”. So while we are hunting this bug, alpha testers could see up to ten such notices in a session — for something that has not actually gone wrong for them.

This partly undoes the care taken on the server side, where I deliberately made this class silent. But it is a real judgement call rather than an obvious defect: alpha users are our own testers, and a visible notice is arguably how they find out there is something to report. That is why I have not decided it.

2. No cap on the server side, unlike the front end

The front-end layer reports each distinct problem once and stops after ten, because each report is an http post from the browser. The server side has no such limit: every bogus request produces a Sentry entry.

I left that asymmetric on purpose. Sentry already groups identical events, and the per-event count is information — it tells us how often a bad url is actually being requested, which the front-end cap deliberately throws away. But it does mean this PR increases Sentry volume, on top of the increase from lifting the book-folder suppression, and you are the one who watches that.
