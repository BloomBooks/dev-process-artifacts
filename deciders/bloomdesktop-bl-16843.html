What this PR is about

Problem

On 6.5, saving a page deletes every zero-width space (U+200B) from the text. Khmer, Thai and Myanmar keyboards insert that character between words, so text is silently altered on every save, and the Leveled and Decodable Reader tools see a whole paragraph as one word: a 26-word Khmer paragraph counted as one 98-letter word, so no level limit can ever trip. Anything rendered without a dictionary for those scripts loses its line breaks. 6.4 keeps the characters.

Cause

CKEditor places a U+200B "filling char" at the caret and tracks it by node; its own data export already omits it. When Bloom rewrote a box's HTML from the live DOM, that node was detached and the character became orphaned text that got saved (BL-16490). The 6.5 fix for that stripped every U+200B from a box on save and reader markup, which also removed the real word breaks.

What the PR does

  • The blanket strip is gone. CKEditor's exported data is used as-is on save, reader markup and talking-book cleanup, so real U+200B word breaks survive.
  • A new helper takes out only the one character CKEditor planted in the node it is tracking (a following plain space becomes an nbsp, as CKEditor does), leaves any word breaks the user typed into that node alone, and drops CKEditor's reference to it.
  • It runs before every rewrite that copies live HTML back into a box, so a filling char can never be orphaned: the nbsp and comment clean-ups after each typing pause, and show/hide invisibles.
  • Tests cover the helper, both clean-ups, and U+200B word breaks surviving save.

Books that already carry an orphaned U+200B from earlier 6.5 builds keep it, the same trade-off 6.4 made for BL-16808.

Worth knowing

  • Verified in a running Bloom from this branch, driven over CDP: Khmer words with U+200B survive a page switch and reload; the Leveled Reader counts four such words as 4 (the card's failing case); Talking Book sentence markup keeps them; both typing-pause clean-ups rewrite a box without losing them; a filling char planted next to bold text is gone after the nbsp clean-up, the reader markup, show/hide invisibles, and a save, with the caret kept. Not tried with a real Khmer keyboard driver.
  • CKEditor itself deletes every U+200B in the node holding its filling char on the next caret move, so a word break typed within a fraction of a second of placing the caret right after bold or italic text can be eaten by CKEditor. This is CKEditor 4.5.1 behavior, identical on 6.4 (the library is unchanged), and out of this PR's scope.
  • The worktree has an uncommitted change to src/BloomBrowserUI/package.json that I did not make and did not commit: the bloom-player and bloom-image-gallery pins became floating versions, apparently from tooling that ran with master's installed modules. Release branches pin, so it stays out of the PR.

Game prompt copy: also guard it?

The drag-activity prompt dialog copies its editable's live HTML into the page's permanent element on every keystroke. If CKEditor is holding a filling char in that dialog at the time, the U+200B is copied as plain text and saved. This is pre-existing: 6.4 behaves the same, and the removed blanket strip never covered that element either, so it is not a regression from this PR. Because the copy happens on every mutation, adding the removal there would also remove CKEditor's caret helper while the user is typing next to bold text, so leaving it is the safer default.
