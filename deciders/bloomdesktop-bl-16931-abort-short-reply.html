What this PR is about

Problem

In a debug build, Bloom could stop with the assert "Cannot close stream until all bytes are written" when the user selected another book while a large (2 MB+) image from the previous one was still being sent. Release builds showed no error, but the browser's request for that image was left hanging, because the reply was never closed or aborted.

Cause

Bloom's local server sends files of 2 MB or more in 512 KB pieces. It tells the browser the full length up front, then reopens the file between pieces so the file is never held locked. If the file was deleted part way through, the loop stopped early and closing the response threw, because fewer bytes had gone out than promised. Most likely the deleted file was the image cache's processed copy, which is cleared when another book is selected. A deleted folder, a file that shrank, a file another process kept locked, and a file that grew past the promised length each threw in the same place.

What the PR does

  • The large-file branch of ReplyWithFileContent counts the bytes it sends. If the file went away, shrank or stayed locked, it logs that and aborts the connection. The browser sees a failed load within milliseconds and nothing is thrown.
  • Any file-system error or access refusal on the reopen between pieces ends the send that way: deleted file, deleted folder, delete-pending, or locked past the retry window.
  • Reads stop at the promised length, so a file that grows mid-send still gets a complete reply of its original length.
  • New RequestInfoTests cases serve a 32 MB file through a real HttpListener and delete it, delete its folder, truncate it, lock it, or grow it mid-send. Each fails against the old code.
