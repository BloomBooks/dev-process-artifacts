What this PR is about

Problem

In a debug build, selecting another book in the Collection tab while a large (2 MB+) image in the current book's preview was still loading could stop Bloom with the assert "Cannot close stream until all bytes are written". Release builds only logged it.

Cause

Bloom's local server sends files of 2 MB or more in 512 KB pieces, reopening the file between pieces so it is never held locked, after telling the browser the full length in Content-Length. If the file was deleted part way through (most likely the processed copy in the image cache, cleared when the user selects another book), the send loop stopped early, and closing the response threw because fewer bytes had gone out than were promised. A file that shrank, a deleted folder, or a file that grew so one piece crossed the promised length each threw in the same place.

What the PR does

  • RequestInfo.ReplyWithFileContent counts the bytes it sends. When the file went away or shrank, it logs that and aborts the connection instead of closing the stream, so the browser sees a failed load and nothing is thrown.
  • A reopen that fails because the file's folder is gone, or because the deleted file is still held open by another process, is handled the same way as a deleted file.
  • Reads stop at the promised length, so a file that grows mid-send still gets a complete reply of its original length.
  • New tests serve a 32 MB file through a real HttpListener and delete it, delete its folder, truncate it, or grow it mid-send. Each case fails against the old code and passes now.
