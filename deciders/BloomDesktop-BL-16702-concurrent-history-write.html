Decision

The lock is held while Bloom reads the upload, not just while it swaps the file in

Bloom saves a posted file by streaming it to a scratch file and then swapping that into place. The new lock is taken for the whole of that — including reading the bytes off the connection — so while one save of history/x.png is in progress, a second save of that same file waits. Both reviewers noticed and neither called it a defect: only requests for the same file wait, this code doesn’t run on the UI thread so Bloom can’t freeze, and the only client is the editor inside Bloom’s own window, posting bytes it already has in memory. The recommendation is therefore to leave it: for a stall to matter, the same page would have to hang mid-upload while a second save of the same file is pending, and in the case this fix exists for both saves come from that one page anyway. If a flow ever appears where something slower or remote uploads here, this is the first thing to revisit.

Decision

Nobody has yet watched the fix work in a running Bloom

The failure was proved live, and the fix is proved by a test that fails without it — but the actual user journey (make a picture, drag it onto two slots, press Replace, see both pictures change) has not been run against a Bloom that contains the fix. It can be, at no AI cost: the book you were using still holds the picture that was generated earlier, so the whole check is drag, drag, Replace. The obstacle is that a Bloom built from this worktree can’t run alongside the one you have open from Project3, which holds the same collection.

FYI

The editor still saves the same picture once per slot

The root cause has two halves, and only Bloom’s half is fixed here. The AI image editor (the separate bloom-ai-image-tools app, which we consume as a built package) writes its result to Bloom once for every slot you assigned, simultaneously — so putting one picture in four slots posts the same few megabytes four times. Bloom now handles that correctly, so nothing is broken; it is simply wasted work, and it stays wasted until the editor de-duplicates by result before saving. That is a change in the other repo, hence its own card rather than something to slip into this PR.

FYI

Reading a file at the exact moment it is replaced can still come back “not found”

Reads deliberately don’t take the new lock, so a response never waits behind somebody else’s multi-megabyte upload. The consequence, which both reviewers raised and the code now spells out in a comment, is that swapping the new file in is a delete followed by a move rather than one atomic step — so a read landing in that split second can 404. This is as old as the endpoint, is not made worse by this change, and can’t currently happen: the editor reads its history files when it opens and writes them when it generates or commits, never both at once. Recorded here only so it isn’t a surprise later.

FYI

A review sub-agent edited the tree it was reviewing

The light review agent proved a point by editing the code under review — it replaced the new lock with if (true) to watch the test fail — while a full test run was in flight, which is what produced the one bogus failure in this session. It put the line back when told. The general lesson is that a reviewing agent should get read-only tools when it shares a live working tree with the session that spawned it, which is a note for the shared skills rather than for this PR.
