What this PR is about

Problem

In a Match Sounds game, an audio button does nothing when its sound file has # in its name. This happens both in Bloom’s Play mode and in BloomPUB. A % in the name breaks the sound the same way (BL-16688), and the same goes for a game page’s correct-answer and wrong-answer sounds.

Cause

Bloom stores these sound attributes as the plain file name. That was decided on purpose in BL-16669, so whatever turns the name into a URL has to encode it. Bloom’s editor preview does; the game runtime in Bloom Player didn’t. So bird#1.mp3 was requested as audio/bird, and beep%41.mp3 as audio/beepA.mp3.

What the PR does

  • One helper, getSoundUrl, builds the URL for a sound in the book’s audio folder and encodes the file name. Bloom’s default correct/wrong sound URLs are left as they are.
  • Preloading (line 968) and playing (line 1064) both use it, so a preloaded sound is still found when it is time to play it.
  • Three unit tests cover a # name, a % name, and preload-then-play of a correct-answer sound. All three fail without the fix.

Should the fix also go into Bloom 6.5?

The card is on the Bloom 6.6 board and its title has no [6.5] prefix, so by our rules the fix belongs on master. But the bug also happens in 6.4 and 6.5, which the reporter hit in 6.4.

Master installs bloom-player@alpha, so it gets this fix automatically. Version6.5 pins bloom-player at exactly 2.20.2. Fixing 6.5 means publishing a 2.20.x release from bloom-player’s master branch and moving 6.5’s pin to it, which also brings along every other bloom-player change made since 2.20.2. I recommend leaving 6.5 alone: the bug only affects sounds with unusual file names, and the workaround (rename the file) is easy.
