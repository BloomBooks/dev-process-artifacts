What this is about

John Thomson reviewed this pull request — the last of four that hand the Edit tab’s toolbox over to React — and left thirteen comments across ten files, marking it as needing changes.

I checked every one against the code rather than taking it at face value. Most are places where a comment I wrote says the wrong thing. Three are findings about the code itself:

  • A guard that this PR quietly turned into dead code.
  • A comment that contradicts another comment in the same pull request.
  • Four different words used for roughly one idea, two of them genuinely colliding.

Nothing he raised challenges the architecture. The questions opposite are the ones where the answer changes what gets done; the rest I would simply fix.

Stephen McConnel’s two earlier comments are already answered and published, and are not repeated here.

The full analysis

Each of the thirteen comments is written up in pr-comments.md at the root of the worktree — the verbatim quote, what I found when I checked it against the code, the options, and a drafted reply. This form carries only the parts that need your judgment.

1. Four names for one idea: current, open, running, active

The toolbox code uses four words for what is roughly “the tool you are using”, and they are not used consistently. John asked for them to be defined once and applied everywhere. I checked each of his specifics and they hold up:

  • activeToolId in the state means which accordion section is expanded, but getActiveToolId() in toolbox.ts returns something different — the tool a loading page demands, falling back to the current one. Two concepts, one word.
  • currentToolId’s own comment says a tool stays current while the toolbox is hidden, while findCurrentTool() is documented as returning “the tool that is currently running”. Both cannot be true.

There are really three states — offered, open, and running — plus a fourth idea (the tool a loading page requires) wearing the word “active”. John warned about names stored in meta.json; that turns out not to bite here, because the file stores tool ids and the historical “Tool”/“Check” suffixes, not these state words.

The cost question is that a full rename is a large mechanical diff landing on a 41-file pull request that two reviewers are already partway through.

2. Obsolete selector names, and tool stylesheets vs emotion

Tool panels still carry a data-toolid attribute spelled with a historical “Tool” suffix, and some stylesheets and automated tests select tools by that old spelling. John asked whether this clean-up could also fix those names, and separately whether tool stylesheets should be replaced by emotion (the styling approach the rest of the front end uses). He noted himself that “either of these changes might want to be separate cards”.

Worth knowing before choosing: the “Tool”-suffixed spelling is also what Bloom writes into each book’s meta.json. So the persisted name has to keep working no matter what the selectors are renamed to — it is not a free find-and-replace.

3. Which bundle should markupSelectionPreservation.ts live in?

Bloom’s Edit tab is several separate documents, each with its own JavaScript bundle. One module, markupSelectionPreservation.ts, keeps the user’s cursor in place while a tool rewrites the text around it. The DOM it edits belongs to the page, but the code that calls it sits in the toolbox. John asked whether it would be better in the page’s bundle, and said “not necessarily, if most of its clients are in the toolbox bundle, but worth considering”.

Its callers today are the reader tools’ markup path, which is toolbox-side. Moving a module between bundles is a build-level change with its own risk.

4. I want to push back on one of his suggestions

A function called isToolOffered is documented as “Is the toolbox currently offering this tool?” John found that wording unclear — it sounds as though the answer changes from moment to moment, when in his reading a tool Bloom does not offer is a near-pathological state. He suggested: “Is this tool one that this version of Bloom implements?”

I think that replacement would mislead in the opposite direction. Being offered really does change from moment to moment, and this PR depends on it: the Game tool is offered when you arrive at a game page and withdrawn when you leave, which is precisely the bug (BL-16602) this work fixes. “Tools this version of Bloom implements” describes a different list entirely.

He is still right that the current wording does not say what makes a tool offered. My preference is to reword it to name both causes rather than adopt his sentence. Disagreeing with a reviewer is your call, not mine, which is why this is here.

5. A redundant filter: keep it or drop it

A helper that picks the first tool to open deliberately skips the “More…” tool. John pointed out this filter can never matter, because “More…” would have to be the only tool on offer, which cannot happen unless most of the toolbox is gone. He is right.

(The genuine defect he found alongside it — a comment claiming “More…” can never be the current tool, which contradicts another comment in this same PR — is being fixed either way; it is not in question here.)

6. The eight straightforward fixes, plus one piece of dead code

The remaining comments are ones I would simply act on. Eight are wording fixes to comments I wrote, with no behavior change — including two that actively mislead today: one implies showTool and hideTool behave asymmetrically when they do not, and one says the toolbox class is where functionality is being moved to when the direction is now the opposite.

The ninth is a real code change. A guard in detachCurrentTool checks whether the current tool is offered. This PR is what made that check impossible to fail, because the current tool is now derived from the offered list. It meant something before — the two could disagree, and that disagreement was the bug this work fixes — and it means nothing now. Removing it, with a line saying why it is unnecessary, stops someone re-adding it later.
