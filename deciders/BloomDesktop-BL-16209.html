Your decision

A transient read failure can wipe a collection's reader word list

Devin's review of the squashed commit, confirmed in the code. Pre-existing; this branch neither causes nor worsens it. Open PR thread.

When the reader tools post their language data, Bloom reads the posted JSON inside a try. If that read throws an IOException, the catch logs it and calls request.Failed(...) — but it does not return. Execution carries straight on with the data variable still an empty string, so Bloom writes that empty string over the collection's ReaderToolsWords-<lang>.json, and then also reports the request as succeeded.

In user terms: the collection's Synphony word list and grapheme data for that language can be replaced with an empty file. And the comment sitting directly above that try says the intent is to ignore such a failure and “just not update the file” — so the code does the opposite of what it documents. The failure it is guarding against is the one the same comment calls likely: switching between books quickly with a large block of data (BL-4313 and friends).

Devin reported this only as the milder “request is both failed and succeeded”. The double response is real, but the data loss is the part that matters.
