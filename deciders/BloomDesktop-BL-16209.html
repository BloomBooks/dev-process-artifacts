Your decisions

Ampersands look double-escaped when collection settings are saved

Found while investigating this card — not fixed here.

The reporter typed a plain & into the language display name. What ended up stored in the collection file is the six characters &amp; — that is, the ampersand was escaped once too often somewhere on the way in. The same thing happened in the Country, Province and District fields of the same collection, which suggests it is not specific to language names but to how those settings text fields are saved.

For a user, the symptom would be that typing Smith & Sons as a display name and reopening the collection shows Smith &amp; Sons. I did not verify whether current Bloom still does this — the collection on the card was made by an older version, so it may already be fixed, or it may not be ours at all (the language chooser is a shared SIL component). Confirming it is a few minutes’ work; chasing the cause could be more.

Any drawing error in the UI blanks the whole of Bloom, silently

Found while investigating this card, and independently raised by Devin — not fixed here.

This is why BL-16209 was so severe. The actual defect was one bad value in one small progress bar, but because there is no error boundary above the screen, React tore down the entire tree and the user got an empty window. The error was reported to Bloom’s common/error endpoint — but that only raises a toast, and the toast is drawn by the same tree that had just died, so nothing appeared at all. Not even a hint.

That means any future render-time mistake anywhere in the Collections tab produces the same outcome: a blank Bloom, no message, and a user who can only report “it stopped working”. An error boundary around the app shell would turn that class of bug into something visible and reportable. The toast-only policy itself is deliberate (BL-4301), so this is about the boundary, not about making JS errors modal.

FYI: the language tag still goes straight into a file name

Devin, informational — pre-existing, out of scope for this card.

The Decodable Reader keeps a per-collection data file whose name is built from the language tag, and that tag is dropped into the file name and folder path with no checking. Escaping it for JSON, which this PR now does, has no bearing on that path. A tag containing a character that is illegal in a file name, or a path separator, would fail or write somewhere unintended.

In practice language tags come from the language chooser and are well-formed, so this is latent rather than live — which is why it is an FYI rather than a decision I acted on.
