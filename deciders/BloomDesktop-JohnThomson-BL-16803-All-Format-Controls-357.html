What this PR is about

Problem

The Format dialog's Characters tab promises that a change made on a text box in the collection's first language applies to the style as a whole, so the same style's boxes in the other languages follow. Every control on that tab kept the promise except Color: a text color chosen on the first-language box changed only that language, and the second-language box beside it kept its old color (BL-16803).

Separately, the manual test "All Format Controls" (Notion test case 357), which walks every control on all four tabs of the dialog and checks where each change lands, had no automated equivalent.

What the PR does

  • Fixes BL-16803. The Color control now writes the color the way bold, size and spacing do: into the language-specific rule always, and into the style's language-independent rule too when the box is in the first language (changeColor). Two unit tests pin that down. Font stays per language, as before.
  • Automates Notion test case 357 as all-format-controls.spec.ts: a Basic Book with the three pages the card names, eight text boxes once the second language is on, then every control on every tab, with each change checked on the box at once and then on every box across the pages; changes on a second-language box reach only its four boxes; the Highlighting tab's colors are read back from the Talking Book tool's highlight; a style is created, changed, and applied.
  • Adds the helper layer for the Format dialog's controls, the toolbox handle, the Talking Book highlight, and reading a page's text-box formatting.
  • Records one suspected bug without fixing it: creating a new style does not carry the box's font into the new style. The check is a separate test marked as an expected failure, so it will complain the day the behavior changes.

Decisions

1. Creating a style drops the box's font

When a person creates a new style from the Format dialog's Style Name tab, Bloom copies the box's current size, spacing, emphasis, color, alignment and indent into the new style, but not its font, so a box that was in Arial falls back to the collection's font (Andika). The manual test says "the text doesn't change; all properties should be copied from Normal". The copy of the font was lost in 2022 when the font control became a React component (BL-10388), so this looks like an accident rather than a design. The e2e test records it as an expected failure.

2. Should the color fix also land on Version6.5?

The BL-16803 card is on the Bloom 6.5 Kanban board, but this PR targets master because the e2e suite only exists there. The fix itself is confined to changeColor in StyleEditor.ts plus two unit tests, so it cherry-picks cleanly.
