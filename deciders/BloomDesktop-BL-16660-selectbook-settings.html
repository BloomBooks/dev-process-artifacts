Collection Settings now writes the settings file five times per OK

You asked that changed settings be saved immediately, so ExperimentalFeatures.SetValue now saves at the end of every call. Clicking OK in Collection Settings calls it four times — for experimental source books, Team Collections, App Builder and AI image editing — and there is a fifth save for the "Automatically update Bloom" checkbox just above them. So one OK click rewrites the whole settings file five times in a row.

Nothing is wrong functionally: each write is a small XML file, and the last one wins. It is visible only as a handful of redundant disk writes on a click the user makes rarely. Devin raised it as informational; I did not act on it, because batching would mean going back to one place knowing that a later call will flush its value — the implicit coupling this whole change set out to remove.

The recent-collections list is changed without being saved, in five places

The sweep you asked for covered every place that assigns a settings value. But the list of recently-opened collections is a mutable object living inside the settings, so code changes it by calling methods on it — MruProjects.AddNewPath(...) and .RemovePath(...) — with no assignment at all. My search could not see those, and five of them never save.

Three are in startup argument handling (opening Bloom on a .bloomCollection, a .bloomProblemBook, or a renamed collection) at Program.cs:664, :685 and :703; two more prune invalid entries at :1646 and :1654. In the normal flow they are flushed a moment later when the collection actually opens and saves — so this is mostly latent, biting only if startup bails out first. What a user would see is a collection they just opened missing from the recent list, or a dead entry that keeps coming back.

I did not touch these: it is a different pattern from the one you asked about, and it sits in startup paths where I would want your eye on it.

Two places deliberately do not save immediately

You said the intent is to save changed settings immediately. Two of the places I first changed had to be reverted, because both run on every startup path — including Bloom's automated command-line commands — and saving there recreated, in miniature, the very problem BL-16660 is about: an unattended bloom upload or hydrate run rewriting the settings file that the interactive Bloom owns.

They are the startup UI-language values in SetUpLocalization and the recent-collections list in ApplicationContainer. Both now carry a comment saying why they are exceptions. Nothing is lost in either case: the UI language is derived again at every startup, and is saved immediately when the user actually picks a language; the collection list is saved by the GUI when it adds a path. This is really a "do you agree with the two exceptions" question rather than an open defect.

FYI — one behaviour change worth knowing about

When the selected book is one Bloom could not reopen next launch — chiefly the stale selection left over from the previous collection while you are switching collections — the new code leaves the stored value alone rather than overwriting it. The old code overwrote it with the unusable path. I judged leaving the good value the safer of the two, since startup would refuse to restore the bad one anyway, but it is a deliberate difference in behaviour rather than a pure refactor, so it should not pass unnoticed.
