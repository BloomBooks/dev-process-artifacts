What this work is about

Problem

When Bloom freezes we get almost nothing. The user kills it and carries on, and freezes are exactly the failure people do not report, so a bug like BL-16697 can only be guessed at. Any problem report is written after the kill, and describes a healthy new process.

Cause

Nobody is watching at the moment it happens — and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait still dispatches sent messages, so IsHungAppWindow and Process.Responding report a thoroughly wedged Bloom as healthy. Measured on a real Bloom: nine minutes frozen, reported responsive throughout.

What the work does

  • Bloom publishes its health — a UI-thread timer heartbeat in shared memory, which is the only signal that detects the freeze described above; plus which log file this run is writing to, what Bloom believes it is doing, and how far shutdown got.
  • Bloom marks its deliberately slow work — publishing, video, upload, download — so a legitimate five-minute job is not reported as a freeze.
  • Bloom announces itself as it starts, in the first moments of Main, so a Doctor already running adopts it at once rather than at its next sweep. Everything before that announcement is time in which a hang or a crash cannot be doctored at all, because Bloom only asks for a dump when a Doctor is already watching.
  • A companion process watches one Bloom, and at the moment of failure gathers stacks, wait chains, WebView2 state and the Event Log, then files a YouTrack card by itself. The report leads with what a reader needs first — where the UI thread is stuck, or what was thrown. Recurrences fold onto one card: a freeze identified by the UI thread's frames, a crash by the faulting thread's exception, the UI thread being no use for a crash since it sits in its message loop throughout.
  • It stays quiet for developer builds, simulated failures, debugged processes, and problems Bloom has already reported itself — with a "Send it anyway" button for the developer who decides one of those reports should go after all.

It ships inside Bloom's installer and is off by default, switched on from the debug menu.

Worth knowing

  • go.sh now stops any running Freeze Doctor before it builds. A Doctor holds the DLLs the build must replace, so a running one made Bloom fail to build at all — it cost a whole test run before the cause was found. If you want a Doctor watching after launching from source, let Bloom start it (the menu toggle) or start one by hand once Bloom is up.
  • --nowatch is worth less than we hoped. Measured twice on a warm build: 35 s to a running Bloom with dotnet watch, 27 s without. Most of the wall clock is Vite and Bloom itself, not the watcher.
  • RunFreezeDoctor is now switched on in your settings, because testing the Bloom-launches-its-own-Doctor path needed it. Turn it off from the same debug menu if you would rather it were off.
  • A spin freeze cannot report where it is spinning. A stack walk of a thread running flat out yields nothing above the message loop, so the report says so and names which thread to open in the attached dump. That is the honest answer rather than a gap, but it does mean a spin needs the dump to diagnose.
  • The wait-chain behaviour still has not been seen against a real frozen Bloom. Only the same-process rehearsal exercises it; the tests cover the code, not what Windows returns.

Decisions

A Doctor that Bloom started will adopt a different Bloom later

When Bloom starts a Doctor, it does not tell it to watch only Bloom-the-executable of that channel — so the Doctor looks for any installed Bloom name. That is what you want when you restart Bloom after a freeze: the same Doctor picks the new one up. But it also means that after the Bloom that started it has gone, the Doctor will adopt any Bloom it finds. Observed during this session: a Doctor started by a development Bloom outlived it and adopted the BloomBetaInternal install that happened to be running.

Why it matters rather than being merely untidy: BetaInternal is not a developer channel, so a genuine freeze or crash in it would be filed as a real card — a report about work you were doing in a different Bloom entirely, from a Doctor you never pointed at it. Nothing incorrect would be in the card; it is the surprise, and the fact that the user never asked that Bloom to be watched, that is the problem.

This PR has never had a third-party bot review

Devin has now been triggered on this PR at least six times across several days and different commits. Every time, the job either never appears or completes with its findings stage still marked pending and no result — the stage that produces the bugs and flags simply does not run here. Its accumulated list from earlier attempts has been worked through, but nothing has reviewed the code as it now stands, including everything added in the last two rounds.

What that leaves: the local review (which found one real defect this round), Greptile's five earlier comments, your own 44 review comments, and the eight failure modes exercised by hand. The most likely cause is the size of the diff — the one job result that can be read is 3.2 MB — so the practical question is whether that is worth doing anything about now.
