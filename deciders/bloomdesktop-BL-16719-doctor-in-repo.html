What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical: the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes and Process.Responding returns true while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout. WM_TIMER is not dispatched, which is why detection rests on a UI-thread heartbeat published through shared memory rather than on either API that looks built for the job.

What the PR does

Adds a companion Windows app — four projects in this repository — that is already running when the trouble starts, gathers what can only be gathered at that instant, and files a YouTrack card by itself.

  • Bloom publishes its health through a shared-memory page a watcher can read without Bloom's cooperation: a UI-thread heartbeat whose silence is the freeze signal, a separate background beat so "UI thread blocked" can be told from "whole process wedged", what Bloom thinks it is doing, and how far shutdown got.
  • Bloom also proves its clean exits, records which log file this run is using, marks its deliberately slow work (publishing and Bloom Library transfers get five minutes rather than one), notices a debugger, and says when it was told to break itself on purpose.
  • The Doctor watches for the three states, gathers evidence while the process still exists, queues reports on disk (a freeze often arrives with a dead network), and files them. On its own initiative it will never touch a frozen Bloom, which may hold unsaved edits living in the WebView2 DOM — only a window-less one, where there is nothing left to save.
  • How it ships: inside Bloom's installer, signed alongside Bloom.exe. Whether it runs is a setting, off by default, toggled by "Run Freeze Doctor" in the collections-tab debug menu. Until it has something to report it shows no window at all — only a tray icon.

Worth knowing

  • Alpha and Beta have never actually run this. Until this run the Doctor exited about a second after starting on those channels, so every hand-test so far was on a developer build. A real Alpha or Beta install is now the most valuable thing to try, and the QA notes on the card lead with it.
  • Filing has never been exercised. Nothing has ever posted to the tracker: developer builds never file, and now simulated failures never file either. The path is unit-tested, but the only way to prove it end to end is BloomFreezeDoctor.exe --force --project AUT, which nobody has run.
  • The window and the supervisor have no test harness. None of the 113 Doctor tests touch StatusForm or DoctorSupervisor, so this run's UI and threading fixes — including an interlock that holds off process exit — are verified by hand only. That is also how every one of those defects was found.
  • .vscode/launch.json is deliberately modified and left uncommitted — a temporary BLOOM_SIMULATE_FREEZE override for testing. It should not be committed.

The crash-dump handshake never fires

The Doctor is built to dump a Bloom that is in the act of crashing: Bloom signals it, holds its own death open for up to three seconds, the Doctor takes a dump from outside, and Bloom then finishes dying. A dump taken that way is worth far more than anything a dying process can capture of itself.

It has never run. Bloom's own FatalExceptionHandler registers for unhandled exceptions inside SetUpErrorHandling(), about a thousand lines before the Doctor's hook is installed, and it answers a fatal exception with a modal problem-report dialog. Handlers run in registration order, so Bloom's runs first and does not come back. A simulated crash duly produced a full report with no dump attached — and nothing anywhere said why, which is fixed separately: that path now records whether it asked and whether it was answered.

Closing the Doctor's window shuts the Doctor down

The window has no close handler, so its X button ends the program — tray icon and all — even while Bloom is still being watched and reports may be queued. The tray menu also has an explicit Quit that does exactly the same thing, so there is currently no way to simply put the window away: minimizing hides it to the tray, but closing kills the watchdog.

Someone tidying their screen would silently switch off freeze detection for the rest of the session, with no reason to suspect it. It also makes a comment in the code untrue — that comment says the "Show report" button survives closing and reopening the window from the tray.
