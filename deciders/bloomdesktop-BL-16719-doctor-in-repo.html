What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical: the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes and both Process.Responding and IsHungAppWindow report it healthy while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout. WM_TIMER is not dispatched, which is why detection rests on a UI-thread heartbeat published through shared memory rather than on either API that looks built for the job.

What the PR does

  • Adds a companion Windows app, shipped and signed inside Bloom's installer, that is already running when the trouble starts.
  • Has Bloom publish its own health through a shared-memory page a watcher can read without Bloom's cooperation, prove its clean exits, name the log file this run is using, mark work that is legitimately slow, and say when it was told to break itself.
  • Has the Doctor watch for the three states, gather evidence while the process still exists, queue reports on disk because a freeze often arrives with a dead network, and file a YouTrack card by itself.
  • Leaves a frozen Bloom alone — it may hold unsaved edits living in the WebView2 DOM. Only a window-less one is ended, where there is nothing left to save.
  • Ships switched off: a debug-menu toggle, "Run Freeze Doctor", starts it at once and is remembered. Until it has something to report it shows only a tray icon.

Worth knowing

  • Every minidump was being silently discarded until the last commit. The attachment budget was 12 MB and a real Bloom’s dump is 16–17 MB, so the primary artifact never reached a card and nothing said so. The budget is now 30 MB and anything too large is named in the card body. Worth knowing because it means no card filed before this commit ever carried a dump.
  • The crash-dump path has still never been exercised. It could not fire at all before this run — nothing created either of the two named events it uses — so both ends are new code that no crash has been run against. It is the least-proven thing in the PR, and the first item on the card's manual-test notes.
  • Joining a freeze and the death that follows onto one card cannot be seen in testing. The join only applies to reports that are actually going to be filed, and nothing provoked deliberately ever is — so a tester correctly sees two report folders. It matters only in the field.
  • The queue now has a non-terminal state. A bundle being sent is deliberately invisible to the drain, which is what lets a gather arriving mid-send know it must not merge into it. That makes the recovery path for a send that never finished load-bearing rather than defensive: without it a Doctor killed mid-upload would strand that report silently. It is tested, but only against a simulated interruption.
  • One capability was deliberately dropped rather than narrowed. A WebView2 renderer crash can no longer count as evidence about Bloom. There is no correct version of that check: the pid in such an Event Log entry is the renderer's own, so it could never tell Bloom's renderer from Teams'. Bloom normally survives a renderer crash anyway, and this code only runs once Bloom has gone.

Two of your answers changed the design rather than merely settling it, so they are worth restating:

  • "Report now" keeps filing, and now says what it is overriding. Your reasoning: needing --force is a real nuisance exactly when you want to check that filing works, and a developer build can have a genuine freeze worth reporting. So it lists the reasons it would normally have declined, and asks, defaulting to No.
  • The merge race is closed your way rather than mine. Instead of making a gather wait on an upload, the drain marks the bundle under a brief lock, uploads with nothing held, then takes the lock again to record the answer. A gather arriving mid-send takes a bundle of its own, remembers whose card it belongs on, and becomes a comment on that card once it exists.

The one thing I was asked to look for and did not find: a simple way to make always-on health publishing cheaper. The expensive-sounding part does not happen — the session file is compared every ten seconds and written only when it has actually changed, which in steady state is never. That claim was wrong in the review flag and in my own previous report.
