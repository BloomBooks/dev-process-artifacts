What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical: the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes and both Process.Responding and IsHungAppWindow report it healthy while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout. WM_TIMER is not dispatched, which is why detection rests on a UI-thread heartbeat published through shared memory rather than on either API that looks built for the job.

What the PR does

  • Adds a companion Windows app, shipped and signed inside Bloom's installer, that is already running when the trouble starts.
  • Has Bloom publish its own health through a shared-memory page a watcher can read without Bloom's cooperation, prove its clean exits, name the log file this run is using, mark work that is legitimately slow, and say when it was told to break itself.
  • Has the Doctor watch for the three states, gather evidence while the process still exists, queue reports on disk because a freeze often arrives with a dead network, and file a YouTrack card by itself.
  • Leaves a frozen Bloom alone — it may hold unsaved edits living in the WebView2 DOM. Only a window-less one is ended, where there is nothing left to save.
  • Ships switched off: a debug-menu toggle, "Run Freeze Doctor", starts it at once and is remembered. Until it has something to report it shows only a tray icon.

Worth knowing

  • The crash path is now proven, and that changed three numbers. A simulated crash produced a 16.9 MB dump, uploaded and linked from a card — with Bloom's own thread caught in the dump sitting inside RequestDumpBeforeDying. It also showed the dump took 2367 ms of a 3000 ms budget on a fast machine, which is why the wait was rebuilt; and that a 17 MB dump cannot be attached to a tracker card at all, which is why S3 is now in the picture.
  • The S3 objects are world-readable. The bucket serves them over plain HTTPS to anyone holding the URL, exactly as Bloom's existing problem-book uploads do; the link's unguessability is the protection, which is why the Doctor's keys carry a random prefix. A deliberate, accepted trade rather than an oversight.
  • Bloom's own S3 keys remain guessable — its problem-book uploads use the bare file name, so two users uploading bloom-1234.dmp overwrite each other and the URLs can be guessed. Untouched here and pre-dating this PR, but it is a real exposure and probably its own ticket.
  • Two things are still inferred rather than measured. The 8 MB attach limit comes from Bloom's 2020 note that YouTrack refuses much over 10 MB, not from a test against today's tracker; and the release-Bloom-early fix has been reasoned and built but not yet exercised by a crash.

Three of your questions turned out to be worth more than the answers:

  • "Where did 12 MB come from?" — nowhere, and neither did my replacement. Bloom had measured YouTrack's real ceiling at ~10 MB years ago and stopped attaching altogether; raising our own number could never have worked, because ours was never the binding one.
  • "Why not let the dump take as long as it takes?" — the limit was a UX judgement calibrated against a measurement that understated reality by more than half, and overrunning it does not delay a dump but loses it. That question is what led to the wait being rebuilt, and to Devin then finding that Bloom was waiting for the upload too.
  • "I thought the first Doctor became the only one running." — correct, and my stated concern was wrong. Checking it turned up that a hand-started Doctor silently discarded its own command-line options when another was already running, which would have quietly invalidated the manual test.
