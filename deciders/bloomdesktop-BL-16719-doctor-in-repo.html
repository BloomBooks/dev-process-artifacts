What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical — the UI stops responding; Bloom exits without reporting anything; or Bloom’s window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes, IsHungAppWindow reports it healthy and Process.Responding returns true while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout. Since Bloom’s UI thread awaits WebView2 constantly, that is likely the common shape of freeze rather than an exotic one. WM_TIMER is not dispatched, which is why detection rests on a UI-thread heartbeat published through shared memory rather than on either API that looks built for the job.

What the PR does

Adds a companion Windows app — the Freeze Doctor, four projects in this repository — that is already running when the trouble starts, gathers what can only be gathered at that instant, and files a YouTrack card by itself.

  • Bloom publishes its health: a UI-thread heartbeat whose silence is the freeze signal, a separate background beat so “UI thread blocked” can be told from “whole process wedged”, what Bloom thinks it is doing, how far shutdown got, and whether a debugger is or has been attached.
  • Bloom proves its clean exits, and marks its deliberately slow work — publishing, uploading, downloading — so a five-minute publish is not reported as a freeze.
  • Bloom asks to be dumped as it dies, waiting on the Doctor’s continued existence rather than on a clock, since the dying process is itself what writes the dump.
  • The Doctor watches for the three states, gathers evidence while the process still exists, queues reports on disk (a freeze often arrives with a dead network), and files them. It will not touch a frozen Bloom on its own, which may hold unsaved edits in the WebView2 DOM — only a window-less one, where there is nothing left to save.
  • Guard rails on filing, since it posts unattended: never from a developer or automation build, never about a rehearsal or a Bloom a debugger has been near, deduplicated by fingerprint so a recurrence is a comment rather than a new card, and at most three new cards a day automatically.

It ships inside Bloom’s installer beside Bloom.exe. Whether it runs is a setting, off by default, toggled by “Run Freeze Doctor” in the collections-tab debug menu.

Worth knowing

  • The three failure modes have been exercised by hand, and only by hand — freezes both visible and invisible to Windows, a window-less zombie ended and restarted, a wait chain Windows can actually see, and a real crash that produced a 16.9 MB dump uploaded to the support bucket. None of that can be staged in a unit test, so the automated suites say nothing about it.
  • Neither of this run’s two fixes has automated coverage — see the first question opposite. One reads the machine’s boot time and the Event Log; the other depends on which of two timers fires first.
  • Health publishing runs in every Bloom, whether or not the Doctor is switched on. That was decided earlier on this branch, because a Doctor installed later still needs the data, but it is a cost that ships to every user.

Should the boot-time fix get a test?

Devin found that a Bloom which died within 30 seconds of the computer starting up was treated as wreckage left over from before a restart, and so was never reported at all. The cause was a sign error: the tolerance around “did the machine reboot after Bloom died?” allowed a boot up to 30 seconds before the death, and since a boot time is always in the past, every early death matched. It is fixed, but nothing would catch the sign being flipped back.

Testing it means the code has to stop reading the boot time for itself and accept it as an argument instead — a small change, but it does alter the shape of a private method. The companion fix (the Doctor forgetting it had asked a Bloom to stop) depends on which of two timers happens to fire first, and is not realistically unit-testable; the manual check for it is already in the test-ideas comment on the card.

Leave the simulated crash armed in your launch.json?

.vscode/launch.json is modified in your working tree and deliberately not committed. It sets BLOOM_SIMULATE_FREEZE=crashthread:120, which is what the manual crash test needed: two minutes after Bloom starts, a background thread throws and Bloom dies on purpose.

That means your next F5 will crash Bloom two minutes in, whatever you were doing. Fine while you are still exercising the Doctor, surprising if you have moved on to something else. Nothing about the branch depends on it either way.
