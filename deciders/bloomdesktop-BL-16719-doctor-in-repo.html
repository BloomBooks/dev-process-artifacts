What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical — the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes, IsHungAppWindow reports it healthy and Process.Responding returns true while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout.

What the PR does

  • Bloom publishes a health heartbeat through shared memory that a watcher can read without Bloom's cooperation, proves its clean exits, records which log file this run is using, tracks in-flight API requests, and notices a debugger.
  • A companion app — the Freeze Doctor, four projects now living in this repo — watches for the three failure states, gathers evidence while the process still exists, and files a tracker card itself. It will not touch a frozen Bloom, which may hold unsaved edits; only a window-less one.
  • It ships inside Bloom's installer, signed alongside Bloom.exe. Whether it runs is a setting, off by default, toggled by “Run Freeze Doctor” in the collections-tab debug menu; turning it on starts it at once.
  • When running normally it shows no window at all — only a tray icon — until it has actually reported something.

Worth knowing

  • Nothing here has been run by hand yet. Every finding so far is from tests and review; the Doctor has not been watched doing its job in this arrangement. Turning the menu item on with BLOOM_SIMULATE_FREEZE set is the test that matters, and the QA notes on the card lay it out.
  • The Doctor's exe is not produced in the agent-dotnet private build tree, because Directory.Build.props disables apphosts there for everything but WebView2PdfMaker. Harmless for tests, but a Doctor launched from such a tree will silently do nothing — that is decision 4, not a bug.
  • Two earlier PRs are superseded. #8218 and #8219 are both contained here in final form; #8219's NuGet-package approach is moot now that both consumers share a repo. Left open rather than closed — decision 5.
  • Greptile re-resolves its own threads when the file changes, so a thread being marked resolved on this PR does not always mean the point was settled. The thread for decision 7 was auto-resolved twice and reopened twice. This report, not the thread state, is the reliable list of what is still open.
  • The three unfixed bugs are all in code that had never been reviewed by anyone before this PR — the Doctor spent its early life on a branch with no review, so decisions 8 and 9 are first looks rather than regressions. Neither is reachable from the tests, which is why review found them and the suite did not.

1 · The YouTrack token's permission scope

The Doctor files its cards using a shared permanent token for the auto_report_creator account, embedded in the program as a base64 literal. The existing reasoning is that Bloom itself already ships that same token in a public repo, so this adds no new exposure — which holds. Devin's point is narrower: the token now also travels inside a second program, one that a support person may be asked to switch on during a call, so it is worth confirming what that token is actually allowed to do on the server. Nothing in the code can answer that; only somebody with YouTrack admin access can.

2 · Turning the setting off leaves a running Doctor alive

Unticking “Run Freeze Doctor” stops the Doctor being started next time, but does not stop one that is already running. I chose that deliberately: the running Doctor is watching this Bloom and may be holding a report it has gathered but not yet managed to send, so killing it on the spot could throw that evidence away. It exits by itself shortly after Bloom does. The cost is that “off” does not mean “off right now”, which a user could reasonably find surprising — and it is listed in the QA notes so a tester does not file it.

3 · The rest of the Doctor's file operations

Bloom requires file operations to go through libpalaso's robust wrappers, which retry when Windows briefly refuses access — usually a virus scanner holding a file that was written a moment ago. The Doctor arrived with 44 plain File and Directory calls, so its tree is currently exempted from that check. One of them was already a real bug and is fixed: renaming a gathered report into the outbox failed about one run in three and lost the report. The other 44 are unconverted.

4 · The Doctor's exe is missing from agent build trees

Builds made through build/agent-dotnet.ps1 — the wrapper that lets a build run while you have Bloom open — deliberately skip generating the small launcher .exe for every project except WebView2PdfMaker, which is exempted because Bloom shells out to it by name. Bloom now shells out to BloomFreezeDoctor.exe by name in exactly the same way, so in such a tree the menu item will appear to do nothing at all. Normal builds are unaffected.

5 · The two superseded pull requests

PR #8218 (Bloom's half of the feature) and PR #8219 (sharing the wire format as a NuGet package) are both contained in this PR in their final form, and #8219's whole approach is unnecessary now that Bloom and the Doctor share a repository. They both still carry review history, including resolved Devin threads, which is why I have not touched them.

6 · Long operations get no extra patience

The Doctor can be told that Bloom is deliberately busy — publishing, uploading, making a PDF — and will then wait five minutes instead of one before deciding it has frozen. Nothing in Bloom ever sets that flag, so every freeze is judged at one minute. The exposure is real but narrow: work behind a progress dialog keeps pumping messages and so keeps the heartbeat alive, and it is only UI-blocking work lasting over a minute that could be reported as a freeze when it is merely slow. It is deliberately unwired because “a request has run a minute” is the same signal as the freeze itself, so no automatic rule can tell legitimately-slow from wedged — a human has to name the operations.

7 · “Report now” can say it failed when it did not

“Report now” gathers a report, then drains the queue and looks for its own report among what was sent. If a support person happens to be running BloomFreezeDoctor --drain by hand at that moment, the drain waits twenty seconds for them to finish, gives up, and files nothing — so “Report now” concludes there is no issue id and tells the user it failed, for a report the other process is about to file perfectly well. The report is not lost; only the message is wrong.

The reason this is a question rather than a fix: the honest correction changes what the drain method returns, so that “somebody else is draining” is distinguishable from “nothing was filed”. Today both are zero, and that method has existing callers and tests.

8 · Wait-chain reports print nonsense thread ids

When Bloom freezes, one of the most useful things a report can say is which thread is waiting on which — the “wait chain”. Windows returns that in a structure whose second half is a union: the thread numbers live at the same place as the object's name, not after it. Our copy of that structure lists them after a 256-byte name field, so the numbers are read from the wrong place, and the structure is the wrong size too, which misaligns every entry after the first. The result is that a card states a thread and process id that are simply garbage.

Nothing crashes, and no test fails — this is the “confident nonsense” failure this whole tool is meant to avoid, appearing inside the tool itself. It is not fixed here because it needs the structure re-expressed as a real union and can only be confirmed against an actually-blocked thread; a rushed version would keep printing rubbish while looking fixed.

9 · A hiccup contacting the tracker throws a report away for good

Before filing, the Doctor looks up the tracker project's internal id. If that one request fails for any reason, the code treats it as “this project does not exist” and marks the report permanently failed, so it is never retried. Every other request in that class distinguishes “try again later” from “never”; this one does not. So an ordinary server hiccup or gateway timeout discards a gathered report for good — which defeats the entire purpose of queueing reports on disk, that being to survive exactly the flaky network a freeze so often comes with.
