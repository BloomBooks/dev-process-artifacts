What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical — the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes, IsHungAppWindow reports it healthy and Process.Responding returns true while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout.

What the PR does

  • Bloom publishes a health heartbeat through shared memory that a watcher can read without Bloom's cooperation, proves its clean exits, records which log file this run is using, tracks in-flight API requests, and notices a debugger.
  • A companion app — the Freeze Doctor, four projects now living in this repo — watches for the three failure states, gathers evidence while the process still exists, and files a tracker card itself. It will not touch a frozen Bloom, which may hold unsaved edits; only a window-less one.
  • It ships inside Bloom's installer, signed alongside Bloom.exe. Whether it runs is a setting, off by default, toggled by “Run Freeze Doctor” in the collections-tab debug menu; turning it on starts it at once.
  • When running normally it shows no window at all — only a tray icon — until it has actually reported something.

Three of those rounds were a reviewer catching a flaw in the previous round's fix, all on the same piece of code — the gate that stops two things draining the report queue at once. That is why this run stops at the skill's four-cycle cap rather than continuing: the pattern could run indefinitely, and what is left is a design choice rather than a defect.

Worth knowing

  • Nothing here has been run by hand yet. Every finding so far is from tests and review; the Doctor has not been watched doing its job in this arrangement. Turning the menu item on with BLOOM_SIMULATE_FREEZE set is the test that matters, and the QA notes on the card lay it out.
  • The Doctor's exe is not produced in the agent-dotnet private build tree, because Directory.Build.props disables apphosts there for everything but WebView2PdfMaker. Harmless for tests, but a Doctor launched from such a tree will silently do nothing — that is decision 4, not a bug.
  • Two earlier PRs are superseded. #8218 and #8219 are both contained here in final form; #8219's NuGet-package approach is moot now that both consumers share a repo. Left open rather than closed — decision 5.
  • Greptile re-resolves its own threads when the file changes, so a thread being marked resolved on this PR does not always mean the point was settled. The thread for decision 7 was auto-resolved twice and reopened twice. This report, not the thread state, is the reliable list of what is still open.
  • The three unfixed bugs are all in code that had never been reviewed by anyone before this PR — the Doctor spent its early life on a branch with no review, so decisions 8 and 9 are first looks rather than regressions. Neither is reachable from the tests, which is why review found them and the suite did not.

What was decided

All nine questions were answered by John and are implemented on the branch. Kept here as the record — each also has its reasoning next to the code it affects, or on the review thread that raised it.

1 · The YouTrack token's permission scope

Left as is. The reasoning settles the question rather than deferring it: the Doctor uses the token for nothing Bloom does not already use it for, and the token is already public — so its secrecy was never what limited the damage, and shipping the same public token in a second program of ours does not change the exposure. Recorded on the review thread, which is now resolved.

2 · Turning the setting off leaves a running Doctor alive

Left as is. It is watching that Bloom and may hold a report gathered but not yet sent; it exits when Bloom does and does not start next time. Listed in the QA notes so a tester does not file it as a bug.

3 · The rest of the Doctor's file operations

Converted now, and the exemption deleted — “no reason to allow the Doctor to use non-robust operations”. All 34 sites now go through libpalaso's RobustFile/RobustIO, and the gate was run for real with everything staged: it passes on its own merits. The only remaining carve-out is the Doctor's test project, matching the existing one for Bloom's tests.

Three FileStream sites keep the documented opt-out, because there the sharing flags are the requirement — two read a log the process being diagnosed still holds open, and the third is the exclusive lock that stops two things draining the report queue at once.

4 · The Doctor's exe in agent build trees

Added to the apphost exception, beside WebView2PdfMaker, for the same reason it exists: Bloom launches the file by name, so without it the menu item silently does nothing in such a tree.

5 · The two superseded pull requests

Both closed, each with a comment pointing here and a note of what is worth preserving from it — the review history stays readable.

6 · Long operations get extra patience

Wired, for the operations John named: making a BloomPUB, ePUB, video or app, and uploading to or downloading from Bloom Library. Marked at the workers rather than the publish screens, so the bulk publisher and app building — the cases that run longest — are covered too.

They nest for real, since building an app makes BloomPUBs on the way, so the depth is counted: an inner operation finishing cannot end the outer one's patience, and a missed exit would leave the Doctor permanently patient, which is freeze detection silently off for the session. Three tests pin that.

The finer version is not done. “Do not report while definite progress is being made” needs a different signal — a progress heartbeat Bloom pokes as files transmit or pages process — rather than a boolean, and the natural shape is a second timestamp in the shared page treated much as the UI heartbeat is. Worth doing once field testing shows whether five minutes is enough; the QA notes ask a tester to report the case that would justify it.

7 · “Report now” could say it failed when it had not

Fixed by distinguishing the two answers. The drain returned a bare count, so “nothing sent” and “another process is sending it” were both zero; the window then said nothing at all, which reads as failure and invites pressing the button again. It now says the report is saved and will be sent.

The bug was wider than the case that was raised: the same silence applied to being offline or over the daily cap, both perfectly normal.

8 · Wait-chain reports printed nonsense thread ids

Layout fixed. The native structure's second half is a union, and the thread numbers live at the same offset as the object's name rather than after it; the struct was also the wrong size, which misaligned every entry after the first.

Simpler than feared, because the object name is never read anywhere — so only the thread branch needed declaring, plus padding to restore the native stride. A test now pins the size and the two offsets, which needs no frozen process; mutation-testing confirmed it catches the original field order. End-to-end confirmation against a real freeze is on the manual test list, as John asked.

9 · A tracker hiccup discarded a report for good

Routed through the same retry classification as its neighbours. That needed no new policy: the existing classifier already treats a definite “not found” as permanent and a 429 or 5xx as worth retrying, which is exactly the line wanted here.
