What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom wrote before it stopped responding. Three different failures arrive looking identical: the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside. A WinForms UI thread blocked in a managed wait still answers window probes, so IsHungAppWindow and Process.Responding both report a completely stuck Bloom as healthy. Measured on a real Bloom: nine minutes frozen, reported responsive throughout. Only a UI-thread timer heartbeat published through shared memory detects it.

What the PR does

Adds a companion Windows app, the Freeze Doctor, as four projects in this repository, and teaches Bloom to publish enough about itself that the Doctor can tell it has stopped and say something useful about why.

  • Bloom publishes its health. A UI-thread heartbeat in shared memory, a per-run session file naming the log this run writes, the API requests in flight, and long-operation scopes at the places Bloom legitimately stops answering for minutes. It announces itself early in startup so a running Doctor adopts it at once.
  • The Doctor watches one Bloom, once a second, reading the shared page rather than asking Bloom anything. It distinguishes frozen, window-less but alive, and gone without proof of a clean shutdown, and waits longer while Bloom says it is doing something slow.
  • It gathers at the moment of failure: managed stacks, the Windows wait chain, WebView2 process state, the right log file, and the Event Log and Windows Error Reporting record of the exit. The report leads with where the UI thread is stuck or what was thrown.
  • It files, and does not duplicate. Reports go to disk first and are sent afterwards; a recurring problem becomes one card with a count.
  • It stays quiet when it should. Developer builds, headless jobs, simulated failures, debugged processes and problems Bloom already reported produce evidence on disk and no card, with a "Send it anyway" button for the developer who decides otherwise.
  • It can clear the way. A window-less Bloom holding the single-instance token can be ended after its evidence is gathered, never a merely frozen one.

It ships inside Bloom's installer with no installer of its own, off by default, switched on from the debug menu on the Collections tab. It is part of the next Beta; whether to offer it to Release users is still open.

Decisions

1. Keep the Doctor's code in three projects, or fold it into Bloom?

Andrew, on Bloom.sln in Reviewable
Do we really want/need 3 new production projects for this?

The Doctor is three production projects plus a test project: the exe (window and entry point only), Core (everything the Doctor does, testable without WinForms), and Protocol (the shared-memory layout, session file and named events that Bloom and the Doctor both compile). Andrew's question is whether that is more structure than the feature needs. The Protocol project in particular exists only because Bloom must compile the same wire format, not because the Doctor is ever installed separately.

Making the Doctor reference Bloom.dll instead would work, but a running Doctor would then hold Bloom.dll open, so every Bloom build while a Doctor is alive fails with MSB3027, and Core's tests would drag in WinForms, WPF and all of Bloom's packages. A cheaper way to lose a project is to keep the Protocol source under BloomExe and have Core compile the same files as linked sources.

2. The Doctor uploads large dumps with S3 credentials Andrew says are being shut down

Andrew, on AccessKeys.cs in Reviewable
I think we better discuss this. If I understand what is happening, it is using credentials we are about to shut down.

A real Bloom crash dump is 16 to 17 MB, too large to attach to a YouTrack card, so the Doctor uploads it to the bloom-problem-books S3 bucket and links it from the card, the same way Bloom's own problem reporter handles large files. It reads the uploaderDev access keys from connections.dll, the file Bloom already ships beside its exe. Andrew believes those keys are about to be retired. If they are, dumps would silently fail to upload; the Doctor already handles that by saying on the card where the dump still is on the user's machine, but the dump itself, usually the most valuable thing in a report, would not reach us.

Preflight cannot settle this: it depends on what replaces the keys and when. The right move is a short conversation with Andrew about the replacement upload path and whether the Doctor can share it.

3. Should the Doctor's tests be kept out of the everyday run?

Andrew, on the test project in Reviewable
Seems like we do something to prevent all these FreezeDoctor tests from running every time. Mark as Nightly or make a new category?

The naming half of Andrew's comment is done. On the category half, this run measured the tests rather than guessing. The 262 tests in the Doctor's own project take 5.4 s in total, about six seconds wall clock; the 27 Bloom-side tests take 0.1 s. One test, RobustFileCopy_LogHeldOpenForWriting_Throws, takes 1.9 s because it waits on a real file lock. Everything else is under a second. The Doctor's tests are a separate project, so they do not run as part of BloomTests anyway; CI would need to invoke them explicitly.

Six seconds is well inside what an everyday run absorbs, which is why Leave as is is recommended.
