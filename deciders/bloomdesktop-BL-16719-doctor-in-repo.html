What this PR is about

Problem

Users tell us Bloom froze, and we get almost nothing to work with. Their problem report is written after they killed Bloom, so it describes a healthy new process, and the log holds only what Bloom managed to write before it stopped responding. Three quite different failures arrive looking identical: the UI stops responding; Bloom exits without reporting anything; or Bloom's window is gone while the process lives on, so the user cannot start Bloom again. BL-16697 is the live example.

Cause

Nobody is watching at the moment it happens, and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait on an STA thread still dispatches sent messages, so the window answers probes and both Process.Responding and IsHungAppWindow report it healthy while Bloom is completely stuck — measured on a real Bloom at nine minutes frozen, reported responsive throughout. WM_TIMER is not dispatched, which is why detection rests on a UI-thread heartbeat published through shared memory rather than on either API that looks built for the job.

What the PR does

  • Adds a companion Windows app, shipped and signed inside Bloom's installer, that is already running when the trouble starts.
  • Has Bloom publish its own health through a shared-memory page a watcher can read without Bloom's cooperation, prove its clean exits, name the log file this run is using, mark work that is legitimately slow, and say when it was told to break itself.
  • Has the Doctor watch for the three states, gather evidence while the process still exists, queue reports on disk because a freeze often arrives with a dead network, and file a YouTrack card by itself.
  • Leaves a frozen Bloom alone — it may hold unsaved edits living in the WebView2 DOM. Only a window-less one is ended, where there is nothing left to save.
  • Ships switched off: a debug-menu toggle, "Run Freeze Doctor", starts it at once and is remembered. Until it has something to report it shows only a tray icon.

Worth knowing

  • The crash-dump path has still never been exercised. It could not fire at all until this run — nothing created either of the two named events it uses — so both ends are new code that no crash has been run against. It is the least-proven thing in the PR, and it is now the first item on the card's manual-test notes.
  • Joining a freeze and the death that follows onto one card cannot be seen in testing. The join only applies to reports that are actually going to be filed, and nothing provoked deliberately ever is — so a tester correctly sees two report folders. It matters only in the field.
  • One capability was deliberately dropped rather than narrowed. A WebView2 renderer crash can no longer count as evidence about Bloom. There is no correct version of that check: the pid in such an Event Log entry is the renderer's own, so it could never tell Bloom's renderer from Teams'. Bloom normally survives a renderer crash anyway, and this code only runs once Bloom has gone.

Decisions

Bloom publishes health data even when the Doctor is switched off

Every Bloom, for every user, opens the shared-memory page, starts a watchdog thread, and rewrites a small session file every ten seconds — whether or not "Run Freeze Doctor" is on, and it is off by default. Devin flagged this as a cost borne by everyone for a feature almost nobody has enabled.

It is intentional, and the reason is real: the data has to already exist when someone switches the Doctor on while a freeze is happening in front of them, and a session file that only started being written after the setting was enabled would be no help to a Doctor started tomorrow to look at an orphaned session. The counter-argument is simply that the bill is paid by all users, always.

Notes

"Report now" files a real card even on a developer build or a rehearsal

Everywhere else, the Doctor refuses to file when the build is a developer one, when the failure was deliberately simulated, when a debugger has been attached, or when Bloom already reported the problem itself. The "Report now" button — the one you have to hold CTRL to reveal — passes straight through all four.

That reads as deliberate rather than forgotten: it is a written-out "yes, file this" on a path only a person can start. Against it: the card's own manual-test notes promise testers that nothing they provoke deliberately is ever sent, and --force already exists for anyone who wants filing on a machine that would normally decline. I have documented the current behaviour in those notes either way, so a tester will not be surprised by a card.

Notes

The Doctor never releases the handle on a Bloom it watched

Each watched Bloom is held through a Process object that is never disposed, so the Doctor accumulates one operating-system handle per Bloom it has watched, for as long as it runs. Slow, and harmless in a short session; untidy in a Doctor left running for days.

The obvious fix is wrong, which is why I have not made it. That handle is what supplies the exit code of a process that has already died — holding it open past the death is the whole point — and the exit examination reads it from a background task. Releasing it when the discovery sweep lets go of the watcher would take it away from an examination still in progress and lose exactly the evidence it exists to preserve. Doing it properly means handing ownership to the examination and releasing it when that finishes, including on its early-return paths.

Notes

The last of the merge race

Two things can write to a queued report at once: a gather adding a new occurrence to it, and a drain filing it. Until this run the gather could write its stale copy back over a bundle that had just been filed, which restored it to "waiting" and dropped the card it had gone to — so the same report was filed twice, by way of the very mechanism meant to prevent duplicates.

That path is now closed: the merge re-reads from disk immediately before writing and refuses if the bundle has left the queue. But it is still a read-then-write, so a very unlucky interleaving remains possible. Closing it completely means taking the same lock the drain uses.

Recommended as-is because the remaining window needs a drain to complete inside the few milliseconds between a re-read and a write, the consequence is one duplicate comment rather than lost evidence, and the alternative makes a gather wait on a network upload.

Notes

A repeat of the same problem still discards its own evidence

When the same problem happens again while its report is still queued, the second report's files are dropped and only a count goes up. That is deliberate for a genuine repeat — two dumps of one freeze are near-identical, and attaching both doubles the size of the card for nothing. A different problem with the same Bloom now does keep its evidence, which is how a crash's dump reaches the card.

Devin flagged the remaining case. The question is whether a repeat's dump is ever worth having — it would be, if the second occurrence had a different stack that the fingerprint was too coarse to tell apart.

Recommended as-is because the fingerprint includes the top five UI-thread frames, so two occurrences sharing it really are the same stack — and a user offline for a fortnight would otherwise upload a dozen copies of it.

Notes

For your information — the tracker token now travels in a second executable

The Doctor files cards using the same shared auto_report_creator token that Bloom itself already ships, embedded in the same split form. No new secret is exposed, but it now sits inside a second program, so Devin asked whether that account's permissions are confined to creating issues in the projects we intend. That is a question about the tracker account rather than about this code, and only you can answer it.
