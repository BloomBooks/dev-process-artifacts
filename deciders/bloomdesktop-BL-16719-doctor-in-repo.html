What this work is about

Problem

When Bloom freezes we get almost nothing. The user kills it and carries on, and freezes are exactly the failure people do not report, so a bug like BL-16697 can only be guessed at. Any problem report is written after the kill, and describes a healthy new process.

Cause

Nobody is watching at the moment it happens — and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait still dispatches sent messages, so IsHungAppWindow and Process.Responding report a thoroughly wedged Bloom as healthy. Measured on a real Bloom: nine minutes frozen, reported responsive throughout.

What the work does

  • Bloom publishes its health — a UI-thread timer heartbeat in shared memory, which is the only signal that detects the freeze described above; plus which log file this run is writing to, what Bloom believes it is doing, and how far shutdown got.
  • Bloom marks its deliberately slow work — publishing, video, upload, download — so a legitimate five-minute job is not reported as a freeze.
  • A companion process watches, and at the moment of failure gathers stacks, wait chains, WebView2 state and the Event Log, then files a YouTrack card by itself, folding recurrences onto one card.
  • It stays quiet for developer builds, simulated failures, debugged processes, and problems Bloom has already reported itself.

It ships inside Bloom's installer and is off by default, switched on from the debug menu.

Decisions

Simplifying the Doctor

You asked for an analysis of four possible simplifications; it is written up here. In short, all four target areas that have genuinely produced bugs — and I would add two you did not list: report freezes only, dropping exit and crash classification (~1,000 lines, the densest bug cluster, and Bloom already reports crashes by other means), and detect zombies but never end them (~600 lines, removing the only irreversible action in the system).

This gates the two decisions below it, because much of the outstanding feedback sits in code these options would delete.

One of them is already done. Your clarification — that Bloom normally reports its own crashes, and the Doctor only needs the ones that exit with no indication why — turned option (E) from "drop exit reporting" into "report on evidence, never on its absence". That is implemented in 51fc21523, with the measurement behind it recorded in the code. So the choice below covers only what is left.

Eight remaining findings from the Fable review

Briefly: a post-mortem gather can connect to whatever owns CDP port 9222 at that moment — possibly a developer's own browser, whose page titles would then be quoted onto a Bloom card; an exception after a card is created turns a successful filing into a false "this happened again" and orphans the uploaded dump; a non-JSON 200 response, such as a captive portal page, escapes and strands a report while crashing --drain; a race can file a card about a Bloom the Doctor itself killed; the fingerprint can absorb other threads' frames and split one freeze across several cards; a cancelled CPU sample prints "rules out a spin loop" for a process that may be spinning; a failed attachment upload is dropped silently; and a balloon click can open the wrong card.

Five of the eight live in the outbox and evidence-gathering code that the simplification options would remove.

Devin's 46 findings on the Doctor PR

Devin reports 22 bugs, four of them marked severe, and 24 investigate flags on #8229. The severe ones concern attachments that may not be access-restricted, queue pruning deleting an upload that is in progress, a drain gate that may not actually exclude a second drainer, and a crash dump that can be aborted part-written. But its list provably contains stale entries, so none of it can be trusted without checking each item against current code — and that checking is most of the work.

The card's summary carries no [6.x] prefix, so the rule that would settle it does not apply, and this may well be deliberate for a large new feature. Changing a PR's base is not mine to decide.
