What this work is about

Problem

When Bloom freezes we get almost nothing. The user kills it and carries on, and freezes are exactly the failure people do not report, so a bug like BL-16697 can only be guessed at. Any problem report is written after the kill, and describes a healthy new process.

Cause

Nobody is watching at the moment it happens — and the worst case cannot be watched from outside at all. A WinForms UI thread blocked in a managed wait still dispatches sent messages, so IsHungAppWindow and Process.Responding report a thoroughly wedged Bloom as healthy. Measured on a real Bloom: nine minutes frozen, reported responsive throughout.

What the work does

  • Bloom publishes its health — a UI-thread timer heartbeat in shared memory, which is the only signal that detects the freeze described above; plus which log file this run is writing to, what Bloom believes it is doing, and how far shutdown got.
  • Bloom marks its deliberately slow work — publishing, video, upload, download — so a legitimate five-minute job is not reported as a freeze.
  • A companion process watches, and at the moment of failure gathers stacks, wait chains, WebView2 state and the Event Log, then files a YouTrack card by itself, folding recurrences onto one card.
  • It stays quiet for developer builds, simulated failures, debugged processes, and problems Bloom has already reported itself.

It ships inside Bloom's installer and is off by default, switched on from the debug menu.

Worth knowing

  • Devin accumulates findings rather than re-deriving them. Its bug count on #8229 ran 20 → 21 → 22 across three successive commits, and it still reports two defects at the exact commit that fixes them. Its list is therefore not "what is wrong now", and every item needs checking against current code before anyone acts.
  • Devin's earlier failure to review was not caused by PR size. I had recorded that its analysis never completed on the combined PR. It has since completed on the pre-split commit too, so those failures were transient at Devin's end. The split earns its place on other grounds, but not that one.
  • Your launch.json simulator block is gone from the working tree. It had to go for the merge, and it carried its own "do not commit". To re-arm, add "env": { "BLOOM_SIMULATE_FREEZE": "crashthread:120" } to the Bloom launch config; kinds are sleep, stawait, spin, failfast, throw, crashthread, zombie, mutexchain, with an optional :seconds.
  • Your shell still exports BLOOM_SIMULATE_FREEZE=zombie, so any Bloom launched from it hides its window and is ended by a running Doctor about 75 seconds later.
  • The wait-chain fix has not been seen against a real frozen Bloom. It changes what Windows returns, and only the same-process rehearsal exercises it; the tests cover the code, not the behaviour.

Decisions

Settled since this report was written

The branch was rebased onto Version6.5 and the temporary split collapsed back into #8229; #8259 is closed and its branch deleted.

Both remaining questions are answered. A failed attachment now says so on the card, the way the too-large path does — and the question about that exposed the too-large path's own wording as misleading, since "still on the user's machine" read as permanent when the folder is kept about 30 days, or less under volume. Both paths now name the date and warn about the volume limit. The YouTrack token stays as it is: no new risk, the key was already exposed by Bloom, and this code uses it as intended — recorded as the first line of the comment on TokenPiece and resolved on its review thread, so it stops recurring.

Simplification. Simplification 4 is implemented — the Doctor watches one Bloom, and five collections keyed by process id became five booleans. The other simplifications were declined; (E) and the exemptions it retired were done earlier. See the simplification analysis.

Review findings. Ten of Fable's twelve are fixed, and Devin's four severe ones are worked: one was real and is fixed (pruning could delete a bundle mid-upload), one was narrower than stated and has been hardened anyway, and three were already fixed in commits its list predates. Two of Fable's remain, and they are the two questions above.

Three older answers arrived and needed no work. The identity check before ending a Bloom by process id was already implemented exactly as chosen — ZombieEnder verifies identity before signalling and again before killing, and the supervisor refuses an id it is not watching. The boot-time comparison no longer exists to be tested: DidMachineGoDown was deleted along with the other absence-explaining exemptions, and its boot-time slack was where Devin's "startup crashes misread as a machine restart" came from — making it testable would mean putting it back. And the launch.json block had already been reverted, as it had to be for the base merge and said "do not commit" on itself.

The rebase dropped one thing deliberately — f8444670d, "Keep automation-launched Bloom windows off the user's active monitor", which is master-only work that came along when a branch was cut from master. The Doctor's own code is byte-identical after the rebase, and the full C# suite passes against Version6.5.
