The fix, in one paragraph

The “By Sentence” radio sits inside two nested BloomTooltips. Hover bubbles from the inner span to the outer one, so MUI opened both at once and they overlapped: the outer group tooltip (lines 95–103) saying “First, put the cursor in a box which has something to record,” and the radio’s own tooltip unconditionally saying “…use the "Clear" button to remove your recording.” The second is a line taller, so its last word peeked out below — the stray text in the report. The fix (lines 137–147) gives the radio a disabled tip only when it is genuinely disabled because of existing audio. When hasRecordableDivs is true the expression yields exactly the object it did before, so the has-audio path is untouched.

Verified live in a running Bloom over CDP on a picture-only page, counting open tooltips in the DOM: with the original code restored, 2 tooltips overlapping at nearly identical coordinates; with the fix, exactly 1, correct text. On a page with text the radio is enabled and still shows “Record one sentence at a time…”.

Decision 1 — from Devin (informational)

A pre-existing mismatch: the tooltip and the radio button disagree about when “By Sentence” is disabled

In the Talking Book tool’s Advanced section, the “By Sentence” radio button and the tooltip wrapped around it each decide independently whether the option is unavailable — and they use different rules.

The tooltip treats it as disabled when there is nothing recordable on the page or when the page has audio at all (lines 132–136). The radio button itself greys out when there is nothing recordable or when there is a whole-text-box recording specifically (lines 150–156, where the audio condition is commented out).

So in the gap between those two rules — a page that has sentence-by-sentence audio but no whole-text-box recording — a user sees a button that looks and behaves as clickable, while hovering it produces the message “If you want to change this mode, first use the "Clear" button to remove your recording.” The message says you can’t, the button says you can.

This is not introduced by this PR and this PR does not change it; Devin raised it only because the fix touches the very line that selects that message. Fixing it means deciding which rule is the correct one, which changes what users can actually click — a real behavior change well beyond the tooltip bug on this card.

Decision 2 — verification gap

The “you already have a recording” branch was not exercised in the real app

The bug on this card was reproduced and the fix confirmed in a running Bloom: on a picture-only page, the old code opened two overlapping tooltips and the new code opens exactly one, with the right text.

The other branch — where “By Sentence” is greyed out because you already recorded the text box as a whole, and the tooltip should still say “use the Clear button to remove your recording” — was not tested by hand, because producing that state needs a working microphone (or an imported recording) and a subscription that includes whole-text-box audio.

By inspection the risk is low: when the page has something recordable, the new expression evaluates to exactly the same object the old code passed, so that message cannot have changed. But “low risk by inspection” is not the same as “someone saw it work”, and this is precisely the message the fix suppresses elsewhere — so if the change were wrong anywhere, this is where it would show. It is already written up as its own section in the QA test-ideas comment on the card.

That satisfied the letter of the rule, but it is a thinner declaration than master’s, and you should know the run leaned on it.

Decision 4 — tooling finding

The front-end test suite only completes here if vitest runs the files one at a time

Running vitest run the normal way on this machine does not finish. It gets through roughly fifteen test files and then simply stops — no error, no failing test, no further output — until something kills it. Because it dies without a summary, it reads like a broken test suite, and it was previously written off as “the Version6.4 suite hangs in the talking-book audio specs”.

That description turns out to be wrong. This run, the talking-book audio specs passed cleanly, and excluding the talking-book tests altogether just moved the stall to a different file. What actually matters is how many files vitest runs at once: adding --no-file-parallelism, so files run one after another instead of spread across worker processes, makes the entire suite complete — 48 files and 524 tests, all green, in about three and a half minutes.

So there is nothing wrong with the tests, and nothing wrong with this branch; the parallel worker pool wedges on this machine. The open question is whether to leave that as folklore each of us rediscovers, or to write it down somewhere it will be found.
