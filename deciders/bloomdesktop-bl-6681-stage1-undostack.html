What this PR is about

Problem

Bloom has five separate undo mechanisms with no shared record of what happened in which order: origami's layout stack, the reader tools' per-box text undo, the image-operation undo, CKEditor's per-editable undo manager, and the browser's own. The Undo button arbitrated between four of them with a hand-written if-chain that also had to remember the BL-16558 rule (repaint the reader highlights after any undo that rewrites a text box), and no new kind of undoable operation — deleting a page, deleting a canvas element — could be added without growing that chain. This is Stage 1 of the plan to retire CKEditor and unify Undo; its whole point is to change no user-visible behaviour.

What the PR does

  • Adds the one undo stack (bookEdit/undo/): index-based with truncate-on-push, O(1) canUndo/canRedo because C# polls it on a timer, page scoping, lazy redo capture, and runUndoable so one gesture produces one entry however many layers record. Entries are data, not page-frame closures, because the page iframe dies on every navigation.
  • Wraps the four existing mechanisms as legacy providers in the old order, including the BL-16558 markup update; handleUndo and canUndo become one-line delegations. The Undo button — which C# drives through the page frame — now reaches the workspace frame's stack explicitly, rather than a second copy of the module bundled into the page frame.
  • Tells the stack about every page-frame navigation from the one place C# performs it (switchContentPage), using the page element's id as identity.
  • Binds Ctrl+Y in the page frame as a last resort: it acts only when nothing earlier claimed the key, the page is not in Change Layout mode, and the stack has something to redo — so origami's and the reader tools' own redo and CKEditor's keep winning until they are converted. No Redo button, no C# involvement.
  • Adapts the Stage 0 seam in toolbox.ts to master's BL-16717 (bookmarks only when something can rewrite the box), and adds CDP live-check harnesses under docs/retire-ckeditor/liveChecks/ that attribute each undo gesture to the mechanism that actually ran.

Verified on a freshly launched Bloom through the real Undo button entry point: the reader-tools undo, CKEditor's undo, origami's undo and the image undo each run exactly once, and Ctrl+Y never double-fires.

Where should this project land now that Version6.5 exists?

The plan's rule was "nothing merges to master until a Version6.5 branch is cut", so every stage goes to a long-lived integration branch, BL-6681-ckeditor, which merges master in weekly. That branch was cut on 2026-09-04 (master is 160 commits past it), and master's AGENTS.md now says ordinary new work targets Version6.5 during the transition. This project is 6.6 work, so master is presumably its right target again — which would also let stage PRs go straight to master, cheaper than the integration branch and its weekly syncs. Nothing has been retargeted.

File the bugs found during verification?

Verifying Stage 1 exposed problems in code this PR does not touch. In priority order: (1) pasting or dropping HTML that contains any <span style=…> makes Bloom's BL-12357 handler treat the paste as internal (CKEditor stamps every transfer with a cke/id) and restore the unfiltered clipboard HTML, so tables, iframes, images and divs with duplicate ids reach the book — a one-condition fix, but captured with synthetic events, so worth one real-clipboard confirmation first; (2) Ctrl+Z with a reader tool active runs two undos and breaks Ctrl+Y; (3) the reader-tools undo restores stale bookmark spans; (4) edit key handlers accumulate on every SetupElements re-run (F6 double-wraps); (5) the dead data-page-id check. Repros for 1, 2, 3 and 4 are committed under liveChecks/.

Restore the three master files the hook reformatted?

When master was merged into the integration branch, the pre-commit hook ran prettier over everything staged and reformatted three of master's own files (crowdin.yml, aiImageEditorOverlay.test.ts, SIL-Niger/branding.less) whose master copies don't satisfy this repo's prettier. They now show as diffs against master and could conflict on a future sync. Restoring master's bytes needs one commit made with --no-verify, which I did not do without asking.
