What this PR is about

Problem

We exceeded the Supabase egress quota (cached egress: 0). The fs edge function fetched every book file it served (thumbnails, .bloompub, PDFs, audio) from S3 and streamed it back through itself. Supabase counts every byte an Edge Function sends back as uncached egress, so all fs traffic on api.bloomlibrary.org/v1/fs counted against the quota.

What the PR does

  • The function only redirects now. fs still does the Parse lookup, the validation (400/404/405/500) and CORS preflights, but for a file it finds it answers with a body-less 302 to the S3 URL, percent-encoded so a non-ASCII title is safe in the header.
  • The Cloudflare worker carries the bytes. For /v1/fs only, it follows the 302 itself and streams the file from S3, so clients still see only api.bloomlibrary.org and get the file. Cloudflare has no egress fees.
  • Response handling moved into the worker: the header whitelist, GET/HEAD, 304 and 206 passed through, other S3 failures become 404, x-amz-* stripped, a one-year cache on harvest thumbnails, and CORS copied from the function's 302.
  • No open proxy: the worker only follows redirects into our four buckets on https://s3.amazonaws.com/; anything else is a 502.
  • Deploy order is worker first (staging worker → merge to develop → production worker → merge to main), spelled out in the PR description and cloudflare/README.md. Docs explain why; a new AGENTS.md declares YouTrack.

Worth knowing

  • Deploy order matters: merging to develop auto-deploys the function to staging, so ops must redeploy the staging worker before this merges, and the production worker before develop → main. The new worker works with the old function; the reverse breaks fs.
  • Nothing in production calls the Supabase fs URL directly (checked OPDS in bloom-azure-functions, BloomLibrary2, bloom-player, the harvester and BloomDesktop). Only local dev and tests do, and a 302 is fine for them.
  • The S3 host allowlist was checked against 4,000 production and 4,000 dev Parse baseUrls: all of them are https://s3.amazonaws.com/<our bucket>/.

Decisions

1. Should the direct Supabase fs URL stop handing out S3 addresses?

Anyone who calls the function's own address (https://sekpsuviwfhzzznzrdgx.supabase.co/functions/v1/fs/..., which needs no login and appears in the committed wrangler.toml) now gets a redirect showing the real S3 address. Older books' S3 paths contain the uploader's email address. Greptile flagged this as a privacy leak.

In practice it reveals nothing new. The same baseUrl, email included, can be read from Parse by anyone with the public application id that bloomlibrary.org ships in its JavaScript, and normal users never see the Supabase address. Locking it down would mean a shared secret that both Supabase projects and both Cloudflare workers have to hold, which adds an ops step to the deploy. I recommend leaving it.
