What this PR is about

Problem

“Update Book” — both the Collections tab command and the automatic pass that runs before the AI image editor opens or after a page-size change — showed a progress dialog that was mostly empty space. PR #8375 took the per-image log out of it but left the dialog alone: a tall window with the percent bar down at the bottom, three-quarters of it blank, and a three-sentence explanation set in the monospace log font. On the card, Hatton asked for something much shorter and attached a mock-up: the bar on top, one sentence under it. The explicit Update Book command came off worse than before, showing that title over a 400px-tall empty log box where the log used to be.

What the PR does

  • Adds SimpleProgressDialog: a title bar, a bar with the percent beside it, and one sentence — “Please wait while Bloom does some housekeeping on your book...” It shows no ordinary progress messages; a warning or error still colours the title bar and appears under the sentence, with Close and Report. It is a separate component from ProgressDialog rather than more switches on it, because that one exists to show a running commentary the user is meant to read.
  • One instance lives in App.tsx, at the top level of Bloom’s UI, and both callers open it over the websocket (MakeUpdateBookProgressProps is shared, so they cannot drift). That is the one document all three tabs render into, so the dialog is visible whichever tab is active and sits outside the page iframe the Edit tab empties while the pass runs.
  • The automatic update no longer needs a window of its own. It used a standalone WinForms ReactDialog, which is what required a separate JS bundle, a WinForms wrapper component, hard-coded window sizes, and code to resize a form that cannot size itself to its HTML. It never needed the WinForms modal in order to wait either — only a way to run its follow-up once the work finished, which is what doWhenDialogCloses is for, the mechanism Update Book already used. EnsurePerPageFixupIfNeeded became EnsurePerPageFixupIfNeededThen, and EditingModel’s tail moved into ReturnToPageAfterFixup, reached through RunOffTheApiLock so it lands back on the UI thread and off the API lock.
  • No dialog picks up another’s state. progress is a shared channel heard by every dialog in the document, and each listener is alive from the moment it mounts, while the existing cleanup only ran for a dialog that had been open before. SimpleProgressDialog now ignores events unless it is the one showing, and ProgressDialog clears all of its per-run state when it opens — including the spinner, which is only ever switched off, by an event broadcast to everyone.
  • A reported problem holds the dialog open (HaveProblemsBeenReported covers Warning, Error and Fatal), instead of closing the instant the work finishes and taking the unread message with it. And a failure to even open the dialog is caught and recovered rather than dropped, because by that point the editor has been emptied and the continuation is the only thing that puts a page back.
  • Strings: BookProcessor.HousekeepingMessage is new in BloomMediumPriority.xlf, without translate="no" (319 of the 320 trans-units added to en/ on Version6.5 in the last 30 days omit it). BookProcessor.AutoUpdateExplanation is deleted, which loses nothing: no translation of it has ever existed, it never shipped, and nothing references it.

Worth knowing

  • The Edit tab keeps its page painted behind the dialog during the automatic pass, which contradicts the “editor is deliberately empty” description on the card. That is not new: the promoted WinForms revision was rebuilt and run side by side to check, and behaves identically. The emptying that SetLayout triggers clears the page-thumbnail list but leaves the main page painted. The test ideas have been corrected accordingly.
  • The error layout was exercised, not assumed. A failure was forced temporarily so the red title bar, the message, the self-sizing dialog and the Close/Report buttons could be seen in a running Bloom — and, importantly, so that clicking Close could be seen to fire the continuation and put the editor back. The scaffolding was removed and the final tree re-checked.
  • The “nothing to do” branch was exercised too — a second page-size change on a book whose pass had already failed, where the continuation runs synchronously with no dialog. The editor came back correctly.
  • BrowserProgressDialog keeps one static slot for the after-the-dialog action. The automatic pass now holds it for the whole run rather than blocking, so anything that opened a second progress dialog in that window would silently drop the Edit tab’s continuation. Every current caller needs a click in the browser, which the backdrop blocks, so it is not reachable today — but it is worth knowing if a progress dialog is ever started from a background or toast path.

Bloom can now be closed mid-update

The old automatic-update dialog was a WinForms window shown with ShowDialog, which disables every window in the application. While it was up, Bloom’s title-bar close button, the system menu and Alt+F4 were all dead.

The replacement is HTML inside the main browser. Its backdrop covers everything Bloom draws, so the user cannot click any control — but it cannot cover the window’s own chrome. So a user can now close Bloom while the pass is still running: a background worker is rewriting every page of the book and heading for a save at the end. Closing there abandons the run. The book on disk is left as the whole-book update left it and Bloom will offer to redo the pass next time, so the expected outcome is “nothing gained” rather than “book damaged” — but the final save is a window where a hard shutdown could catch a write in progress.

You accepted the loss of OS-level modality when you approved this design; this is the same trade with its consequence spelled out. Note the Collections tab’s Update Book has always been in exactly this position, so this is not new to Bloom, only to the automatic pass.
