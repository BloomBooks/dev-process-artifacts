What this PR is about

Problem

“Update Book” — both the Collections tab command and the automatic pass that runs before the AI image editor opens or after a page-size change — shows a progress dialog that is mostly empty space. PR #8375 took the per-image log out of it but left the dialog alone: a tall window with the percent bar down at the bottom, three-quarters of it blank, and a three-sentence explanation set in the monospace log font. On the card, Hatton asked for something much shorter and attached a mock-up: the bar on top, one sentence under it. The explicit Update Book command came off worse than before, showing that title over a 400px-tall empty log box where the log used to be.

What the PR does

  • Adds SimpleProgressDialog, a new small dialog rather than another set of switches on ProgressDialog. The existing one exists to show a running commentary the user is meant to read, and the options for hiding the log, shrinking the box and reserving space for buttons had already piled up. The new one is a title bar, a bar with the percent beside it, and one sentence: “Please wait while Bloom does some housekeeping on your book...”. It shows no ordinary progress messages; a warning or error still colours the title bar and appears under the sentence, with Close and Report.
  • The automatic update shows it in a 620×180 window instead of 620×400, and no longer writes its explanation as a progress message (BookProcessor.cs:390). The Collections tab command shows the same thing through a new embedded instance (CollectionModel.cs:733); it had been sharing the collectionTab dialog with .bloomSource import, which does want a log.
  • Stops a progress dialog picking up another one’s state. progress is a shared channel — every progress dialog in the document, and in Bloom’s other browsers, hears every event — and each listener is alive from the moment it mounts, while the existing cleanup only runs for a dialog that has been open before. A dialog that had never opened therefore accumulated somebody else’s percent, errors and show-buttons, then opened at the last job’s percent with a red title bar and a live Close button; pressing it told Bloom the job was over while the book was still being rewritten.
  • A WinForms form cannot size itself to its HTML, so a failed run grows its window to 300px (GrowDialogForError) to fit the error and the buttons, instead of standing that tall and empty for every run that goes well.
  • Strings: BookProcessor.HousekeepingMessage is new in BloomMediumPriority.xlf, without translate="no"; BookProcessor.AutoUpdateExplanation is marked obsolete as of 6.5 and left in place. Storybook stories cover the ordinary case, the error case, and the WinForms size.

Worth knowing

  • The error layout was verified for real, not assumed. A failure was forced temporarily so the red title bar, the message and the grown window could be seen in a running Bloom; that scaffolding was removed and the final build re-checked. Screenshots of all three states are attached to BL-16893.
  • The automatic dialog is a fixed-size window. 620×180 fits the sentence on one or two lines; a translation that runs longer will scroll inside the window rather than making it grow. That is a real limit of a WinForms-hosted dialog, not an oversight, but it is the thing most likely to look wrong in another language.
  • The cross-dialog leak was pre-existing, not introduced here — both dialogs always had it. Splitting Update Book onto its own instance is what made it reachable, which is why the fix touches the shared ProgressDialog as well as the new one.

What should happen to the template-books item?

One event is still unfiltered

The Collections tab now hosts two progress dialogs: the existing log-showing one, and the new compact one for Update Book. When C# tells a dialog to open it names which one (open-progress carries a which), and each dialog ignores an open meant for the other. When C# tells a dialog to close, it names nobody — so both dialogs act on every close.

Today that cannot cause a problem: only one progress dialog is ever open at a time (the C# side that drives them holds a single job), and telling an already-closed dialog to close does nothing. So this is a latent coupling rather than a bug, and it is the one local-review finding not acted on.

Harden the close event now, or leave it?
