What this PR is about

Problem

The new React Collection Settings dialog still showed a placeholder on its Advanced page, so a user could not turn automatic updating on or off or rename the collection there, which the old WinForms dialog allows.

What the PR does

  • A real Advanced page with Program › Automatically Update Bloom and Collection › Collection Name. Saving and renaming go through the shell's existing settings properties; a name change turns OK into Restart.
  • Since the save stores exactly what it is sent, the dialog trims any text the user edited, on any page, before deciding on Restart and before saving: spaces typed around a collection name are not a rename, and no folder gets a name ending in a space. Values the user did not touch go back exactly as loaded.
  • In a Team Collection the name is greyed out with the old dialog's explanation underneath, faded with the row like any disabled Config-R row's description.
  • Three new strings in BloomMediumPriority.xlf, marked translate="no"; the other labels reuse existing ids.
  • Unit tests, and an e2e journey test that saves auto-update and renames the collection through Restart. For that, a Bloom running under --e2e passes its launch options on when it relaunches itself (as it does to finish a rename), the renaming copy waits for the old Bloom to exit, and the e2e fixture follows the relaunched copy.

1. Should a non-e2e automation Bloom also keep its options across a rename?

Devin flagged that a Bloom started with --automation but not --e2e (for example an agent's dev Bloom, which has --dont-disturb and sometimes its own --user-settings-folder) still loses those options when it relaunches itself to finish a rename: the new copy uses the shared user settings and may take the foreground. That is how every rename relaunch behaved before this PR; we limited forwarding to --e2e because a ./go.sh Bloom's Vite server stops when it exits, so forwarding --vite-port there would leave the new copy loading nothing. The recommended split keeps that reason: forward the harmless options for any automation run, and the Vite and e2e-only ones only for --e2e.
