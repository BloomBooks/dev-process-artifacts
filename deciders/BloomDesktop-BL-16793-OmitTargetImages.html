The change itself

Two things, both in the AI-image-editor API.

  • The clones are no longer offered. A Bloom Games target holds a copy of its draggable's whole content — image container and picture included — so each one looked like another editable image. The card's page offered seven pictures where it has four. EnumerateBookImages now declines any slot inside a target: AiImageEditorApi.cs:1270, using IsSlotInsideGameTarget.
  • The filtering deliberately stays out of SelectImageSlotsOnPage. A picture's identity is its position in that unfiltered list, and the browser side works the same position out for itself, so a declined slot has to keep its place. A test pins that: AiImageEditorApiTests.cs:1366.
  • The clones are kept in step on commit. Now that they can't be edited, nothing else would repoint one when an AI edit replaces a draggable's picture on a page you don't have open — the shadow would keep showing the replaced picture, and its stale reference also stopped Bloom reclaiming the superseded file. AiImageEditorApi.cs:1745 repoints them via GetGameTargetImageCopiesOfSlot.
  • Each of a draggable's pictures maps to its own copy. A target holds a copy of the draggable's whole content, so a draggable with two pictures gives the target two copies; the copy for a given picture is the one in the same position. Pairing by position rather than repointing every copy is what the review fix added: AiImageEditorApi.cs:985, with a test for it.
  • The page you have open needs nothing extra — and that was tested, not assumed. Selecting the swapped picture, which the browser side already does so Ctrl+Z can offer the undo, is what makes Bloom rebuild the copy: aiImageEditorPageCommands.ts:151. An A/B against a running Bloom showed the shadow stays stale without that step and follows with it, so the extra code first drafted for this was dropped and only the comment kept.

Known limitation

After an off-page AI edit, the shadow can briefly be the wrong shape

When the AI image editor replaces a picture belonging to a draggable on a page you do not currently have open, Bloom now points that draggable's target — the shadow the reader drags onto — at the new file. But the shadow's copy also inherited a width, a height and any cropping from the old picture, and this change deliberately leaves those alone. So if the new picture is a noticeably different shape, the shadow can look stretched or cropped differently from the draggable itself.

It corrects itself: the next time you open that page and select that draggable, Bloom rebuilds the whole copy from it and the shadow matches again. Reproducing the sizing rules in the C# would mean a second, poorer copy of logic the browser side already owns, which is why leaving it is recommended.

Confirm

The pull request targets Version6.5, not master

This repo's default branch is master, so a PR opened without thinking would have gone there. This one targets Version6.5 instead, for three reasons: the branch was cut from Version6.5 and its tip was exactly that branch's tip, the card sits on the "Bloom 6.5" board, and the repo's own convention is that release work lands on the version branch and is merged forward to master later.

The project's rule that a [6.X] prefix on a card's summary names the target branch did not settle it, because this card has no such prefix — so this was a judgement call from the evidence rather than something the card stated, which is why it is worth a glance.

For information

Half the diff is beyond what the card asks for

The card asks only that Bloom stop sending game target images to the editor. About a third of the change does something further: it keeps those copies pointing at the right file when an AI edit lands on a page you do not have open. That was chosen deliberately while planning, because the moment the copies stop being editable, nothing else updates them — the shadow would go on showing the replaced picture, and its stale reference to the old file also stopped Bloom from reclaiming that file, so it would sit in the book folder indefinitely.

Flagged here only so a reviewer meeting the diff cold is not surprised to find two things in it.
