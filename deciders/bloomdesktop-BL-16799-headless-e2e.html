What this PR is about

Problem

Every run of the src/BloomE2E suite took over the developer’s desktop: Bloom opened a real window, maximized, in the taskbar. That alone makes the suite unusable while working. Worse, a test could pass while Bloom was driving a document the test never looked at, so publish-text-languages.spec.ts failed roughly one run in three for no visible reason. A handful of workarounds in the test library existed only because Bloom was hard to drive.

Cause

Two of those had one cause. A run gave every WebView2 environment the same remote-debugging port number, so only the first browser process to start could listen on it, and which process that was depended on startup timing; the fixture then attached to whichever document the debugging protocol listed first. Separately, editView/jumpToPage replied “succeeded” to a jump the Edit tab silently dropped while it was loading a page.

What the PR does

  • The suite runs off-screen. A new --headless flag puts the shell and the splash screen far to the left of every monitor, out of the taskbar, without touching the saved window placement. Off-screen rather than minimized, because WebView2 stops painting a minimized window and screenshots come back blank. BLOOM_E2E_HEADED=1, or Playwright’s --debug, shows the window.
  • A test attaches to the document Bloom drives. Browsers built on the UI thread share one WebView2 environment under --e2e, so a run has one browser process and one debugging listener, and a new e2e/shellUrl hook names the document Bloom drives for the fixture to confirm.
  • A run can test the working tree. BLOOM_E2E_VITE_PORT=<n> passes --vite-port, so a front-end edit reaches the suite without the full front-end build.
  • Bloom is easier to drive, each change removing a workaround: JumpToPage queues a jump that arrives while the Edit tab is busy and reports a failure when it can do neither; a new e2e/setCollectionLanguages hook does the work of the Collection Settings dialog’s OK button, so no test composes .bloomCollection XML; the workspace tabs carry data-testid attributes, so the suite works in any UI language; and typing inserts a whole string in one call instead of one key press per character.
  • Other automation debt paid. A visual-regression case collects every failed image comparison and fails once at the end. Toolbox tool registration is a side-effect-free registerAllToolboxTools() that both the bootstrap and the test harness call. The component-tester Playwright suites have a nightly job. The bloom-automation scripts answer --help without killing anything, reject an unknown flag, and reject a malformed process id.
  • The add-e2e-test skill states how the suite stays maintainable as it grows toward a few thousand tests: every step of a test is a helper call, and src/BloomE2E/helpers/ is the one place that knows how to drive Bloom.

Worth knowing

  • Nothing here was tried by hand in Bloom. The page-jump queueing and the toolbox registration list are the two changes a user could notice, and both are covered only by the automated suites. The test ideas on BL-16799 say what to click.
  • Which front end an end-to-end run tests depends on what else is running. A run without BLOOM_E2E_VITE_PORT serves output/browser, which can be any age, and Bloom auto-detects a dev server already on port 5173. So the same run can test different code on two machines. It is written down in src/BloomE2E/AUTOMATION-DEBT.md and left for later.
  • One test’s tab is the next test’s starting state. The suite shares one Bloom per worker, and nothing makes a test put the workspace back. The new capture test leaves the Edit tab and had to be taught to switch back. Also in AUTOMATION-DEBT.md.
Three test waits were enlarged. Do you approve them?

src/BloomBrowserUI/AGENTS.md says: “Don’t use timeouts in tests, that slows things down and is fragile. If a timeout is justified, get my approval and add a comment explaining it.” Three places on this branch enlarge a wait and explain why in a comment, but none of them has your approval, which is the other half of that rule. Devin and Greptile both stopped on it.

The three: an error message wait in the link-target-chooser tests raised from 1 second to 10 (error-handling.uitest.ts:14); the registration opt-out button wait raised from 2 seconds of buffer to 8 (test-helpers.ts:19); and a 120-second per-test limit on the new nightly component-tester job (nightly.yml:422). Each was failing about once per full-suite run and passing when run alone.

All three are waits for something to appear, not sleeps, so a passing run finishes exactly as fast as before; only a failing one now takes longer to give up. That is what the rule is guarding against (slow, fragile) and it is why I think they are the right kind of wait to enlarge.

A test now expects “Spanish” where it expected “español”. Is that the right answer?

One case in the Text Languages publish list (Notion Test Case ID 169) checks what happens to a language after you remove it from the collection while a book still uses it. The publish list keeps showing it, so the book’s text is not silently dropped.

The old test made the language disappear by rewriting the collection file behind Bloom’s back, and the list then showed the language’s own name for itself, “español”. The new test removes it the way a person does, through the code behind the Collection Settings dialog’s OK button, and the list shows the name the collection remembers, “Spanish”. So the test now expects “Spanish” (publish-text-languages.spec.ts:181).

I believe “Spanish” is what a real user sees, because the new route is the one a real user takes. But this is a claim about what Bloom shows a person, so it should be your call rather than mine, and it may mean the Notion test case’s own wording needs updating too.
