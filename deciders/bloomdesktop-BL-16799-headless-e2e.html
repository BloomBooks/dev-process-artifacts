What these two PRs are about

Problem

Every run of the src/BloomE2E suite took over the developer’s desktop: Bloom opened a real window, in the task bar, once per test. That alone makes the suite unusable while working. Worse, a test could pass while Bloom was driving a document the test never looked at, so publish-text-languages.spec.ts failed roughly one run in three for no visible reason. A row of workarounds in the test library existed only because Bloom was hard to drive.

Cause

Two of those had one cause. A run gave every WebView2 environment the same remote-debugging port number, so only the first browser process to start could listen on it, and which process that was depended on startup timing; the fixture then attached to whichever document the debugging protocol listed first. Separately, editView/jumpToPage replied “succeeded” to a jump the Edit tab silently dropped while it was loading a page, so the caller waited a minute for a page that was never coming.

What PR 8285 does: the window leaves the screen

  • A new --headless flag puts the shell and the splash screen far to the left of every monitor and out of the task bar, without touching the saved window placement. Off-screen rather than minimized, because WebView2 stops painting a minimized window and screenshots come back blank. BLOOM_E2E_HEADED=1, or Playwright’s --debug, shows the window.
  • Windows calls a far-off-screen window occluded and Chromium then stops rendering it, so a headless run disables CalculateNativeWinOcclusion and passes --disable-backgrounding-occluded-windows.
  • The window leaves the task bar from the Shell constructor, before the window handle exists. This is the root cause of a failure that cost most of this run to find: assigning ShowInTaskbar on a form that is already showing makes Windows Forms recreate the form handle and every child handle with it, the WebView2 host included. The Edit tab then held a browser that no longer answered a jump to another page, so every test that moves between pages hung.

What PR 8276 does: the debt is paid

  • A test attaches to the document Bloom drives. Browsers built on the UI thread share one WebView2 environment under --e2e, so a run has one browser process and one debugging listener, and a new e2e/shellUrl hook names the document Bloom drives for the fixture to confirm.
  • A run can test the working tree. BLOOM_E2E_VITE_PORT=<n> passes --vite-port, so a front-end edit reaches the suite without the full front-end build.
  • A page change is no longer lost. JumpToPage shows the page, or refuses and says so. A jump asked for while the Edit tab is not showing is remembered and shown when that tab opens, which is what the Book Settings style links do from the Collection tab; before, Bloom showed the last edited page instead.
  • No test composes collection XML. A new e2e/setCollectionLanguages hook does the work of the Collection Settings dialog’s OK button.
  • The suite works in any UI language. The workspace tabs carry data-testid attributes, so no test matches a localized label. Typing inserts a whole string in one call instead of one key press per character.
  • Other debt paid. A visual-regression case collects every failed image comparison and fails once at the end. Toolbox tool registration is a single registerAllToolboxTools() that both the bootstrap and the test harness call, and that skips a tool the toolbox already has. The component-tester Playwright suites have a nightly job. The bloom-automation scripts answer --help without killing anything, reject an unknown flag, and reject a malformed process id.
  • The add-e2e-test skill states how the suite stays maintainable as it grows toward a few thousand tests: every step of a test is a helper call, and src/BloomE2E/helpers/ is the one place that knows how to drive Bloom.

Worth knowing

  • Nothing here was tried by hand in Bloom. Three changes in PR 8276 are ones a person could notice: the remembered page jump, the refused page jump, and the toolbox tool list. All three are covered only by the automated suites. The test ideas on BL-16799 say what to click, and the note on BL-16804 says why there is almost nothing to click there.
  • Which front end an end-to-end run tests depends on what else is running. A run without BLOOM_E2E_VITE_PORT serves output/browser, which can be any age, and Bloom auto-detects a dev server already on port 5173. So the same run can test different code on two machines. It is written down in src/BloomE2E/AUTOMATION-DEBT.md and left for later.
  • One test’s tab is the next test’s starting state. The suite shares one Bloom per worker, and nothing makes a test put the workspace back. Also in AUTOMATION-DEBT.md.
  • A dropped language is named differently on CI and on your machine. Master’s version of the publish test expected español; CI answers espagnol, French for Spanish, every time. Andrew traced it on master while this run was going: Bloom asks LibPalaso for the name of the language in the collection’s metadata language, and LibPalaso honors that only where it can find a native ICU library. Bloom ships icu.net without icuuc.dll, so the answer tracks the machine, not the run. BL-16806 is the card. No test on PR 8276 reaches that lookup any more, so the coverage loss is recorded in AUTOMATION-DEBT.md.
Three test waits were enlarged. Do you approve them?

src/BloomBrowserUI/AGENTS.md says: “Don’t use timeouts in tests, that slows things down and is fragile. If a timeout is justified, get my approval and add a comment explaining it.” Three places in PR 8276 enlarge a wait and explain why in a comment, but none of them has your approval, which is the other half of that rule. Devin and Greptile both stopped on it.

The three: an error message wait in the link-target-chooser tests raised from 1 second to 10 (error-handling.uitest.ts:14); the registration opt-out button wait raised from 2 seconds of buffer to 8 (test-helpers.ts); and a 120-second per-test limit on the new nightly component-tester job (nightly.yml). Each was failing about once per full-suite run and passing when run alone.

All three are waits for something to appear, not sleeps, so a passing run finishes exactly as fast as before; only a failing one now takes longer to give up. That is what the rule is guarding against (slow, fragile) and it is why I think they are the right kind of wait to enlarge.

A test now expects “Spanish” where it expected “español”. Is that the right answer?

One case in the Text Languages publish list (Notion Test Case ID 169) checks what happens to a language after you remove it from the collection while a book still uses it. The publish list keeps showing it, so the book’s text is not silently dropped.

The old test made the language disappear by rewriting the collection file behind Bloom’s back, and the list then showed the language’s own name for itself, “español”. The new test removes it the way a person does, through the code behind the Collection Settings dialog’s OK button, and the list shows the name the collection remembers, “Spanish”. So the test now expects “Spanish” (publish-text-languages.spec.ts:351).

I believe “Spanish” is what a real user sees, because the new route is the one a real user takes. But this is a claim about what Bloom shows a person, so it should be your call rather than mine, and it may mean the Notion test case’s own wording needs updating too.

The Edit tab can still be wedged. Which fix do you want?

A request that changes the page, arriving between two announcements that one page’s DOM has loaded, leaves the Edit tab in SavePending and refusing every later page change until you leave the tab. A person meets it by clicking a page thumbnail at exactly the wrong moment. It is older than this suite, and neither PR causes it or fixes it.

What PR 8276 does is stop the suite from meeting it: jumpToPage now refuses a jump that would arrive at that moment, and the helpers wait until the page has stopped announcing itself. The page list a person clicks does not go through that endpoint, so the defect is still reachable by hand.

The mechanism, from Bloom’s own log: the first announcement moves the tab to Editing; the page change then asks the browser for the page content so it can save the page being left; the second announcement is refused because a save is in flight; and the browser never answers the save request. Written up in src/BloomE2E/AUTOMATION-DEBT.md.

Both fixes change how Bloom saves, which is why this is your call and not mine.
