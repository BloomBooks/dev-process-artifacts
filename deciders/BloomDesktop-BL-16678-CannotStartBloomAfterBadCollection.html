Decision

A broken Bloom installation now shows two dialogs instead of one

While opening a collection, Bloom can discover that pieces of its own program are missing — a damaged or half-finished install. It shows a specific message for that: “Bloom was not able to find all its bits… please run the installer again and choose ‘Repair’”, and then asks to quit.

Before this PR, the code carried straight on after that message into a line that crashed on something it had just failed to build. So the message the user saw was right, but the crash report that went to us named a meaningless internal error instead of the missing file. That is now fixed — the real error is passed along properly. The side effect is that Bloom's normal “had a problem loading the X collection” message also appears, so a user with a broken install sees two dialogs in a row rather than one.

Devin raised this independently, so your answer here also closes its review thread, which is deliberately left open until you decide.

Decision

Bloom now quits if it cannot even show the collection list

The Open/Create Collections dialog is the only way back in when a collection won't open. If showing that fails, Bloom now reports the problem and closes.

Previously the failure went to the general error handler, which during startup shows a message and then lets Bloom keep running — with no window on screen, no way for the user to quit it, and still holding the lock that makes the next launch say “Bloom is already running”. Closing is a poor outcome but a much better one than that, which is why it is recommended; the change worth noticing is that a user who would previously have been left with an invisible Bloom will now see it disappear.

Decision

A collection that won't open stays at the top of the recent list

Nothing removes a collection from the recently-used list just because opening it failed. So if the collection you were last in has become unopenable, every launch from then on tries it, shows the error, and offers you the list — until you pick something else, which pushes the good one to the front.

It is always recoverable, just irritating. I recommend leaving it: the list already drops entries whose folder isn't reachable, and it refuses to re-add one, so demoting on a single failure would quietly remove a Team Collection from the dialog after one launch while the network share happened to be down. A collection that nags is better than one that vanishes.

FYI — found while working, not fixed here

A read-only collection folder kills Bloom outright, blaming Windows Defender

While loading a collection's settings, Bloom checks whether it can write to the collection folder. If it can't, it shows a message about Windows Defender's ransomware protection and then terminates the process immediately — from deep inside loading, so none of the normal shutdown runs. Nothing releases the lock that stops the next launch, and the user is never offered a different collection.

Any folder Bloom can't write to trips this, not just a Defender-protected one — a collection on read-only media or with restrictive permissions gets the same wrong explanation and the same dead end. It is out of scope here, but it is the worst remaining “bad collection makes Bloom unusable” path.

FYI — found while working, not fixed here

Double-clicking a collection file adds it to the recent list before trying to open it

When you open a .bloomCollection from File Explorer, Bloom records it as your most recent collection first and only then attempts to open it. So one double-click on a broken collection makes every later plain launch of Bloom try it again and show the error, even though the user never successfully opened it.

This is closely related to the recent-list decision above and would probably be fixed by the same piece of work, so it is only worth doing if you choose to act on that one.

FYI — found while working, not fixed here

There is no way to start Bloom without opening the last collection

If the remembered collection somehow makes Bloom fail badly enough that you never reach the Open/Create dialog, there is no escape hatch — no command-line switch, and no “hold Shift while launching” to skip straight to the collection list. The only route is editing Bloom's settings file by hand.

This PR makes reaching the dialog much more reliable, which is why it is recommended to leave it; the hatch would be insurance against a case we now believe is handled.

FYI — found while working, not fixed here

If a Team Collection's shared folder drops out, Bloom stops noticing changes and never says so

Bloom watches the collection folder and the shared folder for changes. Starting those watchers is not guarded, and nothing listens for the error they raise when a folder becomes unavailable mid-session — which is what happens when a network share or Dropbox folder goes away.

The practical consequence: Bloom carries on looking normal but silently stops picking up other people's changes until it is restarted. Nobody is told. Failing to start a watcher was the original BL-16679 crash, so this is the same area, but the runtime-drop-out case is a distinct problem and a distinct piece of work.

FYI — tooling, not code

The add-test-ideas skill isn't installed, only cloned

Preflight is supposed to hand the QA write-up to the add-test-ideas skill. That skill exists in your bloom-team-skills clone but has no symlink in ~/.claude/skills, so it can't be invoked by name — an agent that doesn't happen to know it's there will either skip the step or improvise its own format.

I read it out of the clone and followed it, so the comment on the card is in the right shape. The one-line fix is the same symlink the other team skills already have.
