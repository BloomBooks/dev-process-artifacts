What this PR is about

Problem

Bloom was on libpalaso 18.0.0-beta0046, a prerelease. libpalaso 18.0.0 shipped on 2026-10-12. We were also skewed on L10NSharp: Bloom referenced L10NSharp 11.0.1, but L10NSharp.Windows.Forms, whose LocalizationManagerWinforms Bloom calls directly, arrived only through libpalaso, at 10.0.0-beta0004.

What the PR does

  • Moves every project to libpalaso 18.0.0 and SIL.libpalaso.l10ns 18.0.0.
  • Moves L10NSharp to 12.0.0-beta0006, the newest on NuGet. L10NSharp.Windows.Forms becomes a direct reference at the same version, which ends the skew.
  • Raises two direct pins that 18.0.0 now needs: Markdig.Signed 1.4.0, and Microsoft.Extensions.DependencyModel 10.0.9 for icu.net 4. That also makes Bloom load System.Text.Json 10.0.9 instead of the shared framework's 8.x.
  • Drops a System.Resources.Extensions pin that libpalaso now sets itself.
  • Records the upgrade in docs/winforms-dependencies/PLAN.md. The WinForms surface is unchanged.

beta0046 is only 4 commits behind v18.0.0, so the 18.0.0 changelog's breaking items (ordinal comparisons, GlobalMutex, ImageCropper and so on) already ship on master. The per-item review is in the PR description.

Decisions

L10NSharp: keep 12.0.0-beta0006, or stay on 11.0.1?

The brief was to take the newest packages, prereleases allowed. The newest L10NSharp is 12.0.0-beta0006 (with L10NSharp.Windows.Forms 12.0.0-beta0006). Its only changes since 11.0.1 are nullable reference-type annotations, a protected OnClosing → OnFormClosing override in LanguageChoosingDialog, and a where T : class constraint on FallbackLanguagesDlg<T>. libpalaso 18.0.0 was compiled against 11.0.1, but those changes stay binary-compatible. All tests pass, and in a running Bloom the UI-language menu listed 33 languages, switching to español and back worked, and nothing errored. Bloom gains nothing functional from 12, and it is a beta.

Does this PR need a test of its own?

No test was added or changed. The PR only changes package versions and comments, so whether Bloom still works on the new packages is what every existing test checks. BloomTests and BloomFreezeDoctor.Tests both pass on this branch. Beyond the tests, the installer's dependency check passes on the shipped apps, the live check above was done, and all 76 markdown files in the repo render the same HTML under both Markdig versions.

Move our license code onto the core *Info types: in this PR, or its own?

This is step 1 of docs/winforms-dependencies/PLAN.md. Bloom still builds licenses with the WinForms classes CreativeCommonsLicense and CustomLicense in SIL.Windows.Forms, in 4 BloomExe files and 5 test files. The upgrade didn't unlock this: CreativeCommonsLicenseInfo and CustomLicenseInfo have been in SIL.Core since beta0001, and the WinForms classes subclass them. Swapping the constructors and the is checks is therefore mechanical. The real work is the CC badge. Two places, the book's license.png (BookCopyrightAndLicense.UpdateBookLicenseIcon) and the badge endpoint in CopyrightAndLicenseApi, get it from ILicenseWithImage.GetImage(), which a core type doesn't have. The 7 badge PNGs would ship as files, with a small lookup from license to file. Metadata stays on SIL.Windows.Forms until the image work, so the package reference doesn't go away yet. One thing to watch: license.png is written into book folders and published output, and copying the file bytes instead of re-encoding a bitmap changes that file the next time a book's license is saved.
