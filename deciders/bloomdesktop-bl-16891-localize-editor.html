What this PR is about

Problem

The AI image editor is a separate app that Bloom opens in an iframe, and it was English-only. Whatever language a user had set Bloom's own interface to, every button, label, message and art-style name inside the image editor stayed in English. It also showed descriptive text that is never going to be translated at all, sitting in English inside an otherwise translated Bloom.

What the PR does

  • As it starts up, the editor now POSTs its whole string table — every localization id with its English — to a new Bloom endpoint, aiImageEditor/localizations. Bloom replies with just the ids it has a translation for, and the editor shows its own English for everything else. An editor build newer than Bloom's XLF files therefore runs those strings in English and nothing else changes.
  • That endpoint deliberately avoids Bloom's general-purpose i18n/loadStrings, which reports every id it cannot find: on a Developer-channel build that would mean a toast plus a CopyToDistributionXlf_ entry per string, on every launch, for hundreds of strings. A new I18NApi.GetAvailableTranslations does the same lookup silently.
  • The launch reply now also tells the editor which language Bloom's UI is in (uiLanguageId), so the editor can hide the text it never translates instead of showing it in English.
  • 198 English source strings for the editor's UI are added to BloomMediumPriority.xlf and BloomLowPriority.xlf, each with a note giving the translator context.
  • Spanish, French, Indonesian and Portuguese translations of those strings are committed alongside them.
  • The editor package moves from dist-v0.2.5 to dist-v0.2.7 — the build that asks Bloom for its strings.
  • bookEdit/aiImageEditor/AGENTS.md records how this works and why the separate endpoint exists, and the Bloom-exe host-contract test now covers both the new endpoint and uiLanguageId.

Worth knowing

  • Nothing here has been run by hand. The endpoint is covered by a host-contract test that needs a live Bloom, and no one has opened the editor in a Spanish Bloom and looked at it. Whether the right words appear in the right places is unverified.
  • The editor's table has 215 entries; 95 of them have no English entry in Bloom's XLF files. Those will show in English in every language. That is the designed fallback, so nothing breaks — but it means a translated editor is visibly half-translated. Decision 3 asks whether that is the intent for this round.
  • The XLF files themselves check out: all ten parse, no duplicate ids, every id in a language file exists in en/, no existing entry had its id or source text changed, and every new entry carries a translator context note. The {0}-style placeholders in the Spanish, French, Indonesian and Portuguese translations all match their English, and no braces are unbalanced.
  • The new endpoint's silence has one pre-existing exception, worth knowing before someone relies on it. It reports nothing for a string it cannot find, which is the point of it. But on a debug build, a translation whose braces String.Format rejects still raises a dialog, from deeper in I18NApi, once per offending id per editor launch. Nothing triggers it today — the placeholder check above is exactly that — but a future broken translation coming back from Crowdin would surface there, not as a quiet fallback.

1. Spanish, French, Indonesian and Portuguese translations are committed directly

Commit 968deb3b, "Strings for AI-image-editor", adds 4,753 lines to DistFiles/localization/es/, fr/, id/ and pt/ — the four translated language folders. Each new entry is marked state="translated", which is how a translation that a human translator produced and approved looks in these files.

This repo's standing instruction, stated in AGENTS.md and again in DistFiles/localization/README.md, is that only DistFiles/localization/en/ is ever hand-edited; the other language folders are Crowdin's, and Bloom takes whatever Crowdin has. Devin flagged exactly this. Two things follow that are worth weighing: on the next Crowdin sync, whatever Crowdin holds for these ids wins, so translations added here can be replaced or reverted without anybody noticing; and in the meantime they are indistinguishable in the file from reviewed human work.

Against that: the point of the card is to get the editor out of English, and having four languages working now is real value that an empty Crowdin queue does not give.

2. The 198 new English entries have no translate="no"

DistFiles/localization/README.md says new entries are added with translate="no", which is what keeps them out of Crowdin until we say they are ready; .github/skills/xlf-strings/SKILL.md repeats it as a rule for writing entries and again as a thing to check when reviewing them. None of the 198 new entries here carries it, so on the next Crowdin sync all 198 go to translators. Devin flagged this as the second of its two findings.

Since the whole point of BL-16891 is to get these strings in front of translators, sending them is very likely what you want — the recommendation below is to leave them open, and to say so on the thread so the next person sees a rule applied on purpose rather than missed.

3. Nearly half the editor's strings have no English entry in Bloom yet

The editor build this PR pins (dist-v0.2.7) carries a table of 215 strings. 120 of them now have an entry in Bloom's English XLF files; the other 95 do not, so they will show in English in every language, forever, until someone adds them. They are not scattered oddments either — whole areas are missing: every Error.* message, everything under Settings.* and Status.*, the image-info dialog, and the history panel.

Nothing is broken by this — falling back to the editor's own English is exactly what the design intends — but it does mean a Spanish user meets a visibly half-Spanish window, and the missing half includes the error messages, which are the text someone most needs to understand. The test ideas on the card already tell the tester this is expected, so it will not come back as a bug report either way.
