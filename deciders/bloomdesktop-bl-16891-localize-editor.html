What this PR is about

Problem

The AI image editor is a separate app that Bloom opens inside the Edit tab, and it is English-only: whatever language a user has set Bloom's interface to, every button, label, message and art-style name inside the editor stays in English. Bloom has no way to tell the editor anything about language.

What the PR does

  • As it starts, the editor sends Bloom its whole string table and Bloom answers with the ids it has a translation for. Anything Bloom does not know about runs in the editor's own English, so an editor build newer than Bloom's string files still works.
  • That exchange uses an endpoint of its own, aiImageEditor/localizations, rather than Bloom's general-purpose i18n/loadStrings, which reports every id it cannot find — on a Developer build that is a toast and a line written into the local xlf per string, hundreds of times per launch.
  • The launch reply also tells the editor which language Bloom's interface is in, so the editor can hide the text it deliberately never translates (the long art-style descriptions) instead of showing English inside a translated Bloom.
  • It pins the editor to dist-v0.2.8, the build that asks Bloom for its strings.
  • While the editor has a dialog of its own open, Bloom hides the close button it draws over the editor, so two close buttons a few pixels apart cannot shut the whole editor by mistake.

The strings themselves are not in this PR. The English landed on Version6.5 and master separately so Crowdin would pick it up, and the Spanish, French, Indonesian and Portuguese text went to Crowdin as unapproved suggestions rather than being committed. So a translated Bloom shows the editor in English until those translations come back through the usual l10n_master route.

Worth knowing

  • Nothing here has been exercised in a running Bloom this run — no build was launched. The editor's side of the exchange is covered only by the host-contract test.
  • AiImageEditor.Preview.ZoomHint now carries two suggestions per language in Crowdin: the older one translates the wording before it changed ("resize the images"), the newer one the current wording ("to zoom"). A translator will see both and pick; nothing is wrong, but it looks like a duplicate if you meet it cold.
  • The translations went up as suggestions, not approvals, so no translator's existing work was overwritten and every one of them can be rejected.

Does 6.5 wait for the translations?

Crowdin now holds the editor's strings in Spanish, French, Indonesian and Portuguese, but nothing in Bloom reads them yet. Finished translations come back into master as the periodic l10n_master pull request; a release branch gets them only if someone cherry-picks that merge, which DistFiles/localization/README.md says is done for beta and is "conceivable though not usual for a release".

This PR is on Version6.5. So as things stand, 6.5 ships the AI image editor in English in every language, and the translations arrive in whatever release picks up master. The QA notes on the card now tell testers to expect exactly that, so nobody will file it as a bug — but if 6.5 was meant to show the editor translated, the cherry-pick has to be planned rather than assumed.
