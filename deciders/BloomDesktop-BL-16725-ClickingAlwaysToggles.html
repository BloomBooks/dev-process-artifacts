The layout menu stays open behind the subscription dialog

On a subscription that doesn't include custom covers, Custom still appears in the dropdown, greyed out with the subscription badge. Clicking it doesn't change the layout — Bloom opens the subscription settings instead, so you can see what the feature needs. What it doesn't do is close the dropdown, so the little menu is left sitting open while the settings dialog is up, until you click somewhere else to dismiss it.

The reason is that the shared menu component swaps in its own click handler whenever a feature is blocked, so the dropdown's own "and now close" step never runs. That is how every blocked menu item in Bloom has always behaved, and this branch didn't change it — Devin only noticed because it sits next to the new code. Recommending leaving it: it's cosmetic, it predates this work, and the fix would land in a component shared by many other menus, which is a change better made deliberately on its own ticket than tacked onto a data-loss fix.

for your call

"Nothing to do" and "done" look the same to the browser

The browser now tells the C# side which layout it wants rather than asking it to flip. If the page is already in that layout, C# answers "true" and does nothing at all — but "true" is also the answer for a switch that really happened. So if the browser's idea of the current layout ever disagreed with C#'s, your click would simply appear to do nothing, instead of the mismatch showing up somewhere.

Nobody has seen the two disagree, and Devin points out that the old toggle behaved worse in exactly that situation: it would flip you to the layout you hadn't asked for. Recommending leaving it — the reply also doubles as the signal for "there's no saved custom layout yet, build one", so reshaping it means touching a protocol that currently works, for a problem we have no evidence of.

For a moment after a switch, the tick can still show the old layout

Right after a successful switch, the dropdown is redrawn from the page as it exists at that instant — which is still the old page, because Bloom is about to reload it. So for a fraction of a second the tick can sit beside the layout you just left. With the new guard in place, a click during that sliver would be read as "you're already on that one" and ignored.

To hit it you would have to change your mind and click again within a few hundred milliseconds, while the page is visibly reloading, and the only consequence is that the click does nothing — click once more and it works. The stale redraw itself predates this change; the guard just makes its effect "nothing happens" rather than something worse. Recommending leaving it for that reason.

The C# half of the fix has no automated test

The four new tests all exercise the browser side — that clicking the ticked option does nothing, and that the two real switches still ask for the right thing. The C# handler's own two safeguards have no test: doing nothing when the page is already in the requested layout, and refusing a layout name it doesn't recognise. Both were exercised by hand in a running Bloom during this work, and the whole existing C# suite passes, but a future regression in that handler would only be caught by someone trying it manually.

The obstacle is that EditingViewApi has no test fixture at all, and giving it one means standing up an editing view and a book model. Recommending leaving it: the front-end guard is what a user actually touches and it is covered, and the server check is a second line of defence behind it, so new test scaffolding for one controller is a poor trade right now.
