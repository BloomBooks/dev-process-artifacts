Simplifying the Freeze Doctor — options and what each costs

Prepared 2026-08-30, branch BL-16719-doctor-in-repo; revised 2026-08-31 at 51fc21523.

Status: option (E) has been implemented — reworked from "drop exit reporting" into "report on evidence, never on its absence" after John's clarification that Bloom already reports ordinary crashes. See that section for the measurement behind it. Everything else here is still analysis only.

So the worry is fair, and the number that should worry us most is not 19,645 — it is 29 files inside Bloom. The Doctor is a separate process; if it is wrong, a card is wrong. Bloom's own 2,784 lines run inside the application we are trying to protect.

Every one of your four candidates targets a real bug cluster. That is a good sign for the exercise. The largest single cluster — exit classification — is not in your list, and I have added it as (E).

1. Drop developer-build support

What goes. FreezeSimulator.cs (315, in Bloom) and its session field; IsDeveloperChannel and the channel-derivation rules; the debugger machinery (probe sampling, "poisoned by debugger" stickiness, DebuggerCouldExplainIt, three shared-page fields); MayFile / NeverFile / NotForFiling / ReportSavedWithoutFiling; the --force switch.

Size: roughly 1,200 lines, but the striking figure is the spread — the concept appears in 17 files.

Risk: the largest reduction of the four, and not because of the line count. This is a cross-cutting predicate every filing path has to consult, and that is exactly the shape of bug we hit: the "four reasons never to file" existed in one place after we discovered that two paths — the crash-dump path and the exit examination — had each grown a shorter version, so a deliberately simulated crash filed a real card. Cross-cutting predicates are re-derived and get re-derived wrongly.

Capability cost — the highest of the four, and it is not obvious. You lose the ability to exercise the thing before shipping it. The simulator is how the crash, freeze and zombie paths are provoked at all; the whole zombie sequence was validated end-to-end this week only because BLOOM_SIMULATE_FREEZE=zombie was set. Without it, the first real test of the crash path is a user's crash.

Mitigation that keeps most of the win: keep the simulator and the developer-channel filing guard (perhaps 200 lines, one predicate consulted in one place), drop the debugger machinery and the --force/NotForFiling plumbing. Debugger-awareness only exists because the Doctor watches developer machines; if it does not, a developer stopping a debugger is not our problem.

Verdict: do a version of this, but not the whole thing. Dropping the simulator would be trading the ability to find bugs for a smaller diff.

2. Reduce what Bloom sends to two kinds of information

Bloom currently publishes eighteen fields on the shared page and twenty on the session file. My two:

Keep (a): the UI-thread heartbeat. Non-negotiable. The measured finding this whole feature rests on is that a WinForms UI thread blocked in a managed wait still dispatches sent messages, so IsHungAppWindow and Process.Responding report a wedged Bloom as healthy — nine minutes frozen, reported responsive. A timer-driven heartbeat in shared memory is the only detector that works. Everything else is evidence; this is detection.

Keep (b): the session file's identity facts — log path, ports, channel, version. Small, written once, and the log path cannot be derived from outside: Bloom recreates Log.txt each run and falls back to a random name only when another Bloom holds it, so from outside the newest log is the wrong answer exactly in the restart-after-a-freeze case. BloomLogLocator is 222 lines of approximating something Bloom can state in one.

What goes: the API activity tracker (309 + 159 tests + 37 in BloomApiHandler), server thread counts (~150), the activity string and long-operation scopes (~200 across six call sites in Publish/Epub/RAB/video/upload/download), the crash-dump handshake (~270 across both sides), the shutdown-phase protocol (~100), BloomAlreadyReported (~80).

Size: ~1,300 lines out of Bloom, ~400 out of the Doctor, plus tests. It also removes six touchpoints in unrelated Bloom subsystems, which is where "small, safe change" quietly stopped being true.

Risk: high reduction, and concentrated in the right place — most of the Bloom-side bugs were in the activity tracker.

Capability cost, in order of pain:

  1. Long-operation suppression is load-bearing and I would fight for it. Without it, the freeze threshold is 60 seconds flat, and a legitimate two-minute BloomPUB build or video render looks exactly like a freeze. This does not merely lose information — it manufactures false cards, which is the failure mode most likely to make people stop trusting the tool. If you keep a third thing, keep this.
  2. Dropping the shutdown phase drops the clean-exit proof, which returns exit reporting to "only when something corroborates a crash". That is a real loss unless you take (E), in which case it costs nothing.
  3. Reports stop saying what Bloom was doing, which is most of a freeze card's diagnostic value. You would get "the UI thread's stack" and not "…while publishing to BloomPUB".

Verdict: strong, and the best value-per-line of the four — provided long operations survive.

3. Stop trying to send; keep reports on disk for a while

What goes. YouTrackSubmitter (671), most of ReportOutbox (1,043) — the cross-process drain gate, the daily cap, the fingerprint merge, the follow-on window, reclaiming abandoned uploads, retry and backoff — plus ReportOutboxTests (832). SupportUploadCredentials and the AccessKeys changes go with them.

Size: ~2,000 lines, the largest single removal available.

Risk: substantial. This is also the only part of the Doctor that talks to the network and handles credentials, so it removes a whole category of failure (and the outstanding BLOOMBOOKS_NUGET / signing-credential dependency along with it).

Capability cost — the largest of any option here, and I think it changes what the feature is. The stated goal is to improve our chances of collecting information about freezes. Automatic filing is the part that turns "we can investigate a freeze once a user thinks to tell us" into "we learn about freezes nobody reported". Freezes are exactly the failure users don't report — they kill Bloom and carry on. Keeping evidence on disk that someone must think to ask for restores the old dependency on the user reporting.

You would also lose deduplication: today twenty occurrences of one freeze become one card with a count, via a fingerprint of the UI thread's top frames. Without the outbox there is nowhere for that to live.

Middle path worth costing separately: keep filing, drop durability — try once, and if it fails leave the bundle on disk with no retry, no cap, no merge. That removes the gate, the retries and the reclaim logic (~700 lines) while keeping the "we hear about it" property. Reports from an offline machine are lost, but a machine that freezes is usually online again within the hour and the next freeze reports fine.

Verdict: the biggest line saving, and the one I would think hardest about, because it is the only option that changes the feature's purpose rather than its implementation.

4. Watch only one Bloom

What goes. The discovery sweep and its channel-name list; the watcher/probe dictionaries and everything keyed by process id; RestartBlockers (75); most of ProcessIdentity (51) — with a single process you hold a handle for its whole life, so reuse cannot arise; the single-instance-token field and its reasoning; a large part of DoctorSupervisor's 1,268 lines.

Size: roughly 600–700 lines, mostly concentrated in the largest and most stateful file.

Risk: better than the line count suggests, because it removes state, not just code. Four HashSet<int> fields tracking per-process bookkeeping (dumps requested, zombies reported, zombies ended, exits examined, plus who we asked to stop) all collapse to plain booleans when there is one target, and every one of those sets is a place a stale entry can silence or duplicate a report.

Capability cost: genuinely small, as you say. End users run one Bloom. The cases lost are the Ctrl-held second instance and an alpha tester running two channels — and in both, the Doctor still watches one of them.

One thing to keep: the Doctor is launched by Bloom and can simply be told which process id to watch, which is both simpler and more reliable than sweeping. The sweep exists for the "Doctor started later" case, which then degrades gracefully to "attach to whichever Bloom is running".

Verdict: the best risk-to-cost ratio of the four. I would take this one whatever else you decide.

Others worth considering

(E) Report an exit only on positive evidence — DONE, commit 51fc21523

This started as "report freezes only, dropping exits and crashes entirely". John's clarification replaced it with something better: Bloom normally reports its own crashes; what the Doctor needs to cover is the crash that exits Bloom with no indication of why — an exception thrown, and not caught, on a thread Bloom does not control.

That reframes the question. The problem was never that exit classification existed; it was that one of its two regimes reasoned from the absence of evidence. So the fix is not to delete the capability but to delete that regime.

What was wrong with reasoning from absence:

  • It is where the bugs were. Every defect found in ExitClassifier came from it: two of Devin's findings, the conflation of "how far shutdown got" with "who asked for it", and a startup crash read as a machine restart. Absence has many innocent causes and the code kept meeting another one.
  • It could not tell a crash from a Task Manager kill, and said so in the card's own text — "may be a user-initiated kill". A card that concedes it may be about nothing trains people to ignore the next one.
  • It was not needed for the case that justified it — which was measurable, and measured.

The measurement (this machine, 2026-08-31; a minimal .NET 8 program throwing on a thread-pool thread, which is John's scenario in miniature):

SignalPresent?Depends on
ProcessExit handler ranNo — so there is genuinely no clean-exit proof—
Process exit code0xE0434352 (ExitCodeUnhandledManagedException)the CLR alone

Application Error event 1000yesthe Windows fault handler

Four independent signals for the case we must not miss — and the first comes from the CLR, not from any Windows feature an administrator can switch off. WER on this machine is at its defaults (no Disabled/DontShowUI/LoggingDisabled policy keys) and demonstrably working: 526 report folders under C:\ProgramData\Microsoft\Windows\WER, including several AppCrash_Bloom.exe_*. So the narrow rule catches the case, and does not depend on the one signal a policy could remove.

What went: the ExitReportPolicy enum and both regimes, the branch that reported on missing proof, ExitVerdict.Unknown, and the supervisor's choice between regimes.

What stayed, and why the plan changed twice:

  • WindowsExitEvidenceCollector stays. Under this rule its Event Log and WER reading is the trigger rather than a corroboration, so it does more work than before, not less.
  • The stalled-shutdown log check stays, and checking this is what caught a mistake in my own plan. Bloom's 20-second safety net ends with Environment.Exit, so ProcessExit runs and records a shutdown phase — the session file describes a perfectly clean exit. Scraping Bloom's log for its own "forcing Bloom to close" line is the only thing that identifies that case, and dropping it would have silently lost a real bug class.

Honest accounting: this removed 33 lines of logic, not the ~1,000 I first estimated. That estimate was for deleting exit reporting outright; keeping the capability keeps the collector. The value here is not line count — it is that one decision axis and all the reasoning-from-absence are gone, from precisely the file that produced the most defects.

Verdict: done, and it is the pattern I would apply to the rest — separate evidence to gather from evidence to reason from, and never act on an absence. It targets the densest bug cluster and duplicates an existing capability.

(F) Detect and report zombies, but never end them

What goes. ZombieEnder's ending half (~150), the grace period, the work-in-progress check, the quit handshake, RestartBlockers (75), the single-instance-token protocol, and the "Restart Bloom" flow in StatusForm (~150) — around 600 lines with its tests.

Risk: this is the only destructive thing the Doctor does. Every guard around it — grace period, "never kill a frozen Bloom", identity checks, work-in-progress — exists because killing the wrong process, or the right one at the wrong moment, is unrecoverable. Removing the action removes the entire class.

Capability cost: the user must end a window-less Bloom themselves via Task Manager. They already have to notice it. Against that, this removes the only path by which the Doctor can destroy someone's work.

Verdict: high value, low cost. Pairs naturally with 4.

(G) Leave the shape alone; ship it off by default

Already true — it is a setting, off by default, toggled from the debug menu. Worth stating explicitly because it bounds the blast radius of everything above: no user gets this until someone turns it on. That is an argument for shipping a slightly larger thing that has been exercised, over a minimal thing that has not.

If you want a recommendation

(E) is done. Of what remains, take 4 + (F) + the trimmed version of 1 — roughly 1,800 lines, removing the multi-process bookkeeping that produced several bugs and the only irreversible action in the system, while leaving intact the thing the feature exists for: noticing that Bloom is frozen and getting evidence about it off the machine.

Then take 2, keeping long operations as a third — about another 1,300 lines out of Bloom, which is where the risk to users actually lives.

I would leave 3 alone unless the credential dependency is the blocker, because it is the only one that changes what the feature does rather than how much code does it. If it must go, take the middle path — file once, no retry — rather than dropping filing entirely.

Combined, that is on the order of half the diff, with the freeze-detection core, the evidence gatherer, and automatic filing untouched.

One caveat on all of it

Removal is not free of risk either. Every one of these areas is now covered by tests that were written because something went wrong there, and the code carries comments explaining decisions that were expensive to learn. Deleting a subsystem deletes that record too. Where a simplification is taken, the reasoning worth keeping should move into a comment on whatever remains, or into the ticket — otherwise the second attempt rediscovers the same problems.

Also worth noting while it is in view: BloomFreezeDoctor.Core.csproj refers to docs/SPIKE-FINDINGS.md, which does not exist in this repository — the measured findings behind the heartbeat design were left behind in the spike. If simplification 2 is on the table, that document is the evidence for keeping the heartbeat, and it should be recovered before it is lost.
