What this PR is about

Problem

Typing a book title with a line break in it — “Where Are”, Enter, “The Fish Going?” — produces the title “Where AreThe Fish Going?” on bloomlibrary.org. The break is silently swallowed and the two lines are jammed together with not even a space. Titles typed with Shift+Enter are fine. The same wrong title shows in the caption under the book’s thumbnail in the Book Making tab. This worked in 6.2 and broke in 6.3.

Cause

Plain Enter starts a new paragraph, so the title arrives as <p>a</p><p>b</p>. The one method that reduces title markup to plain text has only ever recognised the soft break that Shift+Enter inserts — never a paragraph boundary — and it finishes by asking the XML document for its text, which runs adjacent paragraphs straight together.

It came out as “Where Are The Fish Going?” before purely by accident: HTML Tidy always left whitespace between block elements when it wrote the book file out, and that stray whitespace stood in for the line break. The .NET 8 upgrade (BL-14973, c0f8a714e) replaced Tidy with HtmlAgilityPack, which doesn’t — which is exactly why this fails in 6.3, 6.4 and 6.5 but not 6.2.

What the PR does

  • A block boundary is now a line break, given the same replacement text the soft break already gets — a newline for the book’s stored information, or a space for the one-line thumbnail caption. Plain Enter and Shift+Enter finally behave the same, which is what BL-10630 set out to achieve in 5.2.
  • Headings count too, not just paragraphs, since 6.4 added heading support to text boxes (BL-16649).
  • Any leftover Tidy-era whitespace between the blocks is replaced rather than added to. Without that, a 6.2-era book would carry the file’s own indentation into its title — which is what it does today, giving Where Are             The Fish Going?. Now an old book and a new one report the same thing.
  • One supporting addition: the XML wrapper gains a PreviousSibling property, mirroring the NextSibling it already had.

Because every one of these goes through that single method, the fix covers the uploaded title, the per-language titles, the recorded “original title” on translations, and the collection-tab caption at once.

Worth knowing

  • Nothing has been exercised in the real app. The fix is covered by unit tests and by one end-to-end test through the save path, and both were confirmed to fail without it and reproduce the exact reported title. But no book has actually been typed, saved and uploaded by hand — the running Bloom in this worktree was stopped partway through the run to reinstall the front-end dependencies.
  • Existing books report a slightly different title once re-saved. Today a 6.2-era book already stores a newline in its title, followed by however many spaces the file happened to be indented by; the fix trims that to a clean newline. So it is a tidy-up rather than a reversal — but it is still the part most likely to surprise someone, and the QA notes flag it.
  • The one-line thumbnail caption can now show a double space if a title line happens to end in a space before the Enter. It is invisible wherever the caption is rendered as HTML, since browsers collapse runs of whitespace, and it never reaches a folder name. Left alone rather than adding a whitespace-collapsing pass.

Decisions — all settled

Nothing is waiting on anyone. Andrew answered the three scope questions this run raised; none of them changed the code.

  • Folder name and page title still run the lines together — leave as is. Long-standing behavior, the same for Shift+Enter, and no card opened for it. It is written into the QA notes on the card so a tester doesn’t file it as new.
  • Old books’ titles — keep normalizing, as built. Measured both ways first: today an old book already stores a newline in its title, just with twelve stray spaces of file indentation after it, so this cleans that up rather than changing behavior. A test now pins it.
  • Raw newline in the per-language titles list — leave as is. It predates this change and every reader Bloom has was checked and copes.
