What this PR is about

Problem

After #8305 put a line break between the paragraphs of a title, a tester found a case on 6.4 where the title still reaches the Publish tab and bloomlibrary.org as "OneTwo": type "One Two", put the cursor at the start of "Two", press Enter or Shift+Enter. Show Hidden Characters reveals a zero-width space at the start of the second line. 6.5 does not have the problem.

Cause

CKEditor places a zero-width "filling char" (U+200B) at the caret after a split so the caret stays navigable, and removes it later by holding a reference to that text node. About half a second after every keystroke, cleanUpNbsps assigned the box's innerHTML whether or not it had changed anything. That rebuilds every node, so CKEditor's reference points at a detached node and the character is never removed. It is saved with the title, and Chromium renders a newline adjacent to U+200B as nothing at all, so the line break becomes invisible. Master fixed the rewrite in BL-16558, which is why 6.5 is clean.

What the PR does

  • cleanUpNbsps assigns innerHTML only when it actually converted a non-breaking space (toolbox.ts:1638, :1690). Same code as master's BL-16558 change.
  • Three new tests check node identity, since the existing tests compare serialized HTML and cannot tell "left alone" from "rebuilt identically" (toolboxSpec.ts:132, :145, :160).
  • It does not clean books that already carry an orphaned zero-width space. The blanket strip master has (BL-16490) was judged too risky for 6.4 because Khmer, Thai and Myanmar text uses U+200B legitimately.

Worth knowing

  • The fix has not been exercised by hand in a running Bloom. The reasoning rests on code reading plus a browser check that Chromium drops a newline next to U+200B; the tester's exact keystroke sequence has not been replayed on this build. See the first question.
  • Show Hidden Characters itself rewrites the box's HTML, so it can orphan a filling char that is still present when it is toggled. The tester saw no character in 6.5 with the same Show Hidden Characters code, which is the evidence that the keystroke-pause rewrite was the route that mattered.
  • Books saved by earlier 6.4 builds keep any zero-width space they already have. The round-2 test ideas on the card say so, so the tester will not file it.

Verify in a running Bloom before review?

The change mirrors what master does and the tests pin the DOM behavior, but nobody has replayed the tester's sequence on this build. Should that happen before a human reviews the PR?

The tester's route to the bug has two rewrites in it that could orphan the character: the half-second tidy-up after a keystroke, which this PR fixes, and Show Hidden Characters, which this PR does not touch. The tester's 6.5 observation says the first one is the culprit, and the code agrees, but a replay on a 6.4 build with this change is the only direct proof.
