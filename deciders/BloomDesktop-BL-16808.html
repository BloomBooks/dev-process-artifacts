Enter in a book title should be a line break

What this PR is about

Problem

Typing a book title with a line break in it — “Where Are”, Enter, “The Fish Going?” — produces the title “Where AreThe Fish Going?” on bloomlibrary.org. The break is silently swallowed and the two lines are jammed together with not even a space. Titles typed with Shift+Enter are fine. The same wrong title shows in the caption under the book’s thumbnail in the Book Making tab. This worked in 6.2 and broke in 6.3.

Cause

Plain Enter starts a new paragraph, so the title arrives as <p>a</p><p>b</p>. The one method that reduces title markup to plain text has only ever recognised the soft break that Shift+Enter inserts — never a paragraph boundary — and it finishes by asking the XML document for its text, which runs adjacent paragraphs straight together.

It came out as “Where Are The Fish Going?” before purely by accident: HTML Tidy always left whitespace between block elements when it wrote the book file out, and that stray whitespace stood in for the line break. The .NET 8 upgrade (BL-14973, c0f8a714e) replaced Tidy with HtmlAgilityPack, which doesn’t — which is exactly why this fails in 6.3, 6.4 and 6.5 but not 6.2.

What the PR does

  • A block boundary is now a line break, given the same replacement text the soft break already gets — a newline for the book’s stored information, or a space for the one-line thumbnail caption. Plain Enter and Shift+Enter finally behave the same, which is what BL-10630 set out to achieve in 5.2.
  • Headings count too, not just paragraphs, since 6.4 added heading support to text boxes (BL-16649).
  • Any leftover Tidy-era whitespace between the blocks is replaced rather than added to, so a book written by 6.2 reports the same title as one written today instead of keeping the old single space.
  • One supporting addition: the XML wrapper gains a PreviousSibling property, mirroring the NextSibling it already had.

Because every one of these goes through that single method, the fix covers the uploaded title, the per-language titles, the recorded “original title” on translations, and the collection-tab caption at once.

Worth knowing

  • Nothing has been exercised in the real app. The fix is covered by unit tests and by one end-to-end test through the save path, and both were confirmed to fail without it and reproduce the exact reported title. But no book has actually been typed, saved and uploaded by hand — the running Bloom in this worktree was stopped partway through the run to reinstall the front-end dependencies.
  • Existing books change their stored title the next time they are saved — a 6.2-era book gets a newline where it used to have a space. That is deliberate (question 2 asks whether you agree), but it is the part most likely to surprise someone, and the QA notes flag it.
  • The one-line thumbnail caption can now show a double space if a title line happens to end in a space before the Enter. It is invisible wherever the caption is rendered as HTML, since browsers collapse runs of whitespace, and it never reaches a folder name. Left alone rather than adding a whitespace-collapsing pass.

1. The folder name and page title still run the lines together

A book whose title is typed with Enter still lands in a folder called Where AreThe Fish Going on disk, and the title stored in the book’s own web page is jammed together the same way. Those two come from a different piece of code, which turns the title into a single line by squashing every run of whitespace into one space — and since a paragraph boundary contributes no whitespace at all, there is nothing there to squash. This is not part of the regression: it has always behaved this way, for Shift+Enter as much as for Enter, so a 6.2 book has the same jammed-up folder name. I left it alone, but it is the part of the bug a user is most likely to notice next, since they see the folder.

2. Old books’ stored titles change shape when re-saved

Books written by Bloom 6.2 or earlier have stray whitespace sitting between the paragraphs of their title, left there by the old file writer. The fix throws that whitespace away and puts a real line break in its place, so the very same book reports “Where Are” / “The Fish Going?” on two lines where it used to report them on one with a space. I chose that so a book’s title doesn’t depend on which version of Bloom happened to write it — but it does mean a quiet change to books nobody meant to edit, visible after the next save as a re-upload or a Team Collection change.

3. The per-language titles list now usually contains a raw newline

Alongside the main title, a book records a small list of its titles in each language. That list is assembled by hand into a compact data format, and the assembling code escapes backslashes and quotes but not newlines — so a title with a line break in it puts a real newline inside a piece of text that is supposed to be one line. That was already true for Shift+Enter titles, and has been for years; this fix makes it the common case rather than the rare one. I checked every place Bloom reads that list back: two of them already work around it explicitly, and the other four use a parser that tolerates it (I confirmed that rather than assuming). So nothing is broken today — but it is fragile, and a stricter reader anywhere downstream would choke on it.
