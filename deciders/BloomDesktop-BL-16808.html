What this PR is about

Problem

Follow-up to #8305. A tester found that on 6.4 a title typed as "One Two" with Enter or Shift+Enter pressed at the start of "Two" still reaches the Publish tab and bloomlibrary.org as "OneTwo", even though #8305 now puts a line break between the two lines. Show Hidden Characters reveals a zero-width space at the start of the second line. 6.5 does not have the problem.

Cause

CKEditor plants a zero-width "filling char" (U+200B) at the caret whenever it re-selects a caret that sits next to an inline element, such as the line-break span Shift+Enter inserts, and removes it later by holding a reference to that text node. Bloom's half-second tidy-up after every keystroke took a CKEditor bookmark and restored it, which is such a re-select, and it also assigned the box's innerHTML whether or not anything had changed. Each rewrite detached the node CKEditor was tracking, so the character stayed as ordinary text, a fresh one was planted on the next pause, and the result was saved. Chromium renders a newline adjacent to U+200B as nothing at all, so the line break became invisible. Reproduced in a running 6.4 build over CDP; master fixed both halves in BL-16558 and BL-16717, which is why 6.5 is clean.

What the PR does

  • cleanUpNbsps assigns innerHTML only when it actually converted a non-breaking space (toolbox.ts:1714).
  • The tidy-up takes a CKEditor bookmark only when a tool is active or the box holds a comment or an nbsp, the only cases in which anything rewrites it (toolbox.ts:1528, editableMightBeRewritten). Ordinary typing never plants the character in the first place.
  • Five new tests check node identity and the gate (toolboxSpec.ts).
  • Not done: cleaning books that already carry a stray zero-width space, and stripping one that CKEditor plants on its own and Show Hidden Characters then orphans (see Worth knowing). Master strips those at save (BL-16490), judged too risky for 6.4 because Khmer, Thai and Myanmar text uses U+200B legitimately.

Worth knowing

  • One route to a saved stray character remains, found during verification: press Backspace right after a Shift+Enter line break, so the caret ends up next to the span. CKEditor itself then plants a tracked filling char. If Show Hidden Characters is held while it is there, that feature's own HTML rewrite orphans it and it is saved, folder name included. Without Show Hidden Characters it is removed normally at save. 6.5 has the same live behavior and cleans it at save. The round-2 test ideas describe it so the tester does not file it. See the first question.
  • With synthetic CDP input the Enter variant never produced the character even on the old code; only Shift+Enter did. The tester saw it with Enter using real input, so the Enter route was not directly reproduced here, but the mechanism and the fix are the same for both.
  • Books saved by earlier 6.4 builds keep any zero-width space they already have.
  • Your own launcher from 1:08 PM was still running its watcher in this worktree; my file edits made it rebuild and relaunch Bloom automatically. I stopped that auto-relaunched Bloom because it held my test collection open, and left your watcher running.

Close the Show Hidden Characters route too?

When CKEditor's own filling char is present and Show Hidden Characters is held, the feature's HTML rewrite orphans it and it gets saved. Should this PR also handle that?

It takes a specific sequence: a Backspace that leaves the caret right next to a line-break span, then Ctrl+Shift+Space held before anything else moves the caret. Show Hidden Characters is a debugging aid, and 6.5 behaves the same way live, cleaning up only at save. Leaving it is reasonable for a release branch; the option below is small if you would rather not ship any known route.
