What this PR is about

Problem

When a split pane is shorter than the text box it holds, the published book (especially the PDF) cuts off the bottom line of text, but the Edit tab showed the whole line. The only cue was the red overflow bar across text that looked complete, so authors had no reason to drag the splitter and published cut-off text.

Cause

Every split pane had overflow: hidden, which hides what does not fit but can still be scrolled. When a page loads, Bloom puts focus in the first text box, and the browser scrolls the pane (11px on the card's example page) to show the focused line. Publishing has no focus and no scroll, so it cuts the line.

What the PR does

  • Split panes now use overflow: clip, which clips the same way but cannot scroll, so the Edit tab cuts the line exactly where publishing does, next to the red bar (origami.less:14).
  • overflow: hidden stays as a fallback line for older readers (e.g. Android WebView before Chrome 90) that drop clip.
