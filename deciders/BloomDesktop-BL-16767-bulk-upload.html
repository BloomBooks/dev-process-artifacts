What this PR is about

Problem

Bulk upload (Bloom.exe upload <collection>) fails for every book after the first one or two. Each failed book reports "The instance of CoreWebView2 is uninitialized and unable to complete this operation. See EnsureCoreWebView2Async." Reported on 6.6.1001 Alpha; also reproduced on 6.5.3002.

Cause

The font check that runs while a book is staged for upload created a new hidden browser (an inline WebView2) on the calling thread for every book. In the bulk-upload console process, every inline WebView2 after the first fails to finish initialization. The 10-second navigation wait times out, and the next JavaScript call throws the reported exception. A test that imitates the console message pump reproduced this exactly: book 1 passed, books 2-5 failed with the reported error.

What the PR does

  • The font check is now synchronous PublishHelper.ReportInvalidFonts and drives an OffScreenBrowser: a WebView2 on its own dedicated thread with a real message loop. The ePUB and BloomPUB page checks already use the same mechanism.
  • BookUpload.SetUpStaging is synchronous as well, and the controlToInvokeOn thread juggling is gone from the upload path.
  • A new regression test, ReportInvalidFontsTests, runs the font check for five books in a row in one process, and requires that each run really finds the book's fonts. With the old code the check failed from book two onward; with the fix all five pass, and each check is also faster (about 350 ms against 712 ms).
