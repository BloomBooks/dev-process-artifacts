Decision: inside-back-cover custom layout — finish, split out, or leave?

The branch carried an uncommitted change (now commit 95f21257) adding data-custom-layout-id='customInsideBackCover' to the standard inside back cover and its device twin, End Extra 2 (pug line 278, line 313). That attribute is what lets a cover page keep a customized layout across xmatter updates, and it works on its own. Devin's open flag points out two things: the existing outside-back-cover twin also has a branding CSS rule (branding-base.less line 133, which un-hides the text boxes on a customized cover when a branding would normally hide them), and there is no equivalent rule for the new inside-back-cover id — so if a branding hides inside-back-cover text, a user's customization there would stay invisible. It also notes the change is unrelated to this PR's stated scope (auto-fit + image shrink), so it may not belong in this PR at all. Only you know the intent of this change.

Leave comment
Recommended only because the attribute already works for its core job (preserving the custom layout across updates) and you know whether the branding-CSS half is even wanted — pick a fix option if it is.
