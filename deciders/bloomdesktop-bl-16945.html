What this PR is about

Problem

With Windows set to a Thai regional format, every entry in the UI language menu reads "Invariant Language". Other effects: translations generated for the Simple Comprehension Quiz heading get an empty lang attribute written into the book, and a new collection saves its default second language (English) under the name "Invariant Language (Invariant Country)".

Cause

libpalaso's IetfLanguageTag.GetGeneralCode finds the end of the language subtag with a culture-sensitive IndexOf("-"). Under th-TH on .NET 8, that ignores the hyphen and returns 0, even for tags like fr that have no hyphen. The general code comes out empty, CultureInfo.GetCultureInfo("") returns the invariant culture, and its name gets cached. Every libpalaso language-name lookup that Bloom uses goes through it. It's the same class of bug as BL-16932, but in libpalaso, which upstream still has.

What the PR does

  • New ToPalaso/IetfLanguageTagExtra runs those libpalaso lookups with an invariant CurrentCulture. CurrentUICulture is left alone, so names are still localized as before.
  • Every Bloom call site uses it: the UI language menu, collection and writing-system names, the license message, the book language descriptors, and the generated-translation lang.
  • When a collection loads, a saved name that is exactly the invariant culture's is looked up again. That repairs collections created under a Thai format before this fix, and custom names are unaffected.
  • th-TH unit tests for each of these, all confirmed to fail without the fix. libpalaso itself is left for later, as you asked.

Worth knowing

  • Master and 6.5 use libpalaso versions that still have the bug, so this workaround carries forward on the normal merges. It can come out once libpalaso's GetGeneralCode uses an ordinal search.
  • In the real-Bloom run under th-TH, a dev build crashed at startup on a Debug.Fail in BookThumbNailer after TagLib failed to read a thumbnail's metadata. That's BL-16926's bug, not this one; a release build logs it and carries on.

Git hooks are off for every worktree

The shared repo config at C:\dev\BloomDesktop\.git\config sets core.hooksPath twice: first to .githooks (the branch-aware pre-commit dispatcher), then to nul. Git uses the last value, so no pre-commit hook runs in any BloomDesktop worktree on this machine. Prettier, csharpier and the C# robustness checks are silently skipped on every commit. I didn't touch the setting. For this PR's commits I passed -c core.hooksPath=.githooks, so the hook did run. I don't know who added nul or why.
