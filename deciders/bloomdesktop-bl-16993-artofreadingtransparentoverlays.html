What this PR is about

Problem

An Art of Reading picture (or any black-and-white line art) placed as an image overlay on top of a canvas's background picture is not made transparent when the page is white. Its white rectangle covers the picture beneath it. The same image in an ordinary picture box on a coloured page is transparent, so the "Auto" transparency setting looks broken for overlays.

Cause

Since 6.5 (BL-16336), "Auto" transparency is requested only when the page has a non-white background colour. Nothing treats an image layered over a background picture as needing transparency, so on a white page an overlay is served as the original opaque file. The image itself is fine: Art of Reading files pass the line-art detection.

What the PR does

  • Overlays on a background picture get Auto transparency on white pages. Under Auto, an image in a canvas overlay is treated as needing transparency when its canvas has a real background picture. With only the placeholder, or no background, the overlay stays opaque as before. Older canvases that hold the background picture directly count too; the cover's branding logo and QR code do not. This applies in the edit view, thumbnails, PDF, BloomPUB and ePUB. The line-art check still decides, the Opaque / Transparent choices still win, and coloured pages are unchanged. See bloomImages.ts:547 and HtmlDom.cs:2086.
  • Changes to the background keep it right. Choosing, pasting, undoing or deleting the background picture recomputes every overlay on that canvas straight away (bloomImages.ts:674), as do "Become Background" (canvasControlRegistry.ts:780) and Duplicate.
  • PDF without background colours. These PDFs now honour overlay transparency too. That setting already removes page-colour transparency earlier in the pipeline, so the server's extra check only blocked overlays (BloomServer.cs:1024).
  • Analytics. The "Image Transparency Set" event records whether the image is an overlay on a background picture.
