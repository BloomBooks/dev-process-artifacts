What this PR is about

Problem

An Art of Reading picture (or any black-and-white line art) placed as an image overlay on top of a canvas's background picture is not made transparent when the page is white. Its white rectangle covers the picture beneath it. The same image in an ordinary picture box on a coloured page is transparent, so the "Auto" transparency setting looks broken for overlays.

Cause

Since 6.5 (BL-16336), "Auto" transparency is requested only when the page has a non-white background colour. Nothing treats an image layered over a background picture as needing transparency, so on a white page an overlay is served as the original opaque file. The image itself is fine: Art of Reading files pass the line-art detection.

What the PR does

  • Overlays on a background picture get Auto transparency on white pages. Under Auto, an image in a canvas overlay is treated as needing transparency when its canvas has a real background picture. With only the placeholder, or no background, the overlay stays opaque as before. The cover's branding logo and QR code are not treated as overlays. This applies in the edit view, thumbnails, PDF, BloomPUB and ePUB. The line-art check still decides, the Opaque / Transparent choices still win, and coloured pages are unchanged.
  • One rule per language. The editor decides in bloomImages.ts:529, which only reads the background canvas element, since every page being edited has one. Every C# path, BloomPUB included, now goes through HtmlDom.GetImageTransparencyMode. That one also recognises the older form, where the background picture sits directly in the canvas (HtmlDom.cs:2117).
  • Changes to the background keep it right. Choosing, pasting, undoing or deleting the background picture recomputes every overlay on that canvas straight away, as do "Become Background" and Duplicate.
  • PDF without background colours. These PDFs now honour overlay transparency too. That setting already removes page-colour transparency earlier in the pipeline, so the server's extra check only blocked overlays.
  • Analytics. The "Image Transparency Set" event records whether the image is an overlay on a background picture.

Decisions

How should we answer John's HtmlDom.cs comment, given the legacy branch is still needed in C#?

John commented on the part of HtmlDom.BloomCanvasHasRealBackgroundImage that handles a canvas with no background canvas element, where the picture is an img directly in the bloom-canvas or a background-image style on it:

Again, I don't think we need to handle bloom-canvas elements that don't have background images.

His reasoning (from the matching TS comment) is that books being edited are always fully migrated. That holds for the editor's JavaScript, so the TS branch is gone. The C# code also runs outside editing, though, and there it sees the older form all the time:

  • Publishing converts back. SimplifyBackgroundImages turns every background canvas element back into a plain img in the bloom-canvas for ePUB and BloomPUB. BloomPUB then moves that picture into a style on the bloom-canvas. For those formats this branch is the main path. Without it, overlays would lose their transparency in ePUB and BloomPUB again, which is the bug this PR fixes.
  • The migration doesn't create the element. MigrateToLevel7BloomCanvas only renames bloom-imageContainer to bloom-canvas. The background canvas element is added by JavaScript when a page opens in Edit (or by the page layout update before publishing). So the server's first render of a page not yet opened, and its thumbnail, still see the old form.

That thread is still open with no reply from us. Preflight never replies on its own when it disagrees with a person.
