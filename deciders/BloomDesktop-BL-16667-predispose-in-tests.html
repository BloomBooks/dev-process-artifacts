What this approach is

A response body can still be going out after the worker that produced it has finished, and the framework completes that send on a callback whose only handler catches Win32Exception. Closing the HttpListener underneath it throws something else, on a thread nothing of ours covers, and the process dies.

Production meets that only when Bloom quits. The tests meet it 55 times a run — measured by counting binds in EnsureListening — which is why the tests are where it hurt. So this branch changes when the tests close a listener, and nothing about how anything is sent.

  • BloomServer.PreDispose() — everything Dispose did except closing the listener. Dispose is now PreDispose + CloseListener, same order, same effects.
  • RetiredTestServers.Retire() — used by the 12 fixtures that make a server listen. The listener closes a few fixtures later, once what it was serving has certainly finished.

A mitigation, not a proof: it does not make closing a listener safe, it waits until there is nothing to be unsafe about. The abort reporting also in this PR is how CI will tell us whether that is enough.

The two catches worth knowing about

The guard tests were the problem. The tests written to protect this scheme called CloseAllNow() mid-run, which drains the shared queue — so they closed listeners other fixtures had retired moments earlier, and their own servers had just served a real response through EnsureListening. They were the one place in the suite reliably doing the dangerous thing. They now drive their own queue and retire servers that never listened.

Ports are machine-wide. Retiring raised a run's footprint from about one port to about six, and you run suites in several worktrees at once. Three concurrent runs would have held eighteen of EnsureListening's twenty candidates, and the fourth would not have failed a test — it would have called ProgramExit.Exit() with nothing naming ports. The cap is now 3, and a test holds us to the multi-run arithmetic rather than the single-process version.

The production crash this one does not fix

Option D stops the test runs dying, but Bloom can still die as it quits — and because the crash lands inside the using that owns the application container, the finally after it never runs, including the Sentry flush. So the bug is positioned to suppress its own report, and "we do not see it in Sentry" is weak evidence either way.
