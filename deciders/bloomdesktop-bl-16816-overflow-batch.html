What this PR is about

Problem

A page with many text boxes stays busy for many seconds after it becomes editable. The Alphabet Book page (a 9 × 6 table, 28 text cells in a one-language collection) became editable about 2 s after the jump, then kept the main thread busy until 11–22 s. A click in that time was handled late, once by 8.4 s, which also made the e2e table helpers look as though a first click had been swallowed (BL-16815).

Cause

One second after the page loads, AdjustSizeOrMarkOverflowSoon starts a timer for every text box. Each timer ran the page-wide check, CheckPageAncestorOverflow, which measures every box in the margin box, and each measurement forces a layout. A page of n boxes forced about n × n layouts: about 800 on the Alphabet Book page, 7.7 s of CPU.

What the PR does

  • When a box's timer fires, it checks only that box, as before.
  • The page-wide check runs once for all the boxes whose timers fire together, on a zero-delay timer after all of them (CheckPageAncestorOverflowSoon). If the box that asked last has been deleted by then, the check uses another box in the same margin box.
  • Typing and pasting still run the full check right away.
  • The e2e table helpers clickCell and focusCellTextBox press a cell once instead of up to three times (BL-16815), so a cell that needs a second click fails a test instead of being hidden. A cell of a table inside a cell still gets a double-click first, as a person gives it.
  • Three browser tests cover when and how often the page-wide check runs.

On the production bundle, Bloom's JavaScript after the jump to the Alphabet Book page went from 9.0 s to 1.75 s, and the page is idle by about 4 s instead of about 11 s. A plain page is unchanged.
