What this PR is about

Problem

While zooming the edit page with Ctrl+mousewheel, Bloom goes "Not Responding" for several minutes, with the UI thread busy on one core, and then recovers on its own.

Cause

Every wheel notch posted its own zoom request. Each request runs on the UI thread and calls into the WebView2, while the browser process sends each Ctrl key event to the host synchronously and waits for the answer. A fast spin therefore left the UI thread waiting inside WebView2's accelerator-key handshake. The native stack captured on the card shows the UI thread blocked in CoWaitForMultipleHandles under Controller::HandleAcceleratorKeyEvent, with no Bloom frames on it.

What the PR does

  • The browser now counts wheel notches and sends at most one zoom request every 150 ms. The first notch still goes out at once, so the zoom stays responsive (bloomEditing.ts:1256).
  • The two endpoints zoomPlus and zoomMinus become one endpoint, zoomBy, which carries the accumulated notch count. A fast spin therefore makes one large zoom change instead of many small ones, and no notch is lost (PageControlsApi.cs:98).
  • Deleted the comment that said zooming re-loads the page, which stopped being true in July 2025, and the old comment that said wheel zoom feels sluggish, which this change answers.

The zoom was also driven by hand in a running Bloom: a burst of twelve notches produced two requests instead of twelve, and the zoom still landed on the value the notches asked for.

Worth knowing

  • The throttle makes the freeze far less likely; it does not make it impossible. One zoom request per 150 ms still calls into the WebView2 from the UI thread. The card names two hardening jobs filed separately for that: the per-notch settings save, and re-entrant script injection from inside a WebView2 event.
  • Another session is working the related card about saving the zoom setting on every notch, in its own worktree. If both land, the per-notch disk write goes away as well.
  • The freeze itself was never reproduced on demand; it was captured once with a debugger. So the evidence that this fixes it is the request count, which drops from one per notch to at most one per 150 ms, and not a before-and-after freeze.

Is 150 ms the right gap between zoom requests?

The browser now waits 150 ms after each zoom request before it sends the next one, and the notches that arrive in the meantime are added up and sent together. A larger gap means fewer calls into the WebView2, so less risk of the freeze, but the zoom then moves in bigger visible steps. A smaller gap makes the zoom smoother and brings back some of the risk. 150 ms is about seven zoom changes per second, which looked smooth when I drove it by hand.

Replacing the two zoom endpoints with one

Before this change the browser called edit/pageControls/zoomPlus or edit/pageControls/zoomMinus, and each of them moved the zoom by ten percentage points. Those two are now one call, edit/pageControls/zoomBy?notches=N, so the accumulated notches can travel in a single request. Nothing else in the repository used the old two, and both ends of this API live in this repository, so no other caller can break. It is still a change to an internal interface, which is why it is here and not decided silently.

One more comment in that file is now wrong
