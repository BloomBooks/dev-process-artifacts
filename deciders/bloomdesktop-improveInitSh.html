Review cycles

Preflight's own guidance caps the fix-and-re-review loop at four rounds; this run took six. Rounds 4 and 5 each found a real bug — one of them a good archive being deleted on every single run — so stopping at the cap would have left known defects in. Round 6 found no new bugs, which is where it converged. Every reviewer above is terminal for the final commit; nothing is still pending.

What review caught, and why it mattered

The version I first pushed had a hole big enough to defeat its own purpose. Worth reading if you only read one part of this:

A poisoned file could make itself permanent

The file already at the destination was used as the "only send it if newer than this" baseline without anyone looking at it. An error page left there by the old script therefore had a recent timestamp, the server replied "not modified", no failure was recorded, and the bad file survived every future run — while the summary counted it as a dependency that was present. Now a file only serves as that baseline if it is non-empty, does not look like an error page, and is recorded as having come from the exact URL being requested.

Borrowing could import another branch's binaries

My first gate decided whether a sibling worktree's copy was safe by grepping that worktree's script for the same download line — which says what the sibling would download today, not where the file on its disk came from. A worktree that fetched its dependencies on Version6.4 (which points several of them at a different build) and has since switched branches passed that test while holding the wrong binaries. The gate is now the sibling's own record of where each file came from. That also fixed a bug older than this branch: after switching a worktree between branches, artifacts whose URL changed used to be confirmed as "not modified" for ever instead of re-fetched.

A good archive was deleted on every run

The archive test treated any non-zero unzip -t status as "corrupt" and deleted the file — but 1 only means "fine, with warnings", and 127 means unzip is not installed. Either way a good download was destroyed, reported as corrupt, re-fetched and destroyed again: a loop that never ends and never unpacks anything. My first fix then over-corrected and kept archives that unzip reports as 9, which is what a truncated download or an HTML page saved as .zip actually reports here — so the archives most needing a re-fetch were the ones being kept. Both are fixed, and tested against real garbage, a truncated archive, an HTML page, and a fake unzip reporting disk-full.

And the wget fallback had none of the protection

wget does not save the body of a 404 or 500 — but the case this whole change exists for is an HTML page served with a 200, and wget -N wrote that straight over the good file. That path now uses the same temp-file-and-check sequence as curl.

Both open review threads were closed on the PR with these decisions recorded. No code changed as a result.

1. Should an unreachable build server fail init.sh even when every dependency is already present?

When build.palaso.org cannot be reached, the script stops with a non-zero exit even where nothing is actually missing. It says so explicitly — "all N dependencies are present on disk even so… what failed was checking them against the server" — but it still fails, so init.sh skips the front-end build. You already made this call deliberately: not knowing whether the dependencies are current counts as a failure. Devin then pointed out a consequence that had not been weighed: nightly.yml runs this script under the runner's set -e, so a build-server outage turns the nightly red, and a developer re-running ./init.sh offline in an already-set-up worktree now gets a hard stop where it used to finish. (In a fresh CI clone an outage means everything really is missing, so that job fails either way.)

Open thread: discussion_r3716645706

2. Is the stalled-transfer cutoff too tight for the slowest links the team works from?

To stop a server that accepts a connection and then hangs from stalling init.sh for ever, curl is now told to give up on a transfer averaging under 1 KB/s for two solid minutes (--speed-limit 1024 --speed-time 120). Before this change there was no timeout of any kind, so a hang was forever. Devin's concern: some of this team works from places where 1 KB/s sustained is a real rate, and the ghostscript and ffmpeg archives are tens of megabytes. Such a developer would now get a hard init failure indistinguishable from a genuine outage. I have no way to judge the slowest connection actually in use, which is why this is yours.

Open thread: discussion_r3716952374

3. One C# test fails on a stale output/browser. Rebuild it, or accept the diagnosis?

The C# suite is 3021 passed / 1 failed. The failure is XMatterHelperTests.InsideBackCover_PaperAndDeviceXMatter_ShareOneCustomLayoutId, which arrived from master during this run's merge (BL-16648). It asserts that the paper and device inside-back-cover pages share the id customInsideBackCover, and it reads the built xmatter through BloomFileLocator.GetFactoryXMatterDirectory() — that is, output/browser. Master's commit 5e2c90bda1 added that attribute to src/content/templates/xMatter/bloom-xmatter-mixins.pug on 3 August; this worktree's output/browser was built on 27 July, so the built HTML predates the attribute and the test cannot find it. The string exists in the pug source and in no built file anywhere under output/. Nothing in this PR touches C#, pug or output/browser; the fix is a front-end build, which AGENTS.md tells agents not to run because it wipes and repopulates the shared output/browser.

4. The first run after this lands re-downloads everything once. Fine?

Trusting a file now means being able to tie it to the URL it came from, and for files already on disk there is no such record — we genuinely cannot tell whether a given Bloom.chm came from the 6.5 help build or the 6.4 one. So the first run in each worktree fetches all sixteen artifacts, about 20 MB, and writes the record; every run after that is back to "not modified" and downloads nothing. Measured here: 11.5s for the first run, 8.6s for the second with zero downloads. The record lives in Downloads/dependency-sources.txt, which is gitignored. Related consequence: borrowing from a sibling stays inert until that sibling has run the new script once, since only then does it have records to vouch for its files.

For your information

The papercut is fixed, and two older bugs went with it. An error page can no longer replace a dependency, a failed setup step can no longer pass unnoticed, and the summary tells you whether you can still build. Beyond the papercut: a corrupt archive is now re-fetched instead of silently half-extracting, and a worktree switched between branches no longer keeps the other branch's artifacts for ever.
Borrowed files that were never confirmed re-download in full until the server answers. A borrowed copy gets no provenance record until the server confirms it — deliberately, so an unverified copy cannot masquerade as one we checked. The price: if you borrow while the server is flaky, those artifacts are fetched in full on each later run until one succeeds. Assessed and left alone, since the alternative is trusting a file on a sibling's word indefinitely.
Two cosmetic leftovers, assessed and left. In the wget fallback, -L is wget's --relative, not curl's "follow redirects" — inert here and inherited from the generated original. And an interrupted run can leave a dependency-sources.txt.new in the gitignored Downloads/, which the next run overwrites.
Two notes for the papercut list. The wedged chrome-devtools daemon, and the fact that Devin's API answers plain curl — the devin-review skill has a hard dependency on a browser it does not need. Say the word and they get logged, or written up as a skill change.
