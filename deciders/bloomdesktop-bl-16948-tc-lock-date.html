What this PR is about

Problem

Two regional formats with non-Gregorian calendars break the Team Collection status panel.

  • Thai. When someone whose Windows regional format is Thai checks out a book, every member of the collection sees its "checked out" date 543 years in the future. Locking and syncing are unaffected.
  • Saudi (ar-SA). On a computer set to the Saudi format, the status request fails for every book, checked out or not, so the panel shows no status at all.

Cause

The lock time went into the book's shared status file formatted with the current culture, and was read back the same way. Thai uses the Buddhist calendar, so the file got 2569-… instead of 2026-…. Saudi uses the Um al-Qura calendar, which covers only 1900–2077: it can't read 2026 as a Hijri year, and it throws when formatting DateTime.MaxValue, the value an unlocked book's status carries.

What the PR does

  • The lock time is now written and read with the invariant culture, so it means the same thing on every member's computer. A test locks under one culture and reads under another, both ways, for Thai and Saudi.
  • The status panel's date is now left empty when there is nothing the current calendar can show: an unlocked book, or an old lock time outside Um al-Qura's range (a Thai year like 2569, or a Hijri year like 1448 written by a Saudi computer before this fix). New tests cover both under ar-SA.
  • A lock time already written by a Thai computer stays wrong until that book is checked in, which clears it.
  • Test-only: 11 NUnit substring asserts now compare ordinally, and SubscriptionTests formats its expected date invariantly. th-TH and ar-SA join the weekly culture sweep's defaults, which a manual run also starts from.
