What this PR is about

Problem

When a book is made from someone else's book, Bloom writes a sentence on the credits page naming the original book's copyright holder and licence, and regenerates it every time the page is drawn. Publishers who need different wording — a different attribution formula, an added phrase, a translated form — have had no way to change it.

What the PR does

  • The hint bubble over that sentence now carries a padlock. Clicking it turns the sentence into an ordinary editable field, seeded with the wording Bloom had generated, with the caret already in it.
  • Permission lasts for exactly one rendering of the page. Leaving the page, redrawing it, or clicking the open padlock puts the sentence back to text the user cannot type in, keeping their words.
  • Once the user has typed, Bloom stops generating the sentence for that book: the wording is stored in the data div under originalCopyrightAndLicense and a meta.json flag records that Bloom is no longer the author of it.
  • Everything else about being a derivative is untouched — originalCopyright, originalLicenseUrl and originalLicenseNotes keep their values, so the Copyright dialog, the Publish tab and upload behave exactly as before.
  • Turning on "use the original copyright" hides the sentence altogether, the user's wording included, because the book's own copyright then says the same thing. Turning it off brings their wording back.
  • The editable shape exists only in the throwaway page DOM the editor builds per view; it is locked again at save time, on epub export, and whenever the page is rebuilt.

Worth knowing

  • None of this has been exercised by hand in a running Bloom. The padlock, the caret placement and the re-lock are covered by unit tests against the DOM, not by a pass through the editor with a real derivative book.
  • The behaviour hangs on the editable shape never being written anywhere but the per-view page DOM. Three places put it back: the save path in Book.cs, the epub exporter, and every rebuild of the page. A reviewer worried about the field leaking into a saved book should read those three call sites together.
  • The wording moves from data-derived to data-book once the user owns it, which is how their text gets harvested back into the data div. That switch is the load-bearing part of the design, in MakeOriginalCopyrightNoticeEditable.

Decisions

An emptied notice cannot be reopened

Suppose a user clicks the padlock, selects the whole sentence, deletes it, and leaves the page. Bloom now believes the user owns that sentence, and the user's version is empty, so nothing is drawn on the credits page at all. With no text there is no hint bubble, so there is no padlock to click, and Bloom will not generate the sentence again because it has been told not to. For that book the sentence is gone for good.

Whether this matters depends on how you read the gesture. Deleting everything is a reasonable way to say "I don't want this line", and undoing it is possible up until the page is left. Against that, there is no warning and no route back, and a user who deletes it while experimenting has no way to discover that the padlock is what they lost.

Recommended because deleting the line is a deliberate act with a visible result, the case is written into the test ideas so a tester will not file it as a bug, and the alternatives each trade one surprise for another.
