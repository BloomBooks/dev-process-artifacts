Notes from this round

Closing the startup gap produced three further bugs, and Devin found all three. That is the most useful thing to know about this round, and it is why the extra review cycles earned their cost.

A permanent lock-out. Making the gate consult the repository meant "whichever demands more" now applied to a member who could never refresh their own copy — because being refused is exactly what stops the sync that would refresh it. An administrator who typed a version by mistake would have shut the whole team out on every launch, for ever, fixable only by hand-editing a file on each machine. The repository now decides outright when we can read it, so it can lift a requirement and not only impose one. The reasoning Devin demolished was mine, in a comment asserting the opposite.

A startup stall. Reading the shared folder happens at the one moment with no window at all — splash hidden, nothing on screen — so a dead network share would have looked exactly like Bloom crashing. Now bounded to five seconds on a background task, with a timeout meaning "we don't know". Devin's suggested short-circuit does not work in either direction, and the thread records why so nobody retries it.

An erasure, by the code written to prevent erasure. After pushing the administrator's requirement to the shared folder, Bloom read it back out of the zip it had just written and treated a failed read as "nothing to record" — so a Dropbox mid-sync would leave memory empty and the next ordinary save would delete the requirement for the whole team. It now reads the local file, which is what was just pushed. Devin's own closing line was the answer: the value was already in our hands and we went back to the network for it.

The pattern worth carrying to human review: three of Devin's last four findings were bugs in fixes made minutes earlier in the same session. Each fix was right about the problem it targeted and wrong about something adjacent. A green gate after a fix is weak evidence; a person reading the final diff is not.

1. The download freezes Bloom, and the wait cursor cannot help

Your item 5, investigated as asked. Devin has since promoted it from a flag to a bug — thread open.

You asked whether we get a wait cursor, and whether that would be good enough. We do not, and it would not. There are two independent reasons, and the second settles it.

The first is the one Devin raised: Application.UseWaitCursor marks the open forms, but the cursor only changes when a window processes WM_SETCURSOR. We set the flag and immediately stop pumping messages, so nothing is processed until the download is over and we have set it back.

The second is worse: Application.UseWaitCursor acts on Application.OpenForms, and at the startup gate there are none. No Shell yet, and the splash is only hidden, not closed. So even with a pumping loop there would be nothing to show a wait cursor on.

I could not prove this by observation — a developer build refuses to update, so the call returns instantly and there is no window to look at. That part is analysis, and it is the part a real download would confirm.

What we already have: BrowserProgressDialog.DoWorkWithProgressDialog is built for exactly this shape — work on a background worker, dialog owning the UI thread so the window keeps painting. TeamCollection.cs:2919 is a working example, and the server is already listening by the time we need it. Velopack's DownloadUpdatesAsync takes a progress callback, so real percentages are available rather than a spinner.

2. Is "whoever can write the shared folder controls the flag" the intended trust model?

New, from Devin, on the latest commit — thread left open. A design question rather than a defect.

Because the repository now decides for a Team Collection — which is what lets an administrator undo a mistake — anyone who can write to the shared folder can also lift the protection instantly for every member, and a repository copy that is momentarily complete-but-old wins over the local file.

My reading, for what it is worth: this is not really a new power. The shared folder is where the administrator sets the requirement in the first place, and anyone who can write there can already change collection settings, add and remove books, and alter checkout state. The flag guards against an old Bloom mangling files, not against a hostile teammate.

But the question is pointed at what comes next, and there it deserves a real answer. This is preparation for Cloud syncing, and a cloud service is a different setting: there the requirement would presumably be something the service asserts, not a line in a file every member can rewrite. If the flag ever needs to be tamper-resistant rather than advisory, this is the decision to revisit — the same reasoning that leaves the command-line paths ungated.

3. Startup jobs keep running while Bloom quits for the upgrade

Your item 12, investigated as asked — thread open.

StartupScreenManager hands out one queued startup action per idle event and only unsubscribes when the queue empties. Nothing in it knows Bloom has been asked to quit, and Application.Exit() is not instant — the Shell cancels its own first close while it saves — so the registration check can put up a dialog while Bloom is trying to shut down for the install.

Option 1, recommended. ProgramExit already knows: it sets its force-shutdown thread the moment Exit() is called. Expose IsExiting and add one early return at the top of DoStartupAction. About five lines, in the place that already owns the fact, and it covers every future path that quits during startup rather than just ours.

Option 2. A StopRunningStartupActions() on StartupScreenManager, called from our code just before quitting. Around ten lines, blast radius exactly our feature — but it becomes a second mechanism for "we are quitting", and the next path that needs it has to remember to call it.

Option 3. Leave it. Nobody has seen it happen; it is reasoning from the code, and the window is a second or two.

Worth knowing either way: this cannot be verified here, because the upgrade path that triggers it has never run on a build that can actually update itself.

4. Two smaller things Devin left open

The follow-up messages may be owned by the hidden splash. "Bloom 6.6 has been downloaded…" goes through BloomMessageBox.ShowInfo, which picks an owner via Shell.GetShellOrOtherOpenForm(). At startup there is no Shell, and we only hide the splash, so the hidden splash can end up owning them. Whether they appear, and where, needs the live upgrade run to answer.

The lock-out assumes the topmost form is the Shell. Shell.GetShellOrOtherOpenForm() as Shell yields null if it is not, and the null branch behaves differently. In practice the Shell is open whenever Team Collection monitoring runs. Half of Devin's original scenario went away when cancelling started quitting Bloom; the remaining half is that picking a collection with no Shell would open one while a project context is still alive.

Both are cheap to fix and neither is worth doing blind — they want the same live upgrade run as item 1.
