1. Are these eight strings right, and should they stay untranslatable for now?

You asked to review all the new UI strings. The table on the left has every one.

All eight new strings that go through the localization system are in Bloom.xlf marked translate="no". That was AGENTS.md's default for new entries, not a considered judgment about these particular strings — so it is worth your decision rather than mine.

What hangs on it: a string marked translate="no" is never sent to translators, so every user in every language sees the English. For most new strings that is right, because the wording is still settling and re-translating churn is expensive. But these are the words someone meets when Bloom refuses to open their collection — arguably the worst moment to be reading a language you don't have. The counter-argument is that the audience is narrow (only collections that carry the flag, which today means only ones an administrator hand-edited) and the wording has never been tested on a real user.

Marking them translatable later is cheap and safe. Changing their wording later is only cheap while they are still translate="no" — after that it needs a new id and an obsolete note on the old one.

2. Six failure messages are still hard-coded English

When the upgrade can't happen, we tell the user why in a message box. Four of those explanations are plain English literals in the code with no localization id at all, and two more are developer-only.

They were written that way in the existing update code, where the same words appear in a toast — with an explicit comment that it wasn't thought worth localizing. This branch reuses those exact words, deliberately, so a user gets the same explanation whichever route they came by. What is new is the setting: they now appear in a modal box that a user meets while being told they cannot open their collection, rather than in a toast they may not read.

The two developer-only ones (debugger, developer build) plainly need no translation. "Bloom can only update itself on Windows." is newly written by me and Linux-only. The three connection/download failures are the ones a real user can actually hit.

Other:

3. Collection. is a brand-new id prefix

The seven dialog strings use ids beginning Collection. — a group that does not exist anywhere in Bloom today. The nearest existing groups are CollectionTab. (64 entries, and where all the other update messages live: UpToDate, UpdateFailed, AdminManagesUpdates) and CollectionSettingsDialog. (73 entries).

The prefix is what groups strings for translators, so it is a small piece of information design: it tells a translator what part of Bloom they are looking at. Collection. is honest — this dialog is about a collection and appears before any tab exists — but it creates a one-off group of seven, and "Collection" against a neighbour called "CollectionTab" is the kind of pair that is easy to confuse later.

Renaming is free right now precisely because the entries are translate="no"; AGENTS.md allows changing a new entry's id, and forbids it once translated.

Other:

4. A Team Collection member gets one whole session before the requirement bites

Devin, promoted from a flag to a bug on the latest commit — thread left open. Found independently by the local review.

Picture an administrator setting the minimum version to 6.6 on Monday evening. A teammate on 6.5 starts Bloom on Tuesday morning. The startup gate reads the copy of the settings file on their own machine, which is still yesterday's and says nothing about 6.6, so it lets them in. Bloom then syncs the collection files down from the shared folder — but that is a sync, not a change notification, and only a change notification triggers the mid-session lock-out. So nothing catches it. They work in that collection all day. It is only the next time they launch Bloom, with the flag now sitting in their local file, that they are stopped.

The mid-session lock-out you asked for does work — but only for a change that arrives while Bloom is already running. It does not cover the change that was already waiting when Bloom started.

Whether this matters depends on what the flag is for. If it exists to warn a person, a day's delay is untidy but survivable. If it exists to stop an old Bloom writing to files a new Bloom owns, then a full session of editing is exactly what it was supposed to prevent.

5. Bloom freezes while the upgrade downloads — and the wait cursor may not even appear

Local review, and Devin — thread left open.

When the user clicks Upgrade Bloom, we block the UI thread until the download finishes. At startup that is invisible — there is no window yet. In the Team Collection case there very much is one, and it stops repainting for the whole download. On a slow connection and a full release rather than a delta, that is minutes of a window that looks crashed.

The mitigation in the code today is a wait cursor. Devin points out that it may not even manage that: Application.UseWaitCursor normally needs a turn of the message pump to take effect, and we then immediately stop pumping. So the one signal we thought we had may not exist.

The real answer is a modal progress dialog that keeps pumping messages, which fixes the frozen window and the cursor together. That is new UI rather than a review fix, which is why it is your call rather than mine.

6. The warning triangle never appears — on this dialog or eight others

You asked last round: "Are there other dialogs this will change today? Which ones?" Here is the answer.

Our dialog asks for a warning icon and doesn't get one. The cause: in .NET, MessageBoxIcon.Warning and MessageBoxIcon.Exclamation are the same value (48), so icon.ToString() yields "Exclamation" — and the TypeScript side only knows "warning" and "asterisk". Nothing matches, so no icon renders. (Information works, because its ToString() genuinely is "Asterisk", which is the name the TypeScript already expects.)

The blast radius is eight other call sites, all of which ask for a warning today and silently get none. Fixing it makes a warning triangle appear on all of them at once: CollectionSettingsDialog.cs:394, CollectionModel.cs:601 and :637, SpreadsheetExporter.cs:969, MiscUtils.cs:571, PublishModel.cs:233 and :242, BookCommandsApi.cs:115.

One thing has changed since you last saw this: on your instruction the branch no longer touches BloomMessageBox at all. So this is now purely a pre-existing bug in a shared dialog that our feature happens to use — not something this PR broke, and not something it needs to fix.

7. Every Bloom message box is a fixed 500×200

You asked last round: "go ahead and evaluate what this will affect." Here is the answer.

BloomMessageBox.Show hard-codes dlg.Width = 500; dlg.Height = 200 for every message box in Bloom. Our longest message — the one explaining that the upgrade helps but isn't enough — is about 250 characters, so it is one of the more crowded things that dialog has been asked to hold.

Letting the dialog size itself to its content changes the shape of all of them — which is very likely an improvement, and is also exactly the kind of change that needs someone to look at twenty dialogs.

As with the icon, this branch no longer touches BloomMessageBox, so this is a pre-existing limitation our feature merely runs into.

11. Cancelling the collection chooser now quits Bloom

Devin, final round — fixed and resolved. This one changes something you specified, so it needs your eye.

You asked that the lock-out give the user two ways out and no third: upgrade, or open a different collection. I implemented that with a loop — cancel the chooser and the dialog comes back. Devin pointed out that this builds a trap. The dialog deliberately has no close box, so if the user has nothing newer on their channel and no other collection to open, both offered exits are dead ends and the dialog returns forever. The only way out of Bloom is Task Manager.

I have changed it so that cancelling the chooser quits Bloom, which is exactly what the same cancel does on the startup path. The intent survives — they still cannot stay in that collection — but "none of the above" is now a real answer.

The alternative is a third button, Quit Bloom, on the dialog itself. That is more discoverable than "press Escape twice and Bloom closes", which is arguably a surprising thing to have happen. It costs a new string, and you are reviewing strings in item 1.

Other:

12. Other startup jobs keep running while Bloom quits for the upgrade

Devin, final round — thread left open.

When the user chooses to upgrade at startup, we ask Bloom to quit so the installer can run. But quitting is not immediate — Bloom cancels its own first close while it saves — and meanwhile the queue of remaining startup jobs is still being worked through on idle. One of those is the registration check, which can put up its own dialog. So the user could be looking at a registration prompt while Bloom is trying to shut down for an install.

Nobody has seen this happen; it is reasoning from the code. Fixing it properly means deciding what the startup queue should do once we have committed to quitting, which is a change to Bloom's startup sequencing rather than a review fix — and this run has reached its cap on fix-and-re-review cycles, so I stopped rather than reaching for it.
