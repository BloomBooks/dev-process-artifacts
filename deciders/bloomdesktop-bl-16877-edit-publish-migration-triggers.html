What this PR is about

Problem

Many of the fix-ups a page needs happen only when that page is opened in the Edit tab, so a book carries them on the pages someone happened to visit and nowhere else. BL-16852 built the machinery to detect that and run the whole book through an off-screen pass, but wired it to only two triggers — launching the AI image editor, and changing the page size — to keep the 6.5 change small.

So a book is still brought up to date only when one particular feature needs it. Ordinary editing works on a half-migrated book, publishing can ship un-migrated pages, and a book harvested from the command line comes out different from the same book published locally.

What the PR does

Runs the pass wherever someone is about to work with or publish a book — and, importantly, before they get there.

  • A named chokepoint. Book.EnsureReadyForUserWork does EnsureUpToDate and then the per-page fix-up if it is due. Deliberately not a step inside EnsureUpToDate, which is called from previews, imports, bulk collection operations and throwaway copies, none of which want a whole-book browser pass — and ProcessBook begins by calling BringBookUpToDate, so putting it there would recurse forever. It is serialized, because two callers really do arrive at once.
  • One way into the Edit tab. The front end's goToEditTab() asks for the book to be made ready (app/ensureBookReady), waits, then selects the tab. The tab button, double-clicking a book, the "Edit this book" / "Make a book from this source" button and its context-menu twin all go through it. Because the pass finishes before the tab exists, its progress dialog is never on the activation path.
  • The APIs report instead of navigating. app/makeOrEditBook, app/makeFromSelectedBook and collections/selectAndEditBook make and select the book, then reply { goToEditTab }. That is what makes "make a book from this source" work: the book does not exist until the call has run, so only the front end can prepare the right one.
  • Publishing uses the same entry point. PublishTabPane calls app/ensureBookReady and only then getInitialPublishTabInfo. Separate calls because the two have opposite requirements: the fix-up must not hold the API sync lock (the off-screen pages it loads make their own sync-locked calls), while getInitialPublishTabInfo must keep it, since it assigns the static PublishApi.Model and LibraryPublishApi.Model that other publish endpoints read.
  • The harvester too. CreateArtifactsCommand does the same preparation, so harvested artifacts match a local publish. HydrateBookCommand deliberately does not, and says why: no ProjectContext, so no server, and it feeds automated converters rather than publishing.
  • EditBookCommand is gone. Its handler only did ChangeTab(edit); with the front end owning that step it had no raiser left. The class, its DI registration, the WorkspaceView subscription and handler, injected fields in three classes, the already-callerless CollectionModel.DoubleClickedBook and its stale PerformanceMeasurement entry all go with it.

PublishView, PublishModel and EditingStateMachine are unchanged from master. No new detection logic, metas, strings or settings.

What the interactive test found

This is the part worth reading. The suites and Devin's first pass were clean while three separate hangs sat in the code. Each was found by running Bloom, and each is fixed.

  • Entering the Edit tab hung Bloom. The trigger returned early without showing a page so the pass could have the book to itself; the Edit tab then came up with no page selected, asked for editView/frameSources, that threw for want of a current page, and the resulting problem dialog opened inside the progress dialog's message pump where neither could be dismissed. The same shape was in the original design, so this trigger had never worked.
  • The publish route hung differently. Two app/ensureBookReady calls ran concurrently — PublishTabPane asks on both its mount effect and the switchToPublishTab event — which is the BL-3166 hazard EnsureUpToDateMemory nags about. In a DEBUG build that nag is a MessageBox on a background thread, so Bloom froze behind the progress dialog. Now serialized.
  • A navigation regression (found by Devin, not the tests): the context menu's "Make a book using this source" goes through a generic dispatcher that ignores the reply, so once that endpoint stopped navigating, it made the book and left the user on Collections.

After the fixes, all four routes were re-driven from the UI: Edit tab button, "Edit this book", the context menu's equivalent, and the Publish tab. Each ran the pass, stamped the book, closed the dialog, and arrived with a page (or the publish tools) showing. An already-migrated book goes straight through with no dialog.

Worth knowing

  • The serialization lock covers EnsureReadyForUserWork only, on purpose. The two direct callers of the dialog form (a page-size change and the AI image editor) run on the UI thread, and taking the same lock there could deadlock against a worker thread that holds it while marshalling to the UI thread.
  • The publish gate depends on app/ensureBookReady staying small and sharing nothing — that is what makes requiresSync:false defensible for it. Worth protecting if anyone later adds to that handler.
  • Unrelated, found while testing: BloomServer.RobustFileExistsWithCaseCheck throws when a book sits under a path whose casing the OS reports differently from the string Bloom holds. It killed a harvester run from a temp directory; re-running from a clean path passed. Not filed.
Settled

Everything asked in earlier reports is now closed

  • Publish gate did not gate the front end. Resolved: app/ensureBookReady called before getInitialPublishTabInfo, which stays synchronized.
  • Silent skip when there is no shell form. Resolved: the any-thread form falls back to headless, and the harvester runs the pass for real — proven by running the command.
  • Publish re-entrancy while the dialog is up. Gone: PublishView is back to master, so there is no deferred activation to re-enter.
  • Edit and Publish passes could overlap. You asked me to try to reproduce it before deciding. A bounded search found no C#-initiated tab change that could fire during a modal — but interactive testing then found a real concurrency bug on the publish route, which the serialization above fixes. So the concern was genuine, just not by the route anyone was looking at.
