What this PR is about

Problem

Many of the fix-ups a page needs happen only when that page is opened in the Edit tab, so a book carries them on the pages someone happened to visit and nowhere else. BL-16852 built the machinery to detect that and run the whole book through an off-screen pass, but wired it to only two triggers — launching the AI image editor, and changing the page size — to keep the 6.5 change small.

So a book is still brought up to date only when one particular feature needs it. Ordinary editing works on a half-migrated book, publishing can ship un-migrated pages, and a book harvested from the command line comes out different from the same book published locally.

What the PR does

Makes the pass happen wherever someone is about to work with or publish a book.

  • A named chokepoint. Book.EnsureReadyForUserWork does EnsureUpToDate and then the per-page fix-up if it is due. It is deliberately not a step inside EnsureUpToDate: that is called from previews, imports, bulk collection operations and throwaway copies, none of which want a whole-book browser pass — and ProcessBook begins by calling BringBookUpToDate, so putting it there would recurse forever.
  • Two ways to run it. BookProcessor gains a no-UI form, and one callable from any thread that shows the modal progress dialog where there is a window and falls back to the no-UI form where there is not — so a headless run does the work rather than silently skipping it.
  • Entering the Edit tab. OnBecomeVisible runs the pass before showing a page, requiring the new EditingStateMachine.NoPage. The pass rewrites the book's DOM from a worker thread and every page it loads off-screen announces itself as loaded, including one carrying the id a live editor would be waiting on. That precondition holds on tab entry and fails during SetLayout's mid-save orientation rebuild, which would otherwise schedule the pass a second time.
  • Publishing, wherever it starts. A new publish/ensureBookReady endpoint, called before anything else is asked about the book. It is separate from getInitialPublishTabInfo because the two have opposite requirements: the fix-up must not hold the API sync lock (the off-screen pages it loads make their own sync-locked calls), while getInitialPublishTabInfo must keep it, since it assigns the static PublishApi.Model and LibraryPublishApi.Model that the other publish endpoints read. PublishView and PublishModel are unchanged from master.
  • The harvester too. CreateArtifactsCommand does the same preparation, so harvested artifacts match a local publish.
  • HydrateBookCommand deliberately does not, and says so: it has no ProjectContext and so no server, and is not given a collection to build one from. It feeds automated converters rather than publishing.
  • Comments widened. Three comments narrowed for 6.5 described the fraction-of-page data as present "by the time the AI image editor opens"; it is now present before a book can be edited or published.

No new detection logic, metas, strings or settings — this is the trigger half of BL-16852, already in 6.5 and master.

Worth knowing

  • Nothing has been exercised in the Bloom UI. The Edit-tab trigger and the publish progress dialog have only been reasoned about and covered by the suites. The one path actually run end to end is the harvester, from the command line.
  • The publish gate depends on publish/ensureBookReady staying small and sharing nothing — that is what makes requiresSync:false defensible for it. Worth a reviewer's eye, and worth protecting if anyone later adds to that handler.
  • Unrelated, found while testing: BloomServer.RobustFileExistsWithCaseCheck throws when a book sits under a path whose casing the OS reports differently from the string Bloom holds. It killed a harvester run from a temp directory; re-running from a clean path passed. Not this PR's problem, and not filed.
Decision

Two passes could still overlap if Edit and Publish both start one

Both triggers hand their work to the UI thread and then a modal progress dialog blocks in ShowDialog — which pumps the message loop. So a second request arriving while the first dialog is up gets dispatched inside it, and two ProcessBook runs would rewrite one book's DOM from two worker threads at once.

What makes it hard to reach: the dialog is owned by the shell, so it blocks user-initiated tab switching for as long as it is up. Reaching this needs a tab change that does not come from the user, during the dialog. I have not demonstrated one.

What makes it hard to fix: the obvious guard was tried on an earlier commit here and made things worse — the turned-away caller returned immediately and then navigated, loading a live page while the first pass was still running, which is the same bad end state by another route. Devin caught that. Doing it properly means the second caller waits for the first rather than being refused, which needs a synchronization primitive and a decision about what the Edit path shows meanwhile, since it has no page to fall back to.

Settled since the last report

The three earlier decisions

  • Publish gate did not gate the front end. Resolved, but not as the last report proposed. Rather than dropping the Publish trigger to its own card, it moved to publish/ensureBookReady, called before getInitialPublishTabInfo, which stays synchronized — because that handler assigns two statics about twenty-six other places read.
  • Silent skip when there is no shell form. Resolved. The any-thread form falls back to headless rather than skipping, and the harvester now runs the pass for real — proven by running the command, not reasoned.
  • Publish re-entrancy while the dialog is up. Gone. PublishView is back to master, so there is no deferred activation to re-enter.
