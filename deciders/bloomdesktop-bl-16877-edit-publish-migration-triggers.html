What this PR is about

Problem

Many of the fix-ups a page needs happen only when that page is opened in the Edit tab, so a book carries them on the pages someone happened to visit and nowhere else. BL-16852 built the machinery to run the whole book through an off-screen pass, but wired it to only two triggers: launching the AI image editor, and changing the page size. So ordinary editing works on a half-migrated book, publishing can ship un-migrated pages, and a harvested book comes out different from the same book published locally.

What the PR does

Runs the pass wherever someone is about to work with or publish a book, and before they get there.

  • A named chokepoint. Book.EnsureReadyForUserWork does EnsureUpToDate and then the per-page pass if it is due, serialized because two callers really do arrive at once. It is deliberately not part of EnsureUpToDate, which previews, imports and throwaway copies also call.
  • One way into the Edit tab. The front end's goToEditTab() calls app/ensureBookReady, waits, then selects the tab. Every route (tab button, double-click, "Edit this book" / "Make a book using this source", and the context menu) goes through it, so the progress dialog is never on the tab's activation path. The pass is master's non-blocking EnsurePerPageFixupIfNeededThen behind the top-level "Update Book" dialog. EnsurePerPageFixupIfNeededOnAnyThread makes it synchronous by holding the request (which is requiresSync:false) until the dialog closes.
  • The APIs report instead of navigating. The make/edit endpoints select the book and reply { goToEditTab }. It is true only when a new book was actually made, so cancelling a template's setup dialog stays on Collections.
  • Publishing and the harvester use the same entry point. PublishTabPane calls app/ensureBookReady before getInitialPublishTabInfo, and CreateArtifactsCommand runs the pass without a dialog.
  • EditBookCommand is removed, since nothing raises it any more.

Worth knowing

  • The Edit and Publish entry points now wait, with no timeout, for the "Update Book" dialog to close. The dialog helper keeps its close callback in a static field, so if some other progress dialog opened while this one was up, the wait would never end. No path to that was found (the dialog's backdrop covers all of Bloom), but it is the one way this could hang.
  • Not re-tested by hand this run: the harvester's command-line path (CreateArtifactsCommand). The rebase left it untouched, and it was run for real in an earlier round.
