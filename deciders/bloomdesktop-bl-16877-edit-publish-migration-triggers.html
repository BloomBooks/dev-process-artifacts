What this PR is about

Problem

Many page fix-ups happen only when a page is opened in the Edit tab, so a book carries them on the pages someone happened to visit and nowhere else. BL-16852 built the machinery to detect that and run the whole book through an off-screen pass, but — to keep the 6.5 change small — wired it to only two triggers: launching the AI image editor, and changing the page size. So a book is still brought up to date only when one particular feature needs it. Ordinary editing works on a half-migrated book, and publishing can ship un-migrated pages.

What the PR does

Runs the same pass in the two remaining situations, so a book is up to date before anything works with it.

  • Entering the Edit tab. OnBecomeVisible runs the pass before showing a page, through RunPerPageFixupThenReturnToPage — the path the other two triggers already use — so it inherits running off the API sync lock and landing on the first page if the page it aimed at is gone.
  • Entering the Publish tab. Activate splits in two, deferring the rest of activation until the pass finishes. The pass must not run while the sync-locked workspace/selectTab handler holds the lock, and publishing must not start until it has finished; deferring both together satisfies both.
  • A precondition, made explicit. The pass may only start when the editor has no page. EditingStateMachine gains a NoPage predicate and the Edit-tab trigger requires it. See "what changed this run" — this is what the review turned up.
  • Comments widened. Three comments narrowed for 6.5 described the fraction-of-page data as present "by the time the AI image editor opens"; it is now present before a book can be edited or published.

No new detection logic, metas, strings or settings — this is the trigger half of BL-16852, already in 6.5 and master.

What changed this run

Added the two triggers, then twice corrected how the Edit-tab one starts the pass. The first attempt let an orientation change schedule the pass twice, overlapping; a guard against that turned out to be worse, because the turned-away caller then navigated while the first pass was still running. Both are now fixed at the source: the pass starts only when the editor has no page, and BookProcessor is back to exactly what is on master.

Worth knowing

  • Nothing here has been exercised by hand. Both triggers, and the orientation-change interaction that caused the trouble, have only been reasoned about and covered by the existing suites. The equivalent 6.5 work was live-tested; this has not been.
  • The three decisions opposite are all really one question — whether the Publish trigger is properly gated. The Edit-tab trigger stands on its own.
Decision 1

The Publish gate does not actually gate the publish front end

Deferring the rest of Activate holds back the switchToPublishTab event, but the publish UI does not wait for it. PublishTabPane is mounted fresh on every switch to Publish and calls publish/getInitialPublishTabInfo from its mount effect. That endpoint is registered requiresSync: false, so nothing holds it off, and it runs UpdateModelUponActivation() → EnsureUpToDate() — which can rewrite and save the book — on a non-UI thread while ProcessBook is rewriting the same book on the dialog's worker thread.

Not memory corruption (SafeXmlDocument locks per operation), but a genuine race against the rule that the pass must have the book to itself, and the publish tools render against a half-migrated book. The comment in the PR claiming the tab "does not go live until the book is migrated" is true only of the event, not of the mount.

Decision 2

Publishing silently skips the migration when there is no shell form

The Publish trigger only runs the pass when Shell.GetShellOrOtherOpenForm() returns a form with a created handle. Otherwise it skips the pass entirely and publishes whatever is on disk. EditingModel.RunOffTheApiLock handles the same situation differently — it runs the action inline instead.

The asymmetry may well be right: running inline here would execute under the API sync lock, which is the one thing this code must not do. But it means a headless, early-startup or automated publish quietly ships an un-migrated book, which is the bug this feature exists to prevent.

Leave comment
Decision 3

Publish re-entrancy while the progress dialog is up

_isActive is set as soon as Activate() returns, even though activation was only queued. If something drives a tab change away from Publish and back while the modal is up — Bloom does have C#-initiated tab jumps, and the modal's message pump would dispatch them — Deactivate() runs having never really activated, and the return calls Activate() again, starting a second pass on the same book.

Lower confidence than the other two: it needs a C#-initiated tab change during a modal, which I have not demonstrated. It is the one thing the reverted guard would still have covered, and it disappears entirely if the Publish trigger moves to its own card under decision 1.
