What changed this run

fix: Ship and serve the Andika and ABeeZee fonts correctly
f1cc5ec

The lookup for a bundled font was built from app.getAppPath(), which points at the source tree in development but at <install>/resources/app.asar once packaged — so the installed viewer looked for its fonts one level outside itself and never found them. It now resolves from __dirname when packaged, mirroring what the code just above it already did for the bloom-player folder.

The shipped files also had the wrong names: current Bloom asks for fonts by file name (host/fonts/Andika-Bold.woff2), while we shipped .ttf. Replaced with Andika 7.000 in .woff2 (2.76 MB → 1.19 MB) and added ABeeZee, which Bloom also assumes is present. Plus a real 404 with a loud log when a font we ship is missing, @font-face declarations so the viewer's own start screen uses the bundled copies, CI assertions that the fonts reach the package, and each family's OFL notice.

9c3209c

Decision — most important

Master moved during this run, and the version number you asked for is now behind it

When this run started, master was at version 2.2.1, which is why 2.2.2 was the sensible next number when you asked for a bump. Minutes later, while the reviewers were working, pull request #62 was merged into master: an upgrade of Electron from 30.5.1 to 43.3.0 — thirteen major versions — which set the version to 2.3.0. So our 2.2.2 is now a lower number than what master already carries, and the two disagree in the same file.

Merging master in produces three conflicts, and I stopped rather than guessing at any of them:

  • The version number. Someone has to decide whether this font fix goes out as part of 2.3.0, or as a 2.3.1 after it. That is a release decision, not a mechanical one.
  • AGENTS.md and CLAUDE.md. Master's PR added its own versions of both files, independently of the ones this run created. Master's are broader — they cover the tracker, which platforms are really supported, and where the team skills live. Mine add things master's do not: the commands, the project layout, and specifically the note about static/ only being copied into the build in production, which is the behaviour this whole bug turned on.

There is also something worth checking rather than deciding: everything I verified about the packaged application — the fonts being served out of the asar, the file lookups, the protocol handler — was verified on Electron 30. On paper none of it depends on anything Electron 43 changed, but "on paper" is how this bug survived three years, so it deserves a real packaged run on the merged result.

The font fix then ships as part of 2.3.0 alongside the Electron upgrade, and the agent docs end up as master's file plus the packaging and commands sections that are genuinely new. (~20 minutes including a fresh packaged run on Electron 43 to re-confirm the fonts.) Recommended because 2.3.0 is not released yet, so there is no reason to spend a second version number on this.
Choose this if 2.3.0 is already spoken for — cut, announced, or being tested as the Electron upgrade on its own, so that adding the font change to it would muddy what that release is. (Same work as above, one line different.)
Decision

A fragment of the YouTrack Bot token was printed into this session's transcript

Early in the run, while checking that the tracker was reachable, I ran a shell command that was meant to print only the word "set" to confirm the token existed. It was written wrongly and printed the token's value as well. A redaction filter caught the first part but stopped at an = character, so roughly the last 31 characters of the Bloom Bot's YouTrack permanent token appeared in the session output — and therefore in the on-disk transcript and tool-result logs for this session.

What this does and does not mean: a partial token is not usable on its own, and nothing was sent anywhere outside this machine — the text was printed locally, not posted to GitHub, YouTrack, or the report you are reading. But the Bot token is a shared credential used by the whole team's tooling, it does not expire on its own, and local transcripts are not treated as secret storage. Whether that is worth a rotation is a judgement about how much you care, not something I should decide.

Issue a new permanent token in YouTrack, revoke the old one, and update wherever YOUTRACK_BOT is set for the team. Recommended because it is cheap and certain, whereas reasoning about how much of a shared, non-expiring credential is "enough" to be safe is not.
Delete or redact this session's transcript and tool-result files and keep the existing token. (~5 minutes, no coordination with teammates, but relies on no copy of those files having been made.)
Decision

GitHub never announced your last commit, so the PR page shows no checks at all

When the version-bump commit was pushed, GitHub failed to send out the notification that normally tells everything watching the pull request that it has changed. Nothing was wrong with the push itself — the commit is on the branch and GitHub agrees it is the pull request's latest commit — but the announcement that usually follows it never went out. Two things that were waiting to hear it therefore never woke up: the build workflow, and Greptile.

I worked around both as far as I could. I started the build workflow by hand and it passed on the new commit, both Windows and Linux, including this PR's new font checks; and I re-ran Devin by hand, which also came back clean. Greptile I could not re-run: the "re-review" link in its own comment leads to a login page, and there is no way to press it from here.

What this leaves is mostly cosmetic but genuinely confusing for the next person: anyone opening the pull request sees an empty checks area, as though nothing has been verified, and Greptile's comment still refers to the previous commit. The actual unreviewed difference is a single line — "version": "2.2.1" becoming "2.2.2".

One throwaway commit (git commit --allow-empty) makes GitHub send the notification it missed, which wakes both the build workflow and Greptile and fills in the checks area. (~1 minute, no code change; the cost is one empty commit in the history.) Recommended because it costs almost nothing and means a human reviewer opens a pull request that looks verified instead of untested.
Has the same effect without adding a commit, but leaves a close/reopen pair in the pull request's timeline. (~1 minute, no code change. I did not do this on my own because closing your pull request is not something this run is authorised to do unasked.)
For your information

ABeeZee only covers basic Latin, so some books will still show mixed fonts

ABeeZee was added because Bloom ships it and assumes it is available. Reading the font files directly, Andika 7.000 covers 2,660 characters — Latin, Cyrillic, Greek, Vietnamese, combining accents — while ABeeZee covers 250, which is basic Latin and the common Western European accents and nothing more.

So a book set in ABeeZee whose text uses, say, Vietnamese tone marks or Cyrillic will render those characters from some other font on the machine, mixing letter shapes within a line. That is inherent to ABeeZee, not something this change introduced or can fix — but it is a plausible source of "the fonts look wrong" reports once we start actually serving ABeeZee, which we never did before. The QA notes ask a tester to look at exactly this.
