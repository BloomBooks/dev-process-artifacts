What changed this run

fix: Ship and serve the Andika and ABeeZee fonts correctly
f1cc5ec

The lookup for a bundled font was built from app.getAppPath(), which points at the source tree in development but at <install>/resources/app.asar once packaged — so the installed viewer looked for its fonts one level outside itself and never found them. It now resolves from __dirname when packaged, mirroring what the code just above it already did for the bloom-player folder.

The shipped files also had the wrong names: current Bloom asks for fonts by file name (host/fonts/Andika-Bold.woff2), while we shipped .ttf. Replaced with Andika 7.000 in .woff2 (2.76 MB → 1.19 MB) and added ABeeZee, which Bloom also assumes is present. Plus a real 404 with a loud log when a font we ship is missing, @font-face declarations so the viewer's own start screen uses the bundled copies, CI assertions that the fonts reach the package, and each family's OFL notice.

9c3209c

For your information

Devin finally had something to say — and it was worth hearing

Every earlier consultation came back empty. The first one to see the branch merged with master raised three things, all now resolved threads on the PR with the reasoning written out:

  • "Linked-book fonts still return 404" — not an issue. It assumed a book's stylesheet is applied with that book's own address as its base, which would have put /book/<id>/ in front of every font request and sent it down the wrong branch. bloom-player does not work that way: it copies the stylesheet text into its own page, so font requests always come out at the top level. This PR's own logs show it — the main book's stylesheet sits at a long temporary path, yet its font request arrives with no path at all.
  • "Font endpoint retains broad file access" — correct, and fixed. Font names arrive with web escaping already undone, so a crafted request could have stepped out of the fonts folder and read an arbitrary file on the machine. Now anything that is not one of the six files we ship is reduced to a bare file name, which cannot leave the folder.
  • "Installer contents remain unchecked" — correct, and fixed. The checks I added earlier only proved the build had staged the fonts; they said nothing about what the installer actually contains. There is now a third check that looks inside the packed application itself, and it passed on both Windows and Linux.

A re-run on the fixed commit repeated all three word for word, including the two it had just been fixed for, so that repeat is stale rather than a second opinion.
