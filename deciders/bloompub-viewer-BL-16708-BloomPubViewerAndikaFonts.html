What changed this run

fix: Ship and serve the Andika and ABeeZee fonts correctly
f1cc5ec

The lookup for a bundled font was built from app.getAppPath(), which points at the source tree in development but at <install>/resources/app.asar once packaged — so the installed viewer looked for its fonts one level outside itself and never found them. It now resolves from __dirname when packaged, mirroring what the code just above it already did for the bloom-player folder.

The shipped files also had the wrong names: current Bloom asks for fonts by file name (host/fonts/Andika-Bold.woff2), while we shipped .ttf. Replaced with Andika 7.000 in .woff2 (2.76 MB → 1.19 MB) and added ABeeZee, which Bloom also assumes is present. Plus a real 404 with a loud log when a font we ship is missing, @font-face declarations so the viewer's own start screen uses the bundled copies, CI assertions that the fonts reach the package, and each family's OFL notice.

Worth reading

A check I added last run could never have failed

When Devin pointed out that the CI font checks only proved the build had staged the fonts, and said nothing about what the installer actually contains, that was a fair criticism and I wrote a fix for it. The fix searched the packaged archive for the six font file names.

It could not work. Those six names are also written inside two other files that live in the same archive — the list of fonts the app knows about, compiled into its main program file, and the six font rules added to the start screen's HTML. So the search found the names whether or not a single font file was present. The check reported success in exactly the situation it existed to catch.

What makes this worth telling you rather than burying: I tested it by hand before shipping it, watched it pass against a real package, and took that as proof. It passed for the wrong reason. This run's local review spotted the flaw by noticing where else those names appear.

It now reads the archive's own table of contents instead, and I checked it in both directions — it passes on the real package, and it fails on one with the six fonts removed, where the old search still passed. CI has since run the new version for real against both the Windows and Linux builds. The practical upshot: the green tick on that row in the previous report meant nothing; the one in this report does.
