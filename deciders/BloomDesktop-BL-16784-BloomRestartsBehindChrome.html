Session notes

The bug was verified and the fix measured on the real thing, on this machine's two-monitor setup, with Bloom and Chrome both maximized on the secondary monitor — the exact arrangement in the report. Before the fix, after a collection switch Bloom's window was not even in the top twelve of the window stacking order, with Chrome still in front. After it, Chrome held the foreground going in, and Bloom came out on top and focused.

An intermediate measurement is worth knowing about, because it shaped the fix: making the window merely “always on top” for a moment was not enough on its own. Bloom landed directly behind Chrome, because Windows refuses to hand the foreground to an application that does not already have it, so the raised window was never the active one and slipped back under Chrome the moment the pin was released. That is why the change also takes the keyboard focus outright.

Not verified by hand: switching into a Team Collection, where the syncing progress dialog appears in the same second-and-a-half that Bloom is pinned on top. That is the one interaction this change could plausibly disturb, and it is called out in the test notes on the card.

Also fixed as a side effect: _finishedLoading is set only by the come-to-front code, and Bloom refuses to save its window size and position until that flag is set — so before this change, a collection switch quietly stopped Bloom remembering its window geometry for the rest of the session.

For your confirmation

The pull request targets Version6.5, not master

Bloom's own contributor notes say that when a card's summary starts with a version in square brackets, the fix belongs on that version's branch. This card is titled “[6.5 regression] After changing collections, Bloom is invisible (behind) Chrome browser”, and the branch was cut from the tip of Version6.5 — so the pull request was opened against Version6.5 rather than the usual master.

Both readings of the title are possible: it could name the target branch, or it could simply mean “this is a regression that appeared in 6.5”. Because the two signals agreed, the run did not stop to ask — but retargeting a draft pull request is a single click, so it is cheap to change if the intent was different.

Verification gap

The Team Collection syncing dialog was not tested by hand

When Bloom brings its window forward it pins it above every other window for about a second and a half, then releases it. Switching into a Team Collection puts the syncing progress dialog on screen inside exactly that window of time. The dialog is opened with Bloom's main window as its owner, which normally keeps it above that window even while the window is pinned — so this is expected to be fine, but expected is not the same as seen.

It is the single most plausible way this change could make something worse, so it is written up first in the tester notes on the card. The question is only whether you want it confirmed before this goes to a colleague, or left to the tester.

FYI

A second bug got fixed along the way

Bloom only starts saving its window size and position once an internal “finished loading” flag is set, and the only code that set that flag was the same come-to-front code that was never running after a collection switch. So on the current 6.5, once you switch collections, Bloom silently stops remembering where you put its window — for the rest of that session.

The fix makes that code run again, so the flag gets set and the geometry is saved. It is a real user-visible improvement that this card did not ask for, and it is included here because it is the same one-line cause, not a separate change. It is called out in the tester notes so someone actually exercises it.
