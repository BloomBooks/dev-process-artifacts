Decision · from Devin

Two raises close together can cut each other's protection short

When Bloom brings its window to the front, it pins the window "always on top" for a second and a half and then releases it. That brief pin is what wins the race against whatever application grabbed the foreground while Bloom had no window — it is the heart of this fix.

Each raise starts its own release timer, and none of them know about the others. So if Bloom raises the window twice inside that second and a half, the first timer comes due and releases the pin early — while the second raise still thought it was protected. Raise at zero and again at one second, and the pin drops half a second into the second raise instead of a second and a half. A foreground change arriving in that gap can put Bloom back behind another window, which is the exact symptom this card is about.

Devin rates it non-severe, and it takes two raises of the same window spaced far enough apart to matter. The realistic routes are two Bloom Library downloads in quick succession (both handlers call Shell.ComeToFront()) or a dialog shown, hidden and re-shown inside a second and a half. It is mirrored as an open thread on Extensions.cs:105-112.

Decision · found by preflight

Linux now gets the second-and-a-half "always on top" hold too

Two separate things happen when Bloom comes to the front. It pins the window above the others for a second and a half, and — separately — it takes the keyboard focus by force. Only the second of those is guarded by a Windows check. The pin runs everywhere.

That matters because the old code in ReallyComeToFront flipped "always on top" on and straight back off, with no hold at all. So on Linux, switching collections now leaves Bloom sitting above other windows for a second and a half where it previously did not. Nothing in the PR's comments mentions Linux, so this looks more like a side effect of reusing the helper than a decision anyone made. Whether it is harmless depends on the window manager: the visible risk is a dialog Bloom itself opens right afterwards — the Team Collection sync progress dialog is the one to think about — being held under the main window for that moment.
