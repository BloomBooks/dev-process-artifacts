What this PR is about

Problem

In the 6.5 betas, removing a page often does nothing. The context-menu command is enabled, the "Really Remove Page?" dialog appears, but after clicking Remove the page stays. It happens on any page in any book and survives a restart (BL-16809).

Cause

Since BL-16421 the confirmation is a browser dialog. Like the other edit-tab dialogs it tells C# when it opens and closes, and C# used that flag to disable the page list as well as to lock the workspace tabs. Clicking Remove sends the remove command and the "dialog closed" notice as two concurrent HTTP requests. Whenever the command is handled first (it runs on a deliberate short delay), the page list is still disabled and the command is refused silently. Captured live in 6.5.3018: the unlock was processed about 350 ms after the command had already been dropped.

What the PR does

  • The modal-state flag now only locks the tabs. Disabling the page list dates from when it lived in its own browser and a dialog's backdrop could not cover it; a dialog shown from the workspace root now has a backdrop that already blocks the page list.
  • The C# gate is removed: the page list's Enabled flag and its checks on page clicks and context-menu commands (EditingView.cs:1548, PageThumbnailList.cs:204). The same lag could also swallow a page click made right after a dialog closed.
  • Two dialogs that were still launched from code in the page iframe, Choose Link Target and Book Grid Setup, are now shown through the workspace bundle like the copyright dialog, so their backdrop covers the whole workspace rather than only the book pane (workspaceRoot.ts:86).
  • The comments on the dialogs that post the flag now say what it does, and a papercut records the dev launcher timing out while a direct dotnet watch run works.

Worth knowing

  • Nothing now blocks page-list clicks or commands while a dialog is open except the dialog's own backdrop. If any Edit-tab dialog is ever drawn only over the book pane again (a direct import of ShowEditViewDialog from page-iframe code does this), the page list becomes clickable behind it. The test ideas on the card ask QA to look for exactly that.
  • The two relocated dialogs were verified by reasoning and MUI's source, not by hand: the dev launcher would not start Bloom in this worktree and a direct dotnet watch run serves the stale pre-built bundle. Their behavior is covered in the test ideas.
  • The BetaInternal's page-list API briefly reported the page as already gone with the previous page selected, then reverted, with nothing in its log. It did not recur and is not explained by this fix.
