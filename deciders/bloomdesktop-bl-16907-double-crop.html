What this PR is about

Problem

After upload, a book's cover image on Bloom Library (the online reader, the thumbnail and the BloomPUB) is cropped more than the author chose in Bloom. Example: this book's cover lost 83 more pixels off the top than the author's crop.

Cause

Upload really crops image files and adjusts the page image's style to match. But the book's data-div entry for the same image (coverImage) kept the old crop style. When the uploaded book is opened again (by the harvester, or after "download for edit"), Bloom copies the data-div onto the page, so the old crop is applied again to the already-cropped file, and the BloomPUB step crops it a second time. This started with BL-16173's change to keep the crop structure on upload; uploads from 6.3 don't reproduce it.

What the PR does

  • When really-crop successfully crops an image and rewrites or removes its style, the matching data-div entry gets the same style (SyncDataDivStyle).
  • A failed crop leaves the data-div alone, including for a second use of the same image, so the author's crop survives for reopening to restore it.
  • A custom-layout cover also leaves the data-div alone; its style must never reach the data-div (BL-16357).
  • New tests cover the upload → reopen → publish sequence (it reproduces the 1001×607 result without the fix), the publish-mode path, failed crops, and a custom-layout cover.

This does not repair books already uploaded with the stale data-div; see the decision.

Worth knowing

  • Not exercised by hand: no real upload to the dev library has been done with this build. The test ideas on the card cover that.
  • Pre-existing, unchanged: on a custom-layout cover, the standard layout's data-div entry still keeps the old crop style while its source file now points at the cropped file. Switching such a book back to the standard layout after upload could still show a double crop.

Books already on Bloom Library

This PR fixes new uploads only. Books uploaded with a 6.4 build that has BL-16173 (roughly since May 2026) and a cropped cover already have the stale crop in their data-div on Bloom Library. Every time the harvester processes one of them, it copies that crop back onto the page before any of this code runs, so their online reader, thumbnail and BloomPUB covers stay over-cropped. The authors' own copies are fine, because upload crops a temporary copy.
