What this PR is about

Problem

After upload, a book's cover image on Bloom Library (online reader, thumbnail, BloomPUB) is cropped more than the author chose in Bloom, usually with extra cut off the top. The reported book lost 83 more pixels off the top than the author's crop. Downloading the book for editing showed the same damage: the cover picture shifted, leaving a blank strip.

Cause

Upload really-crops image files and adjusts the page image's style to match, but the book's data-div entry for the cover image kept the old crop style. When the uploaded book is opened again, by the harvester or after "download for edit", Bloom copies the data-div onto the page, so the old crop is applied again to the already-cropped file, and the BloomPUB step crops it a second time. It started with BL-16173, which began keeping the crop structure on upload. Uploads from 6.3 do not reproduce it.

What the PR does

  • When really-crop succeeds and rewrites or removes an image's style, the matching data-div entry follows. On a standard cover it gets the same style as the page image.
  • On a custom-layout cover, the data-div entry describes the standard layout: a crop of the original file in a frame sized for the original's shape. Neither applies to the cropped file, so the entry loses them. Switching back to the standard layout, by the user or automatically when the subscription no longer allows custom layouts, then shows the whole cropped picture, as a newly chosen picture would, rather than cropping it a second time.
  • A failed crop leaves the file unchanged, so the page image keeps its crop style (it used to be removed, and the uploaded book showed the image uncropped) and the data-div is left alone. A duplicate image no longer treats an earlier failed crop as done.
  • Tests cover upload, reopen and publish on the real book's markup (reproducing the double crop without the fix), publish mode, failed and duplicate-failed crops, and a custom-layout cover switched back to the standard layout.

Books already uploaded with the stale data-div are not repaired. We decided against a harvester-side repair; such a book is fixed only if it is uploaded again with a fixed Bloom.
