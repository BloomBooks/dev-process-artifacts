How the 6 test failures were cleared

A red suite is worth nothing if the reason isn't established, so this was measured rather than assumed.

  • First attempt was much worse: 1456 of 2833 failed. Cause: I had isolated the build output to a scratch folder outside the repo, so every repo-root-relative lookup (output/browser, DistFiles) failed. Moving the isolated output inside the repo — which is exactly why master's wrapper uses output/agent/<key>/ — dropped it to 6.
  • The remaining 6: five xmatter-locating tests (XMatterHelperTests, InsertPageAfter_FromDifferentBook_MergesStyles) plus the opt-in Reading App Builder real-build test.
  • The decisive experiment: I reverted all six of my changed files to their base versions in this same worktree, with the same harness, rebuilt, and re-ran. The same five still failed. The change is therefore not the cause — it is this worktree's isolated-output harness. The files were then restored and verified byte-identical to HEAD.
  • The RAB test is the documented opt-in real-build test; it found a real Reading App Builder install and failed in Gradle for environment reasons, as it does on this machine generally.

What the fix actually does

  • Two page sizes went from impossible to working. Ebook2x3Portrait and Ebook7x5Landscape are offered in Bloom but were never added to BloomPdfMaker's size list, so PDF generation failed outright — which also blocked uploading, since upload makes a PDF preview. Added at Program.cs:271, converting at 96px/inch (:295) since these are the only Bloom sizes declared in CSS pixels.
  • Geometry verified against real output, not assumed: Ebook7x5 landscape renders 719.04 × 516.96 pt and Ebook2x3 portrait 355.92 × 525.12 pt, both matching paperDimensions.less to within WebView2's 1/100-inch rounding.
  • The misleading advice is gone (MakePdfUsingExternalPdfMakerProgram.cs:213), along with the dead pref chain behind it — UserPrefs.ReducePdfMemoryUse had been unsettable since 5.5.
  • The test would have caught this (PdfMakerTests.cs:193): sanity-checked by reverting the fix, at which point the two ebook cases fail and the Device16x9 control passes.

Decision

Version6.4 has no isolated-build wrapper, so agents can't reliably test on it

On master, build/agent-dotnet.sh plus some Directory.Build.props logic redirect a build into a private per-terminal tree, so an agent can build and run the C# suite while your Bloom keeps running. Version6.4 has neither.

That cost real time in this run. A plain build fails outright because your running Bloom locks the shared output, and my hand-rolled substitute produced first 1456 and then 6 phantom test failures that each had to be chased down and disproved. Any agent doing 6.4 work — and 6.4 is where shipped bugs get fixed — will hit exactly this and may not bother to disprove it, which is the worse outcome: a real regression dismissed as “probably the harness”.

FYI

The failure message still won't explain the next unknown page size

You chose “drop the sentence only”, so the message now reads as the summary plus whatever BloomPdfMaker printed on its standard output — which for this failure was just “Starting WebView2PdfMaker”. The sentence that actually explained the problem (“…has a very limited set of paper sizes…”) came on standard error, which Bloom still discards.

For this bug it no longer matters — the two sizes now work. It matters the next time a size or option reaches BloomPdfMaker that it doesn't recognize: the user and the error report will again show a failure with no visible reason. Flagging it because it's a one-line change if you ever want it, not because this PR needs it.
