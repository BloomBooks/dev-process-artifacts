What this PR is about

Problem

Bloom offers “Edit with AI…” on a picture, but the item was greyed out on an empty picture box. An empty box is exactly where a user most wants the AI: there is no picture yet, and the editor can make one from a description. The user had to put some picture there first, then ask the AI to replace it.

Cause

The rule that enables the menu item required a real raster picture whose format the editor can open. An empty box shows placeHolder.png, which is neither.

What the PR does

  • “Edit with AI…” is enabled on an empty picture box. A broken picture stays greyed out, which needs a new fact in the rule, because “no real picture” alone cannot tell an empty box from a picture that failed to load.
  • Bloom names the empty box as the one the user launched on. It used to withhold it, and the editor answers a missing box by aiming at the first picture of the book. A user who clicked an empty box on page 5 was therefore aimed at the front cover.
  • Two empty boxes on one page look identical and share a file name, so the page frame also counts the same-named boxes ahead of the clicked one. Without that count the second box always resolved to the first, and the created image landed in the wrong place.
  • Each box Bloom sends carries a name for the user to read: “Page 3”, the page’s own name for front and back matter, “Page 3 - Canvas Background” for the picture behind a page, and “Page 3 - Image 2” for the pictures on top of it. A page with several canvases numbers them all, so a Picture Dictionary page does not show six boxes called “Canvas Background”.
  • The four new strings are in BloomMediumPriority.xlf and come out in the user interface language.
  • The editor half lives in bloom-ai-image-tools, which Bloom pins as an immutable dist- tag. That half is released as dist-v0.1.6 and this PR moves the pin to it, so the two halves ship together: the editor keeps the placeholder graphic out of its “Image to Edit” panel, opens the tool that makes an image from a description, remembers the box the user launched on, and puts the created image back into it.

Worth knowing

  • Nobody has yet opened the editor by hand on a page that holds two empty boxes. That path is the one both of Devin’s bugs lived in, and it is covered by six unit tests across the two sides, but not by a run in a real Bloom. It is the first thing to try.
  • The count of same-named boxes assumes the live page and the saved book list the same pictures in the same order. The three classes Bloom never offers, and the controls Bloom injects into the live page, are excluded on both sides; anything else that appears in one and not the other would shift it. A count that overshoots aims at the first empty box rather than at nothing.
  • The four new strings carry translate="no", which is what the rules ask for on a new string. So on a French interface a front matter box can read a translated page name joined to an English “Image 1” until someone clears that flag. Devin noted it; it is the ordinary state of a new string, not a fault in this change.
  • The published dist-v0.1.6 build is staged into output/browser/aiImageEditor in this worktree, so the Bloom running there serves it the next time the editor opens.

Decisions

How should a page with several canvases name its boxes?

You asked for “Page 1 - Canvas Background” and “Page 1 - Image 1” on a page that has one picture behind it and pictures on top. Most pages are like that. Some are not: a Picture Dictionary page holds six separate canvases and an arithmetic page up to eight, and each canvas has a background picture of its own. Naming every one of them “Canvas Background” would give one page six boxes with the same name, which is worse than no name, because the name is the only thing that tells two empty boxes apart.

So the rule as written says “Canvas Background” only when the page has exactly one canvas. On a page with several, every box is simply numbered, “Page 4 - Image 1” through “Page 4 - Image 6”, backgrounds included.
