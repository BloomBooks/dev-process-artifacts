The fix, in one paragraph

Bloom used to hand the last part of each HTTP reply to the framework, which finished it on a callback whose only handler catches Win32Exception. Closing the listener under such a reply made it fail with something else entirely, on a thread none of our try/catch blocks cover, so it reached the runtime and killed the process. Bloom now issues the same asynchronous write — same I/O completion port, same thread, no change to when the data goes out — but supplies the completion itself, in the new PendingResponseWrites. Owning that last step means a failure at the end of a send is ours to swallow, and that shutdown can wait for sends still in flight. Three other things in the same area that could also kill the process — a Debug.Fail, an unguarded I/O callback, and a Debug.Assert — are fixed too.

The bug is reproduced deterministically by a new test: with the old call restored it kills the test host with exactly the stack from the card, and the new wrapper reports that run as aborted. It passes with the fix.

FYI: a trade-off accepted on your behalf

The two wrapper scripts now strip the indentation off each line of test output before looking for crash phrases. That was necessary — the two scripts genuinely disagreed about tab-indented lines — but Devin pointed out it also means a test's own indented output could trip a crash phrase and produce a false "run aborted" on a run that actually finished.

This was assessed as acceptable and the thread closed with that reasoning: the patterns always allowed indentation, so nothing new was opened up; being wrong in that direction is the safe one; and the verdict prints the exact line it matched, so a false alarm takes one look to diagnose. Flagged here in case you would rather it were tighter.
