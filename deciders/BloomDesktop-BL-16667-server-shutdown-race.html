The fix, in one paragraph

Bloom used to hand the last part of each HTTP reply to the framework, which finished it on a callback whose only handler catches Win32Exception. Closing the listener under such a reply made it fail with something else entirely, on a thread none of our try/catch blocks cover, so it reached the runtime and killed the process. Bloom now issues the same asynchronous write — same I/O completion port, same thread, no change to when the data goes out — but supplies the completion itself, in the new PendingResponseWrites. Owning that last step means a failure at the end of a send is ours to swallow, and that shutdown can wait for sends still in flight. Three other things in the same area that could also kill the process — a Debug.Fail, an unguarded I/O callback, and a Debug.Assert — are fixed too.

The bug is reproduced deterministically by a new test: with the old call restored it kills the test host with exactly the stack from the card, and the new wrapper reports that run as aborted. It passes with the fix.

The unexplained red run: found, named, fixed

You asked for ten more full runs with all output saved. The eighth failed, and the test was SpreadsheetAudioImportTests.NoErrorForEmptyAudio. It has nothing to do with this branch.

The test covers a spreadsheet row for page 17 that deliberately has no audio, and checks that no error was reported about it. But it was written as "no error message contains 17 anywhere", and the error messages for the other pages quote full file paths. Since BL-16664 every temp path contains this process's id — so any test host whose process id happens to contain "17" fails the test. In that run the process id was 178640.

That is roughly one run in ten, and it presents exactly as the thing that had us puzzled: a single red run naming a test unrelated to whatever branch you are on, which passes when you re-run it. It also retroactively explains the first unexplained failure earlier in the day. The assertion now says page 17, which is what it always meant and which a file path cannot trip. Checked against the exact error list from the failing run: the old pattern matches it, the new one does not, and the new one still catches a genuine page-17 error.

Fixed in fd62e496da. Not caused by this branch — BL-16664 is already on master — but this is where it surfaced, and a known one-in-ten flake would undermine the very thing this card is about.
