What this PR is about

Problem

editView/jumpToPage replied with success to a page jump that it had dropped. When the Edit tab was saving or loading a page, the jump was ignored, but the caller was told it worked. An e2e test that asked at the wrong moment saw an empty page frame and asked again, up to three times, 20 seconds apart, and a real "this page will not load" defect looked exactly the same.

Cause

A page announces to Bloom that it has loaded twice. A page change that arrives between the two announcements starts a save that the second announcement leaves unanswered, and the Edit tab then changes no pages at all. The state alone reads Editing in that window, and the DOM cannot show it.

What the PR does

  • EditingModel.JumpToPage says whether it did the jump, and the API replies with a failure when it did not: tab busy, no book, or no such page. A jump asked for while the Edit tab is hidden is shown when the tab opens.
  • The two front-end callers turn off the problem report for that failure, since a user cannot put it right.
  • A new e2e-only endpoint, e2e/editState, reports the Edit tab's state and how many times its page has announced itself. Every e2e helper that changes the page waits for it to settle first.
  • AUTOMATION-DEBT.md records the underlying Bloom defect and two fix directions, both of which change production save behavior.
