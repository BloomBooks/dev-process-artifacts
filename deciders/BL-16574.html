How the two fixes were verified

Both of these bugs are timing/lifecycle accidents that a developer cannot reliably provoke by hand: the internal server answers almost instantly on a dev machine, so the window in which the crash happens is too small to click through. Rather than declare them untestable, both new code paths were exercised on 2026-07-27 in a running Bloom with temporary instrumentation that was discarded before this push — the committed diff contains none of it.

  • Text Box Properties. A settable delay was inserted before the editView/getBookLangs request and log lines were added to both branches of the new guard. With the delay running, dismissing the dialog before the answer arrived was confirmed to reach the new bail-out with all three elements null, and to throw nothing. Leaving the dialog open was confirmed to still fill in the three language names normally. Re-running the same scenario with the fix stashed reproduced the original TypeError, which is what makes the passing result meaningful rather than vacuous.
  • Leveled Reader. A switch was added to force the nullish-opts condition, plus a log line reporting whether the old code would have thrown. With the condition forced, beginRestoreSettings was confirmed to take the default-level branch, resolve, and let tool activation finish.

That exercise also produced an observation worth passing to the reviewer, recorded in the PR description: on current master there appears to be no live path that delivers a nullish opts. Both callers pass toolbox.ts's module-level savedSettings, which starts as {} and is only ever reassigned from get("toolbox/settings"), and ToolboxView.HandleSettings always replies with a dictionary containing at least current and visibility. So the Sentry events for FFH presumably come from an older or since-removed path, and in particular the guard is not reachable by simply making a book with no saved leveled-reader state — that case yields {current, visibility} and takes the default-level branch without touching the guard. The guard is still correct and free; it just should not be described as reproducible today.

About the 9 C# failures

They are not caused by this branch, which changes two TypeScript files and no C# at all. They are artifacts of build/agent-dotnet.sh, the wrapper this repo uses so an agent can build and test while the developer's Bloom is running — it redirects the whole build into a private tree at output/agent/<key>/bin instead of output/Debug/AnyCPU, and two groups of tests depend on the shallower standard path:

  • 4 PdfMakerTests fail with "BloomPdfMaker.exe seems to be missing". The wrapper builds without a native apphost, so BloomPdfMaker.exe is absent from the private tree (the .dll is there); the shared output/Debug/AnyCPU has it.
  • 5 xmatter tests (XMatterHelperTests and one BookTests case) locate their test data as {codeBaseDir}/../../../src/BloomTests/xMatter. Three levels up from output/Debug/AnyCPU is the repo root, so it resolves; three levels up from output/agent/<key>/bin is output/, so it does not.

Both runs of the suite produced the identical 9 failures, and no test touching the changed areas is among them. Verified by inspecting the two output trees directly rather than by assumption.
