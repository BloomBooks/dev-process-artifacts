How it works, in one paragraph

Right-clicking a paragraph in an ordinary text box opens a small menu (TextContextMenu.tsx:105, wired in at bloomEditing.ts:1096). Plain right-click was dead air there before; ctrl+right-click still reaches the developer menu, and text in a canvas element keeps its own menu. The single item toggles a class (noIndent.ts:48), is checked when on and disabled when the paragraph has no indent to remove (noIndent.ts:37). The class is cancelled by one rule (basePage-sharedRules.less:209, copied at basePage-legacy-5-6.less:129). Pressing Enter in a marked paragraph strips the class from the new half (BloomField.ts:280).

One deliberate subtlety worth remembering: the rule zeroes text-indent but leaves margin-left alone. A hanging indent is text-indent:-20pt plus margin-left:20pt, so a marked paragraph in a hanging style lines up with the wrapped lines of a hanging paragraph — which is what a continuation should do — while an ordinary first-line indent goes flush.

the whole feature

Everything above is static checking: unit tests over the logic, a stylesheet that compiles, a type check, and a code review. No one has actually right-clicked a paragraph in a running Bloom and watched the indent disappear. So the parts that only exist at runtime are unproven — whether the menu appears where you clicked, whether the check reads correctly, whether the indent visibly changes, and whether it survives a save-and-reopen.

Two things make this more than routine caution. The branch moved to Version6.4 mid-run, so this code now runs on React 17 through ReactDOM.render rather than the React 18 path it was written against. And the visible effect depends on a stylesheet that only gets rebuilt by a real build, not by the dev server.

Live verification

Format dialog on a text box that holds only a heading

StyleEditor.ts:1003 · from Devin, open thread

The heading commit means a text box no longer always contains a paragraph: a box that starts with a heading keeps just the heading. But the Format dialog works out which paragraph spacing and indent buttons to show by finding a paragraph in the box and reading its actual spacing and indent. With no paragraph to read, those values come back as nothing and the paragraph-spacing control ends up with no selection.

What the user sees: opening Format on a heading-only box shows a blank paragraph-spacing setting. Nothing is corrupted and nothing bad is written — if they pick a value it works normally. The comment sitting in that code already predicted this (“will be a problem if there are no paragraph boxes in the div. I don’t think this should happen”); this branch is what makes it happen. It only arises in converted books, which is exactly the material this card came from.

Heading-only boxes

Ctrl+Z will not undo a “No Indent” toggle

noIndent.ts:48 · from Devin, open thread

Toggling the command changes the paragraph directly rather than going through the text editor, so it is not on the editor’s undo stack. A user who sets No Indent and then presses ctrl+Z will see their previous typing undone instead, with the indent change left alone. Choosing the menu item again does reverse it, so nothing is stuck.

Devin also worried the toggle might be lost if Bloom skipped saving a page it thought unchanged. I traced that and it is not so: Bloom asks the browser for the page and applies whatever comes back, with no “was it modified?” gate — the dirty logic only chooses between saving the whole book and saving just the page. The class does get written.

The canvas element menu commands have lived with the same undo limitation for a long time, which is the argument for leaving it.

Undo

Recommended as-is because the command is its own undo, the existing canvas menus set the precedent, and the alternative adds real complexity for a rarely-used escape hatch.

For information

A determined custom stylesheet could still beat the rule

basePage-sharedRules.less:209 · from Devin, thread resolved

Devin caught that the original rule could lose to hand-written CSS in a book, which is now fixed: the selector requires the editable box as well, so it beats both what the Format dialog writes and the realistic custom-CSS shapes. This matters because basePage is deliberately loaded before a book’s custom stylesheets, so among equally specific rules the book’s own would win.

What remains is narrow: a custom rule crafted at least as specifically as ours would still win, and then “No Indent” would look enabled and do nothing. The only way to be immune is to write the style straight onto the paragraph instead of using a class, which trades a clean, greppable class for inline styling in saved books. Recorded rather than pursued.

Residual specificity risk

The open menu briefly alters the page document

TextContextMenu.tsx:41 · from Devin, open thread

While the menu is open, the MUI menu machinery stops the page scrolling and marks its siblings hidden from screen readers, undoing both on close. If a save happened during that window, the saved markup could pick up a stray hidden marker. In practice the first click lands on the menu’s own backdrop, so clicking away closes the menu rather than triggering a save. The canvas element menu already behaves this way, so this is not new here.
