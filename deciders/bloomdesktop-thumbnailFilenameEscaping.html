What the bug was

Bloom builds a separate miniature copy of each page for the strip down the left of the edit screen, and while building it rewrites every picture's address to add a ?thumbnail=1 marker so the server sends a shrunken image. That rewriting built the correctly-escaped address and then handed it to UrlPathString.CreateFromUnencodedString, which decodes anything containing %XX — undoing the escaping one line after doing it. Written out raw, the browser treated the # in the file name as the start of a fragment and asked for a truncated path:

**BloomServer: File Missing: C:/.../Image with Strange Characters/This Image !@

That line is from the log attached to the card, and it stops exactly at the #. The regression arrived with 5d34c530f9 (BL-16336), which added urlEncode: false; before that the re-encode on the way out happened to restore the escapes.

Which characters actually trigger it — the card asked. # every time; % when followed by two hex digits. The other showy characters in the reported name (! @ $ ^ & ( ) and spaces) are harmless on their own.

What changed this run

37453f58f5 — keep the src URL-encoded

Pass strictlyTreatAsEncoded: true so the string is neither decoded on the way in nor re-encoded on the way out — PageListApi.cs:405. Both flags are needed; each alone breaks the other case. Adds PageListApiTests, verified fix-sensitive: reverting the one line fails three of the tests with exactly the reported symptom.

cfe19be4d0 — hardening, prompted by Devin

Take the path from UrlEncodedForHttpPath rather than UrlEncoded — PageListApi.cs:380 — so a src that is genuinely a path keeps its separators usable. No shipped page content hits this today, so it is hardening rather than a second fix; it costs nothing because a Windows file name can contain neither / nor :.

Session notes

The full C# suite needed six runs to yield one trustworthy result, and the story matters because it nearly produced a false alarm. An early run failed HandleDoubleEncodedUrls, which sounded close enough to a URL-encoding change to be alarming. Reverting the change made it pass; that looked causal. It was not: running the same filter three times on the same code gave pass, pass, fail. The mechanism is visible at BloomServer.cs:2500 — GetFileSystemInfos(di.Name)[0] indexes without checking, so it throws whenever the directory enumeration misses a just-created file. It is inside a #if DEBUG case-checking diagnostic. See decision 2.

Later runs failed far more widely — 85, then 59 — always with FileNotFound / DirectoryNotFound on shared paths like %TEMP%\BookTests and %TEMP%\ePUB_export. Another session on this machine was running BloomTests at the same time, and the fixtures use fixed folder names, so the two runs delete each other's scratch directories. Waiting for a quiet window and retrying gave a clean 3037/3050 on the second attempt — same commit that had failed 59 tests minutes earlier. See decision 3.

None of this touched the change under review: every failure was in book-creation, epub or BloomReader-export fixtures, and the change is one line of string handling on an in-memory XML clone with no filesystem access at all.

Decisions

Five items. None of them block this PR — the fix itself is clean and reviewed.

1. A related alt-text bug I did not fix

When a picture fails to load, Bloom writes a message into the picture's alt text — the words a screen reader announces, and what shows in place of a missing image. It builds that message from the file name, but decodes the name with decodeURI, which by design leaves characters like @ # $ & still in their escaped form. So the reported book shows "This image, This Image !%40%23%24%^%26()2.jpg, is missing" — half-decoded gibberish where the file name should be.

It is cosmetic, it predates this regression, and it is in the main editing page rather than the page list, so it is outside what BL-16658 describes. I left it alone rather than widen the PR, but it is the same family of bug and you may want it swept up while the area is fresh. Note the naive one-word swap is not quite safe: decodeURIComponent throws on a name containing a bare %, such as 50%.jpg, so it needs a guard.

2. A flaky test that cost real time today

HandleDoubleEncodedUrls fails intermittently — roughly one run in three — because a debug-only helper indexes a directory listing without checking it found anything: di.Parent.GetFileSystemInfos(di.Name)[0] at BloomServer.cs:2500. When the enumeration hasn't caught up with a just-written file it throws IndexOutOfRangeException instead of reporting a case mismatch.

This is worth more than its size: because the test name mentions URL encoding, it read as a plausible regression from this very change and sent me down a false trail before repetition disproved it. The next person touching anything URL-shaped will lose the same time.

3. Two test runs on one machine destroy each other

The C# test fixtures use fixed, shared scratch folders under %TEMP% — BookTests, ePUB_export, BloomReaderExport. When a second BloomTests run starts, it wipes the first one's folders, and the first run collapses with dozens of unrelated-looking failures. Today that produced runs of 85 and 59 failures on code that passes cleanly, and it cost several full five-minute suites to untangle.

This will bite harder as more agent sessions run in parallel on one machine, and it is exactly the kind of failure that teaches people to shrug at red test runs. The agent-dotnet wrapper already isolates build output per terminal; the temp folders are the remaining shared resource.

Worth knowing before you decide: another session already has PR #8170 open (BL-16661) nesting the spreadsheet tests' temp folders so no test book sits directly in %TEMP%. That is a neighbouring symptom of the same root problem rather than the same fix — it does not address the fixed-name BookTests / ePUB_export / BloomReaderExport folders that two concurrent runs fight over — but it is the natural place to fold this in rather than open a competing card.

4. Your FEEDBACK setting does not stop Sentry

You asked whether we could detect a Sentry report that this bug would have sent. It sends none — a missing file only reaches Logger.WriteEvent at BloomServer.cs:2165, with no error report and deliberately not even a toast. But checking that turned up something more important.

Your machine has FEEDBACK=off. That gates the analytics client only (Program.cs:1162). Sentry is gated on something different — NonFatalProblem.cs:297 returns early only when IsDev, and IsDev is true only for a channel containing "developer". BloomAlpha's channel is Alpha, so Sentry is live there and your variable would not stop it. The neighbouring IsDevOrAlpha would have covered it. The card's own log shows an unrelated coverIsImage problem firing on that test book, so this is not hypothetical: reproducing on Alpha would send real events under your name.

5. CI never ran for this PR

GitHub registered no checks at all against either pushed commit, while other branches got pr-automation runs in the same window. Nothing was lost — that workflow only kicks off the Devin review and adds its link, and I did both manually — but a workflow that silently skips some PRs is worth knowing about, since the next PR may quietly get no Devin review at all.
