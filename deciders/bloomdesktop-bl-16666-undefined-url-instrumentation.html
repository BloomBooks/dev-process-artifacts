What this PR is about

Problem

Sentry has years of "Cannot Find File" reports for paths like Temp/undefined. The server can say that a file called undefined is missing, but never which part of Bloom asked for it, so these reports have been almost impossible to act on. Finding the one instance we did fix (BL-16447) took a lot of guessing.

Cause

The C# side isn't building a bad temp path. Front-end code does the equivalent of img.src = somethingUndefined, the browser turns the value into the text "undefined" and asks the server for a file by that name. The temp folder is incidental. The book-folder suppression had been hiding every instance that happened on a book page, so Sentry only ever showed a filtered slice.

What the PR does

This fixes no particular instance. It makes the next one name itself.

  • Server: a request whose path has a whole segment that is exactly undefined, null or NaN is treated as our own bug. It is no longer hidden by the book-folder suppression. It goes to Sentry silently (no toast or dialog on any channel) under its own message, naming the page that made the request (the Referer header, now passed through to the report) and the raw url.
  • Front end: a new detector, installed wherever Bloom's global error handler loads, watches src assignment, setAttribute("src"), fetch and XMLHttpRequest. It reports a source-mapped stack naming the offending line, then lets the call go ahead unchanged. It reports each call site once, at most ten per session. Alpha users see a small "A JavaScript error occurred" notice for each one, as you decided.

Expect more "Url built from a JavaScript value" reports in Sentry. That is the point.
