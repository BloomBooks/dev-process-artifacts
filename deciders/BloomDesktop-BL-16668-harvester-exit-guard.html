Why this fix, and why not the other one

Both branches fix the outage and carry the same test. This records why the small one is shipping.

The bug. A command-line verb never calls Application.Run, so the only WinForms message loop in the process belongs to a worker — the off-screen browser PublishHelper uses for page checks, created and disposed once per batch. Ending that loop made WinForms raise Application.ApplicationExit, ApplicationContainer believed it and disposed itself, and it is the parent scope of the ProjectContext still in use. The epub step ran next, asked for BookServer, and got ObjectDisposedException. The harvester treats any non-FontProblems exit code as failure, so the book was marked failed and nothing was uploaded — not even the .bloompub already built.

This fix gates the subscription on Program.RunningInConsoleMode, set for every command-line verb before any of them is dispatched. Two properties make it the right form of the cheap option rather than just the cheapest: it covers every verb, where the earlier RunningHarvesterMode draft left changeLayout, download and upload exposed; and it has no ordering hazard, because the flag is true before any container exists, whereas CreateArtifactsCommand sets the harvester flag after constructing one.

What it does not do, honestly: the false ApplicationExit is still raised in console mode. Nothing listens for it today — the only other subscribers are in ApplicationUpdateSupport (only after an update download, a GUI flow) and Edit/AudioRecording (editing only), neither reachable from a CLI verb — but a future CLI-reachable subscriber would silently reopen this bug. That is the residual risk you are accepting, and it is why #8177 exists.

#8177 stops the false signal being raised at all, by pumping that thread with a private Win32 loop, so nothing has to know to distrust it. It is the better end state and it is parked, not closed. It is bigger, it uses P/Invoke, and it turned out to need a second fix of its own: with no WinForms loop on that thread, Application.MessageLoop goes false, which sent the fatal-error handler down a hard-kill path that skips releasing Bloom’s single-instance token — meaning Bloom might not restart. Fixed there, but it widened the change. The two must not both land: with the pump in place, this guard is dead code.

Decision 1 · Devin, open thread

Should the guard also exempt unit-test runs?

Decided: leave as is. The guard stays on RunningInConsoleMode alone, so the regression test keeps proving the production predicate is wired correctly. Recorded on the PR thread, now resolved.

Devin observed that the guard exempts only Program.RunningInConsoleMode, so a test that builds an ApplicationContainer indirectly — through DownloadBookCommand, UploadCommand, ChangeLayoutCommand or SendFontAnalyticsCommand, all of which construct one — would still subscribe and could still be bitten mid-test. It suggests also exempting Program.RunningUnitTests, since neither mode has a GUI whose exit means anything.

Checked, and it is not reachable today: no test in the repo invokes any of those four commands, and none constructs an ApplicationContainer directly. The only test path that builds one is the fixture already covered.

I left it alone for a reason worth your judgement, because it is a genuine trade rather than an oversight. RunningInConsoleMode is the predicate production depends on. If the guard also honoured RunningUnitTests, the regression test would pass through the test-only exemption — and a future mistake in the production wiring, such as the flag being set too late, would stop failing anything. Today the test fails unless RunningInConsoleMode is genuinely true at container-construction time, which is the property most worth protecting.

Decision 3

A real fix is stranded on the parked branch

Decided: card opened. BL-16670 — Bug, Bloom 6.5, In Progress, assigned to Andrew, carrying the full analysis and the cherry-pick sha. A worktree BL-16670-crash-exit-path was created for it (it needs ./init.sh before it will build).

While reviewing #8177, Devin found that FatalExceptionHandler decides how Bloom dies by asking Application.MessageLoop, which is a per-thread flag. So it answers “does the thread this exception arrived on have a WinForms loop”, not “is there a GUI to shut down”. When the answer is no it calls Environment.Exit(1), which does not run finally blocks — including the one in Main that releases Bloom’s single-instance token, so Bloom may then refuse to reopen.

Asking a per-thread question there is wrong in principle regardless of this card. But it only becomes reachable when some thread pumps WinForms messages without Application.Run, and nothing in Bloom does that unless the pump change lands. So master is not broken today, and this PR does not make it so.

The fix — a Program.MainMessageLoopIsRunning flag consulted instead — exists only on the parked branch. Park that branch and the fix goes with it, along with the knowledge of why it was needed.

What to do about the stranded FatalExceptionHandler fix
recommended
Small in size, but it lands a change to Bloom’s global fatal-error path inside a harvester bug fix, for a problem not reachable without the pump change. Scope creep on a PR chosen for being narrow.

Recommending a card because the finding is real and independently useful, but genuinely does not belong in this PR — and if #8177 is parked or closed, a card is the only thing that keeps it from being lost. Choosing this also largely settles Decision 2, since the card can carry both.

Decision 4 · Devin, open thread · adjacent bug

An epub failure erases the other error codes the harvester was told about

Decided: fixed here. Now |=, in 4e57a679. Checked first, as asked, whether the plain assignment was deliberate — it was not: the commit that introduced it was titled “Fix incorrect exit codes…”, and the accumulating |= above it already existed at that moment, so it was never lossless. Thread resolved.

Found while checking a Devin note about cross-thread reads. In CreateArtifactsCommand.CreateArtifacts every step accumulates its result with |=, because these are [Flags] values — except the epub worker, which at CreateArtifactsCommand.cs:198 does a plain assignment.

So if an earlier step recorded BookHtmlNotFound (2), UnhandledException (1) or LegacyBookCannotHarvest (8) and the epub then throws, the process exits with just 4. GetErrorsFromExitCode reports only EpubException, and the harvester’s record loses the fact that the book’s HTML was also wrong. It is most likely to bite in exactly the configuration this card is about, since the harvester always asks for both artifacts.

Pre-existing, not introduced here, and it does not affect whether this fix is correct — on the fixed code no step sets a flag at all. It looks like a one-character change, but it alters the exit codes the harvester consumes and records, which is a contract rather than a tidy-up, so it did not go into a PR chosen for being narrow.

One character, and the accompanying comment. Cheap and obviously right in isolation, but it changes what the harvester records for a failed book, inside a PR whose whole argument is that it is minimal.

FYI 6 · affects master, not this branch

A test on master fails at random, depending on the process id

Turned up while chasing a suite failure here. SpreadsheetAudioImportTests.NoErrorForEmptyAudio asserts Has.None.Match(".*17.*") over its error messages, meaning “no error about page 17”. Base commit 67c1a788, “Give each test run its own temp directory”, now builds temp paths as $"{key}-p{Environment.ProcessId}", and those paths appear inside the error strings.

So the assertion matches the process id whenever it contains the digits 17 — which for a 4–6 digit Windows pid happens often. That is what failed here, in a run whose temp folder was …-p17428. It is on master, so it will fail randomly for everyone until fixed, and it looks like a one-line change: tighten the pattern to .*page 17.*.

Nothing to do with this branch. Written up on BL-16664, the card for the temp-directory change, which has been moved to Has Comments so its owner sees it.
