What this PR is about

Problem

Bloom's 6.5 features shipped essentially blind. All 41 existing analytics events came from C#, so anything built in React could only be measured by inventing a bespoke endpoint for it — which in practice meant it wasn't measured. Nothing under the Reading App Builder publish path reported anything at all, the AI Image Editor and the new image chooser reported nothing, and Change Picture — the one event covering how a picture gets into a book — was bypassed by both new 6.5 image routes, so it had been quietly under-counting.

Cause

A second problem made this risky to fix: DesktopAnalytics is constructed with allowTracking: false in DEBUG and acts on that inside its own Track method. So a new event was easy to write, easy to believe in, and impossible to observe without shipping it to alpha and waiting.

What the PR does

The test applied to every candidate was whether the answer would change a decision. Counting use of a capability we already know is essential does not; nor does measuring a step whose direction is settled. What does is data that splits a known behaviour into actionable parts.

  • Plumbing. A POST analytics/track endpoint and a trackEvent() helper, so front-end code can report an event at all; C# fills in the book id and the collection's branding, which React in the edit view doesn't know. BloomAnalytics wraps DesktopAnalytics and logs every event before handing it on — to the Bloom log always, and to stderr when tracking is off — so a developer running ./go.sh now watches events scroll past. All 53 call sites go through it, and build/check-csharp-analytics.sh keeps it that way.
  • Where pictures come from, and whether searches succeed. Result counts can't answer the real question: Pixabay and Openverse nearly always return some pictures, so the failure is a full page of wrong ones, and only what the user did next reveals it.
  • Whether the AI editor's funnel converts, and what it costs — open, generate, commit, cancel. A session that generates and then throws everything away is the clearest quality signal available.
  • Two heuristics we cannot otherwise evaluate — every explicit image-transparency override (a user telling us which way line-art detection failed), and custom cover layout, Pro-gated across two releases with no usage data, including the demand we refuse and why.
  • Whether the RAB publish path works on real machines — nothing else watches it, since CI never runs a real build. Plus metadata-apply duration on large books, and whether users correct the reading direction ethnolib chose from their script.

Deliberately excluded: program errors (Sentry's job, not Segment's) and AI prompt text, which can carry arbitrary content lifted from the book. Image-search terms are included on purpose — which Devin has now asked you to sign off on explicitly; that is decision 3.

Two properties the reviewers had to teach this PR, both worth stating because each was violated more than once.

  • Recording an event cannot affect what it is observing. Reporting is now isolated at every boundary it crosses. The worst of the four cases found would have turned a successful, already-paid-for AI generation into a reported failure and lost the image.
  • An event describes what happened, not what was about to happen. Four events were sent at the moment a decision was made rather than the moment it took effect, so a user who backed out was counted as though they had not. Three of the four were fixed in this run; the fourth is decision 2.

2. The AI commit's "applied" count, explained properly this time

You asked to understand this before deciding. Here it is from the top, and a second pass through the code made it worse than I first described.

Who does what. One commit can replace pictures on several pages. For pictures on other pages, C# does the whole job and knows it worked. For a picture on the page you have open, C# cannot touch it — the live page belongs to the browser — so C# only prepares it and hands it back for the browser to swap in. C# sends the event at the end of its own work and counts a prepared picture as applied. The browser then attempts the swap, and it can fail: that is the code path behind "Only 0 of 1 image(s) on the current page could be updated."

Why it is not an edge case. The picture you right-clicked to open the AI editor is, by definition, on the page you have open. So the ordinary journey — edit one picture, use it — is a commit with exactly one replacement, always a current-page one. For that journey the count is always "1 applied, 0 failed", whatever happened. The event exists because BL-16702 was a commit that silently did nothing; in its commonest case it cannot report that.

What I had not spotted before: the per-picture Change Picture events are emitted from the same number, so a failed swap also adds a picture to the "where do pictures come from" breakdown that never entered the book — one of the main things this PR is for. Devin has since raised that half as a bug in its own right, on its own thread, which stays open because the same code move settles both.

What moving it involves. I checked that every property is already available on the browser side: the replacement list it sent carries what generatedCount and reusedCount are counted from, C#'s per-slot results cover the off-page ones, the page frame reports the current-page ones, and the endpoint fills in book id and branding. So nothing new crosses the boundary — the block simply moves from AiImageEditorApi.HandleCommit to the place in aiEditorOverlay.ts that already knows the outcome. About 30 lines; the tests move from C# to vitest. One genuine cost: if the commit's reply never arrives, C# has already sent its event today, whereas the browser version would need to report from its error path too.

The full write-up is on the thread. The companion question — that one commit sends a summary plus one Change Picture per picture — is explained on its own thread and needs no code change: it is deliberate, and the only risk is an analyst adding the two together.

Moderate — about 30 lines across the C#/JavaScript boundary, plus moving its tests. Recommended more strongly than last time: the common case is exactly the broken one, and the same number is also feeding the picture-source breakdown.
A few lines. Honest about what the number is, but leaves the question the event was added for unanswered — and does nothing about the phantom Change Picture events.

3. Search terms leave the machine — Devin wants that signed off by a person

Devin raised this from a note to something it wants a human to own: Image Search carries the term the user typed, and Image Chooser Closed carries the one they accepted on. It is the only place in this work where free-form user text goes to Segment.

It is deliberate, and I still think it is right. The term is what makes the rest of the search data mean anything: without it we can see that someone searched five times and accepted nothing, but not whether the gap is in our art collection or in their spelling. A term repeatedly searched and never accepted is a concrete instruction about what to commission.

What makes it different from AI prompt text — which is excluded by name, via the allow-list that lets the editor send only known properties of known events — is that these are one- or two-word queries typed into a search box for a public art library, of the same kind the user is simultaneously sending to Pixabay. Prompts routinely contain sentences lifted out of the book being written.

It is already in the tester's "known and deliberate" list so nobody files it as a leak. But you are the right person to say yes to it, so:

No work. Recommended because the term is the property that makes the search data actionable, and it is the same text the user is already sending to a public image service.
A line in one place. Keeps ordinary queries intact while capping the worst case of someone pasting a sentence into the search box.
A line in one place, and it costs the main thing these events were added to learn.
