What this PR is about

Problem

Bloom's 6.5 features shipped essentially blind. All 41 existing analytics events came from C#, so anything built in React could only be measured by inventing a bespoke endpoint for it — which in practice meant it wasn't measured. Nothing under the Reading App Builder publish path reported anything at all, the AI Image Editor and the new image chooser reported nothing, and Change Picture — the one event covering how a picture gets into a book — was bypassed by both new 6.5 image routes, so it had been quietly under-counting.

Cause

A second problem made this risky to fix: DesktopAnalytics is constructed with allowTracking: false in DEBUG and acts on that inside its own Track method. So a new event was easy to write, easy to believe in, and impossible to observe without shipping it to alpha and waiting.

What the PR does

The test applied to every candidate was whether the answer would change a decision. Counting use of a capability we already know is essential does not; nor does measuring a step whose direction is settled. What does is data that splits a known behaviour into actionable parts.

  • Plumbing. A POST analytics/track endpoint and a trackEvent() helper, so front-end code can report an event at all; C# fills in the book id and the collection's branding, which React in the edit view doesn't know. BloomAnalytics wraps DesktopAnalytics and logs every event before handing it on — to the Bloom log always, and to stderr when tracking is off — so a developer running ./go.sh now watches events scroll past. All 53 call sites go through it, and build/check-csharp-analytics.sh keeps it that way.
  • Where pictures come from, and whether searches succeed. Result counts can't answer the real question: Pixabay and Openverse nearly always return some pictures, so the failure is a full page of wrong ones, and only what the user did next reveals it.
  • Whether the AI editor's funnel converts, and what it costs — open, generate, commit, cancel. A session that generates and then throws everything away is the clearest quality signal available.
  • Two heuristics we cannot otherwise evaluate — every explicit image-transparency override (a user telling us which way line-art detection failed), and custom cover layout, Pro-gated across two releases with no usage data, including the demand we refuse and why.
  • Whether the RAB publish path works on real machines — nothing else watches it, since CI never runs a real build. Plus metadata-apply duration on large books, and whether users correct the reading direction ethnolib chose from their script.

No free-form user text is collected. Program errors go to Sentry, not Segment. AI prompt text is not among the properties the ai-editor sends, since it carries sentences lifted out of the book. And image-search terms are dropped at Bloom's boundary: an earlier round of this branch did send them and we were then asked not to, so a search is recorded as "someone searched Pixabay in English and got 20 results" with no record of the subject. The gallery still hands the term to Bloom, so re-enabling would be one property here and no change there.

Two things that costs us, stated because nobody should expect them later: we cannot see which subjects people search for and never find — the original argument for collecting the term — and searchCount now counts queries with no way to tell one idea tried in three languages from three different ideas. That second one reverses the reasoning behind an earlier decision on this branch, which is worth knowing if the numbers are ever read closely.

Three properties the reviewers had to teach this PR, each violated more than once.

  • Recording an event cannot affect what it is observing. Reporting is isolated at every boundary it crosses. The worst of the four cases found would have turned a successful, already-paid-for AI generation into a reported failure and lost the image.
  • An event describes what happened, not what was about to happen. Six events were sent at the moment a decision was made rather than the moment it took effect, so a user who backed out was counted as though they had not. All six are fixed.
  • An event must not be able to describe one thing as two. Five separate ways a single AI editing session could appear in both the "committed" and the "thrown away" figures — or twice in one of them — were found and closed, mostly in this run.

What changed this run

You asked for the AI commit's reporting to move to TypeScript, and for the merged dependencies to go in. Both are done. The move then set off the longest review chain of the branch: eight more commits, every one from a Devin finding, and every one real.

  • Both dependencies are now real, and the AI editor's generation events can finally arrive. #2 was merged after the run above, so dist-v0.1.4 is published and Bloom is pinned to it instead of dist-v0.1.3, which predated the editor's own reporting. That was the last thing blocking merge. The blockage itself was my omission: that repository asks for the semver bump to be committed in the PR, mine carried no changeset, so master stayed at 0.1.3 and the publish workflow — which names the tag from package.json and refuses to overwrite — would have declined to produce anything. Adding the changeset and bumping was the whole remaining step; no editor code changed. Verified beyond "the pin resolves": the installed build is 0.1.4, its bundle contains AI Editor Generate, and the tag records the merged commit as its source. 1f13940
  • The AI commit now reports from the browser, where the outcome is actually known. C# could only ever report an intention: for a slot on the page the user has open it stages the replacement and hands the swap to the browser, so a staged slot counted as applied — and since the picture you right-clicked is by definition on the page you have open, a single-picture commit was always reported as "1 applied, 0 failed" whatever became of it. The per-picture Change Picture events came off the same number, so a failed swap also added a picture to the picture-source breakdown that never entered the book. Both now count only pictures that reached the book, and a commit whose request fails outright reports nothing applied — a case C# could not report at all.
  • The image-gallery pin is off. #20 is merged, so the dependency tracks that repository's default branch again and resolves to the merge commit (0.0.4). The lockfile was regenerated by pnpm install rather than hand-edited, and now differs from master only in the gallery's own entries.
  • Then five rounds of concurrency findings in the AI editor, each visible only once the previous was fixed: a partly-successful commit counted as thrown away as well as committed; a commit reported twice when the reply path threw; an in-flight flag that a second overlapping commit could clear too early; a double decrement of the count that replaced it — a defect I introduced — which could leave a session permanently unreportable; and finally the first of two overlapping replies deciding the cancel before the second had landed its picture. The rule now lives in one place: removing it fails four tests instead of one.
  • And two that have nothing to do with analytics. Devin found, at "severe", that applying image credits to a whole book re-reads the embedded metadata of every picture once per picture — a lazy iterator asked for its Count() inside the loop. On a 400-picture book that is roughly 160,000 metadata reads instead of 400, and it appears frozen for minutes. There is a second fault in the same line that Devin did not mention: the loop writes metadata into those files as it goes and the re-enumeration re-decides which to include, so the number being divided by could shift underneath it. One ToList(). Separately, a property value that parses as a date-time was being recorded in the local culture's format ("1/1/2024 10:00:00 AM") instead of as sent, which matters because some of these values are free user text.
  • Two smaller labelling fixes: a refused cover layout could be blamed on the wrong cause while the subscription lookup was still in flight (and that split is the event's entire value), and changing a GIF was filed as an image-chooser pick from an "unknown" provider when it is really a pick from disk.

Worth knowing

  • Still not one event has been seen reaching Segment, and now one more gap worth naming precisely: with the new editor build in place, AI Editor Generate should arrive over the bridge, but you chose automated verification only, so nobody has driven the editor and watched it appear. Everything short of that is checked — the build carries the event, Bloom's event-name check admits it, the suites pass — but the last hop is unobserved. It is first on the tester's list.
  • The AI editor is where by-hand testing should go. Nine of this run's commits touch the code that puts AI pictures into books, and the tester's notes lead with it: closing the editor mid-save, and committing to several pages at once.
  • Two small things I left deliberately, so you can judge them rather than find them. When applying credits to a whole book aborts on a permissions error, the duration event still fires with imageCount=0 — indistinguishable from a book with no eligible pictures; fixing it means changing what that method returns so the caller can tell the two apart. And commitsInFlight is incremented just outside the try, so a synchronous throw from postJson would leave it stuck above zero and that session could never be reported as abandoned — a one-line move, in code I wrote, that Devin raised as informational on the last pass. Neither is urgent; both are quick if you want them.
  • Devin's other informational notes I read and did not act on: the generation count includes failed generations (which is what "how much AI work was thrown away" wants), an unset third language slot captures no reading-direction baseline (so it reports nothing, correctly), the transparency-choice map is module-level and never shrinks (bounded by pictures visited in one run), and the stderr echo of events happens in DEBUG but not alpha builds.

Two things reading the code changed

Not bugs; both from John reading the AI-editor overlay after the run above.

  • "Editor" now says "ai-editor". A bare "the editor" in that file reads as Bloom's Edit tab to anyone who works on Bloom, however dedicated the file is to the other one. The comments say ai-editor wherever the AI image editor is meant; "the page being edited" and the page frame are untouched, because those really are about the editing view.
  • The property allow-list is gone. It filtered the properties the ai-editor sends, and its stated purpose was keeping prompt text out — but we control both ends of that channel, so it was guarding us against ourselves, which is exactly what AGENTS.md says not to do. If something specific must not be forwarded, it is stopped in the ai-editor or removed by name here. I checked the merged ai-editor rather than assuming: it sends only ids, enums, numbers and booleans. The event-name check stays, as a Set, because an unrecognized name would create a new event type in our data rather than land in an existing one — a different concern from filtering properties. cb75b9d
