What this PR is about

Problem

Bloom's 6.5 features shipped essentially blind. All 41 existing analytics events came from C#, so anything built in React could only be measured by inventing a bespoke endpoint for it — which in practice meant it wasn't measured. Nothing under the Reading App Builder publish path reported anything at all, the AI Image Editor and the new image chooser reported nothing, and Change Picture — the one event covering how a picture gets into a book — was bypassed by both new 6.5 image routes, so it had been quietly under-counting.

Cause

A second problem made this risky to fix: DesktopAnalytics is constructed with allowTracking: false in DEBUG and acts on that inside its own Track method. So a new event was easy to write, easy to believe in, and impossible to observe without shipping it to alpha and waiting.

What the PR does

The test applied to every candidate was whether the answer would change a decision. Counting use of a capability we already know is essential does not; nor does measuring a step whose direction is settled. What does is data that splits a known behaviour into actionable parts.

  • Plumbing. A POST analytics/track endpoint and a trackEvent() helper, so front-end code can report an event at all; C# fills in the book id and the collection's branding, which React in the edit view doesn't know. BloomAnalytics wraps DesktopAnalytics and logs every event before handing it on — to the Bloom log always, and to stderr when tracking is off — so a developer running ./go.sh now watches events scroll past. All 53 call sites go through it, and a pre-commit check keeps it that way, because a partial log would be worse than none.
  • Where pictures come from, and whether searches succeed. Search terms, the source they went to, and what the user did next; the Pixabay API-key obstacle; and Change Picture with a source and provider from all four routes, repairing the under-count on the way past. Result counts can't answer the real question: the online sources nearly always return some pictures, so the failure is a full page of wrong ones, and only what the user did next reveals it.
  • Whether the AI editor's funnel converts, and what it costs — open, generate, commit, cancel, key-saved. A session that generates and then throws everything away is the clearest quality signal available.
  • Two things we cannot otherwise evaluate — every explicit image-transparency override, each of which is a user telling us which way our line-art detection failed; and custom cover layout, a Pro-gated feature that has shipped two releases with no usage data, including the demand we refuse and why.
  • Whether the RAB publish path works on real machines, which nothing else watches, since CI never runs a real app build. Plus metadata-apply duration on large books, and whether users correct the reading direction ethnolib chose from their script.
  • Analytics cannot affect what it observes. Reporting is isolated from the code it measures at every boundary — the C# wrapper, the front-end helper, the App Builder reporter, and both package callbacks. This is stated as a property of the PR because reviewers found four places where it was not true, one of which would have lost a generation the user had already paid for.

Deliberately excluded: program errors (Sentry's job, not Segment's) and AI prompt text, which can carry arbitrary content lifted from the book. Image-search terms are included on purpose.

1. The gallery dependency pin must be undone before Bloom merges

Bloom's src/BloomBrowserUI/package.json currently points at github:BloomBooks/bloom-image-gallery#BL-16716-analytics-hooks — a branch, on your instruction, so that this PR's CI can resolve the new ISearchReport interface, which does not exist on master yet.

If Bloom merges in that state, its dependency points at a branch that will be deleted, and the build breaks for everyone. So gallery #20 has to land first, and the pin has to go back to tracking master with a pnpm install to refresh the lockfile. Devin flagged this independently of my own note, and its thread is open.

Two lines plus a lockfile refresh, but it has to happen after #20 merges — so it needs a second short preflight rather than being doable now. Recommended because it leaves nothing for anyone to remember at merge time.
No work now. Relies on the PR description, the card and an open review thread all being read at the right moment.

2. No AI-editor generate events until a new editor build is published

Bloom pins bloom-ai-image-tools at #dist-v0.1.3, which predates the generate reporting added in #2. Everything else about the AI editor's analytics works with the old pin — opening, committing, cancelling and the key are all reported by Bloom's own C# — but the per-generation event, the one that carries the model, the cost and the attempt number, will simply never fire.

This is not something the PR can fix. That package cannot be consumed from a branch (the branch holds no built app, and Bloom cannot build it on install), so delivery is an immutable dist-v* tag produced by a manually-dispatched workflow in that repo, which is refused if the version hasn't been bumped first.

A changeset version bump and one workflow_dispatch in that repo, then a one-line pin change here. Recommended because the generate event is the one that carries the cost figures, which is most of why the AI editor was worth instrumenting.
No work. The funnel reports open/commit/cancel from day one and gains generation data whenever the tag lands.

3. The image chooser's picture count disappears when you scroll

In the image chooser, the "N images" figure beside the search box vanishes as soon as the user scrolls far enough to load a second page of results. Devin found it; it is pre-existing, not something this work introduced — the code that appends a page has always rebuilt the result without carrying the total forward.

It surfaced now because this PR changes that very line, and the fix is one word: spread the previous result, exactly as the neighbouring error branch already does. I held off because it changes what a user sees and has nothing to do with analytics, which is your call rather than mine.

One word, in a line this PR already touches; no new risk beyond the count reappearing. Recommended because otherwise every future reviewer of that file finds it again, as this one did.
Keeps #20 strictly about the analytics interface. Costs a card and a second round trip through review for a one-word change.

4. Should changing the search language count as a new search?

In the image chooser, changing the language dropdown re-runs the search with the same term. Bloom records that as another Image Search event, so a person who types "dog" and then tries three languages produces four searches for one idea.

I have left it counting, because it genuinely is another search — the source is queried again and returns different pictures — and because the event carries the language and its position in the visit, so anyone analysing it can separate the cases. But if you expect "searches per visit" to mean "distinct things someone looked for", the number will read high, and that is a decision about what BL-16716 is measuring rather than something I should settle.

Small and local in the gallery, but it loses the ability to see that someone tried several languages for one term — which is itself a signal about the art we can reach.

5. The AI editor's commit count can be optimistic, and reports twice

Two related things about AI Editor Commit, both raised by Devin.

First, its appliedCount counts pictures on the page currently being edited as applied once C# has staged them — but the browser does the real swap afterwards, and that can fail. So the count can overstate, in precisely the "the commit silently did nothing" case the event exists to catch. Reporting it honestly means emitting the event from the browser once the outcome is known, which moves it across the C#/JavaScript boundary.

Second, a commit of twenty pictures produces twenty-one events: the summary plus one Change Picture each. That is deliberate — it is what makes the picture-source breakdown cover every route — but anything joining the two would double-count unless it knows to pick one.

Moderate — the event moves from C# to the overlay and appliedCount changes meaning. Recommended because a number that overstates success in exactly the failure case it was added to detect is worse than no number.
A few lines. Honest about what the number is, without giving you the answer you actually wanted.

6. Clicking the cover layout you are already on switches you off it

I found this while reviewing, and it is not caused by this work. On a cover page, the Standard/Custom menu shows a tick beside the current choice — but clicking that ticked option toggles you to the other one, because the underlying request is a plain toggle and nothing checks whether the user picked what they already had.

It matters here only because the new event reports what actually happened, so a "standard" event can come from someone who clicked Custom. There is a comment in the code saying so, and the number is correct about the change; it is the menu that is surprising.

No code here. Recommended because it is a real user-facing bug that predates this work, and folding a behaviour change into an analytics PR is how a reviewer loses track of what they are approving.
Small — ignore a selection that matches the current layout. But it changes user-facing behaviour in a PR that otherwise changes none.

No product code; costs real time, perhaps 30–40 minutes of runs, with no guarantee of reproducing it.
