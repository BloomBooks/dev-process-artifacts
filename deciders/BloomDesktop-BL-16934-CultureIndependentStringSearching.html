Decisions

1. The Thai HTML-discovery test cannot fail

The commit before this run added FindBookHtmlInFolder_ThaiNamedBook_ChoosesTheHtmFile. It builds a folder named in Thai holding นิทาน.htm plus the decoys นิทาน.htm.bak, นิทาน.htmbak and notes.txt, sets the running culture to Thai, and checks that Bloom still picks the real .htm file. It was added because the code that finds a book's HTML file is one of the places this branch changed, and a reviewer asked for a test of it under Thai.

It passes either way. We reverted the comparisons on that code path to the old culture-sensitive form and ran the test again: still green. The reason is a genuine difference between the APIs, and it is already written down on this card. The Thai bug is that IndexOf reports a false match when the thing being searched for is all punctuation. EndsWith and StartsWith are backed by different ICU calls, which do not behave that way, so under Thai they answer exactly as they would ordinally. The file-discovery code uses EndsWith and StartsWith, so no arrangement of realistic file names can make it behave differently. (The review suggested a decoy ending in a bare htm with no dot; we measured it, and that does not distinguish them either. The only strings that do distinguish them end in an invisible character such as a soft hyphen, which is not a Thai issue and is not a realistic file name.)

So this is not a broken test — it is real, if modest, coverage that a Thai-named book is still found, and it costs nothing to run. The problem was only that sitting in a file about the Thai bug, it looks like a guard against regressing that fix, and it is not. We have added a comment on the test saying exactly that, and pointing at the IndexOf tests above it, which do fail when the fix is removed. That is why leaving it in place is the recommendation.

Notes

3. Two nearby problems, recorded but not fixed

While the Thai behaviour was being measured for this card, two separate defects turned up in code this branch touches. Both are written up in a comment on BL-16934 and neither is fixed here, because both are behaviour changes rather than the mechanical, no-behaviour-change edit this branch is.

The first is in the comparer that puts books in order in the Collection tab. It decides whether two chunks of a name are equal letter-by-letter, but decides which one comes first using the user's language rules. Under Thai those two disagree, so the ordering is not self-consistent: over a sample of 60 names there were 12,672 name triples where A equals B, B equals C, but A sorts before C. In practice that means books can appear in an unpredictable order for Thai users, with a small risk of .NET throwing on the inconsistent comparer. This branch made the existing behaviour explicit rather than changing it, so the inconsistency is still there.

The second is that a book's content hash is computed over file paths put in the user's language order under a comment saying the order must be predictable. Two machines in different regions can therefore compute different hashes for the same book.

Both are already recorded where the next person will find them, which is why leaving them is the recommendation; the alternative is to give each its own card so it can be scheduled rather than living in a comment thread.
