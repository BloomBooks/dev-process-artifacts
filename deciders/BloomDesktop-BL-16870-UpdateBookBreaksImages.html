What changed this run

This run: e42dd28 Repair pages saved mid-conversion, and refuse an off-screen capture while one is pending, implementing decisions 1 and 4 from the first run. Seven files.

  • Repair on page load (decision 1). A page saved by an early 6.5 Update Book with the old picture still in the canvas next to a background element saved visibility: hidden is now repaired the moment it is shown in the Edit tab: repairInterruptedBackgroundConversion shows the element and removes the stray picture. A converted canvas's obsolete placeholder picture is left alone. Two new Vitest cases.
  • Off-screen capture refuses to save a pending conversion (decision 4). captureContentForExternalProcessing now waits up to 20 seconds (was 4) and, if the conversion is still pending at the cap, returns an error so ProcessBook fails the page and the whole all-or-nothing run. Other pending work still captures as before; the live editor's 4-second cap is unchanged. The policy is a small tested module, pageContentCapturePolicy.ts; the C# poll timeout rose to 60 seconds to stay above the browser's cap.

First run: 8e00983 Run Update Book's per-page pass off-screen so it can't save a half-converted image. Ten files.

  • Why it broke. Since BL-16595 (6.5 only), Update Book visited every page in the live Edit tab and saved each the instant its DOM loaded. On a page whose picture was still in the pre-6.3 form, that save could land mid-way through the browser's conversion of the picture to a background canvas element, saving both the old picture and a hidden new element. Cropping then moved nothing visible and Delete removed only the hidden element.
  • Update Book now runs BookProcessor.ProcessBook, the off-screen per-page fix-up BloomBridge uses. Its capture waits for the page's async work and is all-or-nothing. The live-editor page walk in EditingModel is removed. See CollectionModel.cs:732.
  • The conversion itself is hardened: CanvasElementBackgroundImageManager.ts:218 holds a page-content delay across the cleanup, so any save requested mid-conversion waits. A new Vitest reproduces the original bug and verifies the fix.
  • Progress is shown in the collection tab's React progress dialog with a percent bar, replacing the WinForms dialog that clipped its status line. ProcessBook takes an optional IProgress, WebProgressAdapter forwards percent, and DoWorkWithProgressDialogAsync gained a determinate option.

5. Devin: the live Edit-tab save still gives up after 4 seconds FYI, thread closed

Source: Devin round 2, non-severe, thread. Devin's comment (verbatim): "When conversion exceeds four seconds, wrapWithRequestPageContentDelay still permits a mid-conversion live save. requestPageContent captures at its timeout regardless of remaining delays. The saved page retains the old image beside a hidden replacement, recreating the crop and delete failure."

Assessment: True, and it is the part of decision 4 you chose to leave alone: the off-screen capture got the longer wait and the refuse-to-capture rule, while the live editor kept its 4-second cap so a save can never be left waiting on an image that may never load (BL-16776). The exposure needs a save within 4 seconds of a page appearing on a picture still loading after 4 seconds, and as of this commit such a page is repaired the next time it is shown, so it can no longer leave an uncroppable picture. The thread records this and is resolved.

6. Devin: after a failed run, processed pages stay in memory FYI, thread closed

Source: Devin round 2, non-severe, thread. Devin's comment (verbatim): "After a later page fails, doWhenDialogCloses reselects the mutated b. ProcessOnePage has already merged earlier captures into that instance before the final save. A later save can persist a half-processed book despite the all-or-nothing contract."

Assessment: Not an issue. The contract is about what the failed run writes, and it holds: nothing from the page pass reaches disk. In memory, each page is either fully processed or untouched; the failing page is never merged. That mixed state is what Bloom produces every day when a user opens some pages of an older book in the Edit tab and not others. A later edit-and-save writes for those pages exactly what a successful run would have. Reloading from disk would throw away valid work. The thread records this and is resolved.
