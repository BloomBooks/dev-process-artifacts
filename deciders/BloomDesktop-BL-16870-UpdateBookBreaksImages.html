What changed this run

One commit, 8e00983 Run Update Book's per-page pass off-screen so it can't save a half-converted image. Ten files.

  • Why it broke. Since BL-16595 (6.5 only), Update Book visited every page in the live Edit tab and saved each the instant its DOM loaded. On a page whose picture was still in the pre-6.3 form, that save could land mid-way through the browser's conversion of the picture to a background canvas element, saving both the old picture and a hidden new element. Cropping then moved nothing visible and Delete removed only the hidden element.
  • Update Book now runs BookProcessor.ProcessBook, the off-screen per-page fix-up BloomBridge uses. Its capture waits for the page's async work and is all-or-nothing. The live-editor page walk in EditingModel is removed. See CollectionModel.cs:732.
  • The conversion itself is hardened: CanvasElementBackgroundImageManager.ts:218 holds a page-content delay across the cleanup, so any save requested mid-conversion waits. A new Vitest reproduces the original bug and verifies the fix.
  • Progress is shown in the collection tab's React progress dialog with a percent bar, replacing the WinForms dialog that clipped its status line. ProcessBook takes an optional IProgress, WebProgressAdapter forwards percent, and DoWorkWithProgressDialogAsync gained a determinate option.

1. Books already damaged by the old Update Book are not repaired decision

Anyone who ran Update Book on an older book with an earlier 6.5 beta may already have pages carrying two copies of a picture: a visible old-style one and a hidden background canvas element with visibility: hidden saved on it. This commit stops new damage but does nothing for those pages. When such a page opens in the Edit tab, the conversion code sees a background element already present and leaves everything alone, so the picture still cannot be cropped or deleted. A stray old-style picture beside a background element that is saved hidden is a signature that nothing else in Bloom produces, so a targeted repair on page load is safe to recognise: unhide the element and remove the stray picture.

2. The spinner shows alongside the percent bar FYI

The embedded progress dialog decides at mount time whether to show its title-bar spinner, before it knows the dialog will be opened in percent mode. So during Update Book you see both the spinner and the percent bar until the work finishes. It is purely visual, and the developer saw this version of the dialog when verifying the fix. The same applies to any future caller that asks for the percent bar.

3. The percent bar can run to 100 twice FYI

If the whole-book update has to shrink oversized images first, that step drives the same percent indicator from 0 to 100 on its own. The per-page pass then starts the bar again from 0. A tester would see the bar fill, jump back, and fill again. This only happens for books with oversized images, and the messages beneath the bar make it clear what is going on.

4. Devin: a very slow image can still be saved half-converted decision, thread open

Source: Devin, non-severe bug, mirrored as this inline thread on CanvasElementBackgroundImageManager.ts:218.

Devin's comment (verbatim): "After four seconds, captureContentForExternalProcessing captures while the outer delay remains active. Its timeout preserves the old image beside the hidden canvas element, breaking crop and delete." Its suggested fix: "Make external capture fail instead of serializing while conversion delays remain, or extend its timeout and verify activeDelays is empty before capture. Add a test that advances beyond kMaxWaitTimeMs while the conversion remains pending."

Assessment: Correct, and already known: it is the "shared weakness" noted in chat before this change was made. Both save paths stop waiting after kMaxWaitTimeMs (4 seconds) and capture anyway. The new delay makes a save wait for the conversion, but only within that cap, so an image that takes more than 4 seconds to load (a slow network drive, a huge file) could still be saved with the old picture next to a hidden background element. Before this change the same case was broken with any timing; now it needs a genuinely slow image. There is no cost-free fix: waiting forever risks a save that never completes if an image never loads, and failing a live save is what BL-16776 fixed.
