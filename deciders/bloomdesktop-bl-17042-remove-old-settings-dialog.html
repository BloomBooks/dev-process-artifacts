What this PR is about

Problem

Every page of the React Collection Settings dialog has landed, but the old WinForms dialog was still there behind an "Old Settings" button, with its own save path, its own settings/* endpoints and its own copies of the language chooser and several panels. Two save paths meant every rule had to be fixed twice, and the old one kept code alive that nothing else needed.

What the PR does

  • Removes the old dialog and everything only it used: both WinForms dialogs, the Old Settings button, the four React tab bundles, the old settings/* endpoints and SubscriptionSettingsEditorApi, the old Create Team Collection path, and a startup check that could never fire. Every rule of the old OK handler is in the new save path, except the dead "experimental book sources" option.
  • The language chooser only runs in the browser. The Publish tab's sign-language link, its last WinForms user, opens it itself and saves with one POST.
  • Simplifies the new dialog: it loads its settings before it shows and is rebuilt on every open; a non-administrator gets a small dialog of its own; the Create Team Collection dialog gets its folder and name from the dialog; the posted languages and fonts go straight into the collection's list instead of through copies; one component draws a settings row with its subscription badge.
  • Strings and docs: ten strings nothing uses are marked obsolete (none deleted); the plan doc is removed; e2e docs, the run-bloom skill and the branding-report tool no longer describe or call the old dialog.

Decisions

An e2e test for the Publish tab's sign-language chooser

Choosing a sign language from the Publish tab's tooltip link now opens the browser language chooser and saves with one POST. Nothing automated covers it. A test is easy now: the e2e suite already ships a one-second video (fixtures/videos/short.mp4) and chooseVideoFile, which puts it in a video box through the Sign Language tool's real Import path. A throwaway version of this test ran green in about 20 seconds this session.

The proposed spec, src/BloomE2E/tests/publish-sign-language.spec.ts:

  • make a Basic Book, add a "Video Over Text" page, put the short video in it;
  • on Publish > BloomPUB, hover Sign Language, click the link, search "American Sign Language", pick ase, OK;
  • check: the tooltip names it, the Sign Language checkbox is ticked, the .bloomCollection has SignLanguageIso639Code ase, and Settings' Languages page shows "American Sign Language (ase)";
  • open it again, pick another, Cancel: nothing changes.

It would need a small helpers/publish.ts addition (open the sign-language chooser) and a language-chooser helper (search, pick by code, OK/Cancel) that the Languages-page specs could reuse. Note that the e2e fixture's collections start with "English" as their sign language (see the last question), so the test starts from a language already set.

Collections with no sign-language entry read it as English

Found during the live check; old behavior, not from this PR. When a .bloomCollection file has no SignLanguageIso639Code, Bloom reads the sign language as English ("en"): WritingSystem.ReadFromXml defaults any missing language tag to "en". The Publish tab then says the book's videos contain English, the Sign Language feature is on, and Settings would show English as the sign language. The e2e fixture's collection files are written this way. Collections Bloom itself saves always carry the element, so it matters for older or hand-made files.
