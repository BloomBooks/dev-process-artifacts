What this PR is about

Problem

Users on Bloom 6.3 and 6.4 get "access denied" when Bloom refreshes small pictures in a book folder (license.png, thumbnail.png, branding logos, the QR code). The file's owner is the user, ReadOnly is off and the permissions allow writing, so our existing diagnostic explained nothing. A failed QR code write also stopped the book from being selected at all.

Cause (suspected, not confirmed)

Every report of this kind so far (BL-16507, BL-16915, BL-16919) had Avast running with real-time protection on and the book under Documents, which Avast's Ransomware Shield protects by default. Bloom itself is not at fault: within one book update it overwrites these files in place and never deletes and recreates them.

What the PR does

  • When any file write is refused, the error report now also records whether the file exists (telling "missing" from "hidden from Bloom"), its and its folder's attributes, its cloud placeholder state, whether it can be opened for reading, which sync provider owns the folder (from the Windows Cloud Files API), Defender's Controlled Folder Access setting, which antivirus products have real-time protection on, and whether the file is under Documents. All of it only reads and never throws.
  • The notice names a likely cause only when that evidence supports one: Controlled Folder Access on; Avast active with the book under Documents; or a sync provider or cloud placeholder.
  • A failed QR code write is now a nonfatal notice, so the book still opens. The badge keeps pointing at the QR code file: the old picture if there is one, or a broken image if not, which makes the problem visible.
