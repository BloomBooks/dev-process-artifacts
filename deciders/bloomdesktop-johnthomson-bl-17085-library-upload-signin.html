What this PR is about

Problem

A user who had been signed in to Bloom Library for a long time could no longer upload. Every attempt stopped at "Unable to check for existing copy on server. Please try again in a minute or two." Trying again never helped, and Bloom still showed them as signed in.

Cause

Bloom saves the sign-in's session token and reuses it at every startup without asking the server whether it is still good. The Parse server expires sessions (after a year, by default), and api.bloomlibrary.org then answers every request that needs a signed-in user with 400 "Unable to validate user". Bloom treated that like any other failure.

What the PR does

  • Every request the Bloom Library API client sends now goes through one place. When the server refuses the token there, Bloom signs the user out, so the Sign in button shows again. It doesn't sign out of the website, which would open a browser page. Then it asks the user to sign in again.
  • Bloom signs out only if the refused token is still the current one. A slow request that still carried the old token can't throw away a sign-in the user has just made.
  • The check for an existing copy, and the upload itself, show the new message instead of "try again in a minute or two" or "restart Bloom".
  • Once the command-line bulk uploader has been signed out, it stops trying books. It records each remaining book as failed, with a line in its log. Folders holding more than one .htm file are still reported as needing repair.

  • Nobody has tried this in a running Bloom. Seeing the message and the Sign in button needs a refused sign-in; the test ideas on the card say how to make one by editing user.config.
