What this change does

SpreadsheetImporter.GetPageForLabel() looks for page templates in “the collection the book is in”, and works that out as the book folder’s parent. In a real Bloom collection that is correct. In the tests it was not: they built their book directly in %TEMP%, so the parent was the temp directory itself and Bloom walked every subfolder of it looking for books.

On a working machine that is thousands of folders belonging to other tests and other programs. If any one of them was deleted between being listed and being inspected, FindBookHtmlInFolder threw and took out an entire fixture in OneTimeSetUp — naming a folder that had nothing to do with the test, and hitting a different set of tests each run.

Now each fixture gets a folder of its own, named after itself, under one root, and nests its book inside that:

%TEMP%/BloomSpreadsheetTests/<FixtureName>/Book

So the folder the importer scans as “the collection” only ever holds that one fixture’s folders.

Decision 1

Should the template scan itself survive a folder that disappears?

The card offered two fixes and said “either or both”. This PR does the first one: keep test books out of %TEMP%. The second was to make the scan tolerant, so that a folder vanishing mid-scan is skipped rather than fatal.

Why it might still matter: the tolerance would protect the real product, not just the tests. When a user opens the Add Page dialog, Bloom lists the folders in every source collection and inspects each one. If a folder is deleted in that instant — by a sync client such as Dropbox, an antivirus tool, or the user themselves — the dialog fails instead of quietly skipping it. The narrow version is one line in GetBooksInCollectionDirectories: filter out folders that no longer exist before inspecting them. It does not weaken the bl-291 warning that tells a user their book folder has gone missing, because that check lives on the save path, not the collection scan.

Decision 2

The full C# test suite is not green on this machine — and it is worse without this change

The project’s own instructions say the full C# suite “is expected to be green” when run through the build wrapper. It is not. Run against a pristine checkout of current origin/master, with this change stashed, 65 tests fail and the run aborts partway through, having reached only 1678 of about 2962 tests. With this change applied, 36 fail and the run gets much further.

Two things are worth knowing. First, the failures on my branch are all in publish-side fixtures — ePUB export, CompressBookForDevice, accessibility checks, audio overlays — none of which this change touches, and the ones I spot-checked fail on pristine master too. Second, the pristine baseline fails BogusCkeMaterial_Removed("span"), which is precisely the collateral damage BL-16661 describes: a spreadsheet fixture blowing up in setup and taking unrelated tests down with it. So part of what you are seeing on master is this very bug, still live.

That leaves a genuine open question about the remaining publish-side failures and the aborting test host, which are a separate problem from this PR.

For your information

Folders belonging to renamed or deleted fixtures will linger

The shared %TEMP%/BloomSpreadsheetTests root is deliberately never deleted — deleting it would destroy the folders of any fixture running at the same time. Each fixture reclaims its own folder by name on the next run, so nothing accumulates in normal use. But if a fixture is renamed or removed, or a run crashes and that fixture is never run again, its folder sits under the root until someone clears it by hand. Devin raised this as an informational note; it is a tidiness issue, not a correctness one.
