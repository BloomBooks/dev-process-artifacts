What changed since your decisions

You asked for the card's second fix as well, so this PR is no longer test-only. GetBooksInCollectionDirectories now skips a book folder that has disappeared instead of letting it abort the whole scan. That protects the Add Page dialog in the shipping product, not only the tests: Bloom lists the folders in every source collection and inspects each one, and a folder can be deleted in that instant by a sync client, an antivirus tool, or the user.

Its regression test reproduces the race deterministically rather than hoping to catch it. The scan is lazy, so the test takes one book from the enumerator, deletes the folder of whichever book it has not yet been handed, and carries on. Without the guard it fails with the exact exception from the bug report.

The guard also changed the picture on this branch: before it, the full suite here aborted with 36 failures; with it, the suite runs to completion with one pre-existing failure.

While finishing this, a second card came out of the same area: BL-16664 / PR #8172, which gives each test run its own temp directory so that two agents running the suite at once cannot delete each other's folders. It has its own preflight report.

The two are independent fixes for different causes, and each on its own takes this machine's suite from "aborts with 65 failures" to "completes with 1". You may want to review them as a pair.

Decision 1

The guard makes the failure very unlikely, but cannot make it impossible

Devin pointed out, correctly, that checking whether a folder exists and then opening it are two separate steps. A folder could still be deleted in the gap between them, and the scan would throw exactly as before.

In practice the difference is large. Previously the whole enumeration was exposed: Bloom listed thousands of folders, and any one of them disappearing at any point during a scan lasting seconds would abort it. Now the exposure is the few microseconds between one folder's check and that same folder's inspection. On this branch that is the difference between a suite that aborts and one that finishes.

Closing the gap completely would mean catching the exception rather than testing first. That is a different shape of change: the project's own guidance is to fail fast rather than swallow failures, and a catch here would also hide genuine problems such as a permissions fault. That is why the recommendation is to stop where we are.

Decision 2

One test still fails, and the project's own notes say that particular failure means something

With this branch the suite completes, but XMatterHelperTests.InsideBackCover_PaperAndDeviceXMatter_ShareOneCustomLayoutId fails: it expects the layout id customInsideBackCover and gets an empty string, meaning Bloom could not locate the Factory front/back-matter files. It fails identically on a pristine checkout of master, so nothing here causes it.

It deserves a decision rather than a shrug because AGENTS.md singles this exact case out: "If you see the PdfMaker or xmatter-locating tests fail, that is a real regression in the wrapper / Directory.Build.props, not the known environment noise it used to be." By the project's own account this is a signal — and it is now the only thing between this suite and green.
