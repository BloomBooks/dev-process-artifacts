What this PR is about

Problem

After Edit with AI... puts a new picture on the page, Undo cannot put back what was there. Ctrl+Z does nothing at all, and the Undo button in the top bar brings the old picture file back but uncropped — a picture the user had cropped returns showing the whole photo, at the wrong shape. Found by working through this card's own test ideas after PR #8356 merged.

Cause

Two independent gaps. Nothing listened for Ctrl+Z over a picture: text undo belongs to the CKEditor instance that has focus, and origami binds its own handler in layout mode, but an image change had neither — only the Undo button reached the image undo. And right after the AI editor closes, the keystroke arrives in the top window, where the editor's overlay lives, not in the page.

Separately, a crop is two boxes: the img, which grows past its canvas element and slides under it, and the canvas element that frames it and takes the shape of the part that shows. The undo record captured only the img's box, and restored it only on the background-image path. The canvas element had meanwhile been reshaped to fit the new picture, and the background fitter then rescaled the img to match — which is what erased the crop.

What the PR does

  • The undo record captures the canvas element's box alongside the img's, and undo restores both, telling the sizing code this is not a new image so it keeps the cropping instead of fitting to the whole picture.
  • Ctrl+Z over a picture now reaches the image undo, handled in the page frame and in the top window.
  • It takes the key only when the picture's undo is really the one meant: not from a text field or a rich-text editable, not while a dialog or the AI editor overlay is open, and not before origami and the active tool have had their turn — the same order the Undo button uses.
  • An undo back to a picture that was never cropped is handled as a new image, so it waits for the restored file to load rather than sizing itself from the picture being undone away.

Worth knowing

  • The crop restore is not specific to the AI editor. Every way of replacing a picture — the image gallery, paste, and the C#-driven change — goes through the same function, so all of them now undo back to a cropped picture correctly.
  • Checked by hand in a running Bloom: an ordinary picture canvas element, and a normal background image, each with a real Ctrl+Z and with the Undo button. Reverting the fix reproduced both reported symptoms exactly. The Fill-mode background is the case that is still open.
  • The image undo stack holds one entry per page and is cleared when you leave the page, so undo after an AI replacement is a single step and only on that page. That is pre-existing behavior, not something this PR changes.

Decisions

Undo of a cropped Fill-mode background picture can come back the wrong size

Decided: fix it in a separate card, aimed at master (6.6) — filed as BL-16880. This PR is unchanged, and the test ideas name the limitation so it isn't filed again.

A background picture can be set to Fill, where it is scaled up and cropped so it covers the whole page rather than fitting inside it. Undoing an AI replacement on such a picture can bring it back at the wrong scale or offset, if the AI's picture and the original have different proportions. The ordinary (fit-inside) case is correct, and so is a picture that was never cropped; this is only the Fill case.

The reason is a timing one. When undo puts the old file back, the browser goes on reporting the previous picture's real-world width and height until the restored file has decoded. Bloom's sizing code normally waits for that, but on the undo path we deliberately tell it "this is not a new picture" so that it keeps the cropping — and that same flag is what switches the waiting off. Every other path works from the restored boxes and never asks for those dimensions; the Fill arithmetic is the one place that does.

I have not fixed it because the honest fix separates the two meanings that flag currently carries, which changes a function several other callers use, and because confirming it needs driving a real Bloom — which I am not going to do against your collection unprompted.
