What this PR is about

Problem

Leaving the Edit tab could put up an error report — “Cannot empty page while saving” — and leave the workspace drawn half way between the Edit tab and the tab the user asked for: the new tab’s frame, but no book preview, no “Edit this book” button, and most of the collection’s icons and the whole Sources For New Books panel missing. The user’s page had not finished saving at that point either, so a book title they had just typed had not reached the collection’s book list.

Cause

Clicking another tab while editing starts a save, and the tab change waits until the browser hands the page content back. During that window the tab bar still offers the target tab — the disable travels to React over a websocket, so it cannot win the race — and WorkspaceView still regards the Edit tab as current, so a second click goes straight through ChangeTab. That second request cannot start a save of its own, and the fallback handling it pressed on with the tab change anyway. Completing the change reaches EditingStateMachine.ToNoPage(), which throws while a save is pending — out of the middle of ChangeTab, so the rest of the tab switch never ran. Clicking a page thumbnail and then a tab crashed the same way.

What the PR does

  • EditingStateMachine.DeferUntilSaveCompletes(work) remembers work that arrived while a save was in flight and runs it once that save has completed — in a finally, so a save that fails cannot swallow a pending tab change.
  • WorkspaceView.ChangeTab now offers a RetryWork that re-attempts the whole tab change. Retrying from the top means the existing “already on the desired tab” check turns a duplicate click into a clean no-op, while a genuinely queued click — a thumbnail click followed by a tab click — is still honoured rather than dropped.
  • EditingModel.OnTabAboutToChange’s fallback defers instead of pressing on.
  • Corrected the comment on EditingView.OnVisibleChanged, which claimed ToNoPage() is ignored when it isn’t valid. It throws.

The tab now switches exactly once, after the save — so the collection list also shows the title the user just typed. A new test fixture covers the deferral, including an end-to-end replay of the reported double-click.

Question 1

A second place the same crash could happen

Devin pointed at another route into the same kind of failure. When Bloom opens a different collection — the user clicks a collection card in the collection chooser — it announces the tab change in a way that carries no work to retry, so the new “wait for the save” mechanism does not engage. If a page save were somehow still in flight at that moment, the code would ask the state machine to empty the page and would throw exactly as this bug did.

I do not think it can actually happen, and this PR makes it less likely rather than more: the chooser is a dialog opened from the Collections tab’s own toolbar, so you have to already be on the Collections tab to click a collection — and getting there from the Edit tab is precisely what now waits for the save to finish. Fixing it properly would mean holding a collection switch until the page save completes, which changes behaviour in a path that has no test coverage, in a PR about something else. Devin’s stated reason for it being safe was wrong, though, which is why it is worth your eyes rather than mine.

Question 2

Should the tab bar say it is working?

With this fix, clicking Collections while editing starts a save and the tab changes a moment later. If the user clicks again during that moment, nothing at all appears to happen — the click is absorbed and honoured silently. On a heavy page, or a slow disk, that moment is long enough to notice, and the natural human response to a button that seems not to have worked is to click it again.

The tab bar could instead show the tab the user asked for as pending — greyed, or marked as loading — the instant they click it, rather than waiting for C# to push the state back over the websocket. That is a front-end change in TopBar.tsx and independent of the crash fix, so it can equally well be its own card.

Question 3

Try to reproduce it in a running Bloom?

The crash is reproduced and the fix demonstrated by unit tests that drive the real state machine through the exact sequence from the report. What no test can show is that the workspace looks right afterwards in the actual application — that a double-click on Collections lands you on a fully drawn Collections tab with the book preview and the Sources For New Books panel present.

Doing that by hand needs two clicks inside the save window, which is under a second on an ordinary page. It is reachable with a deliberately heavy page, or by temporarily slowing the save down in a local build. Either way it costs a Bloom session, and a temporary slow down would need to be removed again afterwards.
