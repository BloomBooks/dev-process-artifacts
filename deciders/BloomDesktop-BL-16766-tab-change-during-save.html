What this PR is about

Problem

Leaving the Edit tab could put up an error report — “Cannot empty page while saving” — and leave the workspace drawn half way between the Edit tab and the tab the user asked for: the new tab’s frame, but no book preview, no “Edit this book” button, and most of the collection’s icons and the whole Sources For New Books panel missing. The user’s page had not finished saving at that point either, so a book title they had just typed had not reached the collection’s book list.

Cause

Clicking another tab while editing starts a save, and the tab change waits until the browser hands the page content back. During that window the tab bar still offers the target tab — the disable travels to React over a websocket, so it cannot win the race — and WorkspaceView still regards the Edit tab as current, so a second click goes straight through ChangeTab. That second request cannot start a save of its own, and the fallback handling it pressed on with the tab change anyway. Completing the change reaches EditingStateMachine.ToNoPage(), which throws while a save is pending — out of the middle of ChangeTab, so the rest of the tab switch never ran. Clicking a page thumbnail and then a tab crashed the same way.

What the PR does

  • EditingStateMachine.DeferUntilSaveCompletes(work) remembers work that arrived while a save was in flight and runs it once that save has completed — in a finally, so a save that fails cannot swallow a pending tab change.
  • WorkspaceView.ChangeTab now offers a StartTheChangeOver that re-attempts the whole tab change. Retrying from the top means the existing “already on the desired tab” check turns a duplicate click into a clean no-op, while a genuinely queued click — a thumbnail click followed by a tab click — is still honoured rather than dropped.
  • EditingModel.OnTabAboutToChange’s fallback defers instead of pressing on.
  • Corrected the comment on EditingView.OnVisibleChanged, which claimed ToNoPage() is ignored when it isn’t valid. It throws.

The tab now switches exactly once, after the save — so the collection list also shows the title the user just typed. A new test fixture covers the deferral, including an end-to-end replay of the reported double-click.

Worth knowing

  • Not verified by hand, and deliberately so. The crash is reproduced and the fix verified by the new unit tests, which replay the click sequence through the real state machine. John tried to provoke the original crash in a running Bloom and could not — expected, since the second click has to land inside a sub-second window — and we decided that was not worth engineering around. The test-ideas note on the card says the same, so a tester doesn't read “I couldn't make it crash” as a failed test.
  • The tests were checked for teeth. With the deferral neutered, four of the seven fail — the end-to-end replay with the original InvalidOperationException. They are not passing vacuously.
  • A second rapid click now produces no visible response until the save finishes, rather than an error. Showing the tab as pending was considered and declined for now, so a reviewer meeting this should read it as intended rather than unfinished.
  • If the browser never returns the page content, the queued tab click is dropped. Pre-existing: the first click’s save was already lost in that situation. Worth knowing so it isn’t read as new.
  • Disabling the tabs during a save has been decorative since Dec 2025, and comments still claimed otherwise. Until the top bar became a React component it was _tabStrip.Enabled = false, which swallowed the click synchronously in-process; now SetTabsEnabled only pushes tab states over a websocket and nothing checks _tabsEnabled when a selectTab request arrives. Since the disable is requested from inside the first click’s own request, a second click is already queued behind it on the UI thread — so a double-click reached the “impossible” state every time. The false claim is gone and the trap is now documented on SetTabsEnabled itself, since other code may be leaning on the same assumption.
