What this PR is about

Problem

The book title appears on both the front cover and the title page, and each needs a different bottom padding so its descenders are not clipped. Bloom keeps that padding in the editable’s style attribute, and style is synchronised across every copy of a data-book field through a single data-div entry. So the two pages overwrite each other, and whichever was visited more recently wins; the other one is saved with a value that is wrong for it.

You never see it in the editor, because OverflowChecker re-measures and re-applies the padding every time a page loads. But the saved value is what gets published, and BloomPUB, ePUB, Bloom Reader and BloomLibrary have no OverflowChecker — they render what is in the file. A book published while the front cover holds the title page’s value loses the descender room on its cover title: exactly the clipping bloom-padForOverflow exists to prevent, on the most prominent text in the book. A side effect of the same ping-pong is that those two pages really do change every time they are looked at, so a book shows as modified after merely being browsed — spurious checkouts in a Team Collection.

What the PR does

  • A new _pageDependentAttributes set in BookData names the (data-book key, attribute) pairs whose value legitimately differs from one xmatter page to another. It currently holds exactly one pair, (bookTitle, style); every other key and attribute is untouched by the mechanism.
  • Such a value is now saved in the data-div once per kind of xmatter page, as data-<attr>-<pagetype> — data-style-frontcover, data-style-titlepage. The plain attribute is still written too, holding the most recently saved value, so older Bloom versions and books with no variant yet behave exactly as before.
  • Reading the book keeps first-found-wins for every other attribute, but collects each xmatter page’s own variant instead of letting the first element found decide for all of them. When Bloom reads a single edited page — where the data-div is not part of what it reads — the other pages’ variants are seeded from the data-div, so saving one page cannot forget the others.
  • Restoring routes the saved list through ResolvePageDependentAttributes: an xmatter page gets its own variant under the plain attribute name and never another page’s; the data-div gets the variants verbatim; anything not on an xmatter page gets just the plain attribute. The existing custom-layout exclusions (BL-16357, BL-9460) are untouched.
  • Five new BookDataTests cover both save directions, a whole-book synchronize of a book whose two pages disagree, the legacy upgrade path where the data-div holds only the plain value, and a title on an ordinary page with no data-xmatter-page.

Worth knowing

  • A book whose saved cover padding is already wrong is not retroactively repaired. The fix stops the two pages overwriting each other from now on, but it cannot invent a measurement: only OverflowChecker, running in the editor, knows what the cover needs. So a book last saved with the title page’s 0px on the cover keeps that value until someone opens its front cover in the editor once. Opening such a book and publishing straight away still clips. That is expected, not the fix failing.
  • Bloom still rewrites the book’s .htm on every page navigation — that is its normal page save and this PR does not change it. What the PR changes is that the content no longer differs: repeated front-cover ↔ title-page visits now produce byte-identical files, where before the two paddings swapped every time.
  • Confirmed by hand in a Bloom built from this branch, not just by unit tests. With a title long enough to overflow, the cover kept padding-bottom: 5px and the title page 0px, and the data-div carried both variants plus the plain value. With the change temporarily reverted and Bloom restarted, both pages were forced to the same value — the reported bug — and the variant attributes leaked onto the page elements.
  • Only the book title is covered. Some project-specific xmatter packs put bloom-padForOverflow on other data-book fields as well; see the first question on the right.

An unanswered question on the card asks whether a cheaper approach exists

Before this work started, a colleague left a comment on BL-16811 addressed to you:

“the recommended fix was to merge instead of to replace but it looks to me like something is leaking into this user style attribute that should not have leaked. Still a significant bug but a different approach may be cheaper. @john_thomson is that right or wrong?”

That reads as a different diagnosis: rather than teaching the shared store to keep one value per page, stop the measured padding from being written into the title’s user style in the first place — keep it somewhere that was never meant to be shared between the copies of a field. It was never answered, and this PR implements the per-page approach instead, as instructed.

I have deliberately not replied to it: answering a colleague’s question about the design is yours to do. It is worth deciding before human review, because a reviewer may well ask the same thing.

Should other padded xmatter fields be covered too?

The new mechanism deliberately applies to one field: the book title. But bloom-padForOverflow — the class that makes Bloom measure and store a padding — is also on other data-book fields in some project-specific xmatter packs: author, editor, illustrator, year, publisher, department and location in the Afghan Children Read pack, and the title again in the ABC Reader pack. Any of those that appears on two different xmatter pages at two different type sizes has exactly the same bug as the title did, and would still have it after this PR.

We have no report of any of them actually misbehaving, and each field we add is another field that stops sharing a style between its copies — a behaviour change for those packs.

Should variants for page types a book no longer has be pruned?

Each variant is stored under the kind of page it came from, e.g. data-style-frontcover. If a book later changes xmatter pack, or a page type simply disappears from it, the entry for the old page type stays in the data-div forever. It is inert — nothing reads a variant whose page type is not in the book — and it is a few dozen bytes, but it is never cleaned up.

Pruning is not free: a page type can be temporarily absent while xmatter is being regenerated or swapped, and pruning then would throw away a value the book still wants.

Should already-affected books get repaired somehow?

Because only the editor can measure what the cover needs, an existing book that was last saved with the title page’s value on its cover keeps that wrong value until someone opens its front cover in the editor. Until then, publishing that book still clips the cover title exactly as before. Every book anyone has edited in 6.4 is potentially in that state.

There is no way to compute the right value outside the editor, so the only options are to make the editor visit the two pages once when a book is opened, or to accept that the value corrects itself the first time someone looks at the cover.
