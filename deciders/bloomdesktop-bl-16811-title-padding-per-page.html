What this PR is about

Problem

The book title appears on both the front cover and the title page, and each needs a different bottom padding so its descenders are not clipped. Bloom keeps that padding in the editable’s style attribute, and style is synchronised across every copy of a data-book field through a single data-div entry. So the two pages overwrite each other, and whichever was visited more recently wins; the other one is saved with a value that is wrong for it.

You never see it in the editor, because OverflowChecker re-measures and re-applies the padding every time a page loads. But the saved value is what gets published, and BloomPUB, ePUB, Bloom Reader and BloomLibrary have no OverflowChecker — they render what is in the file. A book published while the front cover holds the title page’s value loses the descender room on its cover title: exactly the clipping bloom-padForOverflow exists to prevent, on the most prominent text in the book. A side effect of the same ping-pong is that those two pages really do change every time they are looked at, so a book shows as modified after merely being browsed — spurious checkouts in a Team Collection.

What the PR does

  • A new _pageDependentAttributes set in BookData names the (data-book key, attribute) pairs whose value legitimately differs from one xmatter page to another. It currently holds exactly one pair, (bookTitle, style); every other key and attribute is untouched by the mechanism.
  • Such a value is now saved in the data-div once per kind of xmatter page, as data-<attr>-<pagetype> — data-style-frontcover, data-style-titlepage. The plain attribute is still written too, holding the most recently saved value, so older Bloom versions and books with no variant yet behave exactly as before.
  • Reading the book keeps first-found-wins for every other attribute, but collects each xmatter page’s own variant instead of letting the first element found decide for all of them. When Bloom reads a single edited page — where the data-div is not part of what it reads — the other pages’ variants are seeded from the data-div, so saving one page cannot forget the others.
  • Restoring routes the saved list through ResolvePageDependentAttributes: an xmatter page gets its own variant under the plain attribute name and never another page’s; the data-div gets the variants verbatim; anything not on an xmatter page gets just the plain attribute. The existing custom-layout exclusions (BL-16357, BL-9460) are untouched.
  • Five new BookDataTests cover both save directions, a whole-book synchronize of a book whose two pages disagree, the legacy upgrade path where the data-div holds only the plain value, and a title on an ordinary page with no data-xmatter-page.

Worth knowing

  • A colleague’s question on the card is still unanswered. Before this work started, a comment on BL-16811 addressed to you asked whether a cheaper approach exists than merging styles. The answer this work settled on is that no page-side merge can work, because publishing regenerates the xmatter from the data-div and only the data-div survives; hence one stored value per page type. A reviewer may ask the same thing, so it is worth answering on the card before review.
  • A book whose saved cover padding is already wrong is not retroactively repaired. Only OverflowChecker, running in the editor, knows what the cover needs, so such a book keeps its wrong value until someone opens its front cover once. Opening and publishing straight away still clips. Expected, and noted for QA in the test ideas.
  • Confirmed by hand in a Bloom built from this branch during the first run. The cover kept padding-bottom: 5px and the title page 0px across repeated visits, and the data-div carried both variants plus the plain value. With the change reverted, both pages were forced to one value. This run’s refactors did not change behaviour, so it was not repeated.
