What this PR is about

Purpose

Many people run Bloom on machines at least five times slower than a developer's, so something that takes 650 ms for us takes three or four seconds for them, and we rarely see it. This adds a Simulate a slow computer item to the testing menu that opens when you right-click the top bar. While it is on, Bloom runs roughly as it would on such a machine.

What the PR does

  • Every WebView2, including off-screen ones and those created later, gets Chromium's 5× CPU throttling (the DevTools command Emulation.setCPUThrottlingRate).
  • Bloom's own process is limited to two cores and put in a Windows job object with a hard cap of 3/10 of one core. Child processes break away from the job, so the WebView2 runtime is slowed only by the DevTools throttling. Turning it on is all-or-nothing: if Windows refuses a step, Bloom is left as it was.
  • The setting lasts for this run only. Children inherit the two-core limit while it is on, so a Bloom that replaces this one (a restart, or an update) puts the original affinity back first thing at startup.
  • WebView2s are tracked through weak references, so users who never use the mode pay one list entry per WebView2 and nothing is kept alive.

Nothing here slows the disk or the network, and a CPU cap makes short tasks stutter rather than slow evenly. Trying it has already turned up BL-17130 (clicks on a page while another loads are ignored).
