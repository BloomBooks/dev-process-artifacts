What this PR is about

Problem

Changing a setting on a sub-page threw the user back to the top-level page. In Bloom's new Collection Settings dialog each language has a More sub-page; ticking a box or picking a value there immediately showed the Languages page again. The value was kept, but every edit cost the user their place.

Cause

Config-R reset the focused page to the top-level page whenever the pane's children changed. A client builds its pages afresh each time it renders, and Bloom's dialog re-renders after every edit, so every edit reset the focus.

What the PR does

  • The reset now follows the top-level page's key and the pane's page index, so it happens when the pane selects a page or starts or ends a search, and not when the client merely re-renders.
  • Two tests: a client re-rendering while a sub-page shows keeps it showing; a search started from a sub-page of the first page leaves it. Each fails without its part of the fix.

1. A sub-page the client removes while it shows

Before this PR, Config-R reset the focused page on every render, so a sub-page could never stay focused after the client stopped rendering it. With the fix, if a client removes the sub-page the user is on, the pane shows nothing (no settings and no back button) until the user picks another top-level page. No client does this today: in Bloom, the only sub-page that can disappear belongs to Language 3, whose Remove button is on the Languages page itself. A proper fix needs the focused page to report that it still exists, which is more machinery than this needs now.
