Decision

Custom stylesheets can no longer set the font for equations

Bloom books can carry hand-written CSS — customBookStyles.css for one book, or customCollectionStyles.css for a whole collection. These are meant to have the final say: the generated font file even says so in its own header, telling the reader its rules “may be over-ridden by rules in customCollectionStyles.css, appearance.css or customBookStyles[2].css”.

That promise holds for ordinary text because the per-language font rules are written weakly enough to lose to a custom rule. The new rule for language-independent text is written much more strongly, because it has to reach inside a page while excluding the cover and credits pages. The upshot is that a book which sets a font for the Equation style through hand-written CSS will now silently render that text in the collection's main-language font instead. Fonts chosen through Bloom's own Format dialog are unaffected, because Bloom marks those as !important.

Both reviewers found this independently, which is why it is here rather than quietly fixed: each remedy trades one risk for another, and choosing between them is a design call.

Recommended because the affected case is narrow — a book whose hand-written CSS sets a font on a style that language-independent text uses — while both fixes push risk somewhere harder to see, and the :where() option in particular could reintroduce the original bug on old Bloom Reader devices. It is also reversible later without touching anything else.

Decision

Who refreshes the stale visual-regression baselines?

The visual regression suite compares screenshots of built books against saved reference images. It is currently failing on master itself — 11 of 12 cases — and has been since the BL-16370 work added a “Made with Bloom” QR badge and a Local-Community layout without regenerating the references. Every differing pixel sits in the back-cover badge area.

This branch inherits those failures; it does not cause them. It regenerates six A5 references, but only for the arithmetic font change that is the point of the PR. Because the suite is red for an unrelated reason, I did not run it during this preflight — a red result would have told us nothing new, and it launches its own copy of Bloom.

For your information

The template question is still open

This PR makes the arithmetic text render consistently, but it does not answer the question you raised earlier: whether the Arithmetic template should keep marking its equations as “in no language” at all, or should simply be given a real font of its own. Everything here works by giving that marking a meaning it previously lacked; removing the marking later would be a separate, larger change to the template and to any book already using it.

One smaller loose end sits underneath it. On an arithmetic page the digits and the equals sign are not the same kind of element — the digits are editable text marked “in no language”, while the equals sign is a fixed label that is not editable. They pick up their fonts by different routes, so if someone styles the Equation style they can still drift apart. Nothing in this PR makes that worse, and nothing fixes it.

Recommended because it is already written up at length in the BL-16624 description, so nothing is actually at risk of being lost — but say the word and it becomes its own card.
