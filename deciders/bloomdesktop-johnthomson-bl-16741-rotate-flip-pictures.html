What this PR is about

Problem

On a picture or text box turned with Rotate right or the rotation knob, hovering over a resize or crop handle showed the cursor for an upright item: at 90°, ↔ on the handles at the top and bottom and ↕ on the ones at the sides. Pressing the handle switched the cursor to the right direction. Cropping and resizing worked; only the hover cursor was wrong. This was the last unticked test idea on BL-16741.

Cause

The handles' rotation-aware cursors were inline styles. The code that shows a row/column resize cursor over a table's borders cleared any inline *-resize cursor from whatever was under the mouse. So hovering a handle wiped its cursor, and the stylesheet's upright cursor showed. A drag re-aligns the control frame, which put the right cursor back.

What the PR does

  • The control frame now carries each handle's cursor as a --handle-cursor-<handle> CSS property, still worked out by the existing getHandleCursorForRotation. Each handle's stylesheet rule reads that property, with the upright cursor as fallback (inline images, which don't rotate, use the fallback). One rule now decides the cursor for hovering and dragging, and nothing that edits inline cursors can wipe it.
  • The table-border hover code now clears only the cursor it set itself. It shows no table cursor where a press would not start a table resize, using the same check as the mouse-down code, so a handle over a table's outer edge keeps its own cursor.
