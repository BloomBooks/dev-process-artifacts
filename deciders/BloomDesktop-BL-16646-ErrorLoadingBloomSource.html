Decision

The crash never reproduced here, so nobody has watched this fix turn a failure into a success

The bug is that importing a .bloomSource and choosing "make a new book based on it" can end with the message "Bloom was not able to import …", even though the book was in fact created. Colin hit it repeatedly on his machine; it has never happened on yours.

The reason is now understood. The import runs on a background thread, and part-way through it renames the new book's folder to the book's title, which makes Bloom refresh the page-list thumbnails — and that refresh reaches into the WebView2 browser control from the wrong thread. Whether that is fatal depends on which COM apartment the browser's controller object ended up in when it was created, which is why the same import fails on one computer and succeeds on another. Colin's machine runs a native ARM64 build; yours is x64, and there the illegal access is tolerated. So on this machine the "before" picture cannot be produced at all: with the fix reverted, two imports ran the offending code path and simply did not fail.

What was confirmed here, with temporary logging in a real Bloom: the rename now arrives on the background thread and the handler body then runs on the UI thread, and the import finishes normally. That proves the marshalling works; it does not prove it cures Colin's failure, because his failure can't be staged here.

Decision

The rename handler now waits for the UI thread instead of just handing work to it

When a book's folder is renamed on a background thread, the code that reacts to it — saving which book is selected, and refreshing the page thumbnails — now runs on the UI thread. It does so with a blocking call: the background work pauses until the UI thread has finished those steps. That keeps the old behavior exactly (everything finishes before the rename returns) and matches what the import code already does elsewhere when it selects a book.

The alternative is to hand the work over without waiting. Nothing would block, but the thumbnail refresh and the "which book is selected" write would land slightly later, while the import carries on — and if the selection changed in that gap, the settings write could be based on a stale comparison. Devin flagged the blocking version as worth a look and then agreed it is safe: it could only deadlock if the UI thread were itself waiting on that background work, and no path in Bloom does that (a modal dialog would still keep processing messages). That reasoning is now a comment in the code.
