1 · Cancel at the very last instant can still install on exit

Both reviewers landed on the same sliver: if the user's Cancel click arrives in the same instant the download finishes, Bloom correctly refuses to restart — but the install-on-exit handler may already be registered, so the update quietly installs whenever Bloom is eventually closed. The window is sub-second; the effect is identical to ordinary background auto-update behavior; and it is documented in the code as a reviewed decision. It contradicts the strict reading of "Cancel means cancel," which is why it gets one more airing here.

2 · One more string could be reused

From the string audit: the gate dialog's "Open a Different Collection" button is a new entry, but the existing, already-translated CollectionTab.OpenCreateCollectionMenuItem — "Open or Create Another Collection" — names the same action (both open the chooser, which does allow creating). Not changed autonomously because it is the most-seen wording in the feature and appeared in every screenshot you reviewed.

4 · FYI: two null-safe sends vs. "fail fast"

Devin (informational) noted that BloomWebSocketServer.Instance?.SendEvent(…) in BookUpload and EditingView turns a would-be crash into a silently dropped notification, which leans against AGENTS.md's fail-fast guidance. The code comments argue the case: Instance is now cleared on Dispose, so these fire only when an upload or download finishes as the collection is closing — losing that notification is the right failure; crashing a handled path is not. Leave as is unless you read it differently.
