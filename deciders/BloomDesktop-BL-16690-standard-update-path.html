The two that would have shipped

Every collection would have failed to open. Moving ProgressDialogApi up to the application container was right, but ProjectContext went on registering it too. I told you that was harmless because a second registration would overwrite the first. It does not: RegisterEndpointHandler does a Dictionary.Add, which throws on a duplicate key, and application-level registrations are deliberately never cleared between collections, so the duplicate never went away. I had generalised from a different method. Devin caught it; I put the duplicate back to be sure, and got this:

My live testing could never have found it, and that is the part worth remembering: the collection I was testing with is one Bloom deliberately refuses to open, so no ProjectContext was ever built. The feature under test was hiding the damage the feature was doing.

The Team Collection lock-out made Bloom quit. This dialog is also reached mid-session, when a repository starts demanding a newer Bloom while a member has the collection open — and there the websocket server already exists and holds its port. Starting a second one throws, and Init answers a SocketException by announcing that Bloom “cannot start properly” and quitting. The WorkspaceView precedent I was copying guards exactly this; I quoted the guard and then left it out. Fixed, and then fixed properly in 41ac07ae once Devin pointed out that Instance was never cleared on Dispose, so the check could be satisfied by a dead server.

1. Cancel keeps downloading, and installs on exit

Press Cancel during the download and the dialog closes, but Velopack carries on, and the exit handler still applies the update the next time Bloom quits — possibly hours later, after the user has worked in a different collection. The comments call this deliberate, on the grounds that it is what an ordinary background update does. That is true; it is also true that here the user made an explicit choice and watched it be ignored.

notes

2. After a cancel, the finished download says nothing

Cancel, and the download keeps the progress reporter attached. When it lands, the update code offers a restart — but this reporter’s offer is deliberately silent (so the dialog would not say the same thing twice) and there is no restart action on this path. So the user never sees the usual “Update for 6.4.108 is ready / Restart Bloom to Update” notification, even though by then the workspace is up and could show it. Note this becomes moot if you take option 1 above, since there would be no download left to finish.

notes

3. “Bloom is already working on checking for updates”

On the mid-session lock-out, Bloom’s own background check may already be running — likely, since automatic updating is on by default. Then the status guard reports a failure, so clicking Upgrade Bloom puts that sentence in the dialog and drops the user at the collection chooser, even though the upgrade they asked for is in fact under way. Not a regression — the private download path this PR deletes did the same — but it is the one common case where the button cannot do what it promises.

Leaving it alone is recommended because the in-flight check will finish and offer the update by toast anyway, so the user does get there — just not through this button.

notes

4. The warning icon never appears

The gate dialog asks for MessageBoxIcon.Warning, and no icon is drawn. Warning and Exclamation are the same value in .NET, so the name that reaches the front end is "exclamation", and the dialog only knows "warning" and "asterisk". Measured live: zero icons rendered. This predates the branch and affects every BloomMessageBox that asks for a warning, not just ours.

notes

5. Collection.NothingNewerAvailable

You asked whether this needs localizing, on the grounds that it should be rare. I do not think it is rare — I think it is the most likely of the endings. AutoUpdate defaults to true, so most users already sit at the head of their channel, which is exactly when the update code finds nothing newer; the Downloaded path is the one needing a coincidence. And in the scenario the flag exists for — a lead on 6.6 setting the minimum while the team is on Release 6.5 — every member sees this message, on every launch, until 6.6 ships. Worth knowing either way: all six of these strings are translate="no" today, so nothing is being translated yet regardless.

notes

6. Dead code next to my new enum

ApplicationUpdateSupport still declares an UpdateOutcome enum and an UpdateResult class that nothing anywhere references. They predate this branch, but they now sit a few lines from the UpdateAttemptOutcome I added, which is a genuine invitation to reach for the wrong one.

notes

7. The two-hour backstop

If the update never reports back, the dialog gives up after two hours. The number is not a judgement about how long an upgrade takes — it is 86 MB, and some users are on links where that really does take hours, which is what Cancel is for. It is only there so a download that has genuinely wedged cannot leave someone with a progress dialog, no collection, and no way out of Bloom.

notes

8. The offline path is not exercised

The fix that makes an offline user see an explanation rather than an empty dialog is reasoned and reviewed, but never run. Testing it honestly means denying the rig network access, which on this machine means a firewall rule scoped to that executable for the duration.

Recommended, because the change is three lines and the failure if it is wrong is a blank dialog, not damage.

9. Is the progress dialog too much ceremony?

Your open question from before, now that there is a picture of it above. Having seen it, I would keep it: a title bar, a short message log and a bar for three sentences over about thirteen seconds is more furniture than the moment strictly needs, but it is the only window that reliably stays in front to report the ending, and it is a component the app already ships.

11. For information: an undisposed wait handle

The reporter waits on a ManualResetEventSlim, which allocates a kernel handle, and it is deliberately never released. Three attempts at disposing it safely each had their own race, because there is no moment anyone can call the attempt over while a cancelled download may still signal it. So one handle leaks per upgrade the user asks for, in a process usually about to exit and reinstall itself, and the code says why.
