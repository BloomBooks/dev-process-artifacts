What this PR is about

Problem

Testing the Electron 43 release (2.3.1) on a sign-language book, the tester saw videos with torn, smeared frames on some pages, and videos that froze partway through toward the end of the book. Which page misbehaved varied from run to run. The same book plays cleanly on bloomlibrary.org.

Cause

Every file the player asks for goes through our bpub:// protocol handler, which handed the request to Electron's net.fetch("file:///…"). Electron's file loader ignores the Range header and always answers 200 with the whole file. Chromium's media loader depends on ranges: Bloom's MP4s keep their index at the end of the file, so it asks for the tail first, then seeks back, then resumes after pauses. Getting the entire file from byte zero every time made every video non-seekable and downloaded each one two or three times per page. Chromium 150 (Electron 43) copes with that worse than Chromium 124 did, and the damaged byte stream showed up as decoder garbage on the hardware decode path and as freezes on the software path.

What the PR does

  • The handler now serves files itself: it parses a single-range Range header and streams exactly the requested bytes as a 206 with Content-Range, Content-Length and Accept-Ranges. Whole-file requests still get a 200. Missing files get a 404 instead of a 500, and out-of-range requests get a 416. (serveFile, parseRangeHeader)
  • Content types come from a small extension map, since net.fetch used to supply them.
  • Two behaviors the file loader gave us for free are kept: file names are percent-decoded and query strings are dropped, for linked-book resources as well as the primary book.
  • Because the decoding is now explicit, it is also defensive: a malformed percent escape falls back to the raw text instead of throwing, and a linked-book resource whose decoded name would resolve outside that book's folder (..%2F..%2F…) is refused. Before this PR the file loader would have followed such a path. (decodeUriComponentSafely, isPathInside)
  • The request log now shows the Range header, so the behavior is visible without DevTools.

Verified on the reported book: videos report their full duration as seekable (was 0), the log shows a handful of small range reads per video instead of three full downloads, and page 12 plays cleanly with hardware decoding on.

Worth knowing

  • The corruption was reproduced on this machine only with hardware video decoding on, and the fix was verified there. It has not yet been confirmed on the tester's machine, which is what the round-2 test ideas on the card ask for.
  • The primary-book path deliberately still serves any absolute path a URL names. That is how bloom-player has always been given the unpacked book (its URL carries the temp folder), so it is not new to this PR and is out of scope here. The containment check applies to linked books, where the name comes from another book's HTML.
  • No version bump is in the PR; 2.3.1 is the current pre-release. See the first decision.

Decisions

1. Bump the version for a new pre-release?

The tester is working from the 2.3.1 pre-release, which has the bug. Getting this fix into their hands means a new pre-release, and every release so far has bumped package.json in its own commit before merging (2.3.1 was such a commit). The PR does not change the version.

2. Also disable hardware video decoding as a belt-and-braces measure?

With the Range fix alone, videos played cleanly on this machine with hardware decoding on. Earlier in the investigation, running the viewer with hardware video decoding turned off also removed the corruption, but that was before the Range fix existed, and the freezes remained. Adding the switch now would trade some CPU during video playback for protection against any GPU-driver decode problem we have not seen. The website plays these videos fine with hardware decoding, which suggests the decoder itself is not at fault.
