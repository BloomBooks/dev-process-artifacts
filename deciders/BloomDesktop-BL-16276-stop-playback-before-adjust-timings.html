Verified in a running Bloom

Beyond the unit tests, the actual repro was driven in the live app on a real three-sentence whole-text-box recording, through both routes named on the ticket.

  • The precondition was proved, not assumed. At the moment Adjust Timings was clicked the player was genuinely still playing — not paused, a quarter-second in, the Play button active — and the highlight was on a sentence rather than the text box.
  • The old failure was measured at that instant: what the previous code would have received was a sentence element, zero segments, no stored end-times, and an audio URL returning 404 — exactly the blank dialog on the ticket.
  • With the fix, from both Play and Listen to the whole page: the dialog opened with its waveform and all three sentence regions with the right text, the highlight was back on the text box, the audio had stopped, the buttons were no longer stuck active, and no temporary highlighting markup was left behind.

Adjust Timings can still open blank, on pages that mix recording modes

This is the one genuine open question, and it comes from Devin. It is not a regression from this fix — the same click was equally broken before — but it is the same symptom the ticket is about, reached by a different route, so you may want it closed while the area is fresh in mind.

The situation needs a page with two different recording modes on it: one text box recorded "By Whole Text Box" and another recorded "By Sentence". Adjust Timings only makes sense for the first kind, and the button is greyed out for the second. But the greying-out is only recalculated when you move between boxes yourself — not as "Listen to the whole page" walks from box to box on its own. So if you select the whole-text-box one (button enabled), press Listen, and then press Adjust Timings while you can hear the by-sentence box, the button is still clickable.

What the user would see is the original bug all over again: a dialog with no waveform and no sentence dividers. The dialog now correctly identifies which text box it landed on, but that box is one whose audio is stored as a separate file per sentence, so there is no single recording to draw and no stored sentence boundaries to lay out.

I confirmed the mechanism in the code rather than taking Devin's word for it: the recording mode really is re-derived from whichever box is playing, and the button state really is not refreshed between boxes during Listen. I did not reproduce it in the running app, which would need a purpose-built mixed-mode page.

A house rule this file has never followed

Devin pointed out that the front-end guidance in src/BloomBrowserUI/AGENTS.md line 60 asks that asynchronous changes to the editable page be wrapped so that anything asking for the page's content waits for them to finish. The new method doesn't do that.

Neither does anything else in audioRecording.ts — the helper appears zero times in the file, including in the long-standing method this new one was deliberately modelled on. So the new code follows the file's existing practice rather than departing from it, and everything it touches is throwaway markup that never reaches a saved book. It's also worth noting the change shortens the time that markup exists, since pausing used to leave it in place indefinitely. I resolved the thread on that basis; raising it here only because a whole file quietly ignoring a documented rule is worth someone knowing.

Every talking-book test runs twice

talkingBookSpec.ts imports a few setup helpers from audioRecordingSpec.ts. Because those helpers live in a test file, importing them also re-runs that file's entire set of tests inside talkingBookSpec's own run. So roughly ninety tests execute twice on every run, and reported totals are inflated — the two tests added here made the total jump by four, which is what sent me looking.

Nothing is wrong, and it costs only about a second, but it makes test counts misleading for anyone trying to reconcile them. Recommending it be left alone because moving the helpers is a change to a shared test file that every talking-book test depends on, which is a poor thing to bundle into a bug fix.
