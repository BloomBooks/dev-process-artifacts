What this PR is about

Problem

Some English in the image gallery never goes through l10n(), so it can't be translated. The Pixabay paste button's tooltip and screen-reader label are an example. Separately, each localized string's English is written twice, once at the call and once in ALL_GALLERY_STRINGS (the list the host is asked to translate), and nothing keeps the two in step. They had already drifted for ImageLibrary.PixabayFindKey.

What the PR does

  • Paste button: its tooltip and label now use the two IDs that were already in the table but never used.
  • Drift: the PixabayFindKey English at the call site is back to the table's and the XLF's wording. The unused ImageLibrary.ThisPage entry is removed.
  • Tooltip removed: "No metadata available" is removed rather than translated. It only appeared on Art of Reading thumbnails, which do have metadata, just not a pixel size. Those thumbnails now have no tooltip.
  • Safeguards: a new test checks every l10n() call against the table both ways (IDs, English, nothing unused). It also fails on any call it can't read. react/jsx-no-literals now warns on text written straight into JSX.
  • Error strings: the ones we don't expect a user to hit stay in English, with a comment saying so.
  • Pre-commit hook: three dead eslint-disable comments (naming a plugin that isn't installed) had made the lint hook fail on every commit. They're removed.
  • AGENTS.md: added, declaring the YouTrack tracker.

No new strings need XLF entries in BloomDesktop.

Two error messages can appear, so the comment next to them is inaccurate

You decided that error messages a user is never expected to see stay in English, each with the comment "not worth it for an error condition we never expect the user to see". Two of them can appear, though rarely. If loading a further page of results fails (say the connection drops while the user scrolls), the pictures already shown stay on screen and an English alert appears beneath them. That applies to "Failed to get more images: …" (ImageSearch.tsx:120) and "Failed to fetch images from Openverse" (OpenVerseProvider.tsx:106). Devin flagged the first; its thread is open.

A first search that fails shows nothing at all

Found while doing this, but a different bug and not fixed here. When the very first search fails and returns no pictures (for example, Openverse is down), the gallery shows an empty area: no pictures, no error, and no "No matches found". That's because the results area only appears when there are pictures or a search is loading (ImageSearch.tsx:205), and "No matches found" is hidden whenever there is an error (line 218). The user can't tell a failure from a search that's still loading.
