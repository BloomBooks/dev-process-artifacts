DecisionA collection named with a trailing period now loses it everywhere

If someone types Grade 1. as a new collection name, Bloom now creates the folder Grade 1, the file Grade 1.bloomCollection, and the collection displays as Grade 1 — the period is dropped. Previously Bloom asked Windows for a folder called Grade 1., Windows silently made Grade 1 anyway, and the settings file kept the period (Grade 1..bloomCollection) so the name still displayed with it. That mismatch is exactly what caused this bug, and three separate places in the code had to be taught to cope with it. This is a visible change to what a user gets, which is why it is here rather than simply done.

The collection would still display as Grade 1., but the folder and file names would disagree again — the state that broke Team Collections here. (~5 lines, but it re-creates the mismatch three code paths now tolerate.)

DecisionThe Open/Create dialog will list collections it used to hide

The dialog's list of collections found on disk used to look only for a settings file named after its folder, so it silently skipped any collection where the two disagree. On your machine that hid four: Heather's, and three whose folder was renamed after creation (BL-15365-Mixtec, BL-15902 Custom front cover2, From Bloom Library - My 5th Basic Book 2). They will now appear. This is the intended fix, but it does change what that dialog shows, and if a folder somehow holds more than one .bloomCollection the fallback picks the first one it finds.

Avoids an arbitrary pick in the odd case of two. (~5 lines in the chooser; would also re-hide a collection whose folder has a stray second file.)

FYISpreadsheet export can still leave a stray collection file behind

Exporting a book to a spreadsheet from the command line reads the collection settings from the book's parent folder. If that folder isn't a collection at all, the settings object it builds writes a brand-new default .bloomCollection into the folder as a side effect, and the export proceeds with default settings. That is long-standing behaviour, not something this branch introduced — but this branch briefly turned it into a hard failure instead, Devin flagged the regression, and the old behaviour was deliberately restored rather than quietly changed under cover of a bug fix. Leaving it means the oddity survives; changing it belongs in its own piece of work, which is why leaving it is recommended here.

Stops the stray file, but changes what a working command does today, and the failure would reach users as a CLI error. (~5 lines; a user-visible behaviour change beyond this bug's scope.)
