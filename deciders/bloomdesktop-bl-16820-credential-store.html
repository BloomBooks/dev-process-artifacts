What this PR is about

Problem

Two Bloom features need an API key the user fetches from another company's website: a Pixabay key for picture search, and an OpenRouter key for "Edit with AI". Bloom kept each key in its own per-channel settings, so a key entered in Beta was missing in Alpha or in a developer build, and it could be lost on upgrade. The keys also sat in the settings file in plain text. Separately, an OpenRouter key on the machine kept working — and kept spending money — however little the collection's subscription covered, and whatever kind of book the user was in.

What the PR does

  • One key file per Windows user. Keys now live in ServiceKeyStore — services.blm under %LocalAppData%\SIL\Bloom — which is independent of channel and version, so every Bloom on the computer sees the same keys. Each value is encrypted for that Windows account on that machine.
  • The file gives nothing away. Its name, its property names and the OpenRouter key's own name (OR) are all deliberately dull, so malware sweeping for files that announce themselves as key stores finds nothing to grab.
  • The store keeps what it did not write. A key it cannot decrypt — another Windows account's, or one a newer Bloom wrote — is left alone rather than deleted, a failed save throws rather than reporting success, and a key containing + or % survives the round trip unchanged.
  • One general API instead of two special ones. ServiceKeysApi serves one key by name, or a whole namespace at once for the picture gallery's per-provider keys. Adding a service needs no change to either the store or the API.
  • An expired subscription now stops the spending. The AI image editor opens in look-around mode whenever the collection's subscription does not cover AI image editing (Pro and above) or the book is based on the Playground template. There Bloom withholds the stored OpenRouter key altogether; the editor shows every tool but runs none of them — including the browser-only "PDF to Images" and "Remove Background" — says so in one dialog on opening, and offers no way to connect an account.

Worth knowing

  • The editor half of this change lives in another repo. Bloom pins bloom-ai-image-tools#dist-v0.1.13, so reviewing what look-around mode actually does on screen means reading that tag, not this diff.
  • Look-around mode has been seen by hand in a Playground book. The other way in — a collection whose subscription code is removed or expires while a key is already saved — has been verified only by unit tests and by reading the code.
  • The one sentence look-around mode shows the user is not yet localizable: it is a constant in the editor library, not an XLF string, because that library has no localization pipeline of its own yet.

Decisions

The API keys existing 6.5 testers have already entered will vanish

Until this branch, Bloom kept these keys in its own per-channel user settings — a Pixabay (and other picture-provider) key under ImageGalleryProviderKeys, and an OpenRouter key under OpenRouterApiKey. This branch deletes both settings and stores keys in the new per-user file instead, and nothing copies the old values across. So anyone who has already typed a key into a 6.5 build finds, on their next update, that picture search asks for a Pixabay key again and "Edit with AI" asks for an OpenRouter key again. Nothing is broken and nothing is lost beyond the typing: the user goes back to the provider's website (or their password manager) and pastes the key once more, and from then on it sticks across every channel, which is the point of the change.

Who this can reach: neither setting exists on Version6.4, so both features arrived during 6.5 and no released Bloom has ever stored one of these keys. The affected population is people running 6.5 alpha or beta builds — testers and developers — not users of a shipped Bloom. That is why the recommendation is to leave it, and the test notes on the card already tell testers to expect it so they do not file it as a bug.

For your information

Nothing in Bloom stops a look-around session from saving an OpenRouter key

The old, OpenRouter-specific endpoint refused to save a key when the book was a Playground book. Its replacement is general — it takes a name and a value and knows nothing about books — so that particular refusal is gone. What replaced it is stronger in the place that matters: Bloom decides in C# whether a session may generate pictures (AiImageEditorApi.cs:485) and, in look-around mode, does not hand the editor the key at all. The editor's own flag only controls what the user sees: tools greyed out, one explanatory dialog, no offer to connect an account. So a look-around session cannot spend money, but the plumbing would let it store a key. Devin raised this and it is answered on its thread; flagging it here only because it is a real reduction in server-side enforcement.

Notes on this one

The "Edit with AI" menu item appears for people who cannot use it

Whether that item shows on a picture's context menu is decided by the feature being visible rather than enabled (CanvasElementContextControls.tsx:462). That predates this PR, but look-around mode now depends on it: it is exactly why a collection with no subscription can open the editor at all and be shown what a subscription would give them. If that ever changed to enabled, the menu item would disappear for those users and look-around mode would become unreachable by that route. Worth knowing rather than acting on — the local review flagged it because it is load-bearing and easy to "tidy up" by mistake.
