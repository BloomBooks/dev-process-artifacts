What this PR is about

Problem

Two things Andrew found testing the credential store. The QA notes on BL-16820 said that a collection without a subscription would open the AI image editor in “look-around” mode, where the tools are on show but nothing can be run; it does not, and it never could. Separately, making the key file services.blm read-only and then saving an API key produced a toast reading only Error in /bloom/api/serviceKeys/keys?prefix=imageGallery, which tells the user nothing they can act on.

Cause

“Edit with AI…” is gated on FeatureName.AiImageEditing like every other Pro feature, so without a subscription the click opens the subscription settings and the editor is never launched — which left half of the playgroundMode condition unreachable. The key store throws on a failed write on purpose, so a key is never reported saved when it was not, but UnauthorizedAccessException is not an IOException, so it missed the API layer’s “Cannot access {0}” branch and fell through to the generic handler that reports "Error in " + RawUrl.

What the PR does

  • Look-around mode is now for Playground books only, rather than opening a hole in the subscription gate. The comments that described the wider behaviour are corrected.
  • A failed write to the key file now tells the user which file could not be updated and that it may be read-only or open in another program, in a dialog with no “Report” button, and the same text becomes the 503’s reason phrase so the front end has something better to show than an endpoint URL.
  • Only a genuine failure to reach the file gets that message; anything else goes to the generic handler, which reports it to us instead of sending the user to look at file permissions.
  • A whole namespace of keys is now written once rather than one file rewrite per key, so a save that fails leaves the file exactly as it was instead of applying part of the change.
  • The permissions and antivirus detail goes to the log, not the dialog, and the report waits until the request has finished, since the dialog is itself served by this server.
  • New string Errors.CannotSaveServiceKey, and a test that makes the key file read-only and asserts the failure names the path and changes nothing on disk.

A modal dialog, where there used to be a toast

The old behaviour was a toast in the corner with a “Report” button. Andrew’s verdict on it was “Not helpful to the user at all… But I think we should live with that.” This PR does two separate things to it: it gives the message real content (which file, and why it might be locked), and it promotes it from a toast to a dialog the user has to dismiss, with the “Report” button removed because nothing has gone wrong with Bloom. The reasoning for the dialog is that the user has just pressed save and the save did not happen, so a message they can miss is a message that leaves them believing a key is stored when it is not. The counter-argument is that a dialog interrupts, and this is a rare situation.

The whitespace check disagrees with the C# codebase

Devin flagged the new C# as wrongly indented, on the grounds that git diff --check objects to it. The check does object — but it objects to every C# change anyone makes in this repo, because the first line of .gitattributes applies indent-with-non-tab to every file, and while .js, .ts, .tsx, .htm and others have overrides, .cs has none. Meanwhile every C# file in Bloom is space-indented and the pre-commit hook runs csharpier over each staged one, which writes spaces. So the attribute is stale rather than the code being wrong. It is not this PR’s business either way, but it is a small, real piece of grit that makes a useful check useless for C#.
