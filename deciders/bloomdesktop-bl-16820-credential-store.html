What this PR is about

Problem

Two Bloom features need an API key the user fetches from another company's website: a Pixabay key for picture search in the Add Image gallery, and an OpenRouter key for “Edit with AI”. Bloom remembered each key per Bloom, so a key typed into Bloom Beta was invisible to Bloom Alpha, and every new build of the same channel asked for it again. A user running two channels, or updating weekly, re-fetched the same key from Pixabay over and over.

Cause

The keys lived in .NET application settings, which resolve to %LocalAppData%\SIL\<product>\<version>\user.config. The product name carries the channel and the folder carries the version, so each channel and each build reads a different file. Settings.Upgrade() cannot bridge them: it only copies a value forward within one channel.

What the PR does

  • A new store, UserKeyStore, keeps every key belonging to the user in one file, %LocalAppData%\SIL\Bloom\services.bloom. That folder has no channel and no version in it, so every Bloom the user runs reads the same keys.
  • Each value is encrypted with the Windows user login (DPAPI, CurrentUser scope), so a copy of the file in a backup, a cloud sync, or a support log is useless to anyone else. Keys do not travel to another computer or another Windows account; there the user is asked again.
  • Each value records a code for how it is encrypted, so a later Bloom can convert the keys it wants and leave the rest alone — keeping a key with the Bloom Library account, which the card asks for later, is such a change. What each code means lives in UserKeyStore, not in the file.
  • The file is deliberately dull and DPAPI is given fixed app-specific entropy. Neither stops anyone who reads Bloom's source, and neither is meant to; both aim at the untargeted credential stealer that sweeps a profile for filenames and words like key, token and api and calls CryptUnprotectData on any blob it finds.
  • A key Bloom cannot read is never deleted, whether it is protected by a method only a newer Bloom understands or belongs to another Windows account. Such a key never reaches the user, so it must not be mistaken for one they cleared.
  • The store knows nothing about any service: a caller picks a name. The gallery uses one name per provider (imageGallery.pixabay) through a new imageGallery/providerKeys endpoint; “Edit with AI” uses openRouter. The two old settings and the OpenRouter-only store go away, with no migration — both features are new in Bloom 6.5.

Worth knowing

  • Nothing has been exercised by hand. The whole feature is covered by unit tests against a temporary folder, and never by entering a real key into a running Bloom. Anything that depends on the two ends actually meeting — the gallery's JSON reaching the store intact, a key surviving a restart — is unverified.
  • Cross-channel sharing is the point and is the hardest thing to test. It needs two Bloom channels installed on one computer, which neither a unit test nor a single dev build can stand in for.
  • Devin keeps re-raising that the gallery key endpoint needs no authentication, and the finding is answered and resolved. It is a property of Bloom's whole localhost API, not of this PR, so a reviewer meeting it for the first time need not chase it here.

Nothing has been tried in a running Bloom

The plan for this work ended with a check by hand: with Bloom running, enter a Pixabay key in the image gallery, confirm services.bloom appears in %LocalAppData%\SIL\Bloom holding an unreadable value, and confirm the key is still there after restarting Bloom. That check has not been done. Everything on the PR is unit tests plus one bundle build.

What could be broken and still look green: the gallery posts its keys as a raw JSON body, and reading that body wrongly is exactly the bug that was found and fixed once already on this branch. A unit test on the store cannot see it, because the store never sees the HTTP request.

There is a Bloom running from this worktree right now, but it was built before these commits, so checking would mean rebuilding and restarting it — which interrupts whatever you have open in it.

A failure to encrypt now throws instead of being swallowed

This is a change to what the user experiences, so it is yours to confirm rather than mine to make quietly.

Before: if Windows refused to encrypt the key, Protect logged it and returned nothing, Set quietly did nothing, and the endpoint told the user their key was saved. At the next launch the key was gone, and they would have kept re-entering it every launch with nothing on screen ever saying why. Now the exception is allowed out, which is what Save already does for a failed write and what the Fail Fast rule in AGENTS.md asks for.

What that means in practice: on the day this happens, the user gets an error rather than silence. Bloom targets net8.0-windows, where DPAPI is always present, so it cannot happen today; it becomes real only if Bloom ever runs somewhere without DPAPI, which is exactly the day we would want to hear about it.
