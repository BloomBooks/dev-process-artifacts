Our written rule says never delete a string entry. We just deleted two.

Devin · Bug · non-severe

Bloom keeps its English interface text in “string list” files, one entry per phrase. Translators work from those entries, so throwing one away throws away the translations done for it. Because of that, src/BloomBrowserUI/AGENTS.md line 65 instructs: “If a string is no longer used, we do not remove it. Instead, add a note like this: <note>Obsolete as of 6.2</note>.”

This branch deletes two entries outright, which is what you asked for. Devin spotted the contradiction and, to its credit, aimed at the right target — not the code, but the rule: “If the team has deliberately adopted a delete-obsolete-entries policy (as a prior commit suggests), the rule files should be updated to match.”

It is right that there is a policy, and right that we are not following it. Commit 901bf1f333 on master already deleted 39 entries this same way, so the written rule has been out of step with practice for a while. Nothing is broken either way — the translated files keep their copies, so re-adding an id recovers its translations — but one of the two has to give.

The registry entry next to the one we fixed has the same stale-id problem.

Devin · Investigate · pre-existing on master

While checking our id swap, Devin looked at the neighbouring entry in the same registry and found canvasControlRegistry.ts:1033 asking for EditTab.Toolbox.ComicTool.Options.OutlineColor — an id that does not exist in the English string list. The two that do exist are …OuterOutlineColor and …TextOutlineColor. Confirmed by grep.

Checking further narrowed it usefully: the panel component itself already asks for the right one, “Outer Outline Color” at panelControls.tsx:206. For panel-type entries the registry’s own label fields are never rendered — so this is stale metadata sitting beside working code, not a broken label. Nobody sees anything wrong today, and wouldn’t even if the panel surface were switched on.

That also means it is the same shape as the bug this card just fixed, and the fix is no longer a guess.

Should a test catch the next one of these?

From the card’s own “suggested follow-up”

BL-16686 ends with a suggestion: a unit test that walks the English string lists and fails when an entry marked obsolete is still referenced in code or content would have caught all four of these when they were introduced. I checked — no such test exists today; nothing in the C# suite cross-checks string ids against usage at all.

It would be a genuinely cheap guard for a mistake this repo has now made four times. But writing a new test is scope beyond the card’s fix, and it needs a decision about strictness — the ids composed at runtime ("TemplateBooks.PageLabel." + label) mean a naive grep would produce false alarms on legitimate cases, so the test needs to be deliberately loose or deliberately narrow.
