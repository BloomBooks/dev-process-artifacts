What this PR is about

Problem

In Publish ▸ Text Languages, a language that is in the book but not named by the collection was listed under a name that depended on which machine Bloom was running on. For a collection of English and French with a book that still had Spanish text, the row read espagnol on the CI runner and español on a developer machine. Two people looking at the same collection and the same book saw different things.

Cause

LibPalaso’s GetLocalizedLanguageName has two code paths and picks between them once per process, by whether a native ICU library can be loaded. Bloom ships no icuuc.dll, so which path ran came down to whether some unrelated software happened to have left ICU where .NET could find it.

What the PR does

  • Turns ICU off for language names at startup. libpalaso 18.0.0-beta0046 makes the switch settable (#1552, BL-15471); WritingSystem’s static constructor sets it false, covering the app, the CLI and the tests alike.
  • Reverts this card’s earlier fix (merged #8286). That fix routed around the bad call for one code path by reading the subtag registry. It worked, but it changed names users had seen for years — a Tibetan row that read ບ່ມຬ་ຠ໅ມຬ་ in 6.5 read Tibetan in 6.6 — it reached only one path, and the special-casing it needed brought its own bugs.
  • Restores 6.5’s names exactly, and now every language name is machine-independent, including the collection-language path the earlier fix could not reach.
  • Bumps 8 libpalaso packages from beta0028 to beta0046, together.

What it does not buy: the name is still rendered in the process’s UI culture, so a Bloom running in French can still say espagnol. The guarantee is one answer per UI language rather than one per machine — which is what the bug report was about.

Worth knowing

  • The ICU-present half is unexercised anywhere. Neither this machine nor libpalaso’s CI has a native ICU library — proved by libpalaso’s own cross-language test cases coming back NotExecuted. So “ICU is available but we declined to use it” is covered by inspection only. The machine that originally showed espagnol was a GitHub runner.
  • The package bump carries 18 beta versions of other people’s libpalaso changes, not just this one fix, across all 8 packages. The suites and the dependency check pass, but that is the broadest risk here.
  • Nothing was checked by hand in a running Bloom beyond the e2e run, which drove a real Bloom and confirmed the Spanish row reads español.

1. Test expectations assume an English UI culture that nothing pins

Several language-name assertions in BookDataTests and BookTests now depend on the UI culture of whatever machine runs them. TestCulture deliberately leaves CurrentUICulture alone (changing it would make L10NSharp serve translated strings and break many unrelated tests), so on a machine whose Windows UI is French, es would come back as espagnol and these tests would fail.

This is a real consequence of the revert: on master those names came from the subtag registry and were culture-independent. It passes on every machine the team and CI actually use. BloomTests/AGENTS.md does say tests must not assume English.

2. A blank Language 1 name defeats the only guard in GetDisplayNameForLanguage

GetDisplayNameForLanguage guards its Language 1 branch with !IsNullOrWhiteSpace(Language1.Name), so a blank name should fall through to a looked-up one. But the fallback calls GetLanguageName, which searches AllLanguages by tag with no blank check — and Language1 is AllLanguages[0]. So the blank name is returned anyway and the guard achieves nothing.

This is restored 6.5 behavior, not a new invention: the code this PR reverts happened to check for blank before its own lookup. Whether a collection can even reach this state is unclear.
