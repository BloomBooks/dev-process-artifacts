Decision 1 · Greptile P1 · Devin informational

A preview that fails once is never retried while the chooser stays open

When the chooser can't fetch a picture, it now shows a message saying so. It remembers that failure against that particular picture's address. So if you click a different picture and then come back to the first one, you get the message again immediately — the chooser does not try to fetch it a second time.

For the case this card is about that is exactly right: a picture too big for the display engine to draw will fail identically every time, and retrying would just cost the user another wait. But the same is true of a picture that failed only because the network blipped for a second. That one would succeed on a second attempt, and the user has no way to ask for one short of closing the chooser and reopening it.

Worth weighing: this is not a regression. Before this change the pane went blank in exactly the same situations and also never retried — the change makes the existing behavior visible rather than introducing it. Both reviewers raised it as a tradeoff to confirm, not as a defect, and the reason the failure is keyed to the address at all is that it's what makes switching between pictures paint correctly on the first try.

Decision 2 · Greptile P2 · Devin informational

The “too large” wording leans on dimensions that may describe a different file

The reassuring wording — “This image is too large to preview here, but you can still use it” — is only used when the image source told us dimensions bigger than the display engine can ever draw. Otherwise the user gets the neutral “This image could not be previewed.”

The snag Greptile found is real and I confirmed it in the code. For Pixabay results, the dimensions we're handed describe the original photograph (PixabayProvider.tsx:86), while the picture actually shown in the preview pane is a much smaller web-sized rendition (line 80). So in principle we could measure one file and blame the failure of another — telling the user a picture is too big when really it just failed to download.

How much it matters in practice is the question. For that to actually happen, a source would have to report an original larger than about 537 megapixels; Pixabay's originals are nowhere near that, and neither are Openverse's. And now that Bloom serves a small stand-in for big local pictures, the too-large wording is close to unreachable in the shipping product anyway. The browser gives us no way to learn why a load failed, so no amount of client-side work makes this precise — Devin's own note calls it an accepted limitation rather than a bug.

FYI 1

The wording is nearly unreachable in the shipping product

Worth saying plainly, because it affects how much either decision above is worth: with your BloomDesktop fix in place, a big local picture gets a small stand-in that previews fine, so no message appears at all. In the gallery's own standalone mode no dimensions are supplied, so the neutral wording is what shows. That leaves the size-specific wording reachable only if an online source ever reports a >537-megapixel original, or if Bloom fails to build a stand-in and serves the original instead. It is a genuine backstop, not a routine path.
