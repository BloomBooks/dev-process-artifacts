Decision

A huge picture with transparent areas previews as a black block

When someone picks an image bigger than 40 megapixels, Bloom now builds a small stand-in copy to show in the chooser, and writes that copy as a JPEG. JPEG cannot store transparency, so if the original had see-through areas — a big line-art scan on a transparent background, say — those areas come out solid black in the preview. The person is then looking at something that misrepresents what they are about to insert, which is the same class of problem this card set out to fix.

It is a narrow case: it needs an image both enormous and transparent, and anything under the threshold is served unchanged and looks right. Nothing about the image that actually gets imported is affected — only the preview.

Decision

TIFFs still show an empty preview — is that in scope here?

The chooser's file filter accepts .tif and .tiff, but no browser will draw a TIFF, so picking one has always given an empty preview pane — exactly the symptom on this card, just from a different cause. Nothing in this change made that worse.

What it does do is make the behaviour odd: a TIFF over 40 megapixels now previews fine, because it gets converted to a JPEG stand-in on its way past the size threshold, while a smaller TIFF still shows nothing. So whether a TIFF previews now depends on how big it is, which is hard to explain to anyone.

Importing a TIFF already works, and works on purpose. Checked by running the real import path on one: Bloom loads it, sees a format browsers can't draw, and re-encodes it — so scan.tif arrives in the book folder as scan.png. The comment in that code says exactly why: “Non-web formats get saved as PNG so browsers can display them.” Bloom's book-packaging code likewise lists .tif/.tiff among the file types a book may contain. So a person can successfully put a TIFF in a book today — they just have to choose it blind, which is the same complaint as this card.

For your information

ImageGalleryApi is now disposable, to clean up the last temp preview

Each time a file is picked, the previous file's stand-in is deleted — so at most one is ever left over, the one for whatever was picked last. That one had nowhere to go, and the code's own comment waved at it being “swept up later” by something that does not exist. The class now implements IDisposable and deletes it there; Autofac already disposes it with the project's lifetime scope. Flagging it because it is a structural change rather than a bug fix, and it was made without asking.
