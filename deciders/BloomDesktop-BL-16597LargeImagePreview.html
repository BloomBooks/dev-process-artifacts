Decision 3 · new from Devin

Generating a preview freezes every other API request for a couple of seconds

Bloom's mini web server protects most of its API endpoints with a single lock, so only one such request is handled at a time. The new preview endpoint didn't say otherwise, so it takes that lock — and it holds it for as long as it takes to decode and shrink the picture, which for the 713-megapixel test scan is about two and a half seconds. For that whole time every other API request waiting on the same lock is stopped.

In practice this happens once, when someone picks a very large image in the chooser, and what they'd notice is other parts of the UI going briefly unresponsive. It isn't a correctness problem and it can't lose data. Devin was right about the mechanism: the endpoint is registered with only three arguments, and the fourth, requiresSync, defaults to true; the endpoint also isn't on the short list that gets routed to the separate thumbnails-and-previews lock.

The handler already has its own _previewLock, and that is what actually guards the cache it shares between requests — so the global lock is largely redundant here rather than load-bearing.
