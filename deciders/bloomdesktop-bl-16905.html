What this PR is about

Problem

The two Sample Shells we ship, The Moon and the Cap and A Family Learns about Immunisations, were several migrations behind (maintenance level 4; current is 14). They had also never been through the 6.5 per-page browser fix-up. So every user who opened one, or made a book from one, had to update it first, and opening the AI image editor or changing the page size brought up the “Bloom needs to update the pages of this book…” dialog. A brand-new book made from Basic Book or another template showed the same dialog, because nothing records that a new book needs no per-page pass.

What the PR does

  1. Bloom writes the body’s data-l1/l2/l3 in lower case, and removes the upper-case data-L1/L2/L3 it used to write. Upper case isn’t valid in data- names, and books that already had the lower-case form ended up with both. Nothing reads the upper-case form.
  2. The shells ship already updated. This is exactly what Update Book produces in SampleShells.BloomCollection, which is now English/English with no sign language and Traditional front/back matter. Before, its Tok Pisin second language leaked empty Tok Pisin boxes into the books. Each shell also ships the Default branding.css, which sizes the new back-cover badge and QR code. ShippedSampleShellsTests fails when a maintenance level is bumped and the shells fall behind, and points to a short README on re-updating them.
  3. A new book made from one of our factory templates is recorded as needing no per-page pass, at its page size. It holds only fresh front/back matter and the template’s non-extra pages. Books from other sources are left alone.

Worth knowing

  • The template fix was checked in Bloom by making a Basic Book in a scratch collection: it now starts with the stamp. Edit with AI wasn’t tried on it, because that collection has no subscription. Before the fix, the dialog was reproduced in your English Books collection. The QA notes on the card ask for the check.
  • Changing data-L* to data-l* is invisible to users. Browsers already treat attribute names as lower case, and nothing in Bloom, Bloom Player, Bloom Library or the harvester reads them by name. An older Bloom opening a book saved by this one adds its upper-case copy back, which is harmless.

Replies to John’s Reviewable comments

John left three blocking comments on the first version of this PR. The PR now does what he asked on the first, agrees with him on the second, and adds the fix his third question pointed to. These are the replies I would post, one per thread, with my own disposition set to “satisfied”. Resolving the threads stays his call.

  1. data-L1 (“Why are we changing these?? Upper-case … is not valid HTML”): “Agreed. The uppercase came from Bloom itself: Book.cs has set data-L1/L2/L3 on every book’s body since 2020. The old shells had lowercase, so updating left both. The first commit now makes Bloom write lowercase and remove any uppercase copy. The shells commit is exactly what Update Book produces after that. The only reader, previewMode.less, already uses lowercase.”
  2. Translation-group font-size (“probably should just stay”): “You’re remembering right. SetupThingsSensitiveToStyleChanges copies the first-language box’s font size onto the group on every edit-time load, for em-based padding (only cover titles use it today). Every edited book saves it, and the next editing load recomputes it. Taking it out of the shells would make them differ from what Update Book produces, and the next re-update would put it back, so it stays. Not saving it at all would be a separate, Bloom-wide change.”
  3. “Why only the sample shells, not the template books?”: “Good question. A book made from a template gets the current maintenanceLevel right away, but nothing recorded that it needs no per-page pass, so the first Edit with AI on a new Basic Book showed the update dialog; I reproduced it. The templates can’t carry that record themselves (several are generated from pug), so the third commit has Bloom record it when it creates a book from one of our factory templates.”
