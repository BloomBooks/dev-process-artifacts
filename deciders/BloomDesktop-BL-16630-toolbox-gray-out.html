Why it broke

The disabling overlay has always been a position: fixed element covering the whole toolbox viewport at z-index: 1001, headers included. What kept the headers normal was a rule in toolbox.less:271 targeting #toolbox h3. When the toolbox root became React/MUI in 6.4 the headers turned into AccordionSummary elements, that selector stopped matching, and the legacy #toolbox is now display: none — so the rule is dead code and the headers fell under the overlay.

The bright stripe was the long-standing calc(100% - 20px) becoming visible for the first time: the uncovered 20 px started landing on the teal active header instead of on panel-colored tool body.

Why the × isn’t dimmed but the bar beside it is

They are in different documents, so the overlay reaches one and not the other:

parent document — the edit tab the × (pure-toggle-label, EditTabPane.tsx:162) sits beside the drawer, not inside it
<iframe id="toolbox"> the dark bar, the headers, the tool body — and #disablingOverlay, whose position: fixed is bounded by this viewport

So the overlay can neither dim nor block the ×, in any version of Bloom, while the bar to its left is the top of the iframe and genuinely under it. That asymmetry is inherent to the iframe boundary and predates 6.4 — the 6.3 screenshot shows the same #282828 bar next to an undimmed ×. Left alone deliberately.

What the detour cost

Worth stating plainly, because it is the lesson of this branch. Widening the overlay to remove a gap that was invisible anyway:

  • dimmed the toolbox scrollbar and swallowed drags on it — and on a short window that scrollbar can be the only way to reach the switch that turns the mode off;
  • took three mechanisms to work around (pointer-events: none on the overlay, a separate blocking rule on the tool body, and opt-ins for the Help link, the switch and the Advanced header) where there had been one;
  • and introduced a failure mode that did not exist before: with dimming and disabling no longer the same thing, a control could look disabled while still responding.

The 20 px was load-bearing — it is the scrollbar allowance — just undocumented. That is why it got removed, and it is now documented rather than removed.

FYI · optional, pre-existing

A 5 px sliver of the wide buttons is still clickable while the tool is disabled

The overlay stops 20 px short of the panel’s right edge so it never covers the scrollbar. The tool body is padded by 15 px. Those two numbers don’t match, so when there is no scrollbar present, a 5 px-wide strip at the right-hand end of the full-width controls — Insert Segment Marker and Import Recording… — sits outside the overlay and still accepts a click while the tool is meant to be switched off.

This is not new and not a regression: the same 20 px gap and the same 15 px padding have shipped together for several releases, and nobody has reported hitting it. Devin raised it as an informational note on the final round.

There is a tidy fix — make the allowance 15 px so it lines up exactly with the padding, which would cover every control while still clearing the scrollbar. The reason I haven’t just done it is that it depends on a real WebView2 scrollbar fitting inside 15 px. Chromium’s classic scrollbar is 15 px, so it very likely does, but if it is 17 px then a sliver of the scrollbar gets dimmed again and we are partway back to the thing you just asked me to undo. You have the build in front of you, so this is a five-second check for you and a guess for me.
