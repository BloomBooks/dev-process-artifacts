The change

Two files. Both edits exist because of the same overlay.

  • ToolboxRoot.tsx — the tool headers get position: relative; z-index: 1005, and a background-color. The background is the part that isn’t obvious. A collapsed header paints no background of its own — the colour you see belongs to the Accordion root, and the root can’t be lifted along with the header, because a z-index there would create a stacking context around the AccordionDetails too and hoist the whole tool body out from under the overlay. So lifting only the header moved its text and left its background dimmed, which kept the stripe on every collapsed header until this was added.
  • audioRecording.less — the strip the overlay leaves uncovered on the right goes from 20 px to 15 px, and gets a name. 15 px does two jobs at once: it is the scrollbar’s measured width, so the scrollbar stays undimmed and draggable, and it is also @toolboxContentPadding — so with no scrollbar present the uncovered strip lands on the tool body’s right-hand padding instead of clipping ~5 px off the ends of Insert Segment Marker and Import Recording, where it used to leave them faintly undimmed and still clickable.

Why it broke

The overlay has always been a position: fixed element covering the whole toolbox viewport at z-index: 1001, headers included. What kept the headers normal was a rule in toolbox.less:271 targeting #toolbox h3. When the toolbox root became React/MUI in 6.4 the headers turned into AccordionSummary elements, that selector stopped matching, and the legacy #toolbox is now display: none — so the rule is dead code and the headers fell under the overlay. The bright stripe was the overlay’s uncovered strip landing on the teal active header for the first time.

Why the × isn’t dimmed but the bar beside it is

Different documents, so the overlay reaches one and not the other:

parent document — the edit tab the × (pure-toggle-label, EditTabPane.tsx:162) sits beside the drawer, not inside it
<iframe id="toolbox"> the dark bar, the headers, the tool body — and #disablingOverlay, whose position: fixed is bounded by this viewport

So the overlay can neither dim nor block the ×, in any version of Bloom. Predates 6.4 — the 6.3 screenshot shows the same #282828 bar beside an undimmed × — and left alone deliberately.
