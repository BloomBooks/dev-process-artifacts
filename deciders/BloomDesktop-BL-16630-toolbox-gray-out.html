Why it broke

The disabling sheet has always been a position: fixed element covering the whole toolbox viewport at z-index: 1001, headers included. What kept the headers looking and behaving normally was a rule in toolbox.less:271 targeting #toolbox h3. When the toolbox root became React/MUI in 6.4 the headers turned into AccordionSummary elements and that selector stopped matching them — the legacy #toolbox is now display: none, so the rule is dead code.

That is what made the long-standing calc(100% - 20px) suddenly visible: the 20 px it left uncovered started landing on the bright teal active header instead of on the panel-colored tool body. The gap itself was there in 6.3 too — measurable in the dark band above the headers — it just never fell on anything colorful.

Pixel evidence from the bug report

The sheet composites as 0.7 × #2E2E2E over whatever is beneath, which makes the diagnosis measurable rather than a matter of opinion. Sampling the reporter’s own two screenshots:

How the panel is disabled now

Dimming and click-blocking used to be one sheet. They are now two mechanisms, which is what buys back the scrollbar:

1005Tool headers — above the sheet, clickable
1002Show Playback Order switch, the Advanced header, the Help link — all opt back in to clicks
1001The sheet — dims only, pointer-events: none
—The tool body — pointer-events: none, which is what actually disables the controls
—The scrollbar — owned by an ancestor of the tool body, so untouched by either

Devin’s findings, one by one

  • Stuck in the mode when Advanced is collapsed — real, fixed, resolved. Its best catch. The Advanced section is used with initiallyOpen={false}, and inShowPlaybackOrderMode survives a page change because removePlaybackOrderUi() is called with leaveChecked=true and never clears the flag. So on returning to a page the sheet is back with the off switch inside a collapsed section whose header was inheriting pointer-events: none — no way out of the mode at all. Same failure mode the previous commit was written to prevent, so it was fixed here rather than deferred.
  • The Help link’s z-index has no effect — refuted, resolved. Devin reasoned that a statically-positioned <a> ignores z-index. But .help-link is a flex item of .ui-audioBody, and the Flexbox spec makes a non-auto z-index take effect on a flex item regardless of position. Decisive evidence: in the reporter’s 6.4 screenshot, taken with the sheet showing, “Help” measures #FFFFFF while white text that is under the sheet measures #6C6B6B in that same image. Re-raised as informational in round 3; still refuted.
  • Headers clickable → can collapse the tool mid-mode — you tested it, and round 3 explained why you were right. Devin’s code path is accurate as far as it goes: collapsing skips the activeToolChangedCallbacks notification, so the teardown never runs. What it missed is that the collapse self-reverts — ToolboxRoot.tsx:645 re-expands the section the instant expandedSectionId goes falsy, using the legacy current tool id that the skipped notification left untouched. So the stranded state is unreachable, which is exactly what you saw. Written up on the thread.
  • Round 3’s re-raise of the “stuck when collapsed” flag — stale. It came back with byte-identical text on the very commit that fixed it, while the same job’s own informational finding verifies that pointer-events: auto on “the TriangleCollapse Button” correctly re-enables its descendants — an opt-in that only exists in that commit. Confirmed present; nothing to do.
  • Informational, kept: that the header z-index only holds while no ancestor creates a stacking context. That is precisely how this bug arose, so it is now a comment beside the rule that depends on it. Informational, noted and left: that the sibling selector couples to the legacy DOM staying intact — fair, though both React paths that mount this tool (LiveToolBodyHost moving the node, and the legacyToolBodyHtml fallback, which injects the wrapper’s outerHTML) preserve the sibling relationship.

FYI · open thread, from Devin

The toolbox’s × close button is now dimmed but clickable

Before this branch, the sheet swallowed clicks across the entire toolbox, which included the × that closes the toolbox — it sits in the dark band above the tool headers. So while Show Playback Order mode was on, you could not close the toolbox at all.

Now that the sheet only dims, that button works again. What it doesn’t do is stop looking disabled: the band above the headers is still dimmed, so you get a grayed-out button that responds. That is the only cosmetic loose end left.

My recommendation is to leave it. The button working is better than the small trap of not being able to close the toolbox, and I confirmed the close path cleans up correctly — it routes through removeRecordingSetup() → removePlaybackOrderUi(page, true), so nothing is stranded on the page. The dimmed appearance of that band is also not new: sampling the reporter’s 6.3 screenshot gives #282828 there against #1A1A1A outside the sheet’s reach, so it has looked that way for several releases and only the clickability changed.
