Three adversarial reviews of the toolbox state

BloomDesktop · BL-16608-toolbox-3-react · PR #8447 · 2026-10-20

PR #8447 Reviewable BL-16608

What was done

Three reviewers were set on the toolbox's state layer at once, each told to be adversarial and to assume the design was worse than it looked: one on simplifying the state, one on naming, one on whether four words for a tool's relationship to the toolbox are really needed. They worked independently and read only; none of them changed anything.

Two of them converged, without seeing each other's work, on the same two findings — which is the strongest signal in the whole exercise.

Already fixed, not up for decision

Two real bugs came out of this and are committed:

  • A page's tool request was never cleared when the tool it asked for turned out to be the one already open. From then on Bloom would answer the question "which tool is in charge of this page?" with a tool that was not running — and the talking-book code reads exactly that to decide whether to play audio. So Talking Book could sit there visibly selected with its audio and highlighting dead. Reachable from the Sign Language template.
  • A lookup declared that it always finds a tool while its own body and comment said it might not. Both its callers already handled the "not found" case the type said was impossible.

The two reviewers who found the first one disagreed about whether it mattered; one called it harmless. Tracing it to the talking-book code settled that it is not.

What survived attack

Worth recording, because it is evidence the design is mostly sound: the page-change counter, the two separate sets of enabled and offered tools, and the page's tool request were each attacked directly and each survived with a concrete reason. One reviewer expected the page's tool request to be derivable from the page itself and showed why it is not.

1. Two words for one idea: open and current

Two of the three reviewers independently concluded that open and current are one idea with two names. The store keeps "open ⊆ offered" as an invariant at every write, so the re-check that turns open into current can essentially never fire. One reviewer found the single place it does fire — a defensive line meant to fall back to the Talking Book tool when nothing is offered — where the re-check defeats that intent and yields "no current tool" instead.

Against that, the same reviewer made the strongest argument on the other side: a derived read fails closed. It re-checks on every read, including from call sites that do not exist yet. Validation at the setter fails open — the first person to add a new way to open a tool and forget the check reproduces BL-16602, which cost a release. We already found one such hole, so the forgetting is not hypothetical.

2. A fifth word, “active”, in 20+ places outside the three files I changed

The vocabulary cleanup stopped at the edge of the three files I touched. The word “active” survives throughout the rest of the toolbox, the reader and talking-book tools, the test harness, the e2e helpers and the C# side — meaning open in some places, current in others, running in others, and enabled on the wire and in meta.json.

The worst single case is a list in the “More…” tool named toolsOffered which is very nearly the complement of what the store calls offered — in the very file the store's own comment warns about. There is also a setCurrentTool with no callers anywhere, and a shared helper named for showing and hiding that actually offers and withdraws.

None of this is a bug. It is the difference between a vocabulary that holds inside three files and one that holds everywhere a reader will look.

3. A latent bug and a C# one, both outside what this PR set out to do

Two further defects turned up that are real but are not this PR's doing:

  • A loop flag is assigned rather than accumulated when the toolbox adjusts its list for a page. If two tools ever both demanded a page type, one being withdrawn would reset the flag and the toolbox would then re-open the wrong tool. Only one tool demands a page type today, so it cannot bite yet.
  • The C# side strips the five characters “Check” from a tool name by length, without checking they are there. A malformed request silently truncates a real tool id and writes a junk entry into the book's meta.json.

4. Small, safe reductions in the store

The state reviewer found several pieces of ceremony it is confident about: a field in the snapshot that no React code reads (so changing it re-renders the whole toolbox for nothing), two accessors exported but used only by a test, a function that writes the state twice where once would do, and a parameter that is inverted and then un-inverted three times.

It also attacked three things and could not break them, which is worth knowing: the page-change counter, the two separate sets of enabled and offered tools, and the page's tool request all survived scrutiny with reasons.
