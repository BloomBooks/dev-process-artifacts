What this PR is about

Problem

Resizing the four quadrants of Bloom’s Collections tab doesn’t stick. Drag the dividers where you want them, go to the Edit tab, come back, and the layout has snapped back to the defaults. It’s a 6.4 regression — it worked in 6.3.

Cause

The splitter sizes only ever lived in CollectionsTabPane’s React state (the vertical one not even there — its sizes were hardcoded). That was invisible while each tab was its own WinForms control with its own browser, kept alive across tab switches. Once we moved to a single browser (BL-15894) and let App.tsx own the workspace root (BL-16012), only the active tab is rendered — so leaving the Collections tab unmounts the pane and discards its state.

What the PR does

  • A new module, persistedSplitterSizes.ts, keeps the sizes outside the component so they survive the unmount, and reads and writes them through the existing app/userSetting API. It’s keyed by setting name so a second splitter elsewhere can reuse it.
  • A new CollectionTabSplitterSizes user setting, so a custom layout now survives restarting Bloom too — which it never did, in any version.
  • The pane derives the sizes during render rather than mirroring them in state, which removes a derived-state useEffect.
  • What gets restored is guarded: an unreadable or wrong-shaped setting falls back to the defaults instead of leaving the tab blank, a late-arriving read can’t overwrite a layout the user just dragged, and each pane is floored at about 50px. That last one matters because the sizes are stored as proportions — a layout chosen on a large monitor, rescaled into a small window, could otherwise bring a pane back invisibly thin.

The two guards added in c17c02d37 have not been re-driven by hand — they are covered by reasoning and by the suite, not by a manual run.
  • The pane’s bottom half stays hidden if you add a source collection to a collection that had none, until you leave and return to the tab.   • minSizes is now passed explicitly to both splitters. It is a no-op — 50 is already the library’s default — kept so the number lives in our code next to the restore-time floor that has to match it.

Decisions

The Collections tab now waits on one more API call before it paints

Before this change, the Collections tab drew as soon as its list of collections came back from Bloom’s local server. It now also waits for the saved splitter sizes, because a splitter only reads its starting sizes once, on its very first render — paint before the sizes arrive and the saved layout is lost. The render gate therefore has two conditions instead of one. If that second request never answers, the user sees an empty Collections tab rather than a partly-drawn one. The request goes to Bloom’s own server on localhost and the first request has the same exposure, so this doesn’t introduce a new class of failure — but it does widen the surface, and it is the one part of this PR I would want a second opinion on before a beta ships.

Notes
FYI — the restore-time floor is approximate on the top/bottom divider

The splitter library keeps a pane from being dragged below 50px, but ignores that minimum when it applies saved starting sizes — which is exactly the path a restored layout takes. So restoreSizes enforces it. Nothing is laid out at the moment we need the number, so it uses the window size as a stand-in for the divider’s container. That is exact for the left/right divider (measured at exactly 50px) but the top/bottom one sits below the toolbar, so its floor lands a few pixels under — 46px when measured. It is a guard against a pane disappearing, not a promise of an exact size, and it is commented as such.
