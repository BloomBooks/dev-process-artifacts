What this PR is about

Problem

Bloom already lets a team work on a collection together through Team Collections, but only by having an administrator share a folder with a file-sync service such as Dropbox. Bloom has no control over that sharing: who can reach the folder, and what they may do there, is up to the sync service and the administrator's skill with it. Cloud Team Collections (BL-16531) keep the same way of working, but put the shared copy on a backend Bloom controls (Supabase). That control is what makes it possible for Bloom to have its own UI for sharing, in which administrators invite people and decide what each may do. This PR adds that UI. The backend ships separately and isn't deployed yet.

What the PR does

  • A new Share button in the Collection tab's top bar opens a Share dialog, built from the card's mockups. People are identified by their BloomLibrary.org sign-in; a signed-out user is asked to sign in first.
  • Starting to share: nothing is saved until an admin presses Start sharing. Before that, the dialog explains what sharing does and lists who will have access: the admin, and for a folder Team Collection everyone its history shows (Admin if the Team Collection lists them as an administrator, otherwise Editor). For a Team Collection it states the consequences (the old collection is frozen, and people need Bloom 6.6) and asks for confirmation.
  • After starting: admins invite people by email as Admin or Editor, change other people's roles, and remove them, all taking effect at once. Nobody can change their own role or remove themselves, so a collection always keeps an admin. Editors see the list read-only. Each person shows when they were last seen, or else when they were invited.
  • Stand-in backend: the dialog talks to an ICollectionSharingService whose only implementation keeps the record in sharing.local.json in the collection folder and enforces the rules the backend will. Freezing the old collection, requiring 6.6, creating the cloud collection and uploading books are separate, still-empty steps in CollectionSharingStarter.
  • Design overview: Design/CloudTeamCollections.md is a new, current overview of the whole Cloud Team Collections feature: architecture, checkout and check-in, the database, the server API, how a collection starts being a cloud collection, and what is still open.
  • TopBarButton and BloomButton can take an icon element (the MUI Share icon) instead of an image file.

Should the Share button be hidden until the backend is live?

Source: Devin, "Sharing dialog promises unavailable migration"

The dialog promises cloud access and a frozen Team Collection, but Start currently writes only a local membership file. Review the user-facing wording or availability before release.

Nothing hides the Share button, so everyone running a master (6.6 alpha) build sees it in every collection. If they press Start sharing, the dialog tells them their people now have access and, for a Team Collection, that the old collection is frozen and everyone needs 6.6. None of that happens: Bloom only writes a small file listing the people into the collection folder. For a Team Collection that's misleading, since teammates carry on as before and nobody is invited. Hiding it would also keep testers from filing the stand-in's limits as bugs, though the test ideas on the card already explain them.
