How the bug worked

Recorded because the fix only makes sense against the mechanism.

Application.Run registers the loop it starts as an application message loop. The off-screen browser runs one on its own dedicated thread. The CLI path never calls Application.Run itself — it waits with Thread.Sleep plus Application.DoEvents — so that browser thread’s loop was the only application message loop in the whole process.

So: building the .bloompub disposes a PublishHelper, which releases the browser, which ends that loop. WinForms concludes the application is exiting and raises Application.ApplicationExit. ApplicationContainer believes it and disposes itself — and it is the parent scope of the ProjectContext still in use. The epub step runs next, asks for BookServer, and gets ObjectDisposedException. The harvester treats any non-FontProblems exit code as failure, so the book was marked failed and nothing was uploaded — not even the .bloompub that had already been built.

In the desktop app this never fired, because the main thread’s loop is still running. It only ever bit a non-GUI entry point.

Decision 1 · Devin bug, open thread · the one that matters

After a crash on the browser thread, Bloom might not start again

Decided: fix it properly. Implemented in 645bbdf — FatalExceptionHandler now consults Program.MainMessageLoopIsRunning instead of the per-thread Application.MessageLoop. Devin’s follow-up pass independently marks the bug resolved. Correct for every worker thread, not just this one.

Application.MessageLoop is a per-thread flag meaning “a WinForms message loop is running on this thread”. Application.Run used to set it on the browser’s thread; a raw message pump does not. That flag is what Bloom’s fatal-error handler uses to decide how to die: FatalExceptionHandler.cs:95 calls ProgramExit.Exit() when true, and a bare Environment.Exit(1) when false. So an exception escaping a callback on that thread — a WebView2 event handler, or the _browser.Dispose() we post — now takes the hard-kill branch.

I first raised this as “Bloom vanishes rather than closing gracefully”, which undersold it. Devin’s second pass traced it further and it is worse: Environment.Exit does not run finally blocks, and Bloom releases its single-instance token in Main’s finally (Program.cs:751). So this path exits without releasing it — precisely the “zombie stops the next instance starting” condition that ProgramExit exists to prevent, and whose own comment says the listener-close and token-release “MUST be done so that Bloom can be started again without problems”. A user whose Bloom crashed this way could find it will not reopen.

What bounds it: the harvester and CLI path — the one this PR exists to fix — is not affected (UseFallback short-circuits first, and only WorkspaceView ever clears it, which the CLI never builds). It needs a crash on that specific thread to trigger. And how much a stale token actually costs depends on the token’s implementation: an OS mutex is released when the process dies whatever happens, a lock file is not — worth checking before deciding how hard to fix.

Decision 3

Decision 4 · Devin, informational

Two ways this class now hangs where it used to throw

Decided: leave as is. Neither path is reachable from any current caller, so no hardening was added.

Devin raised two related observations, and both are fair. First: disposing the synchronization context (which the new pump does, to avoid leaving a control to be finalized on a dead thread) makes Post a silent no-op afterwards, so calling Navigate or RunJavascript on an already-disposed browser would block forever instead of throwing. Second: if the pump’s GetMessage ever returned an error, the exception lands in a catch whose _startupError/_ready handshake the constructor has already consumed, so it would be invisible and callers would block forever.

Neither is reachable today. No caller reuses or re-disposes an instance — PublishHelper.ReleaseBrowser nulls its field and BookProcessor uses using — and GetMessage only fails on an invalid window handle, where we pass IntPtr.Zero. They are latent sharp edges for whoever touches this next, not live bugs. A hang is a nastier thing to debug than an exception, which is the only reason to care.

Whether to harden the hang-instead-of-throw paths
~15 lines in one file, no behavior change on any live path — a _disposed flag that RunAndBlock checks, and faulting any pending waiter if the pump exits unexpectedly.
recommended

Recommending “leave as is” because neither path is reachable from any current caller, and this PR is a targeted fix for a live production outage — hardening unreachable paths widens it for no present benefit. Worth doing if you would rather not leave the trap for the next person; the Leave comment box will put the reasoning next to the code instead.

Decision 8 · Devin, open thread

Each off-screen browser now leaves a small WinForms bookkeeping object behind

Decided: leave as is, and write it down. The reasoning is now a code comment beside ctx.Dispose() in 645bbdf, and recorded on the PR thread.

WinForms keeps a per-thread record (a ThreadContext) for any thread that uses its plumbing. Application.Run’s teardown used to remove that record and release the thread handle it holds; the private pump never does. The record still gets created — implicitly, the moment we install the synchronization context — and disposing that context only disposes the marshaling control, not the record. WinForms holds it in a static table, so nothing reclaims it.

Bloom makes one off-screen browser per batch of page checks, so each batch leaves one of these behind. Devin’s own read is that it will not grow without bound — the table is keyed by native thread id, and ids get reused and overwritten — and the per-instance cost is small. So this looks like a slow, self-limiting drip rather than a leak that ends in trouble, but it is a genuine change from the previous teardown and nobody has measured it.

What to do about the retained ThreadContext
No product code — publish repeatedly in one session and watch the handle count. Turns a guess into a number, and the number decides whether anything else is needed.
Moderate — it removes the per-batch churn entirely and would also settle Decision 1, but it reverses ReleaseBrowser’s deliberate “don’t keep an idle WebView2 around” intent, so it is a real design change rather than a tidy-up.
recommended

Recommending “leave as is” because the cost is small and self-limiting by Devin’s own analysis, and the alternative that would truly remove it (option two) undoes a deliberate design decision for a problem nobody has yet observed. If you would rather not take that on trust, option one is cheap.

There is a middle-ground fix, and it is one word away from the sibling branch

Andrew asked whether something existed between the two candidates: broader than the minimal fix, but still a boolean check rather than a message pump. There is, and it is better than the minimal fix in a way worth recording even though this PR is what lands.

Program.RunningInConsoleMode already exists, and is set at Program.cs:224 for every command-line verb — hydrate, upload, download, getfonts, changeLayout, createArtifacts, spreadsheetExport, spreadsheetImport, sendFontAnalytics. So the guard becomes: don’t subscribe to ApplicationExit at all when that is set.

Three reasons it beats the RunningHarvesterMode guard on the sibling branch. It covers every CLI verb, closing the exact gap that made the minimal fix unattractive (the other verbs never set the harvester flag). It has no ordering hazard: RunningInConsoleMode is true before any container exists, whereas CreateArtifactsCommand sets RunningHarvesterMode after constructing the container and works only because the event fires later. And it asks the honest question — “is there no GUI?” rather than “is this the harvester?”

Its residual exposure is close to nil today: the only other ApplicationExit subscribers are in ApplicationUpdateSupport (only after an update download — a GUI flow) and Edit/AudioRecording (editing only), neither reachable from a CLI verb. What it does not do is stop the false signal being broadcast, so a future CLI-reachable subscriber silently reopens the bug.

Nothing was changed on the strength of this — Decision 3 stands and the pump change is what is on the PR. Recorded because it is the strongest form of the cheap option, and because if this release needs de-risking it is the obvious swap. The two should not both land: with the pump in place the guard is dead code.
