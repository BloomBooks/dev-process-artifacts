Six things need your call

None of these block the PR mechanically — the gate is green and everything safe has been fixed. Each is open as its own thread on the PR, and each will get a reply recording whatever you decide.

1. Sample words come back on one line instead of one per line

Devin (Investigate) · confirmed by hand · PR thread · DecodableStagesSetup.tsx:438

On the Sample Words tab there is a box called "Type Words Here". People naturally type one word per line. The old dialog deliberately displayed the saved list that way too: it stored the words space-separated but converted the spaces back to line breaks when filling the box. The new dialog shows the stored value verbatim, so after you press OK and reopen the dialog, a list you typed down the page comes back as one long wrapped line. Nothing is lost — the words are saved correctly either way now — but it looks different and it makes a long list harder to read and edit. This is purely about presentation.

2. Deleting a letter has no effect until restart, in allowed-words mode

Devin (Bug, non-severe) · PR thread · readerTools.ts:398

This branch changed a shared function so that Bloom's language data is rebuilt from scratch only when the collection defines its stages by letters, not when it defines them by allowed-word lists. The change is deliberate: skipping the rebuild is what lets the setup dialog still show a matching-words preview if the user flips back to the letters approach without saving. The side effect is that the rebuild was also the only thing that ever removed letters — the load path only ever adds them. So in a collection using allowed-word lists, a letter combination the user deletes from the alphabet stays registered for the rest of the session. Bloom decides word length by counting letter combinations, so a deleted combination keeps counting as a single letter and the Leveled Reader's word-length checks and page markup can be wrong until Bloom is restarted. Narrow, but it is a wrong answer shown to the user.

3. Special language symbols are ignored in the dialog, so some typed words vanish from the preview

Devin (Bug, non-severe) · confirmed by reading the code · PR thread · decodableStagesUtils.ts:103

Some languages define special marks — a syllable break, a stress mark, a morpheme break — that Synphony treats as always acceptable inside a word, whatever stage the reader is at. The new dialog tries to honour them, but it reads them from its own copy of the Synphony data, and that copy is always empty: the fields are not part of the data class at all, and the dialog runs in a different bundle from the one where the real data lives. (That bundle split is exactly why the dialog fetches its matching words from the toolbox rather than computing them locally.) The visible effect, only for collections that define such a mark: a word the user typed containing that mark is dropped from the "matching words" list, while a word containing the same mark that came from a sample text is kept — so one list disagrees with itself.

4. Switching tabs can silently drop a letter from your stages

Devin (Investigate) · PR thread · DecodableStagesSetup.tsx:562

Keeping the stages consistent with the alphabet is clearly intended: if a letter is no longer in the alphabet, it should not remain assigned to a stage. The concern is when it happens. Only the active tab is rendered, so every time the user leaves the Decodable Stages tab and comes back, this reconciliation runs again and quietly removes any letter that is not in the alphabet box at that moment. If someone is midway through retyping a letter on the Letters tab and clicks back to Stages to check something, that letter is stripped from every stage, with no warning and no undo. I have not reproduced this by hand — it is a code-reading finding — so it is worth a tester confirming before deciding how far to go.

5. The settings file now records more than the old dialog wrote

Devin (Investigate) · PR thread · DecodableReaderSetupDialog.tsx:73

The old dialog rebuilt the settings from scratch out of the form fields, so only the handful of things it knew about were ever written to disk. The new dialog copies the live settings object and saves the whole copy. Two consequences worth an explicit yes or no. First, any extra working data that happens to be hanging off a stage at that moment would now be written into the settings file. Second, the old rule "don't save a stage that has no data in it" is gone, so an empty stage the user created is saved — and the dialog now deliberately creates an empty Stage 1 for a collection that had none. Both look like intentional consequences of the new always-shows-a-row design, but they change the shape of a file Bloom writes, so it is worth confirming rather than discovering later.

6. The dialog re-implements Synphony's word-splitting (now pinned by tests)

Devin (Investigate) · mitigated · PR thread · decodableStagesUtils.ts:67

Deciding whether a word is decodable means splitting it into the letter combinations the language teaches. Synphony already does this. The new dialog contains a second copy of that logic, used for words the user types (sample-text words still go through Synphony's). Two copies means the same word can in principle get two different answers within a single list. I added tests that run both implementations over the same words and assert they agree, with a guard so the comparison cannot pass trivially — so any future drift will fail the build. Comparing them line by line I found one genuine difference today: the new copy lower-cases the alphabet before matching and Synphony's does not, which makes the new one slightly more forgiving for an alphabet typed with capitals. Harmless in practice, but it is a real divergence rather than a perfect copy.
