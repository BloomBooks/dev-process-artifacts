What this PR is about

Problem

The Decodable Reader tool's Set Up Stages dialog was still the original jQuery dialog, living in an iframe with its own styling and looking nothing like the rest of modern Bloom. It is the screen a teacher uses to define a collection's alphabet, its sample words, and the reading stages that decide which words count as decodable — so it is both prominent and hard to change.

What the PR does
  • Rebuilds the Decodable side of the dialog as a React dialog rendered in the workspace root, with the Letters, Sample Words and Decodable Stages tabs as React components and a drag-sortable stage list. The Leveled Reader's dialog is deliberately untouched and still opens the legacy one.
  • Fixes what saving writes: sample words typed one per line are no longer run together into a single nonsense word, duplicates are dropped, and a stage left empty is discarded with the rest renumbered — matching what the old dialog did.
  • Stops deleted letters from going on affecting word analysis in allowed-words mode, by rebuilding the alphabet without discarding loaded vocabulary.
  • Restores what the old dialog told the user: unreadable files in the Sample Texts folder are listed again with an explanation instead of silently vanishing, an empty folder gets a message, and extension matching is case-insensitive.
  • Exposes the toolbox frame's Synphony data to the dialog across the bundle boundary, so the matching-words preview sees the same special symbols and word lists that Bloom itself uses.
  • Adds a Playwright e2e journey test covering the whole open → edit → save → reopen path across that frame boundary.

1. What should happen to a stage's word list file?

In the allowed-words mode, each reading stage can point at a word list file in the collection. Two behaviours around deleting those files are now inconsistent, and they pull against each other, which is why this is a question rather than a fix.

Clicking the trash icon next to a file deletes it from disk immediately, before anything is saved — so if the user then presses Cancel, the saved settings still name a file that is no longer there. Meanwhile, removing a whole stage now deletes nothing, where the old dialog cleaned the file up once no stage referenced it — so unused files accumulate instead.

Fixing either one the obvious way makes the other worse: making stage-removal delete immediately widens the Cancel problem, and deferring both to Save changes behaviour the old dialog has always had.

2. The dialog is never unmounted, so a listener accumulates

Every time the dialog is shown, Bloom detaches the old container element and makes a new one — but detaching a container does not unmount the React tree inside it, so each dialog session leaves its component alive forever.

For this dialog that matters because the Sample Words tab registers a listener for window focus and removes it in its cleanup, which now never runs. So each time a user opens the dialog and visits that tab, one more listener is left behind, and every later click back into Bloom re-queries the Sample Texts folder once per abandoned session. In a long editing session Bloom does progressively more useless background work and holds on to more memory.

This is not specific to this dialog — the same non-unmounting applies to everything shown that way. This one is just the first to add a window-level listener, which is what makes it visible. That is why it has not been fixed here unilaterally.
