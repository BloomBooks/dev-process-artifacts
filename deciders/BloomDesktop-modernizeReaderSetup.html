Two more bugs, found and fixed on the rebased branch

Devin reviewed the rebased head and found a genuine dead-end, then a hole in my fix for it. Both are now fixed and verified.

025fc05 — The edit view could be left locked with no way out.

Opening the dialog locked the edit view before the dialog was rendered, while the only code that unlocks lives inside the dialog. If the render failed, the user was left unable to touch the book, with no dialog to dismiss, until Bloom restarted — and it was reachable, because clicking Set Up Stages before the reader settings finish loading makes the component throw. The lock is now set from a mount effect, so a failed render never locks anything.

6e3e779 — Closing could later unlock the edit view spuriously.

close() tried to disarm itself, but the handle was re-armed by the very re-render that closing triggers, so a later close request re-ran the unlock. Closing is now idempotent, and the handle is published from an effect instead of during render (which also removes the assign-module-state-while-rendering pattern Devin had flagged from its first review).

Both verified in a running Bloom by counting the actual setModalState requests: one on open, a second on Cancel, and still only two after a further close request — where previously a third would have fired.

Unreadable sample-text files vanish without explanation

Your request: focus on behavior changes from pre-PR code · PR thread (open) · DecodableStagesSetup.tsx:33

Not changes from pre-PR code: the extension list is identical (txt/js/json — same as the model's getReadableFileExtensions), and the old dialog compared case-sensitively too, so a .TXT file was rejected before this PR as well. Devin framed both as defects; neither is a regression.

What did change is that the old dialog explained itself and the new one is silent. Pre-PR it listed every file in the Sample Texts folder and annotated the ones it could not use — "Cannot read this format" for an unsupported extension, "File needs .TXT extension" for one with no extension — and when any were present it revealed a help link, "Help exporting and converting files to use as sample texts". An empty folder got a "please add texts" message. The new dialog filters those files out silently and shows nothing for an empty folder, so someone who drops a .docx in there gets no hint why it is ignored.

All the strings still exist in Bloom.xlf and are already translated (ReaderSetup.FormatNotSupported, .FileNeedsTxtExtension, .HowToExport), but are now referenced only from the legacy ReaderSetup.pug — orphaned for this path.
