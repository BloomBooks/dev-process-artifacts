C — the answer is "leave as is", with a reason

You asked me to make sure the logic is correct. It is, and the two entry points only look different. selectGPCWordNamesWithArrayCompare and selectGPCWordsFromCache both call libSynphony's selectGPCWordsWithArrayCompare with identical arguments; the first then plucks Name off the results, the second memoizes them through theOneWordCache. Same selection routine — which is why the dialog's list and the toolbox's panel produced the same five words when I compared them.

The only practical difference is caching: the dialog's path is uncached, so it always reflects current data. No change made; recorded in a comment on getDecodableStageMatchingWords so it is not re-raised.

D. Unexpected file types vanish — what actually changed

Your round-2 request: focus on behavior changes from pre-PR code · PR thread (open) · DecodableStagesSetup.tsx:33

I read the legacy handler. The extension list itself is not a change — the old dialog used exactly ["txt","js","json"], the same as the new dialog and the same as the model's getReadableFileExtensions. And it compared case-sensitively too, so a .TXT file was rejected before this PR as well. Devin framed both as defects; neither is a regression.

What genuinely changed is that the old dialog told the user, and the new one says nothing. Pre-PR it listed every file in the folder and annotated the ones it could not use: "Cannot read this format" for an unsupported extension, "File needs .TXT extension" for a file with no extension at all. When any such file was present it also revealed a help link, "Help exporting and converting files to use as sample texts". An empty folder got a "please add texts" message. The new dialog filters those files out silently and has no empty-state message, so a user who drops a .docx in the folder now gets no hint why it is being ignored.

The three strings for those messages still exist in Bloom.xlf (ReaderSetup.FormatNotSupported, .FileNeedsTxtExtension, .HowToExport) but are now referenced only from the legacy ReaderSetup.pug, so they are effectively orphaned for the decodable path.
