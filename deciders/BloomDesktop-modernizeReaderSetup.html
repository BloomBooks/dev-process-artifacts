Answering your question on #5

You said you were confident we don't want to change what gets persisted, and asked what the complication was in going back to what we had. The honest answer is that I overstated it, and for the part you care about there is nothing to go back to — the shape already matches.

I inspected the reader settings files of all 25 collections on this machine, including the one this new dialog had just written. Every stage in every file has exactly the keys name, letters, sightWords, allowedWordsFile — the file the React dialog wrote is key-for-key identical to the ones the legacy dialog wrote. The reason is that the dialog clones model.synphony.source, whose stages are the raw objects parsed from the settings file; the words and allowedWords arrays live on separate ReaderStage instances that are never cloned. So the "extra runtime fields could leak into the file" half of the finding does not happen.

That leaves exactly one real difference, which is the only thing left to decide (item A on the right): the legacy dialog dropped a stage with no letters, no sight words and no word-list file, and renumbered the rest. The new dialog saves it.

And on #6 — my estimate was wrong

I had called this moderate work, on the grounds that typed words aren't in the language data yet so there'd be nothing to segment them against. That was mistaken. Synphony's LanguageData.getGpcForm takes the grapheme list as an argument and reads no state off the instance — the alphabet currently in the dialog is exactly what that argument is for. So the dialog now calls Synphony's own routine directly: a few lines added, about 24 lines of duplicated logic deleted. Your instinct was right and it was cheaper than I said.

Four things left

One is the discussion you asked for, narrowed to a single concrete question. The other three came out of Devin's later passes; all three are pre-existing on the branch rather than anything preflight introduced, so I left them alone rather than widening the change myself.

A. Should an empty stage still be saved?

Your #5, narrowed · PR thread (left open) · DecodableReaderSetupDialog.tsx:73

As above, the persisted field shape already matches the legacy dialog exactly, so nothing needs reverting there. The one genuine behavior difference is that the legacy dialog silently dropped a stage that had nothing in it — no letters, no sight words, no word-list file — and renumbered what was left, whereas the new dialog saves it. Related: the new dialog deliberately creates an empty Stage 1 for a collection that has no stages at all, so that a user always sees a row to work with. If we restore the drop-empty-stages rule, that materialized Stage 1 would not survive a save — which is exactly what the old dialog did (one collection on this machine has zero saved stages, so it really did happen).

B. Kept sample words still carry the old alphabet's segmentation

Devin (Investigate), about my #2 fix · PR thread · synphony_lib.ts:40

A fair critique of the fix you approved. Clearing the grapheme list stops a deleted letter combination from being miscounted, which was the reported bug. But the sample words we deliberately keep were each split into letters when they were loaded, and they store that split. So after the alphabet changes in allowed-words mode, those stored splits still reflect the old alphabet until something reloads the words. It is strictly better than before, and it only surfaces if someone changes the alphabet in allowed-words mode and then switches back to stages mode without saving. Fully resolving it means re-splitting the kept words, or giving up the preview by doing the full reset again — which would undo the trade-off you just settled.

C. The dialog asks Synphony a different question than the rest of the code

Devin (Investigate) · PR thread · readerTools.ts:520

The new dialog's matching-words helper passes true as the first argument, which routes to one libSynphony function; the legacy dialog and the toolbox's own stage-words call both pass false, which routes to a different one. So the dialog's list is computed by a different routine than the rest of the reader code uses. In testing they agreed exactly — the dialog and the toolbox panel produced the same five words for the same stage — so there is no visible discrepancy today. But I could not cheaply prove the two routines are equivalent in general, and this is pre-existing on the branch rather than something preflight introduced.

D. Sample text files of an unexpected type vanish silently

Devin (Bug, non-severe) · PR thread · DecodableStagesSetup.tsx:33

The dialog filters the Sample Texts folder listing against its own hard-coded list of file extensions, so a file of any other type simply does not appear — with no message explaining why. Two wrinkles: the model already has its own idea of which files are readable (getReadableFileExtensions), so two separate lists can drift apart; and the dialog's list is case-sensitive as written, so a .TXT file would be filtered out. Which extensions ought to show is a product question, so I have not changed it.
