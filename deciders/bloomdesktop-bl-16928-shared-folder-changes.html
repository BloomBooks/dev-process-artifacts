What this PR is about

Problem

In Bloom 6.6, an administrator will be able to move a folder (Dropbox or LAN) Team Collection to the new cloud collections (BL-16531, BL-16676). While the books are uploaded, the old shared folder must stop changing, or a check-in, rename or delete made on the old system after a book was copied would be lost. Blooms older than 6.6 are shut out by the existing MinimumBloomVersion gate (BL-16690), which the migration sets to 6.6. This PR is for the 6.6 Blooms still on the old Team Collection until the upload finishes.

What the PR does

  • It puts such a Bloom into the existing Disconnected mode, with a message saying why. That mode already blocks every write to the shared folder, while books checked out here and new local books stay editable.
  • AllowSharedFolderChanges (default true, written only while false) and CloudCollectionId are new collection settings, round-tripped like AllowCheckouts.
  • FolderTeamCollection.CheckConnection() runs at startup and before every check-out, check-in, Forget Changes and Force Unlock. It reads the shared settings and reports the pause as the connection problem: "the administrator has paused changes", or "moved to Bloom's cloud sharing; close and reopen to switch over". It runs after the existing folder, network and Dropbox checks, and unreadable settings never disconnect.
  • MakeDisconnected records the reason and leaves out the "click Reload" advice. A running Bloom switches as soon as it notices the shared settings change, checking only the pause there, so a network blip can't disconnect an ordinary collection.
  • The book status panel shows the pause message. BL-16691's paused-checkouts note is localized. The strings are translate="no".

The first version guarded every write operation separately. It is still in the branch history. Reusing Disconnected mode cut the change from about 1,300 lines to 600, of which about 400 are tests.

What changed this run

The implementation was rewritten to reuse Disconnected mode (dd15d979b6). The local review then found that the mid-session path ran the whole connection check, so a momentary blip could disconnect an ordinary collection. It now checks only the pause. Master was merged in, and the setup code that cleared the pause for a new Team Collection made from a paused copy was removed, since such a copy never carries the pause. Commits.

Worth knowing

  • Not yet tried in a running Bloom with two installations. The test ideas on the card describe how to switch the pause on by hand.
  • Rename and delete don't run the connection check first. So a running Bloom could still do one between the pause being written and its noticing the change, normally seconds after Dropbox syncs it.
  • The administrator's own Bloom stays connected right after pushing the pause, until its next check-out or check-in, or a restart. In real use that Bloom is the one switching to the cloud.
