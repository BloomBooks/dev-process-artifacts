What this PR is about

Problem

In Bloom 6.6, an administrator will be able to move a folder (Dropbox or LAN) Team Collection to the new cloud collections (BL-16531, BL-16676). While the books are uploaded, the old shared folder must stop changing, or a check-in, rename or delete made on the old system after a book was copied would be lost. Blooms older than 6.6 are shut out by the existing MinimumBloomVersion gate (BL-16690, in 6.4 and 6.5), which the migration sets to 6.6. This PR is for the 6.6 Blooms that are still on the old system until the upload finishes. It was first written as a 6.5 patch, but that was judged too large a change right before the 6.5 beta, so it now targets master.

What the PR does

  • A new AllowSharedFolderChanges collection setting, on the same pattern as AllowCheckouts: default true, written only while false, picked up mid-session. The shared folder's copy decides. Local settings are used only when the shared copy can't be read, so an administrator's hand edit is pushed up and then pauses everyone.
  • While it's false, nothing writes to the shared folder: check in (including first check-ins), check out, rename, delete, Forget Changes, Force Unlock, collection files and color palettes. The core write methods refuse before doing anything, and the API layer refuses too.
  • Editing books already checked out keeps working, as does deleting a never-shared book. Collection Settings and the reader-tool settings refuse to open while paused.
  • The status panel disables the affected buttons and explains. Once the shared settings carry a CloudCollectionId, it says the collection has moved to Bloom's cloud sharing and to reopen the collection to switch over; before that, that the administrator has paused changes. The strings, and BL-16691's paused-checkouts note, are translate="no" in Bloom.xlf while the feature is in development.
  • A new Team Collection made from a copy of a paused collection starts out unpaused.
