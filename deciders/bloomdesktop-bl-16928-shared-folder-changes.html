What this PR is about

Problem

In Bloom 6.6, an administrator will be able to move a folder (Dropbox or LAN) Team Collection to the new cloud collections (BL-16531, BL-16676). While that happens, the old shared folder must stop changing, or a check-in, rename or delete made on the old system after a book was copied to the cloud would be lost. AllowCheckouts=False (BL-16691) only stops new checkouts, and MinimumBloomVersion (BL-16690) would lock people out of the books they have checked out. The fix has to ship in 6.5, well before 6.6.

What the PR does

  • A new AllowSharedFolderChanges collection setting, on the same pattern as AllowCheckouts: default true, written only while false, picked up mid-session. The shared folder's copy decides. Local settings are used only when the shared copy can't be read, so an administrator's hand edit is pushed up and then pauses everyone, the administrator included.
  • While it's false, nothing writes to the shared folder: check in (including first check-ins), check out, rename, delete, Forget Changes, Force Unlock, collection files and color palettes. The core write methods refuse before doing anything, and the API layer refuses too.
  • Editing books already checked out keeps working, as does deleting a never-shared book. Collection Settings and the reader-tool settings refuse to open, because their changes couldn't be shared.
  • The status panel disables the affected buttons and explains. The message says the collection has moved to Bloom's cloud sharing (Bloom 6.6 needed) when the shared settings carry a CloudCollectionId, and otherwise that the administrator has paused changes. These and BL-16691's paused-checkouts note are all translatable, in Bloom.xlf.
  • A new Team Collection made from a copy of a paused collection starts out unpaused.

Worth knowing

  • Nothing has been clicked through in a running Bloom with two installations; it's covered by unit tests only (38 new C# tests). The test ideas on the card describe how to switch the pause on by hand.

1. Switching the pause off

Once the shared folder's settings say changes are paused, every Bloom refuses to write there, the administrator's included. That also stops the administrator writing the setting that would switch the pause off. So, as built, the only way to undo it is for someone to edit the settings inside the shared folder's Other/Other Collection Files.zip by hand. In real use the pause is meant to be permanent, because the collection is moving to the cloud, and the design doc's recovery step already has support staff reset it. It does make testing awkward, and a pause set by mistake can't be undone from Bloom. I recommend leaving it: an "unpause" exception would reopen a gap in exactly the rule this PR exists to enforce.

2. Two rare races show an error dialog

Both need the pause to arrive at an exact moment. In each case no work is lost; the person just sees Bloom's "something went wrong" dialog instead of the friendly explanation.

  • Deleting a book (CollectionModel.cs:654). If the pause arrives while the "delete this book?" confirmation is open, the book isn't deleted, the selection is cleared, and the error dialog appears (line 684).
  • Closing the collection (TeamCollectionManager.cs:287). If the pause arrives in the instant between checking and pushing the collection files, the refusal escapes the closing handler.

The pause is set once, during a migration, so hitting either is very unlikely. I recommend leaving them.

3. Settings dialogs while paused

While paused, Collection Settings (WorkspaceView.cs:1463) and the reader-tool settings (ReadersApi.cs:361) show the pause message instead of opening. Saving them would change this computer only: nobody else would get the change, and the shared folder's copy would replace it at the next start. This is behavior the implementing agent chose, so it's here for your confirmation. I recommend leaving it; it's the least surprising outcome.
