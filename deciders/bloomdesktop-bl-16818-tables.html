What this PR is about

Problem

Bloom has no way to lay content out in a grid. Authors who want a vocabulary list with pictures or a simple timetable fake it with positioned text boxes, which drift out of alignment and do not translate as one unit. Tables are a Pro-tier feature, and the people who translate Pro books often have no subscription, so a table has to stay translatable and publishable for them while they are kept from building new ones.

What the PR does

  • Adds a Table, built by the bloom-table library (pinned at GitHub tag dist-v0.1.0), as a canvas element from the Canvas tool and as a section type in Change Layout. Bloom supplies the cell content (a Bloom text box, a picture, a video, a nested table) and strips editing markup before save.
  • Gates it: Pro tier plus the tables experiment. Below Pro or with the experiment off, an existing table can still be typed in, translated and published from a derivative, but not restructured.
  • Teaches shared editing code about tables: which of the table's history and CKEditor's gets the next Undo, a press on a row or column boundary starting a resize, copy and paste in a cell, the format gear's position, and picture refitting. A picture cell made after the page loaded gets its own drawing surface, so a press on its picture selects that cell.
  • Improves automation: step captions and per-process experiment settings for e2e runs; under --automation as well as --e2e the browsers share one WebView2 environment so problem dialogs are visible over the debugging port (except legacy-DPI dialogs such as Settings, which need their own); and the e2e helpers refuse a Bloom without --e2e instead of flooding it with problem dialogs.

Decisions

1. Text cells ignore clicks after a picture goes into a cell

On a canvas page, after you put a picture in one cell of a table, clicking another cell's text does not put the cursor there. The first press is taken as the start of dragging the whole table, and when the button comes up the press lands on the page's drawing surface instead of the text, so text editing never starts; the selection can even jump to the page's background picture. Before a picture goes in, the same clicks work. The tables-core e2e test now checks this and fails on it. The cause is in the canvas element manager's mouse handling, not yet pinned down.

2. Undo between typing and table changes, the other direction

A table's changes (add a row, change a cell's type) and typing in its cells go to two separate undo histories, and Bloom decides which one gets the next Undo by which changed last. This run fixed one wrong case: after "add a row, type, add a row, Undo", the next Undo used to take the first row instead of the typing. Reading the code, the mirror case looks wrong too, though I have not reproduced it: after "type, add a row, type, Undo", undoing the second typing marks the typing history as the latest again, so the next Undo would take the first typing instead of the row. Devin's open thread "Structural undo drops text history" is about the same area: a table Undo rebuilds the cells, which discards their typing history.

3. The "takes a video in a cell" e2e test fails

In tables-extended, the test after "re-tiles the cells when the whole table is made wider" fails: a cell's right edge ends up outside the table (cell from x=520 to 580, table ends at 563). It failed the same way at the start of this session on an older build, so this run did not cause it, and because the file runs its tests in order, the six tests after it do not run at all.
