What this PR is about

Problem

Bloom has no way to lay content out in a grid. Authors who want a vocabulary list with pictures or a simple timetable fake it with positioned text boxes, which drift out of alignment and do not translate as one unit. Tables are a Pro-tier feature, and the people who translate Pro books often have no subscription, so a table has to stay translatable and publishable for them while they are kept from building new ones.

What the PR does

  • Adds a Table, built by the bloom-table library (pinned at GitHub tag dist-v0.1.1), as a canvas element from the Canvas tool and as a section type in Change Layout. Bloom supplies the cell content (a Bloom text box, a picture, a video, a nested table) and strips editing markup before save.
  • Gates it: Pro tier plus the tables experiment. Below Pro or with the experiment off, an existing table can still be typed in, translated and published from a derivative, but not restructured.
  • Teaches shared editing code about tables: which of the table's history and CKEditor's gets the next Undo, a press on a row or column boundary starting a resize, copy and paste in a cell, the format gear's position, and picture refitting. A picture cell made after the page loaded gets its own drawing surface, so a press on its picture selects the picture and shows its toolbar, with Choose image. One press on a cell's text starts typing there, where other canvas elements take a first press to select and a second to edit. A picture cell's padding slider says "Padding between border and image" and starts at the padding the cell really has, so a picture can be made to fill its cell.
  • Improves automation: step captions and per-process experiment settings for e2e runs; under --automation as well as --e2e the browsers share one WebView2 environment so problem dialogs are visible over the debugging port (except legacy-DPI dialogs such as Settings, which need their own); and the e2e helpers refuse a Bloom without --e2e instead of flooding it with problem dialogs.

Decisions

1. Undo between typing and table changes, the other direction

A table's changes (add a row, change a cell's type) and typing in its cells go to two separate undo histories, and Bloom decides which one gets the next Undo by which changed last. The last run fixed one wrong case: after "add a row, type, add a row, Undo", the next Undo used to take the first row instead of the typing. Reading the code, the mirror case looks wrong too, though I have not reproduced it: after "type, add a row, type, Undo", undoing the second typing marks the typing history as the latest again, so the next Undo would take the first typing instead of the row. Devin's open thread "Structural undo drops text history" is about the same area: a table Undo rebuilds the cells, which discards their typing history.

2. The "takes a video in a cell" e2e test fails

In tables-extended, the test after "re-tiles the cells when the whole table is made wider" fails: a cell's right edge ends up outside the table (cell from x=520 to 580, table ends at 563). It has failed the same way since before the picture-cell work, and because the file runs its tests in order, the six tests after it do not run at all.
