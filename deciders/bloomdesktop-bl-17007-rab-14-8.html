What this PR is about

(1/2) Andika text showed in the phone's font

Problem. In apps built from Bloom, Andika text showed a two-story "a", online or offline.

Cause. RAB shipped Andika under names bloom-player never asks for, and RAB apps have no internet permission for its fallback (app-builders #2510).

Fix. RAB 14.8 fixes it, so Bloom 6.5 now installs RAB 14.8 instead of 14.0.1. Existing users are asked to update with Prepare. An app built with an older RAB then shows as needing a build, so "Try on phone" can't install the old, still-broken app.

(2/2) Every book in an app's contents menu showed the same picture

Problem. In an app with several books, every contents-menu entry showed one book's cover.

Cause. Bloom writes the menu itself and named every book's picture thumbnail.png; RAB packages pictures by name, so one won. RAB's own fix (#2529) only covers menus RAB builds.

Fix. Bloom copies each book's thumbnail into the project's contents/images as C01-B001-cover.png and so on (RAB's own naming) and uses that name in the menu.

Worth knowing

  • Every 6.5 user who builds apps must update RAB through Prepare, which shows a Windows admin prompt. Clicking No there gives "Bloom could not update Reading App Builder. Please use Help > Report a Problem", which is probably what the reporter, Tammy, hit (decision 4).
  • Checked on an Android 11 emulator, offline. Not yet checked on a real phone; the test ideas on the card ask a tester for that.

1. An existing test now expects the fixed behavior

Build_ReusedBloomPubRefreshesTrackedThumbnailFileName used to check that the contents menu names the shared thumbnail.jpg, which is the bug this PR fixes. It now expects the book's own copy, C01-B001-cover.jpg, and checks that the file exists. Changing what an existing test asserts needs your OK.

2. A book whose BloomPUB or thumbnail can't be found

The walkaround's first proposal. When Bloom can't open a book's BloomPUB, or the BloomPUB has no thumbnail, the menu entry falls back to the old shared name, thumbnail.png. That book would then show some other book's picture, the very bug being fixed. In real builds the BloomPUB is always there at this point; only one older unit test uses made-up paths and relies on the fallback. Leaving it is recommended: it's simple, and the case doesn't arise in practice.

3. Where the picture copying lives

The walkaround's second proposal. RabAppProject was only ever about editing the project's XML files; it now also copies picture files out of BloomPUBs while it writes the menu. Copying fonts out of BloomPUBs is done by the service instead (CopyEmbeddedFontFiles), so the picture copy could live beside it, with RabAppProject only writing names. That's a cleaner split, but the picture's name would then be worked out in two places that must agree. Leaving it is recommended.

4. The message after clicking No on the installer's admin prompt

Installing or updating RAB through Bloom always shows a Windows admin prompt, because RAB goes into Program Files. Clicking No makes the installer exit with code 2, and Bloom says "Bloom could not update Reading App Builder. Please use Help > Report a Problem…". That's probably what the reporter's log shows. A better message would say the installer needs permission and to click Prepare again. Everyone on 6.5 who builds apps will see this prompt once.
