How the fixes were verified

Two of the three fixes are pure CSS, which no test in this repo covers, so they were measured instead — once against the compiled stylesheets in Chromium using Bloom's real link order, and then in the running application.

In the running app, on an A4 Portrait book

The standard-layout column is the defect: the inside back cover was a side-right page there, so the 10mm gutter landed on its left, making a "full page" picture both inset and off-centre by 37.8px. The cover colour was confirmed visually to run edge to edge after the fix.

The branding fix

Against the real compiled RobotsMali stylesheet, a translation group on a custom inside back cover goes from display:none (reproducing the bug in the standard-layout control) to display:flex. RobotsMali is the only branding that hides that group with !important, which is why the selector needs its (0,6,0) specificity.

Also confirmed

An existing book gains data-custom-layout-id when opened for editing, so the feature is not limited to newly created books — which matters for the Vanuatu conversion work that drove the card.

Notes

The full-bleed case has still never been looked at

Bloom books can be set to print with "bleed" — the page content deliberately runs past the trim line so there is no white edge after cutting. This change zeroes the page margins on custom-layout pages, and nobody has yet opened a bleed-enabled book with a full-page picture on a custom Inside Back Cover to see what that looks like.

It is expected to be fine: the Front Cover has done the equivalent for a while via the cover-margin variables (.bloom-page.outsideFrontCover.cover-is-image) and behaves correctly. But "expected to be fine" is exactly the phrase that precedes surprises at a trim edge, and it is the one item from the original plan that has no evidence behind it. It is written into the QA test-ideas comment on the card as the first thing a tester should look at.
