What this branch does

Nothing in BloomTests exercised ImageUtils.NeedToShrinkImages or ImageUtils.FixSizeAndTransparencyOfImagesInFolder — the pair that keeps oversized pictures out of books. BookStorageTests calls the migration that uses them, but always as a no-op: no test ever put an oversized image on disk, so the real GraphicsMagick resize never ran. This branch adds one test file, 461 lines, and changes no production code.

  • The scan — false when everything fits (including an image exactly at the 3840×2800 maximum), true for an oversized PNG and an oversized portrait .jpeg, false when the only oversized image is placeholder.png, and false rather than a throw on a folder of non-images.
  • The fix-up — shrinks oversized landscape PNG, portrait JPG and landscape .jpeg to fit with the aspect ratio preserved; leaves an already-small PNG, an already-small JPG and an oversized placeholder.png byte-for-byte untouched; rewrites nothing when nothing is oversized; and carries creator, copyright and licence through the resize.

Images are generated at run time rather than committed as multi-megapixel binaries. The metadata test was mutation-checked: disabling the CopyTags copy-back in ImageUtils makes it fail, so it is not passing vacuously.

1. A mislabeled picture file crashes the whole image fix-up needs you

Bloom has two steps that work together on a book's pictures. First a quick scan asks "is any picture in this folder bigger than we allow?". If the answer is yes, the fix-up runs and shrinks the offending pictures. The scan is written defensively: if it meets a file it cannot read as an image, it shrugs and moves on. The fix-up is not — it reads every .png and .jpg in the folder with no such protection.

So a book folder that contains both an oversized picture and a file that is not really the image it claims to be will pass the scan and then throw partway through the fix-up, abandoning the whole job. Any picture the fix-up had not reached yet stays oversized, and whatever was calling it — the old-book migration, or BookProcessor.ProcessBook, the step BloomBridge drives over every book — fails with it.

This is not a hypothetical input. Bloom's own code says so: the comment on RobustFileIO.MetadataFromFile reads "Books sometimes use image files that are mislabeled. JPEG files sometimes have been given .png extensions… TagLib crashes trying to read the metadata in such cases", and that method works around it by copying the file to the right extension first. The fix-up calls a different helper, CreateTaglibFile, which has no such workaround.

I confirmed it rather than reasoning about it. With a throwaway test: a folder holding one oversized PNG plus a real JPEG named mislabeled.png — precisely the case that comment describes — the scan correctly returns true and the fix-up then throws TagLib.CorruptFileException out of ImageUtils.cs:1492. The JPEG loop at line 1557 has the same gap; the scan's protection is at lines 1376–1379.

Fixing it means touching production code, which is more than this card asked for — hence bringing it to you rather than just doing it.

2. The full C# suite is not reliably green on master needs you

The project's own guidance says the full suite should be green through the build/agent-dotnet.sh wrapper, and specifically that a failing xmatter-locating test means a real regression in the wrapper rather than background noise. That is not what I saw, and none of it is caused by this branch.

I ran the suite three times. Two runs aborted partway — the test host process itself died on a debug assertion thrown out of Bloom's internal web server, complaining about a missing temp folder — taking 19 and then 43 tests down with it. Crucially, one of those runs was with this branch's test file removed from disk, and it crashed the same way, so the crash is pre-existing and flaky rather than something this change introduced. The third run did not crash at all and finished with a single failure, XMatterHelperTests.InsideBackCover_PaperAndDeviceXMatter_ShareOneCustomLayoutId — which also failed in the without-this-branch baseline.

So: one consistently failing xmatter test, plus a test host that dies unpredictably about two runs in three. Both are on master already. It matters here only because it makes "the suite is green" an unreliable gate for everyone, including the next preflight.
