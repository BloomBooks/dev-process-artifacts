What this branch does

Nothing in BloomTests exercised ImageUtils.NeedToShrinkImages or ImageUtils.FixSizeAndTransparencyOfImagesInFolder — the pair that keeps oversized pictures out of books. BookStorageTests calls the migration that uses them, but always as a no-op: no test ever put an oversized image on disk, so the real GraphicsMagick resize never ran.

  • The scan — false when everything fits (including an image exactly at the 3840×2800 maximum), true for an oversized PNG and an oversized portrait .jpeg, false when the only oversized image is placeholder.png, and false rather than a throw on a folder of non-images.
  • The fix-up — shrinks oversized landscape PNG, portrait JPG and landscape .jpeg to fit with the aspect ratio preserved; leaves an already-small PNG, an already-small JPG and an oversized placeholder.png byte-for-byte untouched; rewrites nothing when nothing is oversized; carries creator, copyright and licence through the resize; and keeps going when a file cannot be read as an image.
  • One production fix — the crash Devin found, described on the right.

Images are generated at run time rather than committed as multi-megapixel binaries. The metadata test was mutation-checked: disabling the CopyTags copy-back makes it fail, so it is not passing vacuously.

You answered Fix it in this PR

A mislabeled picture file crashed the image fix-up done

Bloom has two steps that work together on a book's pictures. A quick scan asks "is any picture here bigger than we allow?"; if so, the fix-up shrinks the offending ones. The scan was written defensively — meeting a file it cannot read as an image, it shrugs and moves on. The fix-up was not, so a folder holding an oversized picture and a file that is not really the image it claims to be passed the scan and then threw partway through the fix-up, leaving every picture it had not yet reached oversized and taking the caller down with it — the book-open migration, or BookProcessor.ProcessBook, the step BloomBridge drives over every book.

The triggering input is one Bloom is documented to meet: the comment on RobustFileIO.MetadataFromFile says books contain JPEG files given .png extensions and that TagLib crashes on them. I reproduced it with a throwaway test before acting.

What I did. Both loops now read metadata through a new TryCreateTaglibFileForImage, which returns null instead of throwing, so only the unreadable file is skipped — the same thing the scan already does — and the failure is logged rather than silently swallowed. The covering test puts an oversized PNG in a folder with a JPEG-named-.png, a PNG-named-.jpg and a file that is not an image at all: the oversized image is still shrunk and the three bad files are left byte-for-byte alone. Committed as 42d69337; Devin's thread is replied to and resolved.

One knock-on: Devin's next pass rightly pointed out the PR description still claimed no production code had changed. The title and body now describe the fix.

The chrome-devtools daemon logged

Logged in bloom-team-skills/PAPERCUTS.md and pushed. There was already an entry from earlier the same day with the same symptom, so rather than duplicate it I corrected it: that entry blamed a broken install and prescribed an upgrade, but the real cause is a stale pidfile.
