What this branch is

Sentry issue 2699459502 (“Cannot Find File”) is dominated by requests for the bare name Checkbox.js. The card assumed no such file exists in Bloom. It does — it is a Vite chunk in output/browser. A bundle injected into a page at the server root imports its sibling chunks by bare name, so they arrive with no directory, and should always be found under BrowserRoot.

This branch does not fix that bug. Why the lookup fails on the affected machines is still unknown: the third lookup is anchored to the application folder, and the absolute browser root is already a factory search path, so on a valid install the file is found regardless. The branch adds the instrumentation needed to find out, plus a genuine weakness the investigation turned up. The branch was renamed to say so.

1. Where the BloomSource import dialog opens

Bloom's Open and Save dialogs used to leave Windows “pointing” at whatever folder you last browsed to, for the rest of that Bloom session. That mattered because a few places looked for files Bloom ships with using a location relative to wherever Bloom happened to be pointing. This branch turns that off, so the dialogs put the pointer back when they close.

Devin flagged that this was switched on in the constructor, so it applies to every caller. I checked all five. Four set their own starting folder and cannot be affected. One does not: the import-a-BloomSource dialog, which sets only a title and a file filter. On Windows Vista and later, where such a dialog opens is driven by the shell's per-application memory of your last folder rather than by that pointer, so the expected answer is “no change” — but that is the sort of thing worth seeing rather than reasoning about, and it is user-facing, so I left it for you.

2. FYI — lookup precedence really did change

The first entry in Bloom's file-search list was a relative location, so it only ever found anything when Windows happened to be pointing at Bloom's own folder. Making it absolute means it now reliably wins — which is what the comment there always intended, but it is a real change in which copy of a shared file gets used when several exist. The front/back-matter precedence tests cover this and pass, and Devin raised it as informational rather than a bug. Flagging it because it is the part of the branch worth reviewing hardest, and because the symptom if it were wrong would be books quietly looking different rather than anything erroring.

3. FYI — the diagnostics fire for any directory-less miss

Devin noticed that the new diagnostic text keys only off “the request had no directory”, so a miss on something like a bare something.pdf also gets the browser-root detail, even though only JavaScript chunks arrive that way for the reason we care about. I left it broad on purpose: a bare-name miss of any kind is rare and unexpected, and knowing where Bloom looked is useful whatever the file type. The cost is a slightly longer message in an already developer-oriented report.
