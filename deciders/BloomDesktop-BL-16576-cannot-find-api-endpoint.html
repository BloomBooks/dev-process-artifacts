Stop reporting missing API endpoints that outside tools legitimately probe

One Sentry issue — 1115 events across 20 users — turned out to be three unrelated endpoints, none of them a Bloom programming error, all shown to the user as the same alarming “Cannot Find API Endpoint” toast. Bloom now returns the 404 and writes a log line, but stops interrupting a user who may not even know another program is talking to Bloom.

How this was verified beyond the tests

  • The bug was reproduced first, on a real old build. An installed Bloom 6.3.2.0, asked once for api/common/instanceInfo, returned 404 and logged the card’s exact message:
9:33:53 AM  NonFatalProblem: Cannot Find API Endpoint
Server could not find an API endpoint for /bloom/api/common/instanceInfo...
   at Bloom.Api.BloomApiHandler.ReportMissingApiEndpoint(IRequestInfo info, String localPath)
  • The card’s diagnosis was wrong and is now corrected on the card. This is not a startup race: common/instanceInfo is registered at application level in ApplicationContainer’s constructor, before the server ever starts listening. It is version skew — the endpoint landed 2026-03-12 when master was 6.4.0.0, and is not in Version6.3 at all.
  • The suppression tests can’t pass for the wrong reason. MissingNonLegacyApiEndpoint_ReportsNonFatalProblem still passes, proving the reporting path is intact and the new tests are exercising a real suppression.

Your call

Is suppressing the whole external/ namespace too broad?

The change stops Bloom warning the user about any missing endpoint whose name begins external/. That namespace is not empty — it currently holds a dozen live endpoints (external/login, external/process-book, external/update-book and so on). So if one of those ever failed to register — say a refactor dropped a registration — Bloom would quietly answer 404 and write a log line, where before it would have shown a developer a toast.

I judged that an acceptable trade and said so in the code: nothing inside Bloom calls these endpoints, so a broken registration surfaces immediately as a broken external tool rather than lying dormant. Devin raised the same point as informational and noted the PR already accepts it. It is flagged here because it is exactly the kind of call a second pair of eyes should get to overrule.

FYI — this cannot quiet the Sentry issue by itself

No action needed unless you want the issue silenced sooner. Because the fix can only exist in builds from here on, the 6.2/6.3/6.4 Blooms already on people’s machines will keep producing these events whenever any tool probes them. The BloomBridge change stops our tool from doing the probing, which should account for most of it, but the issue will not go to zero until those releases age out. If you would rather it stopped showing up in triage now, that is a Sentry ignore-by-release rule rather than anything in code.
