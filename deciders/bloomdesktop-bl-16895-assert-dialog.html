What this PR is about

Problem

In a Debug build of Bloom run without a debugger (the go.sh launcher, dotnet watch), any failed Debug.Assert kills Bloom on the spot: no dialog, no exception handler, no report, and the dev stack goes down with it. A developer publishing a book whose bold title had also been marked bold hit this through the font-weight assert in FontFileFinder. There are about 175 Debug.Assert and Debug.Fail calls in BloomExe, so any of them can do it.

Cause

.NET Framework showed an Abort / Retry / Ignore dialog for a failed assert. .NET 8 does not: the default trace listener breaks into an attached debugger, and otherwise calls Environment.FailFast. Under F5 that still looks like the old behaviour, which is why it went unnoticed. An earlier fix (BL-16512) turned the listener's UI off only while the e2e suite is running.

What the PR does

  • A small trace listener, installed from Main in Debug builds only, replaces the runtime's default one (BloomAssertListener.cs). When an assert fails it logs the message and caller stack, breaks into the debugger if one is attached, returns quietly in e2e, harvester and console modes, and otherwise shows an Abort / Retry / Ignore box where Retry offers to attach a debugger.
  • An e2e run is recognised from the --e2e switch on the command line as well as the parsed flag, so an assert during early startup of an e2e launch cannot raise a dialog nobody can dismiss.
  • The e2e-only workaround in Program.cs is removed and RunningE2eTests is a plain property again, since the listener covers that case.

Release builds are unaffected: Debug.Assert compiles out, and Install is Conditional on DEBUG so the listener is never installed. The FontFileFinder asserts that fired are left as they are; that is a separate question (see BL-15328).
