The toolbox showed one tool and ran another

BL-16602 — Talking Book highlighting went completely dead after visiting a game page, and stayed dead until Bloom was restarted. The fix makes the toolbox tell its older machinery every time the tool on screen changes.

What was wrong, and what changed

A game page can only be edited with the Game tool, so Bloom adds that tool to the toolbox and opens it the moment you navigate to such a page — and takes it away again when you leave. Bloom's toolbox is currently half-rebuilt: the visible list of tools is React, while the machinery that starts and stops each tool is still the old jQuery-era code, and the two talk to each other through a small adapter.

When the Game tool was taken away, the React side picked another section to open — so the panel correctly read Talking Book Tool — but it never told the old side. The old side went on believing the Game tool was current, so getActiveToolId() kept answering "game" and the Talking Book tool was never started again. Every highlight path is gated behind doesCurrentToolPlayAudio(), so nothing highlighted at all — and closing and reopening the Talking Book tool changed nothing, because the confusion was not inside that tool.

This is a 6.4 regression with an interesting cause: in 6.3 the jQuery accordion did this for us. Its refresh() noticed the active panel had been removed, activated another one, and that fired the activate event which ran switchTool(). The React accordion that replaced it had no equivalent path.

The change

  • Every change of which section is expanded now goes through one setActiveSection() helper (ToolboxRoot.tsx:415) that both sets the React state and notifies the legacy listeners. The three callers — the adapter, the accordion's own click handler, and the removal path — can no longer diverge.
  • onToolRemoved (ToolboxRoot.tsx:701) now uses it, so losing the active tool actually activates its replacement.
  • That also fixes the same dead-toolbox state reached a different way: unticking the currently-open tool in More… had exactly the same effect.
  • New ToolboxRoot.spec.tsx drives the add → activate → remove sequence through the real window.toolboxReactAdapter surface and asserts the replacement is reported to legacy. It was confirmed to fail without the fix (expected [ 'gameTool' ] to deeply equal [ 'gameTool', 'talkingBookTool' ]) and pass with it.

Decision · behavior

Which tool should open after you leave a game page?

Right now — and after this fix — Bloom opens the first tool in the toolbox list, which is alphabetical. It does not remember that you were using the Talking Book tool before you wandered onto page 13. So in the reporter's collection, where Talking Book happens to be the only enabled tool, you land back on Talking Book and it feels like Bloom restored what you had. In a collection that also has the Canvas tool enabled, you would land on Canvas instead and have to click Talking Book yourself.

This is worth deciding rather than assuming, because the card is phrased as "returning to the Talking Book tool", which could be read as a promise to restore it. It is not a regression either way: 6.3 also picked an arbitrary neighbour (the panel just before the one that vanished), so this fix restores the old behavior rather than improving on it. Leaving it alone is recommended because remembering the pre-game tool means giving the toolbox a new piece of remembered state, and the Game tool already overwrites the book's saved "current tool" on its way in — that is a design change, not a bug fix, and it does not belong in a regression fix that needs to go into 6.4.

Decision · verification

Should I reproduce the bug in a running Bloom before you review?

Everything proving this fix is at the unit level: a spec that drives the toolbox's real adapter and fails without the change. Nobody has yet watched the actual symptom disappear in Bloom — make a derivative of "The Moon and the Cap", open Talking Book, go to page 13, come back, and click a sentence. No Bloom was running in this session, so doing it means launching one and driving it over the debugging connection.

Recommending against it is a judgement about where it is best done: the mechanism is fully understood, the original diagnosis on the card was itself made from a live stuck instance, and a human (or QA, from the test-ideas comment now on the card) can confirm the symptom in under a minute during review — whereas the agent-driven version costs several minutes of setup and can still miss what a person would notice.

FYI · test environment

The C# suite can't finish cleanly in an agent worktree

Nine C# tests fail here, reproducibly and identically across two complete runs, for reasons that have nothing to do with any code: the isolated build tree the agent wrapper uses is missing two things the shared debug output has. It has no BloomPdfMaker.exe, so the four PDF-making tests report that file as missing; and it can't find the Test-XMatter pack, so five xmatter and style tests fail looking for it. Anyone running the suite this way has to know to ignore exactly those nine, which is a trap.

On top of that, two runs I started while the vitest suite was also running aborted after 347 tests when the test host crashed on an HttpListener being disposed while still writing a response — so the suite is also not safely runnable in parallel with other work. None of this affects this PR, which contains no C# at all.

FYI · dead test harness

The toolbox's browser tests have been broken since React 18

There are seven Playwright tests for this very component under react_components/ToolboxRootTestHarness, and all seven currently fail on master before rendering a single pixel: the shared component-test harness still pins react-dom 17, so it cannot resolve react-dom/client, which the app has used since moving to React 18. They are not run in CI, so nobody noticed. The natural home for a test of "removing the active tool activates its replacement" was there; it went into a vitest spec instead.
