What this PR is about

Problem

bulk-upload-quick-test.spec.ts (Test Case 211) failed about two runs in three. After the collection moves to another bookshelf and is re-uploaded, one book, a different one each time, still showed only the old shelf.

Cause

The sandbox's harvester, not Bloom. When a harvest finishes, it writes the whole book record back from the copy it read when it started. So a re-upload that lands mid-harvest is overwritten with older metadata, possibly including the record's pointer to the uploaded files, and is never re-harvested. Captured in one failing run: Book 2's harvest started 18:02:46, the re-upload landed 18:03:03, and the harvest finished 18:03:07, leaving the old shelf. Filed as BL-16921.

What the PR does

  • Bulk upload now writes BloomBulkUploadResults.json beside its log. It holds the tallies and, for each book, its folder, outcome (new / updated / skipped / failed) and where its files went. Each upload goes to a new folder, and the record can later point elsewhere.
  • The test reads each book's uploaded meta.json (bookshelf) and HTML (front/back matter) at those locations, not from the server's records. It matches each location to its own book and requires no failures in any round.
  • The shelf check is stricter: exactly the new shelf, since Bloom sends only the current one.
  • The e2e launch fixture, which stalled this same test twice, is more patient and can't hang:
    • each probe for the Bloom it started gets up to 30 s (never past the launch deadline) and is then sent again, so one unanswered request can't hold up the whole wait;
    • the launch deadline is 5 minutes for both kinds of launch, since busy machines have taken over two minutes to start Bloom;
    • the fixture's own timeout covers that deadline plus connecting to Bloom and finding its page, so a launch that gives up reports what it saw instead of hitting Playwright's generic timeout.
