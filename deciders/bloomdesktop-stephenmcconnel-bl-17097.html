What this PR is about

Problem

On Publish > Apps, Bloom works out how big each book will be in the app. If anything went wrong reading one book's files, the whole size request failed: no book showed a size, and the user got an error report. The reported case was a BloomPUB deleted between Bloom finding it and reading its size. Sentry has the same error 5 times from 3 users.

Cause

BL-17062 on master already copes with that file disappearing. Three gaps remained:

  • Bloom keeps the BloomPUBs in a folder in %TEMP%, which Windows and users clear. If that whole folder vanished at the wrong moment, the error wasn't caught.
  • When a book has no usable BloomPUB, Bloom estimates its size from the book's own files. Nothing guarded that estimate, so a book file being saved, renamed or deleted part way through broke the request.
  • A book folder deleted part way through reached the book-file lookup. That lookup told the user "Bloom can't save this book" and threw an exception that wasn't an IO error.

What the PR does

  • Checking a kept BloomPUB against its book and reading its size are now one guarded step. Any IO or access error means the book gets an estimate instead.
  • If the estimate from the book's own files fails the same way, the book shows its last estimate, or 0 if it has none. Nothing from the failed attempt is cached, so the next request works it out properly.
  • The book-file lookup has a read-only form that reports a missing folder as an ordinary IO error, without the "can't save" message. The size estimate and the BloomPUB cache use it.
