What this PR is about

Problem

BL-16822 lets a text block hold a picture that its text flows around, the way a picture sits in a Word document. This PR is the code that reads and writes that picture's markup, and the undo for changes to it. Nothing here creates a picture: Insert Image and the gestures are in the next PR (8321), so merged alone it changes nothing a user sees.

Cause

A CSS float only wraps the text of the element it is in, so every language's bloom-editable in the block needs its own copy of the picture, the hidden lang="z" prototype included.

What the PR does

  • Defines the markup: a div.bloom-inlineImage with a dock (left, right, middle, bottom), width, aspect ratio and vertical offset, and an id the copies share.
  • Keeps the copies identical after each change and on page load, taking a visible language's copy over a hidden one.
  • Makes each picture change one entry on Bloom's shared undo stack (from PR 8387), the way table operations are, so Undo and Ctrl+Y restore every language's copy together and keep their order against typing and table operations.
  • Adds a read-only UndoStack.getEntryForNextUndo, so a Ctrl+Z handler in the text can tell when the next undo is a picture change.

Typing after a picture undo leaves its redo available

Insert a picture, press Undo, type a word, then press Ctrl+Y: the picture comes back. In every editor, typing after an undo should discard what could be redone. The shared undo stack discards its redo entries only when it records a new entry of its own. Typing is still recorded by CKEditor, not the stack, so it discards nothing. Table entries have no redo, so picture changes are the first stack entries that show this. Thread.

Repairing a damaged block can delete a picture

When a block has two editables in the same language, which only happens in a damaged book, Bloom's C# repair (FixDuplicateLanguageDivs in TranslationGroupManager.cs) deletes the one it thinks is empty. It decides by the text. An editable holding only a picture has no text, so the repair can delete it and keep the truly empty one. This PR has no C#. Thread.

A newly inserted picture is not protected from Ctrl+A, Delete

Bloom guards elements marked bloom-preventRemoval against Ctrl+A then Delete by undoing the keystroke if one disappears. The guard (BloomField.PreventRemovalOfSomeElements) counts them once, when the page is set up. A block with no picture at that point gets no guard, so a picture inserted later (8321) can be wiped this way. Counting on each keystroke instead would also undo a picture deleted on purpose with the Delete key, so the fix must tell the two apart. Thread.
