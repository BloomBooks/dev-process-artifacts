What changed this run

One commit, f6ad62b8 “Fix BL-16616 don't trigger long-press from shortcut keystrokes” (files changed). QA had reported that after the merged caret fix, holding Ctrl+Shift+Space (show hidden characters) popped up the long-press special-characters panel. Root cause: the long-press keydown handler never checked modifier keys, and the old cursor-jump bug had been masking that. The fix is an 8-line guard at the top of the long-press keydown handler: bail out when Ctrl (without Alt) or the Windows/Cmd key is down, since such a keystroke is a shortcut and never types a character. Ctrl+Alt stays exempt because Windows reports AltGr — which genuinely types characters — as Ctrl+Alt.

Verified live in a running Bloom over CDP: holding Ctrl+Shift+Space mid-text shows the hidden characters, keeps the caret in place, and no longer opens the panel; holding a plain letter key still opens it; the text box was left exactly as found.

FYI — Devin's one flag: Ctrl+Alt shortcuts can still arm long-press

Because the guard deliberately lets Ctrl+Alt through (that's how Windows reports AltGr), a genuine Ctrl+Alt shortcut that is held down — Bloom has one, Ctrl+Alt+2 for heading formatting — can still open the special-characters panel. This behavior is pre-existing: Ctrl+Alt combos never destroyed the text selection, so they could arm long-press even before any of the BL-16616 work; this PR neither introduced nor worsened it, and it only shows if the user holds the shortcut rather than tapping it. That is why the thread was resolved as “leave as is”: the available tightening trades an unlikely cosmetic edge case for a real risk to AltGr typing, a core input path for Bloom's African and European keyboard users.
