What this PR is about

Problem

Every run of the src/BloomE2E suite opened a real Bloom window on the developer's desktop, which makes the suite unusable while working. Three separate controls decided where that window went, and none of them was discoverable: an environment variable BLOOM_AUTOMATION_MONITOR that only the main window read, a silent fallback to the primary monitor, and a BLOOM_E2E_HEADED variable in the Playwright fixture.

What the PR does

BLOOM_AUTOMATION_MONITOR becomes the one control, and every window an automation run opens obeys it, the splash screen included.

ValueWhat happens
headless, or 0Every window opens far outside every monitor. You see nothing, so a run can go on while you work.
a monitor number, counted left to rightEvery window opens on that monitor. Monitor 1 is the leftmost.
unset, or anything Bloom cannot useBloom places its windows as it always does, so a typo shows you a window rather than hiding one.

The variable applies only under --automation, so a Bloom you start yourself is unaffected however it is set. --debug clears an off-screen setting, because stepping through a test whose window you cannot see is pointless. The nightly workflow now asks for headless explicitly. The old Shell.GetAutomationScreen(), the --headless flag and BLOOM_E2E_HEADED are gone.

Four things that are not obvious

Each of these has a code comment where it matters, because each was found the hard way.

  • The window moves off every monitor rather than minimizing or hiding. WebView2 stops painting a minimized window, so every screenshot would come back blank. Windows then reports a far-off-screen window as occluded, so Chromium also needs CalculateNativeWinOcclusion disabled and --disable-backgrounding-occluded-windows.
  • ShowInTaskbar is set in the constructor. Assigning it to a form that is already showing makes WinForms recreate every handle, the WebView2 host included, which breaks navigation.
  • The off-screen window goes straight down from the primary monitor, and leaves four window heights of clearance. Both numbers are about DPI, not about space. Windows gives a window the scale factor of the monitor nearest to it, and this process asks for a size in the primary monitor's own scaled pixels; going sideways makes another monitor nearest, so the window is reinterpreted at its scale. Going down keeps the primary nearest on an ordinary side-by-side layout. Four heights, because Windows scales a monitor by at most 400%. Every unit test passed over both bugs this caused, because they compare in the test process's own coordinates; only real window rectangles showed them.
  • An automation run never writes the saved window placement, because every Bloom of one build shares one user.config.

Two pieces of work this raised are written up in src/BloomE2E/AUTOMATION-DEBT.md rather than done here, at your instruction: the ability to run the suite at a chosen resolution and scale factor, and giving every run a small 1024x586 window by default. The second one has a measured cost, below.

The \\.\DISPLAY<n> device names do not match either, and Microsoft documents no rule for the Settings labels.

1. Your shell says 3, which is now the monitor on the right

2. A monitor stacked below the primary would still get the wrong size

Devin raised this on the below-primary fix, and it is right. The off-screen window goes straight down because Windows applies the scale factor of the nearest monitor, and on a side-by-side layout the primary stays nearest. Put a monitor underneath the primary, overlapping it horizontally, and that lower monitor becomes nearest instead; if its scale factor differs, the window comes out the wrong size, which is the same bug in a new layout.

Nobody on the team has such a layout. Fixing it for every layout means asking Windows for the nearest monitor's scale factor and scaling the requested size by the ratio, which needs per-monitor DPI calls Microsoft does not document. So 6f2a42d244 states the limit in the code comment and in the automation-debt entry, rather than claiming more than the code does. The thread on the PR stays open for your answer: discussion_r3925622620.
