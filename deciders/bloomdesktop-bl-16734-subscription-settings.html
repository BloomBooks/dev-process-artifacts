What this PR is about

Problem

The new (React) Collection Settings dialog had only a placeholder for its Subscription page, so a subscription code could still be entered only in the old WinForms dialog. Every subscription badge and gated menu item ("this needs a subscription, click to get one") also still opened the old dialog.

What the PR does

  • A real Subscription page, built from the pieces of the old Subscription tab (intro, code box with Copy/Paste, tier and expiry, branding summary, expiry warnings, community-subscription invitation), laid out like the card's mockup.
  • The code saves with the rest of the dialog: a changed code turns OK into Restart and goes through the existing subscription-and-bookshelf rules, before the front/back-matter check because a branding can choose the pack. An unchanged code keeps the collection's own subscription, which a book downloaded for editing relies on.
  • Cancel leaves nothing behind: the page checks a typed code without telling Bloom about it, so the code reaches Bloom only on OK, and the old dialog's path is untouched.
  • Every "open the Subscription settings" entry point now opens the new dialog on that page: subscription badges, gated menu items, the comic-book ReadMe links, and the invalid-branding startup check. A badge on one of the new dialog's own pages switches it to the Subscription page, keeping edits. While the old dialog is open, its badges still switch it to its own tab.

Worth knowing

  • The old dialog's own badges (Advanced and Team Collection tabs) were checked by reading the code only: the e2e suite cannot reach the WinForms dialog.
  • The invalid-branding startup path now opens the new dialog, but nothing ever sets CollectionSettings.InvalidBranding, so it cannot fire today.

1. A gated menu command leaves its menu open behind the dialog

On the Collections tab, right-click a book, choose More, then a command the subscription lacks (Export to Spreadsheet). The Settings dialog opens on its Subscription page, but the book menu stays open behind it, and after the dialog closes the person has to dismiss the menu by hand. It has always done this, with the old dialog too: a gated item runs the "open subscription settings" action in place of its own handler, and its own handler is what closes the menu. The same menu-item component is used in menus across Bloom. The new e2e test closes the menu itself (here).

2. An intermittent Playwright worker crash hits the new book-menu test

About one run in ten, the Playwright worker process running the new spec's first test (it makes a book and right-clicks it on the Collections tab) dies with Windows' STATUS_STACK_BUFFER_OVERRUN, before any assertion. That test is then reported as failing after 0 ms and the rest of the file does not run. Across 8 runs each, the same file's other tests and the BL-16736 spec never crashed. Extra logging (DEBUG=pw:*) makes it disappear, and Node writes no crash report. This is the known debt entry (seen before on other book-making specs, cause unknown); I added these numbers to it. The repo rule is to never accept a flaky test without your permission. Devin flagged it too (open thread).

3. Other pages follow the saved subscription, not a typed one

While a person types a new code on the Subscription page, the other pages of the same dialog keep reflecting the subscription the collection has saved: the Bloom Library page's bookshelf list and the Experimental page's checkboxes unlock only after Restart. A new code always needs a Restart anyway, so the person sees the new tier's options right after it. The old dialog behaves the same. The plan doc asked this card to decide; I left it as is and noted it in the test ideas as expected.
