What this PR is about

Problem

Clicking Set Up Levels in the Leveled Reader tool did nothing at all — no dialog, no message, nothing — and stayed broken for the rest of the session. Restarting Bloom made it work again. Set Up Stages in the Decodable Reader tool had the same fault. Reported against 6.5.1330 alpha and not reproducible on demand, because it depends on timing.

Cause

The reader tools remember, in module-level state, that they have already loaded the collection's reader settings. But the ReaderToolsModel those settings live in is held on the top window, and getTheOneReaderToolsModel() deliberately discards that holder and builds a fresh model whenever the frame that created it has been reloaded. So the “already loaded” memory can outlive the data it describes. Once that happened, beginLoadSynphonySettings() saw its flags set, found the settings unchanged, and skipped the work — leaving model.synphony undefined for the rest of the session, and every reader-tool feature that needs it silently dead.

The setup dialog was the visible casualty. It did open, but the first thing it does — post the settings into its own iframe — died on an unguarded synphony.source, so the dialog was never given its data: it never switched to its Reader Levels tab and never filled anything in. What the user saw was an empty tab, or nothing they would recognize as the dialog having opened.

What the PR does

Reviewing the first fix turned up three more routes to the same dead button, so the PR closes the whole family: whenever the reader settings can't be had, something visible has to happen.

  • Loads the settings into the model we actually hold. An unchanged-settings check is no reason to skip loading when the model in front of us has never seen them, so beginLoadSynphonySettings() now refreshes in that case. This is the root-cause fix, and it repairs every reader-tool feature that was silently dead, not just the dialog. It routes the reload through the existing refresh path, which is built for it — that path does the stale word-cache cleanup a reload needs, and creates no second folder watcher to leak.
  • Makes the button self-sufficient. showSetupDialog() loads the settings before showing anything, rather than assuming the owning tool's load happened and survived. This is cheap when they are already loaded.
  • Never leaves a caller waiting forever, in the three places that could: a settings request that outright failed, a refresh whose sample-texts fetch failed, and a throw while building the dialog that a jQuery promise quietly swallowed. Each presented as the same dead button; now each releases its callers, and a real bug is reported instead of retried.
  • Reports the real failure. Guarding synphony means “the settings were not loaded” is what gets reported, instead of a bare “cannot read properties of undefined” that says nothing.
  • Stops a fragile ordering from throwing. requestWordsForSelectedStage() no longer dies when a word-list-changed notification arrives before the dialog has its data and a selected stage row — an ordering that loading the settings right before opening makes reachable.
  • Tests covering the reload into a replaced model, a failed settings request settling rather than hanging, and the descriptive error.

Worth knowing

  • All four fixes were verified by hand in a running Bloom. With the model's settings cleared to reproduce the fault, Set Up Levels reloads them and opens on Reader Levels with all six levels, and Set Up Stages likewise on Decodable Stages. The requestWordsForSelectedStage guard needed a full pnpm build to reach the running Bloom (its bundle is not served by the dev server); after that build, the sequence that threw twice before ran clean.
  • The reader-tool settings path is shared with every book switch. The reload this PR forces in one more case is the same code Bloom already runs whenever you change books, so if anything regressed, stale or doubled word counts after switching books is where it would show. The test-ideas comment on the card points QA at exactly that.
  • The original report was “could not repro”, and the fault is genuinely timing-dependent. Nothing here proves the reporter's exact sequence is the one that was fixed — what is proven is that the state they described no longer leaves the button dead, and that three other routes to the same dead button are closed too.
