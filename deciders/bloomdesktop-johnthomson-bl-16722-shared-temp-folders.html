What this PR is about

Problem

The full C# test suite failed intermittently, about two runs in three on one machine, for reasons that had nothing to do with the change under test. Ten test fixtures used the same temp folder, and each test's setup deletes and recreates it, so one fixture could pull the folder out from under work another was still doing.

Bloom itself had the same flaw. Every BloomPUB, whether the Publish-tab preview or a real one (saved to a file, sent over USB or Wi-Fi, made in bulk, or built into an app), was staged in one of two fixed temp folders, PlaceForStagingBook and BloomReaderExport. Pictures were shrunk in a third, BloomPubImageAdjust. Starting a new BloomPUB deleted whatever was in them, including another running Bloom's files.

What the PR does

  • Each test fixture gets its own temp folder, named after the fixture class. A fixture can no longer override the name and bring back a shared one.
  • The ePUB tests release the ePUB they open. They used to keep output.epub locked for the rest of the run.
  • Each BloomPUB gets its own staging folder, %TEMP%\bps\<five random characters>, and so does picture shrinking. A Bloom claims a folder by creating a marker file in it in a way that fails if another Bloom got there first.
  • The code that recognized the old folder names now recognizes the bps root: the Bloom Player link back to the book being previewed, the no-caching rule for the preview, and the filter that hides missing-file noise while publishing.
  • Cleanup that respects other running Blooms. The root does not start with "bloom", so Bloom's exit sweep of %TEMP%\bloom* never touches it. Instead, every Bloom deletes its own marked staging folders more than a day old when it exits, and a filesystem error there cannot interrupt shutdown.

Worth knowing

  • Nothing has been tried in a running Bloom yet, and the e2e specs that open the BloomPUB preview were not run (question 2). The test ideas on the card list what a tester should try.
  • The card also names the ePUB export folder, which has the same flaw and caused one of its three reported failures. This PR leaves it alone (question 1).

1. Give each ePUB export its own folder too?

Every ePUB Bloom makes is staged under one shared folder, %TEMP%\ePUB_export\0 (EpubMaker.cs:279). Starting a new ePUB deletes what is there and only moves on to 1, 2… when that delete fails. This is the same flaw this PR removes for BloomPUBs. The card names it, and one of its three reported test failures (BookSwitchedToDeviceXMatter, a missing file under ePUB_export\0) came from it. For users it bites only when two ePUBs are made at once, for example from two copies of Bloom.

2. Try the change in a real Bloom before human review?

Everything so far is unit tests and code review. The BloomPUB preview's move to a new folder each time has not been exercised in a running Bloom. Three e2e specs open the preview (publish-text-languages, tables-core, tables-gating), and the nightly will run them after merge. Running them here first would catch a broken preview before a reviewer or tester sees it.

3. Update bloom-player's developer docs?

bloom-player's README-advanced.md and index-for-developing.html show example URLs under …/Temp/PlaceForStagingBook/<book> for viewing the book Bloom is previewing. That folder no longer exists, and the new folder changes with every preview, so a developer following those docs gets a broken link. Bloom already answers http://localhost:8089/bloom/current-bloompub-url with the current preview's address, which the storybook's "Live from Bloom Editor" story uses.
