What this PR is about

Problem

The full C# test suite failed intermittently, about two runs in three on one machine, for reasons that had nothing to do with the change under test. Ten test fixtures used the same temp folder, and each test's setup deletes and recreates it, so one fixture could pull the folder out from under work another was still doing. The ePUB tests also all staged into one shared folder.

Bloom itself had the same flaw. Every BloomPUB (the Publish-tab preview, or one saved to a file, sent over USB or Wi-Fi, made in bulk, or built into an app) was staged in one of two fixed temp folders, and pictures were shrunk in a third. Every ePUB was staged under ePUB_export\0. Starting a new one deleted whatever was in these folders, including another running Bloom's files.

What the PR does

  • Each test fixture gets its own temp folder, named after the fixture class, and the ePUB tests release the ePUB they open.
  • Each BloomPUB and each ePUB gets its own staging folder, %TEMP%\bps\<five random characters>, from the new PublishStaging class, and so does picture shrinking. A Bloom claims a folder by first creating a marker file beside it in a way that fails if another Bloom got there first.
  • The code that recognized the old folder names now recognizes the bps root: the Bloom Player link back to the book being previewed, the no-caching rule for previews, and the filter that hides missing-file noise while publishing.
  • Cleanup that respects other running Blooms. The root does not start with "bloom", so Bloom's exit sweep of %TEMP%\bloom* never touches it. Instead, every Bloom deletes staging folders whose marker is more than a day old when it exits, then the marker. It never touches a folder without Bloom's marker, and an error there cannot interrupt shutdown.
