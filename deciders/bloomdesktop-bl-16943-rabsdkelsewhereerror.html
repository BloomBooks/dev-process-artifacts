What this PR is about

Problem

In Publish > Apps, Prepare can report "Prepare complete." while the "Install build tools" step stays unchecked. Choose Books, Build and the later steps then stay disabled, and nothing tells the user why. A forum user hit this on 6.4.1, and Colin hit it earlier (BL-16491).

Cause

Bloom runs rab.bat -install-sdks-if-needed and names its own JDK and Android SDK folders. Reading App Builder (RAB) 14.0 looks for an existing Android SDK in C:\sdk, C:\sdk2, and so on. If it finds one, it prints Android SDK is already installed at: C:\sdk, installs nothing in Bloom's folder, and exits 0. RAB treats the JDK the same way. The forum user's Bloom also wasn't using its own RAB: it fell back to their standalone RAB 14.6. Separately, Bloom never saw RAB's exit codes; PR #8435 (now in Version6.4) and 14.0.1's own rab.bat fix that.

What the PR does

  • Bloom uses only Reading App Builder for Bloom, with its own JDK and Android SDK, as BL-16148 intended. It never falls back to a standalone RAB. Open in RAB brings forward only a window of that edition.
  • Prepare and Build check the build tools themselves. If Bloom's JDK or SDK isn't there after -install-sdks-if-needed, they stop with a plain error ("Bloom could not set up the tools it needs to build Android apps. Please use Help > Report a Problem…"). Details for support follow: which tool is missing, which folder RAB used instead, and RAB's own error.
  • Bloom requires Reading App Builder for Bloom 14.0.1 (kRabInstallerVersion), which fixes the C:\sdk bug (app-builders #2494) and some Bloom Player bugs. With an older RAB installed, the Prepare step says so (the notice), and Choose Books, Customize and Build stay disabled until Prepare installs 14.0.1. New installs get 14.0.1. A failed download or install stops Prepare with a plain message, and so does an install after which RAB still reports the old version. Bloom only accepts an installer that really is a Windows program: for a missing file, bloomlibrary.org returns its web page with a success status, which Bloom used to save, try to run, and keep reusing. Interrupted downloads leave nothing behind.
  • Errors reach the user as Bloom wrote them. ReportFailure no longer digs down to the innermost error, so the plain messages (and Build's existing RAB diagnostics, BL-16467) are what the user sees.
