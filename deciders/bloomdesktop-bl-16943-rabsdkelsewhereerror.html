What this PR is about

Problem

In Publish > Apps, Prepare can report "Prepare complete." while the "Install build tools" step stays unchecked. Choose Books, Build and the later steps then stay disabled, and nothing tells the user why. A forum user hit this on 6.4.1, and Colin hit it earlier (BL-16491).

Cause

Bloom runs rab.bat -install-sdks-if-needed and names its own JDK and Android SDK folders. When Reading App Builder (RAB) 14 starts, it looks for an existing Android SDK in C:\sdk, C:\sdk2, and so on. If it finds one, it prints Android SDK is already installed at: C:\sdk, installs nothing in Bloom's folder, and exits 0. RAB treats the JDK the same way. The forum user's Bloom also wasn't using its own RAB: it fell back to their standalone RAB 14.6. Separately, Bloom never sees RAB's exit code (rab.bat ends with GOTO :EOF), so a failed download looked like success too; PR #8435 fixes that.

What the PR does

  • Bloom uses only Reading App Builder for Bloom, with its own JDK and Android SDK, as BL-16148 intended. It never falls back to a standalone RAB. Open in RAB brings forward only a window of that edition.
  • Prepare and Build check the build tools themselves. If Bloom's JDK or SDK isn't there after -install-sdks-if-needed, they stop with a plain error ("Bloom could not set up the tools it needs to build Android apps. Please use Help > Report a Problem…"), followed by details for support: which tool is missing, and which folder RAB used instead (RabProjectService.cs).
  • Prepare updates an older Reading App Builder for Bloom when kRabInstallerVersion is newer. Nobody is forced back into Prepare. If the update can't be downloaded, or its installer never starts, Prepare carries on with the installed version. If the installer runs and fails, Prepare stops and reports it, because the older version may no longer be intact. The installer downloads under a temporary name, so an interrupted download leaves nothing behind. This is how users will get the RAB fix (app-builders #2494) once it's released.

When to bump the Reading App Builder installer version

This PR leaves kRabInstallerVersion at 14-0, so Prepare won't update anyone yet. A 14.6 "for Bloom" installer exists (it's in your Downloads). But 14.6 doesn't include the C:\sdk fix: app-builders #2494 isn't merged or released. Bumping means uploading the installer to bloomlibrary.org/RAB/installers/ and changing the version in RabProjectService.cs and the URL in AppPublisherScreen.tsx.

A failed SDK download after PR #8435 merges

PR #8435 (BL-16959) makes RAB's exit code reach Bloom. Once both PRs are in, a failed JDK or SDK download (for example, offline) makes the install command itself fail. Prepare then stops with the raw "cmd.exe exited with code 1" plus RAB's output, before this PR's plain message. The C:\sdk case is unaffected, because RAB exits 0 there.

The old draft PR #8429

Draft PR #8429, a colleague's first attempt at this card, is still open, on the 6.5 base. #8436 replaces it.

When an update's installer runs and fails

If Prepare tries to update Reading App Builder for Bloom and the installer starts but then fails, Prepare now stops and shows the installer's error. Bloom can't tell whether the older version is still intact, because the installer updates the version Bloom reads only at the very end. The user can click Prepare again, which retries the update. When the update can't be downloaded, or the installer never starts (for example, the admin prompt is refused), Prepare still carries on with the installed version. Devin first asked for "carry on"; Greptile then showed that carrying on can't be done safely.
