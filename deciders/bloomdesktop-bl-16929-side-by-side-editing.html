What this PR is about

Problem

Bloom's Edit tab shows one page at a time. People laying out a children's book want to see the page they are editing beside its facing page, and the rest of the book around it, the way it will be read (community request).

What the PR does

  • A page view chooser in the Edit tab's top bar, under the account avatar, switches between one page at a time and all pages. The choice is remembered from page to page and across sessions; choosing all pages zooms out if two pages would not fit across.
  • All pages lays the whole book out in spreads around the page being edited, as the printed book is read. Only that page is editable; the others are read-only renderings in sandboxed iframes, drawn only near the screen and fetched four at a time. None of it is saved with the page.
  • Clicking another page makes it the page being edited in the same place on screen and replays the click: text gets the caret, a picture is selected.
  • Page changes hold steady in both views: the new page loads under the old one, behind a wait cursor, and replaces it only when laid out. This needs PR 8209, which stopped saving from taking the page apart.
  • The controls above the page (Change Layout, game tabs) sit in a bar fixed at the top of the page frame.
  • Commit 401a192c41 is a one-line fix that belongs in PR 8209 (it calls a function master removed, so saving a page with text throws).

Worth knowing

  • In All pages, the hint and source bubbles of the page being edited can cover the start of the facing page's text, and a click there lands on the bubble instead of opening that page. Not addressed; the test notes tell testers to expect it.
  • Right-to-left books were not designed for: the pairs are laid out left to right. The test notes ask a tester to report what they see.

Decisions

Should a click on another page in the grid wait its turn behind page-list commands?

PR 8209 makes every page-list request (a click, or a right-click command such as Duplicate, Delete or Move) wait for the one before it, so Bloom receives them in the order the user made them. A click on another page in the grid bypasses that queue, because the queue lives inside the page list's own frame and nothing exposes it. If someone picks a right-click command in the page list and clicks a page in the grid a moment later, the grid click can reach Bloom first, and the command then acts on the page just clicked: for example, deleting the wrong page. The window is short, but the result can lose a page. Greptile raised this (thread).

Other:

Should the other pages show their videos?

The other pages are drawn from the content Bloom makes for the page list, which removes every video. So in All pages, a page with a video shows without it until you click that page. Getting the videos back needs a small C# change again (a full-size option on the page-list content request), which would put PageListApi.cs back in the PR and let the front end stop rewriting picture addresses. Videos are rare in print-style books and the other pages are only previews, so I recommend leaving it; the test notes already tell testers to expect it. Devin and Greptile both raised it (Devin, Greptile).

Other:

Should I tell PR 8209 about the function it still calls?

At the head of PR 8209, saving a page calls EditableDivUtils.removeCkEditorFillingChars, which master removed. Every save of a page with text then throws, Bloom reports "Bloom could not keep track of your changes to this page", and the typing is lost. This PR carries the one-line fix (commit 401a192c41) so it can be tested, but the fix belongs in 8209, which is John Thomson's.
