What this PR is about

Problem

Logging in to bloomlibrary.org often fails with the alert “Oops, something went wrong when trying to log you into our database”, and the user ends up logged out. Sentry shows two cases over the last 90 days:

  • A brand-new account’s first login, which every new sign-up hits (160 of 240 events).
  • A second login without reloading the page, e.g. after logging in from Bloom’s Publish > Web screen and going to My Books (43 of 240).

Cause

  • New accounts: when the login request creates the user, parse-server’s reply contains only the id, creation time and session token. It leaves out the email and username we sent, and our check requires an email.
  • Second login: after the first login, the session token stays in the shared request headers. The second login sends it, so parse-server treats the request as the current user re-linking their login and issues no new session token.

What the PR does

  • Each login sends its own copy of the headers without any old session token, so every login gets a fresh session. Because the copy is per login, two logins that overlap can’t pick up each other’s new token. The shared token is still set only when a login succeeds (ParseServerConnection.ts:95).
  • When the reply has no email or username, uses the verified Firebase email, which is what we sent for both. It goes into the check, the logged-in user, and the login message to Bloom, which fails without an email (BL-14503). With the username in place, a new user is recognised as the uploader of their own books without reloading (:138).
  • Adds unit tests against a fake parse-server for a second login, a new account, and two overlapping logins. Each fails on the code before its fix.
