What this PR is about

Problem

Logging in to bloomlibrary.org often fails with the alert “Oops, something went wrong when trying to log you into our database”, and the user ends up logged out. Sentry shows two cases over the last 90 days:

  • A brand-new account’s first login, which every new sign-up hits (160 of 240 events).
  • A second login without reloading the page, e.g. after logging in from Bloom’s Publish > Web screen and going to My Books (43 of 240).

Cause

  • New accounts: when the login request creates the user, parse-server’s reply contains only the id, creation time and session token. It leaves out the email we sent, and our check requires both a session token and an email.
  • Second login: after the first login, the session token stays in the shared request headers. The second login sends it, so parse-server treats the request as the current user re-linking their login and issues no new session token.

What the PR does

  • Clears any old session token before the two login requests, so every login gets a fresh session (ParseServerConnection.ts:93).
  • When the reply has no email, uses the verified Firebase email, which is also the account’s username. That email goes into the check, the logged-in user, and the login message to Bloom, which fails without one (BL-14503) (:137).
  • Adds unit tests for both cases against a fake parse-server. Both fail on master.

Worth knowing

  • Neither fix has been tried against a real parse-server login. The test ideas on the card cover both cases on the dev site.
  • Follow-up, deliberately left out of this PR: UserMenuCodeSplit.tsx calls React.lazy inside the component, so the header’s user menu remounts on every navigation and briefly shows a logged-in user the logged-out icon. That is probably how users get prompted to log in a second time. Moving it to module scope fixed it in a test (4 mounts became 1). Every other *CodeSplit component has the same pattern.

1. Also fill in the username for brand-new accounts?

The same reply that leaves out the email also leaves out the username. So after a brand-new account’s first login, the logged-in user’s username is empty until the page is reloaded. The site uses the username to recognise a book’s uploader. A new user who uploads a book from Bloom and then opens it on the site in the same tab won’t see their owner controls (e.g. the draft setting). Also, on a book with no uploader recorded, the new user would be treated as the uploader in the extra panels. Greptile, Devin and the local review all flagged this. It is outside the “only these two things” scope you set, so it is not in the PR.

2. Give each login its own copy of the headers?

The PR clears the old session token from the shared request headers when a login starts. If two logins ever run at once, the first one to finish puts its new token back into those shared headers. The second one then sends that token and gets no session, so the user is signed out. That already happens on master, and this PR neither causes nor fixes it. Devin rates it severe. It is unclear whether two logins really overlap in practice, but a comment in editor.ts says duplicate login notifications to Bloom have been seen. The fix Devin and Greptile both suggest: make a token-free copy of the headers for the two login requests, and leave the shared headers alone until the login succeeds. It is about the same size as the current fix, but differs from the “clear it from connection.headers” approach your brief specified.

3. Declare the tracker in this repo?

BloomLibrary2 has no AGENTS.md or CLAUDE.md at its root, so nothing tells agents that its tickets are YouTrack BL-##### ids handled by the youtrack-api skill. This run used the card named in your brief. Without a declaration, the next preflight in this repo will stop and ask.
