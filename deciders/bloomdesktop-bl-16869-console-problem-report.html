What this PR is about

Problem

When a problem report happened in a Bloom with nobody at the keyboard, Bloom put up a modal dialog no one could dismiss, and the process blocked forever — no error, no exit code, no completion. That hits bloom upload run from a script, and also the child Bloom that Bloom's own Publish → Upload → “Upload this Collection” buttons launch: a bulk upload would stop part way through a collection and sit there in its console window. It is how one real exception (BL-16867) became a 10-minute nightly timeout that took three runs and two wrong timeout increases to diagnose, because the failure looked like slowness rather than an error.

Cause

NonFatalProblem has suppressed dialogs in console mode for a while, but the problem-report dialogs never learned to. So the two paths disagreed: a non-fatal problem in a command-line verb printed and carried on, while a problem report in the same process blocked forever.

What the PR does

  • Adds Program.RunningNonInteractive — command-line verbs only — and a shared helper that reports on stderr and tells the caller to return.
  • Both problem-report entry points honour it: ShowProblemDialog, and HtmlErrorReporter.ShowNotifyDialog — the latter is the path a plain ErrorReport.NotifyUserOfProblem takes, and the one that actually hung the nightly. Both still log and report to Sentry first, so nothing is lost.
  • Makes the failure propagate, since returning is not enough on its own: BookUpload refuses to upload a book whose PDF failed — a partial PDF can be on disk, so the pre-existing “does the file exist” check was not sufficient — and UploadCommand exits non-zero and says the upload failed rather than printing “Bulk upload complete”.
  • Completes that success signal: a collection refused for a missing default bookshelf or too low a subscription tier, and a book skipped for a missing collection file or a colliding ID, now count as failures too. Previously those were logged as errors but still exited 0.
  • --e2e is deliberately excluded, unlike in NonFatalProblem. The e2e suite's problemDialogWatcher fixture finds the dialog among the CDP page targets and fails the test with the exception behind it; suppressing it there would let tests go green through errors they currently catch. Nothing is lost — the bulk-upload child runs the upload verb, so it is in console mode anyway.

Interactive Bloom is unchanged: every guard sits behind RunningNonInteractive, which is false there.

Worth knowing

  • Nothing here has been exercised by hand. No real bulk upload was run — the evidence is the unit tests plus reading the path. The QA notes on the card lead with the manual check that matters most: force a failure and confirm the console window finishes instead of freezing.
  • The propagation path has no automated test — only the dialog guards do. That is decision 1 on the right.
  • A PDF failure is reported twice in a bulk upload: once into Bloom's own log via the pre-existing error path, once into BloomBulkUploadLog.txt via the caller's progress. Deliberate — the second is the one someone chasing a failed upload actually reads.

Decision 1

No automated test covers “a failed PDF is not uploaded”

The tests in this PR cover the dialog guards thoroughly — that a command-line Bloom writes to stderr instead of showing a dialog, that an interactive one still shows it, and that an --e2e run still shows it. They do not cover the second half of the fix: that a book whose PDF generation failed is actually refused by the uploader, and that the run then exits non-zero.

That second half is the part with the nastier failure mode. If it regressed, a bulk upload would silently upload a half-made PDF and report success — worse than the hang this PR fixes, because nobody would notice. The reason it is untested is cost: MakePDFForUpload needs a fully built PublishModel (a book, a collection, a book server, a thumbnailer) and it drives a BackgroundWorker with an Application.DoEvents pump, which this repo's own notes describe as fragile inside the test host. There is no existing fixture to build on.

Decision 2

How much should bloom upload treat as failure?

Before this PR, bloom upload always exited 0. It now exits 1 for anything it refused to do, which is a wider set than the original bug strictly needed. Concretely, it now fails when: no collections were found at all; a collection was skipped for having no default bookshelf; a collection was skipped because its subscription tier does not include bulk upload; a book was skipped for having no collection file in its parent folder; a book was skipped because its ID collides with a book already on BloomLibrary; or, the original case, a book's PDF could not be made.

Each of those already printed an error and already meant “we did not upload what you asked for”, so failing on them is consistent. The tradeoff is that anyone scripting bloom upload today sees exit 0 in all these cases, and a partner's script that checks the exit code will start failing on collections it has been quietly skipping for a long time.
