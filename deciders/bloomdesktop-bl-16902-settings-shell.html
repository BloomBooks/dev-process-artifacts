What this PR is about

Problem

BL-16271 is moving Bloom's collection Settings dialog off WinForms and onto React with Config-R, and nothing on master was ready for that work to start. The React side was an empty two-page skeleton that C# never launched, backed by a placeholder endpoint. Everything that actually saves collection settings lived inside the WinForms dialog's OK handler, reachable from anywhere else only through a static pointer to the currently-open WinForms dialog. None of the seven per-tab cards could begin against that.

What the PR does
  • A real React dialog shell. Seven Config-R pages in the new design's order, with localized labels and placeholder content, sized like Book Settings. A second Settings button on the collections toolbar opens it; the WinForms button is relabelled "Old Settings" until the cutover.
  • Real save behaviour. OK saves everything in one POST and Cancel posts nothing. When a changed value needs a restart, the dialog shows the "Bloom will close and re-open" reminder and relabels OK as "Restart". A validation problem is shown in place instead of closing. Each open starts from freshly fetched values, OK is held while a save is in flight, and a save that fails outright is reported and leaves the user's edits intact to try again.
  • One place where pending settings live. A PendingCollectionSettings session replaces the static DialogBeingEdited pointer, so both dialogs and the React tab components that already exist (Subscription, Team Collection, bookshelf) read and write the same pending state during the overlap.
  • The save logic is now testable. CollectionSettingsUpdater.Validate/Apply holds what the WinForms OK handler used to do, with unit tests.
  • Endpoints. collection/settings GET/POST/cancel and workspace/showSettingsDialog (which can deep-link to a page), sharing the legacy dialog's Team Collection guard.
  • Four settled decisions, and tentative answers to the questions still open, are recorded in docs/collection-settings-react/PLAN.md.

The legacy WinForms dialog keeps working unchanged, through the shared pending session.

Decision 1

Settings endpoints now throw where they used to do nothing

The old code kept a pointer to the open WinForms dialog, and every endpoint that records a pending setting began by checking "is a dialog actually open?". This PR replaces that pointer with a pending-settings session and drops those checks, so several endpoints now assume a session exists and raise a null-reference error if it does not. A user sees that as a "Bloom had a problem" box.

The clearly reachable case — a second click on OK arriving after the first save closed the session — is already fixed on the front end in this PR. What is left is the narrower race where a control sends its value as the dialog is being dismissed: a font, page-numbering, front/back-matter, bookshelf or administrator-email change landing just after OK or Cancel; plus the script-settings link, which needs the WinForms dialog to be open and now throws instead of quietly doing nothing. Devin raised a third variant on its own thread: if a save's reply were lost, the retry would land on an ended session.

There is a real tension here. The repo's own guidance says not to be defensive, and to let incorrect API use throw so we hear about it. Against that, this one surfaces as a crash report to a user rather than to a developer.

Decision 2

Bloom now restarts after OK when it quietly corrects the front/back-matter pack

When Settings is saved, Bloom checks the chosen front and back matter pack and may swap in a different one — because the subscription's branding forces a particular pack, or because the saved pack no longer exists. That swap can happen even when the user changed nothing at all.

In the WinForms dialog this never caused a restart: the corrected pack was written into the collection before the "does anything need a restart?" question was asked, so the answer was always no. The moved code asks the question first, so the correction now counts as a change in its own right. For anyone in a collection whose pack is being corrected, pressing OK in Settings — with nothing touched — will close and re-open the collection every single time.

A new unit test locks in the current behaviour, so it may well be deliberate; either way it differs from the code it replaced.

Decision 3

Clearing the third language does not remove it

When the collection has no third language, the settings the dialog is given describe it as "nothing". When the dialog sends the settings back, the C# side treats "nothing" for a language as "the user didn't tell me anything about this one, leave it alone" rather than "remove it". So a user who clears Language 3 in the new dialog and presses OK would find the third language still there.

Nobody can hit this yet — the Languages page is a placeholder — but it is the contract the Languages card (BL-16739) will be built against, and it is the kind of thing that is much cheaper to settle now than to discover later. Raised by Devin on its own thread, which stays open until this is answered.

Decision 4

The four new page names went into the top-priority translation file without being checked with you

Four new translatable strings were added for the dialog's page names — Front & Back Matter, Subscription, Bloom Library, Experimental — and they went into Bloom.xlf, the file whose strings translators are asked to do first. The repo's own procedure says to stop and confirm the priority file with you before adding an entry, and that did not happen, which is what Devin flagged on its thread.

For what it is worth, that is where the dialog's other tab labels already live, and all four carry the usual marker that keeps them out of Crowdin until the English settles. So this is a confirmation, not a correction — unless you would rather these sat lower.

Leaving them is the recommendation: page names are the first thing a user reads in the dialog, and every other Settings tab label is already top priority.
