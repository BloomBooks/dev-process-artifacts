What this PR is about

Problem

BL-16271 is moving Bloom's collection Settings dialog off WinForms and onto React with Config-R, and nothing on master was ready for that work to start. The React side was an empty two-page skeleton that nothing launched, backed by a placeholder endpoint. Everything that actually saves collection settings lived inside the WinForms dialog's OK handler, reachable from anywhere else only through a static pointer to the open WinForms dialog. None of the seven per-tab cards could begin against that.

What the PR does

  • A real React dialog shell. Seven Config-R pages in the new design's order, with localized labels and placeholder content, sized like Book Settings. A second Settings button on the collections toolbar opens it; the WinForms button is relabelled "Old Settings" until the cutover.
  • Opened from the browser, from any tab. showCollectionSettingsDialog(pageKey?) raises the dialog's launch event directly, with no round trip through C#, and App renders the dialog, so later callers on any tab can open it on a named page.
  • Real save behaviour. OK saves everything in one POST and Cancel saves nothing. A change that needs a restart shows the reminder and relabels OK as "Restart". A validation problem shows in place; a save that fails outright is reported and keeps the user's edits for a retry.
  • Team Collection administrators only. The settings request applies the old button's rule: a non-administrator gets just the reason, in a small dialog with Close, and no editing session opens.
  • One place where pending settings live. A PendingCollectionSettings session replaces the static DialogBeingEdited pointer, so both dialogs and the existing React tabs (Subscription, Team Collection, bookshelf) share the same pending state during the overlap.
  • The save logic is testable. CollectionSettingsUpdater.Validate/Apply holds what the WinForms OK handler did, with unit tests; the legacy dialog keeps working through it.

The plan for the rest of BL-16271 is docs/collection-settings-react/PLAN.md.

Worth knowing

  • Tried by hand in Bloom: the new dialog from the Collections and Edit tabs (including opening on a named page); a forced save failure and its retry; a Team Collection as administrator and as non-administrator; the old dialog's Cancel, OK, rename and subscription undo; and switching between the two dialogs.
  • Not tried by hand: Esc or Cancel while a save is still in flight. The save completes too fast to catch, so that guard is covered by its unit test only.
  • Any save, in either dialog, rewrites a collection with an expired subscription to branding Default. That is how CollectionSettings.Save() has always worked, not something this PR changed.
  • The Descriptor != Descriptor comparison in CollectionSettingsUpdater is always false. It was carried over unchanged, with a comment pointing at BL-16904.
