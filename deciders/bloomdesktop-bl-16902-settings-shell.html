What this PR is about

Problem

BL-16271 is moving Bloom's collection Settings dialog off WinForms and onto React with Config-R, and nothing on master was ready for that work to start: the React side was an empty two-page skeleton that nothing launched, backed by a placeholder endpoint, and everything that saves collection settings lived inside the WinForms dialog's OK handler.

What the PR does

  • A React dialog shell. Seven Config-R pages in the new design's order, with localized labels and placeholder content, sized like Book Settings, opened by a second Settings button on the collections toolbar. The WinForms button is relabelled "Old Settings" until the cutover.
  • Opened from the browser, from any tab. showCollectionSettingsDialog(pageKey?) raises the dialog's launch event directly, and App renders the dialog, so later callers on any tab can open it on a named page.
  • A save path of its own. The GET returns the current values and which of them need a restart; OK posts { values, restartRequired } once. C# copies the values onto a PendingCollectionSettings and applies them with CollectionSettingsUpdater, a copy of the WinForms OK logic, then reopens the collection if needed. A validation problem shows in the dialog; a save that fails outright is reported and leaves OK enabled.
  • Team Collection administrators only. A member who is not an administrator gets just the reason, in a small dialog with Close.
  • The WinForms dialog is untouched. It and its endpoints are exactly as on master; the two coexist only on alpha until the cutover.

The plan for the rest of BL-16271 is docs/collection-settings-react/PLAN.md (§3.0 records what was built).

The zero-length timer in the dialog tests

The front-end rules in src/BloomBrowserUI/AGENTS.md say: "Don't use timeouts in tests… If a timeout is justified, get my approval and add a comment explaining it." The dialog tests' flushDeferredChange helper waits on setTimeout(0). The dialog defers its Config-R change handling into a zero-length timer (Config-R can call onChange while rendering), so the test has to let that timer run before it checks the OK label or the posted values. It is a flush, not a delay, and a comment above it already says so; it was never approved. This is probably one of the two rules Greptile means.

The nulls in the TypeScript types

The same rules file says "We rarely use null in typescript, preferring undefined." The new response types use null in two places: notAllowedMessage: string | null and language3: … | null. Both mirror what C# actually sends: Newtonsoft writes an unset field as JSON null, and "no third language" is null on the wire in both directions. Typing them as undefined would describe the JSON wrongly, or need a conversion step at the boundary. Leaving them is my recommendation; this is probably Greptile's other rule.
