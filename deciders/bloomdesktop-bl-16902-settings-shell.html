What this PR is about

Problem

BL-16271 is moving Bloom's collection Settings dialog off WinForms and onto React with Config-R, and nothing on master was ready for that work to start. The React side was an empty two-page skeleton that nothing launched, backed by a placeholder endpoint, and everything that saves collection settings lived inside the WinForms dialog's OK handler. None of the seven per-tab cards could begin against that.

What the PR does

  • A real React dialog shell. Seven Config-R pages in the new design's order, with localized labels and placeholder content, sized like Book Settings. A second Settings button on the collections toolbar opens it; the WinForms button is relabelled "Old Settings" until the cutover.
  • Opened from the browser, from any tab. showCollectionSettingsDialog(pageKey?) raises the dialog's launch event directly, with no round trip through C#, and App renders the dialog, so later callers on any tab can open it on a named page.
  • Real save behaviour. OK saves everything in one POST and Cancel saves nothing. A change that needs a restart shows the reminder and relabels OK as "Restart". A validation problem shows in place; a save that fails outright is reported and keeps the user's edits for a retry.
  • Team Collection administrators only. The settings request applies the old button's rule: a non-administrator gets just the reason, in a small dialog with Close, and no editing session opens.
  • Its own save pipeline. collection/settings GET/POST/cancel, a PendingCollectionSettings session, and CollectionSettingsUpdater (a copy of the WinForms apply logic) with unit tests.
  • The WinForms dialog is untouched. It and the endpoints its tabs use are exactly as on master; the two only coexist on alpha until cutover, when the old one and its copy of the logic go.

The plan for the rest of BL-16271 is docs/collection-settings-react/PLAN.md; §3.0 records what was built.
