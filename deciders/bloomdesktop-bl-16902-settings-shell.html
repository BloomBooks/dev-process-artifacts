What this PR is about

Problem

BL-16271 is moving Bloom's collection Settings dialog off WinForms and onto React with Config-R, and nothing on master was ready for that work to start. The React side was an empty two-page skeleton that C# never launched, backed by a placeholder endpoint. Everything that actually saves collection settings lived inside the WinForms dialog's OK handler, reachable from anywhere else only through a static pointer to the currently-open WinForms dialog. None of the seven per-tab cards could begin against that.

What the PR does
  • A real React dialog shell. Seven Config-R pages in the new design's order, with localized labels and placeholder content, sized like Book Settings. A second Settings button on the collections toolbar opens it; the WinForms button is relabelled "Old Settings" until the cutover.
  • Real save behaviour. OK saves everything in one POST and Cancel posts nothing. When a changed value needs a restart, the dialog shows the "Bloom will close and re-open" reminder and relabels OK as "Restart". A validation problem is shown in place instead of closing. Each open starts from freshly fetched values, OK is held while a save is in flight, and a save that fails outright is reported and leaves the user's edits intact to try again.
  • One place where pending settings live. A PendingCollectionSettings session replaces the static DialogBeingEdited pointer, so both dialogs and the React tab components that already exist (Subscription, Team Collection, bookshelf) read and write the same pending state during the overlap. As before, a post that lands when no dialog is open — a control losing focus as one closes — is ignored rather than failing.
  • The save logic is now testable. CollectionSettingsUpdater.Validate/Apply holds what the WinForms OK handler used to do, with unit tests, and asks for a restart only for what the user actually changed.
  • Endpoints. collection/settings GET/POST/cancel and workspace/showSettingsDialog (which can deep-link to a page), sharing the legacy dialog's Team Collection guard.
  • Four settled decisions, and tentative answers to the questions still open, are recorded in docs/collection-settings-react/PLAN.md.

The legacy WinForms dialog keeps working unchanged, through the shared pending session.

Worth knowing

  • Nothing added since the manual pass has been tried by hand — this round's endpoint guards and restart change, and the three dialog fixes from the round before (re-opening Settings, OK while a save is in flight, a save that fails outright). All of it is covered by unit tests only.
  • The save endpoint itself still assumes a session is open, unlike the others. The dialog holds OK down while a save is in flight so it cannot send a second one, and the only remaining way in would be a save whose reply never arrived although the settings were applied. One line would close that off, if you would rather not leave it — it is offered under "next step".
  • Every page in the new dialog is a placeholder, so nothing in it can be changed yet. A tester can only exercise the frame — and, much more importantly, re-test the old dialog, whose saving now runs through the moved code.

Decision 1

The four new page names went into the top-priority translation file without being checked with you

Four new translatable strings were added for the dialog's page names — Front & Back Matter, Subscription, Bloom Library, Experimental — and they went into Bloom.xlf, the file whose strings translators are asked to do first. The repo's own procedure says to stop and confirm the priority file with you before adding an entry, and that did not happen, which is what Devin flagged on its thread. That thread stays open until you answer.

For what it is worth, that is where the dialog's other tab labels already live, and all four carry the usual marker that keeps them out of Crowdin until the English settles. So this is a confirmation, not a correction — unless you would rather these sat lower.

Leaving them is the recommendation: the page names are the first thing a user reads in the dialog, and every other Settings tab label is already top priority.
