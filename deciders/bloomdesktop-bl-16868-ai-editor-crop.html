What this PR is about

Problem

Picking Edit with AI... on an image that has been cropped handed the AI image editor the whole, uncropped image file rather than the picture as it appears on the page. The AI therefore worked on a frame the user was not looking at, and composed its results around parts of the picture the book does not show. On commit the two halves of the feature then disagreed: a replacement landing on the currently-open page came back uncropped, while one landing on any other page kept the old crop and so was cropped a second time by a rectangle computed for the image it had just replaced.

Cause

Cropping in Bloom is presentational. The image file keeps its whole frame and the visible rectangle is expressed as width, left and top styles on an image inside a canvas element that fixes the visible box. The launch payload carried only a URL to the file, so no crop travelled with it. At commit time the front end clears those styles, but the C# path for off-page slots never did.

What the PR does

  • A slot whose crop actually hides part of its image is now offered as a rendering of just the visible rectangle, written into a working folder in the book and cleared at each launch. Uncropped slots are offered as their own file, exactly as before.
  • Bloom writes those same styles when it merely fits a background image to its canvas, so a new ImageUtils.CropHidesPartOfImage decides whether anything is really hidden. Without it nearly every background image in a book would be re-encoded at launch to produce a copy of itself. It also refuses a rectangle with no area, which is what a canvas element carrying a width and no height would otherwise produce.
  • On commit, an off-page slot now has the crop cleared and, for a background image marked to cover its canvas, is re-centered to fill it, because there the crop styles are what make the picture full-bleed and clearing alone would letterbox a whole page. The copy that a Bloom Games target holds of a draggable's picture gets the same treatment.
  • The editor's protocol is untouched: it treats a slot's source as an opaque URL, so this is host-side only. Credits still come from the original image file, and the book's own images are never modified.

Off-page picture frames keep their old shape

Raised by Devin, twice, and open since the previous round — the review thread.

When someone accepts an AI result onto a picture that sits on a page they are not currently looking at, the frame around that picture keeps the shape it had for the picture being replaced. A tall result dropped into a frame that used to hold a wide one is shown whole, but with empty space above and below it, until the user resizes the frame by hand. On the page they are looking at this does not happen: the front end follows the crop-clearing with a step that reshapes the frame to suit the new picture.

An off-page cropped picture replacement leaves the picture inside the old canvas shape. The current-page path reshapes that canvas, so off-page replacements become letterboxed.

The reason it was left is that the reshaping rule lives in about a hundred and twenty-five lines of front-end layout code whose inputs are not all present in the saved page. Reproducing it in C# means either guessing at those inputs or moving the rule somewhere both paths can call, which is a larger change than the bug this PR fixes. The picture itself is complete and correct either way; only the frame around it is wrong, and the user can drag it.
