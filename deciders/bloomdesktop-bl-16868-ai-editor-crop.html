What this PR is about

Problem

Picking Edit with AI… on a picture that has been cropped handed the AI image editor the whole, uncropped image file rather than the picture as it appears on the page. The AI therefore worked on a frame the user was not looking at, and composed its results around parts of the picture the book does not show. On commit the two halves of the feature then disagreed: a replacement landing on the currently-open page came back uncropped, while one landing on any other page kept the old crop and so was cropped a second time by a rectangle computed for the image it had just replaced.

Cause

Cropping in Bloom is presentational. The image file keeps its whole frame and the visible rectangle is expressed as width/left/top styles on an <img> inside a canvas element that fixes the visible box. The launch payload carried only a URL to the file, so no crop travelled with it. At commit time the front end clears those styles; the C# path for off-page slots never did.

What the PR does

  • A slot whose crop actually hides part of its image is offered as a rendering of just the visible rectangle, written to .ai-image-editor/cropped/ in the book and cleared at each launch. Uncropped slots are offered as their own file, exactly as before. (TryMakeCroppedViewOfSlotImage)
  • Bloom writes those same styles when it merely fits a background image to its canvas, so CropHidesPartOfImage decides whether anything is really hidden. Without it nearly every background image in a book would be re-encoded at launch to produce a copy of itself.
  • On commit, an off-page slot has the crop cleared — and, for a background image marked to cover its canvas, is re-centered to fill it, because there the crop styles are what make the picture full-bleed and clearing alone would letterbox a whole page. (RefitSlotImageForNewPicture)
  • The copy a Bloom Games target holds of a draggable's picture gets the same treatment; its sizing is still left to the front end.
  • The editor's protocol is untouched: it treats a slot's src as an opaque URL, so this is host-side only.

Credits still come from the original image file, and the book's own images are never modified.

Worth knowing

  • None of this has been exercised in a running Bloom. It is covered by eleven unit tests, including the cover-fill arithmetic, but nobody has opened the AI editor on a cropped picture and looked. The test-ideas comment on the card leads with exactly that check.
  • Opening the editor now costs one GraphicsMagick identify per picture that carries crop styles, plus a full re-encode for each picture that is genuinely cropped (about 30 ms and 105 ms respectively on a 900 KB photo here). A book where most pages are cropped full-bleed photos is the case where that could be felt.
  • Two runs of the full C# suite each failed one unrelated test (a locked localization file, then a drive-name error). Both were my own doing — a build racing the test host in the same isolated tree — and the clean run at HEAD is green. Not a branch problem.

Decisions

Off-page picture frames keep their old shape

When you accept an AI result onto a picture that is not on the page you currently have open, the frame around that picture keeps the shape it had for the picture being replaced. So a wide result dropped into a frame that used to hold a tall picture is shown whole, but with empty space above and below it, until someone resizes the frame by hand. On the page you do have open this does not happen — the front end reshapes the frame to suit the new picture.

This is better than what it replaces: before this branch that picture came back cropped by the old rectangle, so the user saw an arbitrary zoomed-in fragment of the new picture instead of the whole of it. Devin raised it as a bug; I left it deliberately, because reshaping the frame properly means reproducing about 125 lines of front-end layout rules whose inputs include the size of the page canvas, which is a CSS layout result and is not in the saved file at all. This file already declines that kind of duplication for the same reason, in the comment about the Bloom Games target copies.

Devin: “An off-page cropped picture replacement leaves RefitSlotImageForNewPicture inside the old canvas shape. The current-page path reshapes that canvas through adjustContainerAspectRatio, so off-page replacements become letterboxed.”
