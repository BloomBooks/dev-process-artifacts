What the change does

An undo does not edit text in place — it writes a saved snapshot over the whole text box, rebuilding every text node in it. Since #8123 the reader and Talking Book highlights are ::highlight() pseudo-elements painted over live Range objects into those nodes, so every highlight in the box dies at that moment: still registered, painting nothing. Only a markup pass re-creates them, and three separate things stopped one from running.

Why no repaintFix
Nothing scheduled one. The top-bar Undo button produces no keystroke, so the keyup-driven update never ran. Every undo path calls updateMarkupAfterUndoOrRedo() — CKEditor's own undo/redo commands via a new afterCommandExec hook, the top bar's two text-changing branches, and the reader tools' Ctrl+Z interception.
The pass gave up when the selection was a range rather than a caret — and an undo restores whatever selection its snapshot held. The guard now lets an undo through; the bookmark machinery preserves a range just as it does a caret.
jquery.longpress sets its "evaluating" flag on every keydown and clears it on keyup. Ctrl+Z does its work on the keydown, so the flag was always set. Undo is exempt from that flag — Ctrl+Z can't be a longpress, which is about holding a letter key on its own.

Undo also waits on its own timer rather than the shared one, because the keyup that ends Ctrl+Z would otherwise cancel the very update the undo just asked for. It runs immediately, spaced at least 150ms apart so a held Ctrl+Z doesn't re-mark the page on every auto-repeat.

Decision 1

Talking Book's undo doesn't get the fast repaint on Ctrl+Z

Every markup pass stamps a shared counter, and a pass that has to wait for an answer from the server throws its own result away if the counter moved while it waited. That guard is there for a good reason: Talking Book's markup is computed from a copy of the text box taken before the wait, so applying it late could overwrite a character the user typed in the meantime.

The snag is that pressing Ctrl+Z ends with a key-up, and that key-up bumps the counter. So with the Talking Book tool open, the undo's own markup pass is discarded and the key-up's ordinary pass does the work half a second later. Nothing is broken — that is exactly today's behaviour, and the yellow sentence highlight is repaired instantly by other machinery regardless — but the "repaint immediately" benefit doesn't reach that one path. The top-bar Undo button, which produces no key-up, does get it.

Recommendation is to leave it: the visible symptom is already handled, and every way of closing the gap means touching a guard that protects against losing a keystroke. Devin's flag (open).

Decision 2

An undo can wipe the reader tools' redo list

The reader tools keep a small undo list of their own, separate from the editor's. Whenever a markup pass notices the text has changed, it adds an entry to that list and throws away anything that could be redone.

Because this change makes the top-bar Undo button run a markup pass where it previously ran none, a new sequence becomes possible: you press Undo, the pass tidies up a stray non-breaking space (Bloom converts those in some situations, which counts as the text changing), and the redo entry is discarded on the spot.

How much this matters is genuinely unclear, which is why it's here rather than fixed. That list is only reached from the top-bar Undo button — Ctrl+Z is taken by the editor before the reader tool sees it — and there is no Redo button in the top bar at all. It is also the same list this card has already parked a question about removing now that markup no longer rewrites the text; if it goes, this goes with it. Recommendation is therefore to leave it and fold it into that larger decision. Devin's flag (open).
