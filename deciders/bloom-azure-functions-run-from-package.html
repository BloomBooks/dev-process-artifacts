What this PR is about

Problem

Every new instance of bloom-functions holds the requests sent to it for about 2.5–4 minutes before running any of them: median 190 s across 96 cold starts in 30 days. On 2026-10-27 a morning with many cold starts made this visible as a 3.5-minute stall. Deploys also depend on Kudu running npm install and tsc on the server.

Cause

On the Windows Consumption plan, the Node worker loads all of our code, about 2,000 modules, synchronously, one file at a time, from the app's Azure Files share. Nothing else can run until that finishes. Almost half of those modules are googleapis, which only subscriptions uses. Also, contentfulToCrowdin ran its whole Contentful→Crowdin sync at module load, on every instance start.

What the PR does

  • A GitHub Actions workflow builds, lints, tests, prunes and zips the app. It deploys the zip to the staging slot on every push to master; production gets it by a swap, as before, or by a manual deploy that needs approval. The app runs from that one zip. The Kudu deploy script is gone, and build-only packages are dev dependencies.
  • googleapis is loaded on first use, cutting what every instance loads at startup from 2,037 to 1,077 modules.
  • contentfulToCrowdin no longer runs its sync when the module loads. The daily timer waits for the whole sync, Crowdin uploads included, so a failed upload fails that run visibly.
  • Node 20 → 22, since Microsoft no longer supports Node 20 for Functions.
  • DEPLOYMENT.md describes how deployment works. RUN-FROM-PACKAGE-CUTOVER.md holds the one-time Azure and GitHub setup (portal steps, CLI alongside; deploys use each slot's publish profile) and the cut-over, to be deleted afterwards. The staging slot already runs this PR's build; production is unchanged.
