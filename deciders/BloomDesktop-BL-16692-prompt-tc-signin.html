How it behaves, and how that was checked

When Bloom opens a Team Collection and nobody is signed in, the collection tab asks the server whether to invite the user, and puts up the “Please sign in to Bloom” dialog if so. Clicking Sign in to BloomLibrary.org opens the login page in the browser exactly as the top-bar Sign in button always has; the dialog stays up and closes itself when the login comes back.

  • Verified live in the Deutsch Books Team Collection, signed out: the dialog appears on its own at startup, and no dialog appears at all once signed in.
  • You confirmed the full round trip yourself — you clicked Sign in, went through a couple of buttons in the browser, and the dialog closed and the avatar appeared. (Automated clicking couldn't complete the browser side; a synthetic run got the login page but no callback.)
  • The one-invitation-per-run rule was checked at the source: after the dialog had been shown, account/signInInvitationNeeded answers {"needed":false} — which is exactly what a rebuilt collection tab reads when you come back from the Edit or Publish tab.
  • Why the server has to remember it: App.tsx:36 renders the collection tab only while it is the active tab, so anything the front end remembered would be thrown away on a visit to Edit or Publish.

Session notes

  • The websocket approach the Forum nag uses does not work here. The first attempt pushed a LaunchDialog event from a startup action, like ShowForumInvitationDialogIfNeeded does. In a Team Collection the workspace page finished loading about 7 seconds after the startup actions ran (the collection sync goes first), the collectionButtonsDrawn milestone timed out, and the event was sent to nobody. Worth knowing: the Forum invitation has the same exposure on a slow-starting collection.
  • An installed Bloom Alpha had the same collection open for part of the session, which made every dev-build launch hang before its server started (the startup sync couldn't get the collection files) with nothing on stdout. Not a code problem, but it looks exactly like one.
  • While diagnosing that, six orphaned WebView2 processes were killed that turned out to belong to that Bloom Alpha, blanking its window. It had exited on its own by the time this was understood.
  • dotnet watch's hot-reload engine crashed once (a Roslyn edit-and-continue delta error) and took the dev stack down with it; a fresh launch was fine.

For your information

Three of Devin's observations we accepted rather than engineered around

None of these seemed worth added complexity, but you should know they exist:

Reloading the page while the dialog is up loses that run's invitation. The invitation is used up the moment the dialog appears, so if the workspace page reloaded right then, the user wouldn't be re-invited until the next time they start Bloom. They will already have seen the dialog, and a spontaneous reload doesn't really happen outside development.

A restored login is validated in the background. If someone's saved login has been revoked on the server, Bloom still counts them as signed in when it decides whether to invite them, so they wouldn't be invited that run. (Today the validation is a stub on master anyway.)

The once-per-run flag is a plain boolean touched from server threads. With one page ever asking, the worst imaginable outcome is one extra dialog, so no locking was added.

For your information

The Forum invitation may have the same lost-event problem

This feature originally used the same mechanism as the Forum invitation dialog: a startup action pushing a websocket event to the collection tab. That silently failed here because the page wasn't listening yet — in a Team Collection it finished loading about seven seconds after the startup actions ran.

Nothing was changed about the Forum dialog, but the same thing can presumably happen to it on any slow-starting collection: it would just never appear that run, with no error anywhere.
