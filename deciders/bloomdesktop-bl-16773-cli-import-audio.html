What this PR is about

Problem

Testing BL-16773 found that importing a spreadsheet with audio worked from inside Bloom but not from the command line (spreadsheetImport). The command printed nothing and left the book unchanged. The same round of testing found that a few bad command-line arguments crashed with a raw stack trace instead of saying what was wrong: a spreadsheet path that doesn't exist, and sendFontAnalytics given the book's .htm file, or a stray word, where it wants the book's folder.

Cause

To import audio, Bloom splits the text into sentences and checksums each recording with a hidden browser, which loads a helper page from Bloom's local web server. The app always has that server running; the console verb never started one, so the page address was http://localhost:0/…, the page never loaded, and the importer waited forever. Imports without audio never need the browser, which is why they worked. The argument crashes are older than BL-16767/BL-16773; nothing checked the paths before using them.

What the PR does

  • spreadsheetImport starts a local server for the duration of the import.
  • If the helper page never loads, the import fails after 20 s with an error naming the URL instead of hanging, and the helper browser is always cleaned up.
  • spreadsheetImport checks that the book and spreadsheet exist, runs the same validation as the in-app import, and backs up the book only after that. It prints the importer's progress, warnings and errors, which were previously all discarded.
  • sendFontAnalytics accepts the book's .htm file as meaning its folder, and reports a missing book folder or collection file in one line, with a new exit code 4.
  • A new test runs the real spreadsheetImport command in the console message loop with a real browser and mp3. It hung before the fix.

Should the command report failure when audio didn't import?

When a recording named in the spreadsheet is missing or isn't a valid mp3, the command-line import now prints an "Error: Did not import audio on page …" line, but it still saves the book and exits with code 0, meaning success. A script running the import can't tell that some audio was skipped without reading the output. The import inside Bloom behaves the same way: it reports the problem and keeps going. Before this PR the command also exited 0, and printed nothing at all. Devin flagged this (thread). Nothing in our repos checks this command's exit code.

Decision

Should the command-line import clear old recordings first?

The import inside Bloom deletes the book's audio folder before importing, so the book ends up with exactly the recordings the spreadsheet names. The command-line import never did. Importing into a book that already has recordings leaves the old mp3 files sitting in the folder, unused by any text box. Readers don't hear them, but they make the book folder bigger. Matching the in-app import would delete recordings the spreadsheet doesn't mention. The book is backed up first, as it is in the app. Devin flagged this (thread). This is older than this PR.
