What this PR is about

Problem

Testing BL-16773 found that importing a spreadsheet with audio worked from inside Bloom but not from the command line (spreadsheetImport). The command printed nothing and left the book unchanged. The same round of testing found that a few bad command-line arguments crashed with a raw stack trace instead of saying what was wrong: a spreadsheet path that doesn't exist, and sendFontAnalytics given the book's .htm file, or a stray word, where it wants the book's folder.

Cause

To import audio, Bloom splits the text into sentences and checksums each recording with a hidden browser, which loads a helper page from Bloom's local web server. The app always has that server running; the console verb never started one, so the page address was http://localhost:0/…, the page never loaded, and the importer waited forever. Imports without audio never need the browser, which is why they worked. The argument crashes are older than BL-16767/BL-16773; nothing checked the paths before using them.

What the PR does

  • spreadsheetImport starts a local server for the duration of the import.
  • If the helper page never loads, the import fails after 20 s with an error naming the URL instead of hanging, and the helper browser is always cleaned up.
  • spreadsheetImport now does what the in-app import does before importing: it checks that the book and spreadsheet exist, runs the same validation, then backs up the book and clears its audio folder (shared code), so the book ends up with exactly the spreadsheet's recordings. It prints the importer's progress, warnings and errors, which were previously all discarded.
  • If the import finishes but reported an error (such as a missing recording), the book is still saved but the command prints "done, with errors" and exits with a new code 2. Warnings alone still exit 0.
  • sendFontAnalytics accepts the book's .htm file as meaning its folder, and reports a missing book folder or collection file in one line, with a new exit code 4.
  • New tests run the real spreadsheetImport command in the console message loop with a real browser and mp3, covering the audio import (which hung before the fix), clearing old recordings, and exit code 2.

Worth knowing

  • A successful sendFontAnalytics run was not tried, because it sends real analytics. Only the argument checks in front of it changed.
  • The QA notes on the card are in the "Round 2" comment, which now covers exit code 2 and replacing the recordings. The earlier test-ideas comment, which the tester already worked, is kept as the record.
  • If the spreadsheet sits inside the book's own folder, its ./audio recordings are the book's audio folder, so clearing that folder deletes them before they are read and the import reports them missing. The in-app import has always done the same, and the backup keeps them.

Should a failed import put the book's old recordings back?

Both imports, the one inside Bloom and now the command line, back up the book and then delete its audio folder before the steps that can fail: starting the local server, loading the helper page (the 20-second timeout), and the import itself. If one of those fails, the book's text is left unchanged, but its recordings are already gone. The book then can't play its audio until someone restores it from the backup, a .bloomSource under %TEMP%\bloom pre-import backups whose path the import prints. The in-app import has always behaved this way; Devin flagged it on the command line (thread). A failure at that point is rare: the import reports most problems, such as a missing recording, and carries on rather than failing.
