What this PR is about

Problem

A table dragged onto a canvas page puts one bloom-canvas inside another: each picture cell holds a full bloom-canvas of its own. The table support on master (BL-16818) refits cell pictures after the table lays itself out. But the edit view found "the" background image of a bloom-canvas by taking the first one anywhere inside it, and for the outer canvas that can be a cell's picture. A resize of the outer canvas could size the cell's picture to the outer canvas. Converting an outer canvas's old-style picture could write that picture into the cell, which then saves the wrong image. When the outer canvas had no picture element of its own, its hover buttons, Change Image, tooltip, paste and the Motion tool could act on a cell's picture. Separately, a hidden bloom-canvas with a border reports a negative size, which got past master's zero-size guard.

What the PR does

  • Every lookup of a bloom-canvas's own background image in the edit view now goes through one function, getBackgroundCanvasElementFromBloomCanvas in bloomImages.ts: the first background image whose nearest bloom-canvas is the one asked about. It still works while the Image Description tool wraps the picture.
  • Fitting is skipped when the canvas's width or height is zero or less.
  • refitBackgroundImage returns a promise that settles once the picture is fitted.
  • Unit tests cover the size guard, the scoped lookup, a resize with a nested canvas, the legacy conversion with a nested canvas first, and the picture helper on an outer canvas with no picture of its own. The nested tests fail without the fix.

The PR targets master on purpose, because the table feature it tightens is on master only.
