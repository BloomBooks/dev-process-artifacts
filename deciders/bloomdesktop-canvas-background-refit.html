What this PR is about

Problem

A table dragged onto a canvas page puts one bloom-canvas inside another: each picture cell holds a bloom-canvas of its own. Several parts of the canvas code found a bloom-canvas's background image by taking the first one anywhere inside it. On a real page that is always the right one: every bloom-canvas gets its own background element when the page loads, ahead of anything else in it, including a table. But if an outer canvas ever lacked one (so far only in hand-built HTML), resizing, converting an old-style picture, refitBackgroundImage and the picture tools (hover buttons, Change Image, tooltip, paste, Motion) would act on a cell's picture instead.

Separately, a hidden bloom-canvas with a border reports a negative size, which gets past master's zero-size guard, so Bloom writes nonsense geometry for its picture.

What the PR does

  • Every lookup of a bloom-canvas's own background image goes through getBackgroundCanvasElementFromBloomCanvas, which returns the first background image whose nearest bloom-canvas is the one asked about and stops there. On a real page it costs about what the old lookup did; the check is a safeguard. It still works while the Image Description tool wraps the picture.
  • Converting an old-style picture updates the image inside the background element it just found or made.
  • Fitting skips a bloom-canvas whose width or height is zero or less, and waits for a later refit.
  • refitBackgroundImage returns a promise that settles once the picture is fitted.
