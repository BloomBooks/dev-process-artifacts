What this PR is about

Problem

A table dragged onto a canvas page puts one bloom-canvas inside another: each picture cell holds a full bloom-canvas of its own. The table support on master (BL-16818) refits cell pictures after the table lays itself out. But parts of the canvas code still find "the" background image of a bloom-canvas by taking the first one anywhere inside it, and for the outer canvas that can be a cell's picture. A resize of the outer canvas could size the cell's picture to the outer canvas. Converting an outer canvas's old-style picture could write that picture into the cell, which then shows and saves the wrong image. Separately, a hidden bloom-canvas with a border reports a negative size, which got past master's zero-size guard.

What the PR does

  • Every place in the canvas code that looks up a bloom-canvas's own background image now uses one function, getBackgroundCanvasElement: the first background image whose nearest bloom-canvas is the one asked about. That covers page-load setup, the resize path, the legacy-picture conversion and refitBackgroundImage. It still works while the Image Description tool wraps the picture.
  • Fitting is skipped when the canvas's width or height is zero or less.
  • refitBackgroundImage returns a promise that settles once the picture is fitted.
  • Unit tests cover the size guard, the scoped lookup, a resize with a nested canvas, and the legacy conversion with a nested canvas first. The nested tests fail without the fix.

The PR targets master on purpose, because the table feature it tightens is on master only.

Scope the remaining background-image lookups in bloomImages.ts?

This PR fixed the canvas code, but getBackgroundCanvasElementFromBloomCanvas and getBackgroundImageFromBloomCanvas in bloomImages.ts still take the first background image anywhere inside a bloom-canvas. They are used for the hover buttons and the Change Image button on a picture, the picture tooltip, pasting over the picture on a standard-layout page, and the Motion tool.

For an outer canvas that has its own background element, they return the right picture, because that element comes before any table. They go wrong only when the outer canvas has no background element of its own, such as an old-style picture not yet converted: then they return a table cell's picture instead of nothing, so for example Change Image on the outer canvas would act on the cell's picture.

Run the table e2e spec once against this branch?

src/BloomE2E/tests/tables-core.spec.ts drags a table onto a canvas page, puts a picture in a cell and checks that it stays inside the cell. That is the nested case this PR changes, in the real Bloom. Unit tests cover the logic, but nothing has exercised it in a running Bloom yet.
