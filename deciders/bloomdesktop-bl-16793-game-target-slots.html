What this PR is about

Problem

On a Bloom Games page, choosing a picture in the AI image editor and clicking Use this image could put it on one of the drag targets instead of the picture the author had selected. The selected picture was left unchanged, a target ended up showing a picture that did not belong to it, and reloading the page lost the new picture altogether — Bloom rebuilds a target’s content from its draggable, so the edit was thrown away. Reported against 6.5.3045 on page 15 of “Butterfly gardens”.

Cause

The editor identifies a slot by its position — "{pageId}:{ordinal}", an index into the page’s image containers in document order. C# builds that list from the saved HTML; the browser builds it from the live DOM. Both counted the copy of a draggable’s picture that sits inside a game target.

That copy is generated, not authored: the browser writes it in when the draggable is selected or its picture changes, and an untouched target sits empty. So one page can honestly hold a different number of image containers in the two places — on the reported page, 7 live against 10 saved. The index then meant one slot on one side and a different one on the other.

What the PR does

Both sides now leave the target copies out of the numbering, so an index counts only what an author placed and means the same thing whatever state the targets are in.

  • C# — SelectImageSlotsOnPage drops anything inside a data-target-of. The raw selector it used to be lives on as SelectImageContainersWithin, which is still what pairs a draggable’s containers with its target’s copies.
  • Browser — imageSlotsOnPage drops the same containers, through a constant it now shares with the code that records each slot’s share of its page.
  • Tests on both sides pin the invariant: a game page numbers its slots identically whether its targets are filled or empty, and a replacement lands on the author’s picture, not a target’s copy.

Verified against a running Bloom on the reported book: page 15 now numbers its slots the same with the targets filled (10 raw containers) and emptied (7), matching the ids C# sends at launch.

Worth knowing

  • Nothing in a book stores an ordinal, so renumbering is safe for existing books: the ids live only inside one editor session, and the per-slot size hint is written on the element rather than by index.
  • The AI image editor remembers its own last-selected picture between sessions, and it wins over the slot Bloom names at launch — observed while diagnosing this. Because ordinals on Games pages now mean something different, the first launch on a previously-edited book can open with a different picture loaded. It is in the tester notes; whether the editor should honour Bloom’s choice is a question for bloom-ai-image-tools, not this PR.
  • The fix was checked by hand, not only by tests, against the exact book and page from the report, in both target states.
