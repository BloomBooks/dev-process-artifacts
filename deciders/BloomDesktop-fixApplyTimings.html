Every failure was the same OneTimeSetUp error: "In FindBookHtmlInFolder('…\Temp\FixSizeOfImagesInFolder_Metadata'), the folder does not exist."

The chain: my test called BookSelection.SelectBook(...), which does more than its name suggests — it writes the book's folder into Settings.Default.CurrentBookPath and saves it, so the value outlives the test. Meanwhile SpreadsheetImporter.GetPageForLabel treats Path.GetDirectoryName(bookFolder) as a source collection. For a book in a temp folder that is %TEMP% itself, so Bloom enumerates every subfolder of the temp directory as a candidate book and calls FindBookHtmlInFolder on each. Any that vanishes between enumeration and inspection throws — and this machine has ~25,000 entries in %TEMP%, so that window is wide.

The fix is a mocked BookSelection (CurrentSelection was already virtual), which is all GetAeneasTimings needs and touches no global state. Applied to both new tests — the first had the same flaw and was getting away with it — with a comment recording why, so it doesn't come back.

1. Tests can silently corrupt each other through saved settings

The 47-test breakage happened because BookSelection.SelectBook() does something its name doesn't advertise: as well as recording the selection in memory, it writes the book's folder into Settings.Default.CurrentBookPath and calls Save(). A unit test that selects a book therefore leaves persisted state behind for everything that runs after it.

My tests are fixed, but the trap is still there for the next person, and SelectBook is called from plenty of tests. This is a question about whether to do anything beyond this PR.

2. The spreadsheet tests treat your whole temp folder as a Bloom collection

This is the other half of the same failure, and it is the more alarming half. SpreadsheetImporter looks for page templates in "the collection the book is in", computed as the book folder's parent. In these tests the book lives in a temp folder, so the parent is %TEMP% itself — and Bloom then walks every subfolder of your temp directory treating each as a candidate book. On this machine that is roughly 25,000 folders, several of which appear and disappear while the suite runs, and any that vanishes mid-walk throws and takes out the whole fixture.

So those tests can go red because of something entirely unrelated — another test, or any program on your machine that happens to use a temp folder at the wrong moment. That is worth knowing whether or not anyone fixes it, because it will show up again as an unexplained CI failure.

3. FYI — two bits of local tooling misbehaved

Neither affects the code, but both cost time and will cost it again. The chrome-devtools CLI cannot start its own daemon on this machine (chrome-devtools start fails trying to connect to a pipe that was never created), so the documented way to read Devin is broken.
