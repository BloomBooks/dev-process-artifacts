The fix, in one paragraph

GetAeneasTimings serves both Use Aeneas to guess timings and Apply timings file…. It already skipped the Aeneas dependency check for the manual path, but immediately afterwards it still ran espeak -v <lang> -q "hello world" to pick a TTS voice — so on any machine without eSpeak it reported an error and applied nothing. That language code only ever mattered for Aeneas' synthesizer, so it is now computed only on the Aeneas path.

  • eSpeak probe gated on !usingManualTimings — AudioSegmentationApi.cs:431. langCode then stays the requested code, so the orthography-conversion branch falls through naturally.
  • The text-fragments file only Aeneas reads is now written only on that path — AudioSegmentationApi.cs:514.
  • New test asserting this path runs no external command at all — AudioSegmentationApiTests.cs:282. Verified as a real guard: with the fix reverted it fails with the exact reported error. Required making DoesCommandCauseError virtual.

1. Network-share collections still can't apply a timings file

Separately from the eSpeak problem, GetAeneasTimings begins by refusing to do anything at all if the collection's folder path starts with \\ — that is, if the collection lives on a network share rather than under a drive letter. The user gets "Sorry, Bloom cannot split timings if the collection's path does not start with a drive letter." That restriction exists because Python and Aeneas cannot cope with such paths (it came in with BL-9959).

It is the same shape of bug this PR just fixed: a limitation of the forced-alignment tooling being applied to a path that never touches that tooling. After this PR, a user working off a network share still cannot use Apply timings file…, even though reading numbers out of a text file has no such limitation. Nobody has reported it, and it produces a clear message rather than the error dialog from the card.

See AudioSegmentationApi.cs:372.

2. FYI — the manual path still deletes a file it no longer writes

Devin raised this as an informational item. Bloom writes a temporary file listing the sentences (<name>_fragments.txt) for Aeneas to read, and deletes it afterwards. This PR stopped writing that file on the apply-a-timings-file path, but the cleanup line that deletes it still runs on both paths.

Deleting a file that isn't there does nothing and cannot throw here, so there is no bug. The only real effect is a mild oddity: if an earlier Aeneas run crashed and left a stale fragments file behind, applying a timings file would now tidy it up as a side effect — which is arguably a small favour rather than a problem. It is only worth touching for readability, which is why leaving it is recommended. See AudioSegmentationApi.cs:541.
