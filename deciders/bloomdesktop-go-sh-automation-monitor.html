Who obeys BLOOM_AUTOMATION_MONITOR

BloomDesktop, D:\add-e2e-test-skill, branch BL-16804-headless (draft PR 8285). Written 2026-09-03. Found by reading the code, not by running it.

The situation

The environment variable BLOOM_AUTOMATION_MONITOR was added so an automated test run could put its Bloom window somewhere other than the middle of the developer's desktop. It takes a monitor number counted left to right, or headless (or 0), which puts every window far outside every monitor and out of the task bar.

It also applies to the Bloom the developer starts themselves. The variable is honoured by any Bloom started with the --automation flag, and ./go.sh passes that flag. The chain is go.sh → src/BloomBrowserUI/scripts/go.mjs → scripts/watchBloomExe.mjs, which puts --automation in the argument list at line 140. The launcher does not clear the variable, and a child process inherits its parent's environment, so the value in the developer's shell reaches Bloom.

What the developer would see

  • With a monitor number set, their own Bloom opens on that monitor, maximized. Easy to miss, or to blame on Windows having moved a window.
  • With headless or 0 set, their own Bloom opens off every monitor and not in the task bar. It looks exactly like Bloom failing to start: the launcher reports success, the HTTP server answers, and there is no window anywhere.

Why this was missed

The class comment in src/BloomExe/AutomationWindowPlacement.cs:16 states the opposite, in as many words: "A developer who leaves it set in their shell therefore still gets an ordinary, visible Bloom when they start one themselves; only a run that already declared itself automation obeys it." The second half is true. The first half assumed that a developer's own Bloom is not an --automation run, and it is one.

Whichever option is chosen below, that comment gets corrected to match. That is not one of the questions.

There is already a flag that separates the two

Three places pass --automation, and the two test suites pass a second flag, --e2e, that the launcher does not:

Program.RunningE2eTests is the property behind --e2e. So the distinction the variable needs already exists in the code; nothing new has to be invented to draw it.

The second half: what an agent is told

The bloom-automation skill is what an AI reads when it attaches to a running Bloom to debug or check something ad hoc. .github/skills/bloom-automation/ contains no mention of BLOOM_AUTOMATION_MONITOR, of headless, or of a monitor.

The variable is documented in three places, none of which that agent reads: .github/skills/add-e2e-test/SKILL.md, src/BloomE2E/README.md, and .github/workflows/nightly.yml.

So an agent that finds no Bloom window, or a screenshot that does not look like the monitor it expected, has nothing telling it to suspect this variable or to read the line Bloom writes to %TEMP%\SIL\Bloom\Log.txt on every automation start. That line names the value, the monitor chosen, and every monitor the process can see.

1. Which runs should obey the variable

The choice is whether a developer's own Bloom is a thing this variable is allowed to move, and if so how far.

2. What the bloom-automation skill says about it

This one stands whatever the answer above is. Even with the variable confined to test runs, an agent can still meet an off-screen Bloom: it may be asked to run the suite, or to look at a Bloom a test run started.

3. Where the change goes

PR 8285 (BL-16804-headless) is a draft that introduced this variable's current behaviour, so it can absorb a correction to it. It has three decisions of its own waiting, and its own report at bloomdesktop-BL-16804-headless.html.
