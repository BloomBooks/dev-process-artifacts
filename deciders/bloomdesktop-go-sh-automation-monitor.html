Who obeys BLOOM_AUTOMATION_MONITOR

BloomDesktop, D:\add-e2e-test-skill, branch BL-16804-headless (draft PR 8285). Written 2026-09-03, and rewritten the same day: an earlier version of this page recommended confining the variable to end-to-end test runs. That was wrong. The variable already does what it is wanted for, and the questions below are the ones that are actually open.

What the variable does today

Every Bloom started with the --automation flag obeys BLOOM_AUTOMATION_MONITOR. Set it to a monitor number, counted left to right, and every window that run opens goes on that monitor. Set it to headless (or 0) and every window goes far outside every monitor, and out of the task bar too.

Three things pass --automation, and that includes the launcher. So a Bloom an agent starts to look at something, a Bloom the developer starts to watch their changes live, and a Bloom a test suite starts are all moved by this variable.

This is the wanted behaviour: agent work goes on a side monitor and stays out of the way, and the variable's name says exactly that. Nothing in the questions below proposes taking it away.

Two things are wrong, and neither is the behaviour

  • The code says the opposite of what it does. The class comment at src/BloomExe/AutomationWindowPlacement.cs:16 reads: "A developer who leaves it set in their shell therefore still gets an ordinary, visible Bloom when they start one themselves; only a run that already declared itself automation obeys it." The second half is true. The first half is false, because ./go.sh is an --automation run. This gets corrected whichever way the questions below are answered, so it is not one of them.
  • The one hazard is headless, not a monitor number. A monitor number moves a window somewhere the developer can look. headless and 0 make it invisible and keep it out of the task bar, so a ./go.sh the developer runs themselves, in a shell where that value is set, looks exactly like Bloom having failed to start: the launcher reports success, the HTTP server answers, and no window exists anywhere. Question 1 is about that case alone.

What an agent is told about it

The bloom-automation skill is what an AI reads when it drives a running Bloom. .github/skills/bloom-automation/ contains no mention of BLOOM_AUTOMATION_MONITOR, of headless, or of a monitor. The variable is documented in .github/skills/add-e2e-test/SKILL.md, src/BloomE2E/README.md and .github/workflows/nightly.yml, and an agent doing ad-hoc work reads none of those.

Two costs follow. An agent that finds no window may report that Bloom failed to start. And an agent that has not been told the variable is deliberate may clear or override it to get a window it can see, which puts Bloom back in the developer's face. Question 2 is about that.

Bloom already writes one line to %TEMP%\SIL\Bloom\Log.txt on every automation start, naming the value it read, the monitor it chose, and every monitor the process can see. Nothing points an agent at it.

Telling your Bloom from an agent's

Question 1 needs a way to know who ran ./go.sh, so here is what is available. An agent's shell carries CLAUDECODE=1 in its environment, along with several other CLAUDE_CODE_* variables; a terminal the developer opens themselves carries none of them. So the signal exists and is free to read.

The cost is that it ties Bloom's launcher to one particular agent tool by name. If that tool changes the variable, or another agent is used, the launcher quietly reverts to treating every run the same way. That failure is silent, which is the argument against leaning on it.

1. When you run ./go.sh yourself and headless is set

A monitor number is not in question: your own Bloom going to a side monitor is fine, and arguably what you want anyway. This is only about the invisible case, where the value in your shell is headless or 0 and the Bloom you started to look at something never appears.

Leave as is is the recommendation here, and it is pre-selected. You set the value, so you are the one person who can tell why a window is missing, and the log line names it. Both alternatives buy a small convenience with a rule the code has to carry forever, and the second one makes Bloom's launcher name an agent tool. Take one only if you expect to leave headless set in your own shell as a habit.

2. What the bloom-automation skill says about it

This is the question that most directly serves keeping agent work out of your face: an agent that does not know the variable is deliberate is an agent that may work around it.

3. Where the change goes

PR 8285 (BL-16804-headless) is a draft that introduced this variable's current behaviour, so it can carry a correction to it. It has three decisions of its own waiting, in its own report at bloomdesktop-BL-16804-headless.html.
