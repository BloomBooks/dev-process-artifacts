Preflight report · 29 July 2026

Stop BloomBridge from provoking “Cannot Find API Endpoint” on an older Bloom

BloomBridge asks a running Bloom questions that only Bloom 6.5 and later understand. An older Bloom answers 404, and its way of saying “I don’t recognise that” is to show its user a warning — so an ordinary discovery scan alarmed people who had done nothing wrong, and the conversion failed anyway. This branch makes BloomBridge determine the version first, by asking Windows, and refuse to knock — telling the user plainly to update instead.

How this was verified beyond the tests

  • The bug was reproduced first. An installed Bloom 6.3.2.0, asked once for api/common/instanceInfo, returned 404 and logged NonFatalProblem: Cannot Find API Endpoint via ReportMissingApiEndpoint — the exact Sentry message, from one ordinary request.
  • The gate was verified live against that same Bloom. It identified port 8093 → Bloom.exe 6.3.2.0, excluded it, produced the user-facing message — and Bloom’s log gained no new warning, which is the whole point.
  • The endpoint-age claims were checked, not assumed. Both ungated endpoints (common/reloadCollection, external/bringToFront) are registered in origin/Version6.3, so leaving them ungated cannot produce a 404 on the oldest release that matters.
  • A note on netstat: it cannot do this job. Bloom’s server is an HttpListener, so the socket belongs to HTTP.SYS in the kernel and the port is attributed to the System process. netsh http show servicestate is what exposes the real owner, unelevated.

Your call

Should a Bloom 6.4 still be usable for the things that only need discovery?

The gate uses a single minimum of Bloom 6.5, because that is the version where the endpoints BloomBridge needs in order to do anything (add a book, update one, process one, ask about collection languages) all exist. But one endpoint it uses merely to find a running Bloom and learn which collection is open — common/instanceInfo — arrived earlier, in Bloom 6.4.

So there are places that used to work against a 6.4 Bloom and now do not: the “Bloom is running” indicator in BloomBridge’s top bar goes dark, the cleanup screen stops noticing which collection is open, and the two spots that just need a writable collection folder lose that hint. Nothing a 6.4 user could actually convert is affected — they could never do that anyway — but a 6.4 user does see slightly less than before. Devin raised this and asked for a human to confirm the trade; its thread is open.

Notes

FYI — the localized-Windows residual

No action needed unless you disagree. The parser now reads netsh output by shape rather than by its English words, so it works on a translated Windows. One piece is still English-only: the “Request queue name:” header used to tell one block of output from the next. On a localized Windows that reset may not fire, so in principle a port could be credited to the wrong program. The consequence is bounded — the owner must still be named Bloom*.exe, and a version we cannot read fails open to exactly the behaviour that existed before this gate. I judged that not worth more machinery; the alternative is dropping netsh in favour of enumerating Bloom processes, which loses the port mapping.
