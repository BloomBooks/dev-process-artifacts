What the change does

Bloom kept two records of “we are in the Publish tab”, written at different moments. The authoritative one is WorkspaceTabSelection.ActiveTab, assigned in WorkspaceView.cs:1457. The other was the static PublishHelper.InPublishTab, which the book-staging code actually checks, maintained separately by PublishView.Activate()/Deactivate() — always later, after ActiveTab had already changed and after however many other event subscribers had run.

The log on the card shows them disagreeing at the moment of failure: the guard in PublishApi.cs:621 (abort if ActiveTab != publish) let the request through, so ActiveTab said “publish”; the guard at PublishHelper.cs:40 fired, so the flag still said “not publish”.

The second symptom falls out of the same cause: PublishView.Activate() is also what calls SetTabsEnabled(true) (PublishView.cs:108), the safety net that releases the Edit tab’s save lock. A skipped activation loses that too — hence the greyed-out tabs.

  • One owner. ActiveTab is now a property whose setter also sets the static mirror (WorkspaceTabSelection.cs:47). One assignment, no window. It also clears the flag when a new collection initialises to the Collection tab (WorkspaceView.cs:192) — the static previously survived a collection switch.
  • No second writer. PublishView no longer touches the flag; comments at both former sites point at the new owner.
  • A latch that can’t go stale. _isActive is set before Activate()/Deactivate() rather than after (PublishView.cs:64), so a throw inside either can’t leave us believing we’re still where we just left. Exceptions still propagate; nothing is swallowed.

Decision

Should the static flag exist at all?

The fix removed the disagreement between the two records of “which tab are we on”, but it did not remove the duplication. There is still a static bool that mirrors ActiveTab, and it is now written by the ActiveTab setter — which means Bloom.Workspace, previously an inert data holder, now has a compile-time dependency on Bloom.Publish and a side effect on process-wide state whenever anyone constructs one.

Devin’s suggestion is to point the dependency the other way instead: make PublishHelper.InPublishTab a read-only property that consults a registered WorkspaceTabSelection. There would then be exactly one piece of state, read at the moment the guard runs, and Bloom.Workspace would go back to knowing nothing about publishing. The mirror only exists because the staging code is static and has no way to reach the one WorkspaceTabSelection, so this trades the mirror for a static registration point instead.

Should the static flag exist at all?

Recommended because the bug on the card is fixed and provably so, the coupling is one line inside one small file with a comment explaining exactly why it’s there, and the alternative moves work into application startup — a riskier place — for a design win rather than a behavioural one. That’s a fine follow-up card, but a poor thing to fold into a fix you want to ship.

For your information

A second behaviour change I didn’t call out

Moving _isActive = shouldBeActive ahead of the work fixes the case I described: if deactivating throws, we no longer skip the next activation and strand the tabs greyed out. Devin pointed out it also changes the mirror-image case, which my commit message didn’t mention.

If Activate() throws part-way, the view now counts as active, so the next tab switch will run Deactivate() against a publish view that never finished activating — cancelling any PDF/ePUB/video work and broadcasting switchOutOfPublishTab. Every one of those calls is null-safe or idempotent (_model.IsMakingPdf is checked first, the API calls are null-conditional, PublishHelper.Cancel() just clears a reference), so it is harmless — and better than the old behaviour, which skipped the cleanup entirely. But it is a real second change, and you should know it’s there rather than find it later.

A second behaviour change I didn’t call out

Recommended because the comment already sitting above that line explains the reasoning, and the new behaviour is the one you’d want anyway — cleanup that runs is better than cleanup that’s skipped. Worth a tick on “Leave comment” if you’d rather it were spelled out in the source.

For your information

One path still sets the flag only indirectly

Opening a different collection goes through WorkspaceView.OpenSpecificCollection, which raises the tab-changed events with no destination tab and never assigns ActiveTab. So during the tear-down and rebuild, the static keeps whatever it had; what actually resets it is the new WorkspaceView constructor assigning ActiveTab = collection.

That is a genuine improvement on before — previously nothing reset it at all across a collection switch — and a leftover value can only be true, which is the permissive direction: it would allow a staging call, never refuse one, so it cannot produce the crash on this card. The catch is that the invariant now quietly depends on that one line in the constructor continuing to exist. The new test stands in for it and its comment says so explicitly, which is the cheapest guard available short of adding code.

One path still sets the flag only indirectly

Recommended because the whole point of the fix is that exactly one place writes this. A second writer to cover a stale value that can’t cause the failure would trade the invariant for reassurance, and the test comment already documents the dependency.

One red test I couldn’t clear from here

The last full run of the C# suite came back with one failure: RabRealBuildTests.SetupAndBuildAsync_RealReadingAppBuilderBuild_CreatesValidApk, the opt-in test that drives a genuine Reading App Builder + Gradle build all the way to a signed Android APK. It is excluded from CI and only runs when BLOOM_RUN_RAB_MANUAL_TESTS is set, which it is on this machine.

I do not believe this branch caused it. The same test passed in both earlier full runs on this branch, at 49eaf0f0 and 2ce2afc3 — commits that already contain the whole production change. The only difference in the failing run is five lines of comment in PublishApi.cs. Nothing in the diff is under src/BloomExe/Publish/Rab/, and the RAB path reaches the tab-state guard only under Program.RunningUnitTests, where it is bypassed entirely.

What the two failures actually say is that the shared build tree is wedged. The first complained that classes2.dex was “being used by another process”; the re-run then failed differently, on missing intermediates (values-ro.json, AndroidManifest.xml) and Gradle refusing to read its own outputs — the wreckage a build killed mid-flight leaves behind. Reading App Builder puts all of this in C:\temp\SIL\build\RAB.000, which is machine-global: it is shared by every worktree on this machine, and gradle clean is itself one of the steps that now fails.

Clearing that directory would very likely fix it, but it is outside the repo and shared — another worktree (there is a BL-16190-rab-prepare-taglib branch) could be part-way through its own RAB work — so I left it alone rather than delete it on my own initiative.

You have already ruled on this test once, during the BL-14901 preflight: known local-environment failure, leave as is. So this needs nothing from you unless you want it to. The one genuinely new fact is that it is now intermittent rather than consistently broken — it passed twice on this branch today before failing — and the tail of the first re-run still shows the old “The batch file cannot be found” symptom, so the local Reading App Builder install looks partially, not wholly, repaired.
