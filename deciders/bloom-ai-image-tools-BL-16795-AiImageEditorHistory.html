Use an image from History in the slot being worked on (BL-16795)

“Use this Image” used to route by the slot id stored on whichever record the Result pane happened to be showing — which says which slot that image was made for. A picture picked out of History carries whatever page it was saved against in an earlier session, so the button either never appeared (nothing stored, leaving only “Cancel” in that corner of the pane) or committed the picture to a different page of the book.

The workspace now decides the destination (ImageToolsWorkspace.tsx:4149): a run’s result still goes to the slot that run was for; a book image, or something assigned during this session, goes to its own slot; anything the user picked out of a strip goes where they are working — the picture in “Image to Edit”, or the placeholder the editor was opened on. The Result pane is simply told whether the action is available (Workspace.tsx:271), and a history-folder picture now commits by its history id rather than by URL (BloomHostedImageEditor.tsx:139).

Two new harness tests (no stored slot, another page’s stored slot) both fail on the pre-fix code — verified by stashing the component changes and re-running — and pass now. The commit also carries a changeset for the release notes, and the tracker declaration you approved at the start of the run.

Decision

A related route can still send a picture to the wrong page

This run fixed the case in the bug report: pick a picture out of History, press “Use this Image”, and it now lands on the page you are working on. One neighbouring route still behaves the old way. It was raised in the local review and then found independently by Devin, whose thread on the PR is left open waiting for this decision.

Here is what the user would do. Bloom opens the editor on page 3. They drag an old picture out of History into “Image to Edit” — one that was originally made for page 1 — and then pick another History picture in the Result pane. “Use this Image” replaces page 1; page 3, the page on screen, is untouched. It happens because the fallback asks the picture being edited which page it belongs to, and a History picture answers with the page it was made for. Running a tool on that same target is a second way in: the new picture inherits the remembered page too, so committing the run’s own result also lands on page 1.

Asking the edited picture is not simply wrong — it is what makes a chain of edits work. Edit page 3’s picture, get a result, edit that result again, and the second result still belongs to page 3 because of this. The trouble is that a picture rebuilt from an earlier session’s history folder looks exactly like one made moments ago, so the same question gives a stale answer. Which is why this is your call rather than the bot gauntlet’s: closing it means deciding where a chained edit should land when the user has wandered away from the page they opened.

A published prop takes one more argument

This package is published to npm and Bloom consumes it. The fix needed the editor to tell its host which page a picture is going into, so onCommitCurrentResult — part of the published ImageToolsWorkspaceProps — now receives the page id as a second argument alongside the picture. Nothing breaks: TypeScript happily accepts an existing handler that ignores the extra argument, and the only handler that exists lives in this repository. You approved this shape when the plan was written; it is here so the change to a public interface is on the record rather than buried in the diff.
