What this PR is about

Problem

A user running Keyman on an ARM64 Windows PC with Bloom 6.6 Alpha got "Error checking for keyman" on almost every page change in the Edit tab. Because the check failed, Bloom also missed that Keyman was active, so the long-press accent popup stayed on.

Cause

The keyboarding/useLongpress endpoint runs its check on the UI thread with form.Invoke(Func<bool>). WinForms runs that kind of delegate through Delegate.DynamicInvoke. The stack trace shows the reflection stub (InvokeStub_Func`1) throwing InvalidCastException, and once NullReferenceException, before the check itself ever ran. The stub ended up running an unrelated DLR call site, which points to a .NET runtime problem with emitted code on ARM64 (the user had CLR 8.0.19), not to the Keyman check.

What the PR does

The endpoint now passes a MethodInvoker that sets a local, which WinForms calls directly, so this call no longer goes through the reflection stub (KeyboardingConfigApi.cs:25). This works around the problem at this one call site; it does not fix the runtime problem.

Decisions

1. Does this PR need an automated test?

The PR adds no test. The failure happened inside .NET's reflection stub on one ARM64 machine, and no test can make that stub misbehave. What a test could check is narrower: that the endpoint still answers "false" when an input processor is active and "true" when it is not. That would need a running WinForms form and a TSF input processor on the build machine, and InputProcessorDetectorTests already covers the detector itself.

2. Should we go deeper than this one call site?

The walkaround's altitude reviewer judged this change to be a sound workaround but not a root-cause fix. The reflection stub ran code belonging to a different compiled method, which looks like a .NET runtime problem with emitted code on ARM64. The user had .NET 8.0.19. Bloom uses the installed .NET runtime rather than shipping its own.

About nine other places send Func<T> or custom delegates through Control.Invoke. The busiest is ApiRequest.cs:357, which every UI-thread API call goes through. That path did not fail for this user, so the fault seems specific to the keyboarding call's stub. The reviewer also checked the COM declaration of GetActiveProfile and found it correct on both x64 and ARM64.
