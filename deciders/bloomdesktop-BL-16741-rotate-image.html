What this PR is about

Problem

A picture that arrives on its side stays on its side. Bloom could crop a picture and move it, but it could not turn it, mirror it, or set an item on the page at an angle. An author with a photograph the camera saved sideways had to leave Bloom, turn the file in another program, and put it back.

What the PR does

  • Rotate right on the picture menu turns a picture a quarter turn clockwise. An ordinary picture item turns as a box. A background image, which fills its page area and cannot turn as a box, has the picture inside it turned and its own box reshaped to match. The rule a turn follows is this: you get what you would have had if the picture had arrived already turned. So the whole picture ends upright, it fills the page area where the turned picture is that shape, and any crop you had made is kept at the same framing. A picture you had told to fill the page keeps filling it, with its ends cut off rather than blank bands.
  • Flip, with Flip horizontal and Flip vertical, mirrors the picture. The two axes are the ones the user sees, whichever way the picture and its box have been turned.
  • A rotation handle on the control frame, a knob on a short stem above the top edge, turns the selected item to any angle. The angle snaps to every multiple of 45 degrees within 14 degrees of one, and the CTRL key turns the snapping off. An item whose outline comicaljs draws (a speech bubble, a thought bubble, a caption, a rectangle or an ellipse) gets no handle, because that drawn outline stays upright.
  • Dragging, resizing and cropping work on a turned item: mouse movement is converted into the item's own coordinates, and the item is shifted so that the edge opposite the one being dragged stays where it looks. Clicking picks the right item too, which comicaljs alone cannot do, because it tests the un-turned box.
  • Cropping a picture the author has turned works, which it did not before. Every limit a crop drag obeys is now measured on the rectangle the element shows rather than on the picture's own box, which a turn of the picture leaves where it was. The mark that shows which side of a picture is cropped uses the same measurement, so it marks the two sides that are really hidden rather than all four.
  • Undo puts back a Rotate right, a Flip, and a drag of the rotation handle: one step for each command, and one step for each drag. A turn moves the picture's box as well as the picture, and Undo puts both back.
  • Reset Image now clears the crop, the turn and the mirror, and a transparency the user chose by hand, and puts the transparency back to Auto. It does not straighten a turned box, because that angle belongs to the box, as its size and its position do. The picture menu is now in three groups with a line between them: which picture is in the box, how it sits in the box, and the rest.

Every angle and mirror lives in the item's own inline transform, which is saved in the book HTML. It therefore appears in BloomPlayer and in PDF output, where no Bloom JavaScript runs.

What changed this run

Two commits, both of them your answers from the last report.

Cropping a turned picture is fixed. My description of that bug on the last report named the wrong cause. It said the drag moves the content at ninety degrees to the pointer. It does not: writing the picture's top moves a turned picture the same way it moves an upright one, because a CSS transform turns the box about its own centre. The defect was in the limits. Both crop drags measured the picture's own box, and on a turned picture that box and the rectangle the element shows disagree by half the difference of the picture's two dimensions. Dragging the picture about inside the crop therefore had its lower limit above its upper one, so every mouse move gave back the same position and the picture stood still, which is the symptom I reported. Dragging a crop handle stopped the edge at the wrong place, so part of the photograph could not be recovered, or a blank band could be dragged in past the end of it. Two exported functions now measure the rectangle the element shows and clamp in its frame, the four handle limits use them, and the crop marks share the arithmetic. For an upright or half-turned picture, every number is the number the old code produced.

Rotate right is off Ctrl+R. The shortcut goes back to right justify alone, and the command stays on the picture menu. The menu item shows no shortcut, and the translator note for it names none.

Worth knowing

  • No crop drag in this PR has been done by hand in a running Bloom. The one Bloom running on this machine belongs to another worktree, so it does not carry this code, and I did not start a second one. The fix rests on 13 unit tests over the two new functions and on the fact that an upright picture reduces to the old arithmetic exactly. A tester has to work the four side handles and the crop drag by hand, on a turned picture and on an un-turned one. The test ideas on the card say so, and say what the old broken behaviour looked like.
  • The crop change runs for every crop drag in Bloom, not only for a turned picture. That is the risk in it, and it is why the test ideas ask for the un-turned case as well.
  • The guard that binds the document key handlers once stays, though the command that exposed the fault is off the keyboard now. Binding one more copy of every one of those handlers for each canvas element added to the page is wrong on its own account.
  • Rotate right reaches the picture inside the box whenever the box itself cannot turn on the page. That is true of the page background, and also of an item whose outline comicaljs draws. For the second kind the box keeps the size the author gave it and turns about its own centre, rather than being fitted to the page. I could not confirm from the code that a picture ever sits in such a box, so this may be a path nothing reaches. It is written that way so that it is right if anything does. (setTurnedBackgroundLayout)

One question: how the crop drags get tried by hand

The crop change in this run touches every crop drag in Bloom, not only a drag on a turned picture. For an upright picture the arithmetic reduces to what the old code did, exactly, and 13 unit tests cover the new functions, so I am confident in it. It has still never been done with a pointer. Nothing in this PR has: the one Bloom running on this machine was started from another worktree, D:\bloom.worktrees\Add-Tables, so it does not carry this code.

Stopping that Bloom to start one from this worktree would take away a program you are using for other work, and your own review of the PR is the next step in any case. That is why the recommendation is to leave this to you, or to the tester: the test ideas on the card now name both broken behaviours, so whoever works the handles knows what they are looking for.
