What this PR is about

Problem

The Bloom AI image editor generated at whatever resolution the picture already had, so an image that arrived small came back small however much of the page it fills. Someone who wants a print-quality picture in a full-page slot had no way to say so, and nothing in Bloom told the editor what "big enough" meant for that slot.

What the PR does

Bloom now tells the AI image editor the pixel size each image slot in the book wants. The editor offers it as the Upscale tool's "Auto" size and uses it for every generation.

  • One place does the arithmetic. A new module answers "how big should an image be for this space". A paper page wants whatever fills the container at 300 DPI, which is the sum the image tooltip already did; the tooltip now calls that function instead of repeating it.
  • A screen-sized page is measured against the screen the book is published for. A device layout wants the slot's share of the book's own BloomPUB image limit, the Resolution setting in Book Settings. Asking for more only makes pixels the publish step throws away, and asking for less wastes a limit someone raised on purpose. The page is fitted inside the screen on both edges, so the two ebook layouts that are not 16 by 9 do not overshoot the short edge.
  • Slots on pages nobody has open. Only the page laid out in the browser can be measured, so each image container's share of its page is written into the HTML whenever a page is saved. That covers ordinary Edit-tab saves, every "Edit with AI" launch, and "Update Book", which visits every page.
  • A background image is measured against its canvas, not its container. A replacement committed from the editor is re-fitted to fill the whole canvas, while the container covers only as much of it as the current picture happens to reach, so measuring the container asked for the size of the old image's letterbox.
  • The cover's value survives bringing a book up to date. That rebuilds all front and back matter from the template, which used to throw the cover's share away; it now travels through the data-div and is restored.
  • Books that predate this get no guess. A page not saved since this change carries no share, and its slots simply offer no "Auto" size rather than a made-up one.
  • The tooltip stops giving print advice about screens. On a device layout it drops the print-DPI lines, which would mislead on a page nobody prints, and names the book's own screen numbers instead.

Known limitation, deliberately left as is

A share recorded under one page size or layout survives a change to either, so a page nobody reopens keeps the old value until it is next saved. A share is a proportion, so it only goes wrong where the new layout gives that slot a different proportion of its page, and the cost is a suggested size somewhat off rather than a broken picture. The reasoning sits next to recordFractionOfPageOnImageSlots. Whether to wait for BL-16852 instead is the first question on the right.

Decision 1

Should this wait for the auto-migrate work?

John Thomson left a comment on this PR saying a fix is in progress and asking whether it should be merged first, because "a lot of limitations and comments in this one could be removed". A comment on the YouTrack card makes the same point for testing: once Bloom fully updates all of a book's pages when you edit it, the "old book" and "page size changed" special cases stop mattering.

The work he means is BL-16852, "Auto-migrate books", which is In Progress. This PR currently carries real weight for those cases: a page that has not been saved since this change offers no automatic size at all, and a page whose layout changed keeps a stale share until something saves it. If books migrate themselves, both of those disappear along with the code and comments that explain them.

This is a sequencing and scope call, so it is yours rather than mine. Note that nothing here is wrong as it stands: the fallbacks are conservative, and the worst outcome is a suggested size that is somewhat off.

Decision 2

The PR is not a draft, and I left it that way

Preflight normally pulls a PR back to draft, on the grounds that work answering a review is pre-review again. I did not do that here.
