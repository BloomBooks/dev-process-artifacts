What this PR is about

Problem

The Bloom AI image editor generated at whatever resolution the picture already had, so an image that arrived small came back small however much of the page it fills. A user who wants a print-quality picture in a full-page slot had no way to say so, and nothing in Bloom told the editor what "big enough" meant for that slot.

What the PR does

Bloom now tells the AI image editor the pixel size each image slot in the book wants. The editor offers it as the Upscale tool's "Auto" size and uses it for every generation.

  • One place does the arithmetic. A new module answers "how big should an image be for this space". A paper page wants whatever fills the container at 300 DPI, which is the sum the image tooltip already did; the tooltip now calls this function instead of repeating it.
  • A screen-sized page is measured against a screen. A device layout wants the slot's share of a 1280 by 720 screen, the default image limit Bloom publishes BloomPUBs at. The page is fitted inside that screen on both edges, so the two ebook layouts that are not 16 by 9 do not overshoot the short edge.
  • Slots on pages nobody has open. Only the page laid out in the browser can be measured, so the front end writes each container's share of its page into the HTML whenever a page is saved: ordinary Edit-tab saves, every "Edit with AI" launch, and "Update Book", which visits every page.
  • The value reaches the editor. C# reads that attribute when it enumerates the book's images and passes it through; the overlay turns it back into a pixel target using the open page's measured size.
  • Books that predate this get no guess. A page not saved since this change carries no measurement, and its slots offer no "Auto" size rather than a made-up one.
  • The tooltip stops giving print advice about screens. On a device layout it drops the print-DPI lines and describes the screen target instead.

Questions for you

1. Measurements go stale when the book's page size changes

Bloom records each picture's share of its page as the page is saved, and reads that back later to work out what size the picture should be. If someone changes the book's page size, for example from A5 Portrait to Device16x9Portrait, the pages they do not reopen keep the share they had under the old page size. The AI image editor then multiplies that old share by the new page's dimensions, and by the new page's paper-or-screen rule, so it offers a size that is simply wrong until those pages are saved again.

The user sees a plausible-looking but incorrect "Auto" size, with nothing to tell them it is stale. Today the alternative to a wrong number is no number, which is the behaviour for a page that was never saved at all.

Notes

2. The tooltip and the editor measure two different boxes

The tooltip that appears when you hover a picture measures the picture's outer frame on the page. The recorder that writes the share into the book, and the C# code that reads it back, both work from the inner image container instead. For an ordinary picture those two are the same size, so the two numbers agree. For a picture that has been cropped or zoomed, they deliberately are not: the inner container is made larger than the frame, and the overflow is clipped. That is how cropping works.

So on a cropped picture the AI image editor can be told a larger size than the tooltip shows for the same picture, and the recorded share can even come out above one, meaning larger than the page. Both modules carry comments asserting the two can never disagree, which is not currently true. This matters more than usual here because the branch this is stacked on is specifically about sending the editor the cropped view.

Notes

3. Cover and title-page pictures may lose their measurement

When Bloom brings a book up to date it strips the front and back matter out and re-injects it from the current template, carrying only a short, fixed list of attributes across. The share this feature records is not on that list, so a measurement written onto a cover picture would be discarded the next time the book is updated, and the cover would then offer no automatic size until someone opens and saves the cover again.

This was reasoned from the code rather than observed, because nothing here has been run in a live Bloom yet. It may well be that the same update pass re-saves the pages afterwards and the value comes straight back.

Notes

For information: a two-pixel disagreement inside one tooltip

The tooltip's "the image container is W by H dots" line measures the frame one way and the new target line measures it another. The two only differ when the frame has a real border, which happens when the Image Description tool is switched on, and then only by a pixel or two. Nothing here is wrong for a user; it is listed so a reviewer who notices it knows it was seen.
