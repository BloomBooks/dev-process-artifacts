How this was verified

Worth recording because the measurements, not the code, were the hard part — and two of them are counter-intuitive enough to be “corrected” back out by a future reader. Both are written into BloomClipboard's comments.

  • Chromium never tells JavaScript a clipboard operation failed. With the clipboard held by another process, navigator.clipboard.writeText() still resolves, execCommand("copy") still returns true, and readText() resolves with "". Adding .catch() would have accomplished nothing.
  • A .NET clipboard read inside Bloom doesn't fail either. OLE answers it from a data object cached by that process's own earlier read, and Bloom is always reading (the edit-buttons timer polls the clipboard). Measured side by side against a fresh process: ContainsText() returned True and GetText() returned "" in the Bloom-like process while both threw in the fresh one. Only writes fail honestly — which is exactly why the Copy button reported failures and Ctrl+C didn't.
  • The test tool was lying. OpenClipboard(NULL) reports success but grants no exclusivity at all, so the locker used for all of this printed “LOCKED” while copies quietly succeeded. Several intermediate conclusions in this session came from an ineffective lock and had to be thrown away. The rewritten locker holds the clipboard from a thread that owns a real window and self-tests before locking — six write attempts from another process, all of which must be blocked.
  • End to end, against a self-tested lock in a running Bloom: Ctrl+C, Ctrl+V, Ctrl+X and the Copy/Cut/Paste buttons all toast; Ctrl+X preserves the text; the false “no image on your clipboard” message is gone.
  • Three of Devin's findings were regressions this PR introduced, all now fixed. Worth noting what they had in common: each was a case where the new code was more honest than the old code and that honesty leaked somewhere it wasn't wanted — a failure reported to someone who hadn't asked, a wait introduced where a save could slip in, and a reply read strictly enough to throw away a number.

1. A failed Ctrl+X still loses the text — it just says so now

The one thing you asked for that this PR does not deliver · Devin bug + Investigate flag

You singled this out: Ctrl+X deletes the text and, when the clipboard write fails, that text is gone from both the page and the clipboard. I did fix it mid-run, by having Ctrl+X go through Bloom's own cut — which copies first and only deletes if the copy worked.

Then Devin showed that fix was worse than the bug. Bloom's own cut can only put plain text on the clipboard, so cutting a phrase containing bold, a link, or an inline picture threw all of that away — and unlike the original bug, this happened on every cut, not only ones where the clipboard failed. So I took it out. Ctrl+X is back to the browser's own cut, which carries everything, and the change now simply tells the user when a cut failed so they know to press Ctrl+Z.

So the honest state is: nothing is worse than before, failures are now reported everywhere, and the text-loss-on-failure you originally pointed at is still there.

2. The check takes the clipboard, and might spoil the copy it's checking

Devin Investigate · thread left open

To find out whether the clipboard is usable, Bloom asks the operating system for it and immediately hands it back. That is the only truthful way to ask — but for those microseconds Bloom itself holds the clipboard.

The check runs just after the browser's copy, and Devin's point is that "just after" isn't guaranteed: the browser does its actual clipboard write in a separate process, on its own schedule. If the check wins that race, the browser's write fails — silently, because it discards clipboard errors — which means the check could occasionally cause the very failure it then reports.

I have not seen this happen, and I have not measured how wide the window is. My code comment originally waved it away; it now says plainly that the window exists and is unmeasured.

Recommended to leave it for now: the failure mode is a spurious message rather than lost work, the window is microseconds against a check that only runs on an actual copy, and adding a delay without measuring would be guessing — which has already cost this ticket a lot of time.

3. A busy clipboard now pastes nothing, where it used to paste something

Devin Investigate · thread left open · affects the link editor and the subscription code

This is the deliberate trade at the heart of the fix, and Devin is right that it deserves your eyes rather than mine.

When another program holds the clipboard, Bloom's own read of it usually still succeeds — Windows quietly serves the copy Bloom last saw. That is precisely what hid this bug for so long. The fix asks the operating system first and, if the clipboard is genuinely unavailable, reports a failure and pastes nothing rather than pasting something that may be out of date.

The cost: for about a fifth of a second while another program is busy, a paste that would previously have inserted the (usually still-correct) text now inserts nothing and shows a message. That applies to the paste button in the link editor and to pasting the subscription code in Collection Settings as well as to ordinary pasting.

Recommended to leave it: pasting stale content silently is the worse failure — the user cannot tell it happened — whereas a message they can act on costs them one retry. But it is a product call, and the two named paste buttons are the places a user would most likely notice.

4. A second identical failure gives no new feedback

Found while testing · affects every toast in Bloom, not just clipboard ones

When a message is already on screen, an identical one that arrives within its 15-second life is suppressed rather than shown again (ToastHost only replaces a live message if the new one would last longer).

What the user sees: a copy fails and they get told. They try again a few seconds later, it fails again, and nothing visibly happens — which reads as “the second attempt worked” or as the app ignoring them. This is genuinely how the bug looked twice during this session: a Copy-button toast was still on screen, so a following Ctrl+C appeared to report nothing.

5. Copying an image still interrupts with a dialog

Pre-existing, not touched by this PR · now inconsistent with the text paths

Copying a picture has its own clipboard error handling, which puts up a modal dialog saying “Bloom had problems using your computer's clipboard. Some other program may be interfering” plus advice to close other programs and restart (EditingView).

That predates this work and is arguably the better message — it names the likely cause. But it now sits alongside text copy/paste, which after this PR reports the same class of problem as a passing toast the user can ignore. The same underlying failure interrupts you for a picture and doesn't for a sentence.

Recommended to leave it: it is outside this PR's scope, the dialog's wording is genuinely more useful than the toast's, and changing it would be a user-facing decision of its own rather than a tidy-up.

6. The clipboard-locking test tool

Untracked at the repo root · deliberately not in either commit

Lock-Clipboard.ps1 is what made this bug reproducible at all: it holds the Windows clipboard so copy and paste fail on demand. It is not in the PR, per your call to keep it local and attach a copy to the card instead.

Two things changed since that call, which is why it's worth a second look. The tool turned out to be wrong in a way that silently invalidated test results (OpenClipboard(NULL) grants no exclusivity), and the fixed version now self-tests before locking. The copy currently attached to BL-16459 is the broken one, so anyone who picks it up will get misleading results.

7. Each Ctrl+C asks the desktop side twice

Devin, informational · you already accepted the duplication

One Ctrl+C reaches C# twice — once from the keydown handler and once from the browser's own copy event — because neither route alone covers every case. You called this fine for the message, and the duplicate reporting is suppressed (one entry in the log and in Sentry). The duplication that remains is the checking: when the clipboard is genuinely locked each check spends up to 200ms on a server thread before giving up.

Recommended to leave it: 200ms twice, only when the clipboard is already broken, on a non-blocking endpoint — and the redundancy is what makes the feature work across CKEditor's interference.
