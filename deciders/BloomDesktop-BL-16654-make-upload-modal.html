1. The RAB test: nothing is missing on your machine

You asked what's missing, on the grounds that you can build an app from a running Bloom. You're right that nothing is missing, and the test's explanation of itself is wrong — but the fix is not as simple as deleting the check, so this is back with you.

What the test claims. It refuses to start unless buildapp.bat can be found on the system PATH, with a message telling you to install "Reading App Builder's build tools". That premise is false. buildapp.bat is not an installed tool and never appears on the PATH: RAB generates it per project, into that project's own build folder, next to build.gradle, AndroidManifest.xml and ks.jks. On your machine copies exist under three collections (for example English Books\Bloom App Data\build\RAB.000\a\, written 20 April), and it is on neither your User nor your Machine PATH. There is nothing you could install to satisfy that check.

Your toolchain is complete. %LOCALAPPDATA%\SIL\Bloom\ReadingAppBuilder\ has jdk (Zulu 17), android-sdk including build-tools, keystore, appdata and projects, all from mid-April. That is consistent with your builds working.

But removing the check doesn't make the test pass. I tried it. The test then gets further — Prepare succeeds — and dies about 11 seconds later inside RAB's own build step with "'buildapp.bat' is not recognized as an internal or external command". So the check was predicting a real failure, just describing its cause wrongly. In that run the test collection's Bloom App Data\build folder was left completely empty: RAB never generated the project, so the batch file it then tried to run did not exist.

A theory I disproved, so you don't spend time on it. The test deliberately uses a collection named Kasɩm Books, and RAB's log shows that path mangled to Kas?m Books while a sibling path was passed as an 8.3 short name — and there is a real asymmetry in the code, where build= gets the raw path but apk.output= gets the ASCII-safe one. It looked conclusive. It isn't: I re-ran with the collection renamed to plain ASCII and it failed identically, same error, same 11 seconds. So the non-ASCII name is not the cause, and that asymmetry — while real — is not what breaks this.

What's left unexplained is why RAB generates the project when Bloom drives it interactively but not in the test's workspace. That is a question about the test harness's RAB setup, not about BL-16654, and I stopped rather than keep digging on this ticket's time.
