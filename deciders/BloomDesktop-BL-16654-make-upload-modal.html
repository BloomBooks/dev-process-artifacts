What the change does

C# already knew when an upload was running — it toggles the workspace-tab lock in a try/finally around it. Rather than give the Publish tab a second, weaker notion of "busy", this reports that same lock to the browser as navigationLocked (WorkspaceView.cs:745), and the Publish tab uses it at PublishTabPane.tsx:125 via the new useWorkspaceTabInfo hook. So the tools unlock at the moment the upload really stops, not when the browser guesses it has.

Per your decisions on the card: the shared boolean stays (not ref-counted), no tooltip or new localized string on the disabled buttons, no re-entrancy guard on the upload endpoint, and no change to ePUB/BloomPUB/PDF preview generation.

Something your decision on the shared flag depends on

You asked me to keep the single shared boolean and to tell you if that leaves a user-facing issue. My answer when I committed was "it doesn't, because with the tool switcher locked you can't reach a second publish operation." Chasing Devin's finding this run turned up a caller I had not accounted for, so here is the correction:

The Copyright and License dialog is reachable from the Publish tab itself — the "Missing Copyright → Click to fix" link on the Web screen — and it posts editView/setModalState with no edit-tab-only gate on either side, so a dialog opened from Publish does drive the shared lock. That doesn't reopen the overlap hole (it's a modal dialog, so locking is the right behavior while it's open), and the guard committed this run stops it stranding the user. But it does mean the flag is genuinely cross-subsystem, not publish-only — which is the thing to keep in mind if this ever comes back.

Waiting on you

1. The first second of an upload is still unprotected

This is the one substantive decision, and it is the same class of bug as the ticket itself — the new lock just doesn't reach back quite far enough.

When you press Upload Book, the Web screen immediately switches the button to Cancel and starts the progress log, so as far as the user is concerned the upload has begun. But before it actually starts one, it makes two API calls in sequence: a subscription check, and then "Checking for existing copy on server…", which is a real query to BloomLibrary and can take anywhere from a moment to several seconds on a slow connection. C# only takes the lock once the upload proper begins, so for that whole prologue navigationLocked is still false and the publish-tool buttons are live.

What the user would experience: press Upload; while "Checking for existing copy on server…" is showing, click BloomPUB. Nothing stops you. The Web screen is torn down, but the in-flight request completes and starts the upload anyway — so the upload runs with its Cancel button and progress log gone, and a moment later the tabs lock, leaving you parked on BloomPUB and unable to get back to Web until it finishes. Exactly the failure BL-16654 describes.

(The template-warning and upload-collision dialogs both cover the screen with their own backdrop, so they're safe. It is only the bare server round-trip that's exposed.)

2. Nobody has watched this work in a running Bloom

Everything here is verified by types, lint, unit tests and a production bundle build — but the actual behavior, the publish-tool buttons greying out during a real upload and coming back when it finishes or is cancelled, has never been observed in a running Bloom. Devin's finding ended with the same observation. Watching it live is the only way to catch a wiring mistake that compiles and tests clean, and it needs a real book and a real (or sandbox) upload.

3. A dialog opened from the Publish tab drives the Edit tab's lock

Noticed while checking Devin's finding, and pre-existing rather than caused by this branch. The Copyright and License dialog posts editView/setModalState whenever it opens or closes, and neither the browser code nor the C# handler checks which tab you are on. That dialog is reachable from the Publish tab via the Web screen's "Missing Copyright → Click to fix" link, so opening it there increments the Edit tab's modal-dialog depth and locks navigation.

While the dialog is up, locking is arguably right, and the guard committed this run keeps it from stranding anyone. It is only worth acting on if you dislike one subsystem's counter being driven from another tab on principle — which is why leaving it is the recommendation.

Devin arrived at the same soft spot from the other direction: it filed a Bug claiming a dialog could release the upload's lock mid-upload. That specific claim turned out to be false — the two dialogs it named both gate the post on being in the Edit tab — but the class of problem it describes is only prevented by an invariant nobody wrote down: the one dialog that posts ungated is reachable solely from the "Missing Copyright" link, and missing copyright is itself what blocks the upload from starting. Ticking Leave comment below is a cheap way to write that invariant down where the next person will find it.

4. One C# test fails on this machine, by design

The full C# suite came back 3031 passed, 1 failed, 12 skipped. The failure is RabRealBuildTests.SetupAndBuildAsync_RealReadingAppBuilderBuild_CreatesValidApk, an opt-in test that does a real Reading App Builder build. It normally skips itself, but it runs when BLOOM_RUN_RAB_MANUAL_TESTS=1 is set — which it is, in this environment — and then deliberately fails rather than skips if the toolchain is incomplete. Here it stops at the check that buildapp.bat is on the PATH; RAB's build-tools component isn't installed.

So it is machine setup, not a code problem, and nothing to do with this branch — the entire C# change on this PR is one line plus comments, in a file that test never touches.

5. The PR Automation workflow never fired for this PR

pr-automation.yml is supposed to run whenever a PR is opened: it pokes Devin into reviewing the commit, and adds the Devin review link to the PR description. It has run for other branches recently, but for PR #8174 no run was ever created — not queued, not failed, simply absent. I did both of its jobs by hand this run, so nothing is missing from this PR; the question is whether the workflow itself is quietly broken for new PRs.

Worth knowing: because this repo has no other pull_request workflow, if that automation stops firing, Devin silently stops reviewing new PRs and nobody gets a signal that it happened.
