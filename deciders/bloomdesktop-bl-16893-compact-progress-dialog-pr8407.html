What this PR is about

Problem

Bringing a book up to date for 6.5 (Update Book, and the automatic pass before the AI image editor opens or after a page-size change) is slow: about 10 s for the 19-page The Moon and the Cap, and about 17 s in Bloom sessions where Chromium stalls on a proxy lookup. It also makes users wait when nothing needs it yet, such as a page-size change or just opening the Publish tab. Every pass redoes every page, even pages the user has just edited. The progress bar climbs to about 90%, drops back, and slides back to 0 as the dialog closes.

Cause

The pass gave every page a new browser, so each page loaded and compiled the editing code from scratch, and each new browser paid the proxy lookup. The only record of the work was one mark for the whole book. The whole-book update's image passes each ran the bar from 0 to 100% before the page loop started it again.

What the PR does

  • The pass loads every page into one off-screen browser, which keeps the compiled editing code, and that browser skips the proxy lookup. Moon & Cap: about 9.9 s to 5.7 s.
  • Each page records that it has been brought up to date for the current browser maintenance level and page size (data-browser-maintenance-level / -layout, written by the editing JavaScript when its load-time work is done). The automatic pass only processes pages without that mark, so pages edited in the Edit tab are skipped. This replaces the whole-book <meta> record, which is now only read to bring a newer Bloom's level down to ours.
  • A page-size change no longer runs the pass. The Publish tab runs it when a tool is chosen, not when the tab opens, and opens the tool when it is done.
  • The progress bar only moves forward: the whole-book update fills the first 5%, each run gets a fresh dialog, and a finished run shows the full bar for 500 ms before closing.
  • BloomBridge's external/process-book shows the same dialog, on a websocket context of its own, in place of ExternalBusyOverlay. Its replies and status are unchanged.

How should page marks work with BL-16905's already-updated new books?

While this PR was being written, BL-16905 landed on Version6.5. It makes sure a brand-new book needs no update. A book made from one of Bloom's own templates (Basic Book and the like) gets the old whole-book "already updated" mark when it is created (BookStarter.cs). The two shipped Sample Shells (The Moon and the Cap, A Family Learns about Immunisations) ship already updated with that mark, and ShippedSampleShellsTests enforces it.

This PR replaced the whole-book mark with a mark on each page, and no longer reads the old one, so the two changes do not compile together. Also, when a new book is made from a shell, this PR clears the marks on the copied pages, on the grounds that they were updated for another book. So under this PR, a book made from a shell would get one update, about 6 seconds, the first time a Publish tool or the AI image editor needs it.

The template part translates directly: mark every page of the new book, instead of the book. I did that during the merge attempt, and backed it out along with the rest of the merge. The open question is the shells.
