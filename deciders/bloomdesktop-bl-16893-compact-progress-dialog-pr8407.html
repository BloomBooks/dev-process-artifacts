What this PR is about

Problem

Bringing a book up to date for 6.5 is slow. This covers Update Book, and the automatic pass that runs before the AI image editor opens or after a page-size change. It takes about 10 s for the 19-page The Moon and the Cap, and about 17 s in Bloom sessions where Chromium stalls on a proxy lookup. It also makes users wait when nothing needs the book yet: right after a page-size change. The progress bar climbs to about 90%, drops back, and slides back to 0 as the dialog closes. BloomBridge runs show a different, full-screen overlay.

Cause

The pass gave every page a new browser, so each page loaded and compiled the editing code from scratch, and each new browser paid the proxy lookup. The whole-book update's image passes each ran the bar from 0 to 100% before the page loop started it again.

What the PR does

  • The pass loads every page into one off-screen browser, which keeps the compiled editing code, and that browser skips the proxy lookup. Moon & Cap: about 9.9 s to 5.7 s.
  • A page-size change no longer runs the pass; it only makes the book due. Choosing a tool in the Publish tab now runs it if the book is due (not merely opening the tab), and opens the tool when it is done. The AI image editor still runs it before opening.
  • A book is due when its pageLayoutUpdateLevel meta is missing or below the current level. The pass, and making a book from one of our own templates, set it to the current level. A page size or orientation change, a size forced by the xmatter or branding, or any appearance change in Book Settings (theme, margins and so on) sets it to 0. This replaces browserMaintenanceLevel and browserMaintenanceLayout, which missed theme and margin changes. The shipped Sample Shells carry it.
  • A second request while a pass is running waits for that pass instead of reading the book it is rewriting.
  • The progress bar only moves forward: the whole-book update fills the first 5%, each run gets a fresh dialog, and a finished run shows the full bar for 500 ms before closing.
  • BloomBridge's external/process-book shows the same dialog, on a websocket context of its own, in place of ExternalBusyOverlay. Its replies and status are unchanged.

What changed this run

The whole-book record became the single pageLayoutUpdateLevel described above, with the resets, the shipped Sample Shells and the tests to match: d7b9b2d5ea.
