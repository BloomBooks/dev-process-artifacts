What this PR is about

Problem

Saving a page used to destroy it. To read the page's content, Bloom stripped the live page — detached the toolbox tool, took the text editor down, unwound the picture-overlay machinery — leaving a page that could be written to disk but no longer edited. Every save therefore had to end by navigating away and reloading, which is the only reason the editor has a "saved and stripped" state at all: to remember that the page is broken. It also made every page-list command a two-step round trip — ask the browser for the content, wait for the answer to come back on a separate call, then act.

What the PR does

  • The content is gathered from a copy of the page, and the page the user is looking at is never touched.
  • A save can therefore finish and leave the user exactly where they were. The AI image editor's save-after-commit is the first caller: it no longer pulls the page out from under its own overlay.
  • Page-list commands — click, Copy, Paste, Duplicate, Delete, reorder — send the outgoing page's content with the command, so Bloom saves it, carries out the command and navigates in one pass.
  • Teardown that used to ride along with the save (detaching the tool, resetting the controls above the page, overlay cleanup) now happens when the page is actually going away — including when the user simply leaves the Edit tab, which never unloaded the page before.
  • The save result distinguishes "declined", "failed" and "refused", so only "nothing at all happened" falls back to the old round trip.

SavingWithoutReloading.md explains the design, what has been converted, and what is left. This is deliberately not for the current release.

A page command is silently dropped after an outside program rewrites the book

Bloom can notice that another program has replaced the book you have open on disk. When that happens it must not write your version over the other program's work, so the save is refused — and Bloom sends you back to the Collections tab, because reloading a book underneath a live editor proved fragile.

In the short window before that tab switch happens, clicking a page thumbnail, or using Duplicate, Delete, Paste or reorder, now does nothing at all: no save, no page change, and no message explaining why. Previously the same click fell through to the older save route, which had no such guard and overwrote the other program's file — so the current behaviour is strictly safer, just silent.

The obvious repair — skip the save but carry out the command anyway — is only safe for commands that just change which page you are looking at. Duplicate, Delete and Paste express their whole effect in the step that would be skipped, and that is exactly the step that must not run when the book on disk is about to replace yours.

Should the benchmark scripts ship in this PR?

They exist because they are the evidence for the round trip this PR removes, and the design document cites them by name. They are developer/agent tooling, not product code, so a reviewer may reasonably ask why they are in a product change.
