What this PR is about

Problem

Saving the page you were editing used to destroy it. To read the page's content, Bloom stripped the editing markup out of the live DOM — took CKEditor down, detached the toolbox tool, unwound the canvas-element machinery — leaving a page that could be saved but no longer typed in. Every save therefore had to end by navigating away and reloading it, which is why saving flashed, threw away the cursor position, and could not be done casually. Separately, C# could not read the page itself: it had to ask the browser and wait for the answer on another API call. So everything that needed a save first — duplicate, delete, reorder, changing layout, leaving the Edit tab, quitting — was split into a "before" and an "after" around that wait, with two extra states in the editing state machine to sit in meanwhile.

What the PR does
  • The page is gathered from a clone of the page element (nothing else is saved, so nothing else is copied), and the live page is never touched. A save leaves the user exactly where they were, still editing. A tool takes its markup off whichever it is given — the clone for a save, the live page when it is detached — through one method, so the two cannot drift apart.
  • The browser volunteers the page rather than being asked for it: it watches the page and posts the current content to C#, which stores it under the id of that page load. A save then takes that content synchronously.
  • With nothing to wait for, the asynchronous machinery goes: the ask-the-browser API and its browser half, two state-machine states and everything that served them, and the shutdown kludge that cancelled the user's quit and re-issued it once the save came back. Leaving the Edit tab and closing the collection are now straight-line code.
  • C# decides whether a save would change anything, comparing the page it is given, after its own processing, against the page it already has. Opening a page and touching nothing now writes nothing, and neither does leaving the Edit tab or quitting with nothing changed. A command that changes the book itself — a new layout, a copyright, a levelled-reader level — says so, so that skipping the write can never skip its change. Every save, whether it goes on to another page or stays put, makes that decision in one place and clears the same flags afterwards.
  • Several things that made an untouched page look edited are fixed, so that visiting every page of a book, front and back matter included, writes nothing: editor chrome (CKEditor's toolbars, qTip's bubbles and attributes, bloom-ui controls) is stripped in the browser, and only there, so it no longer travels in the gathered content; the SVG Comical draws no longer carries freshly generated ids; a text-measuring scratch element can no longer be written into the book; attributes that come back in a different order no longer count as a change; the cover’s editing-only ?transparent=yes image parameter no longer makes book-wide data look changed; and optional branding images that are not there no longer get the “missing image” text saved into book-wide data.
  • The browser sends each page once as soon as it has loaded, because loading can itself change the page (after a page-size change, images and canvas elements are laid out afresh, and that belongs in the book), and again after every change that settles; C#’s comparison makes an untouched page write nothing. No request carries the page: every save, including the page list’s clicks and commands, uses the snapshot, and the few commands that restructure the page and then reload it send the snapshot at once and wait for C# to take it. When the page is mid-way through asynchronous work that belongs in it (an image being sized, a paste settling), the browser says so, and a save waits, briefly, for the snapshot of the finished page. Snapshots and busy notices go one at a time, in order; a failed post is reported to the user, and nothing is retried.
  • Nothing the editor does for its own display changes the saved page: the Talking Book highlight, including leaving long runs of spaces unpainted, is drawn with the CSS Highlight API rather than temporary markup. And the page list's right-click commands run in the order the user made them: the two that ask a question open their dialogs in the browser, so every command can run inside its request, and a click waits its turn.
  • A game page can be played in the editor while all this goes on. Gathering a copy of such a page used to reach into bloom-player's record of the live page — undoing the tester's drags, and saving the draggables where they had dragged them rather than where the author put them. That is fixed in bloom-player itself (bloom-player#441, in 2.20.3-alpha.1, which this PR requires), so a save now leaves the game alone and writes the authored positions.

src/BloomExe/Edit/SavingWithoutReloading.md explains the design and the measurements.

Worth knowing

  • A leak this PR does not fix, found while verifying it. bloom-player's prepareActivity sets touch-action: none on every draggable (BL-14502, so pointermove works on touch devices) and undoPrepareActivity never takes it off. So entering a game's Play tab once and then saving writes touch-action: none into the book, permanently — I watched it appear in a file that did not have it. Pre-existing rather than ours: the old destructive save read the live page after the same undo, so it wrote it too. You decided to leave it.
  • A deliberate behaviour change to know about when testing: leaving the Edit tab and quitting now write only what changed, where they used to rewrite the whole book every time. The tester's notes on the card ask for the case that would expose a miss (a dialog-made change followed straight away by quitting).
  • Where a change can still be missed, after the wait for a busy page: a click, a command or an exit within about 25 ms of a keystroke, before its snapshot is sent; work that needs C# to finish, asynchronous work that does not register in the delay register (the snapshot path heals itself as the work's mutations arrive, but an exit in the gap is unprotected, as it always was), and work that outlives the four-second cap on either side. Both are unchanged from before this PR; the wait closed the one case the PR had made weaker.
  • At least forty-five real defects from Devin across the whole branch — four of them this run, all in new code written the same day. Not one was caught by the test suites; the one that driving the app did catch is the leak above, which is not ours.
  • Devin's list does shift between runs, slightly. An earlier report of mine said it was identical every time; that was wrong. Across four consecutive reviews each returned much the same 22–23 bugs and 29 flags, but with about one new finding and a few re-worded titles each round — and the re-wordings are why some findings had never been mirrored: they no longer matched the titles already on the PR. Everything currently in the list has now been checked against the actual code.
  • A flaky C# test from master is fixed here, at your request (682aceb). Xml_DoesNotProvide_ThreadSafety checks that a plain XmlDocument breaks under concurrent use, but its threads slept between operations, so a collision was luck: it failed in two of five full runs, and again on this run’s first full suite. Its threads now run without pauses until one throws (capped at ten seconds). It has passed forty runs on its own and three full suites.
