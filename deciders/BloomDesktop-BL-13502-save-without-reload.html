What this PR is about

Problem

Saving the page you were editing used to destroy it. To read the page's content, Bloom stripped the editing markup out of the live DOM — took CKEditor down, detached the toolbox tool, unwound the canvas-element machinery — leaving a page that could be saved but no longer typed in. Every save therefore had to end by navigating away and reloading it, which is why saving flashed, threw away the cursor position, and could not be done casually. Separately, C# could not read the page itself: it had to ask the browser and wait for the answer on another API call. So everything that needed a save first — duplicate, delete, reorder, changing layout, leaving the Edit tab, quitting — was split into a "before" and an "after" around that wait, with two extra states in the editing state machine to sit in meanwhile.

What the PR does
  • The page is gathered from a clone of the body, and the live page is never touched. A save leaves the user exactly where they were, still editing.
  • The browser volunteers the page rather than being asked for it: it watches the page and posts the current content to C#, which stores it. A save then takes that content synchronously.
  • With nothing to wait for, the asynchronous machinery goes: the ask-the-browser API and its browser half, two state-machine states and everything that served them, and the shutdown kludge that cancelled the user's quit and re-issued it once the save came back. Leaving the Edit tab and closing the collection are now straight-line code.
  • C# decides whether a save would change anything, comparing the page it is given, after its own processing, against the page it already has. Opening a page and touching nothing now writes nothing.
  • Several things that made an untouched page look edited are fixed: editor chrome (CKEditor's toolbars, qTip's bubbles and attributes) no longer travels in the gathered content; the SVG Comical draws no longer carries freshly generated ids; and a text-measuring scratch element can no longer be written into the book.

src/BloomExe/Edit/SavingWithoutReloading.md explains the design and the measurements.

1. A page command is silently dropped after another program changes the book

If an outside program rewrites the book while you are in the Edit tab, Bloom protects that program's file by refusing to save. But the command you clicked — a page click, Duplicate, Delete, Paste, reorder — is then abandoned entirely: no save, no action, no navigation, and no message. Your click appears to do nothing until you leave the Edit tab. This is narrow in practice, because the one place that sets this state immediately sends you to the Collections tab, so you are not normally sitting there clicking. It is also strictly safer than what came before, which was to fall through and overwrite the other program's file. Left open from an earlier run for your decision; nothing about it has changed since.

2. Devin's Investigate backlog has not been triaged

Devin returned 27 Investigate flags and 42 informational items against the squashed diff, on top of the bugs already handled. A verified sample of its output describes code that is not at this HEAD, so the list cannot be taken at face value — but it also cannot be dismissed, because the same run independently found three real bugs. Working through it properly is a substantial pass in its own right, and I have not done it.

3. The cover and title page keep re-saving themselves

On the front cover and title page, the title's bottom padding flips between 0px and 3px from one load to the next, which also shifts the cover image. Every visit therefore counts as a real change and rewrites the book, so a book shows as modified after only being looked at — which matters most in Team Collections. It is not caused by this PR: the instability is in how the title's descender is measured, and it predates the branch. Reproduced in two separate books.

4. A snapshot posted just before a reload can outlive it

The endpoint that receives the page's volunteered content runs without synchronisation, so a post sent a moment before Bloom reloads the same page can be stored after the reload has cleared it. Moving to a different page is harmless. Where it could bite is reloading the same page — Change Layout, importing a video, changing the topic or book settings — because C# would then hold a snapshot of the pre-reload page under the correct page id, and the next save could merge that over what the reload rebuilt. The window is about one round trip, and I have not seen it happen; the local review rated it medium confidence and I have not fixed it.
