What this PR is about

Problem

Saving the page you were editing used to destroy it. To read the page, Bloom stripped the editing markup out of the live page (CKEditor, the toolbox tool, the canvas-element machinery), leaving a page that could be saved but no longer typed in. So every save ended by reloading the page, which is why saving flashed and lost the cursor. And C# could not read the page itself: it had to ask the browser and wait, so everything that saved first (duplicate, delete, reorder, Change Layout, leaving the Edit tab, quitting) was split around that wait, with two extra editing states to sit in meanwhile.

What the PR does
  • The page is gathered from a copy of the page element; the live page is never touched, so a save leaves the user where they were, still editing. Each tool takes its markup off whichever it is given (the copy, or the live page when it is detached) through one method.
  • The browser volunteers the page, 25 ms after each change settles and once as it loads, and C# keeps it per page load. Every save uses that copy at once; no request carries the page. The asynchronous machinery goes: the ask-the-browser API, two editing states, and the shutdown kludge that cancelled the user’s quit and re-issued it.
  • C# decides whether a save would change anything, so opening a page and touching nothing writes nothing. A command that changes the book itself says so, so that skipping the write can never skip its change. For the same reason, toolbox settings (the expanded tool, the reader tools’ stage and level, which tools are on) are now written to meta.json as soon as they change.
  • Several things that made an untouched page look edited are fixed: editor chrome, Comical’s regenerated SVG ids, a text-measuring scratch element, attribute order, the image parameter C# adds for editing, and the “missing image” text on optional branding images. What C# adds to a page for editing is now undone in one place, RemoveMarkupBloomAddedForEditing.
  • When the page is busy with work that belongs in it (an image being sized, a paste settling), the browser says so, and a save waits briefly for the finished page. A failed post is reported to the user. Features that cleaned their markup off the live page while saving (Bloom Tables, through bloom-table 0.1.2’s removeTableEditingMarkup; Comical) now clean the copy instead.
  • Needs bloom-player 2.20.3-alpha.1 (bloom-player#441), so that saving a game page while it is being played leaves the game alone.

Worth knowing

  • The toolbox bug was caught only by luck of timing. It had been in the PR all along, hidden because something else on the page made every visit look like an edit until master changed it. Any other setting kept outside the page that waits for a book save to be written would have the same problem. I have not searched for others.
  • A deliberate trade: a click, command or exit within about 25 ms of a keystroke saves the page from just before that keystroke (kQuietMs says why).
  • A leak this PR does not fix: bloom-player leaves touch-action: none on a game’s draggables after the Play tab, and a save writes it. It predates this PR; you chose to leave it, and the tester’s notes say not to report it.
