Pasting a picture only claims the background when it is still a placeholder

Preflight for BL-16542 on branch BL-16542-MorePastingIntoImage, draft PR #8149, at commit cd6bf78b8. Everything below is done; one decision and two FYIs are waiting on you.

What the change does

When you paste an image with nothing selected, Bloom decides between putting the image into the page's existing picture and adding a new picture on top. The rule used to be "if this canvas holds nothing but a background picture, overwrite that picture." That overwrote a real picture the user could see, without them ever selecting it.

The rule is now narrower. After this branch, pasting with nothing selected behaves like this:

  1. Picture area is still an empty placeholder → the pasted image fills it in.
  2. Picture area already holds a real picture → the picture is left alone and the pasted image is added as a new canvas element on top.
  3. Several items on the canvas, or no background at all (a custom-layout front cover) → new element on top, exactly as before.

Selecting a picture and pasting still replaces it — that branch, added earlier on this card, is untouched. So is the picture's own "…" menu Paste image command.

On a subscription tier without overlays, this paste now hits a subscription wall

Adding a picture on top of another picture is an overlay, and overlays are a paid-tier feature. Replacing a picture is not — it has never been gated. Because the new rule sends a case that used to "replace" down the "add an overlay" path, it also sends it through the subscription check.

Concretely: a user in a collection on a tier that does not include overlays opens a page that already has a real picture, clicks nothing, and pastes. Previously the picture was simply replaced. Now they get the "this requires a subscription" dialog and nothing is pasted. The picture is not harmed, and there is a workaround — select the picture first, then paste, which still replaces it with no dialog — but nobody tells them that, and to them it will look like pasting a picture stopped working when they upgraded Bloom.

My read is that this is an acceptable price and not worth special-casing: the reason for the change — don't destroy a picture the user can see unless they selected it — applies just as much on a cheap tier as an expensive one, and carving out an exception would mean the destructive old behavior survives precisely for the users least equipped to recover from it. It would also make the paste rule depend on the subscription, which is a harder thing to explain than the rule we now have. That is why Leave as is is the recommendation below. I have flagged the case prominently in the QA notes so a tester puts real weight on it.

FYI — a user picture named like a placeholder would still be claimed

The test for "is this picture still empty?" looks for the text placeholder.png anywhere in the picture's address, ignoring capitalisation. So a genuine picture the user chose, saved as something like my placeholder.png, or living in a folder called Placeholder.png, would be treated as an empty slot and silently overwritten by a paste.

This is not new and not specific to this change: it is how the whole codebase already decides whether a picture slot is empty, in about a dozen places. Diverging here would make this one check behave differently from every other one. Devin raised it as an observation and said the same — consistent rather than a regression.

Do anything about it?

FYI — the emptiness check guards against a missing picture twice

The line that decides whether the background is empty reads the picture's address with a "if there is a picture" operator, and then the surrounding condition checks "if there is a picture" again. Devin pointed out that one of the two is redundant, and noted that the repo's own guidance discourages extra defensive checks.

Both checks are doing something — the second one is what stops us handing a missing picture to the code that swaps the image in — so the code is correct as written. Removing the redundancy means either nesting the branch one level deeper or reading the address twice, and neither reads better than what is there. This is purely cosmetic; nothing behaves differently either way.
