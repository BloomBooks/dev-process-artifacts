A file called photo%41.jpg became photoA.jpg

Second preflight run for BL-16669. Everything is green, every reviewer is finished, and no finding is left open — what remains are two optional follow-up cards and the question of what you want done next.

PR #8179 (draft) Files changed BL-16669 branch BL-16669-percent-in-filename head cfb4a09d

What was wrong, and what it turned into

Choosing a picture called photo%41.jpg left the page pointing at photoA.jpg, which doesn't exist. %41 is the URL escape for A: CreateFromUnencodedString guesses that anything shaped like an escape must be one, and ChangePicture handed it the name of a file it had just written.

Fixing that opened a bigger question, because Bloom stores file names in several places and does not use one convention. Establishing which is which took a survey of every consumer, and produced the second half of this branch: a written-down convention on UrlPathString, and a one-line pointer at every place that depends on it. Grep for “encoding conventions”.

The answer is genuinely non-uniform, which is why it needed writing down: the game sounds and the data-div image entries hold the plain name, while data-backgroundaudio — sitting right beside them — really is URL-encoded.

Not a regression from BL-16658. That fix lives in PageListApi and is untouched. This bug surfaced while working through that card's test ideas.

Notes from the run

  • The most valuable thing this session caught was its own mistake. Settling the sound attributes as plain names was right for three of them and wrong for the fourth — the same method also handles background music, which is encoded. That would have shipped duplicate music files, and in the worst case deleted one that a page still pointed at. Both the local review and Devin found it independently.
  • Where a wrong guess would have destroyed something, the code now asks the disk. Three places use the existence-guarded decode: the missing-image scan, the data-div read, and the credits dialog. That is what lets a real photo%41.png and a legacy doubly-encoded name coexist.
  • Verified against a running Bloom earlier in the session: a request for the encoded photo%2541.png returns 200 with the real file; photoA.png returns 404.

Over to you

1. Sounds still won't play if their name contains a percent escape

Known gap, deliberately left open

This branch settled that game sounds are stored under their plain file name. That is right for everything in Bloom that treats them as files — but the two places that turn one into a web address simply glue it on the end of audio/ without encoding it. So a sound genuinely called beep%41.mp3 is stored correctly, published correctly, and then fails to play: the browser reads the %41 as an escape and asks for beepA.mp3.

It happens both in BloomPlayer and in Bloom's own editor preview, so it can't be fixed on this branch alone — one of the two places is in another repository. It is written down in the convention note, but nothing tracks it.

2. A test that passes only because the test harness is wrong

Found while adding coverage; not touched by this branch

PretendRequestInfo, which stands in for a real web request in the tests, decodes the address twice, where the real code decodes once. That is why the obvious home for a server-side test of this bug wouldn't work, and the case had to be covered against the real class instead — there is a note in BloomServerTests saying so.

The larger consequence is that HandleDoubleEncodedUrls currently passes because of that discrepancy: it asserts behavior that production deliberately removed some years ago (BL-11319). So the test is not testing Bloom, and would not notice if that part of the server broke.
