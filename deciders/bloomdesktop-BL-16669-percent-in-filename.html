What was wrong, and what it turned into

Choosing a picture called photo%41.jpg left the page pointing at photoA.jpg, which doesn't exist. %41 is the URL escape for A: CreateFromUnencodedString guesses that anything shaped like an escape must be one, and ChangePicture handed it the name of a file it had just written.

Fixing that opened a bigger question, because Bloom stores file names in several places and does not use one convention. Establishing which is which took a survey of every consumer, and produced the second half of this branch: a written-down convention on UrlPathString, and a one-line pointer at every place that depends on it. Grep for “encoding conventions”.

The answer is genuinely non-uniform, which is why it needed writing down: the game sounds and the data-div image entries hold the plain name, while data-backgroundaudio — sitting right beside them — really is URL-encoded.

Not a regression from BL-16658. That fix lives in PageListApi and is untouched. This bug surfaced while working through that card's test ideas.

Sounds with a percent escape. You asked for the Bloom half fixed now and a card for the rest. GameTool's playSound now escapes the name when it builds the URL, so such a sound plays in the editor. Bloom Player still doesn't, and that is BL-16688 — filed with the mechanism traced through the shipped bundle, repro steps, and an explicit note that it was not verified end-to-end in the player.

The test double. PretendRequestInfo now decodes once and strips the query, like the real thing. That immediately allowed the server-level test for a %-named file that could not be written before.

It also proved me wrong, which is the useful part: I had said HandleDoubleEncodedUrls passed only because of the double decode. It still passes without it, because the server decodes a second time and keeps that result only when it finds the file. So the server was already deciding by what is on disk — the same approach this branch took elsewhere — and that one guard is what lets a doubly-encoded legacy URL and a real photo%41.png both work.
