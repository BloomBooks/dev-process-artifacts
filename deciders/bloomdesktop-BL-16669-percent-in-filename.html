A file called photo%41.jpg became photoA.jpg

Preflight report for BL-16669 — the branch is green and the PR is open in draft. Three questions are waiting for you, all of them about problems that were already there before this change.

PR #8179 (draft) Files changed BL-16669 branch BL-16669-percent-in-filename head fafc8092

What was wrong

Choosing a picture called photo%41.jpg in the image chooser left the page pointing at photoA.jpg, which doesn't exist, so nothing appeared. %41 is the URL escape for the letter A.

UrlPathString.CreateFromUnencodedString has long carried a guess: if the string it is given looks like it contains an escape, assume the caller was wrong about it being unencoded, and decode it. The comment beside it already conceded the cost — “makes it impossible to have, say %20 in your actual file name”. PageEditingModel.ChangePicture passed it the name of a file it had just written into the book folder, so the guess could only ever be wrong there.

The guess has to stay: several callers really do hand that method an already-encoded string and rely on the decode. So the fix is at the call sites — the ones holding a genuine file-system name now say so. All 42 call sites were audited; 29 now declare themselves, 6 are deliberately left guessing, and the rest are empty strings.

This is not a regression from BL-16658. That fix lives in PageListApi and is untouched. It is the same family of mistake, and this bug surfaced while working through that card's test ideas.

1. Sound file names are written one way and read back another

Devin, Investigate · thread · PublishHelper.cs:1350

When Bloom publishes a book it tidies up duplicate media files: if two sounds are byte-for-byte identical it keeps one and repoints everything at it. When it repoints a sound, it writes the file's name in plainly, with no encoding. But the code that reads that same attribute back, ten lines above, expects it to be encoded. For a sound whose name contains a percent sign followed by two characters, the name would come back different from what was written, and the sound would go missing from the published book.

This is not new and this PR does not touch it. The reason it isn't simply fixed the way everything else here was is that it isn't clear which side is wrong: the editor's own JavaScript also writes these attributes plainly, so the writer is arguably the one that's consistent and the reader is the odd one out. Changing the reader affects how every existing book's sounds are interpreted.

2. Saving a picture's copyright can quietly do nothing

Devin, Investigate · thread · EditingModel.cs:1196

After you edit a picture's copyright and licence, Bloom finds that picture on the page in order to update it — by looking for a picture whose reference matches the file name exactly. Bloom sometimes appends extra information to that reference, such as a marker that the picture should be shown with a transparent background. When it has done so, the exact match finds nothing, and the update silently does not happen. There is no error; the code even carries a comment reading “log? unexpected”.

This change fixed a different half of the same method (the name is now encoded to match what the picture chooser writes), which is why it came up. But the exact-match part is pre-existing and fixing it means changing how the picture is located, which is broader than this bug.

3. The cover-image entry has the same split, and Bloom disagrees with itself about it

Local review · PublishHelper.cs:1231 vs :1216

Exactly the same shape as item 1, but for the cover image. In the very same method whose picture and video cases I did fix, the entry that records the book's cover image is written plainly and read back as though encoded. For a cover picture whose name contains a percent escape, publishing a book with duplicate images could leave the cover pointing at a name that isn't there.

What stopped me fixing it is that Bloom genuinely contradicts itself here. Book.cs:2490, which is the main place this entry is written, deliberately writes it decoded — while two separate readers treat it as encoded. UrlPathString's own documentation points at three old cards (BL-3901, BH-6143, BL-11145) about books in the wild that got this wrong in both directions. Guessing here could break cover images on existing books.
