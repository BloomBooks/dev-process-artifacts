What this does

Our tests name their scratch folders after themselves — about 180 calls of the form new TemporaryFolder("SomeFixtureTests") — and those names resolve to machine-global paths. That was harmless when one person ran the suite at a time. It is not harmless now that agents work in several worktrees at once, because TemporaryFolder's constructor deletes any existing folder of that name before creating it. One run's setup therefore deletes another run's in-flight folder, and the victim fails somewhere unrelated, naming a folder it never heard of.

Rather than rename 180 call sites — which would still leave Bloom's own code writing to the shared temp directory while under test — this points the whole process's temp directory at %TEMP%\BloomTests\<key>-p<pid>\ before any fixture runs. Every existing call site keeps its familiar name, now scoped to the run.

A side benefit worth knowing: because every temp path the run computes now descends from one folder, deleting that folder removes everything the run made in temp. Under the old scheme cleanup depended on each fixture disposing each folder it created, and several never did.

Decision 1

A third source of flaky runs, unrelated to either PR

About one run in three ends early — not with a test failure, but with the test host process crashing. Six full runs on this branch: four finished, two did not. In plain terms, Bloom's little web server is being shut down while it is still handling a request, and the resulting crash takes the whole test host with it. It wears two faces, both from the same lifetime problem: Cannot access a disposed object … ThreadPoolBoundHandle from BloomServer.RequestProcessorLoop, and Cannot access a disposed object … HttpRequestQueueV2Handle while a response is still being written.

It is worth knowing that an aborted run can still print "Passed!" — one of these stopped after 348 of 3046 tests and reported success, because everything that had run so far had passed. A run has to be checked for "Test Run Aborted" as well as for its pass count, or a third of runs can look green while having barely started.

It is definitely not caused by this branch. It aborted a run whose only change from a previous complete run was documentation comments, which cannot alter behaviour. It also appeared during earlier runs on master.

It is, however, the reason the full-suite figures above come from the most recent complete run rather than simply "the last run".

It matters because it is the last remaining reason a run of the suite does not finish, and because it is easy to misattribute: for a while today I was crediting these aborts to the temp-folder problem this PR fixes.

For your information

What a failing run leaves behind, and for how long

A run that fails keeps its temp folder, so you can see what the failing test wrote; a run that passes deletes its own. Anything left behind is cleared by a later run once it is more than a day old. Both halves were checked directly rather than assumed: one failing test leaves a folder, one passing test does not, and the count in %TEMP%\BloomTests\ moves accordingly.

Two consequences to be aware of. Folders belonging to a fixture that is later renamed or deleted will sit there until the day is up. And if you crash out of many failing runs in quick succession you will accumulate one folder per run for a day, which is untidy but bounded.

For your information

This overlaps with BL-16661, but does not replace it

These two changes fix different causes of the same symptom, and each on its own takes this machine's suite from "aborts with 65 failures" to "completes with 1". This one stops separate runs from deleting each other's folders; BL-16661 stops a test book in %TEMP% making Bloom treat the whole temp tree as a collection.

Keeping both is worthwhile: this one alone would leave the importer still scanning whatever its book's parent folder happens to contain, and BL-16661 alone would leave two concurrent runs deleting each other's folders. They also compose without conflict — the spreadsheet folders simply nest inside the per-run root.
