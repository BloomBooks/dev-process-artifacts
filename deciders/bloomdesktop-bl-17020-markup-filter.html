What this PR is about

Problem

Bloom's Edit tab has several separate undo histories: CKEditor keeps one per text box, pictures have their own, the reader tools have theirs, and Change Layout mode has origami's. Ctrl+Z in a box undoes only that box, and many edits (moving, resizing or deleting a canvas element, most toolbox changes) cannot be undone at all. PR 8484 replaces them with one undo history for the whole page, built from recorded DOM mutations, but at 221 files it is too big for a person to review.

While a page is being edited, Bloom and its libraries put markup into it that a save strips. If the page history recorded it, an undo would put it back where a save could keep it, and a change to it would make the next undo refuse.

What the PR does

This is PR 2 of 3 in the re-cut that docs/undo/REVIEW-PLAN.md lays out. All three add the page history as code that nothing in Bloom calls yet, so master's behaviour does not change, and they merge in order: 8520 (engine), 8525 (markup filter), 8526 (input, keys and page readiness).

  • editTimeMarkup.ts lists the elements, classes, attributes and style properties that exist only while a page is being edited, each rule naming the step of the save path that strips it; a few more cover markup that a save keeps but that Bloom works out again, which undo leaves alone. On the .bloom-page only the four page colors that C# saves are recorded.
  • createEditTimeMarkupFilter builds the engine's filter interface from those rules.
  • Tests that drive the engine with the filter, including a randomized test of edits, undos and redos.
