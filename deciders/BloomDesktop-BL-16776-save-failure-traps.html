Don’t let a failed page save trap the user in Bloom

Three commits on BL-16776-save-failure-traps, based on Version6.4. The crash is fixed and the two exits it was blocking — changing tabs and quitting — no longer depend on the save succeeding.

Draft PR Mergeable No findings anywhere 4 items for you

What this PR is about

Problem

Switch a front cover to custom layout, add an image to it, and the book can reach a state where the page will never save again. Every action that saves — clicking a page thumbnail, switching to the Collections or Publish tab, even quitting — puts up “Bloom had trouble saving a page” and then does nothing else. There is no way out of the program except Task Manager. Reported from 6.5.3007 with Little Zebra branding.

Cause

A branding HTML value can itself contain an <img> marked as the cover image. UpdateDomFromDataSet collects every data-book node up front, then restores the branding element — which replaces everything inside it, orphaning that image. When the orphan’s turn comes, the update code reaches for parents it no longer has and throws.

That alone would be one failed save. What makes it inescapable is separate: leaving the Edit tab and shutting down both run their real work only after Book.Save() returns, so a save that always throws blocks both of them permanently.

What the PR does

  • Skips collected nodes that an earlier update has since detached from the document, in both of UpdateDomFromDataSet’s passes. This is the crash itself.
  • Leaving the Edit tab now reports a failed save and changes tabs anyway.
  • Shutdown likewise reports and carries on, so quitting never depends on the save.
  • The state machine now runs the caller’s recovery action when the post-save action throws, not only when applying the page content does — completing a design that already existed for the other failure path.
  • A regression test for the orphaned-image crash.

The other half of the report — the branding logo being designated as the cover image in the first place, in bloomImages.ts — is not touched here, has no card of its own, and belongs on 6.5, where custom cover layouts actually exist.

Worth knowing

  • On 6.4 this is a fix for books made elsewhere. A custom-layout front cover can only be created in 6.5 — 6.4 has no cover-layout UI at all — so the bad data always arrives from a 6.5-authored book. 6.4 is built to open those, and its copy of the save code crashes on them exactly as 6.5 does, which is what the regression test pins down. The two save-failure traps are unconditional 6.4 behaviour and are unrelated to covers.
  • The forward-merge into 6.5 will conflict, certainly. PR #8248 is already merged into Version6.5 and renames TabChangedDetails.PostponedWork to CompleteTheChange on exactly the lines this PR wraps in a try/catch. Mechanical: keep the try/catch, use the new name.
  • Nothing here was exercised in the running app. The crash and both traps were diagnosed against a live 6.5.3007 session, its log, and the book on disk, and the crash is covered by a unit test — but the tab-change and shutdown paths have only been reasoned about, not driven by hand.
  • One test fails on Version6.4 before this branch exists. InsideBackCover_PaperAndDeviceXMatter_ShareOneCustomLayoutId — confirmed failing at the base commit, so a reviewer seeing it red need not chase it here.

The front-end half has no card, and belongs on 6.5

Two defects produced this report. This PR fixes the second — the crash, and the fact that it made Bloom unusable. The first is in the editor: on a custom-layout front cover whose picture is still the placeholder, normalizeCoverImageDesignation takes the branding logo to be the book’s cover picture and saves that into the book. Nobody is tracking it.

It has to be fixed on 6.5. The function is present on both branches, but it does nothing unless the front cover is in custom layout, and 6.4 has no cover-layout UI or endpoint at all — the “Cover Layout Changed” event in the crash log exists only in 6.5’s EditingViewApi. So the bad data can only be made on 6.5.

BL-16780 / PR #8256 is the nearest work, but it is a 6.4 card fixing the read side — which picture becomes the book icon, in Book.GetCoverImagePathAndElt. I checked its branch: the editor code is untouched, so it cannot stop the logo being written into the book. What it does give us is the rule, already agreed and implemented in C#: an image counts only inside an image container, plus a branding / licence / QR exclusion. The front end excludes only Bloom’s own UI images.
