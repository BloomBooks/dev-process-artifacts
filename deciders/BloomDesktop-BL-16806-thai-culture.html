What this PR is about

Problem

On a machine whose regional format is Thai, Bloom names languages wrongly. A language the collection does not itself name — one whose text is still in a book after the collection stopped listing it — shows as its bare code (en) or as "Unknown language" instead of its name.

Cause

.NET's culture-sensitive string search treats the hyphen as ignorable under th-TH, so "en".IndexOf("-") returns 0 rather than −1. LibPalaso's GetGeneralCode finds the end of a language subtag with exactly that search, so every tag's general code comes out empty and the name lookups built on it fail (BL-16945).

Bloom already has the workaround: ToPalaso/IetfLanguageTagExtra wraps the affected LibPalaso calls and runs them with an invariant CurrentCulture. PR #8426 converted Bloom's call sites, but the fallback this PR touches landed on master separately and so was never converted.

What the PR does

Routes the three LibPalaso calls in CollectionSettings.GetDisplayNameForLanguage's fallback — GetLocalizedLanguageName, GetBestLanguageName and GetGeneralCode — through IetfLanguageTagExtra, matching what the rest of Bloom already does. Three lines, in one file; no behavior change on a machine that was already naming languages correctly.

This is a stopgap by design. LibPalaso PR #1550 makes those searches ordinal at the source; once that lands and Bloom takes the version bump, IetfLanguageTagExtra and every call to it can be deleted together, as the class's own remarks say. Master only — 6.4 and 6.5 do not have the code this fixes.

Worth knowing

  • Nothing here has been seen in a running Bloom. The evidence is the test suite under a forced th-TH culture, not a machine actually set to Thai regional format. If you want one thing confirmed by hand, that is it.
  • Two other direct LibPalaso calls remain in BloomExe, and both are fine. MiscUtils.TryGetParts and WorkspaceView's GetManuallyOverriddenEnglishNameIfNeeded — the latter is an ordinal string switch whose fallback callback is already wrapped, so #8426 left it alone deliberately. No action needed; noted so a reviewer doesn't chase them.

Should th-TH join the weekly culture sweep?

Devin and Greptile independently raised the same point: nothing will catch it if this call site regresses under Thai again.

The tests themselves are not missing — the two GetDisplayNameForLanguage_LanguageNotInCollection_* fixtures cover exactly this path, and they are among the 13 that fail on master under Thai and pass here. What is missing is that the scheduled sweep runs only fr-FR and tr-TR. th-TH is listed in that workflow as a candidate to trial, never adopted.

It cannot simply be switched on. The workflow's own rule is to adopt a culture "only once it is green or its failures are fixed", because a permanently-red scheduled job teaches everyone to ignore it — and Thai still fails 16 unrelated tests: Buddhist-calendar date handling (GetExpirationDate, WhenWasBookLocked), HTML save and normalization (SaveAsHTML_*, GetXmlDomFromHtml_*), and packaging (CompressBookForDevice, DuplicatePage_WithAudio). None of them are language names, and none are this PR's doing.
