What this PR is about

Problem

Every page you click in the Edit tab leaks that whole page: its document, its frame and its entire JavaScript realm. In a long session the WebView2 renderer grows without limit; Bloom's Performance Measurement tool showed 2.21 GB after 77 page clicks in a large book.

Cause

Changing pages keeps the toolbox iframe and only navigates the page iframe. On each page load the toolbox binds handlers onto the page's text boxes using the toolbox frame's own jQuery 1.12, which keeps every such element in its global cache until the element is removed through jQuery. Navigating an iframe never tells it, so the long-lived toolbox frame holds one text box per page visited, and each keeps its detached document and whole realm alive.

What the PR does

  • Adds ToolBox.releaseElementsForTools: one sweep of jQuery's own cleanData over the page, so no future tool can reintroduce the leak by forgetting to unbind.
  • Calls it from pageUnloading(), which every page change and leaving the Edit tab already run, after the active tool detaches.
  • Adds a regression test (toolboxReleaseSpec.ts).

Measured live: with the release disabled, 12 page clicks kept ~14 dead documents and ~200 MB of JS heap; with it, both stayed flat.

Worth knowing

  • The fix stops new accumulation; it does not free pages a running Bloom leaked before the fix loaded. Those go when the toolbox frame is rebuilt (leaving the Edit tab and coming back), so this matters only when comparing numbers mid-session.
  • Memory figures without a forced garbage collection are meaningless for this leak: they show growth whether or not the fix is in. Testers are told to look for a level line, not a flat one.
  • The branch's history has a no-op merge of the original ec4b358 commit; pr-ready-for-human's squash will fold it away.

Decisions

Also put the fix on Version6.5?

The card has no [6.x] prefix and the PR targets master (6.6). The leak is just as present in 6.5, which users run today, and the card's original author noted the fix cherry-picks cleanly. The 6.5 code around pageUnloading() differs from master's, so a 6.5 version would need its own small conflict resolution and its own test pass.

File cards for the two Performance Measurement tool defects?

The card describes two bugs in Bloom's own memory measurement, found during the investigation and not fixed by this PR: (1) it can count unrelated programs as part of Bloom, because Windows reuses process ids after a process exits (Adobe's sync tool was seen adding ~30 MB to Bloom's total); (2) "Select Page" always reports 0 seconds and samples memory before the page has loaded. Neither affects users directly, but both make the tool's numbers misleading to whoever investigates the next memory or speed report.
