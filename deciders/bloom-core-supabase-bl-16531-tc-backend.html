What this PR is about

Problem

Cloud Team Collections (BL-16531) was built in BloomDesktop PR #8052, with its Supabase backend (database schema, edge functions, local dev stack) sitting in the Bloom Editor repo by mistake. The backend belongs here, so it can be reviewed, merged and deployed separately from the Bloom client. The client side, including the new Share dialog (BloomDesktop #8394), is written against it. Reviewing the port also turned up real security and concurrency problems in the carried-over backend.

What the PR does

  • Port: the tc schema as declarative files plus its generated migration, the seven edge functions (check-in, download, stale-upload sweep) with Deno tests, and the local dev stack and ops scripts under team-collections/.
  • Security: the "finish" functions can be called only by the edge functions, after they have identified the caller from their own token. A checkout belongs to one copy of the book, identified by a GUID the client makes and saves before asking. The server stores only its hash, and check-in, unlock, delete and takeover all need the GUID.
  • Concurrency and data safety:
    • Check-in finish rechecks the lock and base version.
    • Row locks follow one consistent order, including the expiry reaper and delete/unlock/force-unlock.
    • Event ids now commit in order per collection, so polling never skips a change.
    • The sweep waits a 48-hour grace period.
    • Paths are normalized and validated up front.
  • Last seen: each member's last_seen_at is updated when they open or poll the collection, at most every 10 minutes.
  • Starting a cloud collection (BL-16676):
    • An "initial upload in progress" flag hides a collection from the joinable list until the admin clears it.
    • While the flag is set, legacy:<old email> placeholder locks let old-system checkouts carry over; their owners take them over later with the GUID.
    • A service-role support function and script delete a failed migration.
  • CI: a db-tests job runs the pgTAP suite on every PR.

The contract the Bloom client follows is team-collections/docs/CONTRACTS.md v1.12. Nothing is live until someone applies the migration and sets the secrets on a hosted project.

Worth knowing

  • The support delete script has never actually deleted anything. Try it against a MinIO or sandbox bucket before relying on it.
  • Polls and writes in the same collection now briefly wait for each other (the event-order fix). That is cheap at Bloom's scale, but worth knowing if many members poll one collection.
  • A future realtime client shouldn't advance its cursor from realtime event ids, which can arrive out of order. Only polling is safe for the cursor.
