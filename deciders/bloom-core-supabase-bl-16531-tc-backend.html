What this PR is about

Problem

Cloud Team Collections (BL-16531) was built in BloomDesktop PR #8052, with its Supabase backend sitting in the Bloom Editor repo by mistake. The backend belongs in bloom-core-supabase so it can be reviewed, merged and deployed separately from the Bloom client. The client side, starting with the Share dialog (BloomDesktop #8394), is written against it.

What the PR does

It brings the backend over from #8052 with its behavior unchanged, fitted to this repo's conventions:

  • Database: the tc Postgres schema as declarative files in supabase/schemas/tc/, plus the initial migration generated from them. It covers collections, members and roles, books, checkouts and history, with row-level security and the RPCs the client calls. Its pgTAP tests run on Postgres 17 (the source used 15).
  • Edge functions: seven functions (two-phase check-in and download, and the stale-upload sweep), with names unchanged. Shared helpers are in _shared/tc/, the AWS SDK is pinned exactly, and the Deno tests moved to where CI runs them.
  • Local dev stack and ops: MinIO via compose, dev credentials, a smoke test, AWS provisioning and Firebase claim scripts, plus the contract, schema and go-live docs. All of it is under team-collections/.
  • Config: config.toml exposes the tc schema and seeds TC dev accounts. Existing functions are untouched. Also an AGENTS.md declaring the repo basics and the YouTrack tracker.

Nothing is live until someone applies the migration and sets the TC secrets on a hosted project.

Worth knowing

  • None of these problems is a regression from the port. The same code is in #8052, where only the final tree was ever tested.
  • Merging to develop deploys all seven TC functions to staging. Without the tc schema and secrets there they fail straight away, and existing functions are unaffected.
  • The edge functions haven't been served end to end here: the MinIO smoke test wasn't run. Only the unit and database tests ran.

Where to fix the backend problems the bots found

Devin and Greptile together raised about ten real problems in the backend logic, all carried over unchanged from #8052. Two are security holes: a member can call the internal "finish" functions directly and skip the server's check of what was uploaded, and a member can take over someone else's checkout by replaying machine details anyone in the collection can see. Several are races that can lose or overwrite work: the sweep, stale check-ins, lock acquisition, retries. Two are small operational mistakes: the S3 endpoint setting and missing IAM permissions. Some are one-line fixes; the security two and the sweep need design decisions. None of it is reachable until the schema and secrets are set up on a hosted project.

Deploying the TC functions to staging on merge

The staging and production workflows run supabase functions deploy with no names, so merging deploys all seven TC functions. Until someone applies the schema and sets the secrets, those endpoints just return errors. Existing functions are unaffected.

Run the database tests in CI

The 102 pgTAP tests pass locally but no workflow runs them, so a schema change could break them unnoticed. A CI job would start the local database in the GitHub runner, apply the migration, and run supabase test db.
