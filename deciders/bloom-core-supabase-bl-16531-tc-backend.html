What this PR is about

Problem

Cloud Team Collections (BL-16531) was built in BloomDesktop PR #8052, with its Supabase backend (database schema, edge functions, local dev stack) sitting in the Bloom Editor repo by mistake. The backend belongs here, so it can be reviewed, merged and deployed separately from the Bloom client. Reviewing the port turned up security and concurrency problems. A design review then reworked the data model so that changing your email loses nothing, and so that book names and retried check-ins can't cause conflicts.

What the PR does

  • Port: the tc schema as declarative files plus its generated migration, the seven edge functions, the local dev stack and support scripts under team-collections/, and a CI job running the database tests on every PR.
  • People: a core.users row per person with an id of Bloom's own; the sign-in token is looked up in it, and every lock holder, member and history author points at it. Rows are made only when needed, the name comes from Bloom's Registration dialog at each sign-in, and a support script moves a person to a new login.
  • Books are named by instance id everywhere. Their name is for display only and needn't be unique, and their version is a number per book.
  • Check-in: a start resumes an earlier attempt only if it is identical, and otherwise replaces it, so a finish only ever commits what its own start proposed. Finish rechecks the lock, the checkout GUID and the base version. Only the edge functions can commit uploaded files. The stale-upload sweep repairs S3 after failed check-ins and then forgets the attempts it has cleaned up.
  • Checkouts belong to one copy of a book: the client makes a GUID, and the server stores only its hash.
  • Starting a cloud collection (BL-16676): the collection stays hidden until the upload is done. Checkouts from the old folder Team Collection are locked to that person's email, and the lock becomes theirs at their first sign-in. A support script deletes a failed migration.
  • Collection files are one set per collection, sent only by admins. Last seen times feed the Share dialog.

The desktop client (#8052) still speaks the earlier v1.12 contract and needs the work in DESIGN.md §9 before the two can work together. Nothing is live until someone applies the migration on a hosted project.

Other:

Heads-up: an email another login already has

A person's user row keeps the email of the login that owns it. If someone signs in with a new BloomLibrary account whose email is the same as an existing row's, the server refuses to create or claim their row, answering email_in_use. The existing row belongs to another login, typically the person's own old account.

Bloom would then say nothing can be joined until the Bloom team runs the new move-user script (02_functions.sql:148). Taking the address over automatically would let whoever holds an email take someone else's collections, which is why the server refuses. This fits your "email changes stay a database-admin task" decision, so the recommendation is to leave it and have the client show a clear message.
