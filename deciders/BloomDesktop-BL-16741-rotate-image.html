What this PR is about

Problem

A picture that arrives on its side stays on its side. Bloom could crop a picture and move it, but it could not turn it, mirror it, or set an item on the page at an angle. An author with a photograph the camera saved sideways had to leave Bloom, turn the file in another program, and put it back.

What the PR does

  • Rotate right on the picture menu, shortcut Ctrl+R, turns a picture a quarter turn clockwise. An ordinary picture item turns as a box. A background image, which fills its page area and cannot turn as a box, has the picture inside it turned and shrunk to fit; that drops the crop, because the cropped region described the picture as it was. Neither path acts on a box that still holds the grey placeholder.
  • Flip, with Flip horizontal and Flip vertical, mirrors the picture. The two axes are the ones the user sees, whichever way the picture and its box have been turned.
  • A rotation handle on the control frame, a knob on a short stem above the top edge, turns the selected item to any angle. The angle snaps to every multiple of 45 degrees within 14 degrees of one, and the CTRL key turns the snapping off. An item whose outline comicaljs draws (a speech bubble, a thought bubble, a caption, a rectangle or an ellipse) gets no handle, because that drawn outline stays upright.
  • Dragging, resizing and cropping work on a turned item: mouse movement is converted into the item's own coordinates, and the item is shifted so that the edge opposite the one being dragged stays where it looks. Clicking picks the right item too, which comicaljs alone cannot do, because it tests the un-turned box. The control frame turns with the item, so its parts are corrected for the angle as well: each handle shows the cursor for the direction it really moves on screen, each tooltip is turned back so that the text stays level, and the mark that shows which side of a picture is cropped is measured from the laid-out sizes rather than from the upright box around the turned item.
  • Undo puts back a Rotate right, a Flip, and a drag of the rotation handle, one step for each command and one step for each drag.
  • Reset Image now clears the crop, the turn and mirror of the picture, and a transparency the user chose by hand, and puts the transparency back to Auto. It does not straighten a turned box, because that angle belongs to the box, as its size and position do. The picture menu is now in three groups with a line between them: which picture is in the box, how it sits in the box, and the rest.

Every angle and mirror lives in the item's own inline transform, which is saved in the book HTML, so it appears in BloomPlayer and in PDF output, where no Bloom JavaScript runs.

So on a page with four added items, one press turned the picture four quarter turns and left four undo steps. It is fixed. It is worth knowing because it is the kind of defect that a quick try never meets: with one item on the page the shortcut behaves perfectly.
  • Flip after a turn of the box was wrong until this run. On any branch build you tried before now, Flip horizontal on an item turned a quarter turn mirrored it from top to bottom. If you tested Flip earlier and thought it odd, that is why.
  • The unit tests are new ground for this code. Notes

What Flip should mean at an angle that is not a quarter turn

Flip mirrors the picture inside its box, and the two commands are named for what the user sees: Flip horizontal makes the left of the picture the right, on screen. Until this run the code worked that out from the turn of the picture only, so on an item whose box had been turned a quarter turn, Flip horizontal mirrored the picture from top to bottom instead. Devin found that, and it is fixed: the code now adds the turn of the box to the turn of the picture before it decides which axis of the picture to mirror.

That leaves one honest limit. A mirror of the picture can only be about one of the picture's own two axes, and on an item turned to, say, 37 degrees by the rotation handle, neither of those axes lies along the screen. The code takes the angle of the box to the nearest quarter turn and mirrors about the axis of the picture nearest the one you asked for. So at 37 degrees Flip horizontal mirrors about the axis that is 37 degrees off the screen vertical, not about the screen vertical itself. The result is a correct mirror of the picture, at a slightly unexpected angle. At every multiple of 90 degrees, which is where the snapping puts most items, it is exactly right.

Notes

Should Undo reach a turn after you select something else?

Turn an item with the rotation handle, then click on something else, then press Ctrl+Z. The turn is not undone. Select the turned item again and Ctrl+Z does undo it. Devin raised this, and it is a fair question rather than a defect.

The rule comes from the existing image undo records, which each ask that the selection is on the picture the record belongs to. It is one undo stack for each item, not one for the page. A turn follows the same rule. The argument for it is that Ctrl+Z then means "undo what I did to this item", which is predictable when several items are being worked on. The argument against it is that a user who turns an item, clicks away, and reaches for Ctrl+Z gets nothing.
