Pictures with a % or # in the name vanish from a published BloomPUB

What this PR is about

Problem

Publishing a book to BloomPUB silently dropped any picture whose file name contained a %, #, & or +. The page came out with a blank space where the picture should be, in the BloomPUB preview inside Bloom and in BloomPUB Viewer alike. Steve McConnel found this in 6.5.1322 while testing the earlier percent-in-filename fix, and gave the exact evidence: the file in the published book had been renamed to Restroom%41%42_r.jpg while the page still asked for Restroom%2541%2542.jpg. Ordinary names, spaces included, came through fine — which made it look narrower than it is: red & green.jpg and one+one.jpg were just as broken.

Cause

Publishing shrinks and re-encodes each image, which renames it (photo.png becomes photo_r.jpg), and then has to point the page at the new file. It did that by searching the page's style for the old name and substituting the new one — encoding both names with a different encoder than the one that wrote the style in the first place. The writing encoder escapes %, #, & and +; the searching one escapes none of them. So for any such name the search matched nothing, the page went on naming the file the resize had just replaced, and the picture was gone.

What the PR does

  • The publish step now replaces the url outright instead of hunting for the old name, so there is no old-name encoding left to get wrong. Anything else in the style is untouched. (BloomPubMaker.cs:511)
  • The two places in the same file that read a file name out of a page get the matching treatment — they were decoding in a way that turns a literal + in a file name into a space. (line 472, line 481)
  • A new test fixture publishes a picture under ten different awkward names and checks the page still points at a file that exists. Seven of the ten fail without the fix; the other three — a plain name, a name with spaces, an Amharic name — are there to prove nothing ordinary regressed. (CompressImagesTests.cs:55)

Worth knowing

  • This is not a regression from the BL-16669 fix that shipped. The faulty reference-rewriting came in with the line-art work (BL-16336) in June. It is a sibling of the percent-in-filename bug, found while testing that fix, which is exactly why it turned up on a build that already contained it.
  • Small images hide it completely. Nothing gets renamed unless the image really needs work — bigger than 1280×720, a photographic PNG worth turning into a JPEG, a format browsers can't show, or a page whose background colour needs the picture made transparent. A book of small pictures on white pages publishes correctly even without this fix, so reproducing it by hand needs a real camera photograph.
  • ePUB was never affected, and needs no matching change. That path replaces %, &, + and spaces with _ in the file and the reference together, so the two cannot drift apart.
  • The duplicate-media tidy-up that runs immediately after was also fine. It already goes through the proper url-handling helpers, so a reviewer wondering whether it shares the flaw can stop there.
  • Nobody has published a real BloomPUB from this branch by hand. The coverage is a unit test over the publish step, which is where the defect was; the end-to-end path has not been exercised. That is the first decision on the right.

Confirm the fix in a real publish?

The new tests drive the exact publish step that was broken, and they fail without the fix — so the mechanism is genuinely pinned. What has not happened is somebody starting Bloom from this branch, putting a large percent-named photograph in a book, publishing a BloomPUB, and looking at it. That end-to-end path involves a few more moving parts than the test covers (the book gets copied to a temp folder, the html is rewritten, everything is zipped), and a mistake in any of them would look exactly like the bug we just fixed.

Recommending “leave as is” because the test exercises the one step that was wrong, and the QA notes on the card already ask a tester to publish exactly this case — with real photographs, which is what makes it reproduce.

The other half of Steve's report lives in Bloom Player

Steve also found that a game sound whose name contains a % stays silent when you actually play the game — and, importantly, that this happens in the Bloom editor too, not only in a published book. That is worth knowing because the QA notes on the card currently claim the in-editor case was fixed; it was not.

The reason is that playing a game, in either place, runs Bloom Player's code, which builds the sound's web address by pasting the raw file name on the end without escaping it. Bloom then goes looking for BeepA.mp3 and finds nothing. Setting the sound in the Games tool does play it, because that button uses Bloom's own code, which escapes properly — which is exactly the split Steve observed. This is already filed as BL-16688; the question is whether to do it now.

Steve couldn’t find the click-sound setting because it’s gone

Steve asked whether canvas element click sounds — the sound you attach to a picture so it plays when a reader touches it — still exist, saying he couldn’t work out how to set one. He couldn’t because the menu item that sets it now only appears when the picture is on a draggable game page. On an ordinary page there is no longer any way to reach it.

This came in with the canvas-controls rework in February and looks like an accident of that change rather than a decision: nothing else about the feature was removed, the setting is still read and still plays, and books that already have one still work. It is unrelated to this PR — it only surfaced because Steve was testing sounds.
