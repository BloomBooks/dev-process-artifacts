What this PR is about

Problem

Two unrelated faults, both found by Steve McConnel while testing the earlier percent-in-filename fix in 6.5.1322.

Pictures went missing from published books. Publishing to BloomPUB silently dropped any picture whose file name contained a %, #, & or + — a blank space where the picture should be, in Bloom's own preview and in BloomPUB Viewer alike. Steve gave the exact evidence: the file in the published book had been renamed to Restroom%41%42_r.jpg while the page still asked for Restroom%2541%2542.jpg. Ordinary names, spaces included, came through fine, which made it look narrower than it was: red & green.jpg and one+one.jpg were equally broken.

A picture's click sound could not be set at all. Steve asked whether the sound that plays when a reader touches a picture still existed, because he could not work out how to set one. He couldn't: the menu item had been reachable only on draggable-game pages since the canvas controls were reworked in February, so on an ordinary page there was no way in.

Cause

The first is an encoder mismatch. Publishing shrinks each image, which renames it, and then has to point the page at the new file. It did that by searching the page's style for the old name and substituting — encoding both names with a different encoder than the one that wrote the style. The writing encoder escapes %, #, & and +; the searching one escapes none of them. So nothing matched, and the page went on naming the file the resize had just deleted.

The second was a one-condition oversight: the flag deciding whether to offer the click sound was gated on the page being a draggable game, rather than on the thing selected being a picture.

What the PR does

  • Publishing now replaces the url outright rather than hunting for the old name, so there is no old-name encoding left to get wrong. Anything else in the style is untouched. (BloomPubMaker.cs:511)
  • The two places in the same file that read a file name out of a page get the matching treatment — they were decoding in a way that turns a literal + in a file name into a space. (line 472, line 478)
  • Any picture can take a click sound again, on any page. Text is deliberately left alone: it never had a click sound, and its form of that menu item does something else entirely — it points at the Talking Book tool. (buildCanvasElementControlRegistryContext.ts:216)
  • Tests for both. The publish one puts a picture through ten awkward names and checks the page still points at a file that exists — seven fail without the fix (CompressImagesTests.cs:55). The menu one covers picture and text, on a game page and an ordinary one, and the page's background picture; only the "picture on an ordinary page" case fails without the fix (its tests).

Steve's third finding — a game sound with a % in its name staying silent when you play the game — is Bloom Player's, tracked as BL-16688, and is deliberately not in this PR.

Worth knowing

  • The publish fix has been confirmed by hand — you tested it, so the end-to-end path is no longer resting on the unit tests alone.
  • Neither fault is a regression from the BL-16669 work that shipped. The faulty reference-rewriting came in with the line-art work in June; the click-sound gate came in with the canvas-controls rework in February. Both surfaced while testing that fix, which is why they turned up on a build that already contained it.
  • Small images hide the publish bug completely. Nothing gets renamed unless the image really needs work — bigger than 1280×720, a photographic PNG worth turning into a JPEG, a format browsers can't show, or a page whose background colour needs the picture made transparent. Reproducing it by hand needs a real camera photograph.
  • ePUB was never affected and needs no matching change. That path replaces %, &, + and spaces with _ in the file and the reference together, so the two cannot drift apart.
  • The click-sound change alters which items a picture's menu offers, and that menu also carries Choose image, cropping, copyright and the game commands. The tests cover the sound item; the rest of the menu is only covered by eye. It is called out in the QA notes for that reason.

Should a page's background picture offer “play when touched”?

You asked to broaden the click sound to all image overlays, which is done. Devin then pointed out that gating on “has a picture” also reaches the background picture — the one filling the whole page behind everything else — and not only the pictures sitting on top of it. So on an ordinary page you can now attach a sound to the page's background picture, and touching anywhere in the picture plays it.

Two things make this less clear-cut than it looks. It was already the case inside a draggable game: the old condition had no background-picture exclusion, unlike the draggability check immediately above it, which does exclude it explicitly. So this is the same behavior now reaching ordinary pages rather than something new. And attaching a sound to a full-page picture is a plausible thing for a book maker to want — touch the picture, hear the word. Against that, “overlay” in your instruction reads more like the pictures on top than the background itself, and the codebase does distinguish the background picture where it matters.

Whichever way this goes, the behavior is now pinned by a test, so a change here is a visible edit rather than a silent drift.

Recommending “leave as is” because excluding it would be the only place in this PR that removes something currently available, and it is a reasonable thing to want. The open Devin thread gets your reasoning either way.
