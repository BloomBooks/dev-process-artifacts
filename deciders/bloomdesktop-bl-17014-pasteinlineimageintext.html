What this PR is about

Problem

Pasting a picture into a text block pasted the picture's file path as text instead of the picture. Most ways of copying a picture (Bloom's own Copy Image, a file copied in Explorer, a browser's "Copy image") put the path on the clipboard beside the picture, and the browser pasted the text. The Paste button sent the picture to the page's canvas instead.

What the PR does

  • Pasting a picture (Ctrl+V or the Paste button) into an ordinary text block adds it as an inline image, where Insert Image puts one. With an inline image selected, the paste replaces its picture. One Undo takes the paste back, and a save made before the picture arrives waits for it. A clipboard holding formatted text (Word, Excel) still pastes as text. (Stephen's work, in inlineImagePaste.ts.)
  • A new end-to-end test pastes a picture into a text block and checks that it becomes an inline image in every language, the file reaches the book folder, no path goes into the text, and the saved book has it.
  • So that the test touches nobody's clipboard, Bloom uses an in-memory clipboard when it runs under --e2e. All of Bloom's C# clipboard calls go through a new BloomClipboard, and the page's through utils/bloomClipboard.ts. A build ban and a lint rule keep it that way, and a new e2e/clipboard hook lets tests fill and read it. In a normal run they call the same clipboard functions as before.

Worth knowing

  • Nobody has used Copy, Cut and Paste in a normal Bloom since they moved behind the wrapper. They should behave as before, except that the first clipboard use on a page now waits for one local request. The card's test ideas ask a tester to check them.
  • The test pastes by sending the paste event Ctrl+V produces, not by pressing Ctrl+V, because a real Ctrl+V makes WebView2 read the Windows clipboard. Specs that press the real keys still use the Windows clipboard; AUTOMATION-DEBT.md records this.
