What this PR is about

Problem

Pasting a picture into a text block pasted the picture's file path as text instead of the picture. Ctrl+V in a text block is left to the browser and CKEditor, and most picture copies (Bloom's own Copy Image, a file copied in Explorer, a browser's "Copy image") put the path or URL on the clipboard as text beside the picture, so the text is what got pasted. The top-bar Paste button sent the picture to the page's canvas instead, or pasted the same text.

What the PR does

  • With the focus in a text block that can take inline images, pasting a picture (Ctrl+V or the Paste button) adds an inline image holding it to that block, docked right at the start of the block, where Insert Image puts one.
  • It reuses the canvas paste's round trip, so there is no C# change: JS asks C# for the clipboard picture with an id unique to that paste, and C# copies it into the book folder and calls changeImage with the id. The image appears only once the picture has arrived, so a failed or cancelled paste leaves nothing, and one Undo takes back the whole paste. A save made in the meantime waits for the picture.
  • A clipboard with formatted text as well as a picture (Word, Excel, part of a web page) still pastes as text.
  • Blocks that can't take inline images, and a paste with a canvas picture selected, behave as before. The Paste button with the focus in an ordinary text block now adds an inline image there instead of pasting onto the canvas.

Worth knowing

  • Checked by hand in a running Bloom: Ctrl+V of an Explorer file copy and of a Bloom-style picture plus path, the Paste button (before and after the focus change), and a Word-style clipboard (left as text). Not checked by hand: a paste with a canvas picture selected (unit-tested only), a screenshot or browser "Copy image", and declining the JPEG warning.
  • With a Reader tool (Leveled or Decodable) open, Ctrl+Z in the text goes to the Reader tool by design (onUndoOrRedoKeyDown), so it does not take back a pasted picture; the Undo button does. Insert Image has always behaved the same. See the second decision.

With an inline picture selected, should pasting a picture replace it?

Clicking an inline picture selects it without taking the focus out of its text block. So if you select one and press Ctrl+V with a picture on the clipboard, this PR adds a second picture to the block and leaves the selected one alone. On a canvas, pasting onto a selected picture replaces it (BL-16542), and an inline picture's own toolbar already has a "Paste image" button that replaces it. Before this PR, the same keystroke pasted the file path as text.

File a card for the Reader tools' Ctrl+Z with inline pictures?

With the Leveled or Decodable Reader tool open, Ctrl+Z in the text is taken by the Reader tool for its own history, so it doesn't remove an inline picture just added (pasted or inserted); only the Undo button does. During the live check, that Reader-tool undo also put back a hidden CKEditor bookmark (an invisible cke_bm span that looked like an extra space in the text), which would have been saved into the book. Both predate this PR and are outside its scope.
