What this PR is about

Problem

In a debug build, selecting another book in the Collection tab while its preview is still loading a large picture (2 MB or more) pops up "Debug.Assert failed: (Debug Only) Cannot close stream until all bytes are written." In a release build the exception is only logged.

Cause

RequestInfo.ReplyWithFileContent() sends files of 2 MB or more in 512 KB pieces. It sets Content-Length first, then reopens the file between pieces. Book pictures are served from the runtime image cache, which Bloom clears (deleting its files) whenever the selected book changes. When the reopen found the file gone, the loop stopped early and OutputStream.Close() threw InvalidOperationException because fewer bytes had been written than promised. That exception reached the catch-all in BloomServer.RequestProcessorLoop(), which calls Debug.Fail.

What the PR does

  • The piece-by-piece copy is now WriteFileInPieces(). It is given the Content-Length, reports whether it wrote exactly that many bytes, and stops once it has. So a file that disappears during its last piece still gets a complete reply, and a file that grows never writes past the promise. A missing folder counts the same as a missing file, and a file that got shorter counts as incomplete.
  • When the file could not supply the promised length, ReplyWithFileContent() logs it and aborts the response instead of closing it. The browser sees a dropped connection for a picture it no longer shows. The request is still marked as fully processed.
  • Six unit tests in RequestInfoTests cover the file staying put, the file or its folder deleted after the first piece, the file deleted during its last piece, and the file getting shorter or longer part way through.

Worth knowing

  • Nobody has run the fix in a live Bloom. The failure needs a book with pictures over 2 MB and a book switch in the middle of a transfer, so the evidence is the unit tests plus the full suite. The QA test ideas on the card cover checking that big pictures and videos still load normally.
  • If a deleted file is still held open by another program, Windows can refuse the reopen with an access-denied error instead of "not found". That case still escapes as it did before this PR. It needs a non-NTFS drive or an old Windows, and nothing in the card's log shows it.
