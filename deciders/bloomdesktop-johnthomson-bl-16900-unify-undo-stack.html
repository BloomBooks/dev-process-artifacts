What this PR is about

Problem

Ctrl+Z did nothing after a table operation such as adding a row, though the Undo button took it back. And after "add a row, type in it, click another cell", Ctrl+Z and Undo took the row away with the text typed in it, which could not be brought back.

Cause

  • CKEditor handles Ctrl+Z in a text block and knows nothing of Bloom's undo stack; the page took the key first only for inline-image changes.
  • Once the toolbox loaded the reader settings, ReaderToolsModel.restoreState set a reader markup type on every page, so the reader tools claimed the undo keys with no reader tool open.
  • The stack asked CKEditor only about the focused box, so typing in a box the person had clicked out of was invisible, and the older row went first.

What the PR does

  • The page's undo keys live in undo/undoKeys.ts: Ctrl+Z is taken for any entry on the stack, and for typing in a box other than the focused one; one Ctrl+Y handler replaces the separate binding.
  • The undo of typing goes to the box whose typing is newest, wherever the focus is (undo/ckeditorChanges.ts). Each box's latest change has its place in the order the stack's entries share, so typing and table changes are undone in time order. A first paste or cut is recorded once CKEditor has saved it, and every box with typing keeps its place, however many change. No typing undo in Change Layout mode.
  • restoreState no longer sets the markup type.

Worth knowing

  • The CKEditor undo provider is on the Undo button's path for all typing, and now chooses the box and the order differently. That is the part to read hardest; ckeditorChangesSpec.ts lists the cases.
