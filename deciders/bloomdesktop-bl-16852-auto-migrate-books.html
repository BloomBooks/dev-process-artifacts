What this PR is about

Problem

Old books reach the editor and the publish path with most pages un-migrated. Many DOM fix-ups — notably converting a legacy image to the 6.3+ background canvas element, and computing layout-derived image and canvas measurements — run only when a page is actually opened for editing. So on an old book the AI image editor found only the images on pages that happened to have been opened, and publishing could ship un-migrated pages. In the reported case a dictionary showed far fewer images than it has, and different runs found different subsets.

What the PR does

It applies those per-page fix-ups to the whole book automatically, when needed, at the points where it matters. The heavy lifting reuses BookProcessor.ProcessBook — the off-screen per-page pass that "Update Book" and BloomBridge already use — so this PR adds the "is it needed, and if so run it behind a progress dialog" layer around it.

  • Detection. On a successful run ProcessBook stamps two <meta> values: the Bloom version and the page size it ran at. NeedsPerPageFixup is due when the book is unstamped, stamped by an older Bloom, or stamped at a different page size; it is skipped for a book that cannot be saved or has structural errors.
  • Running it. EnsurePerPageFixupIfNeeded runs the pass behind a modal progress dialog (a determinate percent bar and a one-line explanation), and remembers a per-book failure so it does not re-prompt every tab switch.
  • Where. Called when a book is opened for editing, before the publish tab goes live, and after a page-size change. All three are deferred off Bloom's API sync lock so the off-screen pages' own API calls don't block behind them.
  • Interplay with the AI image editor's size hints (PR 8359, now merged in). That PR writes each image slot's share of its page whenever a page is saved and falls back gracefully when it is absent. Because this PR re-saves every page before editing or publishing and after a page-size change, the value is always present in normal operation; 8359's fall-backs are kept as hardening and their comments now say so.
  • Strings. One translate="no" entry in BloomMediumPriority.xlf.

Worth knowing

  • Live check of the final edit-open and page-size flows is pending. The exclusive-access fix changes when the first page appears (after the dialog, not before). Unit fixtures pass and the design mirrors the already-verified Publish gating, but the two flows have not yet been re-watched on a running Bloom since that change (the developer's concurrent testing pre-empted the scripted check); the developer's current instance runs this build.
  • Live-tested end to end. Opening for edit, changing page size, and switching to Publish each run the fix-up and stamp the book correctly; an image-heavy 20-page book completes in ~30s with no stall after the lock fix; an already-migrated book is a no-op.
  • One residual, low-risk. ProcessBook's BringBookUpToDate raises BookRefreshEvent on the background worker thread. For the edit sites an existing guard short-circuits it; on the publish tab EditingModel.Visible is false so it touches no UI. No crash path was found, but it is fragile against future tab-order changes.
  • Pre-existing, not this PR: a book on the legacy-5-6 appearance theme can be switched to a page size its frozen stylesheet doesn't define (e.g. Ebook 7x5); the pages and thumbnails then render with zero height. Verified in source: basePage-legacy-5-6 has no Ebook7x5Landscape rule, and the size list isn't filtered by theme. Switching back restores it; worth its own card.
  • Team Collection books not checked out are skipped (they can't be saved). Per the developer, such books can't be published anyway, so this is not a gap.

Decision — settled

Failed migration still lets you publish

Decided: leave as is. Recorded on the review thread and resolved. No action needed.

When ProcessBook throws (e.g. a page times out), the modal shows the error, then publishing continues on the not-fully-migrated book, and the per-session failure cache means later Edit/Publish activations skip the retry until Bloom restarts. Devin rates this severe.

Devin: "When ProcessBook fails, EnsurePerPageFixupIfNeeded returns normally and publishing continues with unprocessed pages. The failure cache also suppresses later attempts."

My read: factually correct, but not a regression — before this PR every book published straight from its on-disk DOM, so a failed migration just falls back to the prior behavior, and the user has already seen an error. Blocking publish outright would make a book with any un-migratable page impossible to publish. "Update Book" is also a manual retry that ignores the cache.
