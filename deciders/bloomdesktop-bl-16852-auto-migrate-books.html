What this PR is about

Problem

Many of the fix-ups a page needs happen only when that page is opened in the Edit tab: converting an old-style image to the 6.3+ background canvas element, recording each image slot's share of its page, canvas-element geometry. They need a real browser that has laid the page out, so nothing else applies them, and a book carries them on the pages someone happened to visit and nowhere else.

That is what BL-16852 reported. The AI image editor works across the whole book and sizes each image from the share-of-page its slot records — data only those fix-ups write. On an old dictionary it found a fraction of the images, and different runs found different subsets.

What the PR does

It gives Bloom a way to know whether a book has been through those per-page fix-ups, and runs them over the whole book, off-screen, when something actually depends on them.

  • Detection. A new kBrowserMaintenanceLevel, beside the existing kMaintenanceLevel and kMediaMaintenanceLevel, records how far a book has been taken. ProcessBook stamps that level and the page size it ran at into the book's HTML; the pass is due when the book records no level, a lower one, or a different page size. Deliberately not a Bloom-version comparison: version numbers are not comparable across channels, and keying off them would reprocess every book on every build.
  • A level from the future comes back down. A book a newer Bloom took past what we produce cannot go on claiming that level once we write it, because the pages we add would never get that Bloom's extra fix-ups. Saving brings the record down to ours, so the newer Bloom sees the book as due again. One-way — a level at or below ours is left alone.
  • Where, in 6.5. Launching the AI image editor (which empties the editor, runs the pass behind a determinate progress dialog, then returns to the page) and changing the page size. Entering the Edit or Publish tab deliberately does not; that is held for 6.6 under BL-16877.
  • Strings. One translate="no" entry in BloomMediumPriority.xlf.

Team Collection books that are not checked out are skipped, since they cannot be saved.

Decision 1

The page-size trigger runs the whole-book pass while a page is still on screen

When you change a book's page size, Bloom now runs the whole-book update right then. Everywhere else this feature runs, it first empties the editor — no page, no thumbnails — because the update rewrites the book's pages from a background thread and must have the book to itself. The page-size path does not: it navigates to the page you were on and starts the update alongside it.

Both reviewers flagged this independently. The local pass identified a specific mechanism: every page the update loads off-screen is a full editing page that reports itself as loaded, and Bloom accepts such a report whenever it is expecting a page load and the page id matches — which it does for exactly one off-screen page, the one you are sitting on. So the off-screen copy can be mistaken for the real one, and work queued for the real page load is consumed and never runs. The AI-editor path is immune only because emptying the editor first makes Bloom ignore those reports. Two lesser consequences follow: the update starts by bringing the book structurally up to date, which the page-size code itself elsewhere describes as invalidating the page objects it is holding; and nothing refreshes the editor or thumbnails afterwards, so they can keep showing the pre-update version.

Not observed in live testing — changing page size worked and stamped correctly — but it is a timing-dependent fault, which is exactly the kind that does not show up on demand.
