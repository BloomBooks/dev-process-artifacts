What this PR is about

Problem

On the very day a subscription expires, Bloom contradicts itself. The Bloom Subscription tab of Collection Settings says the subscription is still good — green tick, tier, “Expires: today” — along with a yellow warning that it expires today. But subscription-gated features, the Canvas tool most visibly, are already switched off telling the user the subscription isn’t valid. Confirmed in 6.4.

Cause

The two sides compare different things. The dialog compares whole dates, so a subscription is good through the end of its expiration day. The C# compared a date to a timestamp: the stored expiration date is midnight at the start of that day, so from 00:00 the code counted as expired and the tier dropped to Basic — and it is the tier that turns the tools off.

What the PR does

  • A subscription is now valid through the end of its expiration date everywhere: the expiry check compares whole dates (Subscription.cs:212).
  • The tier calculation now calls that same check instead of repeating the comparison, so there is one definition of “expired” rather than two that can drift apart (Subscription.cs:397).
  • The Settings dialog and the collection-tab status banner worked out “today” in UTC while the C# used the computer’s local clock — a smaller version of the same disagreement that shifts the boundary by up to a day for users far from UTC. Both now use a shared local-date helper (subscriptionCodeControl.tsx:216).
  • New tests pin the day boundary — expires tomorrow, today, yesterday — asserting both the expiry answer and the resulting tier, so a later change can’t quietly move the cutoff back (SubscriptionTests.cs:95).

Worth knowing

  • The one red test is a documented flake, not this change. ExportEpubTests.ConflictingIds_AreNotConfused died on “Failure to completely load visibility document”. The repo’s own MakeEpubWithRetries helper documents exactly that message as the known failure mode and notes that “two tries were needed at least once per run on average”. It passes when run alone, the full suite was green one commit earlier, and nothing in the diff touches ePUB export.
  • Nothing here has been exercised by hand. Seeing the bug or the fix needs a subscription code that expires on a chosen date, or the machine clock moved. The QA notes on the card spell out how; the time-zone cases in particular are unlikely to get covered by accident.
  • A time-zone behavior change rides along. Switching the two status displays from UTC to the local date is correct and is what makes the fix hold everywhere, but it changes what those displays do for users far from UTC — a slightly wider blast radius than the headline fix.

Leaving Bloom open across midnight

DecidedLeave as is — “not a serious enough problem to fix, in relation to all the other work we want to do.” Recorded on the review thread (now resolved) and in the QA notes on the card, so a tester won’t file it as a new bug.

Devin raised this, and it is real. Bloom works out which subscription tier you have once, at the moment it opens the collection, and every feature gate reads that stored answer. So if someone leaves Bloom running overnight on the day their subscription runs out, the paid tools keep working past midnight until they restart or reopen the collection.

The important qualifier: this PR does not introduce it. The tier has always been computed once at construction, so a session spanning the old cutoff behaved exactly the same way. This change moves which midnight matters by one day; it does not make the staleness better or worse. Fixing it properly means making the expiration-sensitive checks re-read the clock, or adding something that invalidates the subscription at midnight — either of which reaches every consumer of the tier.
