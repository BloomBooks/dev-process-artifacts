Decision 1 · from Devin

A QR-code bug in someone else's merged change

Devin reported one Bug against this PR, "Failed QR writes leave broken badges". When Bloom fails to write a QR code image, the code still hands back that image's file name, so the "Made with Bloom" badge can end up pointing at a picture that is missing, or at the QR code for a different language. Devin's example: a book switches from English to Thai while the image file is locked, so the badge shows the Thai address but scanning the unchanged picture still opens the English one.

The catch is that this is not code this PR changes. It lives in BookStorage.cs, it arrived from PR #8420 (BL-16930, "Don't let a failed QR code write stop a book from opening"), and it is already merged into Version6.4. Devin only saw it because this run merged the base into the branch. It is already written up on the PR with that assessment, so the record exists either way. The question is only whether it deserves its own card.

Decision 2 · from the local review

A shortcut in the xMatter folder can crash Bloom

Bloom works out an xMatter pack's name by finding -XMatter in its folder name and keeping everything before it. If that text is not there at all, the search reports "not found" and the code then asks for a negative number of characters, which throws. In normal use this cannot happen, because Bloom only looks at folders it found by searching for names ending in -XMatter.

There is a second way in, though. XMatterPackFinder also follows any Windows shortcut sitting in the xMatter folder and accepts whatever folder it points at, without checking the name. So a shortcut pointing somewhere ordinary makes XMatterInfo.Key throw. This is long-standing and not something this PR introduced; the Thai fix does not change it either way. It surfaced because the review was looking hard at this exact line.
