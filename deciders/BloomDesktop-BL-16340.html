What the change does

Pressing Cancel asks the upload to stop; it notices between stages, which is why a long stage like making the PDF still finishes first. The screen greys out UPLOAD BOOK the moment you press Cancel, and the only thing that un-greys it is C# reporting how things ended. The bug was that sometimes that report never came: the upload ran to completion, published the book, and left the button dead with no way back.

  • The Cancel request queued behind the work it was interrupting. It ran on the UI thread and took Bloom’s global API lock — both busy for minutes during an upload. It now jumps that queue, like Bloom’s other cancel endpoints.
  • A cancel during the two set-up round trips was discarded, because the upload request began by clearing the flag. It is cleared at the true start of an attempt now, and a late upload request declines to run.
  • The screen is always told how things ended, on every route out — success, failure, exception, or the book being rejected before it started.

Two things the review added: a cancel that lands after the book is genuinely on BloomLibrary now reports success rather than claiming cancellation, and the collision dialog’s “different book” button no longer rewrites the book’s identity on disk for an upload it then declines.

Decision 1 · Devin bug, thread open

The “already on BloomLibrary” dialog after you cancel

When you press UPLOAD BOOK, Bloom asks the server two questions before the upload really begins — one being “is there already a copy of this book up there?”, which can be slow. Cancel is showing during all of it.

Cancel during that check and the check still finishes, so the “this book is already on BloomLibrary” dialog pops up anyway — after you cancelled. Pressing Upload in it reports the cancellation again rather than uploading.

I have already fixed the damaging half: the dialog’s “these are different books” button used to give the book a brand-new identity on disk and then decline to upload, leaving it permanently altered for nothing. What is left is purely what the user should see.

Decision 2 · 3 Devin threads open

The first moments of an upload are still fuzzy

Three of Devin’s open findings are really one problem: Bloom shows the Cancel button the instant you click UPLOAD BOOK, but the server doesn’t consider the attempt started until its first request arrives. In that gap:

  • A Cancel pressed in the very first instant can overtake that first request and be wiped out by it — so the book uploads anyway. (Before this branch, a cancel anywhere in the whole two-round-trip window was discarded, so this is a much smaller version of the same thing.)
  • Cancelling in that window can print two identical “Upload was cancelled” lines.
  • A cancel arriving when the server thinks nothing is running is deliberately silent, which in a rare ordering can leave the button greyed with nothing left to re-enable it.

Patching these one at a time is what produced the last two rounds of churn; they pull against each other, which is why they are here as one question.
