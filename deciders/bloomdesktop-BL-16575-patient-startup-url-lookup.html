What this change does

The startup URL lookup used a single 2.5s-per-attempt / 3s-overall budget regardless of who was asking. On a slow connection it routinely lost that race, which is the source of BLOOM-DESKTOP-ERZ / -2H2 (~889 events / 141 users in 90 days) — with no user-visible symptom, because Bloom just carries on with the built-in fallback URL. Rather than suppress the reports (the approach in the now-closed #8082), this makes the lookup likely enough to succeed that a remaining report is worth reading.

Per attemptRetriesOverall ceiling
Background (startup; supplies acceptFinalUrl) 10s 2 40s
Blocking (acceptFinalUrl == null) 2.5s 1 3s — unchanged

Nothing waits on the background retrieval, so it can afford patience. The blocking path is often on the UI thread (Help menu, login, the too-new-book-format message), so it still gives up fast rather than freezing Bloom. Sentry reports are kept but fingerprinted and tagged, so an old-version event, a long-timeout failure and a short-timeout failure are three distinguishable things.

2. Is 40 seconds the right amount of patience?

You asked for a startup budget generous enough that the lookup is unlikely to fail when the computer is online and the server is working. I picked 40 seconds overall, made up of three attempts of 10 seconds with room for the SDK's backoff between them. That number is a judgement call, not a derived one. Nobody waits on it — it runs on a background thread while Bloom carries on — so the cost of it being too large is only that a doomed attempt keeps a thread and an S3 client alive a bit longer, and that a genuinely-offline machine takes 40s to conclude it is offline. The cost of it being too small is that we keep getting the Sentry noise this card is about.

3. A blocking caller still fires its own duplicate request

If you click something that needs a URL right now — a Help menu link, signing in, submitting a problem report — while the background retrieval is still running, Bloom does not wait for that in-flight request. It starts a second, independent one with its own short 3-second budget. This is pre-existing behaviour (the original author explicitly decided locking was not worth it), but this change widens the window in which it can happen from about 3 seconds to as much as 40, so it will now happen far more often. In practice the cost is one extra anonymous download of a small JSON file. The upside of leaving it is real: it guarantees a blocking caller is never made to wait for the patient budget, which is exactly the freeze we are trying to avoid.

4. A corrupt server response still gets read as "no internet"

The failure handler treats every exception the same. If the file we download is fine but its contents will not parse — bad JSON, say, because someone published a broken file — Bloom sets its internal "no internet" flag for the rest of the session, which switches off other online features, exactly as if the network had been unreachable. That is pre-existing behaviour and this change does not make it worse. It is now at least visible: because the Sentry fingerprint includes the exception type, a parse failure lands in its own bucket rather than hiding among the timeouts, so you would be able to tell the difference when reading reports.

5. FYI — the blocking path's retry can almost never happen

The short path allows one retry, but its single attempt may take up to 2.5 seconds inside a 3-second overall ceiling. So a retry only ever gets to run if the first attempt fails almost instantly — a DNS failure, or a refused connection. If the first attempt genuinely times out, the overall ceiling stops everything before a second one could accomplish anything. This is unchanged from before and is deliberate (responsiveness beats success rate on a path where Bloom is frozen); it is now written down in the code. Raising it here would mean accepting a longer freeze, which is the opposite of what this change is for.
