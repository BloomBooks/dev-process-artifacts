What this PR is about

Purpose

Bloom Library is about to link book downloads (and later read-online files) as api.bloomlibrary.org/v1/fs/... URLs. Today every such request costs a Supabase call, a Parse lookup and an S3 fetch. If the URL carries the time the file last changed, the URL always names the same bytes, and Cloudflare can serve repeat requests from its cache.

What the PR does

  • Two versioned forms: ?v={epochMs} for downloads, and {bookId}@{epochMs} in the path for read online, so a book's relative links carry it. The version is stripped before calling fs (today the @ form 404s).
  • The fs lookup is cached (Cache API, keyed on path, version and Origin, since fs's CORS answer depends on it), so repeat requests make no Supabase call. Only GET/HEAD use it, and only lookups that found a file are stored.
  • The file is cached a year through Cloudflare's normal cache (2xx only), with ?v= on the S3 URL as the per-version cache key (S3 ignores it; a custom cacheKey needs Enterprise). Tiered Cache, Range and HEAD are handled by Cloudflare.
  • Response headers: Cache-Control: immutable, X-Bloom-Fs-Lookup: cached|fetched, and for downloads a Content-Disposition naming the S3 object, so titles with +, % or non-ASCII characters download under their real names.
  • Unversioned URLs are unchanged (OPDS, older links, Bloom Reader, the thumbnail rule).
