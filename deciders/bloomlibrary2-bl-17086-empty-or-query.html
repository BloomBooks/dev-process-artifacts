What this PR is about

Problem

The production Parse server logs about 750 errors a day: $or argument must be a non-empty array. They come from the website. The cards on the Resources page, and any other collection with no filter anywhere, ask Parse for a book count or for stats with a query MongoDB rejects. The count is then blank, or the stats fail. This went unnoticed for years (BL-13026, now closed as a duplicate, saw it in 2024), because the website hides a failed query and nothing reported it.

Cause

A collection with no filter of its own gets one built from its child collections' filters (BL-10187, 2021). When none of those children has a filter either, the website still built an empty "any of these" filter, and Parse got an empty $or. The earlier fixes that skip the query for a collection with no filter (BL-9742 for the book count, BL-10126 for stats) relied on getting no filter at all, which this code had stopped returning.

What the PR does

The PR has two commits, kept separate on purpose: the first is the fix, the second adds the error reporting.

  • getFilterForCollectionAndChildren returns no filter when nothing in the collection's tree has one, so the book count, stats and moderator widget skip the query again.
  • The :language: subset page uses a filter that matches no books in that case. Otherwise it would list every book in that language.
  • As a backstop, constructParseBookQuery turns an empty "any of these" into "match no books" (objectId $in []), not an empty $or.
  • Every server error (5xx) a request from the site gets is now reported to Sentry, once per distinct failure per page load. The report carries the method, path, server message and query, but never the headers (session token) or any request body that isn't a Parse query (such as login's, which holds the Firebase token). This is one axios interceptor, installed in src/index.tsx.
