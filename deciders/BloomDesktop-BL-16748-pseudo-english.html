What this PR is about

Problem

Nothing in Bloom shows which on-screen strings actually go through localization. A hard-coded string, a mangled placeholder, a label the layout will clip once the text grows — all of it looks fine in English, and only surfaces when a translator or a user in another language hits it.

What the PR does

On the developer and alpha channels, the UI Language menu now offers Pseudo-English (i18n test). L10NSharp 10.1.0-beta0001 transforms the live English at lookup time for the standard qps-ploc pseudo-locale — each vowel doubled and accented, the whole string bracketed, so Title Missing becomes [Tîitlée Mîissîing]. A tester then reads the problems straight off the screen: plain English means the string was never internationalized, a visible {0} or %0 means a broken placeholder, a missing ] means truncation, brackets mid-sentence mean the sentence is concatenated at runtime, and clipped layout means we cannot absorb the ~30–40% growth real translations bring. No qps-* translation files exist or are ever written.

  • The locale is turned on for the developer and alpha channels only, and a stored qps-ploc is refused on a channel that does not offer it — otherwise a setting carried over from an alpha would leave a release user with a mangled UI and no menu entry to escape it. Because the previous version's settings are migrated after that point, and the migration's Reload() discards the corrected value, the same guard (RefusePseudoLocaleWhereNotOffered) is re-applied once migration has run.
  • WorkspaceView names the locale itself (Palaso's language-name lookup has nothing useful to say about a pseudo-locale) and puts it last in the menu rather than sorting it among real languages.
  • I18NApi pseudolocalizes the English fallback it returns for ids that are not in the English XLIFF. Without this those come back as plain English and are indistinguishable from hard-coded text, which defeats the exercise.
  • The locale is excluded from the two places where the list of available localizations feeds book data rather than the UI: the pre-translated content TranslationGroupManager writes into a new book, and the hint-bubble language chooser.
  • Several UI strings mark their hyperlink words with [square brackets]. Because pseudo-localization brackets the whole string as well, the five parsers that took the first [ and the next ] swallowed the sentence into the link and ate the wrapper — making those strings look un-internationalized, which is the one thing this locale must never get wrong. A shared findLinkTextBrackets() now anchors on the first ] and takes the nearest [ before it, and the markdown link regex no longer allows [ inside link text.
  • DistFiles/localization/README.md documents that the locale is runtime-derived, that no qps-* XLF should ever exist, and which surfaces stay plain English on purpose, so the tester's rule stays exact.

  • The bracket fix affects nine link-bearing strings across five components. Two were confirmed end to end — the Team Collection paragraph live in a running Bloom, and the ePUB one through the localization API and unit tests — but not all nine were clicked through.
  • A brief flash of plain English during startup is normal and pre-existing: every React string renders its English default for a frame before its lookup returns. This locale is simply the first thing that makes it visible. It is written into the QA notes so a tester does not file it as a missing translation.

Where the migrated-pseudo-locale guard lives

Bloom sets up localization early in startup, and only later brings forward the settings from the previous version you had installed. That later step ends by re-reading the settings file, which threw away the correction the earlier step had made. So a tester who picked Pseudo-English in an alpha, and then upgraded to a newer beta or release build, would get a Bloom whose entire interface was mangled — and on those channels the menu does not offer Pseudo-English, so there was no way to switch back.

The fix re-applies the same guard immediately after the settings are brought forward, in one place that covers both of the later points where Bloom applies the stored language. Devin also suggested an alternative: move the settings migration to before localization is set up. That would remove the ordering problem at the source rather than compensating for it, but it moves a step that a lot of startup depends on, and the command-line entry points have their own constraints about what may run when — so it is a much riskier change for the same result. That is why leaving it as it stands is recommended.

The nine sentences that contain a link

Nine strings in Bloom put a clickable link inside a sentence, marked with square brackets in the string itself. Pseudo-English brackets the whole sentence too, and the two collided: the link swallowed the sentence and the outer bracket vanished. That is worse than an ordinary display bug here, because a sentence with no brackets is exactly the signal a tester is told means "this string was never internationalized" — so it would send them chasing a bug that is not there.

These are now handled by one shared helper with unit tests, and two of the nine were confirmed in the real app. The other seven (Copyright & License, Book Settings, the publish-upload terms, the custom-page-layout tooltip, the Adjust Timings dialog, and the second ePUB note) were not clicked through. They are listed in the QA notes on the card for a tester to check.
