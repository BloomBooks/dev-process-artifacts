What this PR is about

Problem

We have no way to see which of Bloom's on-screen strings actually go through localization. A string someone hard-coded, a placeholder that got mangled, a label the layout clips once it grows — all of it looks perfectly fine in English, and only surfaces when a translator or a user in another language hits it.

What the PR does

On the developer and alpha channels, the UI Language menu now offers Pseudo-English (i18n test). L10NSharp pseudolocalizes every lookup for the standard qps-ploc pseudo-locale by transforming the live English at lookup time — each vowel doubled and accented, the whole string bracketed, so Title Missing becomes [Tîitlée Mîissîing]. A tester then reads the problems straight off the screen: plain English means the string was never internationalized, a visible {0} or %0 means a broken placeholder, a missing ] means truncation, brackets mid-sentence mean the sentence is concatenated at runtime, and clipped layout means we can't cope with the ~30–40% growth real translations bring. No qps-* translation files exist or are ever written.

  • Takes L10NSharp 11.0.1, whose only breaking change (dropping the net461 target) cannot reach Bloom. All three co-located apps move together, because they share one L10NSharp.dll in the ship folder.
  • Program.SetUpLocalization turns the locale on for developer and alpha only, and GetDesiredUiLanguage refuses a stored qps-ploc on a channel that doesn't offer it — otherwise a setting carried over would leave a user with a mangled UI and no menu entry to escape it.
  • WorkspaceView names the locale itself (Palaso has nothing useful to say about a pseudo-locale) and puts it last in the menu rather than sorting it among real languages.
  • I18NApi pseudolocalizes the English fallback it returns for ids missing from the English XLIFF — otherwise those look exactly like hard-coded text, which defeats the exercise. It also stops the pseudo-locale defeating GetTranslation's sentinel, which had been handing a mangled sentinel to the user in the "requires a higher subscription tier" message.
  • Fixes bracket bugs the locale exposed: several UI strings mark link text as [see our research], and the code found the pair by taking the first [, which the locale's own wrapper brackets broke — swallowing whole sentences into links. Now anchored on the first ] via findLinkTextBrackets, with five call sites and the markdown link regex updated.
  • Keeps the locale out of the two places the available-languages list feeds book data rather than UI: the pre-translated content written into a new book, and the hint-bubble language chooser.
  • Adds an e2e test that a real Bloom offers the locale, plus unit coverage of the server-side fallbacks; and documents in DistFiles/localization/README.md which surfaces stay plain English on purpose, so the tester's rule stays exact.

Should we guard against compounding the pseudo transform?

Two reviewers independently raised the same concern about I18NApi. When a string id is in none of Bloom's three English XLIFF files, GetTranslationDefaultMayNotBeEnglish falls back to whatever the caller passed as the current text, and this PR then pseudolocalizes that. The transform is not idempotent, so if the text handed in had already been transformed on an earlier pass, the result compounds — [[Tîîitléée]] — and a tester would reasonably read that as a bug in the feature.

I traced every route and could not make it happen. The only caller that reads the DOM asks solely for keys absent from the front end's dictionary, and every answer is cached there, so a key's text is submitted at most once per document; later passes fill from the cache. The dictionary and the DOM only ever reset together, with a fresh document in English. The other two callers pass the book's own page label and never write the result back.

So this is not a known defect. It is a question of whether to spend a guard on a path that is one front-end refactor away from becoming reachable, in exactly the place a tester in this locale is looking.

Recommending Leave as is because it cannot currently occur, the cheap guard trades a real (if unlikely) false negative for a hypothetical false positive, and a [[ in the UI would be obvious and reported rather than silent. Its Devin thread stays open until you answer, and I will record whatever you decide there.
