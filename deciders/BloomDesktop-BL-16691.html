Decision 1

Every collection file gains an AllowCheckouts line

Answered: write the line only when checkouts are paused, with a comment explaining why. Applied in c4705dc62c, plus a test that the element disappears when checkouts are re-allowed and the collection still reads back as allowing them.

Bloom does not edit the collection settings file in place — whenever collection settings are saved it rebuilds the whole file from scratch. That is why this change has to write the new AllowCheckouts line out as well as read it: a setting that is read but never written would be silently erased the next time anything saved settings, quietly un-pausing checkouts for the whole team. (There is a unit test guarding exactly that.)

The side effect is that the line is now written for every collection, including the overwhelming majority that will never use the feature. So the first time anyone saves collection settings after upgrading, that collection's file changes. In a Team Collection, Bloom watches those files and pushes local changes up to the shared folder, so this one-off change travels to the team too. Nothing breaks — it is churn, not damage.

The recommendation is to leave it: every other true/false setting in that file (AllowNewBooks, IsSourceCollection, ShowBlorgLanguageQrCode and the rest) is written unconditionally, so making this one the single exception would be a surprise for the next person to read the file, and the churn is one-off per collection either way.

Decision 2 · open thread on the PR

A refused checkout can pop up an error report

Answered: handle the failure on both paths and refresh the book status. Applied in c4705dc62c; the PR thread is documented and resolved.

Bloom now refuses a checkout on the server side when checkouts are paused, as a backstop in case the button is somehow clickable. Devin flagged what happens when that backstop fires, and having checked it, it is worse than I first thought — there are two paths and neither tells the person what is going on.

Pressing the disabled button's normal path just clears the busy cursor, so the click appears to do nothing. But the checkout that Bloom posts after the registration dialog — the one that runs once someone saves an email address — is sent with no failure handling at all, and a rejected post with no handler ends up in Bloom's standard “something went wrong” problem-report window. So that person is told Bloom has a problem when in fact the administrator simply paused checkouts. I confirmed this by following the post through wrapAxios, which reports the error unless explicitly told not to.

How reachable is it? Narrow. The button is already disabled in that state, and the setting cannot change while Bloom is running, since collection settings are only read as the collection opens — so it needs the panel to be working from a snapshot taken before the setting took effect. But the registration path is precisely where that is most likely, because it posts without re-checking. This is also a defect this branch introduces: before the guard existed, that endpoint only failed on a genuine exception.

For your information

A typo in the setting pauses the team's checkouts

Answered: leave as is, and record the reasoning in the code. The comment is at the read site in CollectionSettings.Load.

Bloom reads true/false settings with a helper that hands back whatever the parse produced, and a failed parse produces false. So <AllowCheckouts>no</AllowCheckouts>, or a stray character, does not get ignored — it pauses checkouts for everyone. A missing line is still safely “allowed”, because in that case it is the default text that gets parsed.

This is inherited, not introduced: every true/false setting in that file has always behaved this way. It is called out here only because this is the first one where an administrator's typo is felt by the whole team at once, and because there is no screen to set it from — hand-editing is the only way in. It is written up in the QA notes on the card so a tester confirms the behavior rather than reporting it as new.

For your information

Where an administrator has to edit the setting

Answered: leave as is — it stays recorded on the PR and in the QA notes on the card.

In a Team Collection, editing your local .bloomCollection while Bloom is closed achieves nothing. On startup Bloom replaces the local settings files with the team's copies from the shared folder — “whatever wins in the repo wins everywhere” — so the edit is thrown away before anyone sees it. This cost us a round of confusion while testing the feature.

It sticks in two ways: edit the local file while Bloom is running, so the collection-file watcher pushes it up to the shared folder, or edit the copy inside the shared folder's Other Collection Files.zip directly. The first is confirmed working. This is pre-existing behavior for every collection-level setting rather than anything this change introduced, but since this setting has no UI at all, hand-editing is the only route in — so it is the first thing an administrator will hit. It is recorded in the PR description and the QA notes; the recommendation is to leave it there until there is somewhere real for administrator instructions to live.
