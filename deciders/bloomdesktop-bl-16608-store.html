Why these are worth doing now rather than later

1. uiMounted rides in the React snapshot, but no component reads it

uiMounted is a field on IToolboxUiState — the immutable snapshot React subscribes to. ToolboxRoot sets it true as it mounts and false as it unmounts. The only place that reads it is readerToolsModel.ts, twice (if (!isToolboxUiMounted()) return;), and it reads it imperatively through the accessor, not from a snapshot. No component renders anything from it.

Because it lives in the snapshot, setting it builds a new state object and notifies every subscriber — so ToolboxRoot’s own mount schedules a re-render of the toolbox for a fact nothing renders. In practice that is two extra renders in the life of the page, so the cost is conceptual rather than measurable: the snapshot is supposed to be what the UI is made of, and this is the one member that isn’t.

It would become a module-level let uiMounted = false beside theState, with the same two exported functions. About eight lines move; the two readers and the four call sites do not change at all. toolboxState.spec.ts has a test on the pair, which keeps working.

2. showToolboxChanged(wasShowing) is inverted at every single use

The one caller passes the negation of the checkbox:

showToolboxChanged(!this.checked);

and then every use inside the function negates it back:

"visibility\t" + (wasShowing ? "" : "visible")
if (openTool && wasShowing) { ...log "deactivating"... }
setToolboxVisible(!wasShowing);

The parameter names the state the toolbox was in before the toggle, so a reader has to invert it in their head at each use to work out what the function does. Since !wasShowing === this.checked, passing this.checked as nowShowing removes every negation and the body reads forwards: log "visible" when it is now visible, log “deactivating” when it is not, setToolboxVisible(nowShowing).

It is a four-line change in one function with one caller, and the two are in the same file. The check that it is right is that the suite still passes and the toolbox still hides and shows — and toolbox showing and hiding is the one thing a tester is certain to exercise.

3. setOpenTool refuses to the console — is that loud enough?

You asked for one path to open a tool that always does the right thing, and for a bad open to be refused and logged rather than thrown. That is what it does now: if the tool is not on offer, setOpenTool returns without changing anything and writes a console.error naming the tool asked for, what the toolbox is actually offering, and what to do instead.

You also wondered aloud about a toast in alpha. There is no browser→C# toast path in Bloom today — the only thing in that direction is a debug bridge — so a toast is not a line of code, it is a small new piece of plumbing. It would also be the first time this file needed anything outside itself.

Worth weighing against it: the condition is a programming error, not a user situation. It can only happen if someone writes a new way to open a tool and forgets to offer it first — and whoever does that is a developer, running a dev build, with the console open. AGENTS.md says not to be defensive about internal API misuse, which points the same way.
