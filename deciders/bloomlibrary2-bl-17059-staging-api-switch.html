What this PR is about

Purpose

Backend changes to the Bloom API (now: Cloudflare keeping copies of book files, bloom-core-supabase#15) reach staging-api.bloomlibrary.org well before production. Staging runs the backend's develop branch but forwards everything else to the same production services and data, so the real site, with real books, is the best place to try those changes. Until now the site could only call api.bloomlibrary.org. This PR lets a tester switch one browser to staging without a special build.

What the PR does

  • Opening any page with ?api=staging sends this browser's Bloom API calls to staging; ?api=prod switches back. The choice is remembered in this browser and read once when the site loads. Only those two values are accepted.
  • On localhost the staging calls go through a new /staging-api Vite proxy, so the switch works there too.
  • While staging is on, a "Staging API" banner with no close button floats at the bottom of every page. Its "Switch back" link changes only api in the address, keeping filters and date ranges.
  • The banner is a general OverlayBanner made from alpha's "Under Construction" message, which now uses it too: closable, raised above the staging banner when both show, and saying "alpha" instead of "next".

On phones, the staging banner covers the book reader's page slider

Devin found this (thread). The staging banner has no close button and sits at the bottom center of every page. The book reader fills the whole screen and has a page slider along the bottom. On a phone-width screen the banner covers the middle of that slider, so a tester can't tap there to jump to a page while staging is on. Only testers who turned staging on are affected. Wider screens and other pages are fine.
