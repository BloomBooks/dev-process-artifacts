What this PR is about

Problem

Bloom uploads books to, and logs in to, one of two web sites: bloomlibrary.org or dev.bloomlibrary.org. Until now the build decided this. A debug build used the development site; every other build used the production site, unless the person who started Bloom first set the BloomSandbox environment variable. A tester on an alpha or an internal beta build had no way to reach the development site, and a developer had to start Bloom from a shell to change sites.

What the PR does

  • Adds Use dev.BloomLibrary.org (restarts Bloom) to the top-bar context menu, with a tick when Bloom uses the development site.
  • Shows the item only on developer, alpha, unstable, and internal beta builds. Public beta and release builds never show it.
  • Keeps the choice for each user, but stores it only while it differs from what the build does on its own. If the user picks the site the build already uses, Bloom clears the stored choice, so BloomSandbox keeps control.
  • Restarts Bloom when the choice changes. The upload destination and the saved login belong to one run only, so a restart is the safe way to change them.
  • Asks the development launcher to restart Bloom when ./go.sh started it. Without this, Bloom’s own restart made the launcher stop the whole process tree, including the Vite server.
  • Ignores a stored choice on a build that does not show the item. User settings live in a folder named for the version, so a build without the item could otherwise obey a choice that it cannot change.

1. The words on the menu item

The item reads Use dev.BloomLibrary.org (restarts Bloom). The text in parentheses warns the user before the click, because Bloom closes and starts again as soon as the tick changes. It also makes this the longest line in the menu, and it repeats a warning that the user needs only once.

Notes

2. What the user sees if the restart does not happen

Bloom saves the choice first, then asks to be restarted. If the development launcher is absent and the attempt to start a new copy of Bloom fails, Bloom closes and nothing comes back. The choice is not lost, because the next start of Bloom uses the site that the user picked. The user still sees Bloom disappear with no message, and can believe that Bloom crashed.

Notes

3. How the code recognizes an internal beta build

The item appears on developer, alpha, and unstable builds through the property ApplicationUpdateSupport.IsDevOrAlpha, which is already there. Internal beta has no such property, so the new code searches the channel name for the text betainternal. That works today, because the channel name comes from the folder that holds the build. It stops working quietly if somebody renames the channel.

Notes

4. No automated test covers the new choice

The rule that selects the site reads Program.RunningUnitTests first and returns the answer of the build, so that a developer’s menu choice cannot change what a test run does. That guard also stops a unit test from reaching the new rule. Only the manual test ideas on the card cover it.
