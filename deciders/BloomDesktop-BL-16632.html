The race guard on the other branch

A button refresh asks the server whether the current text box has a recording, and works out which box to ask about at the moment it starts. If you change page while an answer is still in flight, that answer comes back describing a box you have already left, and gets applied to the box you are on now — telling the tool that a brand-new page's untouched text box has a whole-text-box recording. This is why the card's own repro steps (“record By Whole Text Box, add a new page, type”) only sometimes show the problem, and why it reproduced every time for the reporter but not for you: it depends on whether the answer beats the page change.

That defect pre-dates this PR and is not fixed here. The guard for it — each refresh takes a generation number and only the most recent one may apply what it hears back — lives on BL-16632-stale-button-state-answers with its own regression test. Left alone, that branch is invisible: no card, no PR, nothing to remind anyone it exists.

The tooltip doesn't match the button it explains

Separate from the bug, and older than this PR: the “By Sentence” radio button and the tooltip that explains why it is greyed out use different conditions. The button is greyed out only when the current box has a whole-text-box recording, but the tooltip appears whenever the box has any recording — so a box recorded by sentence shows “first use the Clear button to remove your recording” hovering over a button that is perfectly usable. And when a page has no text at all, that same wording appears, even though the real reason is that there is nothing to record; Bloom already has a “put the cursor in something recordable” message that fits, and uses it two controls further down.

This is exactly the confusing message the reporter photographed, so it is tempting to fix here; it is also untouched user-facing wording in a regression PR, which is your call rather than mine.

FYI — the tool now re-checks the page's text more often

Devin noted this twice, as an observation rather than a problem, and an earlier version of this report repeated its framing more darkly than the numbers deserve. Working out whether the page has anything recordable is one getElementsByClassName plus a text check per visible text box, and it now happens on every button refresh rather than at a few points. For scale: that same refresh already makes two HTTP round trips to the Bloom server per keystroke — updateMarkup runs on most keypresses and ends in a refresh, which asks checkForAnyRecording once for the page and once for the current box. The added DOM work is noise beside that. The QA notes still ask a tester to type continuously on a text-heavy page and watch for stutter.
