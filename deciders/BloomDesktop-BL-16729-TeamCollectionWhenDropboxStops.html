The one that mattered

After a disconnect part way through a session, every book in the collection would have looked like a book you had just made on this computer — no "checked out by" information, nothing showing as being in the Team Collection at all.

The stand-in collection Bloom swaps in when it disconnects answers book-status questions out of the local status files, and only trusts a local status whose collection id matches its own. Nothing sets that id on a collection object after the collection has been opened — WorkspaceModel calls SetCollectionId once. Until now that was harmless, because disconnecting only ever happened during startup, early enough for that one call to reach the stand-in. Making disconnection possible mid-session is exactly what this PR adds, so the stand-in built at that point kept a null id and every book's status comparison failed.

Devin found it; CompleteDisconnect now carries the id across (TeamCollectionManager.cs:649). Covered by MakeDisconnected_MidSession_StandInInheritsTheCollectionId, which I checked fails without the fix. The QA notes on the card now ask a tester to click through books while disconnected.

1 · Repeat "you may have missed changes" warnings are swallowed DEVIN · SEVERE

Devin, mirrored as an open thread · TeamCollection.cs:664

When the shared folder delivers a very large batch of changes at once, Bloom can be told that more happened than it could take in, and it warns: "Bloom may have missed some changes your teammates made. Please click Reload Collection." The user reloads, and all is well.

If it happens again later in the same session, they get no second warning. The message log treats an error carrying the same id as a duplicate and drops it, and it looks across the whole session rather than since the last reload — so the user is left believing they are up to date when Bloom has just told itself otherwise.

That de-duplication is deliberate and predates this branch: the comment on IsRedundantMessage explains that some repo problems repeat constantly and would otherwise flood the log. What is new is that this PR writes this particular message from the overflow path, where "it happened again, after you reloaded" really is new information rather than noise.

2 · Teammates' checkouts stay invisible after a late folder arrival DEVIN · SEVERE

Devin, mirrored as an open thread · FolderTeamCollection.cs:1211

In the narrow case this PR adds support for — the shared folder's Books arriving late, while Dropbox is still delivering it — Bloom starts watching part way through the session and then scans to work out what it missed. That scan notices books that were added or whose content changed, but not books a teammate merely checked out while nobody was watching. Those books keep showing as available to check out until something else touches them or the user reloads.

The cause is that the scan asks HasBeenChangedRemotely, which compares book checksums, and a checkout does not change a book's checksum — it changes the status stored alongside it. The live watcher path has no such gap, because it reacts to the file write itself.

The direction of the error is the unsafe one: a book shown as available that someone else has out is how two people end up editing the same book.

3 · A failed catch-up scan never runs again DEVIN · NON-SEVERE

Devin, mirrored as an open thread · FolderTeamCollection.cs:1188

When the Books folder turns up late and Bloom starts watching it, it then scans to work out what it missed. If that scan's directory listing fails — the share blinks out at exactly that moment — the scan gives up. The watcher itself is running by then, so future changes are picked up fine; but the catch-up never runs again, so whatever was already sitting in the folder stays unannounced until the user reloads.

Narrow window, bounded damage, and not quite a one-liner to fix: the flag that would make the heartbeat retry is the same one that controls whether the watcher gets created, and the watcher has by then been created successfully, so retrying needs a little more care than flipping it back.

4 · A vanishing folder can throw out of StartMonitoring DEVIN · NON-SEVERE

Devin, mirrored as an open thread · FolderTeamCollection.cs:1074

StartMonitoring checks that the Books folder exists and then calls StartBooksWatcher, which assigns the watcher's Path. That assignment throws if the folder has gone in the meantime. The deferred-retry path was taught to catch exactly this in an earlier round of Devin review; the startup path was not, so there the exception escapes without the failure being reported and without Bloom going Disconnected.

The window is two adjacent statements wide, which is why this is a question rather than something I just fixed — the same try/catch treatment would close it, but it is one more piece of defensive code in a change already under fire for size.
