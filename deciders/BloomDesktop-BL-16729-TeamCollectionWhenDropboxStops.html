Why not the single whole-folder watcher

You asked which I thought was better. Watching the whole Team Collection folder and filtering would notice the Books folder instantly and would need no catch-up scan — both real advantages — but one watcher means one notification filter. The Other folder would start receiving file-name and directory events it does not get today, and that path runs into the check that can block in a modal and shut the user out of the collection when a teammate raises the minimum Bloom version. It would also make the debouncing helpers, which are per-watcher-per-event-type, share state between the two kinds of change, and it would add the Lost and Found folder plus Bloom's own temporary write traffic to the same notification buffer.

That puts the risk on the path that works today for every collection, in order to fix a case that only affects a joiner mid-sync. The catch-up it saves turned out to be about ten lines reusing what was already there.

Manual testing settled a question I had been asserting

Two rounds of testing, and the second produced a definite answer that changes how this feature should be described.

The near-instant path does not fire. With a Team Collection on a USB stick, physically pulling the drive out produced this in the event log:

11:32:00  periodic check found a problem (TeamCollection.MissingRepo); looking again in 15s
11:32:15  periodic check confirmed a problem (TeamCollection.MissingRepo); disconnecting

No watcher-failure line at all. Windows never told Bloom the folder had become unwatchable, so the once-a-minute check did the entire job — in exactly its designed timing. I had been describing instant detection as the headline mechanism; it is not, and the honest number is about 75 seconds however the folder goes away. The notes on the card now say so.

The watcher subscription stays. It costs nothing, it is the documented mechanism, it is how a notification-buffer overflow is detected — a real and separate case — and it may well fire in situations other than media removal. It is simply best-effort, which I should have said rather than promising seconds.

The first round's mistake was mine. I had recommended subst as the quick way to simulate a lost drive. Removing a subst letter does not invalidate handles that are already open, so Bloom keeps watching the real folder underneath. It only ever exercises the periodic check — which, as it turns out, is the path that matters anyway.

And chasing it flushed out a real bug. Looking up a window to marshal to reached Application.OpenForms, which is not thread-safe, from outside a try — and every caller is on a watcher's thread or the timer's. Had it thrown, the disconnect would have been silently discarded and Bloom would have carried on looking connected indefinitely, since every later check would hit the same thing. Fixed; the marshalling no longer touches Application.OpenForms at all.

The timing was re-confirmed, not just inherited

You had already chosen to leave the check at 60 seconds with a 15-second confirmation. That decision was made believing the watcher covered vanished folders instantly and the periodic check was a backstop for Dropbox. Since it is now known to be the only mechanism that fires, the question was put again with that correction, and the answer was the same: leave it.

The reasoning holds up. What this card fixes is going hours unaware; nobody loses work in 75 seconds, they just see slightly stale status for a minute. And the confirmation delay cannot usefully drop below 15 seconds anyway, because the Dropbox reachability answer is cached for 10 — a faster second look would simply return the first one and confirm nothing.

A justification I had to withdraw

The deferred-watcher work earlier in this run was justified on the grounds that a joiner's Dropbox might not have delivered the shared folder's Books sub-folder yet. Testing showed that is not a real state: you cannot join a collection in that condition at all, because the join fails earlier on the missing folder.

What is genuinely reachable is narrower — reopening a collection already joined, at a moment when Books is absent, such as while Dropbox restores the shared folder onto a new machine. Monitoring starts on every collection open, not only at join. And the sync still fails and still tells the user in that case; what the retry avoids is having to restart Bloom once the folder arrives.

Kept after weighing it, on the reasoning that its failure mode is inert and the same restructure independently stops a missing Books folder from silently skipping the Other watcher. The code comment and the QA step now state the real reachability instead of the version I had assumed, and the QA step's expected result is corrected too — it said the collection would open normally, when in fact it reports a sync error.

Investigated and dismissed: "the administrator has paused checkouts"

After the Dropbox test, restarting Dropbox and reloading the collection left Bloom saying an administrator had paused checkouts. That turned out not to be caused by this work, and not to be a bug at all.

The shared folder's own collection settings have carried <AllowCheckouts>False</AllowCheckouts> since 20 August, three weeks before this branch existed — almost certainly left behind by testing the administrator-pause feature, which has no UI to switch it back off. Bloom was reporting a real setting. Reopening a collection syncs that setting down from the shared folder, which is exactly what that feature is for.

Two things ruled out along the way. The pause feature is entirely on Version6.5 already and this branch does not touch it — no AllowCheckouts lines in the diff, and no changes to the collection settings or the status panel. And the event log contains no "AllowCheckouts changed remotely" line, which is what the code writes whenever it changes that value, so nothing altered it during the session; it was already false.

It also looked at first as though a restart cleared the message and a reload did not, which would have been a genuine UI-refresh bug. It did not: the message only ever renders on a book that would otherwise be available to check out, so a checked-out book looks normal even while checkouts are paused. The setup section of the QA notes now warns testers about this, because a paused collection blocks most of the script and there is no UI hinting at why.
