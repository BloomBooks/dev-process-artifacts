Three pre-existing bugs were fixed along the way

  • Three stuck busy flags, all the same shape. _writeBookInProgress (two sites) and _syncIsRunning were each set before the work and cleared only where it finished normally, so any throw left them set for the rest of the session. That already suppressed change notifications; and because the new heartbeat asks "are we busy writing?" before each check, a stuck flag would have silently switched the whole feature off — in precisely the flaky-share conditions that make those writes throw. All now clear in a finally.
  • MakeDisconnected leaked the collection it replaced, nulling CurrentCollection without stopping its watchers and leaving Dispose unable to reach it — so the abandoned collection went on watching and queueing changes indefinitely.
  • A failed book-status fetch rendered the book as available for checkout. CollectionsTabBookPane.tsx set disconnected where the interface field is isDisconnected.

Why not the single whole-folder watcher

You asked which I thought was better. Watching the whole Team Collection folder and filtering would notice the Books folder instantly and would need no catch-up scan — both real advantages — but one watcher means one notification filter. The Other folder would start receiving file-name and directory events it does not get today, and that path runs into the check that can block in a modal and shut the user out of the collection when a teammate raises the minimum Bloom version. It would also make the debouncing helpers, which are per-watcher-per-event-type, share state between the two kinds of change, and it would add the Lost and Found folder plus Bloom's own temporary write traffic to the same notification buffer.

That puts the risk on the path that works today for every collection, in order to fix a case that only affects a joiner mid-sync. The catch-up it saves turned out to be about ten lines reusing what was already there.

Still on your list: run it in a real Bloom

The one thing neither the tests nor a reviewer can settle. Nothing in this PR has been exercised in a running Bloom: no share has been pulled out from under one, no Dropbox has been killed mid-session, and nobody has watched the notification appear. The quoted timings — a second or two for a vanished share, about seventy-five seconds for Dropbox — are intended, not observed.

The script on the card covers both failure modes and, more importantly, the negative cases: a collection that is working must never be disconnected by mistake, because there is no automatic way back from that. It now also covers the joiner case added this round, where the shared folder arrives after Bloom has already opened the collection.
