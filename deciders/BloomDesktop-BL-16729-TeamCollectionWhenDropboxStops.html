What changed in this run

Four commits reached the remote in this run; the branch had none of them before.

  • 26dbdcd75 — the collection history file is no longer written while the message lock is held. Appending to log.txt used to happen inside the lock that guards the in-memory message list, so if anything else on the machine had that file open, every reader of Team Collection status waited out RobustFile's seconds of retrying — including the Team Collection button, which is read on the UI thread. Messages are now queued under that lock (which is what keeps the file in the same order as the in-memory log) and written outside it under a separate one. Ordinary appends give up after a couple of quick tries and carry anything unwritten to the next attempt; a new Flush() at shutdown does the stubborn retry instead. This was John's review comment, and the design is essentially the one he sketched.
  • 0a69a6001 — books deleted while we had no watcher are now noticed. When the shared folder's Books sub-folder arrives late, the catch-up only looked at books that were present, so a book a teammate had deleted meanwhile sat in the local collection until a restart. It now raises the same deletion event the watcher would have, and leaves the question of whether the book really was deleted to the existing tombstone check. Also John's comment; renames turned out to be handled already.
  • f7bba890e — merge of master (62 commits), folded in before publishing so the gate ran against the code as it will actually merge.
  • f38cfff5c — two real bugs Devin found, both on the disconnect paths. A Books folder that vanished again between the once-a-minute check and the work reaching the UI thread would have thrown out of a posted callback with nothing to catch it, taking Bloom down (FolderTeamCollection.cs:1127). And the stand-in collection Bloom creates when it disconnects has a message log of its own that nothing ever disposed, so its “you are now disconnected” messages would never have been flushed — a regression from the first commit above (TeamCollectionManager.cs:734). Both fixed, the second with a regression test.

1. Should a Team Collection be disconnected when the computer has no network, even if its folder is local?

Devin raised this and I deliberately have not changed it, because it is a question about when Bloom should declare a collection disconnected rather than a clear-cut defect.

The once-a-minute connection check asks Windows whether any network is available at all, and if the answer is no it returns “No network is available on this computer” (FolderTeamCollection.cs:1875). That test runs before anything asks whether this particular collection needs a network, and a few lines earlier Bloom has already confirmed the shared folder is right there and readable.

So picture someone whose Team Collection folder is on a local drive, a USB stick, or a Dropbox folder that simply has not synced yet, working on a laptop with the Wi-Fi switched off. The folder is perfectly readable and everything works. Before this branch that verdict was only reached when something happened to ask; now the heartbeat asks every sixty seconds, so two consecutive checks — about seventy-five seconds — would take that user from working normally to Disconnected on their own machine, with no way back except “fixing” a problem that was never affecting them and reloading the collection.

How much this matters turns on something the code cannot tell me: whether anyone really runs a Team Collection that does not need the network. If every real collection lives on Dropbox or a network share, this is close to theoretical.

2. FYI — a mock-only constructor could trip over the new shutdown flush

The local review noticed this, and it is not a bug today. TeamCollection has a parameterless constructor that exists only so Moq can subclass it, and it leaves the message log null. Disposing now calls Flush() on that log unconditionally, so a future test that disposed such a mock would get a null-reference error. Nothing disposes one today, and production cannot reach that constructor.

I left it alone because the project's own guidance is to fail fast rather than add defensive null checks, and a guard here would be exactly that. It is recorded so whoever next writes a test against a mocked FolderTeamCollection is not puzzled by it.
