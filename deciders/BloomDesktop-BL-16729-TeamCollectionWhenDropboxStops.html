Three pre-existing bugs were fixed along the way

  • Three stuck busy flags, all the same shape. _writeBookInProgress (two sites) and _syncIsRunning were each set before the work and cleared only where it finished normally, so any throw left them set for the rest of the session. That already suppressed change notifications; and because the new heartbeat asks "are we busy writing?" before each check, a stuck flag would have silently switched the whole feature off — in precisely the flaky-share conditions that make those writes throw. All now clear in a finally.
  • MakeDisconnected leaked the collection it replaced, nulling CurrentCollection without stopping its watchers and leaving Dispose unable to reach it — so the abandoned collection went on watching and queueing changes indefinitely.
  • A failed book-status fetch rendered the book as available for checkout. CollectionsTabBookPane.tsx set disconnected where the interface field is isDisconnected.

Over to you

1. A Team Collection with no Books folder still reports itself as healthy

A Team Collection's shared folder contains a sub-folder called Books, which is where the actual book files live. When Bloom starts watching a collection, it checks for that folder; if it isn't there, Bloom quietly gives up on watching for book changes and carries on. Nothing is logged and the user is told nothing.

That behaviour predates this PR. What Devin points out is that the change arguably makes the false reassurance stronger: the new once-a-minute connection check looks at the shared folder, the network, and Dropbox — all of which are fine in this situation — and so keeps confirming that all is well, while book changes from teammates cannot possibly arrive. Devin rates it severe.

When we planned this work you were offered a fix for exactly this and chose to leave it out, on the grounds that a first-time join legitimately passes through this state while the folder is still syncing. So this is a straight re-ask now that a reviewer has pushed back, not new information.

Devin found a second way into the same hole. When somebody creates a Team Collection, Bloom sets the collection up — including starting the watchers — before it publishes it as the current collection. So if a watcher fails to start during that window, the failure had nowhere to be reported and was dropped entirely. I have made that case log and report to Sentry rather than vanish, but whether it should disconnect is the same question as above. The two differ in likelihood: this one needs Windows to actually refuse the watcher, which is rare; the missing-Books case happens routinely on a still-syncing join.

Both threads are open on the PR awaiting this decision: missing book watcher and new collection setup. Whatever you choose applies to both.

2. Nothing here has been run in a live Bloom

Everything in this PR is verified by unit tests and by the compiler. Nobody has pulled a network share out from under a running Bloom, or quit Dropbox mid-session, and then watched what actually happens on screen.

So the parts that are genuinely unproven are the ones only a real run can show: whether the notification actually appears and reads well at the moment of failure, whether clicking it opens the Team Collection dialog as intended, whether the quoted timings (a second or two for a vanished share, about 75 seconds for Dropbox) hold in practice, and whether the once-a-minute check — which contacts dropbox.com with a five-second timeout — ever makes the interface stutter.

The QA notes on the card lay out a full manual script, including the negative tests that matter most (a working collection must never be disconnected by mistake).

3. For information: this PR grew a thread-safety fix you did not ask for

No action needed. Bloom keeps a log of Team Collection events — what you see in the Team Collection dialog. Devin found that this log could be written from two threads at once, which could duplicate entries or throw an error; in a file-watcher callback that error would have taken Bloom down.

Fixing it properly took two goes. First I made the log lock internally, and said in the commit that callers still getting the live list was theoretical. Devin then showed it was not: two of the dialog's own API endpoints are deliberately served off the UI thread and read that list directly, so a message arriving while the dialog was fetching its log could genuinely have failed the request with "Collection was modified". The log now hands out a copy instead.

Worth knowing because it is scope this card did not ask for — it is a pre-existing latent bug in shared code, not part of noticing a lost folder. It is here because the new file-watcher path made it reachable from a new direction. Only one production caller reads that property, so the change is contained, and the full C# suite is green.

4. For information: how long Bloom waits before giving up

No action needed unless the numbers feel wrong to you. Bloom re-checks the connection every 60 seconds; if a check fails it looks again after 15 seconds and only disconnects if that second look also fails. So a genuine Dropbox outage is noticed in roughly 75 seconds, while a brief network blip is ridden out.

The 15-second gap is not arbitrary: Bloom caches its "can I reach dropbox.com" answer for 10 seconds, so a faster re-check would just return the first answer and confirm nothing. A share that physically vanishes is still caught immediately by a different mechanism, so this delay only applies to the problems Windows does not announce.
